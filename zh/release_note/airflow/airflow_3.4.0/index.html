airflow 3.4.0

📦PyPI：https://pypi.org/project/apache-airflow/3.4.0/ 📚 文档：https://airflow.apache.org/docs/apache-airflow/3.4.0/ 🛠 Release Note：https://airflow.apache.org/docs/apache-airflow/3.4.0/release_notes.html 🐳 Docker 图片：“docker 拉 apache/airflow:3.4.0” 🚏 约束：https://github.com/apache/airflow/tree/constraints-3.4.0

重大变化

任务循环（#73005、#74222、#74275、#74345）

Airflow 3.4.0 引入了任务循环（AIP-111）：一个装饰任务组可以重复多次 使用“.loop()``. A conditional loop works like a ``do ... while”循环在运行时决定的时间 - 主体至少运行一次，并且“until”条件决定何时停止，边界为 max_iterations。每次迭代都可以使用前一次迭代的结果，并且迭代运行一次 一个又一个（迭代中的任务仍然可以并行运行）。保留重试尝试 在每次尝试的 UUID 下，因此每次迭代的数据都会被保留并可以有选择地清除。

详细使用说明请参见：doc:/authoring-and-scheduling/loops。

..注意:: 降级到 3.4.0 之前的任何版本可能会很慢，具体取决于 3.4.0 的数量 升级后已写入的 XCom 行。升级已在 300m排XCom桌子，所以请不要担心升级时间（我们确保 XCom 数据在迁移过程中没有被触及或读取以保留它 快）。

这是因为此版本包含开始存储新 XCom 的迁移 xcom_v2 表中的行，为了降级，我们必须将这些行移过来 到旧表，如果不复制就无法做到这一点 写入xcom值。

当发现无法映射回的数据时，降级将拒绝继续 安全。每个迁移单独提交，因此后面的 3.4.0 迁移 此时已被逆转：修复数据并重新运行 降级，或运行“airflow db migrate”返回到3.4。

在 MySQL 上，这些检查后的失败会使架构部分降级， 因为MySQL无法回滚DDL。在尝试之前进行备份 建议降级MySQL，这样在这种情况下可以恢复。

非 Python Dags 的 Dag 导入器 (#72369、#73728、#73853、#74020、#74084、#74333、#74586)

Airflow 3.4.0 可以用其他语言编写整个 Dag - 计划、任务和依赖项 比Python。 AIP-85 在任务 SDK 中添加了一个可插入的 Dag 导入器，它教导 Dag 处理器 识别“.py”之外的源格式：每种格式注册一个导入器，处理器运行 匹配语言运行时，生成的 Dags 在 Airflow 中显示，如 Python Dags。格式 其上包含 TypeScript、Go 和 Java 语言 SDK 以及本机 YAML Dag 格式（a .yaml file with a $schema 标记，根据模式进行验证并内置到实际运算符中， 具有显式模板）。 Dag Importer 框架和语言 SDKs 在 3.4 中是实验性的 他们的 API 可能会改变。

详细使用说明请参见：doc:/administration-and-deployment/dag-importers。

在 BaseExecutor.executor_queues 下统一执行器工作负载队列 (#63491)

执行器工作负载状态现在存储在统一的“BaseExecutor.executor_queues”映射键上 通过“WorkloadType`` and scheduled through ``trigger_workloads”。之前的每类型属性 和入口点（queued_tasks, queued_callbacks, supports_callbacks, trigger_tasks， order_queued_tasks_by_priority) 和 Airflow 3.3 连接测试表面折叠成 此映射并保留为向后兼容的垫片，发出“RemovedInAirflow4Warning”（将 在 Airflow 4.0 中删除）。树外执行器应声明“supported_workload_types”并且 实施“trigger_workloads”。连接测试现在可以在相同的心跳下进行 预算作为任务并优先考虑。参见 #63491 <https://github.com/apache/airflow/pull/63491>_ 获取完整的迁移指南。

psycopg3 现在是默认的 Postgres 驱动程序 (#68496)

psycopg3 (psycopg) 现在是元数据数据库的默认驱动程序，用于同步和 异步引擎，取代 psycopg2 和 asyncpg。裸露的“postgresql://”（或遗留的 postgres:// / postgres+psycopg2://) sql_alchemy_conn 被重写为 postgresql+psycopg://, and the derived async URL uses postgresql+psycopg_async://时 psycopg3 已安装（否则回退到 asyncpg）。 Airflow 也会禁用 psycopg3 服务器端语句准备（prepare_threshold = None），以便元数据数据库正常工作 交易模式 PgBouncer 后面的框，推荐的生产设置。保留 psycopg2 或 asyncpg，安装额外的apache-airflow-providers-postgres[psycopg2] / [asyncpg] 显式配置连接；有关详细信息，请参阅#68496 和#69469，包括如何重新启用 声明准备。

资产触发的 Dags 默认为每个事件创建一次运行 (#68517)

单资产计划和资产 OR 表达式现在为每个事件创建一次 Dag 运行，而不是 在一次运行中消耗所有排队的事件。这也适用于“AssetOrTimeSchedule”和 PartitionedAssetTimetable。

要保留批处理，请设置“batch_asset_events=True`` on the timetable or enable ”[调度程序] batch_asset_events“ 并重新解析受影响的 Dags。已经序列化的时间表没有这个 选项保留其之前的批处理行为，直到重新解析。

需要多个事件的时间表，包括“schedule=[a, b]”、资产 AND 表达式和 使用“RollupMapper”分区时间表，默认继续批处理。显式设置 这些时间表的“batch_asset_events=False”会引发时间表验证错误。
