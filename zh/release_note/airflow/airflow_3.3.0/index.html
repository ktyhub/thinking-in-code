airflow 3.3.0

小版本 发布时间2026年7月6日 来源apache/airflow 英文原文

airflow 3.3.0

📦PyPI：https://pypi.org/project/apache-airflow/3.3.0/ 📚 文档：https://airflow.apache.org/docs/apache-airflow/3.3.0/ 🛠 Release Note：https://airflow.apache.org/docs/apache-airflow/3.3.0/release_notes.html 🐳 Docker 图片：“docker 拉 apache/airflow:3.3.0” 🚏 约束：https://github.com/apache/airflow/tree/constraints-3.3.0

重大变化

资产分区（#64571、#65447、#66030、#66848、#67184、#67475、#67716、#68978）

Airflow 3.3.0 以 3.2.0 中引入的资产分区为基础，大幅扩展了资产分区的方式 单个上游资产事件扇出到分区的下游 Dag 运行。新的分区映射器 — RollupMapper (many-to-one), FanOutMapper (one-to-many), and FixedKeyMapper + SegmentWindow（分类汇总）- 由时间窗口（日/周/月/季度/年）和 wait_policy (WaitForAll or MinimumCount(n)) 来控制分区何时运行。窗户 可以及时向前或向后扇出，并且每个上游事件的总扇出受新的限制 [scheduler] partition_mapper_max_downstream_keys 配置（每个映射器均可配置）。气流 3.3.0 还添加了“PartitionedAtRuntime”时间表，它让 Dag 声明其分区键 在运行开始时分配，而不是从上游事件映射。

详细使用说明请参见：doc:/authoring-and-scheduling/assets。

任务和资产状态存储（#65759、#66073、#66160、#66463、#66586、#66859、#67041、#67292、#67319）

Airflow 3.3.0 引入了一流的任务和资产状态存储 (AIP-103)。任务可以持续存在 任意键值状态在重试后仍然存在并通过新的“task_state_store”访问器运行，以及 资产可以通过“asset_state_store”携带自己的状态——两者都可以从任务 SDK 获得。状态被保留 默认情况下在元数据数据库中，或在自定义工作端后端中（[workers] state_store_backend），通过定期垃圾收集和可选的支持每个键保留 clear_on_success，可通过核心 API 和执行 API 完全管理。

详细使用说明请参见：doc:/core-concepts/task-and-asset-state-store。

可插入重试策略 (#65474)

任务重试行为现在是可插入的 (AIP-105)。除了固定的“retries”计数之外，您还可以 附加自定义重试策略来决定是否以及何时重试任务，从而启用诸如 仅在特定异常时重试或根据自定义逻辑进行后退。

详细使用说明请参见：ref:concepts:retry-policies。

语言任务 SDK（Java 和 Go）（#65958、#67161、#67635、#67699）

Airflow 3.3.0 添加了一个协调器层 (AIP-108)，可以编写单独的任务实现 使用非 Python 语言，而 Dag 及其调度保留在 Python 中。在 Dag 中声明了一个任务 与“@task.stub(queue=...)”；工作人员将其路由到配置的协调员 （JavaCoordinator for JVM languages, ExecutableCoordinator 用于独立的本机二进制文件 例如 Go），在语言运行时运行任务并代理变量、连接和 XCom 通过执行 API。

..警告::

协调器层和 Java/Go SDK 在 3.3.0 中处于实验阶段，将来可能会发生变化 基于用户反馈的版本。

详细使用说明请参见：doc:/authoring-and-scheduling/language-sdks/index。

清除、重新运行和回填的 Dag 捆绑版本 (#63884)

新的“rerun_with_latest_version”设置控制是否清除、重新运行或回填 Dag 运行 使用最新的捆绑版本或初始运行的原始版本。默认已解决 按优先级：显式请求参数/CLI 标志，然后是 Dag 级别 rerun_with_latest_version， 然后[core] rerun_with_latest_version, and finally False for clear/rerun and True 回填（保留历史行为）。 Airflow 2.x 始终使用最新代码重新运行； 3.x 引入了默认为原始版本的捆绑版本控制，此设置为用户提供了控制权。

有关完整详细信息，请参阅：doc:/administration-and-deployment/dag-bundles。

提供程序示例 Dags 作为专用捆绑包 (#66161)

现在可以通过“ProvidersManager”发现提供商发行版提供的示例 Dags，并且 注册为他们自己的 Dag 捆绑包——每个提供商一个，名为 apache-airflow-providers-<distribution>-example-dags (or <distribution>-example-dags 为 第三方提供商）。 [core] load_examples 选项仍然控制它们是否注册。 REST API clients 为提供商提供的示例 Dags 过滤了“bundle_name`` by ``"dags-folder"” 必须更新为新的每个提供商捆绑包名称； Dag 标识符未更改。

远程日志记录解析与 airflow.logging_config 解耦 (#67056)

远程任务日志处理程序解析现在由共享“airflow_shared.logging.factory”拥有 模块并应用单一的、明确定义的优先级：

  1. 用户自定义 [logging] logging_config_class exporting REMOTE_TASK_LOG / DEFAULT_REMOTE_CONN_ID（现有的自定义配置继续工作）；
  2. ProvidersManager scheme dispatch — the scheme of [logging] remote_base_log_folder 选择一个 提供者RemoteLogIO class, instantiated via a no-argument from_config()类方法；
  3. 过渡遗留后备读取“airflow_local_settings.py”（将在 Airflow 4.0 中删除）。

airflow.logging_config.load_logging_config is deprecated (it now emits DeprecationWarning 和 委托给新的私人助手），并且“configure_logging”不再急切地解析远程 处理程序 - 第一次使用时解析是惰性的。注册了“remote-logging:”区块的提供商却这样做了 不实现“from_config”将跳过并出现警告并进入旧路径。

迁移：用新的替换对“airflow.logging_config.load_logging_config()”的直接调用 帮助者，并拥有提供者远程日志句柄
