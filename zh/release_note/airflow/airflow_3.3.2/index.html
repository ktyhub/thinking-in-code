重大变化

回填端点不再透露 Dags 中存在哪些回填 ID

在其路径中命名回填的四个路由 - GET /backfills/{backfill_id} 和 pause, unpause and cancel 路线 - 解决了他们授权的 Dag 每当路径的 id 与任何行都不匹配时，就会从请求中提供的“dag_id”中反对。 调用者无法看到未知的 id 和 Dag 上的回填，因此得到不同的答复， 它枚举 Dags 中的回填 ID。

现在，路径中指定的回填是这些路由唯一授权的内容。

行为改变：

  • 请求对调用者现在无法读取的 Dag 进行回填会返回“404” (Backfill not found) — 未知 id 得到的相同响应 — 而不是 403 returned before. A caller who can read the Dag still gets 403 用于写入 他们不被允许制造。
  • 请求正文中的“backfill_id`` in the path is never authorized against a ``dag_id” 或查询字符串。 GET /backfills, POST /backfills and POST /backfills/dry_run 在他们的路径中指定没有回填并继续授权请求。
  • 现在，所有四个路由都以相同的详细信息“Backfill not found”回答未知 ID。 之前回答的“pause``, ``unpause`` and ``cancel”路线 Could not find backfill with id {backfill_id}. Clients matching on detail 必须更新。 (#71113)

显式凭证现在优先于会话 cookie

get_user() 被写入为首选显式不记名令牌，然后是 OAuth2，然后是 会话 cookie，但只要存在 cookie，就无法达到该优先级。 JWTRefreshMiddleware 运行 首先，单独从“_token”cookie 解析用户并将其标记在 request.state, and get_user() 在查看之前返回该缓存用户 明确的凭证。每个核心-API 路由上的有效订单都是 cookie over bearer。

因此执行的请求携带会话 cookie 和显式凭证， 并被记录在审计日志中，作为 cookie 的主体而不是身份 client 呈现。现在，仅当请求不包含任何内容时，才会尊重缓存的用户 明确的凭证。

行为改变：

请求携带 both _token cookie and an Authorization: Bearer 标头

现在被解析为不记名代币的主体，之前它被解析为
饼干的。这同样适用于与 OAuth2 令牌组合的 cookie。

当有效的“`_token`” cookie 伴随它时。之前cookie默默地接管了
并且作为 cookie 的主体，请求成功；失败现在已经很响亮了。

携带单个凭证的请求不受影响。仅保留 Cookie 的浏览器会话

``JWTRefreshMiddleware`` 的令牌刷新行为不变。
