DeepTutor v1.5.16

DeepTutor v1.5.16 Release Notes

发布日期： 2026.08.22 v1.5.15 在图书阅读器下方添加了一个捕获收件箱，这样做可以阻止其翻页。这个问题在这里得到了修复，还有一个新的连接知识源——一个由其自己的附加组件填充的 MarginNote 4 库——以及一系列只能通过特定网关访问的故障：工具调用 ID 一直增长，直到提供者拒绝它们，嵌入因我们故意省略的参数而被拒绝，以及仅在您命名了正确的绑定时才适用的温度限制。直接插入——无需迁移，无需重新索引。

新消息

MarginNote 4 作为知识库

连接一个库，MN4 插件会将您的笔记、摘录、卡片和思维导图节点推送到其中 - 无需上传，无需索引，也不会从 MarginNote 中复制任何内容。从库的 设备 选项卡配对设备，将一次性令牌粘贴到附加组件中，然后同步逐渐到达 DeepTutor 拥有的商店。 打开该库可以在其自己的七个工具上运行，而不是在 rag 上运行：搜索摘录和注释文本、读取单个对象、按类型列出、遍历文档的子项、跟踪链接、按标签过滤以及读取思维导图卡。聊天循环将轮流交给他们，就像处理黑曜石保险库一样，因为没有索引的库没有任何可检索的块。 由 @evan188199-tech 作为 #931 贡献。这是第一阶段——只读导航；已计划回写。

书页又翻了

捕获收件箱作为读者弹性行的第二个子项登陆，而不将该行设为弹性列，因此 PageReader 的 h-full 折叠为 auto：正文停止滚动，翻页页脚 cli 完全从视图中消失。一行布局修复；我们运行的每个门在回归过程中都是绿色的，因为这里没有任何东西对类型或测试可见。

流式工具调用 ID 停止增长

OpenAI 兼容提供商前面的路由器可能会在每个增量块上重新发送整个工具调用 id。三个核心站点附加它而不是分配它，因此 id 每个块增长一个副本 - #937 看到 47,241 个字符 - 并且超过提供者的 64 个字符上限，每一轮都会以 Invalid 'messages[i].tool_calls[0].id': string too long 死亡，表现为“我无法从模型输出中产生有用的响应”。 name 在两个站点上都有相同的缺陷，该缺陷潜伏在该网关上，并且对任何重复该名称的站点都是致命的。现在，三个站点共享一个累加器：id 和 name 整体到达并进行分配，arguments 分段到达并连接。

模型限制遵循模型，而不是路线

Kimi 模型锁定服务器端温度并拒绝使用 HTTP 400 的显式值。对此的覆盖自 v1.5.5 之前就已存在，但它是从配置绑定的规范中解析的 - 因此它从未为 #938 触发，后者做了普通的事情并将 binding="openai" 指向 Moonshot。路由不是强制执行限制的，因此路由不再决定：当配置的规范说明了有关模型的内容时，它获胜，否则模型自己的供应商规范会回答。每个模型固有的覆盖都以同样的方式在通用绑定后面丢失。

嵌入从需要 encoding_format 的网关恢复

ModelScope 将缺失的 encoding_format 读取为 '' 并拒绝请求（#934）；当该字段“存在”时，SiliconFlow 会拒绝它，这就是我们省略它的原因。分歧双方都使用相同的 Qwen3-Embedding 权重，因此没有默认值和模型系列规则可以同时满足两者。幸福的路径是字节相同的——该字段仍然被省略——并且命名参数和我们将要发送的值的 400 恰好可以通过 encoding_format="float" 重试一次。

索引中的图像并行描述

LlamaIndex 管道一次描述提取的图像。它们现在与每个图像超时和进度线同时运行，可通过 image_description_concurrency（默认 4）和 image_description_timeout_seconds（默认 60）进行调整。事实证明不接受图像的模型在没有图像的情况下不再重试 - 图像是那里的问题，并且从其周围的文本发明的描述将被索引为事实。贡献为 #933。

LightRAG 会聚而不是悬挂

现在，针对 LightRAG 基础的传输失败在重试之前会进行分类：可重试 HTTP 状态最多可进行 3 次有上限的 Retry-After 尝试，其他任何操作都会立即失败，并且两个重试层不再相乘。取消会清除而不是泄漏，Codex 传输失败会传播而不是被吞噬。贡献为 #940。

什锦

  • 索引进度线是可翻译的。 所有 22 个制作者都将硬编码的英语发送到日志框。现在，线路携带模板及其值，前端会以您的语言呈现它；没有 i18n 的消费者——日志、快照、CLI——准确地阅读他们之前读过的内容。
  • **删除的知识库不再困扰您的会话。**它的名字徘徊在每个会话的上下文芯片中（#936）。
  • 开发 Docker 映像再次拥有前端。 它的主管针对一个不包含源、配置和 scripts/ 的生产独立包运行 node scripts/dev.mjs，因此 docker compose -f docker-compose.dev.yml up 死了（#906）。现在，舞台采用了构建器的整个 web/ 树。生产形象从未受到影响。
  • 提供程序的拒绝正文在到达日志之前受到限制。 该日志存在，因此您可以将 deeptutor.jsonl 附加到错误报告，并且某些提供程序将拒绝的请求（模式，有时是消息）回显到其中（#930）。
  • 两个 MarginNote 库不能再声明一个商店。 “My Lib”和“My/Lib”均派生 My_Lib.db；注册现在会拒绝名称冲突，删除库会删除我们为其创建的商店。
  • MN4 设备桥首先检查凭据。 /sync 和 /heartbeat 在验证令牌之前解析了它们的存储，因此未经身份验证的 POST 为每个不同的标头值创建了一个数据库 - 并且配对写入调用者的工作区，而设备路径读取默认的工作区，这可能会永远 403 每次同步。

升级注意事项

pip install -U deeptutor； Docker用户拉动ghcr.io/hkuds/deeptutor:latest。没有架构更改，没有重新索引，没有迁移。

  • MarginNote 4 库一开始是空的。 连接它，从 设备 选项卡配对设备，然后将一次性令牌粘贴到 MN4 附加组件中 — 该令牌仅显示一次，仅保留其哈希值。该商店位于data/user/marginnote4/<name>.db，并与图书馆一起删除； MarginNote 本身没有任何内容被触及。
  • MarginNote 库不会被 rag 扫描。 就像黑曜石金库一样，它们只能通过自己的工具访问，因此 Book 和 rag_search 会跳过它们，而不是报告空结果。
  • 新的图像描述旋钮适用于下一个索引构建，而不是下一个问题，并且位于设置 → 知识库下。 完整 Changelog：https://github.com/HKUDS/DeepTutor/compare/v1.5.15…v1.5.16
