mempalace v3.11.0

现在可以按照引导步骤审核和修复宫殿，并且 EmbeddingGemma 2 作为具有本机图像、音频和视频搜索功能的选择性嵌入器出现。每一座宫殿都会记录建造它的嵌入模型，并且拒绝用不同的模型打开。对话挖掘停止丢弃文本、状态、搜索、唤醒，中心矿井在大型宫殿上保持响应，3.11 审查的一轮正确性修复加强了元数据更新、恢复和 HTTP 验证。

升级注意事项

  • 升级后的第一个对话挖掘器会重新挖掘它所覆盖的每个对话文件一次。 交换分块器不再丢弃文本 (#2591)，因此在 3.11 之前归档的对话抽屉将被视为过时，并且会从仍在磁盘上的记录中重新分块和重新嵌入；磁盘上不再存在的成绩单保留在抽屉中。项目文件不会被重新挖掘。预计每百万个抽屉大约需要 40 分钟到 3 小时，具体取决于硬件。在大宫殿上，先备份，在安静的时候分批运行，例如mempalace mine <dir> --mode convos --limit 200；中断的运行会从停止处恢复。
  • 宫殿拒绝使用与建造它的模型不同的嵌入模型打开。 搜索、挖掘和 MCP 写入停止，并显示一条消息，指出修复方法：将 embedding_model（config.json 或 MEMPALACE_EMBEDDING_MODEL）设置回建造宫殿所用的模型，或使用 mempalace repair rebuild-index 重新嵌入。打开一个没有记录模型的宫殿，其中包含已配置的模型和名为 mempalace palace set-embedder 的警告。 （＃2694，＃2717）
  • EntityRegistry.research() 和 confirm_research() 被删除。 它们是一个选择加入、默认关闭的维基百科查找，CLI、MCP 服务器、矿工或挂钩中没有任何内容被调用。 entities.json 中现有的 wiki_cache 条目仍由 lookup() 读取。 (GHSA-mrj5)

EmbeddingGemma 2 和嵌入器身份

  • EmbeddingGemma 2 可作为选择性嵌入器使用。 设置 embedding_model: embeddinggemma2 并安装 mempalace[embeddinggemma2] 或 mempalace[multimodal] 用于媒体（Python 3.10+、PyTorch）。它在 CUDA（如果存在）、Apple MPS 或 CPU 上运行，并支持 768/512/256/128 尺寸。 CUDA 内存不足错误会将批次减半并重试。 （＃2694，＃2717）
  • 本机图像、音频和视频检索。 内置 media 源适配器将原始文件嵌入到单独的 mempalace_assets 集合中，并且选择加入 CLI/MCP 媒体搜索会返回键入的本地资产引用以及匹配的抽屉。文件级检索是实验性的。 (#2694)
  • 除非您选择加入，否则现有宫殿不会受到影响。 默认 MiniLM 路径保持不变，并且不会重新嵌入任何内容。未知的 embedding_model 保持 MiniLM 后备，而已知名称的未遂事件将被拒绝，而不是默默地后备。 (#2717)
  • 每个宫殿都会记录哪个嵌入者构建了它，并且每个写入路径都会因不匹配而关闭失败。 CLI、MCP、我的和 repair 检查记录的身份； repair rebuild-index和--mode from-sqlite经过验证重建后再次记录；新的 Qdrant 和 pgvector 宫殿记录了它； MCP 拒绝而不是退回到 Chroma 的默认嵌入器。 （#2717；修复#2709）

宫殿审计和指导修复

  • mempalace audit 对宫殿的组织程度进行评分， 跨越五层（房间、翼楼、隧道、走廊和知识图），并提供具体结果、--json 输出和用于 cron 或 CI 的 --fail-under。它是只读的，并且针对 MCP 服务器正在服务的宫殿运行。 (#2576)
  • 引导修复工具： mempalace instructions audit 引导代理和用户完成调查结果； rooms propose / apply 给机翼一个封闭的房间组； wings split 将机器级转录翼变成每个项目一个翼； tunnels propose / prune 和 hallways --rebuild / --prune-spellings 清理嘈杂的链接； kg normalize 将一次性谓词映射到封闭词汇表上。在 --yes 之前，一切都是试运行，中断的运行在重试时完成。 LLM 支持的步骤默认为本地端点，并且需要 --accept-external-llm 来执行其他操作。 （#2576、#2655、#2656、#2657、#2664、#2668、#2669）
  • SQLite 后端上的仅元数据更新速度快了约 6000 倍，因此大型宫殿的侧翼和房间移动只需几秒钟即可完成。 (#2576)

3.11 评论的正确性修复

  • 元数据感知更新和更新插入保护用于嵌入的输入。 在发布之前拒绝并发文档或元数据更改，并且从嵌入元数据中省略已删除的字段。 (#2734)
  • **抽屉列表将元数据和页面预览保留在一个恢复的快照中，**并在恢复挂起时回退到 Chroma。 (#2734)
  • **房间恢复在应用更改之前拒绝损坏的日志，**并且批准的隧道提案保留其完整的拼写上下文。 (#2734)
  • 格式错误的 HTTP 工具名称会返回正常的 JSON-RPC 验证错误，而不是在调度期间失败。 (#2734)

表演和大型宫殿

  • 状态、搜索和唤醒在大型宫殿上保持响应。 计数缓存在使用前不再过期（在 360k 抽屉宫殿上，8-12 秒降至约 1 毫秒），MCP 服务器几乎在每次调用时停止重新加载向量索引，唤醒从 SQLite 读取最近的抽屉，挖掘不再使用二次分页重新扫描宫殿。 (#2593)
  • 非常大的宫殿上的地雷所做的冗余工作要少得多， 并且 HTTP 集线器上的地雷会产生文件之间的排队请求。 （＃2567，＃2593，＃2688，＃2689，＃2690，＃2691）
  • 日记读取和单抽屉查找从 SQLite 读取（当 SQLite 已有行时）。 (#2650)

错误修复

  • 在 --- 降价规则之后、第一个用户轮流之前或在简短的交流中，对话挖掘不再丢弃文本。 (#2591)
  • mempalace_reconnect 不再在正在运行的矿井下运行； 它最多等待 10 秒，然后返回 MineInProgress，而某些文件失败的矿井会引发 MineFileErrors 并退出 1。（#2701、#270
