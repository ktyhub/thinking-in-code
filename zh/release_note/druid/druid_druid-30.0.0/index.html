druid 30.0.0

大版本 发布时间2024年6月17日 来源apache/druid 英文原文

druid druid-30.0.0

Apache Druid 30.0.0 包含超过 407 个新功能、错误修复、性能增强、文档改进以及来自 50 个贡献者的额外测试覆盖范围。

请参阅完整的更改 了解更多详细信息，包括错误修复。

在升级到 Druid 30.0.0 之前，请查看升级说明 和不兼容更改。 如果您要跨多个版本进行升级，请参阅升级说明页面，其中列出了最新 Druid 版本的升级说明。

# 即将删除

作为 Druid 持续改进的一部分，我们将弃用某些功能和行为，转而采用更新的迭代，这些迭代提供更强大的功能并且更符合标准 ANSI SQL。其中许多新功能已成为多个版本的新部署的默认功能。

以下功能已弃用，我们目前计划删除 Druid 32.0.0 中的支持：

  • 不符合 SQL 的空处理：默认情况下，Druid 现在区分空字符串和没有数据的记录，以及空数字记录和 0。有关详细信息，请参阅 NULL 值。有关SQL兼容逻辑的教程，请参见Null处理教程。
  • 非严格布尔处理：Druid 现在严格使用 1 (true) 或 0 (false)。以前，true 和 false 可以分别表示为 true 和 false 或 1 和 0。此外，Druid 现在为 True && NULL 等布尔比较返回空值。有关更多信息，请参阅布尔逻辑。有关使用 SQL 兼容逻辑的过滤器示例，请参阅查询过滤器。
  • 双值逻辑：默认情况下，Druid 现在使用三值逻辑进行摄取和查询。这主要影响对具有 NULL 值的列使用逻辑 NOT 运算的过滤器。有关更多信息，请参阅布尔逻辑。有关使用 SQL 兼容逻辑的过滤器示例，请参阅查询过滤器。

# 重要功能、更改和弃用

本节包含有关新功能和现有功能的重要信息。

# 并发追加和替换改进

流式摄取管理程序现在支持并发追加，即流式任务可以与替换任务（压缩或重新索引）同时运行，如果它也恰好使用并发锁。将上下文参数 useConcurrentLocks 设置为 true 以启用并发追加。

一旦您将 Supervisor 更新为 "useConcurrentLocks": true，就会无缝过渡到并发追加，而不会导致任何摄取延迟或任务失败。

#16369

Druid 现在通过跟踪使用此类挂起段的任务集来主动清理陈旧的挂起段。 这允许并发附加和替换仅升级最小的待处理段集，从而提高性能并消除错误。 此外，它还有助于减少元数据存储上的负载。

#16144

# 对复杂列进行分组

Druid 现在支持对复杂列和嵌套数组进行分组。 这意味着本机查询和 MSQ 任务引擎都可以在返回结果时对复杂列和嵌套数组进行分组。

此外，MSQ 任务引擎可以在摄取过程中对支持的复杂列（例如 JSON 列）进行汇总和排序。

#16068 #16322

# 删除了基于 ZooKeeper 的段加载

由于已知问题，基于 ZooKeeper 的段加载正在被删除。 它已在多个版本中被弃用。 Druid Coordinator 的最新改进显着增强了基于 HTTP 的段加载的性能。

#15705

# 改进的 groupBy 查询

在 Druid 将实时段推送到深层存储之前，这些段由溢出文件组成。 分段指标（例如 query/segment/time）现在报告实时分段的每个溢出文件，而不是整个分段。 此更改消除了在堆上具体化结果的需要，从而提高了 groupBy 查询的性能。

#15757

# 改进了 AND 过滤器性能

Druid 查询处理现在可以根据其他过滤器的选择性自适应地确定 AND 过滤器的子级何时应计算索引以及何时在扫描期间简单地匹配行。 它称为过滤器分区，可以显着提高性能，具体取决于查询中过滤器的顺序。

例如，采用 SELECT SUM(longColumn) FROM druid.table WHERE stringColumn1 = '1000' AND stringColumn2 LIKE '%1%' 之类的查询。以前，Druid 在处理过滤器时使用索引（如果可用）。 这并不总是理想的。想象一下如果 stringColumn1 = '1000' 匹配 100 行。对于索引，我们必须找到 stringColumn2 LIKE '%1%' 的每个正确值来计算过滤器的索引。如果 stringColumn2 具有超过 100 个值，则结果比简单地检查剩余 100 行中的匹配情况更糟糕。

通过新的逻辑，Druid 现在在处理 AND 过滤器的每个子句时检查索引的选择性。 如果它确定计算索引需要比匹配剩余行更多的工作，Druid 就会跳过计算索引。

在查询的 WHERE 子句中编写过滤器的顺序可以提高查询的性能。 更多改进即将推出，但您可以通过重新排序查询来尝试现有改进。 将计算强度较低的索引（例如 IS NULL、= 和比较（>、>=,、< 和 <=））放在 AND 过滤器的开头附近，以便 Druid 更有效地处理您的查询。 不以这种方式排序过滤器不会降低以前版本的性能，因为回退行为是 Druid 之前所做的。

#15838

# 集中式数据源架构 (alpha)

您现在可以配置 Druid 在协调器上集中管理数据源架构。 以前，Broker 需要查询数据节点和任务以获取分段模式。 集中数据源模式可以缩短代理的启动时间和部署效率。

要启用此功能，请设置以下配置：

  • 在公共运行时属性中，将 druid.centralizedDatasourceSchema.enabled 设置为 true。
  • 如果您使用的是 MiddleManager，则还需要在 MiddleManager 运行时属性中将 druid.indexer.fork.property.druid.centralizedDatasourceSchema.enabled 设置为 true。

#15817

# MSQ 对窗口函数的支持

现在，您可以使用上下文标志 enableWindowing:true 在 MSQ 任务引擎中运行窗口函数。 在本机引擎中，您必须使用 group by 子句来启用窗口函数。 MSQ 任务引擎中删除了此要求。

#15470 #16229

# MSQ 对 Google 云端存储的支持

现在，您可以通过将函数 google() 作为参数传递给 EXTERN 函数，将 MSQ 结果导出到 Google Cloud Storage (GCS) 路径。

#16051

# RabbitMQ 扩展

新的 RabbitMQ 扩展可作为社区贡献提供。 RabbitMQ 扩展 (druid-rabbit-indexing-service) 允许您管理 Rabbit 索引任务的创建和生命周期。这些索引任务通过超级流从RabbitMQ读取事件。

由于超级流允许一次交付并完全支持分区，因此它们与 Druid 的现代摄取算法兼容，没有以前的 RabbitMQ firehose 的缺点。

请注意，这使用 RabbitMQ 流功能，而不是传统的交换。您需要确保您的消息在消费之前位于超级流中。有关更多信息，请参阅RabbitMQ 文档。

# 流式传输完成报告

流任务完成报告现在有一个额外的字段 recordsProcessed，它列出了该任务处理的所有分区以及每个分区的记录计数。 使用此字段可以查看任务的实际吞吐量，并决定是否应该垂直或水平扩展工作人员。

#15930

# 改进了 Kinesis 的内存管理

Kinesis 摄取内存调整配置现在更简单：

  • 您不再需要设置配置 recordsPerFetch 和 deaggregate。
  • fetchThreads 不能再超过堆的预算量（100 MB 或 5%）。
  • 使用 recordBufferSizeBytes 为 Kinesis 获取线程和主摄取线程设置基于字节的限制，而不是基于记录的限制。我们建议将此设置为 100 MB 或堆的 10%，以较小者为准。
  • 使用 maxBytesPerPoll 设置 Druid 一次从共享缓冲区轮询的数据量的基于字节的限制。默认值为 1,000,000 字节。

作为此更改的一部分，以下属性已被弃用：

  • recordBufferSize，请使用recordBufferSizeBytes代替
  • maxRecordsPerPoll，请改用maxBytesPerPoll

#15360

# 改进了 Kinesis 流的自动缩放功能

Kinesis 自动缩放器现在考虑最大延迟（以分钟为单位）而不是总延迟。 为了保持向后兼容性，此更改是现有 Kinesis 连接的选择加入。 要选择加入，请将主管规范中的 lagBased.lagAggregate 设置为 MAX。 新连接默认使用最大延迟。

#16284 #16314

# 查询

# 动态表追加

您现在可以使用 TABLE(APPEND(...)) 函数基于表模式隐式创建联合。

例如，以下查询是等效的：

SELECT * FROM TABLE(APPEND('table1','table2','table3'))

和

SELECT column1,NULL AS column2,NULL AS column3 FROM table1
UNION ALL
SELECT NULL AS column1,column2,NULL AS column3 FROM table2
UNION ALL
SELECT column1,column2,column3 FROM table3

请注意，如果使用不同的输入类型定义相同的列，则 Druid 使用限制最少的列类型。

# 不兼容的更改

# EXPLAIN 查询中对 targetDataSource 的更改

Druid 30.0.0 包含一项重大更改，可将 targetDataSource 的行为恢复到 28.0.0 和早期状态，这与 Druid 29.0.0 和仅 29.0.0 不同。在 29.0.0 中，targetDataSource 返回包含数据源名称的 JSON 对象。在所有其他版本中，targetDataSource 返回包含数据源名称的字符串。

如果您从 29.0.0 以外的任何版本升级，则行为不会发生变化。

如果您从 29.0.0 升级，则这是不兼容的更改。

#16004

# 删除了基于 ZooKeeper 的段加载

由于已知问题，基于 ZooKeeper 的段加载正在被删除。 它已在多个版本中被弃用。 Druid Coordinator 的最新改进显着增强了基于 HTTP 的段加载的性能。

#15705

# 删除了协调器配置

删除了以下协调器配置：

  • druid.coordinator.load.timeout：不需要，因为已知此参数的默认值（15 分钟）适用于所有集群。
  • druid.coordinator.loadqueuepeon.type：不需要，因为该值始终为 http。
  • druid.coordinator.curator.loadqueuepeon.numCallbackThreads：不需要，因为基于 ZooKeeper（curator）的段加载不再是一种选择。

现在默认启用自动清理非活动数据源的压缩配置。
