druid druid-26.0.0

Apache Druid 26.0.0 包含超过 390 个新功能、错误修复、性能增强、文档改进以及来自 65 个贡献者的额外测试覆盖范围。

在升级到 Druid 26.0.0 之前，请查看升级说明和不兼容的更改。

# 亮点

# 自动类型列架构（实验）

新的“自动”类型列模式和索引器已添加到本机摄取中，作为嵌套列功能的下一个逻辑迭代。此自动类型列索引器可为给定输入生成最合适的列，生成 STRING、ARRAY<STRING>、LONG、ARRAY<LONG>、DOUBLE、ARRAY<DOUBLE> 或 COMPLEX<json> 列，所有列都共享通用的“嵌套”格式。

“auto”生成的所有列都具有索引来帮助快速过滤（与经典的 LONG 和 DOUBLE 列不同），并使用基于基数的阈值来尝试仅在可能实际加速查询时使用这些索引（与经典的 STRING 列不同）。

此“自动”索引器生成的 COMPLEX<json> 列存储简单标量类型的数组，其方式与“json”(v4) 对应项不同，将它们存储为 ARRAY 类型列。这意味着 JSON_VALUE 函数现在可以提取整个数组，例如 JSON_VALUE(nested, '$.array' RETURNING BIGINT ARRAY)。目前复杂对象数组的存储方式没有变化。

这一改进还为 Druid 添加了全新的功能，ARRAY 类型列，与经典的多值 STRING 列不同，它具有 ARRAY 语义。当前，当所有值都是具有相同类型元素的数组时，只能通过“自动”类型索引器创建这些列。

数组数据类型是一种允许您在数据库表的单个列中存储多个值的数据类型。数组通常用于存储可以作为一个组轻松访问和操作的相关数据集。

此版本添加了对将基本值数组（例如 ARRAY<STRING>、ARRAY<LONG> 和 ARRAY<DOUBLE>）存储为专用嵌套列的支持，而不是将它们分解为单独的元素列。

# 架构自动发现（实验性）

我们正在向 Druid 添加带有类型推断的模式自动发现。通过此功能，当架构可用时，可以检测每个传入字段的数据类型。对于可能包含添加、删除或更改字段的传入数据，您可以选择拒绝不合格数据（“数据库始终正确 - 拒绝错误数据！”），或者您可以让架构自动发现更改数据源以匹配传入数据（“数据始终正确 - 更改数据库！”）。 建议对新用例和摄取使用模式自动发现。对于现有用例，请小心切换到模式自动发现，因为 Druid 会将类似数组的值（例如 ["tag1", "tag2]）摄取为 ARRAY<STRING> 类型列而不是多值 (MV) 字符串，这可能会导致下游应用程序在回复 MV 行为时出现问题。推迟切换，直到有正式的迁移路径可用。

要使用此功能，请在任务或主管规范中将 spec.dataSchema.dimensionsSpec.useSchemaDiscovery 设置为 true，或者，如果在控制台中使用数据加载器，请取消选中 Configure schema 步骤上的 Explicitly define schema 切换。如果您在维度列表中显式列出维度，则 Druid 可以推断出整个架构或部分架构。

架构自动发现可用于本机批量和流式摄取。

# UNNEST 数组（实验）

UNNEST 的酷炫之处在于它允许进行更广泛的操作，而这在数组数据类型上是不可能的。您可以使用 UNNEST 函数 (SQL) 或 unnest 数据源（本机）取消数组的嵌套。

Unnest 将嵌套数组或表转换为单独的行。 UNNEST 函数在处理包含嵌套数组的复杂数据类型（例如 JSON）时特别有用。

例如，假设您有一个名为“orders”的表，其中有一列名为“items”，其中包含每个订单的产品数组。您可以使用 unnest 提取单个产品（“each_item”），如以下 SQL 示例所示：

SELECT order_id, each_item FROM orders, UNNEST(items) as unnested(each_item)

这会生成一个结果集，其中每个订单中的每个商品占一行，其中包含订单 ID 和单个商品的列

请注意左表/数据源后面的逗号（示例中为 orders）。这是必需的。

# MSQ 的排序合并联接和哈希随机联接

现在，我们可以通过将排序合并算法的上下文参数 sqlJoinAlgorithm 设置为 sortMerge 来执行随机连接，或者忽略它以执行广播连接（默认）。

多阶段查询可以使用排序合并连接算法。使用该算法，每个成对连接都被规划到具有两个输入的自己的阶段中。与广播相比，这种方法通常性能较差，但可扩展性更高。

将上下文参数 sqlJoinAlgorithm 设置为 sortMerge 以使用此方法。

广播哈希联接类似于本机联接查询的执行方式。

# Firehose 摄取已删除

旧版 Druid 流格式使用的 Firehose/解析器规范已被删除。 Firehose 摄取在版本 0.17 中已弃用，并且在版本 24.0 中删除了对此摄取的支持。

# 信息架构现在使用数字列类型

Druid 系统表 (INFORMATION_SCHEMA) 现在使用 SQL 类型而不是 Druid 类型作为列。此更改使 INFORMATION_SCHEMA 表的行为更像标准 SQL。如果您依赖于以下任一情况，您可能需要在以下情况下更新查询，以避免出现意外结果：

  • 数字字段被视为字符串。
  • 列编号从 0 开始。列编号现在从 1 开始。

#13777

# frontCoded 段格式更改

indexSpec 上的 stringEncodingStrategy 的 frontCoded 类型具有新的段格式版本，通常具有更快的读取速度和减小的段大小。此改进与 Druid 25.0 向后不兼容。

# 空值强制移出表达式处理引擎

输入到 Druid 本机表达式处理引擎并由其创建的空值不再将 null 强制转换为适当的“默认”值（如果是 druid.generic.useDefaultValueForNull=true）。这不应影响现有行为，因为这已转移给消费者，并且内部运营商仍将在此模式下使用默认值。但是，ZZPH100​​ZZ 值的处理可能会发生细微的行为变化。直接调用者可以通过使用 ExprEval 的新 valueOrDefault() 方法而不是 value() 来获取默认值。

#13809

# 简化的依赖项

druid-core、extendedset 和 druid-hll 模块已合并到 druid-processing 以简化依赖性。引用这些的任何扩展都应更新为使用 druid-processing。当与新版本的 Druid 一起使用时，现有的扩展二进制文件_应该_继续正常运行。

此更改不会影响最终用户。它确实会影响任何为 Druid 开发扩展的人。
