druid 34.0.0

Apache Druid 34.0.0 包含超过 270 个新功能、错误修复、性能增强、文档改进以及来自 48 个贡献者的额外测试覆盖范围。

请参阅完整的更改集 了解更多详细信息，包括错误修复。

在升级到 Druid {{DRUIDVERSION}} 之前，请查看升级说明 和不兼容的更改。 如果您要跨多个版本进行升级，请参阅升级说明页面，其中列出了最新 Druid 版本的升级说明。

重要功能、更改和弃用

本节包含有关新功能和现有功能的重要信息。

Java 11 支持

自 Druid 32.0 起已弃用 Java 11 支持，最早从 Druid 35.0.0 起将删除官方支持

基于 Hadoop 的摄取

自 Druid 32.0 起，基于 Hadoop 的摄取已被弃用，并且最早将在 Druid 35.0.0 中被删除。 我们推荐 Druid 其他支持的摄取方法之一，例如 基于 SQL 的摄取 或 使用 Kubernetes 的无 MiddleManager 摄取。

作为此更改的一部分，您现在必须选择使用已弃用的 index_hadoop 任务类型。如果您不这样做，您的基于 Hadoop 的摄取任务将会失败。

要选择加入，请在 common.runtime.properties 文件中将 druid.indexer.task.allowHadoopTaskExecution 设置为 true。

#18239

使用 SET 语句作为查询上下文参数

现在，您可以使用 SET 语句通过 Druid 控制台 或 API 定义查询的查询上下文参数。

#17894 #17974

Druid 控制台中的 SET 语句

Web 控制台现在支持使用 SET 语句来指定查询上下文参数。例如，如果您在查询中包含 SET timeout = 20000;，则会设置超时查询上下文参数：

SET timeout = 20000;
SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2

#17966

使用 API 的 SET 语句

向 /druid/v2/sql 发出的 SQL 查询现在可以包含多个 SET 语句来为最终语句构建上下文。例如，以下 SQL 查询结果包括 timeout、useCache、populateCache、vectorize 和 engine 查询上下文参数：

SET timeout = 20000;
SET useCache = false;
SET populateCache = false;
SET vectorize = 'force';
SET engine = 'msq-dart'
SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2

此查询的 API 调用如下所示：

curl --location 'http://HOST:PORT/druid/v2/sql' \
--header 'Content-Type: application/json' \
--data '{
  "query": "SET timeout=20000; SET useCache=false; SET populateCache=false; SET engine='\''msq-dart'\'';SELECT  user,  commentLength,COUNT(*) AS \"COUNT\" FROM wikipedia GROUP BY 1, 2 ORDER BY 2 DESC",
  "resultFormat": "array",
  "header": true,
  "typesHeader": true,
  "sqlTypesHeader": true
}'

此改进也适用于使用 MSQ 任务引擎的 INSERT 和 REPLACE 查询。请注意，不支持 JDBC。

改进的 HTTP 端点

您现在可以在 /druid/v2/sql 端点的 HTTP 正文中使用原始 SQL。您可以将 Content-Type 设置为 text/plain 而不是 application/json，这样您就可以提供未转义的原始文本。

#17937

克隆历史（实验）

您现在可以使用动态协调器配置 cloneServers 来配置历史记录的克隆。克隆历史记录对于滚动更新等情况很有用，您希望启动新的历史记录来替代现有历史记录。

将配置设置为从目标历史服务器到源历史服务器的映射：

  "cloneServers": {"historicalClone":"historicalOriginal"}

克隆不参与常规段分配或平衡。相反，协调器会将对原始 Historical 所做的任何段分配镜像到克隆上，以便克隆成为源的精确副本。克隆历史上的段也不计入副本计数。如果原始历史消失，克隆将保持源服务器的最后已知状态，直到从 cloneServers 配置中删除。

当您使用本机查询引擎查询数据时，您可以通过设置查询上下文参数 cloneQueryMode 来首选 (preferClones)、排除 (excludeClones) 或包含 (includeClones) 克隆。默认情况下，克隆被排除在外。
