项目

  • 将 DSL 类加载机械移至 core/dsl 下。 core/classloader 仅包含 DSL 类型 — RuleClassLoader、DSLClassLoaderManager、ClassLoaderGc、UnloadProbePayload 和 BytecodeClassDefiner — 因此现在是 core/dsl/classloader，而 Catalog 则移至 core/dsl，因为规则文件分类不是类加载问题。 “将生成的类定义到正确的加载器中”调度的三个副本（MAL、LAL、MeterSystem）折叠成静态 BytecodeClassDefiner.define，这也为 JDK 17 --add-opens 提供了一个而不是四个的基本原理。生成类转储目录查找的四个副本中的三个变为 DslGeneratedFileWriter.resolveClassDumpDir； OAL 保留了自己的，因为它的调试标志可以独立于环境变量设置，并且两个测试依赖于此。没有行为改变。
  • 扩展 GET /inspect/entities 管理 API 以检查 任何 OAP 保留的指标，即使该节点未在本地定义。当本地注册表未知该指标时，调用者提供 valueColumn + valueType，并且存储后端从其自己的运行配置解析物理索引/表/组（不读取数据库模式/表元数据）：ES 使用合并的 metrics-all 索引 + metric_table 鉴别器，JDBC 通过 table_name 鉴别器探测节点的功能表，而 BanyanDB综合只读度量方案。不再需要范围 - entity_id 使用通用 name 叶进行结构解码（服务/第二级/关系）。本地定义的指标与以前一样保留准确的字段名称、范围和 mqeEntity。
  • 添加 POST /inspect/values 管理 API — 通过提供其 {valueColumn, valueType} 读取由 另一个 OAP（此节点未在本地定义）保存的指标的值系列。真正的 MQE 引擎在请求范围的 InspectQueryContext 覆盖上运行（如果不存在则提供 — 本地目录总是获胜），这使得外部度量看起来已注册到每个读取路径：ValueColumnMetadata 解析其值列/类型/范围，存储位置注册表解析它所在的位置（MetadataRegistry 合成 BanyanDB 度量架构，IndexController 解析 ES metrics-all 索引， TableHelper 探测 JDBC 函数表），因此读取返回本机 MQE ExpressionResult，没有每个 DAO 的特殊情况。仅限管理员（强制读取此 OAP 无法验证）；未镜像到公共 REST / GraphQL 表面。请参阅检查 API。
  • 删除始终开启的警报到事件转换 (EventHookCallback)。触发的警报不再作为 Alarm/AlarmRecovery 事件合成到事件管道中；事件现在仅源自真实事件源（代理、SkyWalking CLI、Kubernetes 事件导出器）。通过警报存储 (getAlarm/queryAlarms) 和配置的警报挂钩，警报仍然可用。这会删除记录的“已知事件”并删除每个警报火灾的 1-2 条综合事件记录。
  • 适用于所有 OAP HTTP/REST 服务器的 TLS，具有证书热重载功能。 将 restSSLEnabled / restSSLKeyPath / restSSLCertChainPath 配置结构添加到每个 OAP HTTP 服务器 - 核心 REST、共享服务器、管理、PromQL、LogQL、TraceQL 和 Zipkin 查询/接收器 - 每个服务器都有自己的专用环境变量（SW_CORE_REST_SSL_*、SW_RECEIVER_SHARING_REST_SSL_*、 SW_ADMIN_SERVER_REST_SSL_*、SW_PROMQL_REST_SSL_*、SW_LOGQL_REST_SSL_*、SW_TRACEQL_REST_SSL_*、SW_QUERY_ZIPKIN_REST_SSL_*、SW_RECEIVER_ZIPKIN_REST_SSL_*）。共享的 Armeria HTTPServer 会轮流从磁盘重新加载密钥对（通过 TlsProvider.ofScheduled），因此无需重新启动 OAP 即可获取刷新的证书，这与现有的 gRPC SSL 热重加载行为相匹配。 HTTP TLS 仅适用于服务器端（无 mTLS）。
  • 新的 queryAlarms GraphQL 查询 - 用于警报的实体/图层/规则过滤器。 在旧版 getAlarm 旁边添加了全面的警报查询 API。新的 queryAlarms(condition: AlarmQueryCondition!): Alarms 接受单一输入类型，捆绑警报记录存储的每个过滤器：entities: [Entity!]（重用 MQE Entity 形状 - 固定到特定服务/实例/端点/进程或其关系，与警报 id0 或 id1 匹配）； layer: String（按报警实体的层进行过滤 - 单个匹配，因为报警行保留一层）； ruleNames: [String!]（触发警报规则的过滤器）；加上 keyword、tags、duration、paging。旧版 getAlarm 标记为 @deprecated，但仍路由至相同的 DAO — 没有 client 损坏。后端添加：AlarmRecord 上的新 layer 列在警报生成时间通过 MetadataQueryService.getService(serviceId).getLayers() 填充；现有的 id0/id1 列从 storageOnly = true 翻转为索引，以便实体过滤器下推到存储。 IAlarmQueryDAO.queryAlarms(condition, limit, from) 是一种新的抽象方法 - 如果第三方存储后端错过覆盖（SWIP-14 模式），则它们会在编译时失败。所有三个捆绑后端都实现了它：BanyanDB / Elasticsearch / JDBC。 运算符语义： (1) 关系实体是精确匹配的。 传递{scope: ServiceRelation, serviceName: A, destServiceName: B} 只匹配id0=serviceId(A) AND id1=serviceId(B) 所在的报警，而不匹配任何一侧触及A 或B 的报警。更广泛的“涉及 A 的任何内容”查询应该传递单个非关系实体（{scope: Service, serviceName: A} — 扩展为 id0=A OR id1=A）。 (2) 每个警报行单个层。 持久化列存储一个层（实体解析层的第一个条目
