caddy v2.10.0

球童2.10来了！除了错误修复之外，此版本还具有以下功能：

  • 加密的 ClientHello (ECH)： 这项新技术对 TLS 连接的最后一个明文部分进行加密：ClientHello，其中包括所连接的域名。 ECH 的草案规范 已接近最终确定，因此我们现在可以支持 TLS 的此隐私功能。这是一个强大但微妙的功能；我们强烈建议您阅读我们网站上的ECH 文档。
  • 后量子 (PQC) 密钥交换： Caddy 现在默认支持标准化 x25519mlkem768 加密组。
  • ACME 配置文件： ACME 配置文件是一个实验草案，允许您比传统 CSR 方法更灵活地选择证书的属性。例如，在某个配置文件下，Let’s Encrypt 将颁发 6 天证书。 Caddy 最终可能会默认使用该配置文件。
  • Via 标头： 反向代理现在设置 Via 标头而不是重复的 Server 标头。
  • 全局 DNS 提供商： 您现在可以指定要使用的默认“全局”DNS 模块，而不必在需要 DNS 提供商的配置的每个部分进行本地配置（例如，ACME DNS 质询和 ECH）。这是 Caddyfile 中的 dns 全局选项，或者是 JSON 配置中的 dns 参数，它是 tls 应用程序配置中的 dns 参数。
  • 默认使用的通配符： 以前，Caddy 会为您的配置中的每个域获取单独的证书；现在，通配符（如果存在）将用于子域，而不是获取单独的证书。这一变化的动机是 ECH 提供的子域隐私的新可能性。可以使用 Caddyfile 中的 tls force_automate 覆盖它。实验性的 auto_https prefer_wildcard 选项已被删除。
  • libdns 1.0 APIs： 你们中的许多人使用 DNS 提供程序模块 来解决 ACME DNS 挑战或启用动态 DNS。它们实现由 libdns 定义的接口来获取、设置、附加和删除 DNS 记录。经过 5 年的生产经验，包括 ECH 的经验教训，libdns API 已更新，1.0 测试版已被标记。 DNS 提供商包需要更新其代码以兼容，这将有助于确保未来的稳定性和明确定义的语义。多个软件包已更新或正在更新（cloudflare、rfc2136 和 desec 等）。
  • 全局 dns 配置： 现在 Caddy 配置的多个组件可能会影响 DNS 记录（ACME 挑战、ECH 发布等），因此有一个新的 dns 全局选项可用于在单个位置指定您的 DNS 提供商配置。这可以防止所有域都由单个 DNS 提供商管理的服务器的凭据重复。 感谢众多贡献者的帮助，让这一切成为可能！ :tada: :partying_face: :chhampagne: ：警告：虽然传统上支持最后 2 个 Go 次要版本以适应某些发行版/包管理器策略，但我们现在仅支持最新的 Go 次要版本。 Go 新版本中添加的隐私和安全优势（例如后量子密码学）值得尽快向所有人提供，而不是阻碍整个用户群或维护多个代码编译配置。

加密的 ClientHello (ECH) 详细信息

（这是一个简短的概述。我们建议阅读完整文档。） 通常，在建立 TLS 连接时，服务器名称（域名或“SNI”）以明文 ClientHello 形式发送。使用 ECH，真实的服务器名称由“外部”ClientHello 加密（并包装），该“外部”ClientHello 具有您选择的通用 SNI。由于同一服务器上的许多站点共享相同的外部 SNI，clients 和服务器都具有与域名相关的更多隐私。 Caddy 实现了完全自动化的 ECH，这意味着它只需指定 DNS 提供商和要使用的外部/公共域名即可生成（并且很快、轮换）、发布和提供 ECH 配置。 完全自动化的 ECH 需要在 Caddy 二进制文件中内置一个 DNS 模块。 为了让 client（例如浏览器）知道它可以使用 ECH 以及要使用哪些参数，必须发布服务器的 ECH 配置。此配置包括公共名称、加密参数和用于加密内部 ClientHello 的公共密钥。按照惯例，浏览器读取包含 ech SvcParamKey 的标准化 HTTPS 类型 DNS 记录。 Caddy 为所有受保护的域设置此 DNS 记录，但需要插入并配置 DNS 提供商模块才能执行此操作。如果您已经在使用 DNS ACME 挑战，则应该已经插入了 DNS 提供商。如果您更喜欢使用 DNS 模块 从源代码构建 Caddy，则使用 xcaddy 很容易，例如：$ xcaddy build --with github.com/caddy-dns/cloudflare 启用 ClientHello 所需的最低配置也是_推荐_配置，因为它在大多数情况下可以最大化隐私优势。您只需要 ech 全局选项和指定的 DNS 提供商。以下是使用 Cloudflare 作为名称服务器的示例： 球童文件：

{
	debug  # not required; recommended while testing
	dns cloudflare {env.CLOUDFLARE_API_KEY}
	ech ech.example.net
}

example.com {
	respond "Hello there!"
}

这可以保护您在 ech.example.net 公共名称后面的所有网站（在本例中为 example.com）。 （另一个例子，Cloudflare 对它所服务的所有站点使用 cloudflare-ech.com。我们建议选择一个公共域并用它来保护您的所有站点。） 您选择的外部/公共名称应指向您的服务器。 Caddy 将获得该名称的证书，以便在需要时为 clients 提供安全、可靠的连接。如果没有证书，clients 可能会被迫不安全地连接，或者在某些情况下根本无法连接，这不仅使它们容易受到攻击，而且还有暴露服务器站点名称的风险。 然后，Caddy 使用指定的 DNS 提供商来发布您的各种站点名称的 ECH 配置。它为您网站的域（不是您的 ECH 公共名称）创建（或增强）HTTPS 类型记录。请注意，DNS 提供程序模块是独立维护的，并且可能尚未测试与 HTTPS 类型记录的兼容性。如果您遇到问题，请联系您的模块的维护人员。 如果您有更高级的配置需求，可以使用 JSON 配置（更多详细信息即将推出；目前，请参阅#6862 或查看源代码；或使用 caddy adapt 将 Caddyfile 转换为 JSON）。

测试和验证加密的 ClientHello

首先确保 Caddy 在配置中启用 ECH（和 DNS 模块）的情况下成功运行。您应该看到它正在生成 ECH 配置并将其发布到您的域名的日志。 您将需要使用支持 ECH 的 client。 curl 的一些自定义版本可以这样做，Firefox 和基于 Chrome 的现代浏览器也可以这样做，但您需要首先启用 DNS-over-HTTPS 或 DNS-over-TLS（因为，显然，以明文形式查询受保护域名的 DNS 会暴露该域并违背 ECH 的目的）。 如果重复使用现有域名，请清除 DNS 缓存。 Firefox 在 about:networking#dns 的缓存中有一种方法可以做到这一点。 一旦您拥有合适的 client，请在加载站点时使用 Wireshark 捕获网络数据包。您应该在数据包捕获中_仅_看到外部/公共名称作为 SNI（服务器名称指示符）值。如果您在任何时候看到真实的站点名称，则 ECH 无法正常工作 - 可能是 client 或服务器问题。在提交错误之前，请首先尝试将其确定为服务器问题。但一定要报告服务器错误！谢谢你！ （请注意，ECH 不会自动为 CNAME 域名发布，并且该域名必须已在区域中拥有记录。）
