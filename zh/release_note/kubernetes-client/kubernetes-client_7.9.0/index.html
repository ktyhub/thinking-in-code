kubernetes-client v7.9.0

错误

  • 修复#8024：（httpclient-vertx-5）派生的 client 上的 WebSocket 操作（exec/attach/portForward/WebSocket 支持的手表） - 通过在已构建的 HttpClient 上调用 newBuilder()/build() 生成的操作 - 不再回退到 Vert.x 的裸 WebSocketClient默认值。 Vertx5HttpClientBuilder.build() 派生 client 的短路路径重用了原始 client 的纯 HTTP 连接（其配置完好无损），但始终创建一个全新的 WebSocketClient，根本没有任何选项，丢弃 trust/密钥材料（因此根据 JVM 默认 trust 存储而不是配置的集群 CA 进行 TLS 验证）和配置的限制（maxFrameSize/maxMessageSize 回落到 64 KiB/256 KiB，而不是无限制，maxConnections 回落到 50，而不是 8192，因此即使在普通 HTTP 上，超大的 exec/attach 消息也会被悄悄丢弃）。这仅影响 kubernetes-httpclient-vertx-5，这是选择加入的 - 捆绑的默认 kubernetes-httpclient-vertx (Vert.x 4) 从派生时重用的同一个 client 提供 WebSocket，并且从未受到影响 - 并且它通过 7.8.0 存在于 7.6.0 中。派生比看起来更频繁：OpenShiftClientImpl 在每个 adapt(OpenShiftClient.class) 上派生以安装其 OAuth 令牌刷新拦截器，OpenShiftOAuthInterceptor 在每次令牌刷新时派生，而 BaseClient#newClient 在设置不同的 RequestConfig 时派生。派生的 client 现在完全重用原始的 WebSocketClient，就像他们已经重用其 HTTP client 一样，因此它们不能再偏离它，并且每次派生都不会分配第二个传输。请注意，共享传输还意味着关闭派生系列中的任何 client 也会对整个系列关闭它：从 adapt(OpenShiftClient.class) 获取的 client 上的 close() 现在也会结束它派生自的 client 上的 WebSocket 操作，这已经是 client 的 HTTP 请求以及其他四个实现所做的事情。任何可用的东西都不会丢失，因为原始的 HTTP client 无论如何都被关闭了；变化是每个导数 WebSocketClient 不再处于未封闭状态
  • 修复#8029：（httpclient-vertx-5、httpclient-jetty）WebSocket 连接现在遵循配置的代理，因此 exec/attach/portForward 和 WebSocket 支持的手表不再直接连接到 API 服务器并绕过强制的出口代理。两种实现都通过与 HTTP client 分开的传输（Vert.x 5 WebSocketClient 和 WebSocketClient 后面的第二个 Jetty HttpClient）提供 WebSocket，并且都没有提供代理配置； Jetty 的 WebSocket 传输现在还接收代理 BasicAuthentication 条目。 OkHttp、JDK 和 Vert.x 4 模块不受影响，因为单个 client 可以同时服务这两个模块。在 httpclient-vertx-5 上，配置的连接超时也没有应用于 WebSocket client，因此 WebSocket 连接可能会在超时后挂起。值得指出的一个后果是：当代理凭证无法解码时 - HttpClientUtils.decodeBasicCredentials 对于不是 Basic 的任何内容返回 null，或者其解码值没有完全拆分为两个 : 分隔的部分，因此包含冒号的代理密码就足够了 - client 会回退到在请求上标记 Proxy-Authorization，而不是在传输上配置它。此类 WebSocket 连接现在到达代理并被 407 拒绝，而不是默默地直接完成到 API 服务器，因此仅因为绕过代理而看似有效的设置现在将失败
  • 修复#7807：（kube-api-test）现在解析KUBE_API_TEST_STARTUP_TIMEOUT环境变量，而不是在每次使用时抛出ClassCastException - 该值（始终是String）被传递给Integer / Boolean目标的Class.cast()，这只会扩大引用类型并且从不解析，因此无法通过环境配置超时所有。 @EnableKubeAPIServer 上的新 startupTimeout 属性（例如 @EnableKubeAPIServer(startupTimeout = 180000)）允许以声明方式覆盖它，并且所有三个配置路径（注释、构建器、环境变量）现在拒绝非正值
  • 修复#7983：（mockwebserver）WebSocket 升级现在从 Vert.x 请求处理程序同步执行，而不是从异步 HttpServerRequest#body() 回调执行。推迟升级可以首先处理请求结束事件，因此 HttpServerRequest#toWebSocket() 间歇性地抛出 IllegalStateException: Request has already been read 并且升级丢失（表现为片状 exec/attach 模拟服务器测试）。升级请求不携带body，因此在读取请求之前通过Upgrade标头检测并升级；对于常规 HTTP 请求，异步路径不变
  • 修复 #7955：（java-generator）恶意 CRD 模式值无法再将可执行代码注入生成的 Java 源中。模式控制值（枚举值、CRD 组/版本/名称、属性名称、描述和默认值）作为完全转义的 Java 字符串文字发出，因此，一旦 javac 对其进行解码，带有 Unicode 转义引号的值就无法脱离其文字。作为深度防御，每个生成的类在写入之前也会重新解析和结构验证（启用 Java Unicode 转义预处理以匹配 javac），在任何剩余结构不匹配时中止生成
  • 修复 #8028：（openshift-model、kube-api-test）不再由两个工件运送任何软件包，因此每一对都可以一起放置在 JPMS 模块路径上。 openshift-model 不再捆绑 openshift-model-config 拥有的 io.fabric8.openshift.api.model.config.* 类（其 Export-Package 通配符将它们从该依赖项中内联）；他们仍然通过它接触消费者。 Fabric8ClientInjectionHandler移至io.fabric8.kubeapitest.junit.inject
