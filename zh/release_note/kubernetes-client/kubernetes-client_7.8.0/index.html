kubernetes-client v7.8.0

小版本 发布时间2026年6月29日 来源fabric8io/kubernetes-client 英文原文

kubernetes-client v7.8.0

错误

  • 修复 #7953：(httpclient-jdk) 无正文请求现在保留请求的 HTTP 方法，而不是默默地默认为 GET。 JdkHttpClientImpl.requestBuilder 仅在 body != null 分支内部调用 HttpRequest.Builder.method(...)，因此无主体的 DELETE/POST/PUT/PATCH（例如 client.raw(uri, "DELETE", null)）在 JDK 后端作为 GET 发送；当没有主体时，该方法现在设置为 BodyPublishers.noBody()，匹配 OkHttp、Jetty 和 Vert.x 后端
  • 修复#7435：（kubernetes-client）当单个重新同步周期抛出时，SharedIndexInformer 的定期重新同步不再永久且无声地停止。 DefaultSharedIndexInformer.scheduleResync通过Utils.scheduleAtFixedRate运行重新同步，其自重新调度链仅在前一个周期正常完成时重新准备下一个周期；未捕获的异常异常地完成了（未观察到的）resyncFuture，并且再也没有安排重新同步，没有日志，而独立监视保持 isWatching() 报告 true（需要重新启动才能恢复）。重新同步命令现在捕获并 WARN 记录故障，以便计划在下一个时间间隔再次触发
  • 修复 #7933：(kubernetes-client-api) 确定性 TLS trust 失败（untrusted 证书、过期证书、主机名不匹配）现在被分类为终端并快速失败，而不是由共享 StandardHttpClient.shouldRetry 退避循环重试（约 19 秒耗尽）。分类器遍历 CertificateException、CertPathValidatorException、CertPathBuilderException 和 SSLPeerUnverifiedException 的 getCause() 和 getSuppressed() 树。影响 HTTP 请求和 WebSocket 连接路径上的所有五个 HTTP client 模块（jdk、jetty、okhttp、vertx-4、vertx-5）
  • 修复#7867：（kubernetes-server-mock）WatchEventsListener 现在缓冲在 Vert.x 触发 onOpen 之前安排的传出监视事件，并在 WebSocket 可用后重播它们，从而结束了开放端竞争，其中 CRUD 操作在注册侦听器的 handleWatch 和填充 webSocketRef 的 onOpen 之间着陆，安排了取消引用 null 的发送webSocketRef;由此产生的 NullPointerException 被执行者默默吞掉，事件被丢弃。缓冲事件在初始同步 ADDED 后重播，因此保留顺序
  • 修复 #7896：(kubernetes-client) 现在，当手表完全关闭且 2 秒内没有消息时，AbstractWatchManager.watchEnded() 会发出 WatcherException，补偿 v1/events 上的 GKE 特定行为，其中 GKFE 代理通过裸露的 WebSocket 关闭（代码 1000，无正文）拒绝过时的 resourceVersion，而不是{"type":"ERROR","code":410}，使用相同的过时资源版本导致无限期的重新连接循环
  • 修复#7907：(httpclient-vertx-5) WebSocket-over-TLS 操作（exec/attach/portForward/WebSocket 支持的监视，以及依赖于它们的 CRD 建立等待）现在再次 trust 集群证书。 Vert.x 5.1 重写了 WebSocket client，以通过每个连接 ClientSSLOptions 解析 TLS，该连接忽略了 client 用作 trust 材料唯一载体的自定义 SslContextFactory，因此 WebSocket 握手默默地回退到默认的 JVM trust 存储，PKIX 失败验证，并挂起至 client 端超时（常规 HTTPS 请求/响应不受影响）。 HTTP 和 WebSocket clients 现在均使用从提供的 trust/密钥管理器派生的 Vert.x TrustOptions/KeyCertOptions 进行统一配置
  • 修复#7873：（kube-api-test）Utils.findFreePort 现在记录它在 JVM 的生命周期内分发的每个端口，并跳过已返回的任何端口，消除了作为 JUnitExtensionOnMethodTest.simpleTest2 薄片出现的背靠背重复端口窗口 - 探测器 ServerSocket 在调用者绑定它之前已关闭，因此 EtcdProcess.startEtcd() 和KubeAPIServerProcess.startApiServer() 可以从 Random.nextInt 获取相同的端口，etcd 将赢得绑定，apiserver 将使用 bind: address already in use 退出 1，在 ProcessReadinessChecker 中显示为 Connection reset by peer
  • 修复#7857：(kubernetes-server-mock) WatchEventsListener.onClosing 现在在侦听器的发送执行器上对服务器端 WebSocket.close(...) 进行排队，而不是直接在 Vert.x 事件循环上调用它。这保留了已在该执行器上排队的任何数据帧的 FIFO 顺序，因此在 client 启动的监视关闭之前安排的事件（例如 watch.close() 之前的最终 create/delete 上的 ADDED/delete 对）在关闭帧之前传递，而不是通过针对已关闭套接字的写入而默默地丢弃
  • 修复#7832：（声纳）重新中断 8 个生产代码 catch 块中的线程，这些块吞没了 InterruptedException 而不保留中断状态（S2142）
  • 修复#7841：（mockwebserver）将 Dispatcher 关闭分为两个阶段，因此 MockDispatcher 仅在 HTTP 服务器耗尽后拆除每个会话的 WebSocketSession 执行器，从而删除了正在进行的升级的 onOpen 可能落在关闭执行器上的窗口。 shutdown() 仍然在 httpServer.close() 之前运行，以解除阻塞的调度（例如 QueueDispatcher.take()）；新款 releaseResources() 紧随其后。 WebSocketSession.send() 还可以防御性地追赶 RejectedExecutionException，因此任何剩余的关闭竞赛都会保持沉默，而不是像 Vert.x Unhandled exception 那样冒泡。 KubernetesMixedDispatcher 现在将两个生命周期挂钩委托给其内部 MockDispatcher，修复了 CRUD 模式 WebSocket 会话执行器从未关闭的先前存在的泄漏
  • 修复#7779：(kubernetes-client) ExecWebSocketListener 现在通知用户提供的 ExecListener 与 terminateOnError / 通道 3 退出状态完成竞争的传输级错误 - listener.onFailure（或 onClose）仅触发一次，由专用标志门控，而不是 si
