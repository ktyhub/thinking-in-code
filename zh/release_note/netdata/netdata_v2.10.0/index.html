发布亮点

秘密管理

将收集器凭据保留在纯文本配置文件中。 Netdata 现在允许您在收集器配置中引用机密，而不是直接存储它们。密码、令牌和 API 密钥在运行时从您选择的源解析。

解析器

Netdata 提供四种解析器类型，从简单到企业级：

旋转变压器 语法 最适合
环境变量 ${env:VAR_NAME} 秘密已注入Netdata服务环境
文件 ${file:/absolute/path} 存储在磁盘上本地文件中的机密（Docker 机密、Kubernetes 作为卷安装的机密）
命令 ${cmd:/absolute/path args} trusted 本地命令返回的机密（例如 1Password CLI、自定义脚本）
秘密库 ${store:<kind>:<name>:<operand>} 在云提供商或 Vault 中集中管理的秘密

支持的 Secretstore 后端

对于集中管理机密的组织，Netdata 与四个机密存储后端集成：

后端 亲切 操作数格式 认证方式
AWS Secrets Manager aws-sm secret-name[#key] 环境凭证、ECS 任务角色、EC2 实例配置文件
Azure 密钥保管库 azure-kv vault-name/secret-name 服务主体、托管身份、默认凭证链
谷歌秘密管理器 gcp-sm project/secret[/version] 元数据服务器、服务帐户文件
HashiCorp Vault vault path#key 令牌、令牌文件

通过 Netdata 动态配置 UI (Collectors → go.d → SecretStores) 或通过 /etc/netdata/go.d/ss/ 下的配置文件配置机密存储。

示例

MySQL 收集器引用 HashiCorp Vault 的密码：

# /etc/netdata/go.d/mysql.conf
jobs:
  - name: mysql_prod
    dsn: "netdata:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

您可以自由混合解析器类型。例如，从环境变量中读取用户名，并从同一配置值中的密钥库中读取密码：

jobs:
  - name: mysql_prod
    dsn: "${env:MYSQL_USER}:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

它是如何工作的

  • 每次收集器作业启动或重新启动时都会解析机密。
  • 更新秘密存储会自动重新启动使用它的收集器作业，以便它们获取新的凭据。
  • Secretstore 配置值本身也支持 ${env:...}、${file:...} 和 ${cmd:...} 解析器，因此后端凭据也不需要以纯文本形式存储。

[!提示] 有关详细设置、后端特定身份验证指南和故障排除，请参阅机密管理文档。

  • 复制仪表板以帮助从现有仪表板创建新的自定义仪表板

Nagios 插件收集器

使用新的 Nagios 插件收集器 直接在 Netdata 内运行 Nagios 兼容插件 和自定义脚本。任何遵循 Nagios 插件输出格式 的可执行文件都可以开箱即用：打包的 Nagios 插件、自定义 shell 脚本或编译的二进制文件。

你得到什么

特色 详情
检查状态监控 跟踪进程退出代码中的 OK、WARNING、CRITICAL 和 UNKNOWN 状态
自动性能数据图表 Nagios 性能数据值自动解析并绘制图表
基于阈值的警报 当 perfdata 包含警告/严重阈值时，Netdata 会生成阈值状态图（正常/警告/严重）并创建内置警报
执行指标 测量每次检查的运行持续时间、CPU 时间和内存使用情况
Nagios 式调度 可配置的检查间隔、重试间隔、最大检查尝试次数和时间段
软/硬状态逻辑 在触发警报之前，在 retry_interval 至 max_check_attempts 上重试非正常结果，从而防止因瞬时故障而产生误报

内置警报

收集器附带四个库存警报：

警报 触发时间
nagios_job_execution_state_warn 支票处于 WARNING 硬状态
nagios_job_execution_state_crit 支票处于 CRITICAL 硬状态
nagios_job_perfdata_threshold_state_warn perfdata 指标超出其警告阈值
nagios_job_perfdata_threshold_state_crit perfdata 指标超过其临界阈值

所有库存警报都会抑制软重试状态。仅在配置的 max_check_attempts 连续失败后才会触发警报。

示例

# /usr/local/lib/netdata/checks/check_api.sh
#!/bin/sh
resp=$(curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time 5 "$1" 2>/dev/null)
code=$(echo "$resp" | cut -d' ' -f1)
time=$(echo "$resp" | cut -d' ' -f2)

[ "$code" -ge 500 ] && echo "CRITICAL - HTTP $code | response_time=${time}s;~:2;~:5" && exit 2
[ "$code" -ne 200 ] && echo "WARNING - HTTP $code | response_time=${time}s;~:2;~:5" && exit 1
echo "OK - HTTP $code | response_time=${time}s;~:2;~:5"
exit 0
# /etc/netdata/scripts.d/nagios.conf
jobs:
  - name: api_health
    plugin: /bin/sh
    args: ["/usr/local/lib/netdata/checks/check_api.sh", "http://localhost:8080/health"]
    check_interval: 1m
    retry_interval: 15s
    max_check_attempts: 3

这会生成检查状态图、执行指标，并且因为脚本会发出带有阈值的 perfdata（response_time 带有警告 >2 秒/临界 >5 秒），所以会生成带有阈值状态图和内置警报的自动响应时间图表。

[!提示] 有关完整的设置指南、自定义脚本演练和时间段配置，请参阅 Nagios 插件收集器文档。

Azure Monitor 收集器

使用新的 Azure Monitor 收集器 从 Netdata 监视整个 Azure 基础结构。它通过自动资源发现从 Azure Monitor 指标 API 收集平台指标：将其指向您的订阅，它会找到您的资源，将它们与内置配置文件（预配置的指标集）进行匹配，然后开始收集指标。

[!重要] 这是一个 alpha 功能。配置格式可能会在即将发布的版本中发生变化。

你得到什么

特色 详情
38 个内置服务配置文件 涵盖计算、数据库、网络、存储、AI/ML、分析、容器等的 1,300 多个指标
自动发现 通过 Azure 资源图发现资源并启用匹配配置文件，无需按资源进行配置
多重订阅 在单个收集器作业中监视多个 Azure 订阅的资源
灵活的发现范围 按资源组、区域或标签缩小发现范围，或使用自定义 Azure 资源图 KQL 查询
内置警报 针对 Azure 关键资源状况的预配置警报
用户界面配置 通过 Netdata 动态配置 UI 进行配置，无需编辑文件
