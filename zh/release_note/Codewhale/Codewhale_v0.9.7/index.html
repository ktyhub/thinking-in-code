Codewhale v0.9.7

Codewhale 是 Shannon Labs 的公共产品。 codewhale 命令、npm 包和发布资产名称保留小写技术名称 标识符。旧版 npm 包 deepseek-tui 已弃用，并且 不再收到进一步的发布。来自 v0.8.x 旧版 deepseek 的用户 / deepseek-tui 名称应随 docs/REBRAND.md 一起迁移。

安装

推荐 — npm（一个命令，两个入口点）

npm install -g codewhale

包装器下载匹配的 codewhale 和 codew 命令资产 从本版本开始。两者都包含相同的编译运行时。

Docker / GHCR

docker run --rm -it \
  -e DEEPSEEK_API_KEY="$DEEPSEEK_API_KEY" \
  -v codewhale-home:/home/codewhale/.codewhale \
  ghcr.io/hmbown/codewhale:v0.9.7

该图像公开与 codewhale 和 codew 相同的运行时。的 latest 标签也在发布时进行了更新。

货物（Linux / macOS）

cargo install codewhale-cli --locked

Cargo 包安装 codewhale。 Cargo 无法创建第二个命令 来自一个二进制目标的别名；想要更短拼写的用户可以添加 codew 到已安装的可执行文件的符号链接。 npm、Homebrew、存档、 shell-installer 和容器通道直接安装这两个命令名称。

  • 对于安装程序路径，运行 CodeWhaleSetup.exe；它安装 codewhale.exe和codew.exe下 %LOCALAPPDATA%\Programs\CodeWhale\bin 并将该目录添加到 当前用户路径。

v0.9.7 里有什么

Codewhale v0.9.7 保持目录普通。 Grok 4.6 作为普通目录登陆 OrcaRouter 作为一个行而不是一堆提供者形状的特殊情况进行连接 指定的提供商，并通过解除 lru 中的恐慌安全建议来清除 导致它发生的引脚，而不是生活在它周围。

添加

  • Grok 4.6 是直接 xAI 默认值，grok 别名移至其上， grok-4.5 仍然可以明确选择。它的 500K 上下文、文本/图像输入、 工具和结构化输出支持，low/medium/high/xhigh 推理 努力（默认high）和服务器端网络搜索均来自 models.dev 形状的目录而不是特定于模型的代码。 reasoning_effort 仅在确切的第一方 https://api.x.ai/v1 路线上到达线路， 并且使用感知的 200K 代币定价边界范围仅限于直接 xAI，因此 重用模型 slug 的聚合器路由无法继承 xAI 计费。
  • OrcaRouter 是一流的命名提供商：ORCAROUTER_API_KEY，默认基础 URL https://api.orcarouter.ai/v1，默认deepseek/deepseek-v4-pro， orcarouter/auto 路由、CLI --provider 选择器和 TUI 选择器条目 （＃5321）。

已更改

  • 推理努力标准化和模型选择器读取模型已发布的内容 reasoning_options 从目录中列出，而不是将每条路线折叠到 历史性的低/中阶梯。发布工作量列表的任何目录行 保留自己的词汇。
  • 文档记录 DeepSeek 的实时 DeepSeek-V4-Pro-0813 后端标签，而 可调用的 API ID 仍为 deepseek-v4-pro。没有别名被重新映射，也没有 deepseek-v4-pro[1m] 选择器已发送。

已修复

  • 复制用户或助理消息时采用其规范内容而不是 重新序列化转录行，保留角色字形，延续轨道，以及 clipboard 的视觉包装，同时保留创作的 Unicode， Markdown 和硬换行。工具和思维细胞保留在现有的基础上 完整转录本路径（#5319）。
  • load_session 不再在每次读取时运行崩溃恢复。快照读取去 通过无副作用的 load_session_snapshot 并且恢复是明确的 通过 recover_session_for_resume，因此嵌入主机检查耐用性 工具仍在运行时的会话不再获得虚假的崩溃修复 （＃5320）。

安全

  • lru 移动到 0.18 以清除 RUSTSEC-2026-0253，其中 LruCache::pop() 是 不安全，可能会留下悬空列表指针。 ratatui-core 传递强制 lru ^0.16 的 =0.1.0 引脚被抬起，因此 ColorCompatBackend 现在从跟踪光标应答 get_cursor_position() state — 上游推荐的启动 CPR 竞赛的解决方法 （ratatui/ratatui#2483、ratatui/ratatui#2640）该引脚最初有效 周围。 ratatui 本身保持固定在 =0.30.0，因此 API 表面为 不变。

已知问题

  • 集成测试 exec_persistent_service::failed_exec_kills_pending_service_and_exits_nonzero 是并行负载下确认的薄片（“服务 pid 文件从未出现”）。 它是孤立通过的，与任何 v0.9.7 更改无关。
