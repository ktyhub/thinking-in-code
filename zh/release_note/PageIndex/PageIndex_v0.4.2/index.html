PageIndex v0.4.2

PageIndex 现在的构建成本比矢量索引更便宜。

  • PageIndex SDK、本地或云 — 无矢量、基于推理的 RAG，端到端。
  • 更快的索引 — PageIndex Flash 引擎从布局统计中获取树：结构生成本身不涉及 LLM，LLM 仅写入节点摘要，并且树扩展同时提出一波节点。
client = PageIndexClient()
client.submit_document("report.pdf")
client.chat("What does the report conclude?")

索引、聊天、代理集成，一台 client。 本地模式不需要服务器、矢量数据库、PageIndex API 密钥。

亮点

  • Flash引擎：本地默认（mode="standard"保留经典的LLM管道）。当 trustworthy 时，会消耗嵌入的书签，并且默认情况下会启用树优化 — optimize="merge" 用于确定性的无 LLM 传递，"full"（默认）添加 LLM 扩展，它同时运行一波节点，而不是一次一个往返。
  • 一个完整的表面，本地和云：PageIndexLocalClient(storage_path=...) 与云相同的 client — 提交、树、页面内容、聊天和代理工具都存在于两种模式中，因此代码在它们之间移动不变。
  • 云文档，您自己的模型：api_key 决定您的文档所在的位置；配置好的聊天模型决定谁回答——并将两者结合起来。 PageIndexClient(api_key="pi-...", chat_model="openai/gpt-5.2") 在实时云工具集上运行相同的进程内文档 QA 引擎。页面内容通过您的流程流向您的提供商（根据您的凭证）； doc_id 以提示级别为目标； enable_citations 保留托管聊天。
  • 代理集成：云 MCP 工具合约，正在处理 - client.agent_tools()（普通函数）、as_openai_tools()、as_anthropic_tools()、as_claude_mcp()，以及用于系统提示的一键调用 openai_agent_config() / anthropic_runner_config() / claude_agent_config() 捆绑包和 agent_instructions()。云clients通过MCP桥获取实时服务器工具集（默认为只读端点）；本地 clients 获取具有相同架构和信封的进程内子集 — 代理提示端口不变。
  • 聊天界面：chat() — 在任何后端提问、回答； chat(stream=True) 显示运行情况，将思考和工具调用融入文本中，或者通过 .events 作为键入事件； chat(protocol="responses" | "messages") 使用该协议自己的形状本机驱动 OpenAI 响应或人择消息 API，而 chat_completions() 保留 OpenAI 兼容的信封 - 所有这些都具有 doc_id 定位、流式传输、诚实使用会计和跨轮提示缓存连续性。脚本逐字附加：协议通道的输出不变地返回到下一个请求。
  • 模型和连接旋钮：index_model / chat_model、index_backend / chat_backend（以及每次调用的 backend）逐字传递到每个通道 - LiteLLM 路由提供商、无钥匙 OpenAI 兼容服务器、Azure/Bedrock/Vertex 包括在内。
  • index= / chat= 插槽：平面参数的分组拼写 - 字符串简写或映射（index={"model": ..., "storage_path": ...}、chat={"model": ..., "backend": ...}）。 "cloud" / "local" 命名一侧，可选的 mode= 对其进行交叉检查，PageIndexLocalClient / PageIndexCloudClient 占用相同的插槽。 PageIndexCloudClient() 读取为 PAGEINDEX_API_KEY；无论环境如何，裸露的 PageIndexClient() 都会保持在本地。
  • 键入的配置形状：IndexConfig / CloudIndexConfig / LocalIndexConfig / ChatConfig，附带 py.typed，以便您的类型检查器看到它们。
  • 没有什么会悄然失败：未知的键、混合的方面、空值和模式/内容冲突拒绝使用消息中的法律词汇进行构建；无效凭据或丢失模型会使索引运行失败，而不是存储带有空白摘要的文档；每个云错误都带有其 HTTP 状态。
  • 依赖关系：Python >= 3.10；基础安装中的 openai-agents（聊天引擎）； SDK 的 [anthropic] 和 [claude] 附加产品。 Pillow >= 9.0 现在是 highlight_region 的必需依赖项。

也在0.4.2

  • 在您的 Claude 订阅上运行。 将 index_model 或 chat_model 设置为 claude-code/ 型号，例如chat="claude-code/opus"、索引和 chat() 通过 Claude 代码调用 Claude 模型：您的计划涵盖使用情况，并且不需要 API 密钥 (pip install -U "pageindex[claude]")。它的本地索引在 Flash 模式下运行。 同样在 0.4.1 中：
  • Flash 可以正确读取文件。 每页顶部的“目录”链接不再隐藏文件标题（AmEx 10-K 在一个节点中包含前 131 页，现在索引便宜约 30%）。第 20 条注释与大纲相连，两份标题相同的审计报告各保留一个标题，一页一页构建的幻灯片为一个部分。
  • **在任何脚本中扩展。**树扩展现在分割以中文、日语、阿拉伯语、印地语和其他脚本标题的部分，在无法解析的答复后再次询问，并将短节点自己的文本保留为摘要长度（summary_max_words），而不是固定的 200 个标记。
  • 更多提供程序。 节点摘要会关闭 LiteLLM 未标记的模型上的推理，其中包括 OpenRouter，并且 chat(protocol="responses" | "messages") 发送您编写的模型名称，因此与 OpenAI 和 Anthropic 兼容的服务（例如 OpenRouter）可以在这些通道上工作。 同样在 0.4.0 中：
  • 更便宜的 Flash 索引。 叶子仅总结其自己的文本，文档描述读取顶级摘要，在接受它的模型上，节点摘要默认为 reasoning_effort="none"（summary_reasoning_effort 选择另一个值），并且每个部分扩展询问一次，并且仅当阅读各个片段比整体更便宜时才进行拆分。
  • 新的默认型号。 未设置型号时，本地模式索引为 gpt-6-luna，答案为 gpt-6-sol。没有聊天模型的云 client 仍使用托管聊天。
  • litellm 1.105.0 或更新版本，第一个支持 gpt-6-luna 的版本。 pip install -U pageindex对其进行了升级。 同样在 0.2.22 中：
  • Flash 保持单词完整。 单词间隙是根据每个字符代码的字体宽度来测量的，因此页面文本和标题不再拆分“infe rence”之类的单词，并且章节标题再次与其书签匹配。
  • 更稳定的 Flash 树。 索引不再因“标记为最终后删除或更改”而失败，运行标题不再提前将介绍或前言剪切一页，并且展开仅保留在节点内打印的小节。 optimize_tree(pdf_path) 和 tree_optimize CLI 按布局顺序读取两列页面，不再需要 pymupdf。
  • 标准模式。 当模型在该部分自己的上方列出标题（“第 3 章”上方的“第二部分”）时，大部分拆分不再无限循环，并且目录项在开始之前永远不会结束。 同样在 0.2.21 中：
  • 突破性：一棵树形状，本地和云。 get_tree 节点在两种模式下都携带 start_index、end_index 和 summary； page_index 和 prefix_summary 不见了。在新索引的文档中，父级的范围和摘要覆盖其整个部分，并且其第一小节之前的页面成为 "<title> (intro)" 节点。早期索引的文档保留自己的范围和摘要。
  • 本地 get_ocr(format="node") 返回每个节点自己的文本。 父节点的文本在其第一个小节开始的页面处停止，并且当介绍节点保留该开头时为空；介绍节点显示为其自己的条目。之前索引的文档也以这种方式读取，无需重新索引。
  • 节点导航。 pageindex.utils 中的 get_node、get_node_parent、get_node_path 和 get_node_map 从 get_document_structure() 获取树并在本地遍历它，因此一次获取可服务任意数量的查找。
  • 标准模式像 Flash 一样进行总结。 每个部分的摘要在其子部分完成后立即开始，并且短节点保留自己的文本。 同样在 0.2.20 中：
  • 更快的 Flash 索引。 节点摘要首先运行最深的节点，并在树扩展仍在决定时开始，因此模型通道永远不会闲置：222 页的报告索引需要 73 秒而不是 98 秒，一本 758 页的书需要 137 秒而不是 174 秒。现在每个摘要的上限为 summary_max_words（默认 150），这将摘要阶段又减少了三分之一到一半。
  • client 上的索引旋钮。 summary_max_words、summary_concurrency、use_embedded_toc 和 optimize 可在 PageIndexClient(...) 或 index= 插槽中设置（本地闪存模式），并且 --summary-max-words / --summary-concurrency 加入 CLI。 summary_concurrency 立即降低整个索引通道以实现严格的速率限制。
  • 人为车道采用您所写的模型。 chat(protocol="messages")、anthropic_runner_config() 和 claude_agent_config() 使用您设置的 chat_model，因此不再需要 model=。前缀选择路线：bedrock/、vertex_ai/ 和 azure_ai/ 前往 Bedrock、Vertex AI 和 Azure AI Foundry，其他任何东西都直接前往 Anthropic。 [anthropic] extra 现在需要 anthropic>=0.122.0。

  • resolve_citations 返回可显示的引文。 client.resolve_citations(answer, doc_id=...) 现在返回 {"answer": ..., "citations": [...]} — 每个引文标签被编号 Markdown 链接 [[1]](#pageindex-citation-01) 替换的答案文本，以及每个引文的完整数据由 anchor 和 index 引导。

  • get_document_id(name) 在一次 API 调用中通过显示名称查找文档的 ID，这对于将引文文档名称解析为 ID 很有用。
  • 提示对齐：SDK 的本地引用和发现提示现在与聊天 MCP 服务器匹配 - 删除了发明的“来源”页脚，恢复了缺少的改写和重试持久性步骤，并且从发现说明中删除了仅 SDK 的分页教程。 同样在 0.2.17 中：
  • 引用解析为页面坐标。 client.get_citations(answer, doc_id=...) 读取引用答案中的引用标签 - chat(citations=True) 写入的 <cite doc="…" page="…" block="…"/> 标签和托管聊天写入的 <doc=…;page=…;block=…> 标签 - 并为每个引用返回一个条目以及文档的 ID；对于以 beta_headers=["block_reference"] 索引的云文档上的块级引用，该条目还包含块的页面、边界框、类型和文本。传递 doc_id= （chat(doc_id=...) 所采取的）来确定名称查找的范围，或者省略它以针对您的库进行解析。
  • 一个块，一个调用。 client.get_block(doc_id, block_id) 返回单个布局块，因为 API 为其提供服务 — {doc_id, page, block_id, bbox, block_type, text}、bbox 为 [x0, y0, x1, y1]，以页面宽度和高度的千分之一 (0-1000) 表示，原点位于左上角。仅限云；本地页面内容没有块。
