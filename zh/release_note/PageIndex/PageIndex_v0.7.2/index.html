PageIndex v0.7.2

修订 发布时间2026年11月19日 来源VectifyAI/PageIndex 英文原文

PageIndex v0.7.2

  • 比矢量 RAG 便宜：对于索引和查询。
  • 更快：树是根据布局统计数据创建的。
  • 统一 SDK：无矢量 RAG。 本地或云，用于索引和聊天。
  • 在您的克劳德订阅上运行。 索引、聊天、代理集成，一台 client。 本地模式不需要服务器、矢量数据库、PageIndex API 密钥。
client = PageIndexClient()
client.submit_document("report.pdf")
client.chat("What does the report conclude?")

亮点

  • Flash引擎：本地默认（mode="standard"保留经典的LLM管道）。当 trustworthy 时，会消耗嵌入式书签，并且默认情况下会启用树优化 — optimize="merge" 用于确定性的无 LLM 传递，"full"（默认）添加 LLM 扩展，它会同时运行一波节点，而不是一次一个往返。
  • 一个完整的表面，本地和云：PageIndexLocalClient(storage_path=...) 与云相同的 client — 提交、树、页面内容、聊天和代理工具都存在于两种模式中，因此代码在它们之间移动不变。
  • 云文档，您自己的模型：api_key 决定您的文档所在的位置；配置好的聊天模型决定谁回答——并将两者结合起来。 PageIndexClient(api_key="pi-...", chat_model="openai/gpt-5.2") 在实时云工具集上运行相同的进程内文档 QA 引擎。页面内容通过您的流程流向您的提供商（根据您的凭证）； doc_id 以提示级别为目标； enable_citations 保留托管聊天。
  • 代理集成：云 MCP 工具合约，正在处理 - client.agent_tools()（普通函数）、as_openai_tools()、as_anthropic_tools()、as_claude_mcp()，以及用于系统提示的一键调用 openai_agent_config() / anthropic_runner_config() / claude_agent_config() 捆绑包和 agent_instructions()。云clients通过MCP桥获取实时服务器工具集（默认为只读端点）；本地 clients 获取具有相同架构和信封的进程内子集 — 代理提示端口不变。
  • 聊天界面：chat() — 在任何后端提问、回答； chat(stream=True) 显示运行情况，将思考和工具调用融入文本中，或者通过 .events 作为键入事件； chat(protocol="responses" | "messages") 使用该协议自己的形状本机驱动 OpenAI 响应或人类消息 API，而 chat_completions() 保留 OpenAI 兼容的信封 - 所有这些都具有 doc_id 定位、流式传输、诚实使用会计和跨轮提示缓存连续性。脚本逐字附加：协议通道的输出不变地返回到下一个请求。
  • 模型和连接旋钮：index_model / chat_model、index_backend / chat_backend（以及每次调用的 backend）逐字传递到每个通道 - LiteLLM 路由提供商、无钥匙 OpenAI 兼容服务器、Azure/Bedrock/Vertex 包括在内。
  • index= / chat= 插槽：平面参数的分组拼写 - 字符串简写或映射（index={"model": ..., "storage_path": ...}、chat={"model": ..., "backend": ...}）。 "cloud" / "local" 命名一侧，可选的 mode= 对其进行交叉检查，PageIndexLocalClient / PageIndexCloudClient 占用相同的插槽。 PageIndexCloudClient() 读取为 PAGEINDEX_API_KEY；无论环境如何，裸露的 PageIndexClient() 都会保持在本地。
  • 键入的配置形状：IndexConfig / CloudIndexConfig / LocalIndexConfig / ChatConfig，附带 py.typed，以便您的类型检查器看到它们。
  • 没有什么会悄然失败：未知的键、混合的方面、空值和模式/内容冲突拒绝使用消息中的法律词汇进行构建；无效凭据或丢失模型会使索引运行失败，而不是存储带有空白摘要的文档；每个云错误都带有其 HTTP 状态。
  • 依赖关系：Python >= 3.10；基础安装中的 openai-agents（聊天引擎）； SDK 的 [anthropic] 和 [claude] 附加件。 Pillow >= 9.0 现在是 highlight_region 的必需依赖项。

也在0.7.2

  • 页面提取不再单独收取上传费用。 PageExtractClient().extract("invoice.pdf", schema) 随其作业上传文件，作业是唯一的费用：提取，但至少是文件的上传价格（每 1,000 页 0.10 美元）。
  • litellm 1.109 或更新版本。 1.106 下面的上限消失了：1.109 修复了它的 mcp 导入。 pip install -U pageindex对其进行升级。 同样在 0.7.1 中：
  • Page Search and Page Extract get clients of their own. PageSearchClient and PageExtractClient sit beside PageIndexClient, on the same API key and the same documents.他们上传的内容没有构建大纲索引，PageIndexClient.build_outline_index(doc_id) 随后构建了一个。 PageExtractClient().extract("invoice.pdf", schema) 将文件保留在“页面提取”集合中，因此同一文件不会上传两次。
  • Page Search and Page Extract keys are read too. Without PAGEINDEX_API_KEY, PageSearchClient reads PAGEINDEX_SEARCH_API_KEY and PageExtractClient reads PAGEINDEX_EXTRACT_API_KEY, so their users keep the key they have once their account moves to PageIndex.来自 pageindex-search 或 pageindex-extract：从旧的 SDK 迁移。
  • BREAKING: search and extraction moved off PageIndexClient. search(), search_documents(), extract(), get_extract(), list_extracts(), wait_extract(), cancel_extract() and delete_extract() are now on PageSearchClient(client=client) and PageExtractClient(client=client). 同样在 0.7.0 中：
  • client 中的页面搜索。 client.search(questions, document=doc_id) 对于每个问题返回可能回答该问题的页面，每个页面都有其相关性。 Without document it searches across a collection, a folder, a metadata filter or all your documents: the most relevant documents are found first, and only their pages searched. client.search_documents(questions, ...) 仅返回文档。仅云。
  • Page Extract in the client. client.extract("report.pdf", schema) returns JSON that fits a JSON Schema or a Pydantic model, from a PDF or an uploaded document, and waits for the result by default. get_extract()、list_extracts()、wait_extract()、cancel_extract() 和 delete_extract() 管理作业。仅云。
  • 页面作为图像，以及可以更改的元数据。 page_image(doc_id, page, box=...) 以 JPEG 字节形式返回页面，或者仅返回 box 中的部分，绘制得更清晰。 update_document(doc_id, metadata=...) sets or removes metadata keys, list_documents(filter=...) lists documents by metadata, wait_document() waits until a document is ready and get_collection() returns one collection.仅限云，wait_document() 除外。 同样在 0.6.0 中：
  • PageIndex Cloud 上的集合。 create_collection()、list_collections() 和 delete_collection() 管理它们，submit_document(..., collection_id=...) 将文档存储在一个文档中，list_documents(collection_id=...) 列出它。没有声明元数据字段的集合从其文档的元数据中学习它们。
  • Own-model chat kept to one collection, with boxed citations. chat(collection_id=...) keeps cloud discovery inside that collection, and citations="cite_with_boxes" makes each citation carry a box on its page.调用从未见过其图片的页面上的框被丢弃。
  • get_citations 解析库路径，例如 Research/report.pdf，这是 MCP 服务器现在引用文档的方式。 同样在 0.5.3 中：
  • Cheaper, faster summaries. Node summaries now run with the least thinking each model takes: "none", else "minimal", else "low", and on Claude its own off switches.在一份 22 页的收益报告中，gpt-5-nano 的摘要成本仅为十分之一，并且在 9 秒内完成，而不是 64 秒，而 o3 的成本还不到一半。
  • 索引停止为它从未读取的缓存写入付费。 在对输入上方的提示缓存写入进行计费的模型（例如 GPT-5.6 及更新版本）上，索引不写入缓存：gpt-6-luna 为 $0.164 而不是 $0.184 索引 1,000 个页面。 index_backend={"prompt_cache_options": {"mode": "implicit"}} 保留模型自己的缓存，这使得在 30 分钟内再次索引的文档可以读取第一次运行的缓存。
  • 突破性：您选择的推理工作会按选择到达。 summary_reasoning_effort 或 index_backend reasoning_effort 模型不会在不可见的情况下被丢弃（gpt-5-nano 考虑到 "none" 以其完全默认的思维运行，比未设置慢 7 倍）。现在它会在任何模型调用之前引发并说明要传递的内容。 同样在 0.5.2 中：
  • PageIndex Cloud 上的 Flash。 client.submit_document("report.pdf", mode="flash") 使用 Flash 构建云文档树，就像本地模式一样。
  • BREAKING：云 mode 仅需要 "flash" 或什么也不需要。 "standard" 仅保留本地值，并且任何其他值（包括 "mcp"）都会引发而不是传递到服务器。 同样在 0.5.1 中：
  • Flash 以少得多的内存解析大型 PDF。 在具有一两个 CPU 的机器上，或者对于具有 Type-3 字体的文档，Flash 的解析器现在一次保存一页而不是整个文档：一本 1,665 页的教科书峰值为 434 MB，而不是 3.1 GB。树没有变化。
  • 损坏的字体映射不再挂起 Flash。 字体的 ToUnicode 映射中的杂散 )、{ 或 } 会导致解析循环，直到内存耗尽；此类 PDF 现在已建立索引。 同样在 0.5.0 中：
  • 推理模型保留其推理。 聊天运行的每个请求以及之后的每个回合都会在每条路线上向模型发送自己的推理：Claude 的思维、来自 Kimi、GLM、Qwen 等人的 reasoning_content、OpenRouter 的 reasoning_details、GPT 的推理项、Gemini 的思想签名和 Bedrock 的加密推理。 Claude 现在也可以通过 OpenRouter 等网关读取提示缓存。
  • reasoning_effort="none" 关闭了 Claude 的思维，在 chat() 和索引摘要中，它是默认值（Sonnet 5.5 仍然在工具调用之间思考）。在 Opus 5.5 和 Fable 上（无法将其关闭）以及在任何 claude-code/ 型号上，显式 "none" 会引发，并且汇总默认值会以低值运行它们。
  • 比 LiteLLM 的模型地图更新的模型，例如 bedrock/global.openai.gpt-6.1-terra：在 LiteLLM 拒绝的情况下，PageIndex 一次获取 LiteLLM 发布的地图并再次发送。 LITELLM_LOCAL_MODEL_COST_MAP=True 将其关闭。
  • 在索引、聊天和云 API 上重试遵循官方 OpenAI 和 Anthropic SDKs：速率限制等待服务器请求的时间，最多 60 秒，丢失的 OpenAI 密钥立即失败，并且不重试 402、413 和 422。 Flash 摘要一次运行 128 个，因此大型文档的摘要阶段大约快四分之一。
  • Claude 订阅索引作为一个 Claude 代码工作流程运行，一次最多可生成 64 个摘要，而不是 16 个。PAGEINDEX_CLAUDE_CODE_WORKFLOW=0 每次调用都会返回一个进程。
  • 分叉的工作进程不再挂起。 从具有 client（Linux 上的 multiprocessing、gunicorn --preload、Celery）的进程分叉的工作进程不再挂起或读取另一个进程的回复。
  • 突发事件：extra_body 到达每个提供商。 只有 OpenAI 获取的字段，例如 store 和 verbosity，在 Claude 和 Gemini 上未被看到而被丢弃，现在被加注； litellm.drop_params = True 再次掉落它们。 extra_body拒绝reasoning_effort，它有自己的说法。
  • 重大：云读取超时在重试后会引发请求“ConnectionError”而不是“ReadTimeout”，因此 except requests.Timeout 不再捕获它。
  • Gemini 历史记录在没有 model 的情况下保存，因为 0.4.5 到 0.4.7 返回了它，发送早期的 Gemini 工具调用而没有自己的思想签名。使用 model 保存的历史记录将保留它们。 同样在 0.4.7 中：
  • 读取和更改文件夹的元数据字段。 get_metadata_schema(folder_id) 返回适用于文件夹文档（其顶级文件夹的，否则帐户的）的字段，delete_metadata_schema(folder_id) 删除文件夹声明的字段，以便可以使用 create_metadata_schema() 再次声明它们。文档保留其元数据。仅云。 同样在 0.4.6 中：
  • 消息通道与 Anthropic 2.2 配合使用。 Anthropic 2.2.0 默认在服务器持有的线程上运行其工具运行程序，因此在 OpenRouter 的 Anthropic 端点等代理后面，第二个模型调用失败，返回的 messages 重复了最终答复。 chat(protocol="messages") 现在在每个回合都会发送整个对话，就像早期的 anthropic 版本一样，而 messages 每个回合都会传送一次。 同样在 0.4.5 中：
  • 多轮聊天保留提示缓存。 使用 API 聊天模型，chat_completions() 和 chat(protocol="chat_completions") 在 messages 下返回运行的新消息（工具调用、工具结果、答案）（使用 stream_metadata=True 进行流式传输：在结束使用块上）。附加它们，history += r["messages"]，下一回合将准确地重新发送模型所看到的内容，因此提示缓存会继续命中。 Responses 也将其转录本移至 messages； items 仍然会读取，并带有 DeprecationWarning，直到以后的版本将其删除。
  • 结果读起来像官方 SDKs。 协议通道返回 ChatObject：仍然是一个字典，并且也可以通过属性读取，就像官方 SDK 读取相同的 JSON、r.choices[0].message.content 一样。消息流以 get_final_message() / get_final_text() 结尾，响应流以 response.created 然后 response.in_progress 开头。
  • 令牌使用情况，包括失败。 本地索引返回 usage，自有模型聊天 usage 列出每个模型调用（claude-code/ 模型报告总数）。失败的运行会带来 PageIndexAPIError.usage 上的花费，而缩短的答案（长度、内容过滤器、拒绝）会引发而不是返回一半答案，到目前为止的文本在 partial_answer 上。
  • create_metadata_schema(folder_id, fields) 声明文件夹文档可能携带的元数据字段；聊天的元数据搜索通过它们进行过滤、排序和计数。仅云。
  • 本地代理工具将自己描述为云 MCP 服务器，因此针对一个工具编写的提示会在另一个工具上读取相同的工具文本。
  • BREAKING：消息流事件是字典。 chat(protocol="messages", stream=True) 生成 ChatObject 字典，而不是 Anthropic SDK 事件对象。 event.type、event["type"] 和 event.model_dump() 都可以工作，但针对 SDK 事件类的 isinstance / match 不再匹配，并且设置属性 (event.delta.text = ...) 会使事件保持不变：编辑字典 (event["delta"]["text"] = ...)。
  • **突破：extra_body 不再采用 model、folder_id 或 api_base。**改为通过 model=、folder_id= 或 backend=。
  • litellm 1.105.1 或更新版本，低于 1.106，直到修复 1.106 的 mcp 导入。 pip install -U pageindex 选择匹配的版本。 同样在 0.4.4 中：
  • 缺少登录信息说明如何登录。 在没有 Claude 登录信息或过期登录信息的 claude-code/ 模型上建立索引现在会失败，并出现一个简短的错误，最终修复：运行 claude，然后运行 ​​/login。在任何型号上，同步 submit_document() 和 chat() 调用产生的错误不再在其上方显示不相关的 RuntimeError: no running event loop。 同样在 0.4.3 中：
  • 更安静的 Claude 运行。 在 Python 3.12 及更早版本上，claude-code/ 运行并且使用 as_claude_mcp() 的应用程序不再打印 asyncio 的“…将报告 returncode 255”警告。
  • 旧代理 SDK 是这么说的。 对于比 0.2.166 更旧的 claude-agent-sdk，claude-code/ 型号现在会在修复它的命令 pip install -U "pageindex[claude]" 前面停止。
  • 订阅示例。 cookbook/pageindex-claude-subscription.py 使用 claude-code/haiku 索引一篇论文并流式传输 claude-code/opus 的答案。 同样在 0.4.2 中：
  • 在您的 Claude 订阅上运行。 将 index_model 或 chat_model 设置为 claude-code/ 型号，例如chat="claude-code/opus"、索引和 chat() 通过 Claude 代码调用 Claude 模型：您的计划涵盖使用情况，并且不需要 API 密钥 (pip install -U "pageindex[claude]")。它的本地索引在 Flash 模式下运行。 同样在 0.4.1 中：
  • Flash 可以正确读取文件。 每页顶部的“目录”链接不再隐藏文件标题（AmEx 10-K 在一个节点中包含前 131 页，现在索引便宜约 30%）。第 20 条注释与大纲相连，两份标题相同的审计报告各保留一个标题，一页一页构建的幻灯片为一个部分。
  • **在任何脚本中扩展。**树扩展现在分割以中文、日语、阿拉伯语、印地语和其他脚本标题的部分，在无法解析的答复后再次询问，并将短节点自己的文本保留为摘要长度（summary_max_words），而不是固定的 200 个标记。
  • 更多提供程序。 节点摘要会关闭 LiteLLM 未标记的模型上的推理，其中包括 OpenRouter，并且 chat(protocol="responses" | "messages") 发送您编写的模型名称，因此与 OpenAI 和 Anthropic 兼容的服务（例如 OpenRouter）可以在这些通道上工作。 同样在 0.4.0 中：
  • 更便宜的 Flash 索引。 叶子仅总结其自己的文本，文档描述读取顶级摘要，节点摘要在接受它的模型上默认为 reasoning_effort="none"（summary_reasoning_effort 选择另一个值），并且每个部分扩展询问一次，并且仅当阅读各个部分比整体更便宜时才进行拆分。
  • 新的默认型号。 本地模式索引为 gpt-6-luna，并在未设置型号时使用 gpt-6-sol 进行应答。没有聊天模型的云 client 仍使用托管聊天。
  • litellm 1.105.0 或更新版本，第一个支持 gpt-6-luna 的版本。 pip install -U pageindex对其进行了升级。 同样在 0.2.22 中：
  • Flash 保持单词完整。 单词间隙是根据每个字符代码的字体宽度来测量的，因此页面文本和标题不再拆分“infe rence”之类的单词，并且章节标题再次与其书签匹配。
  • 更稳定的 Flash 树。 索引不再因“标记为最终后删除或更改”而失败，运行标题不再提前将介绍或前言剪切一页，并且展开仅保留在节点内打印的小节。 optimize_tree(pdf_path) 和 tree_optimize CLI 按布局顺序读取两列页面，不再需要 pymupdf。
  • 标准模式。 当模型在该部分自己的上方列出标题（“第 3 章”上方的“第二部分”）时，大部分拆分不再无限循环，并且目录项在开始之前永远不会结束。 同样在 0.2.21 中：
  • 突破性：一棵树形状，本地和云。 get_tree 节点在两种模式下均承载 start_index、end_index 和 summary； page_index 和 prefix_summary 不见了。在新索引的文档中，父级的范围和摘要覆盖其整个部分，并且其第一小节之前的页面成为 "<title> (intro)" 节点。早期索引的文档保留自己的范围和摘要。
  • 本地 get_ocr(format="node") 返回每个节点自己的文本。 父节点的文本在其第一个小节开始的页面处停止，并且当介绍节点保留该开头时为空；介绍节点显示为其自己的条目。之前索引的文档也以这种方式读取，无需重新索引。
  • 节点导航。 pageindex.utils 中的 get_node、get_node_parent、get_node_path 和 get_node_map 从 get_document_structure() 获取树并在本地遍历它，因此一次获取可以服务任意数量的查找。
  • 标准模式像 Flash 一样进行总结。 每个部分的摘要在其子部分完成后立即开始，并且短节点保留自己的文本。 同样在 0.2.20 中：
  • 更快的 Flash 索引。 节点摘要首先运行最深的节点，并在树扩展仍在决定时开始，因此模型通道永远不会闲置：222 页的报告索引需要 73 秒而不是 98 秒，一本 758 页的书需要 137 秒而不是 174 秒。现在每个摘要的上限为 summary_max_words（默认 150），这将摘要阶段又减少了三分之一到一半。
  • client 上的索引旋钮。 summary_max_words、summary_concurrency、use_embedded_toc 和 optimize 可在 PageIndexClient(...) 或 index= 插槽中设置（本地闪存模式），并且 --summary-max-words / --summary-concurrency 加入 CLI。 summary_concurrency 立即降低整个索引通道以实现严格的速率限制。
