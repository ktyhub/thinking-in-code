OCRmyPDF v17.11.0

小版本 发布时间2026年8月28日 来源ocrmypdf/OCRmyPDF 英文原文

OCRmyPDF v17.11.0

增强

  • 当页面打开时，新的 --max-ocr-image-mpixels 会对发送到 OCR 的图像进行下采样 超过了给定的大小，限制了最大的内存消耗。的 可见页面永远不会被下采样，因此输出外观在每个页面中都不会受到影响 模式；它所交换的是非常高分辨率扫描的 OCR 准确性。 34号 megapixel 页面峰值为 492 MB，峰值为 325 MB --max-ocr-image-mpixels 8，并识别相同的文本。参见“记忆” 性能文档中有关如何调整内存限制大小的部分。
  • watcher.py（watcher extra）获得了可配置的输出布局和 冲突政策。这些是仅限观察者的更改；它们不影响 ocrmypdf 库 API。
    • 新的OCR_OUTPUT_STRUCTURE设置（--output-structure）：FLAT （默认情况下，所有输出都直接在目标目录中）， YEAR_MONTH（{destination}/{year}/{month}/{filename}，与 旧的 OCR_OUTPUT_DIRECTORY_YEAR_MONTH=1) 或 HIERARCHY， 镜像目标下的输入目录树，例如 input/a/b/c.pdf → output/a/b/c.pdf。
    • 新的 OCR_ON_CONFLICT 设置 (--on-conflict) 控制发生的情况 当预期的目标文件已存在时：SUFFIX（默认） 以操作系统风格编写 name (1).pdf、name (2).pdf、…； SKIP日志 并保留文件未处理； OVERWRITE 是旧行为。 行为更改：默认值现在是 SUFFIX，因此现有输出 文件不再被静默覆盖。
    • 这两个设置现在同样适用于 OCR_OUTPUT_DIRECTORY 和 OCR_ON_SUCCESS_ARCHIVE使用的归档目录；以前的 存档目录总是扁平的，并且默默地覆盖了一个名称 碰撞。
    • 输出和存档文件名以及目录组件已清理 对于比输入端更严格的文件系统（例如 SMB 共享）：Windows/SMB 上的非法字符（<>:"/\|?* 和控件 字符）被替换为 _，尾随点/空格被删除， 和保留的 DOS 设备名称（CON、PRN、AUX、NUL、COM1-9、 LPT1-9) 的前缀为 _。
    • OCR_OUTPUT_DIRECTORY_YEAR_MONTH 现已弃用，取而代之的是 OCR_OUTPUT_STRUCTURE=YEAR_MONTH。它仍然很荣幸并记录了 弃用警告；如果两者均已设置，则 OCR_OUTPUT_STRUCTURE 获胜。
    • 请参阅批处理的“使用 watcher.py 监视的文件夹”部分 完整描述的处理文档，包括注释 对于 SMB 用户，有关 client 端目录/文件信息缓存延迟的信息。

性能

  • 发送到 OCR 的图像不再在不需要时进行解码和重新编码 改变它。在没有预先存在的文本要屏蔽且没有过滤的页面上 插件——扫描文档的普通情况——光栅化页面 已经是 OCR 图像，因此它是链接的而不是重写的。生产 它花费了 3.3 秒和 34 megapixel 页面上的全尺寸缓冲区，out 整个文件大约需要 15 秒。构建掩码现已推迟 直到文本区域实际上需要消隐，因为这一步迫使 解码。最低 Pillow 版本提升至 12，因为决定是否 任何解码图像都会读取形状固定在 Pillow 11 中的属性 （pi-heif已经需要枕头11.1，所以有效地板几乎不移动）。
  • 默认情况下，将大图像文件的峰值内存减少约三分之一 设置。在 34 megapixel 页面上，进程树的峰值为 752 MB，现在 峰值为 492 MB。两个变化说明了这一点：不再光栅化页面 分配第三个整页缓冲区来纠正 PDFium 的舍入 渲染大小增加一两个像素，释放的堆内存现在返回到 OCR 引擎运行之前的操作系统，而不是计入我们的 只要发动机工作，就常驻设置。光栅化也是 更快，因为纠正大小不再对整个页面重新采样。
  • 多个 OCR 作业现在可以在单个 Python 进程中同时运行。 API 之前在 ocrmypdf.ocr() 的整个持续时间内都持有锁定，因此第二个 另一个线程中的调用必须等待第一个线程完成。插件状态是 现在由读写锁保护：安装插件集需要它 独占，而作业则在运行时共享它。因此，飞行中的工作 无法将其依赖的插件基础结构替换为它下面的， 而过去安装的作业同时进行。
  • 现在每个解释器安装一次插件集并重复使用，而不是 每次通话时都会重新安装。之前每次 ocrmypdf.ocr() 调用 重新执行作为文件路径给出的插件模块并将它们反弹到 sys.modules。插件不得依赖于每个作业的重新执行，并且 不得在插件管理器上存储每个作业的状态，这些并发作业 现在请求相同的插件集共享。
  • 请求不同插件集的作业相互序列化，因为 安装第二组必须等待第一组作业完成。使用 跨并发作业或单独进程设置相同的插件。
  • 对于具有大图像的文档，图像优化速度要快得多。 带有 PNG 预测器的存储为 /FlateDecode 的图像已经完全保存 PNG IDAT 块包含什么内容，因此现在直接将其重新打包为 PNG 而不是被解码为位图并重新编码。在 6 页的文档中 包含一张 9000x9000 图像，优化步骤从 3.4 秒变为 0.6 秒， 并与下面的 JPEG 一起更改为 0.04s；总运行时间从 10.0 秒至 7.0 秒。输出不变：压缩的 数据被逐字重复使用。不可直接重新打包形式的图像 还是走以前的路。
  • 在图像优化期间，我们解码了所有 JPEG，即使代码 路径是一个优化设置，解码后的 JPEG 永远不会 重新编码（低于 --optimize 2）。我们现在仅在代码路径上进行解码 使用解码后的 JPEG。输出不变。
  • 未压缩的图像（没有 /Filter 的图像）不再产生虚假图像 “优化器无法处理”警告。这样的形象浮现出来 IndexError 内部，优化器的尽力处理程序捕获并 报告为警告；现在它已被识别并悄悄地跳过。
  • 删除了图像优化器中声称可以处理的无法访问的分支 基于 ICC 的色彩空间中每个分量图像 1 位。较早的支票发送 每 1 个 bpc 图像发送到 JBIG2 通道，JBIG2 通道通过以下方式处理基于 ICC 的图像 在提取之前中和配置文件，因此分支永远无法运行。
  • 删除了跨所有进程序列化工作池的进程范围锁 Executor 实例。 Executor.pool_lock 被保留但不再被收购， 并已弃用；它将在未来的主要版本中删除。不变量 它受到保护 - 共享控制台上只有一个进度条呈现 - 是 现在由进度条强制执行，如果已经有另一个进度条，则进度条会自行禁用 拥有控制台。
  • 请注意，每个配置为 jobs=M 的 N 个并发作业现在最多可以生成 N*M 工人，之前他们被序列化为 M。尺寸 jobs 因此。
  • 并发进程内作业的已知限制：它们必须使用相同的 max_image_mpixels。 Pillow 的减压炸弹限制是解释器全局的 最后设置它的工作获胜。使用单独的进程来运行作业 不同的配置。

修复

  • 修复了 pypdfium2 光栅器中潜在的释放后使用问题。 to_pil()让 Pillow 别名 PDFium 的位图缓冲区，适用于某些格式 - 灰度渲染 其中，这是每个单色和灰度页面——并且缓冲区被释放 紧接着，离开Pillow阅读PDFium释放的内存。
  • Windows：OCRmyPDF 不再打印“[WinError 2] 系统找不到 搜索 Ghostscript 和 Tesseract 时出现文件指定的警告 （[#1671]（https://github.com/ocrmypdf/OCRmyPDF/discussions/1671））。这些 消息来自于探测注册表项，而这些注册表项根本不存在 程序由包管理器（例如 Scoop）安装，或未安装 根本不。由于搜索随后会在其他地方继续进行并且通常会成功，因此这些 失败是正常的，现在以调试级别记录，命名位置 那个被搜查了。如果确实找不到程序，OCRmyPDF 仍然 报告该错误。
  • Windows：修复了 PROGRAMFILES 环境变量指向时的崩溃 不存在的文件夹。
  • --mode strip 无法删除 OCRmyPDF 本身的 OCR 文本图层 生产（{issue}1730）。 OCRmyPDF 将其文本层移植为 Form XObject 剥离仅检查页面内容流，因此不可见的文本 从未被发现。同样的缺陷使 --mode redo 堆叠了第二个文本层 在旧的之上而不是替换它。剥离现在下降到 形成 XObjects。谢谢@Anai-Guo ({issue}1732)。
  • 剥离现在还可以解析从祖先继承的页面 /Resources /Pages节点，而不是只看页面自身的资源。
  • 剥离后变空的文本层现在已从页面中删除 而不是作为残留的 Form XObject 外壳被留下。
  • 在 Python API 中的现有选项对象上设置 clean_final 否 较长的叶子 clean 未设置。 --clean-final 意味着 --clean，但规则 存在于一个字段验证器中，该验证器仅在选项对象被执行时运行 构造，因此随后分配给该属性会默默地跳过它。
  • 超出范围或拼写错误的选项的验证错误现在命名选项 他们是关于，他们的措辞来自 Pydantic 而不是 由于是手写的，所以略有改动。例如现在的--jobs 999 报告--jobs: Input should be less than or equal to 256。的集合 接受的值不变。
