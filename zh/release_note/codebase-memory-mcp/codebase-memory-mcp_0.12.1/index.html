codebase-memory-mcp v0.12.1

codebase-memory-mcp v0.12.1

#v0.12.1

每个安装路径都会再次运行，并且 Helm 图表会加入图表中。

v0.12.1 修复了 v0.12.0 的软件包安装以及我们在检查每个频道时发现损坏的其他安装路径。它还将 Helm 图表链接到它们部署的内容，并阻止图表为容器映像创建注册表。

升级？ 升级后每个现有项目的第一个索引是一次完全重建（图像标识已更改；见下文）。

修复：安装

  • npm、PyPI 和 Go 安装。 npm i、pnpm add、pip install 和 Go 包装器无法在任何平台上安装 v0.12.0。每个包装器拒绝超过 256 MiB 的存档成员，并且每个 v0.12.0 二进制文件为 331-335 MB。所有三个包装纸都没有尺寸限制。在解压之前，仍会根据版本的 checksums.txt 验证存档，其内容必须完全是预期的文件，并且二进制文件必须回答 --version。谢谢@Hydrplexus 的精确报告（#2657）。
  • Homebrew. 公式仍然是 0.10.3，在 Linux 上它安装了动态链接构建，这需要 glibc 2.38（Ubuntu 22.04、Debian 12 和 RHEL 9 没有它）。它现在安装当前版本，并在 Linux 上安装可在任何发行版上运行的静态 -portable 版本。
  • go install。 固定的 go install .../pkg/go/cmd/codebase-memory-mcp@vX.Y.Z 从未工作过，而 @latest 安装了过时的版本。版本现在带有 pkg/go/vX.Y.Z 标签，包装器会安装与其自身版本匹配的版本。
  • npm next。 next dist 标签不再指向旧的候选版本；稳定的发布会推动它。
  • Docs. winget 和 Chocolatey 被列为安装频道，但未发布；它们会被移除，直到它们被移除为止。 Windows arm64 构建发布并现已上市。

安装路径冒烟测试。 现在，每个拉取请求和每个版本都会安装 npm、PyPI 和 Go 包装器，就像用户的包管理器针对真实版本档案所做的那样，并运行每个安装的二进制文件。仅在这些安装通过后才会发布版本，因此无法安装我们提供的内容的安装程序将无法再联系到您。

图中的 Helm 图表

Helm 图表曾经是一个孤立的节点。现在它链接到它部署的内容（#2663）：

  • 图表 → 对象 (DEPLOYS、via: chart)：从图表的 templates/ 渲染的每个 Kubernetes 对象（子图的对象属于子图）。
  • 值文件 → 图表 (CONFIGURES)：Chart.yaml 旁边的 values.yaml 和 values-<x>.yaml。
  • 图表→图像（DEPLOYS、ref: image）：每个图像其对象按字面名称命名（模板化图像不命名）。

HelmRelease → Chart → Deployment → Image 现在是一条可通行路径。在 20 个基础设施存储库中，没有传出边缘的图表从 260 个中的 238 个下降到 109 个，并且出现了 2,511 个图表到对象的链接；其他所有边都保持相同。

图像在注册表中保存代码名称

没有注册表主机的映像过去存储在发明的 docker.io/library/... 下 (#2654)。 Docker Hub 只是 Docker 的默认设置：Podman 和 CRI-O 通过搜索列表解析短名称，镜像重写它们，并且本地构建标记可能根本不存在于注册表中。现在，图像保留其书面名称，当未指定主机时，其名称为 registry: unknown；保留指定的主机（Docker Hub 的拼写变为 docker.io）。 FROM nginx 和 image: docker.io/library/nginx 现在是两个 Image 节点。这会更改映像标识，这就是每个项目在升级后重建一次的原因。

升级注意事项

  • 升级后每个现有项目的第一个索引是一次完整重建。
  • 没有指定注册表的图像节点现在带有 registry: unknown 和书面名称，而不是 docker.io/library/...。
