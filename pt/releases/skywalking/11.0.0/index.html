Projeto

  • Mova o maquinário de carregamento de classe DSL para core/dsl. core/classloader mantinha apenas tipos DSL — RuleClassLoader, DSLClassLoaderManager, ClassLoaderGc, UnloadProbePayload e BytecodeClassDefiner — então agora é core/dsl/classloader, e Catalog muda para core/dsl porque uma taxonomia de arquivo de regras não é uma preocupação de carregamento de classe. Três cópias do despacho "definir uma classe gerada no carregador correto" (MAL, LAL, MeterSystem) se transformam em um BytecodeClassDefiner.define estático, o que também dá à lógica do JDK 17 --add-opens uma casa em vez de quatro. Três das quatro cópias da pesquisa do diretório dump da classe gerada tornam-se DslGeneratedFileWriter.resolveClassDumpDir; OAL mantém o seu próprio, porque seu sinalizador de depuração é configurável independentemente da variável de ambiente e dois testes dependem disso. Nenhuma mudança de comportamento.
  • Estenda o GET /inspect/entities admin API para inspecionar uma métrica persistida por qualquer OAP, mesmo um que este nó não defina localmente. Quando a métrica é desconhecida para o registro local, o chamador fornece valueColumn + valueType e o back-end de armazenamento resolve o índice/tabela/grupo físico a partir de sua própria configuração em execução (sem leitura de esquema de banco de dados/metadados de tabela): ES usa o índice metrics-all mesclado + discriminador metric_table, JDBC investiga as tabelas de função do nó pelo discriminador table_name e BanyanDB sintetiza um esquema de medida somente leitura. O escopo não é mais necessário — o entity_id é decodificado estruturalmente (serviço/2º nível/relações) com uma folha name genérica. As métricas definidas localmente mantêm os nomes exatos dos campos, escopo e mqeEntity como antes.
  • Adicione o administrador POST /inspect/values API — leia a série de valores de uma métrica persistida por outro OAP (um que este nó não define localmente) fornecendo seu {valueColumn, valueType}. O mecanismo MQE real é executado em uma sobreposição InspectQueryContext com escopo de solicitação (fornecimento se ausente - o catálogo local sempre vence) que faz com que a métrica externa pareça registrada em cada caminho de leitura: ValueColumnMetadata resolve sua coluna/tipo/escopo de valor e os registros de local de armazenamento resolvem onde ele reside (MetadataRegistry sintetiza um esquema de medida BanyanDB, IndexController resolve o índice ES metrics-all, TableHelper investiga as tabelas de funções JDBC), portanto, a leitura retorna o MQE ExpressionResult nativo sem maiúsculas e minúsculas especiais por DAO. Somente administrador (uma leitura forçada deste OAP não pode ser validada); não espelhado na superfície pública REST/GraphQL. Consulte Inspecionar API.
  • Remova a conversão sempre ativa de alarme em evento (EventHookCallback). Um alarme acionado não é mais sintetizado no pipeline de eventos como um evento Alarm/AlarmRecovery; os eventos agora se originam apenas de fontes reais de eventos (agentes, SkyWalking CLI, Kubernetes Event Exporter). Os alarmes permanecem disponíveis através do armazenamento de alarmes (getAlarm/queryAlarms) e dos ganchos de alarme configurados. Isso elimina um "Evento Conhecido" documentado e remove de 1 a 2 registros de eventos sintéticos por disparo de alarme.
  • TLS para todos os servidores OAP HTTP/REST, com certificado hot-reload. Adiciona a estrutura de configuração restSSLEnabled / restSSLKeyPath / restSSLCertChainPath a cada servidor OAP HTTP — núcleo REST, servidor de compartilhamento, admin, PromQL, LogQL, TraceQL e consulta/receptor Zipkin — cada um com suas próprias variáveis de ambiente dedicadas (SW_CORE_REST_SSL_*, SW_RECEIVER_SHARING_REST_SSL_*, SW_ADMIN_SERVER_REST_SSL_*, SW_PROMQL_REST_SSL_*, SW_LOGQL_REST_SSL_*, SW_TRACEQL_REST_SSL_*, SW_QUERY_ZIPKIN_REST_SSL_*, SW_RECEIVER_ZIPKIN_REST_SSL_*). O Armeria HTTPServer compartilhado recarrega o par de chaves do disco em rotação (via TlsProvider.ofScheduled) para que os certificados atualizados sejam coletados sem reiniciar o OAP, correspondendo ao comportamento de recarga a quente SSL gRPC existente. HTTP TLS é apenas do lado do servidor (sem mTLS).
  • Nova consulta queryAlarms GraphQL — filtros de entidade/camada/regra para alarmes. Adiciona uma consulta de alarme abrangente API junto com o legado getAlarm. O novo queryAlarms(condition: AlarmQueryCondition!): Alarms aceita um único tipo de entrada agrupando cada filtro que o registro de alarme armazena: entities: [Entity!] (reutiliza a forma MQE Entity - pino para serviços/instâncias/endpoints/processos específicos ou suas relações, combinados com o alarme id0 OU id1); layer: String (filtrar pela camada da entidade alarmada — correspondência única, pois as linhas de alarme persistem em uma camada); ruleNames: [String!] (filtro pelo qual a regra de alarme disparou); mais keyword, tags, duration, paging. O legado getAlarm está marcado como @deprecated, mas ainda roteia para o mesmo DAO - sem quebra de client. Adições de back-end: uma nova coluna layer em AlarmRecord preenchida no momento do alarme via MetadataQueryService.getService(serviceId).getLayers(); as colunas id0/id1 existentes passaram de storageOnly = true para indexadas para que o filtro de entidade seja enviado para armazenamento. IAlarmQueryDAO.queryAlarms(condition, limit, from) é um novo método abstrato – back-ends de armazenamento de terceiros falham na compilação se perderem a substituição (padrão SWIP-14). Todos os três back-ends incluídos o implementam: BanyanDB/Elasticsearch/JDBC. Semântica do operador: (1) As entidades de relação são de correspondência exata. Passar {scope: ServiceRelation, serviceName: A, destServiceName: B} corresponde apenas ao alarme onde id0=serviceId(A) AND id1=serviceId(B), e não a qualquer alarme que toque A ou B em qualquer lado. Consultas mais amplas "qualquer coisa que envolva A" devem passar a entidade individual sem relação ({scope: Service, serviceName: A} - que se expande para id0=A OR id1=A). (2) Camada única por linha de alarme. A coluna persistente armazena UMA camada (a primeira entrada da lista de camadas resolvidas da entidade - origem primeiro para relações). Um serviço em [GENERAL, K8S_SERVICE] cujos metadados são resolvidos primeiro para GENERAL é arquivado em GENERAL; consultar layer: "K8S_SERVICE" irá perdê-lo. Observação sobre migração do operador: as linhas de alarme de pré-atualização existentes continuam a ser filtráveis ​​pelos campos getAlarm herdados; os novos filtros de entidade/camada/regra em queryAlarms se aplicam apenas a alarmes gravados após a atualização (os índices de armazenamento existentes não fazem a transição de index: false → true no local; novos índices lançados diariamente selecionam as colunas indexadas). As adições de esquema não bloqueiam - o bootstrap ignora silenciosamente as alterações nos atributos da coluna nos índices existentes.

  • Novo módulo admin-server — host compartilhado para APIs de gravação sob demanda/administrador. Funciona em duas portas: uma superfície HTTP REST (padrão 17128) para endpoints voltados para o operador e um barramento gRPC interno do administrador (padrão 17129) para RPCs de cluster ponto a ponto (regra de tempo de execução Suspender / Retomar/Avançar; instalação de depuração DSL/coletar/parar/stopByClientId). O barramento interno do administrador é um transporte dedicado separado da porta gRPC do agente público/cluster (core.gRPCPort, padrão 11800) para que os RPCs administrativos privilegiados fiquem fora do raio de explosão da rede do agente - os operadores vinculam o gRPCHost apenas a uma interface ponto a ponto privada. Ativado por padrão para que o módulo de recurso de status possa ser acessado imediatamente; o host se liga ao 0.0.0.0:17128 e não tem autenticação integrada e deve ser protegido por gateway com listas de permissões de IP, nunca exposto à Internet pública (consulte o aviso de segurança do administrador API). Defina SW_ADMIN_SERVER= (vazio) para desabilitar totalmente. O bloco de configuração da regra de tempo de execução perde suas chaves restHost/restPort/restContextPath/restIdleTimeOut/ restAcceptQueueSize/httpMaxRequestHeaderSize (e os env vars SW_RECEIVER_RUNTIME_RULE_REST_* correspondentes); os botões de nível de host se movem sob o novo bloco admin-server (SW_ADMIN_SERVER_HOST / SW_ADMIN_SERVER_PORT / SW_ADMIN_SERVER_GRPC_HOST / SW_ADMIN_SERVER_GRPC_PORT / SW_ADMIN_SERVER_INTERNAL_COMM_TIMEOUT etc.).
  • Atualização de regras de tempo de execução para MAL e LAL. Os operadores agora podem enviar alterações de regras de métricas (MAL) e de log (LAL) sem reiniciar o OAP. Um push para um novo endpoint administrativo persiste a regra no back-end de armazenamento configurado e cada nó no cluster converge para o novo conteúdo em aproximadamente 30 segundos. Fluxos de trabalho comuns:
    • addOrUpdate — crie ou substitua uma regra. Body é o YAML bruto que você normalmente enviaria com os arquivos de regras estáticas do OAP. Retorna 200 quando a regra é aplicada localmente e persistida; os pares o pegam na próxima varredura periódica (≤ 30 s).
    • inactivate — pausa suave é uma regra. O OAP para de emitir métricas para essa regra, mas a medida de backend (e seu histórico) é preservada, portanto, um addOrUpdate posterior para o mesmo (catalog, name) não tem perdas. A intenção "desligada" é durável durante as reinicializações; as regras agrupadas no disco não são ressuscitadas automaticamente quando um inactivate remove a substituição de tempo de execução. Esta é a maneira segura de colocar uma regra offline.
  • delete — remove uma linha INACTIVE (regras ativas retornam 409 requires_inactivate_first). Para regras somente de tempo de execução sem YAML incluído no disco, a linha é eliminada; a medida de back-end (se houver) é deixada como um artefato inerte, correspondendo à semântica de exclusão de regras agrupadas (remover um YAML de otel-rules/ no disco também não elimina sua medida). Para regras que possuem um gêmeo YAML empacotado, delete simples retorna 409 requires_revert_to_bundled - deixar o pacote agrupado assumir silenciosamente o controle do (catalog, name) é uma mudança de estado significativa que requer uma decisão explícita do operador. Emita novamente com ?mode=revertToBundled para retornar ao pacote: esse caminho executa o pipeline de mudança de esquema (reidrata o DSL de tempo de execução localmente e, em seguida, aplica o pacote YAML por meio do pipeline de aplicação padrão para que o delta de tempo de execução→pacote elimine métricas somente de tempo de execução, registre métricas somente de pacote e reutilize métricas compartilhadas em pacote no formato correspondente) antes de remover a linha. Retorna 400 no_bundled_twin quando ?mode=revertToBundled é usado sem um YAML empacotado no disco.
    • get / bundled / list / dump - terminais de leitura para buscar o YAML de uma única regra (com suporte a ETag; ?source=bundled lê o YAML empacotado no disco mesmo quando uma substituição de tempo de execução está em vigor), listando a sobreposição de pacote versus tempo de execução por catálogo, inspecionando estado de regra em todo o cluster como um envelope JSON ({generatedAt, loaderStats, rules} — cada linha carrega status/localState/loaderKind/bundled/bundledContentHash para que uma UI possa renderizar emblemas de substituição sem uma segunda viagem de ida e volta) e exportar todas as regras como um tar.gz para backup/DR. As atualizações a quente sobrevivem à reinicialização do OAP: na inicialização, o OAP mescla arquivos de regras agrupados com regras de tempo de execução persistentes, para que o cluster nunca regresse silenciosamente aos padrões agrupados. Todas as gravações administrativas para um cluster de regras de tempo de execução são serializadas em um único OAP "principal" (primeiro par classificado determinístico, sem eleição de líder) - nós não principais que recebem uma gravação HTTP encaminham-na de forma transparente para o principal por meio do barramento gRPC interno do administrador, de modo que um balanceador de carga L7 na frente da porta administrativa pode rotear qualquer solicitação do operador para qualquer OAP. A convergência do cluster no tick de atualização periódica é configurável via receiver-runtime-rule.refreshRulesPeriod (30 s padrão). O endpoint está desabilitado por padrão e escuta na porta 17128 (HTTP) quando habilitado. Ele não possui autenticação integrada — os operadores devem protegê-lo como gateway com listas de permissões de IP e nunca expô-lo à Internet pública. As rotas são montadas no novo host HTTP admin-server, que está ativado por padrão; habilite o recurso de regra de tempo de execução com SW_RECEIVER_RUNTIME_RULE=default.
  • Depurador ao vivo para MAL/LAL/OAL — implementa Depurador ao vivo SWIP-13 para MAL/LAL/OAL. Depurador de tempo de execução baseado em amostra que captura entradas/saídas por estágio à medida que as três DSLs processam a ingestão ao vivo. O custo do caminho ocioso é uma leitura de bool volátil por site de chamada de teste que o JIT elimina após o aquecimento; sessões ativas se espalham para cada peer do cluster através do barramento gRPC interno do administrador para que cada peer capture sua própria fatia. O fan-out é seguro para LB: qualquer nó pode servir qualquer verbo (POST cunha sessionId no nó receptor, transmite a instalação para pares, retorna 404 rule_not_found somente quando nenhum nó possui a regra), portanto, um balanceador de carga L7 na frente da porta administrativa roteia as solicitações do operador livremente. É montado no host admin-server compartilhado (/dsl-debugging/* para plano de controle de sessão, /runtime/oal/* para o seletor de regras OAL). Desativado por padrão; habilite com SW_DSL_DEBUGGING=default (o próprio servidor de administração está ativado por padrão). injectionEnabled é um switch codegen de tempo de inicialização cujo padrão é true - uma vez que o módulo é habilitado, as sondas são acionadas e as sessões registram amostras; defina false somente se a superfície REST for desejada, mas nenhuma sobrecarga de teste do lado do codegen for aceitável. Os limites por sessão impõem limites rígidos (recordCap ≤ 10.000, retentionMillis ≤ 1 hora) — solicitações fora do intervalo retornam 400 invalid_limits. As sessões LAL aceitam um sinalizador granularity=block|statement por sessão - o modo de bloco captura os estágios do analisador/extrator/sink; O modo de instrução registra adicionalmente uma entrada line por instrução de extração individual, carregando o número da linha de origem e o texto DSL literal para que a IU possa destacar qual instrução foi disparada. As capturas MAL renderizam o mapa SampleFamily sobrevivente do filtro em nível de arquivo ({"families": N, "items": [...]}), de modo que as expressões multimétricas mostram o estreitamento do filtro entre famílias na carga útil capturada. As cargas úteis de captura incluem corpos de log brutos e mapas analisados ​​— trate a porta administrativa como infraestrutura autenticada de acordo com o aviso de segurança do administrador API. Referências de operador por DSL: MAL, OAL, LAL.

Mesmo quando ativado, ele fica inerte, a menos que o nó de dados execute a imagem BanyanDB compatível com plug-in com o amostrador .so montado - um nó sem esse suporte ignora a configuração e aquele que não consegue carregar o plug-in registra um erro e mescla sem filtro, então nada é descartado inesperadamente. As duas janelas de tolerância usam -1 para "herdar o padrão do nó de dados" (mesclagem de 30s/finalização de 5m) porque o nó trata qualquer tolerância não positiva como não definida. enabledEvents aceita uma string separada por vírgula para que possa ser configurada a partir do ambiente (SW_STORAGE_BANYANDB_TRACE_PIPELINE_ENABLED_EVENTS e sua variante ZIPKIN_), bem como uma lista de blocos YAML; um valor vazio retorna para PIPELINE_EVENT_MERGE, portanto, PIPELINE_EVENT_FINALIZE é executado somente quando nomeado explicitamente. O config de cada plugin é passado literalmente como um protobuf Struct: listas e objetos aninhados (por exemplo, keepTagRules) agora sobrevivem ao carregador de configuração e são serializados como ListValue/Struct reais em vez de serem nivelados em uma string. Observe que um float escrito como um espaço reservado ${ENV:default} ainda alcança o plug-in como uma string JSON, porque o resolvedor de espaço reservado compartilhado preserva apenas String/Inteiro/Longo/Booleano; os amostradores originais aceitam um número cotado exatamente por esse motivo. Consulte Trace Tail Sampling para saber como um rastreamento é avaliado e Armazenamento BanyanDB para obter as chaves de configuração.
  • Correção: um valor em branco em bydb.yml (key: sem nada depois) abortou a inicialização do OAP com um NullPointerException opaco de java.util.Properties, que rejeita valores nulos. O carregador de configuração do BanyanDB agora ignora entradas em branco e deixa o campo em seu padrão, o mesmo resultado que omitir a linha.
  • Roteie regras LAL dentro de uma camada por seu tipo de entrada, para que uma única camada possa hospedar regras em diferentes entradas proto. Cada regra compilada agora carrega seu tipo de entrada efetivo (a classe proto para a qual seus getters parsed.* são convertidos, ou null para regras baseadas em analisador/não digitadas) e LogFilterListener ignora qualquer regra cujo tipo não corresponda ao log de entrada em vez de executar todas as regras na camada. Isso corrige um ClassCastException latente (capturado e registrado por log) que era acionado sempre que um log MESH de um formato atingia uma regra compilada para outro - por exemplo, um log de acesso Envoy TCP ou um perfil de rede LogData atingindo a regra HTTP envoy-als. Adiciona uma regra envoy-als-tcp (inputType: TCPAccessLogEntry) junto com o HTTP envoy-als existente; ambos compartilham a camada MESH e cada um agora vê apenas seu próprio tipo de entrada.

O auxiliar de gancho HTTP compartilhado tratou apenas 200 e 204 como sucesso, portanto, qualquer outro 2xx - notavelmente o 202 Accepted retornado por APIs de entrada assíncrona, como Eventos API v2 do PagerDuty - produziu send to ... failure. Response code: 202 no nível de ERRO em cada alarme entregue. O alarme ainda foi dado; a entrada do log estava errada. A verificação agora aceita toda a faixa 2xx, para todos os ganchos de alarme.
