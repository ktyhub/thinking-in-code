Codewhale v0.10.1

Codewhale é o produto público da Shannon Labs. O codewhale os nomes de comando, pacote npm e release-asset permanecem técnicos em letras minúsculas identificadores. O pacote npm legado deepseek-tui está obsoleto e não recebe mais lançamentos. Usuários provenientes do legado v0.8.x deepseek / Os nomes deepseek-tui deverão migrar com docs/REBRAND.md.

Instalar

Recomendado – lançamento oficial do GitHub

Nova instalação do macOS/Linux (binários com soma de verificação desta versão):

curl -fsSL https://codewhale.net/install.sh | CODEWHALE_VERSION="v0.10.1" sh
"$HOME/.local/bin/codewhale" --version

Para Windows, use o instalador ou arquivo correspondente abaixo. Para um existente instalação direta, execute codewhale update; ele imprime o caminho do executável e mantém compilações mais recentes. Se o diretório de instalação estiver ocupado por uma compilação diferente, use a migração de diretório novo no guia de instalação.

Embalagem secundária — npm e Cargo

npm install -g codewhale
# or build from source
cargo install codewhale-cli --locked

O wrapper baixa os ativos de comando codewhale e codew correspondentes deste lançamento. Ambos contêm o mesmo tempo de execução compilado.

Docker/GHCR

docker run --rm -it \
  -e DEEPSEEK_API_KEY="$DEEPSEEK_API_KEY" \
  -v codewhale-home:/home/codewhale/.codewhale \
  ghcr.io/codewhale-hq/codewhale:v0.10.1

A imagem expõe o mesmo tempo de execução que codewhale e codew. O A tag latest também é atualizada no lançamento.

Carga (Linux / macOS)

cargo install codewhale-cli --locked

O pacote Cargo instala o codewhale. Cargo não pode criar um segundo comando alias de um destino binário; usuários que desejam uma ortografia mais curta podem adicionar um Link simbólico codew para o executável instalado. O npm, Homebrew, arquivo, shell-installer e canais de contêiner instalam ambos os nomes de comando diretamente.

Adicionado

  • /plugin doctor relata registros e instantâneos integrados obsoletos e /plugin doctor --fix os aposenta. Um plugin de usuário, um instantâneo e uma execução nomes de processos e um instantâneo dentro da janela de tolerância são mantidos. O o state.json anterior é mantido como state.json.pre-gc.
  • Os plug-ins revisados podem declarar rotas OAuth compatíveis com OpenAI. O anfitrião possui PKCE, atualização e armazenamento de credenciais e verifica a revisão em cada solicitação (docs/PLUGIN_PROVIDERS.md, #6805). A capacidade do provedor avança a política de revisão do plugin para v5 (v6 com o host de extensão): recibos mais antigos exigem revisão explícita novamente.
  • O login da conta OrcaRouter usa PKCE e salva a mesma chave API durável que configuração manual; seu catálogo ao vivo mantém linhas compatíveis com bate-papo e preços declarados e fatos sobre modalidade (#6867).
  • Host de extensão experimental TypeScript. Novidade nesta versão e fora de padrão: ligue-o com [features] extension_host = true. Um plugin que declara uma entrada native TypeScript ou JavaScript (o Cordis / DeepSeek Modelo de plugin de chicote) pode contribuir com ferramentas, comandos de barra, pré-execução ganchos de política, seções de prompt aditivas, raízes de habilidades revisadas e plugin-local Estado JSON. Seu código é executado em um separado Processo de nó, nunca dentro do Codewhale (Bun é opcional por meio [extension_host] runtime), e cada chamada passa pelo próprio portão do Codewhale: uma ferramenta de extensão nunca é tratada como somente leitura, portanto sempre atende aos portão de aprovação (acesso total, bypass ou concessão de sessão para aquele plugin revisado pode satisfazê-lo), um comando é executado somente quando você o digita e um plugin deve ser revisado e ativado primeiro. O host está em sandbox no macOS (Seatbelt) e em Linux com bubblewrap, sem rede direta e sem leitura do protegido locais de credenciais (lojas secretas da Codewhale e Codewhale, Codex e casas DSH). Uma extensão nativa é iniciada somente depois que o sandbox é verificado em lançamento: se o bubblewrap estiver faltando ou sua investigação de namespace falhar, a ativação será recusou com o erro concreto. Módulos host integrados fixados do próprio Codewhale mantenha uma exceção diagnosticada e cada efeito ainda precisará de uma operação Rust bilhete. No Windows, uma extensão nativa inicia apenas em um arquivo Menos recém-criado. AppContainer privilegiado cujo único recurso é registryRead (Winsock não pode iniciar sem ele), depois que o Codewhale verifica seu token e um arquivo real e sonda de rede; caso contrário, a ativação será recusada. Outros arquivos que você pode ler, como arquivos do projeto .env, permanecer legível e plug-ins que compartilham o host pode interferir um no outro, então ative apenas os plug-ins que você revisou (docs/EXTENSIONS.md).
  • Comandos de barra de extensão: um plugin registra um com ctx.commands.register. Ele é executado apenas quando você digita e pode mostrar texto ou enviar um prompt como sua próxima mensagem que passa pela curva ordinária e suas aprovações; não pode chamar o modelo ou a própria ferramenta. Um comando não pode assumir uma função interna nome do comando ou de outro plugin e um comando markdown com o mesmo nome vence. Um comando tem 30 segundos e os comandos são apenas TUI: o Runtime API não os lista nem os executa.
  • A criação de extensões nativas agora inclui ouvintes de políticas por meio ctx.on('tools/pre-execute', ...), solicita seções através ctx.prompt.registerSection e estado local do plugin persistente por meio de ctx.storage. Os ouvintes podem negar, perguntar, revisar ou fazer anotações; Rust verifica novamente as chamadas revisadas e possui todas as aprovações. As seções de prompt não podem substitua o prompt do sistema e o estado não expõe histórico ou segredo da sessão API. Esses serviços compartilham as revisões revisadas do host experimental e fora de padrão ciclo de vida do proprietário e são retirados quando seu proprietário descarrega ou é revogado; o estado salvo permanece disponível quando o plugin é recarregado.
  • A entrada da ferramenta de extensão é verificada em relação ao esquema JSON que a ferramenta registrou, antes que um cartão de aprovação apareça e novamente antes que a chamada chegue ao host. Um chamada inválida volta ao modelo como um erro nomeando o que corrigir, e o anfitrião nunca vê isso. Um esquema que não pode ser compilado ou que se refere fora de si com $ref, é recusado quando a ferramenta é registrada.
  • Uma ferramenta de extensão pode chamar ferramentas principais elegíveis com core/call enquanto o turno comum está executando essa ferramenta de extensão. Rust fornece um temporário ticket de invocação e ainda possui planejamento, ganchos, permissões, aprovação e execução. O ticket está vinculado ao proprietário do plugin, ao processo host e ao vivo invocação e expira quando essa invocação termina ou é revogada. Comandos, temporizadores e inicialização de plugins não podem usar este caminho. As concessões de aprovação têm escopo para a construção de extensão revisada; uma subvenção ao modelo não cobre isso. As chamadas de shell e de rede exigem a solicitação de uma pessoa, mesmo com um lembrete concessão; um modo de permissão que não pode apresentar esse prompt recusa a chamada. Ferramentas MCP, uso do computador, outras extensões, lançamentos de agente/fluxo de trabalho e ferramentas de alteração de permissão permanecem indisponíveis por esse caminho. Um cancelado a invocação retira suas aprovações pendentes em vez de decidí-las por você.
  • A identidade do host de extensão é verificada na inicialização: seu nível trust relatado e os resumos do módulo integrado devem corresponder ao processo iniciado pelo Rust. Host integrado plug-ins de código e de terceiros têm namespaces de processo e de proprietário separados; a tabela fixa o módulo do protocolo MCP e o chicote de execução. O O back-end Host MCP opcional usa o TypeScript SDK oficial para enquadramento, com Rust mantendo credenciais, acesso à rede/processo, aprovação e bilhetes de operação. Todas as 30 comparações registradas existentes passam localmente. O backend Rust permanece o padrão até que a plataforma e as portas de implementação passem; seus adaptadores de protocolo permanecem na janela de compatibilidade.
  • Um plugin pode declarar diversas entradas native (native.paths, até 64). Eles ativar em ordem sob um proprietário, para desativar, revisar a alteração ou travar derruba todos eles. Se uma entrada não for ativada, apenas essa entrada será retiradas: entradas que já foram ativadas permanecem registradas, e o plugin falha somente quando nenhuma entrada é ativada.
  • Configurações e contexto do plug-in: [plugins."<name>".config] por conta própria config.toml é passado para o apply(ctx, config) do plugin e verificado contra seu esquema Config exportado; .codewhale/config.toml de um projeto não puder configurá-lo, uma alteração será aplicada em /plugin reload e /plugin show listará as chaves, nunca os valores. Ferramentas e comandos também recebem o espaço de trabalho do a sessão que os chamou e um diretório de dados privado para o plugin em ~/.codewhale/extension-host/data/plugins/; sem casa, credencial ou outro o caminho do espaço de trabalho é passado.
  • codewhale --enable <feature> e --disable <feature> funcionam a partir do Comando codewhale; antes, eles foram rejeitados. Coloque a bandeira antes de qualquer subcomando.
  • O pacote host de extensão carrega código licenciado pelo MIT (Cordis, Schemastery e outros). Seus avisos de licença de terceiros são gerados a partir do que o pacote na verdade contém e está escrito ao lado do pacote quando ele é descompactado, e THIRD_PARTY_NOTICES.md lista os pacotes.
  • Tempo de execução do host de extensão: Bun 1.4.0 ou mais recente é opcional; O nó permanece o padrão. [extension_host] runtime = "node" | "bun" | "auto" escolhe: unset significa node (ou bun quando a tabela define apenas um caminho bun), bun executa apenas Bun e auto prefere um Bun suportado e usa Node quando nenhum é encontrado ou o host Bun falha ao iniciar. Uma escolha explícita nunca recua e as reinicializações mantêm o tempo de execução em que a sessão foi iniciada pela primeira vez; um binário de tempo de execução substituído no meio da sessão é recusado. Um caminho node ou bun configurado é usado como fornecido e falha ruidosamente em vez de passar para PATH, e um tempo de execução encontrado em PATH dentro de um diretório node_modules ou o diretório de trabalho é ignorado, não executado. codewhale doctor e /plugin mostram qual tempo de execução executa o host, por que e como sua memória é limitada. No Bun, o host nunca instala pacotes automaticamente e ignora .env e bunfig.toml em seu diretório de dados. As extensões não podem executar código nativo dentro do host em nenhum dos tempos de execução: bun:ffi, Bun.FFI, node:ffi, os componentes SQLite, process.dlopen, process.execve, threads de trabalho e ShadowRealm são recusados, e o host não será iniciado se uma dessas restrições não for válida. Limite conhecido: esse bloqueio cobre os pontos de entrada de código nativo encontrados até agora (Bun 1.4, Nó 22 e 26); aquele que um tempo de execução mais recente adiciona não é coberto até que seja adicionado. O limite de memória de 1 GiB usa RLIMIT_DATA no Linux, o Job Object no Windows e, para um host Bun, um limite de kernel jetsam no macOS; um host Node no macOS é verificado a cada pulsação. Bun é qualificado apenas no macOS: os testes de host Rust, com limite de memória incluído, não executaram um host Bun no Linux ou Windows (CI os executa com Node e os conjuntos de host JS em Bun 1.4.0 no Linux). host/hello informa o tempo de execução e a versão que realmente é executada.

O planejador de commit, o backup de colagem superdimensionada e as notas de aproveitamento do projeto não leia ou escreva através de links que saem do espaço de trabalho. No Unix, auditar e os logs de aprovação são criados apenas pelo proprietário e não são abertos por meio de um link; O Windows permanece inalterado. Os IDs das pistas devem ser nomes simples. Um arquivo de sessão é recusado quando registra um ID de sessão diferente do seu nome. O atualizador não segue um redirecionamento de HTTPS para HTTP simples e para de ler uma resposta maior de 512 MB.
  • Nada é escrito através de um .codewhale que seja um link. A execução do fluxo de trabalho diário não cria mais .codewhale/ ou seu razão quando é aberto, apenas quando o primeiro registro é gravado e lê e anexa através do mesmo ajudantes confinados como outro estado. O bloqueio de coordenação do subagente recusa um diretório .codewhale ou state vinculado antes de criar qualquer coisa.
  • No Unix, o log de tempo de execução é criado apenas pelo proprietário e não é aberto por meio de um ligação; um log existente de uma versão anterior é reduzido. O Os arquivos de bloqueio .reconcile.lock e current.json.lock são criados apenas pelo proprietário também.
  • Blocos inline ```repl em uma resposta agora seguem as mesmas regras que Ferramenta code_execution. Eles nunca são executados no modo Plano ou quando code_execution não está na superfície da ferramenta do torneamento e são admitidos como uma chamada code_execution com o mesmo código: ganchos antes da ferramenta, regras de ferramentas não permitidas, revisão automática (incluindo seu revisor) e repositório todas as leis se aplicam, então a mesma aprovação sob a permissão da sessão postura (uma chamada bloqueada, negada ou sem resposta ignora-a com um sinal visível nota). Só conta uma cerca que abre sua própria linha, aqui e no rlm o filho da ferramenta ronda, então uma resposta que menciona uma cerca em prosa não vale nada. Uma chamada rlm(...) de uma cerca obtém uma resposta infantil única em vez de uma filho que executa seu próprio código. Os documentos não descrevem mais o kernel REPL como sandbox.

Ferramentas que gravam arquivos ou executam comandos são nem listado nem executado, a menos que o operador defina require_approval = false na configuração do servidor MCP; o sinalizador approved do próprio client não conta mais como aprovação. Na inicialização, os nomes dos servidores em stderr cada ferramenta configurada retém e a configuração que permite isso.

O mesmo vale para uma resposta de erro do servidor que menciona um endereço expirado ou inválido. sessão. A chamada relata um resultado desconhecido e a próxima chamada é reconectada. Apenas uma chamada que o transporte HTTP recusou para uma sessão obsoleta, antes do o servidor lidou com isso, ainda é tentado novamente uma vez.

Composto, comandos wrapper, interpretador, não reconhecidos e configurados por opção são concedido como o comando exato e chamadas de interação/espera em um shell em execução como a chamada exata.
  • A aprovação do plano de fluxo de trabalho sinaliza recursos de shell, rede e gravação de arquivos para as famílias de ferramentas Bash, Web e File independentemente da caixa das letras.
  • Uma sessão de agente não pode mais atualizar, retomar ou executar uma automação cuja auto_approve, trust_mode ou allow_shell armazenado é maior que o a sessão é mantida, a menos que a mesma atualização reduza esses campos.
  • O resumo de aprovação que cada Runtime client recebe para tarefa e a criação/atualização de automação agora nomeia o modo trust solicitado, shell, aprovação automática, modo e espaço de trabalho, nos mesmos campos que o cartão TUI mostra.
  • Uma concessão de sessão shell mantém sua família de comandos somente quando cada opção é uma opção conhecida sem valor, como --release ou --porcelain; outras opções, em qualquer grafia, conceda o comando exato. Famílias cujos argumentos são o que funciona ou está instalado (go run, deno run, cargo run, make, git bisect, git submodule, instalações de pacotes) concedem o comando exato.
  • A aprovação do plano de fluxo de trabalho reconhece nomes de ferramentas em qualquer estilo de cotação e com um sufixo de padrão ('Web', `File`, Web(*)), and flags rlm, Git e GitHub, controle de computador e navegador e ferramentas de tarefas/automação com o capacidades que carregam.

Python code_execution (e todos os outros Python runner), portas de tarefa gate_run, portas de verificação personalizadas e de conclusão, sessões persistentes de terminal e run_tests agora iniciam do mesmo ambiente infantil limpo como exec_shell; variáveis que uma porta declara são ainda passou. gate_run também executa /bin/sh -c em vez de um login shell, para que os arquivos de perfil não possam reexportar o que foi removido.
  • Um workflow iniciado com verify: true agora precisa de aprovação mesmo para um plano somente leitura, porque as portas de conclusão executam a construção e o teste do espaço de trabalho roteiros.
  • Os comandos do Git não entregam mais credenciais de provedor a programas que um a configuração do git do espaço de trabalho pode ser iniciada (core.fsmonitor, ganchos, filtros) quando eles passam pelo auxiliar git compartilhado do Codewhale: eles começam do limpo ambiente mais o agente ssh, localização de configuração global e identidade do autor. O provisionamento e a entrega da árvore de trabalho do subagente ainda não o utilizam. O git_status somente leitura, As ferramentas git_diff, histórico e verify também desativam o espaço de trabalho fsmonitor, ganchos e filtros de limpeza/processo.

  • URLs de proxy passados para filhos executados por modelo (HTTP_PROXY, HTTPS_PROXY, ALL_PROXY, FTP_PROXY, CARGO_HTTP_PROXY) mantêm seu host e porta, mas perder qualquer peça user:password@.
  • Mudança de comportamento: o ambiente filho limpo agora mantém a construção não secreta configuração - CARGO_* (exceto registro e chaves semelhantes a token), RUSTFLAGS, RUST_LOG, RUST_BACKTRACE, VIRTUAL_ENV, JAVA_HOME, vá caminhos, NVM_*/NODE_OPTIONS e variáveis do pacote CA - então run_tests e gates mantêm o diretório de destino, o limite de trabalho e o conjunto de ferramentas do usuário. Conexão strings como DATABASE_URL ainda são descartadas; coloque-os no projeto própria configuração ou agrupar o comando em um script que os define, quando uma compilação precisa deles.
  • As regras de negação nas configurações de permissão agora são válidas para essas formas de ocultar um palavra de comando até que o shell a execute: uma variável ($v), uma substituição, uma lista glob ou chave, citação ANSI-C com escape ou um shell lendo seu script de um tubo, string aqui ou processo substituição. As regras em um arquivo execpolicy.toml separado são aplicadas quando o comando é executado, portanto, tal comando é recusado em tempo de execução, em vez de antes de um prompt de aprovação. Embora qualquer regra de negação esteja configurada na permissão configurações, tal comando é recusado em vez de ser verificado em relação ao texto o shell irá reescrever (um a política de aprovação sempre pergunta). Isto também se aplica a formulários comuns, como como source "$HOME/.cargo/env", eval "$(pyenv init -)" e $PYTHON -m pytest; nomeie o comando diretamente para executá-lo. O mesmo acontece quando o texto não analisa de forma limpa (uma citação não terminada, substituição ou heredoc, um case dentro de $( … )) ou quando o orçamento de análise acabar. Comandos depois if, then, while, do, ! e palavras semelhantes, function f { … } corpos e cargas úteis do find -exec agora são verificadas como qualquer outro comando.
  • Os comandos wrapper são desembrulhados pela sua gramática de opções reais, então chroot DIR cmd, sudo --user NAME cmd e timeout -s SIG N cmd expõem cmd (e qualquer carga útil -c) para negar regras. Opções ausentes em um wrapper tabela são lidas com e sem valor, as opções BSD e macOS são coberto (env -P, xargs -J, chroot -u) e mais invólucros são reconhecidos (caffeinate, arch, sandbox-exec, nsenter, unshare, runuser, flock, watch, wsl, noglob, nocorrect), incluindo grafias .exe. Código passado como string para trap, su -c, flock -c, script -c, watch, cmd /c e PowerShell -Command são verificados como linha de comando.
  • A aritmética (( … )) não lê mais << como um heredoc que esconde as linhas depois dele, e uma string de substituição xargs ou find -exec usada como comando ou como código shell (xargs -I{} sh -c {}) conta como conhecido apenas na execução tempo.
  • Os comandos task_shell_start e task gate agora são verificados em relação ao shell deny e pergunte regras, como qualquer outro comando shell.
  • Uma concessão de "aprovação para sessão" para um comando shell cobre apenas variantes de sinalizadores desse comando conforme escrito; um comando com opções antes do subcomando, uma cadeia ou código aninhado corresponde apenas a uma repetição idêntica.
  • A superfície do shell somente leitura para subagentes rejeita uma palavra que comece com um * sem aspas, cujas correspondências podem ser lidas como opções; citar o padrão ou atribua um prefixo de caminho (src/*.rs).
  • Um prefixo trusted ou de permissão como git status não cobre mais opções colocado antes do subcomando (git -c key=value status, git --exec-path=… status), nem um comando que execute código aninhado ou cujo a palavra de comando é resolvida em tempo de execução. Esses comandos são solicitados em vez disso. Negar digitado as regras também correspondem a uma palavra de comando qualificada por caminho (/bin/rm).
  • Comandos contendo parênteses não são mais aprovados automaticamente como paralelos comandos somente leitura, já que alguns shells os tratam como qualificadores glob ou substituição de comando.
  • As árvores de trabalho do subagente permanecem sob o .codewhale-worktrees/<repo>/ por repositório raiz: um worktree_path absoluto agora é mantido na mesma contenção que um relativo, com links simbólicos resolvidos antes da verificação. Qualquer começo que pergunte para uma árvore de trabalho mantém o cartão de aprovação, mesmo para uma função somente leitura. Um worktree_base começando com - foi recusado e git worktree add agora recebe seu caminho e base após --.
  • Os nomes da frota e do roteador de raciocínio devem ser nomes de arquivo simples (opcionalmente origin/name); um nome com separadores de caminho ou .. é recusado antes de qualquer o arquivo é consultado por meio de uma verificação compartilhada na caixa do fluxo de trabalho.
  • pandoc_convert e image_ocr aplicam a mesma lista de negação de leitura e verificações de armazenamento de credenciais como read, por meio de um auxiliar compartilhado e pandoc sempre funciona com --sandbox. Isso precisa do pandoc 2.15 ou mais recente; um mais velho pandoc recebe uma mensagem de atualização em vez de uma conversão.
  • Uso do computador: os caminhos de saída de captura de tela e zoom devem ser .png/.jpg/.jpeg arquivos dentro do diretório de gravações, e o zoom sempre corta o último raster capturado em vez de um arquivo de origem nomeado pelo chamador.
  • A sincronização do registro de habilidades recusa uma chave de índice que não seja segura para um único caminho nome antes de ser usado como diretório de cache, o mesmo verifica um instalado o nome da habilidade já recebe.
  • O .codewhale/config.toml de um projeto não pode mais configurar notes_path; é ignorado com as outras chaves somente do usuário. A ferramenta note e /note recusam um arquivo de notas que é um link simbólico ou cujo diretório é resolvido fora do espaço de trabalho e uma nota é liberada para o disco antes que a ferramenta relate sucesso.
  • Compara e mostra que lê o conteúdo do repositório (codewhale review, o Ferramentas git_diff/git_show, verificação, entrega, registros de tentativa de tarefa, @diff e as rotas diff de tempo de execução API) compartilham um conjunto de sinalizadores: sem diff, sem textconv e submódulos comparados apenas por commit, portanto, um submódulo filtros configurados e drivers diff nunca são executados. Leituras da árvore de trabalho (git_diff, git_show, git_blame, planejamento de commit, verificação, tarefa registros de tentativa, @diff/@git) também passam pela revisão reforçada comando, então os filtros limpos do repositório também não são executados. git_blame e shell somente leitura git blame pula textconv e shell somente leitura git leituras neutralizam os filtros limpos do repositório.

Frota e agentes

  • codewhale fleet run <spec> --check executa todas as validações que uma execução real faria e para por aí: nada é criado, lançado ou gasto.
  • Um agente na fila diz por que está esperando, por exemplo, quando os lançamentos são acelerado após os limites de taxa do provedor e quando para de esperar (#6277).
  • Agentes somente leitura podem executar comandos de inspeção encadeados (um dos principais cd, &&, ;, separadores echo, 2>/dev/null) e um comando recusado agora nomeia a regra que quebrou e o que fazer em seu lugar. Trabalhadores de frota duráveis aceite os mesmos comandos somente leitura que os agentes em sessão. A hora de um agente o orçamento começa quando é lançado, e um agente na fila que nunca consegue uma vaga diz que nunca começou (#6015).
  • Parar um agente que grava arquivos mantém e nomeia o trabalho que teve mudou, como uma parada orçamentária já mudou (#5529).
  • workflow(fleet:) executa frotas salvas na UI do Fleet e encontra espaço de trabalho Frotas sob .codewhale/fleets.
  • O tempo de execução API pode interromper a execução de um agente delegado a partir do desktop.
  • A resposta de um agente finalizado não é mais cortada. Sua linha e sua conclusão notificação mostra a primeira frase do seu resultado em vez de um Título ## Summary ou sua última ferramenta, e abrindo o agente mostra o todo resultado ou o motivo completo da interrupção, mesmo quando nenhuma transcrição foi capturada. Cada agente também tem um nome: o rótulo de uma tarefa de fluxo de trabalho ou o nome do despacho aparece nas linhas, na notificação e no tempo de execução API, nunca é id interno (#6565).
  • A página mobile mostra os agentes do thread: uma faixa nomeando cada um, seu estado e o que está fazendo ou o que encontrou, reconstruído quando a página reconecta. O cache de prompt do subagente agora conta para a sessão, incluindo relatórios somente gravação em cache. PRICE e /cache mostram o pai, os agentes e taxas de acerto combinadas, cada uma rotulada e ponderada por todos os tokens de entrada, incluindo gravações de cache, e o rodapé cache N% ainda significa as próprias solicitações desta conversa (#6565).
  • As visualizações GIT, FILES e NOTES do dock são reais. GIT mostra o branch e onde está contra a sua montante, as mudanças (com seus caminhos um Digite away), árvores de trabalho vinculadas e os últimos cinco commits, e mantém atualizando durante um turno enquanto estiver aberto. Diz "não é um repositório git" somente quando isso for verdade, relatará falhas nas sondagens de status na visualização e no compositor em vez de reivindicar uma árvore limpa, considera cada caminho não mesclado como um conflito, e apenas diz que há mais caminhos alterados quando a lista é limitada. FILES lista os arquivos nesta sessão editados, incluindo gravações sem recibos de comparação, e o arquivos que ele lê, com cada caminho exclusivo retido além do resumo da atividade visualização de doze caminhos. FILES e seu emblema são atualizados da sessão atual mesmo antes de o TASKS ser aberto. As edições com recibos mostram seu tamanho e abrem suas diferenças. NOTAS lista suas notas do /note. O idiota emblema, a visualização Git e a linha git do modelo agora compartilham um chamada git status --porcelain=v2, portanto, há menos processos git do que antes (#6565).
  • O trabalho em segundo plano informa quando termina, mesmo entre as atualizações. Em lote avisos de shell cobrem comandos explicitamente em segundo plano ou desanexados; primeiro plano resultados e conclusões antigas anteriores a esta sessão da TUI permanecem em silêncio. A troca de sessões não repete um aviso de conclusão. Em lote contagem de avisos concluídos, com falha e parados de trabalho separadamente; comandos shell, prompts de tarefas e erros permanecem no aplicativo, longe das notificações da tela de bloqueio. Um servidor de desenvolvimento em execução não retém mais o aviso. Falhou, matou e os projéteis expirados mantêm seus resultados e os últimos oito projéteis finalizados fique listado por sessão. As tarefas concluídas não parecem mais ativas ou reabrem o doca. Os rótulos de plano de fundo seguem o idioma da IU, as visualizações longas do agente mantêm seu ponteiro de resultado completo, e o indicador silencioso usa o relógio do motor e limite sem marcar uma ferramenta ativa como silenciosa (#6565).

Confiabilidade de lançamento

  • Faça upload da versão completa em um rascunho privado e verifique o tamanho de cada ativo e resumo SHA-256 e, em seguida, publique. Uma nova tentativa interrompida não pode reutilizar obsoleta bytes do mesmo tamanho. As tags de versão CNB e GHCR seguem a publicação canônica.
  • O bootstrap do Ubuntu Lighthouse requer CIDRs de origem SSH trusted ou um explícito aceitação do SSH público antes de alterar o host; IPv6 malformado e padrão amplo redes são recusadas.
