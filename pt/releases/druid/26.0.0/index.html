<a name="26.0.0-highlights-auto-type-column-schema-%28experimental%29" href="#26.0.0-highlights-auto-type-column-schema-%28experimental%29">#</a> Esquema de coluna de tipo automático (experimental)

Um novo esquema de coluna e indexador do tipo "automático" foi adicionado à ingestão nativa como a próxima iteração lógica da funcionalidade de coluna aninhada. Este indexador de coluna de tipo automático que produz a coluna mais apropriada para as entradas fornecidas, produzindo colunas STRING, ARRAY<STRING>, LONG, ARRAY<LONG>, DOUBLE, ARRAY<DOUBLE> ou COMPLEX<json>, todas compartilhando um formato 'aninhado' comum.

Todas as colunas produzidas por 'auto' possuem índices para auxiliar na filtragem rápida (ao contrário das colunas clássicas LONG e DOUBLE) e usam limites baseados em cardinalidade para tentar utilizar esses índices apenas quando é provável que realmente acelere a consulta (ao contrário das colunas STRING clássicas).

As colunas COMPLEX<json> produzidas por este indexador 'automático' armazenam matrizes de tipos escalares simples de maneira diferente de suas contrapartes 'json' (v4), armazenando-as como colunas do tipo ARRAY. Isso significa que a função JSON_VALUE agora pode extrair arrays inteiros, por exemplo JSON_VALUE(nested, '$.array' RETURNING BIGINT ARRAY). Não há mudança na forma como as matrizes de objetos complexos são armazenadas neste momento.

Essa melhoria também adiciona uma funcionalidade completamente nova ao Druid, colunas digitadas ARRAY, que, diferentemente das colunas clássicas de vários valores STRING, se comportam com a semântica ARRAY. Atualmente, essas colunas só podem ser criadas por meio do indexador do tipo 'auto' quando todos os valores são matrizes com o mesmo tipo de elementos.

Um tipo de dados array é um tipo de dados que permite armazenar vários valores em uma única coluna de uma tabela de banco de dados. Arrays são normalmente usados ​​para armazenar conjuntos de dados relacionados que podem ser facilmente acessados ​​e manipulados como um grupo.

Esta versão adiciona suporte para armazenar matrizes de valores primitivos, como ARRAY<STRING>, ARRAY<LONG> e ARRAY<DOUBLE> como colunas aninhadas especializadas, em vez de quebrá-las em colunas de elementos separados.

<a name="26.0.0-highlights-auto-type-column-schema-%28experimental%29-schema-auto-discovery-%28experimental%29" href="#26.0.0-highlights-auto-type-column-schema-%28experimental%29-schema-auto-discovery-%28experimental%29">#</a> Descoberta automática de esquema (experimental)

Estamos adicionando descoberta automática de esquema com inferência de tipo ao Druid. Com esse recurso, o tipo de dados de cada campo recebido é detectado quando o esquema está disponível. Para dados recebidos que podem conter campos adicionados, descartados ou alterados, você pode optar por rejeitar os dados não conformes (“o banco de dados está sempre correto - rejeitando dados inválidos!”) ou pode permitir que a descoberta automática do esquema altere a fonte de dados para corresponder aos dados recebidos (“os dados estão sempre corretos - altere o banco de dados!”). A descoberta automática de esquema é recomendada para novos casos de uso e ingestões. Para casos de uso existentes, tenha cuidado ao mudar para a descoberta automática de esquema porque o Druid ingerirá valores semelhantes a array (por exemplo, ["tag1", "tag2]) como colunas do tipo ARRAY<STRING> em vez de strings de vários valores (MV), isso pode causar problemas em aplicativos downstream que respondem ao comportamento MV. Não mude até que um caminho de migração oficial esteja disponível.

Para usar esse recurso, defina spec.dataSchema.dimensionsSpec.useSchemaDiscovery como true em sua tarefa ou especificação de supervisor ou, se estiver usando o carregador de dados no console, desmarque a alternância Explicitly define schema na etapa Configure schema. O Druid pode inferir o esquema inteiro ou parte dele se você listar explicitamente as dimensões em sua lista de dimensões.

A descoberta automática de esquema está disponível para ingestão nativa de lote e streaming.

<a name="26.0.0-highlights-unnest-arrays-%28experimental%29-" href="#26.0.0-highlights-unnest-arrays-%28experimental%29-">#</a> Matrizes UNNEST (experimentais)

Parte do que é interessante no UNNEST é como ele permite uma gama mais ampla de operações que não eram possíveis em tipos de dados Array. Você pode desaninhar matrizes com a função UNNEST (SQL) ou a fonte de dados unnest (nativa).

Unnest converte matrizes ou tabelas aninhadas em linhas individuais. A função UNNEST é particularmente útil ao trabalhar com tipos de dados complexos que contêm matrizes aninhadas, como JSON.

Por exemplo, suponha que você tenha uma tabela chamada “pedidos” com uma coluna chamada “itens” que contém uma matriz de produtos para cada pedido. Você pode usar unnest para extrair os produtos individuais ("each_item") como no exemplo SQL a seguir:

SELECT order_id, each_item FROM orders, UNNEST(items) as unnested(each_item)

Isso produz um conjunto de resultados com uma linha para cada item em cada pedido, com colunas para o ID do pedido e o item individual

Observe a vírgula após a tabela/fonte de dados esquerda (orders no exemplo). É obrigatório.

<a name="26.0.0-highlights-sort-merge-join-and-hash-shuffle-join-for-msq" href="#26.0.0-highlights-sort-merge-join-and-hash-shuffle-join-for-msq">#</a> Junção de classificação e mesclagem e junção aleatória de hash para MSQ

Agora podemos realizar junções aleatórias definindo o parâmetro de contexto sqlJoinAlgorithm como sortMerge para o algoritmo sort-merge ou omitindo-o para realizar junções de transmissão (padrão).

Consultas em vários estágios podem usar um algoritmo de junção de classificação e mesclagem. Com este algoritmo, cada junção de pares é planejada em seu próprio estágio com duas entradas. Essa abordagem geralmente tem menos desempenho, mas é mais escalável do que a transmissão.

Configure o parâmetro de contexto sqlJoinAlgorithm como sortMerge para usar este método.

As junções de hash de transmissão são semelhantes à forma como as consultas de junção nativas são executadas.

Expande a autenticação baseada em OIDC no Druid adicionando um autenticador JWT que valida tokens de ID associados a uma solicitação. O autenticador pac4j existente funciona para autenticar usuários da web enquanto acessam o console, enquanto este autenticador serve para validar solicitações Druid API feitas por Direct clients. Os serviços que já oferecem suporte ao OIDC podem anexar seus tokens de ID às solicitações do Druida sob o cabeçalho da solicitação de autorização.

<a name="26.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-real-time-tasks" href="#26.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-real-time-tasks">#</a> Tarefas em tempo real

<a name="26.0.0-upgrade-notes-and-incompatible-changes--incompatível-changes" href="#26.0.0-upgrade-notes-and-incompatible-changes--incompatível-changes">#</a> Alterações incompatíveis

<a name="26.0.0-upgrade-notes-and-incompatible-changes--incompatível-changes-firehose-ingestion-removed" href="#26.0.0-upgrade-notes-and-incompatible-changes--incompatível-changes-firehose-ingestion-removed">#</a> Ingestão de Firehose removida

A especificação firehose/parser usada pelos formatos de streaming Druid legados foi removida. A ingestão do Firehose foi descontinuada na versão 0.17 e o suporte para essa ingestão foi removido na versão 24.0.

#12852

<a name="26.0.0-upgrade-notes-and-incompatible-changes--incompatível-changes-information-schema-now-uses-numeric-column-types-" href="#26.0.0-upgrade-notes-and-incompatible-changes--incompatível-changes-information-schema-now-uses-numeric-column-types-">#</a> O esquema de informações agora usa tipos de colunas numéricas

A tabela do sistema Druid (INFORMATION_SCHEMA) agora usa tipos SQL em vez de tipos Druid para colunas. Essa alteração faz com que a tabela INFORMATION_SCHEMA se comporte mais como o SQL padrão. Talvez seja necessário atualizar suas consultas nos seguintes cenários para evitar resultados inesperados se você depender de um dos seguintes:

  • Campos numéricos sendo tratados como strings.
  • Numeração de colunas começando em 0. A numeração de colunas agora é baseada em 1.

#13777

<a name="26.0.0-upgrade-notes-and-incompatible-changes--incompatível-changes-%60frontcoded%60-segment-format-change" href="#26.0.0-upgrade-notes-and-incompatible-changes--incompatível-changes-%60frontcoded%60-segment-format-change">#</a> Alteração no formato do segmento frontCoded

O tipo frontCoded de stringEncodingStrategy em indexSpec com uma nova versão de formato de segmento, que normalmente possui velocidades de leitura mais rápidas e tamanho de segmento reduzido. Esta melhoria é incompatível com versões anteriores do Druid 25.0.

Para obter mais informações, consulte o destaque da estratégia de codificação de string frontCoded.

<a name="26.0.0-upgrade-notes-and-incompatible-changes-developer-notes" href="#26.0.0-upgrade-notes-and-incompatible-changes-developer-notes">#</a> Notas do desenvolvedor

<a name="26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-null-value-coercion-moved-out-of-expression-processing-engine-" href="#26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-null-value-coercion-moved-out-of-expression-processing-engine-">#</a> Coerção de valor nulo removida do mecanismo de processamento de expressão

Valores nulos inseridos e criados pelo mecanismo de processamento de expressão nativa Druida não forçam mais null ao valor 'padrão' apropriado do tipo se druid.generic.useDefaultValueForNull=true. Isto não deverá impactar o comportamento existente, uma vez que este foi transferido para o consumidor e internamente os operadores ainda usarão valores padrão neste modo. No entanto, pode haver mudanças sutis de comportamento no manuseio dos valores null. Chamadores diretos podem obter valores padrão usando o novo método valueOrDefault() de ExprEval, em vez de value().

#13809

<a name="26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-simplified-dependencies" href="#26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-simplified-dependencies">#</a> Dependências simplificadas

Os módulos druid-core, extendedset e druid-hll foram consolidados em druid-processing para simplificar as dependências. Quaisquer extensões que façam referência a estes devem ser atualizadas para usar druid-processing. Os binários de extensão existentes devem continuar a funcionar normalmente quando usados ​​com versões mais recentes do Druid.

Esta alteração não afeta os usuários finais. Isso afeta qualquer pessoa que desenvolva extensões para o Druida.
