Recursos, alterações e descontinuações importantes

Esta seção contém informações importantes sobre recursos novos e existentes.

Suporte Java 11

O suporte Java 11 foi descontinuado desde o Druid 32.0, e o suporte oficial será removido já no Druid 35.0.0

Ingestão baseada em Hadoop

A ingestão baseada em Hadoop foi descontinuada desde o Druid 32.0 e será removida já no Druid 35.0.0. Recomendamos um dos outros métodos de ingestão suportados pelo Druid, como ingestão baseada em SQL ou ingestão sem MiddleManager usando Kubernetes.

Como parte dessa mudança, agora você deve optar por usar o tipo de tarefa index_hadoop obsoleto. Se você não fizer isso, suas tarefas de ingestão baseadas em Hadoop falharão.

Para aceitar, defina druid.indexer.task.allowHadoopTaskExecution como true em seu arquivo common.runtime.properties.

#18239

Use instruções SET para parâmetros de contexto de consulta

Agora você pode usar instruções SET para definir parâmetros de contexto de consulta para uma consulta por meio do console Druid ou do API.

#17894 #17974

Instruções SET no console Druid

O console da web agora oferece suporte ao uso de instruções SET para especificar parâmetros de contexto de consulta. Por exemplo, se você incluir SET timeout = 20000; em sua consulta, o parâmetro de contexto de consulta de tempo limite será definido:

SET timeout = 20000;
SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2

#17966

SET instruções com o API

Consultas SQL emitidas para /druid/v2/sql agora podem incluir múltiplas instruções SET para criar contexto para a instrução final. Por exemplo, os seguintes resultados de consulta SQL incluem os parâmetros de contexto de consulta timeout, useCache, populateCache, vectorize e engine:

SET timeout = 20000;
SET useCache = false;
SET populateCache = false;
SET vectorize = 'force';
SET engine = 'msq-dart'
SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2

A chamada API para esta consulta é semelhante a esta:

curl --location 'http://HOST:PORT/druid/v2/sql' \
--header 'Content-Type: application/json' \
--data '{
  "query": "SET timeout=20000; SET useCache=false; SET populateCache=false; SET engine='\''msq-dart'\'';SELECT  user,  commentLength,COUNT(*) AS \"COUNT\" FROM wikipedia GROUP BY 1, 2 ORDER BY 2 DESC",
  "resultFormat": "array",
  "header": true,
  "typesHeader": true,
  "sqlTypesHeader": true
}'

Essa melhoria também funciona para consultas INSERT e REPLACE usando o mecanismo de tarefas MSQ. Observe que JDBC não é compatível.

Terminais HTTP aprimorados

Agora você pode usar SQL bruto no corpo HTTP para terminais /druid/v2/sql. Você pode definir Content-Type como text/plain em vez de application/json, para poder fornecer texto bruto que não tenha escape.

#17937

Históricos de clonagem (experimental)

Agora você pode configurar clones para Históricos usando a configuração dinâmica do Coordenador cloneServers. Os históricos clonados são úteis para situações como atualizações contínuas em que você deseja lançar um novo histórico em substituição a um existente.

Defina a configuração para um mapa do servidor histórico de destino para o histórico de origem:

  "cloneServers": {"historicalClone":"historicalOriginal"}

O clone não participa da atribuição ou balanceamento regular de segmentos. Em vez disso, o Coordenador espelha qualquer atribuição de segmento feita ao Histórico original no clone, para que o clone se torne uma cópia exata da origem. Os segmentos no clone Histórico também não contam para contagens de réplicas. Se o histórico original desaparecer, o clone permanecerá no último estado conhecido do servidor de origem até ser removido da configuração do cloneServers.

Ao consultar seus dados usando o mecanismo de consulta nativo, você pode preferir clones (preferClones), excluir (excludeClones) ou incluir (includeClones) configurando o parâmetro de contexto de consulta cloneQueryMode. Por padrão, os clones são excluídos.

Como parte desta mudança, novos Coordenadores APIs estão disponíveis. Para obter mais informações, consulte Coordenador APIs para clones.

#17863 #17899 #17956

Tarefas de morte incorporadas no Overlord (Experimental)

Agora você pode executar tarefas de eliminação diretamente no próprio Overlord. As tarefas de eliminação incorporadas oferecem vários benefícios; eles:

  • Elimine segmentos assim que forem elegíveis
  • Não ocupe espaço de tarefas
  • terminam mais rápido, pois usam consultas de metadados otimizadas e não lançam um novo JVM
  • Elimine um pequeno número de segmentos por tarefa, garantindo que os bloqueios em um intervalo não sejam mantidos por muito tempo
  • Ignore os intervalos bloqueados para evitar o bloqueio do cabeçalho
  • Requer configuração mínima
  • Pode acompanhar um grande número de segmentos não utilizados no cluster

Este recurso é controlado pelas seguintes configurações:

  • druid.manager.segments.killUnused.enabled - Se o recurso está habilitado ou não (o padrão é false)
  • druid.manager.segments.killUnused.bufferPeriod - O período de tempo que um segmento deve ficar sem uso antes que possa ser removido permanentemente dos metadados e do armazenamento profundo. Isso pode servir como um período de buffer para evitar a perda de dados se os dados acabarem sendo necessários após serem marcados como não utilizados (o padrão é P30D)

Para usar tarefas de eliminação incorporadas, você precisa ter o cache de metadados de segmento ativado.

Como parte desse recurso, novas métricas foram adicionadas.

#18028 #18124

Seleção de nível preferencial

Agora você pode configurar o serviço Broker para preferir Históricos em uma camada específica. Isto é útil para implantação em zonas de disponibilidade. Os corretores em uma AZ selecionam históricos na mesma AZ por padrão, mas ainda mantêm a capacidade de selecionar nós históricos em outra AZ se os históricos na mesma AZ não estiverem disponíveis.

Para ativar, configure a propriedade druid.broker.select.tier como perferred nas propriedades de tempo de execução do Broker. Você pode então configurar druid.broker.select.tier.preferred.tier para o nível que deseja que cada corretor prefira (ou seja, para corretores em AZ1, você pode definir isso para o nome do nível de seus servidores históricos AZ1).

#18136

Melhorias no dardo

O mecanismo de consulta Dart agora usa o endpoint /druid/v2/sql como outros mecanismos de consulta SQL. O antigo endpoint específico do Dart não é mais compatível. Para usar o Dart para uma consulta, inclua o parâmetro de contexto de consulta engine e defina-o como msq-dart.

#18003 #18003

A ativação do Dart permanece a mesma, adicione a seguinte linha aos seus arquivos broker/runtime.properties e historical/runtime.properties:

druid.msq.dart.enabled = true

Além disso, o Dart agora consulta tarefas em tempo real por padrão. Você pode controlar esse comportamento configurando o parâmetro de contexto de consulta includeSegmentSource como REALTIME (padrão) ou NONE, de maneira semelhante às tarefas MSQ. Você também pode executar consultas síncronas ou assíncronas.

Como tal alteração não é totalmente suportada pelo sistema subjacente, uma solicitação para fazer tal alteração resultará em um erro 400.

Gerenciamento de cluster

Tempo limite configurável para subtarefas

Agora você pode configurar um tempo limite para tarefas do tipo index_parallel e compact. Configure o parâmetro de contexto subTaskTimeoutMillis para o tempo máximo em milissegundos que você deseja esperar antes que uma subtarefa seja cancelada. Por padrão, não há tempo limite.

Usar esta configuração ajuda as tarefas pai a falharem mais cedo, em vez de ficarem presas na execução de subtarefas zumbis.

Notas de atualização e alterações incompatíveis

Notas de atualização

Ingestão baseada em Hadoop

A ingestão baseada em Hadoop foi descontinuada desde o Druid 32.0 e será removida já no Druid 35.0.0.

Recomendamos um dos outros métodos de ingestão suportados pelo Druid, como ingestão baseada em SQL ou ingestão sem MiddleManager usando Kubernetes. Como parte dessa alteração, agora você deve optar por usar o tipo de tarefa index_hadoop obsoleto. Se você não fizer isso, suas tarefas de ingestão baseadas em Hadoop falharão. Para aceitar, defina druid.indexer.task.allowHadoopTaskExecution como true em seu arquivo common.runtime.properties. #18239

Consultas groupBy e topN

Druid agora usa o tipo de consulta nativa groupBy, em vez de topN, para consultas SQL que agrupam por e ordenar pela mesma coluna, tem LIMIT e não tem HAVING. Isso acelera a execução de tais consultas, uma vez que groupBy é vetorizado, enquanto topN não é.

É possível restaurar o comportamento anterior configurando o parâmetro de contexto de consulta useLexicographicTopN como true. O comportamento do useApproximateTopN permanece inalterado e o padrão permanece true.

#18074

Configuração IS_INCREMENTAL_HANDOFF_SUPPORTED removida

Removida a referência de contexto IS_INCREMENTAL_HANDOFF_SUPPORTED dos supervisores, pois a publicação incremental tem sido o comportamento padrão desde a versão 0.16.0. Este contexto foi originalmente introduzido para suportar reversão para LegacyKafkaIndexTaskRunner em versões anteriores a 0.16.0, que já foi removido.

Configuração useMaxMemoryEstimates removida

Removida a configuração useMaxMemoryEstimates. Quando definido como falso, o Druid usou uma estimativa de memória muito mais precisa que foi introduzida no Druid 0.23.0. Esse método mais preciso é o único método disponível agora. A configuração foi padronizada como falsa para vários lançamentos.
