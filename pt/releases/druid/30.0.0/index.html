<a name="30.0.0-upcoming-removals" href="#30.0.0-upcoming-removals">#</a> Próximas remoções

Como parte das melhorias contínuas do Druid, estamos descontinuando certos recursos e comportamentos em favor de iterações mais recentes que oferecem recursos mais robustos e estão mais alinhados com o SQL ANSI padrão. Muitos desses novos recursos têm sido o padrão para novas implantações em diversas versões.

Os seguintes recursos estão obsoletos e atualmente planejamos remover o suporte no Druid 32.0.0:

  • Tratamento nulo não compatível com SQL: Por padrão, o Druid agora diferencia entre uma string vazia e um registro sem dados, bem como entre um registro numérico vazio e 0. Para obter mais informações, consulte valores NULOS. Para obter um tutorial sobre a lógica compatível com SQL, consulte o tutorial de manipulação de nulos.
  • Manuseio booleano não estrito: Druida agora usa estritamente 1 (verdadeiro) ou 0 (falso). Anteriormente, verdadeiro e falso podiam ser representados como true e false ou como 1 e 0, respectivamente. Além disso, Druid agora retorna um valor nulo para comparações booleanas como True && NULL. Para obter mais informações, consulte Lógica booleana. Para obter exemplos de filtros que usam a lógica compatível com SQL, consulte Filtros de consulta.
  • Lógica de dois valores: por padrão, o Druid agora usa lógica de três valores para ingestão e consulta. Isso afeta principalmente os filtros que usam operações NOT lógicas em colunas com valores NULL. Para obter mais informações, consulte Lógica booleana. Para obter exemplos de filtros que usam a lógica compatível com SQL, consulte Filtros de consulta.

Os supervisores de ingestão de streaming agora suportam anexação simultânea, ou seja, tarefas de streaming podem ser executadas simultaneamente com uma tarefa de substituição (compactação ou reindexação) se também estiver usando bloqueios simultâneos. Depois de atualizar o supervisor para ter "useConcurrentLocks": true, a transição para acréscimo simultâneo ocorre perfeitamente, sem causar atraso de ingestão ou falhas de tarefa.

O Druid agora executa a limpeza ativa de segmentos pendentes obsoletos, rastreando o conjunto de tarefas usando esses segmentos pendentes. Isso permite que acréscimos e substituições simultâneos atualizem apenas um conjunto mínimo de segmentos pendentes e, assim, melhorem o desempenho e eliminem erros. Antes que o Druid envie segmentos em tempo real para armazenamento profundo, os segmentos consistem em arquivos derramados. <a name="30.0.0-important-features%2C-changes%2C-and-deprecations-improved-and-filter-performance" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-improved-and-filter-performance">#</a> Melhor desempenho do filtro AND

O processamento de consulta druida agora determina de forma adaptativa quando os filhos dos filtros AND devem calcular índices e quando simplesmente corresponder as linhas durante a varredura com base na seletividade de outros filtros. Conhecido como particionamento de filtros, pode resultar em aumentos dramáticos de desempenho, dependendo da ordem dos filtros na consulta.

Por exemplo, faça uma consulta como SELECT SUM(longColumn) FROM druid.table WHERE stringColumn1 = '1000' AND stringColumn2 LIKE '%1%'. Anteriormente, o Druid usava índices ao processar filtros, se eles estivessem disponíveis. Isso nem sempre é ideal; imagine se stringColumn1 = '1000' correspondesse a 100 linhas. Com índices, temos que encontrar todos os valores de stringColumn2 LIKE '%1%' que sejam verdadeiros para calcular os índices do filtro. Se stringColumn2 tiver mais de 100 valores, acaba sendo pior do que simplesmente verificar se há correspondência nas 100 linhas restantes.

Com a nova lógica, o Druid agora verifica a seletividade dos índices à medida que processa cada cláusula do filtro AND. Se determinar que seria mais trabalhoso calcular o índice do que corresponder às linhas restantes, o Druid ignora o cálculo do índice.

A ordem em que você escreve os filtros em uma cláusula WHERE de uma consulta pode melhorar o desempenho da sua consulta. Mais melhorias estão chegando, mas você pode testar as melhorias existentes reordenando uma consulta. Coloque índices menos intensivos para calcular, como IS NULL, = e comparações (>, >=, < e <=) perto do início dos filtros AND para que o Druid processe suas consultas com mais eficiência. Não ordenar seus filtros dessa maneira não prejudicará o desempenho das versões anteriores, pois o comportamento de fallback é o que o Druid fazia anteriormente.

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-centralized-datasource-schema-%28alpha%29" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-centralized-datasource-schema-%28alpha%29">#</a> Esquema de fonte de dados centralizada (alfa)

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-rabbitmq-extension" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-rabbitmq-extension">#</a> Extensão RabbitMQ

Uma nova extensão RabbitMQ está disponível como contribuição da comunidade. A extensão RabbitMQ (druid-rabbit-indexing-service) permite gerenciar a criação e a vida útil de tarefas de indexação de coelho. Essas tarefas de indexação leem eventos de RabbitMQ até super streams.

Como os superstreams permitem entrega exatamente uma vez com suporte total para particionamento, eles são compatíveis com o algoritmo de ingestão moderno do Druid, sem as desvantagens do firehose anterior do RabbitMQ.

Observe que isso usa o recurso de streams do RabbitMQ e não uma troca convencional. Você precisa ter certeza de que suas mensagens estão em um super stream antes do consumo. Para obter mais informações, consulte documentação do RabbitMQ.

<a name="30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60googletasklogs%60-upload-buffer-size" href="#30.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60googletasklogs%60-upload-buffer-size">#</a> Tamanho do buffer de upload GoogleTaskLogs

Alterado o tamanho do buffer de upload em GoogleTaskLogs para 1 MB em vez de 15 MB para permitir mais uploads em paralelo e evitar que o serviço MiddleManager fique sem memória.

#16236

<a name="30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes" href="#30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes">#</a> Alterações incompatíveis

<a name="30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-changes-to-%60targetdatasource%60-in-explain-queries" href="#30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-changes-to-%60targetdatasource%60-in-explain-queries">#</a> Alterações em targetDataSource em consultas EXPLAIN

O Druida 30.0.0 inclui uma alteração significativa que restaura o comportamento do targetDataSource para seu estado 28.0.0 e anterior, diferente do Druida 29.0.0 e apenas do 29.0.0. Em 29.0.0, targetDataSource retorna um objeto JSON que inclui o nome da fonte de dados. Em todas as outras versões, targetDataSource retorna uma string contendo o nome da fonte de dados.

Se você estiver atualizando de qualquer versão diferente da 29.0.0, não haverá alteração no comportamento.

Se você estiver atualizando do 29.0.0, esta é uma alteração incompatível.

#16004

<a name="30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-zookeeper-based-segment-loading" href="#30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-zookeeper-based-segment-loading">#</a> Carregamento de segmento baseado em ZooKeeper removido

O carregamento de segmento baseado em ZooKeeper está sendo removido devido a problemas conhecidos. Ele foi descontinuado por vários lançamentos. Melhorias recentes no Druid Coordinator melhoraram significativamente o desempenho com carregamento de segmentos baseado em HTTP.

#15705

<a name="30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-coordinator-configs" href="#30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-coordinator-configs">#</a> Configurações do coordenador removidas

Removidas as seguintes configurações do Coordenador:

  • druid.coordinator.load.timeout: Não é necessário porque o valor padrão deste parâmetro (15 minutos) funciona bem para todos os clusters.
  • druid.coordinator.loadqueuepeon.type: Não é necessário pois este valor é sempre http.
  • druid.coordinator.curator.loadqueuepeon.numCallbackThreads: Não é necessário porque o carregamento de segmento baseado em ZooKeeper (curador) não é mais uma opção.

A limpeza automática de configurações de compactação de fontes de dados inativas agora está habilitada por padrão.
