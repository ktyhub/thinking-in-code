<a name="31.0.0-important-features-changes-and-deprecations-projections-experimental" href="#31.0.0-important-features-changes-and-deprecations-projections-experimental">#</a> Projeções (experimentais)

Druid 31.0.0 inclui suporte experimental para um novo recurso chamado projeções. As projeções são pré-agregados agrupados de um segmento que são usados ​​automaticamente no momento da consulta para otimizar a execução de quaisquer consultas que se 'ajustem' ao formato da projeção, reduzindo o custo de cálculo e de E/S, reduzindo o número de linhas que precisam ser processadas. As projeções estão contidas em segmentos de uma fonte de dados e aumentam o tamanho do segmento. Mas eles podem compartilhar dados, como dicionários de valores de colunas codificadas por dicionário, com as colunas do segmento base.

Atualmente, as projeções suportam apenas a ingestão baseada em JSON, mas podem ser usadas por consultas que usam o mecanismo de tarefas MSQ ou o novo mecanismo Dart. O desenvolvimento futuro permitirá a criação de projeções como parte da ingestão baseada em SQL.

Temos muitos planos para continuar a melhorar esse recurso nas próximas versões, mas estamos entusiasmados em disponibilizá-lo para que os usuários possam começar a experimentar, já que as projeções podem melhorar drasticamente o desempenho da consulta.

Para obter mais informações, consulte Projeções.

<a name="31.0.0-important-features%2C-changes%2C-and-deprecations-low-latency-high-complexity-queries-using-dart-%28experimental%29" href="#31.0.0-important-features%2C-changes%2C-and-deprecations-low-latency-high-complexity-queries-using-dart-%28experimental%29">#</a> Consultas de baixa latência e alta complexidade usando Dart (experimental)

A topologia de tempo de execução assíncrona distribuída (Dart) foi projetada para oferecer suporte a consultas de alta complexidade, como junções grandes, agrupamento por alta cardinalidade, subconsultas e expressões de tabela comuns, comumente encontradas em cargas de trabalho de data warehouse ad-hoc. Em vez de usar mecanismos de data warehouse como Spark ou Presto para executar consultas de alta complexidade, você pode usar o Dart, aliviando a necessidade de infraestrutura adicional.

Para obter mais informações, consulte Dart.

<a name="31.0.0-functional-areas-and-related-changes-querying" href="#31.0.0-functional-areas-and-related-changes-querying">#</a> Consultando

<a name="31.0.0-functional-areas-and-related-changes-querying-dart" href="#31.0.0-functional-areas-and-related-changes-querying-dart">#</a> Dardo

Dart é um mecanismo de consulta com trabalhadores multithread que realiza embaralhamentos na memória para fornecer simultaneidade ajustável e custos de infraestrutura para consultas de baixa latência e alta complexidade.

Para experimentar o Dart, defina druid.msq.dart.enabled como true em suas propriedades de tempo de execução comuns. Em seguida, você pode selecionar Dart como mecanismo de consulta no console da web ou por meio do API /druid/v2/sql/dart, que aceita a mesma carga útil JSON que /druid/v2/sql. O Dart é totalmente compatível com as formas de consulta Druid atuais e o formato de armazenamento do Druid. Isso significa que você pode experimentar o Dart com suas consultas e fontes de dados existentes.

<a name="31.0.0-functional-areas-and-related-changes-querying-projections" href="#31.0.0-functional-areas-and-related-changes-querying-projections">#</a> Projeções

Como recurso experimental, as projeções ainda não estão bem documentadas, mas podem ser definidas para ingestão de streaming e ingestão de lote 'clássica' como parte do dataSchema. Para obter um exemplo de especificação de ingestão, consulte a descrição da solicitação pull para #17214.

O campo groupingColumns na especificação define a ordem em que os dados são classificados na projeção. Em vez de definir explicitamente a granularidade como na tabela base, você a define com uma coluna virtual. Durante a ingestão, a lógica de processamento encontra a coluna virtual de granularidade “melhor” que é uma expressão timestamp_floor e a utiliza como a coluna __time para a projeção. As projeções não precisam ter uma coluna de tempo definida. Nesses casos, eles ainda podem corresponder a consultas que não estão sendo agrupadas no prazo.

Existem novos sinalizadores de contexto de consulta que foram adicionados para auxiliar na experimentação com projeções:

  • useProjection aceita um nome de projeção específico e instrui o mecanismo de consulta que deve usar essa projeção e falhará na consulta se a projeção não corresponder à consulta
  • forceProjections aceita verdadeiro ou falso e instrui o mecanismo de consulta que deve usar uma projeção e falhará na consulta se não conseguir encontrar uma projeção correspondente
  • noProjections aceita verdadeiro ou falso e instrui os mecanismos de consulta a não usarem projeções

<a name="31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes" href="#31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes">#</a> Notas de atualização

<a name="31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-array-ingest-mode-now-defaults-to-array" href="#31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-array-ingest-mode-now-defaults-to-array">#</a> O modo de ingestão de array agora é padronizado como array

O sinalizador de contexto de ingestão baseado em SQL arrayIngestMode agora tem como padrão array em vez de mvd. Isso significa que os tipos SQL VARCHAR ARRAY não são mais traduzidos e armazenados implicitamente em colunas VARCHAR, mas são armazenados como VARCHAR ARRAY. Essa alteração permite que outros tipos de matriz, como BIGINT ARRAY e DOUBLE ARRAY, sejam inseridos com MSQ em seus respectivos tipos de coluna de matriz, em vez de falharem como acontece no modo mvd.

Para continuar a armazenar sequências de vários valores, modifique quaisquer consultas de inserção/substituição para agrupar os tipos de matriz com o operador ARRAY_TO_MV.

A validação existe para evitar a mistura de colunas VARCHAR e VARCHAR ARRAY na mesma tabela, portanto, qualquer ingestão afetada por essa alteração falhará e fornecerá uma mensagem de erro descritiva em vez de exibir um comportamento inesperado.

A opção arrayIngestMode de none foi removida. Foi introduzido antes da lógica de validação de tabela como um meio para os operadores de cluster forçarem os escritores de consulta a definir explicitamente array ou mvd em seus contextos de consulta, mas fornece pouca utilidade no Druid 31.

Consulte os seguintes tópicos para obter mais informações:

  • Ingerir dimensões de vários valores sobre como ingerir strings de vários valores.
  • Ingerir matrizes para ingerir matrizes.

#16789

<a name="31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-removed-task-action-audit-logging" href="#31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-removed-task-action-audit-logging">#</a> Registro de auditoria de ação de tarefa removido

O registro de auditoria de ação de tarefa obsoleto foi removido. Esta alteração inclui as seguintes atualizações:

  • O endpoint /indexer/v1/task/{taskId}/segments não é mais suportado.
  • Druid não grava ou lê na tabela de metadados druid_taskLog.
  • Druida ignora a propriedade druid.indexer.auditlog.enabled.
  • Druida não emite a métrica task/action/log/time.

Essas alterações são compatíveis com versões anteriores de todas as extensões de armazenamento de metadados existentes.

#16309

<a name="31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-removed-firehose-and-firehosefactory" href="#31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-removed-firehose-and-firehosefactory">#</a> Firehose e FirehoseFactory removidos

Firehose e FirehoseFactory removidos e implementações restantes. O Apache descontinuou o suporte para firehoses Druid na versão 0.17. O suporte para ingestão de firehose foi removido na versão 26.0.

#16758

<a name="31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-front-coded-dictionaries" href="#31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-front-coded-dictionaries">#</a> Dicionários com código frontal

<!--Continue até 32. Em seguida, mova-o para alterações incompatíveis -->

Os dicionários com código frontal reduzem o armazenamento e melhoram o desempenho, otimizando strings em que a parte frontal é semelhante.

Depois que esse recurso estiver ativado, você não poderá fazer downgrade facilmente para uma versão anterior que não ofereça suporte ao recurso.

Para obter mais informações, consulte Guia de migração: dicionários com código frontal. Se você já estiver usando esse recurso, não precisará realizar nenhuma ação.

<a name="31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-storage-improvement-features" href="#31.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-storage-improvement-features">#</a> Recursos de melhoria de armazenamento

Druid 31.0.0 inclui melhorias de armazenamento que não são compatíveis com versões anteriores. Depois de ativar a classificação flexível de segmentos ou compressão para colunas complexas, você não poderá fazer downgrade para uma versão anterior a 31.0.0. Teste exaustivamente esses recursos antes de implementá-los em seu cluster de produção.

<a name="31.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes" href="#31.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes">#</a> Alterações incompatíveis

<a name="31.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-the-scan-query-legacy-mode" href="#31.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-the-scan-query-legacy-mode">#</a> Removido o modo legado de consulta de verificação

O modo legado de consulta de verificação nativa foi removido. Foi introduzido no Druid 0.11 para manter a compatibilidade durante uma atualização de versões mais antigas do Druid, onde a consulta de varredura fazia parte de uma extensão contrib.

#16659

"legacy":false codificado após a remoção do modo legado para evitar erros durante atualizações ou downgrades contínuos.

#16793

<a name="31.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-zk-based-segment-loading" href="#31.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-zk-based-segment-loading">#</a> Carregamento de segmento baseado em ZK

O carregamento de segmentos baseado em ZK agora está desativado. ZK servedSegmentsPath foi descontinuado no Druid 0.7.1. Este caminho legado foi substituído por liveSegmentsPath.

Processos de atendimento a segmentos, como Peons, Históricos e Indexadores, não criam mais entradas ZK loadQueuePath. As propriedades druid.zk.paths.loadQueuePath e druid.zk.paths.servedSegmentsPath não são mais utilizadas.

Mude primeiro para o carregamento de segmento baseado em HTTP e depois execute a atualização de versão.

<a name="31.0.0-upgrade-notes-and-incompatible-changes-%60storageadapter%60-changes" href="#31.0.0-upgrade-notes-and-incompatible-changes-%60storageadapter%60-changes">#</a> alterações no StorageAdapter

Se você escrever extensões personalizadas, especificamente mecanismos de consulta ou qualquer outra coisa que envolva a interface StorageAdapter, 31.0.0 incluirá alterações em APIs de baixo nível que podem impactar você. Todos os métodos em StorageAdapter agora lançam uma exceção Druid.

Prepare-se para essas alterações antes de atualizar para 31.0.0 ou posterior. Para obter mais informações, consulte as seguintes solicitações pull:

  • #16985
  • #16849
  • #16533
