druida druida-0.22.0

Apache Druid 0.22.0 contém mais de 400 novos recursos, correções de bugs, melhorias de desempenho, melhorias de documentação e cobertura de teste adicional de 73 colaboradores. Veja o conjunto completo de alterações para detalhes adicionais.

<a name="22-new-features" href="#22-new-features">#</a> Novos recursos

<a name="22-query" href="#22-query">#</a> Mecanismo de consulta

<a name="22-multi-distinct" href="#22-multi-distinct">#</a> Suporte para vários agregadores distintos na mesma consulta

Druid agora pode suportar múltiplas contagens 'exatas' de DISTINCT usando o agregador de agrupamento normalmente usado com conjuntos de agrupamento. Observe que isso se aplica apenas a contagens exatas - quando druid.sql.planner.useApproximateCountDistinct é falso e pode ser ativado configurando druid.sql.planner.useGroupingSetForExactDistinct como true. https://github.com/apache/druid/pull/11014

<a name="22-array-agg" href="#22-array-agg">#</a> Funções agregadoras SQL ARRAY_AGG e STRING_AGG

A função de agregação ARRAY_AGG foi adicionada, para permitir acumular valores ou valores distintos de uma coluna em um único resultado de array. Esta versão também adiciona STRING_AGG, que é semelhante ao ARRAY_AGG, exceto que une os valores da matriz em uma única string com um 'delimitador' fornecido e ignora valores nulos. Ambas as funções aceitam um parâmetro de tamanho máximo para controlar o tamanho máximo do resultado e falharão se esse valor for excedido. Consulte a documentação SQL para obter detalhes adicionais. https://github.com/apache/druid/pull/11157 https://github.com/apache/druid/pull/11241

<a name="22-bitwise" href="#22-bitwise">#</a> Expressões e agregadores de funções matemáticas bit a bit

Várias novas funções SQL funcionam para realizar matemática 'bit a bit' (junto com expressões nativas correspondentes), incluindo BITWISE_AND, BITWISE_OR, BITWISE_XOR e assim por diante. Além disso, as funções de agregação BIT_AND, BIT_OR e BIT_XOR foram adicionadas para acumular valores em uma coluna com a função bit a bit correspondente. Para obter detalhes completos, consulte documentação SQL. https://github.com/apache/druid/pull/10605 https://github.com/apache/druid/pull/10823 https://github.com/apache/druid/pull/11280

<a name="22-human-format" href="#22-human-format">#</a> Funções de formato de número legível por humanos

Três novas funções SQL e de formato de número de expressão nativa foram adicionadas no Druid 0.22.0, HUMAN_READABLE_BINARY_BYTE_FORMAT, HUMAN_READABLE_DECIMAL_BYTE_FORMAT e HUMAN_READABLE_DECIMAL_FORMAT, que permitem transformar os resultados em um formato de consumo mais amigável para resultados de consulta. Para obter mais informações, consulte documentação SQL. https://github.com/apache/druid/issues/10584 https://github.com/apache/druid/pull/10635

<a name="22-expr-agg" href="#22-expr-agg">#</a> Agregador de expressões

Druid 0.22.0 adiciona uma nova função agregadora de expressão de consulta 'nativa' JSON, que permite usar expressões nativas Druid para executar operações de "dobra" (alternativamente conhecidas como "redução") para acumular algum valor em qualquer número de colunas de entrada. Isso adiciona flexibilidade significativa ao que pode ser feito em um agregador Druida, semelhante em muitos aspectos ao que era possível com o agregador Javascript, mas de uma maneira muito mais segura e em área restrita. As expressões agora capazes de realizar uma "dobra" nas colunas de entrada também completam as habilidades das expressões nativas, além das funções anteriormente possíveis de "mapa" (colunas virtuais de expressão), "filtro" (filtros de expressão) e pós-transformação (pós-agregadores de expressão). Como usa expressões, o desempenho ainda não é ideal e ainda não está documentado diretamente, mas é a tecnologia subjacente por trás das funções SQL ARRAY_AGG, STRING_AGG e agregador bit a bit também adicionadas nesta versão. https://github.com/apache/druid/pull/11104

<a name="22-sql-routing" href="#22-sql-routing">#</a> Melhorias no roteamento de consultas SQL

Druid 0.22 adiciona alguns novos recursos para fornecer aos gravadores de extensão controle aprimorado sobre como as consultas são roteadas entre roteadores e corretores Druid. O primeiro adiciona uma nova estratégia de seleção de corretor manual ao roteador Druida, que permite que uma consulta especifique manualmente para quais corretores Druida uma consulta deve ser enviada com base em um parâmetro de contexto de consulta brokerService para qualquer pool de corretores definido em druid.router.tierToBrokerMap (isso corresponde ao 'nome de serviço' do conjunto de corretores, druid.service). O segundo novo recurso permite que o roteador Druid analise e examine consultas SQL para que as estratégias de seleção de corretores também possam funcionar para consultas SQL. Isso pode ser habilitado configurando druid.router.sql.enable como verdadeiro. Isso não afeta as consultas JDBC, que usam um mecanismo diferente para facilitar conexões "fixas" com um único intermediário. https://github.com/apache/druid/pull/11566 https://github.com/apache/druid/pull/11495

<a name="22-query-error-log" href="#22-query-error-log">#</a> Registro de erro de consulta aprimorado

As exceções de consulta foram alteradas do nível WARN para o nível ERROR para incluir informações adicionais nos logs para ajudar a solucionar falhas de consulta. Além disso, foi adicionado um novo sinalizador de contexto de consulta, enableQueryDebugging, que incluirá rastreamentos de pilha nesses logs de erros de consulta, para fornecer ainda mais informações sem a necessidade de habilitar logs no nível DEBUG. https://github.com/apache/druid/pull/11519

<a name="22-batch" href="#22-batch">#</a> Ingestão de lote nativo

<a name="22-shuffle-deep-storage" href="#22-shuffle-deep-storage">#</a> Suporte para uso de armazenamento profundo para dados aleatórios intermediários

As tarefas de ingestão de duas fases nativas do Druid 'perfect rollup' agora suportam o uso de armazenamento profundo como um local de embaralhamento, como uma alternativa aos discos locais em gerentes intermediários ou indexadores. Para usar esse recurso, configure druid.processing.intermediaryData.storage.type como deepstore, que usa o tipo de armazenamento profundo configurado. Nota - Com o tipo "deepstore", os dados são armazenados no diretório shuffle-data no caminho de armazenamento profundo configurado, a limpeza automática para este diretório ainda não é suportada. É possível configurar regras de ciclo de vida de armazenamento em nuvem para limpeza automática de dados no local do prefixo shuffle-data. https://github.com/apache/druid/pull/11507

<a name="22-batch-memory" href="#22-batch-memory">#</a> Melhor uso da memória da tarefa de ingestão de lote nativo

A ingestão em lote nativa do Druid recebeu uma nova opção de configuração, druid.indexer.task.batchProcessingMode, que introduz dois novos modos operacionais que devem permitir que a ingestão em lote opere com um consumo de memória heap menor e mais previsível. O modo CLOSED_SEGMENTS_SINKS é o mais agressivo, e deve ter o menor consumo de memória, e funciona eliminando o rastreamento de memória e mmap de segmentos intermediários produzidos durante a criação do segmento, mas não é muito bem testado neste ponto, por isso é considerado experimental. CLOSED_SEGMENTS, que é a nova opção padrão, elimina mmap de segmentos intermediários, mas ainda rastreia todo o conjunto de segmentos no heap, embora seja relativamente bem testado neste ponto e considerado estável. OPEN_SEGMENTS usará o caminho de ingestão anterior, que é compartilhado com a ingestão de streaming e executa um mmap em segmentos intermediários e constrói uma linha do tempo para que esses segmentos possam ser consultados por consultas em tempo real. Isso não é necessário para lote, mas o modo OPEN_SEGMENTS pode ser selecionado se ocorrer algum problema com os 2 modos mais recentes. https://github.com/apache/druid/pull/11123 https://github.com/apache/druid/pull/11294 https://github.com/apache/druid/pull/11536

<a name="22-batch-wait-for-handoff" href="#22-batch-wait-for-handoff">#</a> Permitir que tarefas em lote aguardem até a transferência do segmento antes de serem concluídas

As tarefas de ingestão em lote nativas do Druid agora podem ser configuradas opcionalmente para não terminarem até que os segmentos ingeridos sejam completamente carregados pelos servidores históricos. Isto pode ser útil para cenários em que vale a pena manter um slot de tarefa extra ocupado usando o estado da tarefa como uma medida para saber se a ingestão foi concluída e os segmentos estão disponíveis para consulta. Isso pode ser habilitado adicionando awaitSegmentAvailabilityTimeoutMillis ao tuningConfig na especificação de ingestão, que especifica o tempo máximo que uma tarefa aguardará o carregamento dos segmentos antes de terminar. Se nem todos os segmentos estiverem disponíveis quando esse tempo limite expirar, o trabalho ainda será bem-sucedido. Porém, no relatório de ingestão, segmentAvailabilityConfirmed será falso. Isso indica que a transferência não foi bem-sucedida e esses segmentos recém-indexados podem não estar disponíveis para consulta. Por outro lado, se todos os segmentos ficarem disponíveis para consulta nos serviços Históricos antes que o tempo limite expire, o valor dessa chave no relatório será verdadeiro. Este valor tuningConfig não é suportado para tarefas de compactação neste momento. Se um usuário tentar especificar um valor para awaitSegmentAvailabilityTimeoutMillis para Compactação, a tarefa falhará informando ao usuário que ela não é suportada. https://github.com/apache/druid/pull/10676

<a name="22-compact" href="#22-compact">#</a> Gerenciamento do ciclo de vida dos dados

<a name="22-compact-granularity" href="#22-compact-granularity">#</a> Suporte ao gerenciamento de segmento e granularidade de consulta para compactação automática

A compactação manual e automática do Druid agora pode ser configurada para alterar a granularidade do segmento, e a compactação manual também pode alterar a granularidade da consulta. Além disso, a compactação preservará a granularidade do segmento por padrão. Isso permite que as operadoras executem opções com mais facilidade, como alterar dados mais antigos para segmentos maiores e granularidades de consulta em troca da redução do tamanho dos dados. Consulte documentos de compactação para obter detalhes. https://github.com/apache/druid/pull/10843 https://github.com/apache/druid/pull/10856 https://github.com/apache/druid/pull/10900 https://github.com/apache/druid/pull/10912 https://github.com/apache/druid/pull/11009

<a name="22-compact-skip-lock" href="#22-compact-skip-lock">#</a> Permitir que a compactação pule temporariamente os intervalos bloqueados

A compactação automática do Druid agora, por padrão, ignora temporariamente os intervalos bloqueados em vez de esperar que o bloqueio seja liberado, o que deve melhorar a taxa na qual as fontes de dados podem ser compactadas. Isso é controlado por druid.coordinator.compaction.skipLockedIntervals e pode ser definido como falso se esse comportamento não for desejado por algum motivo. https://github.com/apache/druid/pull/11190

<a name="22-config-cleanup" href="#22-config-cleanup">#</a> Suporte para limpeza automática adicional de metadados

Você pode configurar a limpeza automatizada para remover registros do armazenamento de metadados após excluir algumas entidades do Druid:

  • registros de segmentos
  • registros de auditoria
  • registros do supervisor
  • registros de regras
  • registros de configuração de compactação
  • registros de fontes de dados criados por supervisores Esse recurso ajuda a manter o desempenho quando você tem uma alta taxa de rotatividade de fontes de dados, o que significa que você cria e exclui frequentemente muitas fontes de dados de curta duração ou outras entidades relacionadas. Você pode limitar o período de retenção de registros de metadados não utilizados para evitar que seu armazenamento de metadados fique cheio. Consulte documentação de limpeza automática para obter mais informações. https://github.com/apache/druid/pull/11078 https://github.com/apache/druid/pull/11084 https://github.com/apache/druid/pull/11164 https://github.com/apache/druid/pull/11200 https://github.com/apache/druid/pull/11227 https://github.com/apache/druid/pull/11232 https://github.com/apache/druid/pull/11245

<a name="22-data-cleanup" href="#22-data-cleanup">#</a> Descartando dados

Uma nova configuração, dropExisting, foi adicionada ao ioConfig das tarefas de ingestão de lote nativas do Druid e compactação, que se definida como verdadeira (e appendToExist for falsa), a tarefa de ingestão marcará transacionalmente todos os segmentos existentes no intervalo como não utilizados, substituindo-os pelo novo conjunto de segmentos. Isso pode ser útil em casos de uso de compactação em que o ofuscamento normal não substitui completamente um conjunto de segmentos em um intervalo, como ao alterar a granularidade do segmento para um tamanho menor e alguns dos intervalos de granularidade menores não teriam dados, deixando os segmentos originais apenas parcialmente ofuscados. Observe que esta funcionalidade ainda é experimental e pode resultar em indisponibilidade temporária de dados dentro do interval compactado. Alterar esta configuração não faz com que os intervalos sejam compactados novamente. Da mesma forma, markAsUnused foi adicionado como uma opção à tarefa Druid kill, que marcará quaisquer segmentos no intervalo fornecido como 'não utilizados' antes de excluir todos os segmentos não utilizados. Isso é útil para permitir que a sequência de marcar como não utilizado -> excluir ocorra com uma única chamada API para o chamador, bem como permitir que a ação de desmarcar ocorra sob um bloqueio de intervalo de tarefa. https://github.com/apache/druid/pull/11070 https://github.com/apache/druid/pull/11025 https://github.com/apache/druid/pull/11501

<a name="22-coordinator" href="#22-coordinator">#</a> Coordenador

<a name="22-coord-timeout" href="#22-coord-timeout">#</a> Controle sobre o comportamento do tempo limite de carregamento do segmento coordenador com gerenciamento de segmento baseado em Apache Zookeeper

Uma nova opção de configuração dinâmica do coordenador Druid permite controlar o comportamento sempre que uma ação de carregamento de segmento expira ao usar o gerenciamento de segmento baseado em Zookeeper. replicateAfterLoadTimeout quando definido como verdadeiro, o coordenador tentará replicar o segmento que falhou ao carregar para um servidor histórico diferente. Isso ajuda a melhorar a disponibilidade do segmento se houver alguns servidores históricos lentos no cluster. No entanto, o histórico lento ainda poderá carregar o segmento mais tarde e o coordenador poderá precisar emitir solicitações de descarte se o segmento for replicado em excesso. https://github.com/apache/druid/pull/10213

<a name="22-coord-balance" href="#22-coord-balance">#</a> Balanceamento mais rápido do segmento do coordenador

Outra nova opção de configuração dinâmica do coordenador, useBatchedSegmentSampler, quando definida como verdadeira pode potencialmente fornecer um grande aumento de desempenho na velocidade com que o coordenador pode processar a fase de balanceamento do segmento. Isso deve ser particularmente notável em clusters muito grandes com muitos segmentos, mas é desabilitado por padrão para ser cauteloso. https://github.com/apache/druid/pull/11257

<a name="22-coord-replication" href="#22-coord-replication">#</a> Status de carga API aprimorado para calcular opcionalmente a sub-replicação com base no tamanho do cluster

O status de carregamento do coordenador Druida API agora suporta um novo parâmetro de consulta de URL opcional, computeUsingClusterView, que quando especificado fará com que o coordenador calcule a sub-replicação para segmentos com base no número de servidores disponíveis no cluster para os quais o segmento pode ser replicado, em vez da contagem de replicação configurada na regra de carregamento. Por exemplo, se as regras de carregamento especificarem 2 réplicas, mas houver apenas 1 servidor que pode conter segmentos, este API não reportará como sub-replicado porque os segmentos são tão replicados quanto possível para o tamanho de cluster determinado. https://github.com/apache/druid/pull/11056

<a name="22-coord-rep-limit" href="#22-coord-rep-limit">#</a> Limites opcionais para o número de replicantes não primários carregados por ciclo de coordenação

Uma nova configuração dinâmica do coordenador, maxNonPrimaryReplicantsToLoad, com valor padrão de Integer.MAX_VALUE, permite que os operadores definam um limite superior rígido para o número de replicantes não primários que serão carregados em um único ciclo de execução do coordenador. O valor padrão imitará o comportamento que existe hoje. Exemplo de uso: se você definir essa configuração como 1.000, o coordenador carregará no máximo 1.000 replicantes não primários em cada execução do ciclo de execução. Ou seja, se você ingerisse 2.000 segmentos com um fator de replicação de 2, o coordenador carregaria 2.000 replicantes primários e 1.000 replicantes não primários na primeira execução. Em seguida, na próxima execução, os últimos 1.000 replicantes não primários serão carregados. https://github.com/apache/druid/pull/11135

<a name="22-web-query" href="#22-web-query">#</a> Visualização de consulta

A documentação embutida agora também deve incluir informações do tipo Druida: e deve fornecer sugestões melhores sempre que ocorrer um erro de consulta: Finalmente, a visualização de consulta do console web agora suporta a combinação de teclas de atalho command + enter (no Mac) e ctrl + enter no Windows e Linux. https://github.com/apache/druid/pull/11158 https://github.com/apache/druid/pull/11128 https://github.com/apache/druid/pull/11203 https://github.com/apache/druid/pull/11365

<a name="22-clouds-assume-role" href="#22-clouds-assume-role">#</a> Suporte de ingestão S3 para assumir uma função

A ingestão de lote nativo do Druid de fontes de entrada S3 agora pode usar o recurso AssumeRole na AWS para acesso a arquivos entre contas. Isso pode ser utilizado configurando assumeRoleArn e assumeRoleExternalId na especificação da fonte de entrada S3 em uma tarefa de ingestão em lote. Consulte a documentação da documentação da AWS e do lote nativo para obter mais detalhes. https://github.com/apache/druid/pull/10995

<a name="22-clouds-gcs-lookup" href="#22-clouds-gcs-lookup">#</a> Suporte do Google Cloud Storage para pesquisas de URI

As pesquisas Druid agora suportam o carregamento via Google Cloud Storage, semelhante à funcionalidade existente disponível no S3. Isso requer que o druid-google-extensions seja carregado além das extensões de pesquisa, mas além disso é tão simples quanto usar um URI do Google Cloud Storage. https://github.com/apache/druid/pull/11026

<a name="22-odds-and-ends" href="#22-odds-and-ends">#</a> Outras alterações

<a name="22-avro-union-by-type" href="#22-avro-union-by-type">#</a> Extraindo campos de união Avro por tipo

A ingestão Avro usando lote Druid ou ingestão de streaming agora oferece suporte a um mecanismo alternativo de extração de dados para tipos Avro Union. Esta nova opção, extractUnionsByType, só funciona ao utilizar um flattenSpec para extrair dados aninhados de tipos de união e fará com que os dados extraídos estejam disponíveis com o tipo como parte do caminho nivelado. Por exemplo, dada uma coluna de união multitipada someMultiMemberUnion, com esta opção habilitada, um valor longo seria extraído por $.someMultiMemberUnion.long em vez de $.someMultiMemberUnion, e extrairia apenas valores longos da união. Consulte a documentação do Avro para obter informações completas. https://github.com/apache/druid/pull/10505

<a name="22-mysql-mariadb" href="#22-mysql-mariadb">#</a> Suporte usando conector MariaDb com extensões MySQL

As extensões Druid MySQL agora suportam o uso da biblioteca de conectores MariaDB como uma alternativa ao conector MySQL. Isso pode ser feito configurando druid.metadata.mysql.driver.driverClassName como org.mariadb.jdbc.Driver e inclui suporte completo para listas de permissões de parâmetros URI JDBC usadas por pesquisas JDBC e ingestão baseada em SQL. https://github.com/apache/druid/pull/11402

<a name="22-dynamic-config" href="#22-dynamic-config">#</a> Adicionar variável de ambiente DynamicConfigProvider

Druid agora fornece uma implementação DynamicConfigProvider que é apoiada por variáveis de ambiente. Por exemplo:

druid.some.config.dynamicConfigProvider={"type": "environment","variables":{"secret1": "SECRET1_VAR","secret2": "SECRET2_VAR"}}

Consulte a documentação do provedor de configuração dinâmica para obter mais informações. https://github.com/apache/druid/pull/11377

<a name="22-dynamic-config-schema-registry" href="#22-dynamic-config-schema-registry">#</a> Adicionar DynamicConfigProvider para registro de esquema

Os formatos de ingestão que suportam o Confluent Schema Registry agora suportam o fornecimento desses parâmetros por meio de um DynamicConfigProvider, que é a alternativa mais recente ao PasswordProvider. Isso permitirá que as tarefas de ingestão usem o provedor de configuração para fornecer essas informações, em vez de diretamente nas especificações JSON, permitindo formas mais seguras de fornecer credenciais e outras informações de configuração confidenciais. Consulte a documentação do formato de dados e do provedor de configuração dinâmica para obter mais detalhes. https://github.com/apache/druid/pull/11362

<a name="22-security" href="#22-security">#</a> Correções de segurança

<a name="22-security-protos" href="#22-security-protos">#</a> Controle de protocolos permitidos para fontes de entrada HTTP e HDFS

Druid 0.22.0 adiciona novos recursos para controlar o conjunto de protocolos permitidos usados por fontes de entrada HTTP e HDFS na ingestão em lote. druid.ingestion.hdfs.allowedProtocols é configurado por padrão para aceitar hdfs como protocolo, e druid.ingestion.http.allowedProtocols por padrão permitirá http e https. Isto pode causar problemas com implantações existentes, uma vez que é mais restritivo do que o comportamento padrão atual em versões mais antigas do Druid, mas no geral permite aos operadores mais flexibilidade na proteção dessas fontes de entrada. https://github.com/apache/druid/pull/10830

<a name="22-security-ldap" href="#22-security-ldap">#</a> Correção da lógica de expiração para cache de credenciais internas LDAP

Esta versão do Druid também corrige uma falha na extensão druid-basic-security ao usar LDAP, onde o cache de credenciais não expirava corretamente, potencialmente retendo informações de credenciais expiradas depois que deveriam ter expirado, até que outro gatilho fosse acionado ou o serviço fosse reiniciado. Clusters druidas que usam LDAP para autorização devem ser atualizados para 0.22.0 sempre que possível para corrigir esse problema. https://github.com/apache/druid/pull/11395

<a name="22-bug-fixes" href="#22-bug-fixes">#</a> Correções de bugs

Druida 0.22.0 contém mais de 80 correções de bugs, você pode ver a lista completa aqui.

<a name="22-upgrading-to-22" href="#22-upgrading-to-22">#</a> Atualizando para 0.22.0

Considere as seguintes alterações e atualizações ao atualizar do Druid 0.21.x para 0.22.0. Se você estiver atualizando de uma versão anterior ao 0.21.0, consulte os release notes das versões intermediárias relevantes.

<a name="22-up-dropped-zk-3.4" href="#22-up-dropped-zk-3.4">#</a> Suporte eliminado para Apache ZooKeeper 3.4

Seguindo 0.21, que oficialmente descontinuou o suporte para Zookeeper 3.4, que está em fim de vida há algum tempo, o suporte para ZooKeeper 3.4 agora foi removido em 0.22.0. Certifique-se de atualizar seu cluster Zookeeper antes de atualizar seu cluster Druid para 0.22.0. https://github.com/apache/druid/issues/10780 https://github.com/apache/druid/pull/11073

<a name="22-up-batch-lineage" href="#22-up-batch-lineage">#</a> Correção de alocação de segmento de ingestão de lote nativo

Druid 0.22.0 inclui uma importante correção de bug na indexação de lote nativa, onde falhas transitórias de subtarefas de indexação podem resultar em partições não contíguas nos segmentos de resultados, que nunca se tornarão consultáveis devido à lógica que verifica o conjunto 'completo'. Esse problema foi resolvido na versão mais recente do Druid, mas exigiu uma alteração no protocolo que as tarefas em lote usam para alocar segmentos, e essa alteração pode causar problemas durante downgrades contínuos se você decidir reverter do Druid 0.22.0 para uma versão anterior. Para evitar falha de tarefa durante um downgrade contínuo, defina

druid.indexer.task.default.context={ "useLineageBasedSegmentAllocation" : false }

nas propriedades de tempo de execução do overlord e aguarde a conclusão de todas as tarefas que têm useLineageBasedSegmentAllocation definido como true antes de iniciar o downgrade. Depois que todas essas tarefas forem concluídas, o downgrade não deverá ter mais problemas e a configuração poderá ser removida da configuração overlord (recomendado, pois você desejará que esta configuração seja habilitada se estiver executando o Druid 0.22.0 ou mais recente). https://github.com/apache/druid/pull/11189

<a name="22-up-sql-buckets" href="#22-up-sql-buckets">#</a> As séries temporais SQL não ignoram mais buckets vazios com toda a granularidade

Antes do Druida 0.22, um grupo SQL por consulta que usa uma única chave de agrupamento universal (por exemplo, apenas agregadores) como SELECT COUNT(*), SUM(x) FROM y WHERE z = 'someval' produziria um conjunto de resultados vazio em vez de [0, null] que poderia ser esperado desta consulta sem resultados correspondentes. Isso ocorreu porque abaixo disso seria planejado uma consulta de série temporal com granularidade 'ALL' e skipEmptyBuckets definido como verdadeiro no contexto da consulta. Esta última opção fez com que os resultados de tal consulta não retornassem resultados, pois não há intervalos com valores para agregar e, portanto, eles são ignorados, criando um conjunto de resultados vazio em vez de um conjunto de resultados 'nulo'. Este comportamento foi alterado para se comportar de acordo com outras implementações SQL, mas o comportamento anterior pode ser obtido configurando explicitamente skipEmptyBuckets no contexto da consulta. https://github.com/apache/druid/pull/11188

<a name="22-up-reingest" href="#22-up-reingest">#</a> Alterações incompatíveis com a reingestão do Druida

As tarefas em lote que usam uma fonte de entrada 'Druida' para reingerir dados de segmento não aceitarão mais as seções 'dimensões' e 'métricas' de suas especificações de tarefa e agora usarão internamente um novo filtro de colunas para especificar quais colunas do segmento original devem ser retidas. Além disso, timestampSpec não é mais ignorado, permitindo que a coluna __time seja modificada ou substituída por uma coluna diferente. Essas alterações também corrigem um bug em que as colunas transformadas seriam ignoradas e indisponíveis nos novos segmentos. https://github.com/apache/druid/pull/10267

<a name="22-up-ie11" href="#22-up-ie11">#</a> O console web Druid não suporta mais o IE11 e outros navegadores mais antigos

Algumas coisas ainda podem funcionar, mas não são mais suportadas oficialmente para que os recursos mais recentes do Javascript possam ser usados para desenvolver o console web. https://github.com/apache/druid/pull/11357

<a name="22-up-ie11" href="#22-up-ie11">#</a> Tamanho máximo da fila de carregamento de segmento padrão alterado

A configuração dinâmica do coordenador druida maxSegmentsInNodeLoadingQueue foi alterada de ilimitado (0) para 100. Isso deve fazer com que o coordenador se comporte de maneira muito mais relaxada durante períodos de volatilidade do cluster, como uma atualização contínua, mas limita o número total de segmentos que serão carregados em qualquer ciclo do coordenador a 100 por servidor, o que pode diminuir a velocidade na qual um cluster completamente parado é iniciado e carregado a partir do armazenamento profundo. https://github.com/apache/druid/pull/11540

<a name="22-dev-notes" href="#22-dev-notes">#</a> Avisos do desenvolvedor

<a name="22-dev-expr-cache-key" href="#22-dev-expr-cache-key">#</a> CacheKeyBuilder movido de druid-processing para druid-core

A classe CacheKeyBuilder, que é anotada com @PublicAPI, foi movida de druid-processing para druid-core para que as expressões possam estender a interface Cacheable para permitir que expressões gerem chaves de cache que dependem de algum estado externo, como versão de pesquisa. https://github.com/apache/druid/pull/11358

<a name="22-dev-query-processing-pool" href="#22-query-processing-pool">#</a> O mecanismo de consulta agora usa o novo QueryProcessingPool em vez do ExecutorService diretamente

Isso afeta algumas assinaturas de métodos no mecanismo de processamento de consultas, como QueryRunnerFactory e QuerySegmentWalker, para permitir que extensões se conectem a várias partes do pool de processamento de consultas e estratégias alternativas de agendamento do pool de processamento no futuro. https://github.com/apache/druid/pull/11382

<a name="22-dev-segment-loader" href="#22-dev-segment-loader">#</a> SegmentLoader agora é extensível e personalizável

Isso permite que as extensões forneçam implementações alternativas de carregamento de segmentos para personalizar como os segmentos Druid são carregados do armazenamento profundo e disponibilizados para o mecanismo de consulta. Este deve ser considerado um api instável e é anotado como tal no código. https://github.com/apache/druid/pull/11398

Para obter uma lista completa de problemas em aberto, consulte https://github.com/apache/druid/labels/Bug.
