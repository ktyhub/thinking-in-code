#fluxo de ar 3.3.0

📦 PyPI: https://pypi.org/project/apache-airflow/3.3.0/ 📚 Documentos: https://airflow.apache.org/docs/apache-airflow/3.3.0/ 🛠 Release Notes: https://airflow.apache.org/docs/apache-airflow/3.3.0/release_notes.html 🐳 Docker Imagem: "docker pull apache/airflow:3.3.0" 🚏 Restrições: https://github.com/apache/airflow/tree/constraints-3.3.0

Mudanças Significativas

Particionamento de ativos (#64571, #65447, #66030, #66848, #67184, #67475, #67716, #68978)

Com base no particionamento de ativos introduzido no 3.2.0, o Airflow 3.3.0 expande substancialmente a forma como um um único evento de ativo upstream se espalha para execuções Dag downstream particionadas. Novos mapeadores de partição — RollupMapper (many-to-one), FanOutMapper (one-to-many), and FixedKeyMapper + SegmentWindow (rollup categórico) — composto com janelas de tempo (dia/semana/mês/trimestre/ano) e um wait_policy (WaitForAll or MinimumCount(n)) para controlar quando o particionamento é executado. Janelas pode se espalhar para frente ou para trás no tempo, e a distribuição total por evento upstream é limitada pelo novo Configuração [scheduler] partition_mapper_max_downstream_keys (configurável por mapeador). Fluxo de ar 3.3.0 também adiciona o horário PartitionedAtRuntime, que permite que um Dag declare que sua(s) chave(s) de partição são atribuídos quando a execução é iniciada, em vez de mapeados a partir de um evento upstream.

Para instruções de uso detalhadas, consulte :doc:/authoring-and-scheduling/assets.

Armazenamento de estado de tarefas e ativos (#65759, #66073, #66160, #66463, #66586, #66859, #67041, #67292, #67319)

Airflow 3.3.0 apresenta um armazenamento de estado de primeira classe para tarefas e ativos (AIP-103). As tarefas podem persistir estado de valor-chave arbitrário que sobrevive entre tentativas e é executado por meio de um novo acessador task_state_store, e ativos podem carregar seu próprio estado via asset_state_store — ambos disponíveis na tarefa SDK. Estado é mantido no banco de dados de metadados por padrão ou em um back-end personalizado do lado do trabalhador ([trabalhadores] state_store_backend), suporta retenção por chave com coleta de lixo periódica e um opcional clear_on_success, e é totalmente gerenciável através do Core API e Execution API.

Para instruções de uso detalhadas, consulte :doc:/core-concepts/task-and-asset-state-store.

Políticas de nova tentativa conectáveis (#65474)

O comportamento de nova tentativa de tarefa agora é conectável (AIP-105). Além de uma contagem fixa retries, você pode anexe uma política de repetição personalizada que decida se e quando uma tarefa será repetida, permitindo estratégias como como tentar novamente apenas em exceções específicas ou recuar com base na lógica personalizada.

Para instruções de uso detalhadas, consulte :ref:concepts:retry-policies.

Tarefa de linguagem SDK (Java e Go) (#65958, #67161, #67635, #67699)

Airflow 3.3.0 adiciona uma camada de coordenador (AIP-108) que permite que implementações de tarefas individuais sejam escritas em idiomas não Python enquanto o Dag e seu agendamento permanecem em Python. Uma tarefa é declarada no Dag com @task.stub(queue=...); o trabalhador o encaminha para um coordenador configurado (JavaCoordinator for JVM languages, ExecutableCoordinator para binários nativos independentes como Go) que executa a tarefa em um tempo de execução de linguagem e faz proxy de variáveis, conexões e XComs de volta através da Execução API.

.. aviso::

A camada Coordenador e os Java/Go SDKs são experimentais no 3.3.0 e podem mudar no futuro versões com base no feedback do usuário.

Para instruções de uso detalhadas, consulte :doc:/authoring-and-scheduling/language-sdks/index.

Versão do pacote Dag em limpeza, reexecução e preenchimento (#63884)

A nova configuração rerun_with_latest_version controla se uma execução Dag limpa, reexecutada ou preenchida usa a versão mais recente do pacote ou a versão original da execução inicial. O padrão foi resolvido por precedência: um parâmetro de solicitação explícito/sinalizador CLI e, em seguida, o rerun_with_latest_version de nível Dag, então [core] rerun_with_latest_version, and finally False for clear/rerun and True para preenchimentos (preservando o comportamento histórico). O Airflow 2.x sempre é executado novamente com o código mais recente; 3.x introduziu o controle de versão do pacote padronizado para a versão original, e essa configuração dá controle aos usuários.

Veja :doc:/administration-and-deployment/dag-bundles para detalhes completos.

Exemplo de provedor Dags como pacotes dedicados (#66161)

Exemplo de Dags enviados por distribuições de provedores agora são descobertos via ProvidersManager e registrados como seus próprios pacotes Dag – um por provedor, denominado apache-airflow-providers-<distribution>-example-dags (or <distribution>-example-dags para fornecedores terceirizados). A opção [core] load_examples ainda determina se eles estão registrados. REST API clients que filtraram bundle_name by "dags-folder" para exemplos de Dags enviados pelo provedor deve atualizar para os novos nomes de pacotes por provedor; Os identificadores Dag permanecem inalterados.

Resolução de registro remoto desacoplada de airflow.logging_config (#67056)

A resolução do manipulador de log de tarefas remotas agora pertence ao airflow_shared.logging.factory compartilhado módulo e aplica uma precedência única e bem definida:

  1. um [logging] logging_config_class exporting REMOTE_TASK_LOG / definido pelo usuário DEFAULT_REMOTE_CONN_ID (as configurações personalizadas existentes continuam funcionando);
  2. ProvidersManager scheme dispatch — the scheme of [logging] remote_base_log_folder seleciona um método de classe do provedor RemoteLogIO class, instantiated via a no-argument from_config();
  3. um substituto herdado de transição com leitura airflow_local_settings.py (a ser removido no Airflow 4.0).

airflow.logging_config.load_logging_config is deprecated (it now emits DeprecationWarning e delegados para novos ajudantes privados), e configure_logging não resolve mais ansiosamente o problema remoto manipulador – a resolução é lenta no primeiro uso. Provedores que registraram um bloco remote-logging:, mas não não implementam from_config são ignorados com um aviso e caem no caminho legado.

Migração: substitua as chamadas diretas para airflow.logging_config.load_logging_config() pelo novo ajudantes e fazer com que as classes de manipulador de log remoto do provedor implementem um from_config sem argumento método de classe que diz airflow.providers.common.compat.sdk.conf.

As métricas do temporizador OpenTelemetry agora usam histograma (#64207)

O temporizador OpenTelemetry e as métricas de tempo agora são registradas como histogramas em vez de medidores, preservando contagem, soma e distribuição de intervalos entre gravações.

A métrica "segundos atrás" de processamento de Dag agora está marcada (#62487)

dag_processing.last_run.seconds_ago.{dag_file} agora é uma métrica legada. O novo dag_processing.last_run.seconds_ago is emitted with file_path, bundle_name e file_name tags (file_path + bundle_name identifica exclusivamente o arquivo Dag). A métrica legada ainda é emitido por padrão e pode ser desabilitado via [metrics] legacy_names_on.

Nova página de prazos em Navegar (#67586)

Uma nova página Prazos está disponível no menu Navegar, acessível a qualquer função que já tenha can_read and menu_access em Dag Runs.
