Mudanças Significativas

Loops de tarefas (#73005, #74222, #74275, #74345)

Airflow 3.4.0 introduz Task Loops (AIP-111): um grupo de tarefas decorado pode ser repetido uma série de tempos decididos em tempo de execução usando o loop .loop(). A conditional loop works like a do ... while - o corpo é executado pelo menos uma vez e uma condição until decide quando parar, limitada por max_iterations. Cada iteração pode usar o resultado da iteração anterior e as iterações executam uma após o outro (as tarefas dentro de uma iteração ainda podem ser executadas em paralelo). Tentativas repetidas são mantidas sob um UUID por tentativa para que os dados de cada iteração sejam preservados e possam ser limpos seletivamente.

Para instruções de uso detalhadas, consulte :doc:/authoring-and-scheduling/loops.

.. nota:: O downgrade para qualquer versão anterior a 3.4.0 pode ser lento, dependendo do número de Linhas XCom que foram gravadas após a atualização. A atualização foi testada em um Tabela XCom de 300 m de linha, então não se preocupe com o tempo de atualização (garantimos que os dados do XCom não foram tocados ou lidos durante a migração para mantê-los rápido).

Isso ocorre porque esta versão contém uma migração que começa a armazenar novos XCom linhas em uma tabela xcom_v2 e, para fazer o downgrade, temos que movê-las para a tabela antiga, e não há como fazer isso sem copiar o valores xcom escritos.

O downgrade se recusa a continuar quando encontra dados que não consegue mapear com segurança. Cada migração é confirmada separadamente, portanto, as migrações posteriores do 3.4.0 já foram revertidos nesse ponto: corrija os dados e execute novamente o faça downgrade ou execute airflow db migrate para retornar ao 3.4.

No MySQL, uma falha após essas verificações deixa o esquema parcialmente rebaixado, já que MySQL não pode reverter DDL. Fazendo um backup antes de tentar o é aconselhável fazer downgrade em MySQL, para que possa ser restaurado nesse caso.

Importador Dag para Dags não Python (#72369, #73728, #73853, #74020, #74084, #74333, #74586)

O Airflow 3.4.0 pode criar um Dag inteiro - cronograma, tarefas e dependências - em um idioma diferente do que Python. AIP-85 adiciona um importador Dag conectável na tarefa SDK que ensina o processador Dag a reconhecer formatos de origem além de .py: cada formato registra um importador, o processador executa o tempo de execução da linguagem correspondente e os Dags resultantes aparecem no Airflow como Python Dags. Os formatos que aparecem nele são as linguagens TypeScript, Go e Java SDKs e um formato nativo YAML Dag (um Marcador .yaml file with a $schema, validado em um esquema e incorporado em operadores reais, com modelos explícitos). A estrutura Dag Importer e a linguagem SDKs são experimentais em 3.4 e seus APIs podem mudar.

Para instruções de uso detalhadas, consulte :doc:/administration-and-deployment/dag-importers.

Unifique filas de carga de trabalho do executor em BaseExecutor.executor_queues (#63491)

O estado da carga de trabalho do executor agora é armazenado no mapeamento unificado BaseExecutor.executor_queues com chave por WorkloadType and scheduled through trigger_workloads. Os atributos anteriores por tipo e pontos de entrada (queued_tasks, queued_callbacks, supports_callbacks, trigger_tasks, order_queued_tasks_by_priority) e a superfície de teste de conexão Airflow 3.3 são dobradas em este mapeamento e mantidos como calços compatíveis com versões anteriores que emitem RemovedInAirflow4Warning (a ser removido no Airflow 4.0). Executores fora da árvore devem declarar supported_workload_types e implementar trigger_workloads. Os testes de conexão agora são admitidos sob o mesmo batimento cardíaco orçamento como tarefas e priorizado antes delas. Veja #63491 <https://github.com/apache/airflow/pull/63491>_ para obter o guia de migração completo.

psycopg3 agora é o driver padrão do Postgres (#68496)

psycopg3 (psycopg) agora é o driver padrão para o banco de dados de metadados, tanto para sincronização quanto para o mecanismo assíncrono, substituindo psycopg2 e asyncpg. Um postgresql:// simples (ou um legado postgres:// / postgres+psycopg2://) sql_alchemy_conn é reescrito para postgresql+psycopg://, and the derived async URL uses postgresql+psycopg_async:// quando psycopg3 está instalado (caso contrário, voltando para asyncpg). O fluxo de ar também desativa o psycopg3 preparação de instruções do lado do servidor (prepare_threshold = None) para que o banco de dados de metadados funcione da caixa por trás do modo de transação PgBouncer, a configuração de produção recomendada. Para manter psycopg2 ou asyncpg, instale o extra apache-airflow-providers-postgres[psycopg2] / [asyncpg] e configure a conexão explicitamente; consulte #68496 e #69469 para obter detalhes, incluindo como reativar preparação de declaração.

Dags acionados por ativos criam uma execução por evento por padrão (#68517)

Programações de ativo único e expressões OR de ativo agora criam uma execução Dag por evento em vez de consumindo todos os eventos enfileirados em uma única execução. Isto também se aplica a AssetOrTimeSchedule e PartitionedAssetTimetable.

Para reter o lote, defina batch_asset_events=True on the timetable or enable [agendador] batch_asset_events e analise novamente os Dags afetados. Horários já serializados sem isso opção reter seu comportamento de lote anterior até ser analisado novamente.

Programações que exigem vários eventos, incluindo schedule=[a, b], expressões de ativos AND e horários particionados usando RollupMapper, continuam em lote por padrão. Configuração explicitamente batch_asset_events=False para esses horários gera um erro de validação de horário.

As cores personalizadas do gráfico retornam via ui_color and ui_fgcolor (#68760)

Os atributos ui_color and ui_fgcolor em operadores e grupos de tarefas colorem a visualização do gráfico novamente - o preenchimento do nó de ui_color and the operator label from ui_fgcolor, como fizeram em Airflow 2. Eles foram ignorados silenciosamente desde o Airflow 3.0.

O valor pode ser uma cor bruta (um código hexadecimal como #e8b7e4 ou um nome CSS) ou um token de tema Chakra - um token de paleta como blue.500 or a semantic token such as brand.solid que se adapta a modo claro e escuro (incluindo tokens adicionados por meio de temas de interface de usuário personalizados); um token é resolvido através de um variável CSS controlada por tema. A borda do nó continua refletindo o estado de execução da instância da tarefa; o a cor personalizada é aplicada somente ao preenchimento e ao rótulo.

O airflow.utils.helpers.validate_key utility now raises ValueError em vez de AirflowException quando uma chave inválida é fornecida (por exemplo, um formato inválido ou um violação do limite de comprimento).

As linhas do log de auditoria não vinculadas a um Dag agora exigem a visualização AUDIT_LOGS_ALL (#70759)

Linhas no log de auditoria cujo dag_id is NULL registra operações que não estão vinculadas a um Dag, como alterações de conexão, variável e pool. Eles foram devolvidos a qualquer interlocutor que pudesse ler logs de eventos, porque não há chave por Dag para autorizá-los e ambos os caminhos de leitura caíram de volta a uma verificação de log de auditoria em nível de Dag.

Eles agora estão conectados a um AccessView.AUDIT_LOGS_ALL dedicado, da mesma forma AccessView.IMPORT_ERRORS_ALL bloqueia erros de importação para arquivos sem Dag registrado. Linhas vinculadas para um Dag mantenha sua verificação por Dag existente.

  • GET /eventLogs no longer returns rows with a NULL dag_id para chamadores sem o novo visualizar e os exclui de total_entries and pagination. GET /eventLogs/{event_log_id} retorna 403 for such a row. An id matching no row still returns 404.
  • Com o gerenciador de autenticação simples, a visualização é concedida apenas à função ADMIN. Com a autenticação FAB manager ele mapeia para uma nova função All Audit Logs resource, which ships in the Admin; personalizado as funções que precisam ler essas linhas devem receber All Audit Logs.can_read explicitamente.
  • Um gerenciador de autenticação que não consegue mapear um AccessView solicitado agora nega essa visualização e emite um UserWarning instead of raising KeyError. Isso afeta gerentes de autenticação mais antigos que o núcleo eles são executados, o que anteriormente falhou na solicitação com um erro de servidor.

Os nomes das equipes agora devem estar em letras minúsculas e não podem conter dois sublinhados consecutivos (#70886)

airflow teams create and airflow teams sync agora aceita apenas nomes correspondentes (?!.*__)[a-z0-9_-]{3,50} - letras minúsculas, dígitos, hifens e sublinhados simples. Superior cartas de caso e __ foram aceitas anteriormente.

Um nome de equipe está incorporado no namespace da variável de ambiente AIRFLOW_CONN__<TEAM>___<ID> que contém segredos com escopo de equipe e o back-end coloca o nome em letras maiúsculas quando cria essa variável. data_eng and Data_Eng, portanto, resolveu um único namespace entre eles e um nome contendo ___ não pôde ser diferenciado do separador.

airflow db migrate coloca em minúscula cada nome de equipe armazenado, movendo os pacotes Dag dessa equipe, Conexões, variáveis, pools e gatilhos com ele. Dois nomes armazenados que diferem apenas no caso seriam colapsar em uma linha e mesclar silenciosamente duas equipes, de modo que a migração se recuse a começar enquanto qualquer uma dessas par existe - renomeie todos, exceto um primeiro. Nomes que permanecem inválidos por outro motivo, como contendo saídas __, are migrated as they are; they keep working, but airflow teams sync diferente de zero até que sejam renomeados.

Mudanças na forma como eventos de ativos pendentes acionam execuções de Dag (#70972)

A exclusão de registros de eventos de ativos com airflow db clean agora também remove quaisquer eventos de ativos que sejam ainda pendente para um Dag downstream. Isso afeta principalmente Dags que aguardam uma condição de múltiplos ativos, onde um evento pendente pode ser eliminado antes que a condição seja atendida. Excluindo um evento de ativo agora consistentemente significa que não irá desencadear uma corrida; anteriormente, esse gatilho pendente ainda poderia disparar após o evento ter sido eliminado.

Da mesma forma, um evento de ativo que estava na fila de um Dag enquanto estava agendado naquele ativo ainda é usado para acionar a execução e aparece entre os eventos de acionamento da execução, mesmo que o ativo seja posterior removido da programação do Dag. Anteriormente, eles eram descartados silenciosamente.

Os retornos de chamada agora resgatam um token de uso único antes de serem executados (#71192)

Um trabalhador agora resgata um token de uso único de retorno de chamada com o servidor API (PATCH /execution/callbacks/{callback_id}/run) antes de importar e executar o retorno de chamada. Resgatando o token move o retorno de chamada da fila para a execução e o troca por um escopo de execução de curta duração ficha. Antes desta mudança, um retorno de chamada era executado sem que o trabalhador fizesse qualquer chamada autenticada, portanto, o o token cunhado para ele nunca foi verificado.

Como o token é de uso único, uma mensagem reenviada ou reproduzida que atinge um retorno de chamada que é já em execução ou concluído é recusado em vez de ser executado novamente. Um trabalhador em 3.4 precisa de um servidor API que atende esse endpoint; um trabalhador conversando com um servidor API mais antigo negocia a versão API e se comporta como se o ponto final não estivesse lá.

Limpar uma tarefa agora descarta suas entradas de armazenamento de estado de tarefa por padrão (#72100)

Limpar uma instância de tarefa agora descarta suas entradas task_state_store, então a próxima tentativa começa desde o início, em vez de retomar de um ponto de verificação ou reconectar-se a um trabalho externo registrada pela tentativa cancelada. As novas tentativas não são afetadas e mantêm o estado da tarefa como antes. Isto se aplica para limpar instâncias de tarefas individuais (o terminal/caixa de diálogo de limpeza e airflowctl tasks/dags claro); limpar uma execução inteira do Dag ainda mantém o estado da tarefa (rastreado em #72929 <https://github.com/apache/airflow/issues/72929>_). Para preservar o comportamento antigo, passe keep_task_state=True (ou marque "manter estado da tarefa" na caixa de diálogo de limpeza; um padrão por navegador é disponível em Configurações > Limpeza). Observe que uma limpeza de instância de tarefa agora também exclui Linhas task_state_store para essa instância de tarefa.

[core] execute_tasks_new_python_interpreter agora se aplica aos processos de tarefas do Airflow 3 (#72164)

No Airflow 3, a opção não teve efeito na execução da tarefa (apenas o trabalhador do Edge a leu). Quando definido para True, the task supervisor now exec\ é um novo intérprete logo após bifurcar a tarefa processo, que evita que o fork herde um bloqueio mantido por um thread supervisor (um bloqueio permanente aguarde a primeira chamada TLS da tarefa). As implantações que mantiveram a opção True do Airflow 2 obtêm este comportamento, e o custo inicial do intérprete por tarefa, na atualização sem ações adicionais; definir para False para manter o garfo vazio. O processo da tarefa lê o valor global, portanto, um Edge com escopo de equipe a configuração por si só não o ativa. Edge trabalhadores com a opção True já iniciam um novo intérprete para o supervisor e agora iniciará um segundo para a tarefa. O processador Dag, o retornos de chamada de gatilho e tarefa (que o supervisor de retorno de chamada executa a partir de um fechamento que não pode ser nomeado em homenagem a um filho executado) não são afetados e mantêm o garfo vazio.

Pause Dags graciosamente drenando execuções ativas (#72407, #73225, #73055, #73763)

O Airflow agora suporta um estado de agendamento draining para Dags. A drenagem impede o agendador de criar novas execuções de Dag agendadas ou acionadas por ativos, permitindo ao mesmo tempo o Dag já enfileirado e em execução corre para continuar. As execuções acionadas explicitamente permanecem permitidas.

Após o término das execuções pendentes do Dag, o Dag faz a transição automaticamente para paused. Os usuários podem cancele a drenagem para retornar o Dag para active.

Execuções manuais, preenchimentos e materializações de ativos em um Dag pausado podem drenar o Dag em vez de retomando-o: escolha Drain na UI ou defina drain_dag na solicitação REST API. Drenagem permite que execuções inacabadas do Dag sejam iniciadas ou retomadas, exceto aquelas retidas por preenchimentos pausados, não cria execuções programadas e pausa o Dag novamente quando todas as execuções inacabadas terminam. Os preenchimentos pausados permanecem pausados e devem ser retomados para que suas execuções terminem e a drenagem seja concluída.

A UI, REST API e agendamento airflowctl expose the active, draining, and paused estados, e a lista de Dags pode pausar, drenar ou retomar vários Dags selecionados de uma vez. Existente is_paused API usage remains supported; use scheduling_state quando o estado de drenagem deve ser selecionados ou relatados explicitamente.

Reanalisar um arquivo sem Dag registrado agora requer a visualização REPARSE_ALL (#72896)

Um arquivo que não foi importado antes de definir qualquer Dag não possui chave por Dag para autorizar uma nova análise contra, então PUT /parseDagFile/{file_token} previously returned 404 para isso. Reanalisando tal arquivo agora está bloqueado em um AccessView.REPARSE_ALL dedicado - uma ação de gravação própria, distinta da permissão para visualizar erros de importação - e o modal de erros de importação Dag ganha uma ação de nova análise para esses arquivos.

  • PUT /parseDagFile/{file_token} para um arquivo sem Dag registrado autoriza contra REPARSE_ALL and returns 403 when the caller lacks it, instead of 404. Um arquivo que tem um Dag registrado mantém sua verificação can_edit por Dag existente.
  • Com o gerenciador de autenticação simples, a visualização é concedida apenas à função ADMIN. Com a autenticação FAB manager ele mapeia para uma nova função All Reparses resource, which ships in the Admin; personalizado as funções que precisam analisar novamente esses arquivos devem receber All Reparses.can_read explicitamente.

Removido o comando --file-io option from the airflow info (#73054)

--file-io carregou o relatório em file.io e imprimiu um link compartilhável. arquivo.io não é mais aceita uploads anônimos, portanto a opção não funcionou; também terminou em um rastreamento não tratado em vez de relatar a falha.

Redirecione a saída::

informações de fluxo de ar --anonymize > airflow-info.txt

Observe que --file-io applied --anonymize implicitly. Pass --anonymize explicitamente quando compartilhando um relatório: airflow info simples imprime strings de conexão, incluindo senhas, em texto não criptografado.

As pulsações da tarefa não são mais repetidas por [workers] execution_api_retries (#73244)

Os batimentos cardíacos tinham dois mecanismos de repetição sobrepostos: a tarefa SDK API client repetia todas as solicitações, incluindo batimentos cardíacos, e o supervisor contava separadamente falhas consecutivas de batimentos cardíacos em relação a [workers] max_failed_heartbeats. As novas tentativas do client também tiveram o efeito colateral indesejado de bloqueando o loop de monitor do supervisor enquanto ele recuava, portanto, durante uma interrupção do servidor API, o o supervisor atrasaria o encaminhamento dos logs da tarefa e/ou perceberia que o subprocesso da tarefa havia saiu.

As novas tentativas de pulsação agora são governadas exclusivamente por max_failed_heartbeats, cujo padrão foi ajustado de 3 to 30 para manter aproximadamente a mesma tolerância para um servidor API inacessível que os dois mecanismos combinados deram antes.

Se você definiu [workers] max_failed_heartbeats explicitamente, você pode querer reconsiderar o valor que você escolheram. Agora é todo o orçamento de nova tentativa: com o padrão [trabalhadores] min_heartbeat_interval of 5 seconds, the worker tolerates roughly 5 * max_failed_heartbeats segundos de indisponibilidade do API antes de encerrar uma tarefa em execução. Você provavelmente deveria manter o valor resultante abaixo de qualquer [scheduler] task_instance_heartbeat_timeout configurado (padrão 300 segundos).

Callbacks de alerta de prazo validados no momento da análise; intervalos numéricos obsoletos (#73294)

DeadlineAlert now refuses a callback that is not exactly AsyncCallback ou SyncCallback, então uma subclasse falha quando o Dag é analisado, e não quando o agendador lê de volta. O agendador decodifica retornos de chamada armazenados pelo nome exato da classe, de forma que nenhuma classe seja nomeada por um Dag autor é importado ou instanciado lá, o que significa que uma subclasse pode ser escrita e nunca mais leia.

Passando um número como interval is deprecated and now emits RemovedInAirflow4Warning. Isso ainda é aceito e contado em segundos, mas os tipos suportados são timedelta e VariableInterval. A timedelta subclass such as pendulum.duration(...) é aceito e normalizado para um timedelta simples, onde anteriormente passou na validação e depois falhou durante serialização. Subclasse interval=True is refused, because bool is an int e seria caso contrário, será considerado um segundo.

O endpoint POST /assets/{asset_id}/materialize agora requer um corpo de solicitação JSON (#73328)

Anteriormente era aceita uma solicitação sem corpo e o ativo era materializado com valores padrão. O endpoint agora requer um corpo JSON explícito, consistente com os outros endpoints mutantes: um solicitação sem corpo é rejeitada com 422 e um formulário HTML vazio não é uma entrada válida mais. Todos os campos do corpo permanecem opcionais, portanto, um objeto vazio ({}) é um corpo válido.

Os números de tentativas do TaskInstance agora aumentam antes do início da próxima tentativa (#73554)

.. nota::

Se você tiver algum sistema externo que procure nos logs de tarefas ou no estado do TI um TI pronto para nova tentativa, você precisará estar ciente dessa mudança e atualizar seu código.

Por exemplo, se você fez uma solicitação para GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id} esperando obter informações sobre a tentativa falhou, agora você precisará olhar para GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id}/tries/{try_number - 1}

Quando uma tarefa é up_for_retry, try_number agora identifica a próxima tentativa. Para recuperar a tentativa que falhou, solicite /tries/{try_number - 1}. A IU mostra a tentativa pendente e fornece um link para os logs da tentativa anterior.

O Airflow agora aloca o UUID de uma instância de tarefa e tenta números juntos de forma imutável para que eles sejam consistentes identifique a mesma tentativa.

Anteriormente, quando uma tarefa entrava no período de espera para novas tentativas, ela recebia um novo UUID, mas continuava tente o número N e tenha o estado de UP_FOR_RETRY até que esse período termine (ponto em que tente seria marcado como FAILED e o número de tentativa aumentado). Em vez disso, a tentativa falhada é imediatamente marcado com estado FAILED e uma nova tentativa criada no estado UP_FOR_RETRY.

Descontinuar dependências do TaskGroup cyclic (#73746)

Um Dag cujos TaskGroups dependem uns dos outros em um ciclo, quando cada TaskGroup é tratado como um único unidade, agora emite um TaskGroupCycleDeprecationWarning no tempo de análise e mostra um aviso Dag em a UI que nomeia os grupos de tarefas e as tarefas envolvidas. Esses Dags ainda analisam e executam, porque seus as dependências de tarefas são acyclic, mas o Airflow 3.5 está planejado para rejeitá-las no momento da análise.

Uma dependência dentro ou fora de qualquer tarefa em um TaskGroup conta como uma dependência de todo o grupo, portanto, um o caminho que sai de um TaskGroup e volta a ele é um ciclo. Por exemplo, a >> bridge >> b, com a and b in the same TaskGroup and bridge fora dele, faz com que o grupo dependa de bridge and bridge depend on the group, even if a >> b também está definido.

  • Mova tarefas entre TaskGroups, ou fora deles, para que cada grupo dependa dos outros em um somente direção. No exemplo acima, mova bridge into the group, or move b para fora dele.
  • Para capturar esses Dags no CI, execute seus testes de Dag com -W erro::airflow.sdk.exceptions.TaskGroupCycleDeprecationWarning. A verificação é executada quando um Dag é adicionado a um DagBag, so only tests that load your Dags into a DagBag e afirma que há nenhum erro de importação os detecta; um teste que importa apenas um arquivo Dag não.

Consulte "Dependências do TaskGroup Cyclic" na documentação do Dags.

Coordenadores de linguagem SDK carregam manipuladores de tarefas de um pacote Dag (#73970)

Os kwargs do coordenador experimental jars_root (Java) and executables_root (Go) foram removidos. CI e imagens de produção agora são baseadas em Docker Hardened Images e Debian 13 (#73038)

As imagens de produção e CI do Airflow agora são baseadas em Docker Hardened Images <https://dhi.io>_ para Python e Debian 13 "trixie".

Python não é mais compilado a partir do código-fonte durante a construção da imagem - ele vem da base reforçada imagem em vez disso, que remove o download da fonte, sua verificação de assinatura e a compilação da construção. Python ainda vive em /usr/python, que agora é um link simbólico para o Localização /opt/python que a imagem base usa, portanto, os caminhos dentro da imagem permanecem inalterados.

O argumento de construção BASE_IMAGE agora tem como padrão ghcr.io/apache/airflow/base/python:<version>-debian13-dev, espelho público do Airflow do imagem upstream dhi.io/python, portanto, a construção de uma imagem não precisa de credenciais de registro. Qualquer um substituir a imagem BASE_IMAGE with a plain debian:bookworm-slim deve mudar para uma imagem que já fornece Python, ou construa o sabor legacy.

O sistema operacional base mudou do Debian 12 "bookworm" para o Debian 13 "trixie". Pacotes de biblioteca renomeados em time_t transition (for example libssl3 is now libssl3t64 de 64 bits da trixie) deve ser atualizado em RUNTIME_APT_DEPS / ``ADDITIONAL_RUNTIME_APT_DEPS personalizado e compatível com MySQL client agora vem do MariaDB 11.8.

Para a linha 3.4.x, imagens de produção construídas da forma anterior - Python compiladas de fontes em Sabor debian:bookworm-slim - are still published as the deprecated legacy, selecionado com o novo argumento de construção AIRFLOW_IMAGE_FLAVOR="legacy". Eles serão removidos no Airflow 3.5.0.

O PYTHON_LTO build argument is gone. To build a FIPS-compliant image, point BASE_IMAGE em um Em vez disso, variante FIPS da imagem reforçada, por exemplo dhi.io/python:3.13.16-debian13-fips-dev.

Tarefa SDK API client trusts o armazenamento de certificados do sistema em vez de certifi (#73116)

Com [api] client_use_public_certs habilitado (o padrão), a tarefa SDK client que se comunica com o A execução API agora trusts armazena certificados do sistema operacional por meio de truststore em vez de o certifi CA bundle. CAs from [api] ssl_ca_file and [api] ssl_cert ainda está trusted além do armazenamento do sistema, e certifi não é mais uma dependência da tarefa SDK.

Os trabalhadores devem ter as CAs públicas das quais dependem instaladas no armazenamento do sistema (por exemplo, o Pacote ca-certificates em imagens baseadas em Debian). No macOS e no Windows, validação de certificado é delegado ao sistema operacional, que pode rejeitar certificados de servidor aceitos pelo OpenSSL, como certificados de CA privada sem o uso de chave estendida serverAuth.

Trabalhadores mais antigos não podem mais retomar tarefas adiadas cujo next_kwargs contém classes personalizadas (#73577)

Quando uma tarefa adiada é retomada em um trabalhador com uma tarefa SDK mais antiga, o servidor API não reconstrói mais classes arbitrárias do next_kwargs to convert them to the legacy format. Built-in value types, assets and asset aliases (including asset access control) are still converted, without constructing them. A deferred task whose next_kwargs armazenado, mantendo qualquer outra classe agora falha em tal trabalhador com um erro ao nomear o tipo e solicitando a atualização da tarefa SDK, em vez de travar em uma carga útil que ela não pode decodificar.

O que fazer: se você administra trabalhadores com apache-airflow-task-sdk 1.1.x or older and your deferrable operators or triggers pass instances of custom classes in next_kwargs (for example via self.defer(..., kwargs=...) or in the trigger event payload), upgrade the Task SDK on those workers to 1.2.0 or later. Newer workers receive next_kwargs unchanged and are not affected. Until all workers are upgraded, pass only built-in values, assets and asset aliases in next_kwargs de tarefas que podem ser retomadas em trabalhadores mais velhos.

Os kwargs de retorno de chamada do Deadline Alert são decodificados onde o retorno de chamada é executado (#74830)

Os argumentos de palavra-chave dos retornos de chamada do Deadline Alert não são mais decodificados pelo agendador. Eles são mantidos em sua forma serializada e decodificados onde o retorno de chamada é executado: pelo gatilho para um AsyncCallback, and by the callback runner on the worker for a SyncCallback.

Os trabalhadores que executam alertas de prazo SyncCallback precisam de uma tarefa SDK que inclua esta alteração, portanto atualize apache-airflow and apache-airflow-task-sdk em trabalhadores juntos. Um trabalhador com um apache-airflow atualizado e uma tarefa mais antiga SDK falham em tais retornos de chamada com um erro de executá-los. Os retornos de chamada criados antes da atualização são executados como antes.

Backends XCom personalizados que substituem serialize_value must implement store_value para suportar loops de tarefas (#74858)

Cada iteração de uma tarefa dentro de um loop é sua própria instância de tarefa, mas serialize_value recebe o mesmo dag_id, run_id, task_id, map_index and key para todos eles, então um back-end que constrói seu local de armazenamento a partir deles torna o XCom de cada iteração leia novamente como o valor da última iteração. Os backends devem substituir store_value e load_value instead, and build the storage location with XComCoordinate.build_path, que é exclusivo por instância de tarefa ou por gravação quando a gravação não pode conhecer a instância de tarefa.

Um Dag que usa um loop falha na inicialização quando o backend XCom configurado ainda armazena valores através de serialize_value, mesmo que já grave em um local exclusivo. Isso inclui XComObjectStorageBackend from apache-airflow-providers-common-io 1.10.1 e anteriores; atualize o provedor antes de usar loops de tarefas com ele.

Os back-ends do Custom Task State Store também precisarão incluir scope.region_id em sua chave de armazenamento para suportar tarefas mapeadas dentro de um loop e iterações de loop regeneradas por limpeza.

airflow.utils.email foi descontinuado em favor do provedor SMTP (#75414)

As funções em airflow.utils.email (send_email, send_email_smtp, send_mime_email, build_mime_message and get_email_address_list) agora reside em airflow.providers.smtp.utils.emailer. The old names still work and raise a DeprecatedImportWarning. O fluxo de ar agora requer apache-airflow-providers-smtp>=3.2.0.

Mantenha [email] email_backend set to airflow.utils.email.send_email_smtp. O Airflow trata esse valor como "enviar e-mails de tarefas com SmtpNotifier", que lê todas as configurações de SMTP da Conexão. Mudando para o caminho do provedor envia através das configurações [smtp].

Se você chamar essas funções diretamente:

  • A conexão SMTP é pesquisada com BaseHook.get_connection. Um script executado fora do Airflow processos precisam da conexão em uma variável de ambiente ou backend de segredos, não apenas nos metadados banco de dados.
  • As configurações são lidas através da configuração da Task SDK, portanto os valores são alterados em tempo de execução com airflow.configuration.conf.set() are not seen. airflow.cfg e variáveis de ambiente funcionam como antes.
  • Testes que patch airflow.utils.email.send_mime_email não interceptam mais a chamada feita por send_email_smtp. Patch airflow.providers.smtp.utils.emailer.send_mime_email em vez disso.

  • O servidor API usa um segundo pool de conexão de banco de dados

    Os trabalhadores do servidor API agora executam algum trabalho de banco de dados no mecanismo assíncrono, bem como no mecanismo de sincronização, e cada mecanismo tem seu próprio pool de conexões, dimensionado pelo mesmo [database] sql_alchemy_pool_size and [database] sql_alchemy_max_overflow settings. What uses the async pool depends on the --apps option of airflow api-server:

    • execution: pulsações da tarefa e diversas leituras da Execução API.
    • core: a entrada do log de auditoria registrada para cada solicitação de gravação por meio do REST API ou da UI.
    • all (o padrão): ambos acima.

    Em todos os modos, um trabalhador pode, portanto, abrir até duas vezes sql_alchemy_pool_size + sql_alchemy_max_overflow connections (30 with the defaults) and keep up to twice sql_alchemy_pool_size of them idle. Account for this, per [api] workers, when sizing PgBouncer or the database's max_connections. O pool assíncrono é usado desde #67800, #73403, #73407 e #76416. (#76430)
