kubernetes-client v7.8.0

Erros

  • Correção nº 7953: (httpclient-jdk) solicitações sem corpo agora preservam o método HTTP solicitado em vez de padronizar silenciosamente para GET. JdkHttpClientImpl.requestBuilder chama apenas HttpRequest.Builder.method(...) dentro da ramificação body != null, portanto, um DELETE/POST/PUT/PATCH sem corpo (como client.raw(uri, "DELETE", null)) foi enviado como GET no backend JDK; o método agora é definido com BodyPublishers.noBody() quando não há corpo, correspondendo aos backends OkHttp, Jetty e Vert.x
  • Correção nº 7435: (kubernetes-client) A ressincronização periódica de um SharedIndexInformer não para mais de forma permanente e silenciosa quando um único ciclo de ressincronização é iniciado. DefaultSharedIndexInformer.scheduleResync executa a ressincronização através de Utils.scheduleAtFixedRate, cuja cadeia de auto-reprogramação rearma o próximo ciclo somente quando o anterior for concluído normalmente; uma exceção não detectada completou o resyncFuture (não observado) excepcionalmente e a ressincronização nunca mais foi agendada, sem nenhum registro, enquanto o relógio independente manteve isWatching() reportando true (foi necessário reiniciar para recuperar). O comando de ressincronização agora captura e WARN registra a falha para que o agendamento seja acionado novamente no próximo intervalo
  • Correção nº 7933: (kubernetes-client-api) Falhas determinísticas de TLS trust (certificado não rusted, certificado expirado, incompatibilidade de nome de host) agora são classificadas como terminal e falham rapidamente em vez de serem repetidas pelo loop de espera StandardHttpClient.shouldRetry compartilhado (dreno de aproximadamente 19 s). O classificador percorre as árvores getCause() e getSuppressed() para CertificateException, CertPathValidatorException, CertPathBuilderException e SSLPeerUnverifiedException. Afeta todos os cinco módulos HTTP client (jdk, jetty, okhttp, vertx-4, vertx-5) na solicitação HTTP e nos caminhos de conexão WebSocket
  • Correção nº 7867: (kubernetes-server-mock) WatchEventsListener agora armazena em buffer eventos de observação de saída que são agendados antes do Vert.x disparar onOpen e os reproduz assim que o WebSocket estiver disponível, fechando a corrida aberta onde uma operação CRUD chega entre handleWatch registrando o ouvinte e onOpen preenchendo webSocketRef agendou um envio que desreferenciava um nulo webSocketRef; o NullPointerException resultante foi engolido silenciosamente pelo executor e o evento foi abandonado. Os eventos em buffer são reproduzidos após a sincronização inicial dos ADDEDs para que a ordem seja preservada
  • Correção nº 7896: (kubernetes-client) AbstractWatchManager.watchEnded() agora emite um WatcherException quando um relógio fecha corretamente, sem mensagens em 2 segundos, compensando um comportamento específico do GKE em v1/events, onde o proxy GKFE rejeita um resourceVersion obsoleto com um fechamento de WebSocket simples (código 1000, sem corpo) em vez de {"type":"ERROR","code":410}, causando um loop de reconexão indefinido com o mesmo recurso obsoletoVersion
  • Correção nº 7907: (httpclient-vertx-5) operações WebSocket sobre TLS (relógios apoiados por exec/attach/portForward/WebSocket e esperas de estabelecimento CRD que dependem deles) agora trust o certificado de cluster novamente. Vert.x 5.1 reescreveu o WebSocket client para resolver TLS por meio de um ClientSSLOptions por conexão que ignorou o SslContextFactory personalizado que o client usou como seu único transportador de material trust, então os handshakes do WebSocket silenciosamente voltaram para o armazenamento JVM trust padrão, falharam na validação do PKIX e foram suspensos no Tempo limite do lado client (solicitação/resposta HTTPS normal não foi afetada). Tanto o HTTP quanto o WebSocket clients agora são configurados uniformemente com Vert.x TrustOptions/KeyCertOptions derivado dos gerenciadores de chaves/trust fornecidos
  • Correção # 7873: (teste kube-api) Utils.findFreePort agora registra todas as portas distribuídas durante a vida útil do JVM e ignora qualquer porta já retornada, eliminando a janela de porta duplicada consecutiva que apareceu como um flake JUnitExtensionOnMethodTest.simpleTest2 - a sonda ServerSocket foi fechada antes do chamador vinculá-la, para que EtcdProcess.startEtcd() e KubeAPIServerProcess.startApiServer() pudessem extrair a mesma porta de Random.nextInt, etcd venceriam o vínculo e apiserver sairia 1 com bind: address already in use, surgindo em ProcessReadinessChecker como Connection reset by peer
  • Correção nº 7857: (kubernetes-server-mock) WatchEventsListener.onClosing agora enfileira o WebSocket.close(...) do lado do servidor no executor de envio do ouvinte em vez de invocá-lo diretamente no loop de eventos Vert.x. Isso preserva a ordem FIFO com quaisquer quadros de dados já enfileirados naquele executor, de modo que os eventos programados antes de um fechamento de observação iniciado por client (por exemplo, um par ADDED/DELETED em um create/delete final antes de watch.close()) são entregues antes do quadro de fechamento em vez de serem descartados silenciosamente por gravações em um soquete já fechado
  • Correção nº 7832: (sonar) Interromper novamente o thread em 8 blocos de captura de código de produção que engoliram InterruptedException sem preservar o status de interrupção (S2142)
  • Correção # 7841: (mockwebserver) divide o desligamento do Dispatcher em duas fases para que o MockDispatcher apenas destrua os executores WebSocketSession por sessão depois que o servidor HTTP for drenado, removendo a janela onde o onOpen de uma atualização em voo poderia pousar em um executor desligado. shutdown() ainda roda antes de httpServer.close() para desbloquear despachos bloqueados (por exemplo, QueueDispatcher.take()); o novo releaseResources() corre atrás. WebSocketSession.send() também captura RejectedExecutionException defensivamente para que qualquer corrida de desligamento residual permaneça silenciosa em vez de borbulhar como um Vert.x Unhandled exception. KubernetesMixedDispatcher agora delega ambos os ganchos de ciclo de vida para seu MockDispatcher interno, corrigindo um vazamento pré-existente onde os executores de sessão WebSocket no modo CRUD nunca eram desligados
  • Correção nº 7779: (kubernetes-client) ExecWebSocketListener agora notifica o ExecListener fornecido pelo usuário sobre erros de nível de transporte que correm com a conclusão do status de saída terminateOnError / canal 3 - listener.onFailure (ou onClose) é acionado exatamente uma vez, bloqueado por um sinalizador dedicado, em vez de ser engolido silenciosamente quando o onError adiado tarefa observa exitCode.isDone()
  • Correção nº 7765: (kubernetes-client) BaseOperation.informOnCondition agora interrompe o informante em linha quando o predicado interno completa o futuro, fechando uma corrida CompletableFuture postComplete onde um garçom ajudando a drenar dependentes poderia disparar informer.stop após cf.complete já ter acionado uma solicitação HTTP falsa de ?watch=true
  • Correção nº 7847: (kubernetes-client) BaseClient.addToCloseable agora sincroniza no conjunto fechado interno em vez do parâmetro fornecido pelo chamador, para que os chamadores não possam quebrar a exclusão mútua passando referências diferentes (sonar S2445)
  • Correção nº 7847: (kubernetes-client-api) KUBERNETES_SUBDOMAIN_REGEX usa quantificadores possessivos nos grupos externos para bloquear retrocesso no estilo ReDoS na entrada de subdomínio adversário; a semântica ainda corresponde ao padrão canônico de subdomínio RFC 1123 (sonar S5998)
  • Correção nº 7847: (kubernetes-client-api) Serialization.yamlMapper constrói o mapeador em um local antes de atribuir ao campo volatile, para que leitores simultâneos não possam mais observar uma instância parcialmente inicializada com módulos ainda não registrados (sonar S3064)
  • Correção nº 7847: (mockwebserver) a limpeza do arquivo temporário de certificado/chave autoassinado passa por Files.deleteIfExists com registro em vez de engolir o valor de retorno File.delete() (sonar S899)
  • Correção #7847: (httpclient-okhttp) OkHttpClientBuilderImpl agora escolhe o primeiro X509TrustManager de um TrustManager[] de múltiplas entradas em vez de passar null para sslSocketFactory e NPE'ing de OkHttp; O sslContext fornecido pelo usuário é preservado para configurações multi-CA (sonar S2637)
  • Correção nº 7847: (httpclient-okhttp) OkHttpClientImpl.doClose remove verificações de nulos mortos em dispatcher e connectionPool que são garantidos como não nulos pelo OkHttp API (sonar S2583)

Melhorias

  • Correção nº 7675: (mockwebserver) campo MockWebServer.dispatcher marcado como volatile para que uma chamada setDispatcher(...) seja visível de forma confiável para o thread do manipulador de solicitação Vert.x sem sincronização adicional. MockWebServer.reset() Javadoc foi reforçado para tornar explícito seu contrato não destrutivo (nenhuma alteração no servidor em execução, despachante, ouvintes, estado SSL/TLS, porta ou protocolos)
  • Correção nº 7809: (kubernetes-client) Suporte para seletores de fragmentos para lista e observação - incluindo informantes
  • Correção nº 7837: (kubernetes-client) Acompanhamentos no seletor de fragmentos
  • Correção #7899: (kubernetes-client) Retorno de chamada antes de re-listar para Informantes

Atualização de Dependência

  • Correção #7849: bump istio.io/client-go de 1.29.2 para 1.30.0
  • Correção nº 7894: aumente k8s.io/autoscaler/vertical-pod-autoscaler de 1.6.0 para 1.7.0
  • Correção nº 7894: aumente k8s.io/gengo/v2 de 2.0.0-20251215205346-5ee0d033ba5b para 2.0.0-20260408192533-25e2208e0dc3
  • Correção nº 7894: aumente k8s.io/kube-openapi de 0.0.0-20260319004828-5883c5ee87b9 para 0.0.0-20260414162039-ec9c827d403f
  • Correção nº 7875: aumento de vertx5.version de 5.0.12 para 5.1.1, adaptando alterações de comportamento de httpclient-vertx-5 para Vert.x 5.1 (as opções de mecanismo SSL não aceitam mais uma matriz de protocolo vazia; erros de fluxo de corpo de solicitação são redefinidos com HTTP/2 CANCEL para que não sejam tentados novamente como IOExceptions transitórias)

Novos recursos

  • Correção nº 7926: (httpclient-vertx-5, httpclient-vertx) ativação do aquecimento TLS na fábrica Vert.x HTTP client. Vertx5HttpClientFactory/VertxHttpClientFactory agora expõe setTlsWarmup(TlsWarmup) com os modos OFF, CONTEXT (padrão, inalterado) e FULL. FULL executa um handshake TLS de loopback descartável síncrono, uma vez por JVM, fora do loop de eventos quando o client é construído, de modo que a primeira conexão real não bloqueia mais o loop de eventos no carregamento de classe JDK/Netty TLS único - para usuários em JVMs com CPU fria ou com aceleração rígida atingindo o bloco/tempo limite da primeira conexão descrito em #7921. O comportamento padrão permanece inalterado; consulte as perguntas frequentes sobre CDS e orientação de dimensionamento de CPU de pod para pods com aceleração rígida
  • Correção nº 5084: scripts Jbang para gerar metadados graalVM
  • Correção nº 7375: (gerador crd) Suporte @JsonClassDescription para adicionar descrições a classes no esquema CRD gerado.
