caddy v2.10.0

Esta página é traduzida automaticamente. O texto original em inglês é a referência.

#caddie v2.10.0 Caddy 2.10 está aqui! Além de correções de bugs, esta versão apresenta:

  • ClientHello criptografado (ECH): Esta nova tecnologia criptografa a última parte de texto simples de uma conexão TLS: o ClientHello, que inclui o nome de domínio ao qual está conectado. O rascunho das especificações para ECH está quase finalizado, então agora podemos oferecer suporte a esse recurso de privacidade para TLS. Esta é uma capacidade poderosa, mas cheia de nuances; é altamente recomendável ler a documentação ECH em nosso site.
  • Troca de chaves pós-quântica (PQC): Caddy agora suporta o grupo criptográfico x25519mlkem768 padronizado por padrão.
  • Perfis ACME: Os perfis ACME são um rascunho experimental que permite escolher propriedades de seus certificados com mais flexibilidade do que os métodos tradicionais de CSR. Por exemplo, Let's Encrypt emitirá certificados de 6 dias sob um determinado perfil. Caddy poderá eventualmente usar esse perfil por padrão.
  • Cabeçalho Via: O proxy reverso agora define um cabeçalho Via em vez de um cabeçalho Servidor duplicado.
  • Provedor de DNS global: Agora você pode especificar um módulo DNS "global" padrão para usar em vez de configurá-lo localmente em todas as partes da sua configuração que exigem um provedor de DNS (por exemplo, desafios de DNS ACME e ECH). Esta é a opção global dns no Caddyfile, ou na configuração JSON, é o parâmetro dns na configuração do app tls.
  • Cartões curinga usados ​​por padrão: Anteriormente, Caddy obtinha certificados individuais para cada domínio em sua configuração literalmente; agora, os curingas, se presentes, serão utilizados para subdomínios, em vez de obter certificados individuais. Esta mudança foi motivada pela nova possibilidade de privacidade de subdomínios proporcionada pela ECH. Pode ser substituído por tls force_automate no Caddyfile. A opção experimental auto_https prefer_wildcard foi removida.
  • libdns 1.0 APIs: Muitos de vocês usam módulos de provedor de DNS para resolver desafios de DNS ACME ou para ativar DNS dinâmico. Eles implementam interfaces definidas por libdns para obter, definir, anexar e excluir registros DNS. Após 5 anos de experiência em produção, incluindo lições aprendidas com ECH, os libdns APIs foram atualizados e o 1.0 beta foi marcado. Os pacotes de provedores de DNS precisarão atualizar seu código para serem compatíveis, o que ajudará a garantir estabilidade e semântica bem definida para o futuro. Vários pacotes já foram atualizados ou estão em processo de atualização (cloudflare, rfc2136 e desec, para citar alguns).
  • Configuração global do dns: Agora que vários componentes da configuração do Caddy podem afetar os registros DNS (desafios ACME, publicação ECH, etc.), há uma nova opção global dns que pode ser usada para especificar a configuração do seu provedor DNS em um único lugar. Isto evita a repetição de credenciais para servidores onde todos os domínios são gerenciados por um único provedor DNS. Obrigado aos muitos colaboradores que ajudaram a tornar isso possível! :tada: :partying_face: :champagne: : aviso: Embora tradicionalmente suportemos as duas últimas versões secundárias do Go para acomodar algumas políticas de distribuição/gerenciador de pacotes, agora oferecemos suporte apenas à versão secundária mais recente do Go. Vale a pena disponibilizar os benefícios de privacidade e segurança adicionados nas novas versões Go (como criptografia pós-quântica) para todos o mais rápido possível, em vez de reter toda a base de usuários ou manter múltiplas configurações de compilação de código.

Detalhes criptografados do ClientHello (ECH)

(Esta é uma breve visão geral. Recomendamos a leitura da documentação completa.) Normalmente, os nomes de servidores (nomes de domínio ou "SNI") são enviados no texto simples ClientHello ao estabelecer conexões TLS. Com o ECH, o nome verdadeiro do servidor é criptografado (e empacotado) por um ClientHello "externo" que possui um SNI genérico de sua escolha. Com muitos sites no mesmo servidor compartilhando o mesmo SNI externo, tanto o clients quanto o servidor têm mais privacidade em relação aos nomes de domínio. Caddy implementa ECH totalmente automatizado, o que significa que ele gera (e [em breve] (https://github.com/golang/go/issues/71920), rotaciona), publica e fornece configurações de ECH simplesmente especificando um provedor DNS e o nome de domínio externo/público a ser usado. O ECH totalmente automatizado requer um módulo DNS integrado ao seu binário Caddy. Para que um client, ​​como um navegador, saiba que pode usar o ECH e quais parâmetros usar, a configuração do ECH do servidor deve ser publicada. Esta configuração inclui o nome público, parâmetros criptográficos e uma chave pública para criptografar o ClientHello interno. Por convenção, os navegadores leem o registro DNS padronizado do tipo HTTPS contendo um ech SvcParamKey. Caddy define esse registro DNS para todos os domínios protegidos, mas precisa do módulo provedor DNS conectado e configurado para fazer isso. Se você já estiver usando o desafio DNS ACME, você já deve ter um provedor DNS conectado. Se preferir construir o Caddy a partir da fonte com um módulo DNS, é fácil com xcaddy, por exemplo: $ xcaddy build --with github.com/caddy-dns/cloudflare A configuração mínima necessária para habilitar ClientHello também é a configuração recomendada, pois maximiza os benefícios de privacidade na maioria das situações. Você só precisa da opção global ech e de um provedor DNS especificado. Aqui está um exemplo usando Cloudflare como servidor de nomes: Caddyfile:

{
	debug  # not required; recommended while testing
	dns cloudflare {env.CLOUDFLARE_API_KEY}
	ech ech.example.net
}

example.com {
	respond "Hello there!"
}

Isso protege todos os seus sites (example.com neste caso) com o nome público ech.example.net. (Como outro exemplo, a Cloudflare usa cloudflare-ech.com para todos os sites que atende. Recomendamos escolher um único domínio público e usá-lo para proteger todos os seus sites.) O nome externo/público que você escolher deve apontar para o seu servidor. Caddy obterá um certificado para este nome para facilitar conexões seguras e confiáveis para clients quando necessário. Sem um certificado, clients pode ser forçado a se conectar de forma insegura, ou não conseguir se conectar, em alguns casos, o que não apenas os deixa vulneráveis, mas também corre o risco de expor os nomes dos sites do seu servidor. Caddy então usa o provedor DNS especificado para publicar as configurações ECH para seus vários nomes de site. Ele cria (ou aumenta) registros do tipo HTTPS para os domínios dos seus sites (não o seu nome público ECH). Observe que os módulos do provedor DNS são mantidos de forma independente e podem não ter sido testados quanto à compatibilidade com registros do tipo HTTPS. Entre em contato com os mantenedores do seu módulo se tiver problemas. Se você tiver necessidades de configuração mais avançadas, você pode usar a configuração JSON (mais detalhes em breve; por enquanto, consulte #6862 ou veja o código fonte; ou use caddy adapt para converter um Caddyfile em JSON).

Testando e verificando ClientHello criptografado

Primeiro, certifique-se de que o Caddy seja executado com sucesso com o ECH ativado (e um módulo DNS) na configuração. Você deverá ver registros de que está gerando uma configuração ECH e publicando-a em seu(s) nome(s) de domínio. Você precisará usar um client que suporte ECH. Algumas compilações personalizadas do curl o fazem, e o Firefox e os navegadores modernos baseados no Chrome também o fazem, mas você precisa primeiro ativar o DNS sobre HTTPS ou DNS sobre TLS (já que, obviamente, consultar o DNS em texto simples para um nome de domínio protegido irá expor o domínio e anular o propósito do ECH). Se estiver reutilizando um nome de domínio existente, limpe o cache DNS. O Firefox tem uma maneira de fazer isso com seu cache em about:networking#dns. Depois de ter um client adequado, use Wireshark para capturar pacotes de rede enquanto você carrega seu site. Você deve ver apenas o nome externo/público como valores SNI (ServerName Indicator) na captura de pacotes. Se a qualquer momento você vir o nome verdadeiro do site, o ECH não está funcionando corretamente - pode ser um problema do client ou do servidor. Antes de registrar um bug, tente primeiro identificá-lo como um problema de servidor. Mas definitivamente relate bugs do servidor! Obrigado! (Observe que o ECH não é publicado automaticamente para domínios CNAME e o domínio já deve ter um registro na zona.)
