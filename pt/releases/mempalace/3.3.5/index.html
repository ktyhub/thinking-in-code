mempalace v3.3.5

#mempalace v3.3.5 3.3.5 é uma versão de correções. Nenhum novo recurso voltado para o usuário — a energia do ciclo foi direcionada para integridade de dados, recuperação e correção de processos cruzados. Se o seu palácio alguma vez atingiu Internal error: Error finding id depois de uma grande mina, ou se um gráfico de conhecimento triplo desapareceu silenciosamente no vazio, ou se você está executando o Windows / um host multilocatário - esta versão é para você. O título corrige:

  • mempalace repair --mode from-sqlite recupera palácios presos em apply_logs. Quando o escritor do segmento HNSW do ChromaDB é bloqueado (a classe de corrupção relatada no upstream e em #1308), --mode legacy e o reparo inline chamam Collection.count() como sua primeira leitura - que é exatamente a chamada que surge. O antigo modo de falha era um reparo imprimindo Cannot recover — palace may need to be re-mined from source files mesmo que as tabelas SQLite estivessem totalmente intactas. O novo modo lê (id, document, metadata) diretamente de chroma.sqlite3 por meio da junção de segmento de metadados, nunca abre um chromadb client contra o palácio corrompido e reinsere tudo em um novo palácio sob sua função de incorporação configurada. Verificado de ponta a ponta em um palácio corrupto do mundo real com 52.300 linhas. (#1308)
  • Duas classes de perda silenciosa no gráfico de conhecimento agora são erros de tempo de gravação. Os triplos com valid_to < valid_from costumavam ser armazenados de forma durável, mas inacessíveis (o filtro temporal não correspondia a as_of); add_triple() agora rejeita intervalos invertidos no momento da gravação. E as strings de data encaminhadas para SQLite são validadas antecipadamente por meio de sanitize_iso_temporal() (também conhecido como sanitize_iso_date()), que aceita YYYY-MM-DD e datas UTC canônicas (YYYY-MM-DDTHH:MM:SSZ / +00:00) e rejeita todo o resto - entradas de linguagem natural como "yesterday" não produzem mais conjuntos de resultados vazios silenciosamente. Mudança de comportamento: entradas de data parcial que funcionavam em 3.3.4 ("2026", "2026-05") agora apresentam erro; passe uma data completa ou uma data e hora UTC canônica. (#1214, #1164, #1167, #1374, #1417)
  • EntityRegistry.save() agora é seguro contra falhas. O mapa de pessoas/projetos contém meses de mineração de dados, e o código antigo fazia um Path.write_text() não atômico - uma perda de energia, OOM ou kill -9 entre truncado e descarga completa o limparia silenciosamente (o load() do registro engole JSONDecodeError). Salvar agora grava em um arquivo temporário irmão, fsyncs e os.replace()s no lugar. O registro anterior permanece intacto em qualquer falha antes que a renomeação retorne. (#1215)
  • MCP tool_search passa pela janela de descarga HNSW pós-mina em massa. Depois de uma mina CLI, os metadados do segmento HNSW do ChromaDB podem ser liberados por aproximadamente 30-60s; A pesquisa MCP com escopo de asa estava atingindo Internal error: Error finding id para toda a janela. tool_search agora detecta esse transiente específico, descarta os caches locais do MCP e de back-end compartilhado do palácio, dorme 2s e tenta novamente uma vez. As novas tentativas bem-sucedidas são marcadas com index_recovered: true para que os chamadores possam observar quando foram disparadas. Correção parcial para o cluster #1315 mais amplo – tool_check_duplicate e outras ferramentas de toque de índice ainda precisam do mesmo wrapper. (#1396)
  • Correção de processos cruzados no Windows e em hosts multilocatários. ChromaBackend.close_palace() agora libera corretamente o bloqueio de arquivo SQLite do lado rust do ChromaDB - reabrindo o mesmo caminho do palácio depois que shutil.rmtree não falha mais com SQLITE_READONLY_DBMOVED. E o _kg do servidor MCP não é mais um singleton de nível de módulo: hosts multilocatários girando MEMPALACE_PALACE_PATH entre chamadas de ferramenta agora acessam o arquivo SQLite correto por meio de um cache lento por caminho. (#1067, #1105, #1136, #1160)
  • O Windows stdio é UTF-8 em todos os aspectos. mempalace search > out.txt e invocações de fact_checker canalizadas não mojibake texto de gaveta cirílico/CJK no limite do processo. mcp_server, hooks_cli e cli/fact_checker são todos reconfigurados de forma idêntica. (#1282)
  • Correção de roteamento miner.detect_room para monorepos. A verificação de substring era bidirecional, portanto, qualquer token que fosse uma substring de um nome de sala ou vice-versa correspondesse - views/billing-page/src/Foo.test.tsx roteado para uma sala interviews porque "views" in "interviews" correspondeu primeiro. Agora usa correspondência de token delimitado por separador (-, _, ., /). (#1004, fecha #1002)
  • mempalace compress não trava mais em palácios acima de ~32k gavetas. A busca de gaveta agora é paginada, espelhando a correção #851 em miner.py. (#1073, #1107) Interno: a confiabilidade do teste também foi aprovada - tests/test_palace_locks.py e tests/test_chroma_collection_lock.py mudaram de fork para spawn para geração de subprocessos (Python 3.13 + pai multithread = deadlock em fork, e macOS proíbe fork-without-exec via CoreFoundation), e vários arquivos de teste agora envolvem sqlite3.connect(...) em contextlib.closing() para que as conexões sejam liberadas no caminho de falha também. (#1430, #1431) As promessas não mudaram. Cada palavra armazenada exatamente. Tudo fica na sua máquina. Sem telemetria. Não há alternativas para a nuvem APIs sobre as quais não falamos. Cada lançamento aprimora o que já está lá.
