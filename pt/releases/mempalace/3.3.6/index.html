mempalace v3.3.6

3.3.6 é um lançamento de recursos. O título do ciclo funciona: recuperação multilíngue por padrão (incorporaçãogemma substitui MiniLM, cosseno interlingual salta de 0.35 → 0.88), o primeiro corte do gráfico de memória viva (corredores dentro das asas, túneis através das asas, potenciação hebbiana + decaimento de Ebbinghaus para que as conexões se fortaleçam com o uso e desapareçam sem), mineração de documentos de escritório (PDF, DOCX, PPTX, XLSX, RTF, EPUB através do novo --mode extract), números de linha virtuais + ponteiros de armário cirúrgico que citam intervalos exatos de linhas em datas exatas e o passe de limpeza de detecção de entidade que mantém o "Código" fora de seus corredores e o "Código Claude" atômico. As promessas não mudaram. Cada palavra armazenada exatamente. Tudo fica na sua máquina. Sem telemetria. Cada lançamento aprimora o que já está lá.

Recursos

  • Mineração de documentos do Office via --mode extract. O novo mempalace mine <dir> --mode extract ingere livros PDF, Word (.docx), PowerPoint (.pptx), Excel (.xlsx), RTF e EPUB, além do caminho de código-fonte/texto existente. Instalar com pip install mempalace[extract] — extrai striprtf para RTF e MarkItDown (com sub-extras [docx,pdf,pptx,xlsx]) para formatos binários. Os usuários de Python 3.9 obtêm cobertura RTF apenas porque MarkItDown requer 3.10+. As gavetas do caminho de extração carregam metadados extract_mode para que o minerador convo "já minerado?" a geração de verificação e identificação de gaveta permanece isolada por modo (#1528). (#1555)
  • Números de linha virtuais + ponteiros de armário cirúrgico. Gavetas armazenadas agora carregam números de linha virtuais para que o verbo CLI lido e os ponteiros de armário possam citar intervalos de linha exatos. Os ponteiros do armário (Nível 6a) incluem informações de data + intervalo de linhas derivadas do nome do arquivo e da análise de data do corpo do conteúdo (python-dateutil agora é um departamento principal), então o MemPalace pode apontar linhas exatas em datas exatas, em vez de apenas "em algum lugar nesta gaveta". (#1555, #1584)
  • Corredores dentro da ala. Quando duas entidades (pessoas, projetos, tópicos) co-ocorrem na mesma gaveta, o minerador agora registra um "corredor" - uma borda do gráfico conectando-as dentro daquela ala. Calculado automaticamente como parte da etapa pós-mineração no compute_hallways_for_wing para que o gráfico cresça gradativamente com novo conteúdo, sem comando separado. Fundação para navegação entre entidades entre salas dentro de um palácio. (#1558, #1560)
  • Túneis entre asas promovidos nos corredores. Quando a mesma entidade aparece em corredores em várias alas, o MemPalace agora a promove automaticamente em um túnel - permitindo que as consultas saltem da ala de uma pessoa para a ala do projeto em que aparecem, sem que ninguém ligue para create_tunnel manualmente. Os túneis de tópico do caminho compute_topic_tunnels existente permanecem inalterados. (#1565)
  • Dinâmica da memória viva (potenciação hebbiana + decaimento de Ebbinghaus). Corredores e túneis ficam mais fortes cada vez que a mesma conexão é reforçada por novo conteúdo ("o que dispara junto, fios juntos") e desaparecem gradualmente se uma conexão parar de aparecer nas gavetas de entrada. Os pesos de navegação rastreiam o uso real do palácio em vez de serem estáticos, portanto, a classificação de recuperação melhora com o tempo, à medida que o palácio é realmente usado. (#1578)
  • Transcrições da ferramenta API são roteadas automaticamente para wing_api. Transcrições de conversas de ferramentas de IA estilo API (Claude Code, Claude.ai, ChatGPT, exportações de Slack-bot, JSON genérico em forma de OpenAI, etc.) agora são roteadas para um wing_api dedicado em vez de se misturar nas alas de conversação humana. Evita que o tráfego de chamadas de ferramentas polua as alas pessoais/do projeto e melhora a precisão da pesquisa quando você procura "o que eu disse" versus "o que o agente disse". (#1236)
  • Incorporação multilíngue por padrão para novas instalações: embeddinggemma-300m ONNX (q8, MRL→384-dim). O incorporador anterior do MemPalace (all-MiniLM-L6-v2) é treinado apenas em inglês - similaridade de cosseno multilíngue em médias de texto traduzidas paralelamente 0.35 em DE/FR/HI/IT/KO/RU (RU em 0.17, quase ortogonal). Um usuário que fala russo efetivamente não consegue encontrar suas próprias memórias, o que quebra a promessa de design de "recuperação de 100%" do CLAUDE.md. A nova classe EmbeddinggemmaONNX em mempalace/embedding.py traz isso para a média 0.88 (validado sem perdas versus o Ollama gguf por meio de teste direto de tempo de execução ONNX). Downloads lentos do onnx-community/embeddinggemma-300m-ONNX (~300 MB) no primeiro uso via huggingface_hub. A saída é truncada para 384 dims por meio do Matryoshka Representation Learning, de modo que o modelo é uma opção para as coleções de 384 dim do ChromaDB - sem alteração de esquema. O prefixo Sim ("task: sentence similarity | query: ") é aplicado automaticamente. Onboarding (python -m mempalace.onboarding) agora oferece o modelo multilíngue como padrão - escolhê-lo grava embedding_model: embeddinggemma em config.json para que as execuções subsequentes o selecionem sem nova solicitação. As instalações existentes que nunca definiram o env var ou executaram a integração permanecem no minilm (retrocompatibilidade). MEMPALACE_EMBEDDING_MODEL=minilm|embeddinggemma substitui ambos. A troca de modelos em um palácio existente requer reincorporação - execute mempalace repair rebuild-index após a mudança. (#1483)
  • Deps multilíngues movidos para o núcleo. huggingface_hub, tokenizers e numpy agora são dependências necessárias para que o caminho multilíngue funcione imediatamente após pip install mempalace. O extra [multilingual] é mantido como um alias autônomo para retrocompatibilidade com scripts de instalação. O próprio modelo ONNX de 300 MB ainda é baixado lentamente no primeiro uso, não no momento da instalação.
  • Erro de incompatibilidade de nome EF do ChromaDB mais amigável. Trocar MEMPALACE_EMBEDDING_MODEL em um palácio existente sem executar rebuild-index revelou anteriormente o Embedding function conflict: new: X vs persisted: Y ValueError do ChromaDB - preciso, mas não informava aos usuários como se recuperar. ChromaBackend.get_collection() agora resolve esse erro e aponta para ambas as opções: reverter o env var ou executar mempalace repair rebuild-index --palace <path>. (#1483)
  • Alternar hooks.auto_save para sessões de modo silencioso. O novo botão de configuração (e a fiação do sinalizador --silent CLI através do gancho de salvamento) permite que os usuários optem por não salvar o diário automático em Stop / PreCompact. Útil para sessões de “modo silencioso” onde você não deseja que todas as conversas sejam capturadas. O comportamento padrão permanece inalterado — o salvamento automático ainda é executado, a menos que seja explicitamente desativado. (#711)
  • Filtrar palavras comuns de conteúdo em inglês a partir da detecção de entidades. Palavras de conteúdo em inglês de alta frequência ("sistema", "usuário", "memória", "projeto", "contexto" etc.) estavam sendo marcadas como entidades pelo detector por gaveta e poluindo o registro de entidades como "pessoas". Uma lista de palavras COCA enviada (palavras de conteúdo principais) agora é consultada durante a classificação da entidade para que sejam filtradas antes de chegarem ao registro. Reforçado contra JSON malformado na lista de palavras agrupada. (#1605)
  • Correspondência de entidades sem distinção entre maiúsculas e minúsculas no momento da mineração. A construção inicial do palácio (mempalace init) combinou nomes de entidades sem distinção entre maiúsculas e minúsculas, mas o etiquetador por gaveta usado durante a mineração incremental não o fez - portanto, a mesma pessoa foi marcada de forma diferente entre init e ingest ("Aya" vs. "aya" tornaram-se entidades distintas). O etiquetador incremental agora reflete o correspondente que não diferencia maiúsculas de minúsculas, restaurando a consistência da etiqueta da entidade em todo o ciclo de vida do palácio. (#1557)

Correções de bugs

  • Perda silenciosa de dados em três caminhos de upsert. Três sites de upsert (ingestão de arquivo, ingestão de conversa e uma ramificação de reparo) estavam chamando o incorporador em conteúdo não fragmentado, truncando silenciosamente no limite máximo de token do incorporador. Gavetas longas chegaram com apenas a seção principal indexada, quebrando a promessa de “recuperação de 100%” em conteúdo de formato longo. Todos os três agora passam primeiro pelo chunker para que o documento completo seja incorporado e armazenado. (#1540, continuação de #1539)
  • O chunker de parágrafo emitia pedaços grandes para parágrafos longos. O divisor de parágrafo presumia que os parágrafos eram sempre mais curtos que CHUNK_SIZE e os emitia inteiros; parágrafos longos (texto jurídico, redações técnicas densas) excediam silenciosamente a janela de contexto do incorporador. O divisor agora limita cada pedaço emitido para homenagear CHUNK_SIZE. (#1538, correções #1534)
  • O limite de blocos por arquivo foi codificado e muito baixo para transcrições grandes. Um limite de segurança limitou os blocos por arquivo em um valor ajustado para o código-fonte; a mineração de transcrições de conversas muito grandes deixou cair silenciosamente o limite. Agora configurável, com o padrão aumentado para cobrir tamanhos de transcrição realistas. (#1554, correções #1455)
  • Subprocesso de gancho/impasse ChromaDB no Windows. Ganchos Stop/PreCompact podem travar contra um ChromaDB client já aberto no Windows, deixando o host (Claude Code) preso esperando no gancho. Correção de três partes: tempo limite do PID obsoleto na recuperação do bloqueio da mina, caminho de saída ocioso no servidor MCP e erros estruturados quando o padrão de conflito é detectado para que o host possa se recuperar. (#1562, correções #1552)
  • create_tunnel nomes de asas hifenizados corrompidos. O analisador de endpoint foi dividido em -, então asas cujo nome continha um hífen (mem-palace, my-app) foram truncadas no meio do nome e o túnel apontou para um endpoint inexistente. A análise do endpoint agora preserva o slug completo. (#1529, correções #1504)
  • **O cache do gráfico de conhecimento do MCP produziu gráficos duplicados para caminhos do palácio com links simbólicos/casos diferentes. ** A chave do cache era a string do caminho bruto, então /Users/me/.mempalace/palace e /Users/me/.mempalace/Palace (dobrados em maiúsculas no macOS) ou um alias com link simbólico produziram duas instâncias KnowledgeGraph armazenadas em cache separadas apontando para o mesmo arquivo SQLite, com risco de leitura obsoleta. O cache agora é normalizado via realpath + normcase para que eles sejam recolhidos em uma única chave canônica. (#1383, correções #1372)
  • Nomes de pastas de projeto hifenizados truncados com gancho de salvamento. O analisador de nome de asa estava dividido em - e mantendo apenas o primeiro segmento, então mem-palace se tornou mem. A correção preserva o slug completo da pasta do projeto para que os palácios hifenizados permaneçam coerentes nas invocações de gancho. (#1424, correções #1410)
  • O minerador ignorou silenciosamente os links simbólicos. Os usuários ficaram confusos sobre a perda de dados após a mineração; o mineiro estava pulando links simbólicos sem trazê-los à tona. Agora registra cada link simbólico ignorado com o motivo para que a lacuna fique visível. (#1466, correções #1462)
  • O PYTHONPATH vazado pelo host pode ocultar os próprios módulos do MemPalace na importação. O pacote __init__ agora remove as entradas vazadas na importação para que o MemPalace importado seja sempre o instalado. (#1439, correções #1423)
  • **scripts de gancho stock-bash do macOS. ** Os scripts de gancho usaram mapfile (bash 4+), quebrando o estoque do macOS /bin/bash 3.2. Mudou para um pipeline sed para que os ganchos funcionem imediatamente em todos os Mac. (#1441, correções #1440)
  • Os ganchos Plugin Stop/PreCompact podem travar indefinidamente em um filho preso. O tempo limite limitado garante que o host sempre possa avançar, mesmo se o processo filho do MemPalace não estiver íntegro. (#1470, correções #1465)
  • Os manipuladores MCP agora retornam erros estruturados JSON-RPC para entradas malformadas. Nomes de parâmetros desconhecidos retornaram -32602 Invalid params em vez de um Python TypeError não estruturado; parâmetros com formato errado retornam um erro estruturado em vez de um rastreamento bruto. (#1500, #1513)
  • CLI distingue "o palácio não existe" de "o palácio existe, mas está vazio". Dois estados que parecem iguais para um novo usuário agora são relatados separadamente com mensagens de próxima etapa acionáveis para cada um. (#1532, correções #1498)
  • mempalace repair pós-aprovação: reconstrução VACUUM + FTS5. Após um reparo no palácio, o arquivo gráfico de conhecimento SQLite manteve páginas fragmentadas e um índice FTS5 obsoleto; executar VACUUM e reconstruir o FTS5 no final recupera o disco e restaura o desempenho da pesquisa. (#1523)
  • Isolamento do modo Convo miner. A opção "já minerado?" a geração de verificação e ID de gaveta ignorou extract_mode, portanto, a alternância de modos reminerou o mesmo conteúdo (duplicação de dados) ou colidiu IDs de gaveta entre modos. A definição do escopo por modo mantém as gavetas de cada modo isoladas e com eliminação de duplicação correta. (#1528, correções #1505)
  • Validação FTS5 no final da mina. A mineração agora valida a integridade do índice FTS5 como uma pós-etapa para que a corrupção seja detectada no momento da gravação, não no momento da leitura. (#1548, correções #1537)
  • hooks_cli travou em caminhos de instalação superficiais. Código indexado Path.parents[3] assumindo uma árvore de instalação profunda, aumentando IndexError quando o MemPalace executou a partir de um caminho raso (por exemplo, /opt/mp). Adiciona uma proteção para que instalações superficiais não travem mais nos comandos do gancho. (#1585)
  • Quarentena de segmento HNSW: byte zero vs dim ausente. A heurística de quarentena anterior sinalizou qualquer segmento HNSW sem o campo de metadados dim como corrompido, mas a maioria era recuperável; a verificação agora distingue segmentos de índice ausentes recuperáveis ​​​​de realmente corrompidos, preservando segmentos de índice em funcionamento. Arquivos de lista de links de zero byte (segmentos parcialmente escritos) agora são rejeitados completamente. (#1452, #1461, correções #1457)
  • Arquivo detentor de bloqueio de mina escrito como UTF-8 em vez de cp1252. Nomes de usuário e caminhos não-ASCII do Windows não corrompem mais o arquivo de bloqueio e quebram a detecção de bloqueio obsoleto. (#1438)
  • A reivindicação do slot do minerador agora grava um PID de espaço reservado imediatamente. A falha entre a reivindicação e a gravação do PID não deixa mais um bloqueio fantasma. (#1543, correções #1443)
  • mine_convos agora é executado dentro de mine_palace_lock. Duas invocações simultâneas de convos mine não podem mais corromper o índice. (#1477)
  • Limpeza da ferramenta de migração. A ferramenta de migração da versão ChromaDB agora fecha sua conexão SQLite e remove o diretório temporário do palácio se uma exceção for disparada no meio da migração; migrações com falha param de vazar identificadores de arquivos e disco. A gravação atômica do registro de entidade agora exclui seu arquivo secundário .tmp se a gravação ou renomeação falhar. (#1216, #1408, correções #1373)
  • A ferramenta de reparo tolera células de metadados vazias/nenhuma. O ChromaDB ocasionalmente retorna células com dictos de metadados vazios ou None durante a reconstrução; ambos são agora coagidos a padrões sensatos para que a reconstrução seja concluída e os palácios que de outra forma estariam presos se recuperassem. (#1459, #1445, correções #1426)
  • O manipulador MCP create_tunnel agora propaga erros. Endpoint ou direção incorreta estava sendo engolida e retornada como sucesso enganoso; agora se propaga como um erro estruturado do MCP. (#1546, correções #1473)
  • Túneis explícitos foram armazenados em um local codificado ~/.mempalace/tunnels.json path that ignored MempalaceConfig.palace_path. Drawers, KG triples, the people map, and every other piece of palace state honour the configured palace_path (and the MEMPALACE_PALACE_PATH env var), but palace_graph._TUNNEL_FILE was a module-level constant initialised once from os.path.expanduser("~") + "/.mempalace/tunnels.json". Under any setup where $HOME is isolated from the configured palace — subagent profiles with their own $HOME, sandboxes, multi-tenant hosts, container mounts that move the palace to /srv/ — drawers landed in the configured palace while tunnels silently landed in a different file that no other process touching the same palace could see. Worst case is the agentic one: an isolated worker calls create_tunnel then list_tunnels`ZZPH10 0ZZ`palace_graph._TUNNEL_FILE is replaced by _get_tunnel_file() which derives the path from a new MempalaceConfig.tunnel_file property (sibling of palace_path). The default single-user install is unchanged because the default palace_path is still ~/.mempalace/palace and its sibling tunnels.json is the legacy path. Backwards-compatibility: if the configured tunnel file does not exist but a file is present at the pre-3.3.6 hardcoded ~/.mempalace/tunnels.json path AND the two paths differ, _load_tunnels logs a one-line ``WARNING`' nomear ambos os caminhos e retornar uma lista vazia - intencionalmente NÃO migramos automaticamente porque a fusão silenciosa do estado do túnel em dois locais corre o risco de destruir dados mais recentes; o próprio usuário move ou copia o arquivo. (#1467)
  • create_tunnel did not validate that the source and target rooms actually exist in the chroma index. _require_name only checked that wing/room names were non-empty strings; nothing queried the collection to confirm at least one drawer carried matching {wing, room} metadata. Pointing an explicit tunnel at a phantom room — common when an agent fabricates a room name it expects to exist, or types a slug wrong — silently succeeded. Combined with the read-bubble described in the previous fix, an agent could create_tunnel → list_tunnels and have both calls return its own bogus write. create_tunnel now calls _check_room_exists(wing, room, col) for both endpoints before persisting an explicit tunnel; if either endpoint has zero matching drawers the call raises ValueError naming the offending wing/room pair. Three deliberate carve-outs: (1) kind != "explicit" skips validation because topic tunnels generated by compute_topic_tunnels use synthetic topic:<name> room identifiers that don't correspond to real chroma rooms; (2) _get_collection returning None (palace not yet created, transient backend failure, tests without a real chroma backend) skips validation rather than fail-closed — matches the tolerance pattern used everywhere else in palace_graph; (3) exceptions raised by the underlying col.get(where=..., limit=1, include=[]) query are logged and treated as "can't verify, allow" so a temporary index fault never blocks legitimate writes. Behaviour change: existing callers that previously created tunnels pointing at empty rooms (e.g. as scaffolding before mining them) will now raise ValueError. Arquive primeiro a gaveta e depois crie o túnel – esta é a ordem que a documentação sempre recomendou. (#1468)

Desempenho

  • O minerador Convo pré-busca o conjunto minerado uma vez. Estava emitindo uma consulta WHERE por arquivo para verificar "já minerado?"; agora pré-busca o conjunto completo extraído uma vez, reduzindo o tempo de espera em grandes corpus de transcrição. (#1474)
  • Retorno de chamada de progresso do rebuild_index. Reconstruções de várias horas agora relatam o progresso com a impressora ETA padrão; os usuários não precisam mais adivinhar se o processo está progredindo. (#1487)
  • Diagnóstico de inicialização a frio do MCP + aquecimento opcional. Adiciona visibilidade sobre qual incorporador está carregando e quanto tempo leva, além de um caminho de aquecimento opcional para que os usuários possam ver e resolver a latência lenta da primeira consulta. (#1530, correções #1495)

Interno

  • palace_graph._TUNNEL_FILE (module-level constant) replaced by _get_tunnel_file(config=None) and _legacy_tunnel_file(). Tests previously monkeypatching the constant must now monkeypatch the resolver functions. The tests/test_palace_graph_tunnels.py::_use_tmp_tunnel_file helper, tests/test_closets.py::TestTunnels setup/teardown, and three tests in tests/test_miner.py were updated accordingly. Topic-tunnel tests in test_miner continue to work without stubbing _get_collection because kind="topic" causa um curto-circuito no novo caminho de validação.
