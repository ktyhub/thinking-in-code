#repomix v1.18.0

Esta versão introduz o modo sandbox para o servidor MCP, confinando-o a um único diretório de espaço de trabalho, juntamente com um conjunto de alterações de reforço de segurança na superfície da ferramenta MCP e no processamento de repositório remoto!

Novidades 🚀

Modo Sandbox MCP (#1753, #1754)

O servidor MCP agora pode ser confinado a um único diretório de espaço de trabalho com o sinalizador --sandbox:

# Confine to the current working directory
repomix --mcp --sandbox

# Confine to a specific directory
repomix --mcp --sandbox path/to/project

Por padrão, o servidor MCP pode ler qualquer caminho que o usuário host possa, o que é conveniente para um assistente local trusted, mas muito amplo quando o servidor é exposto a um client ou agente nãotrusted, como ao incorporar o Repomix em um aplicativo hospedado. No modo sandbox:

  • Cada caminho é relativo à raiz do espaço de trabalho. Caminhos absolutos, ~, .. e caminhos de unidade/UNC do Windows são recusados ​​e caminhos resolvidos fora da raiz (inclusive por meio de links simbólicos) são eliminados.
  • Os resultados e as mensagens de erro são virtualizados, portanto os caminhos do host nunca são expostos.
  • Somente as ferramentas somente leitura e confinadas à raiz são registradas: pack_codebase, read_repomix_output, grep_repomix_output, file_system_read_file e file_system_read_directory. O empacotamento remoto, a geração de habilidades e a anexação de saídas externas estão desativados.

Este é um confinamento da superfície da ferramenta no nível do aplicativo, não uma sandbox no nível do sistema operacional: ao hospedar o servidor para clients untrusted, ainda execute-o sob o isolamento usual da sua plataforma (contêineres, usuários dedicados).

Consulte Servidor MCP – Modo Sandbox para obter detalhes.

Agradecimentos especiais a @huy-trn por projetar e implementar este recurso. É ótimo ter um colaborador de longa data de volta! 🎉

Fortalecimento de segurança 🔒

As ferramentas do sistema de arquivos MCP agora são somente sandbox

As ferramentas file_system_read_file e file_system_read_directory agora são registradas apenas no modo sandbox. Fora do --sandbox, eles podiam ler qualquer caminho que o processo pudesse, enquanto sua varredura Secretlint integrada era apresentada como mais proteção do que fornece: ele reconhece formatos secretos conhecidos no conteúdo do arquivo e nada mais. No modo sandbox, a raiz do espaço de trabalho fornece a essas ferramentas um limite de acesso real, com a verificação secreta mantida como uma proteção heurística adicional.

Se a configuração do seu MCP dependesse dessas duas ferramentas, adicione --sandbox [dir] aos argumentos do servidor para continuar a usá-los, confinados a esse espaço de trabalho.

As descrições e a documentação das ferramentas também foram reformuladas para descrever a varredura do Secretlint como o que ela é: uma heurística de conteúdo de melhor esforço, não um limite de acesso.

Consulte o comunicado de segurança para obter detalhes. Obrigado ao @rafaelfiguereod-stack pelo report! 🙏 https://github.com/yamadashy/repomix/security/advisories/GHSA-rpmv-562j-qxrv

Credenciais em URLs de repositório são editadas antes do registro

URLs remotos são rotineiramente escritos com credenciais embutidas (https://<token>@github.com/owner/repo.git), especialmente em CI. O Repomix anteriormente ecoou esses URLs como estão na saída do console, logs de rastreamento, mensagens de erro (o git repete a linha de comando completa em sua saída de falha) e a resposta MCP pack_remote_repository, persistindo a credencial na rolagem do terminal, logs de construção de CI e sistemas de agregação de log. Todos esses caminhos agora editam credenciais de informações do usuário e parâmetros de consulta de credenciais conhecidos (token, private_token, access_token e similares) antes que a URL seja gravada em qualquer lugar.

Consulte o comunicado de segurança para obter detalhes. Obrigado a @kakashi-kx pelo relatório! 🙏 https://github.com/yamadashy/repomix/security/advisories/GHSA-w8cw-mgw9-74h7

Endpoints de metadados em nuvem são recusados como alvos de clone

O empacotamento remoto agora se recusa a clonar endpoints de metadados de instâncias de nuvem (169.254.0.0/16, fd00:ec2::254, 100.100.100.200, metadata.google.internal), que fornecem credenciais e não hospedam nenhum repositório git. Através do servidor MCP, um agente de IA escolhe a URL, de modo que uma instrução injetada poderia direcionar um clone para um endereço que o usuário nunca solicitou. As redes privadas (RFC1918) permanecem permitidas, uma vez que a clonagem de servidores git auto-hospedados é normal.

Como atualizar

npm update -g repomix

Como sempre, se você tiver algum problema ou sugestão, informe-nos sobre os problemas do GitHub ou sobre nossa [comunidade Discord] (https://discord.gg/wNYzTwZFku).
