LightRAG v1.5.8rc1

Notas importantes

v1.5.8rc1 é um candidato a lançamento. Teste-o em uma cópia dos seus dados antes de atualizar a produção.

Destaques

1. Armazenamento de configuração: LightRAG agora lembra qual modelo de incorporação construiu seus vetores

Em versões anteriores, a alteração de EMBEDDING_MODEL ou EMBEDDING_DIM em uma implementação existente falhava silenciosamente. Dependendo do back-end, o LightRAG manteve os vetores antigos e retornou vizinhos errados ou abriu um novo contêiner de vetores vazio (Milvus/Qdrant/PostgreSQL) e serviu um gráfico de conhecimento sem nenhum vetor.

v1.5.8 adiciona um armazenamento de configuração. É um pequeno namespace KV (config) que contém as linhas de base de incorporação de cada espaço de trabalho: para cada destino de vetor (entidades, relacionamentos, pedaços), o espaço de incorporação em que seus vetores foram gravados. Se o espaço mudou, o servidor se recusa a iniciar e nomeia o alvo e a saída, em vez de apresentar resultados ruins.

  • Backends: JsonKVStorage, PGKVStorage, MongoKVStorage e OpenSearchKVStorage, selecionados com LIGHTRAG_CONFIG_STORAGE. Se não for definido, ele segue LIGHTRAG_KV_STORAGE, portanto, a maioria das implantações não precisa de nova configuração. RedisKVStorage não é admitido, portanto as implantações do Redis são padronizadas para JsonKVStorage, com um aviso de inicialização.
  • Não é necessária nenhuma preparação. Na primeira inicialização do v1.5.8, uma implantação existente registra suas linhas de base por conta própria. Uma linha de base é registrada apenas com base em evidências: uma sonda de adoção reincorpora alguns registros armazenados (até 8 por alvo) e os compara com os vetores armazenados, ou o contêiner é confirmado como vazio. Uma análise que não pode ser executada (por exemplo, o serviço de incorporação está inativo) não registra nada e é tentada novamente na próxima inicialização.
  • Âncora de implantação. A primeira inicialização também vincula a implantação ao contêiner de configuração que ela abriu, em WORKING_DIR/config_storage_anchor.json (tipo de back-end + UUID do contêiner). Cada inicialização posterior recusa um contêiner de outro tipo ou outro UUID. Portanto, um LIGHTRAG_KV_STORAGE alterado, um banco de dados diferente ou um volume substituído não movem mais sua configuração silenciosamente.
  • Novas ferramentas off-line:
    • lightrag-rebuild-vdb reincorpora uma área de trabalho ao modelo atual e registra as novas linhas de base. Esta é a saída após uma mudança intencional de modelo.
    • lightrag-migrate-config move o armazenamento de configuração para um backend de outro tipo, por exemplo de arquivos JSON para PostgreSQL.
    • lightrag-clear-storage limpa um espaço de trabalho offline, incluindo registros de configuração.
  • Vários servidores, um WORKING_DIR: suportado quando cada servidor possui seu próprio WORKSPACE e porta. Um segundo servidor no mesmo espaço de trabalho é recusado onde o sistema de arquivos suporta bloqueios de arquivos.

Para obter mais informações, consulte:

  • docs/LightRAG-API-Server.md: Migração de armazenamento de configuração entre tipos de back-end
  • lightrag/tools/README_REBUILD_VDB.md, README_MIGRATE_CONFIG.md, README_CLEAR_STORAGE.md
  • docs/design/ConfigurationStorageDesign.md: a visão geral do design

2. Gravações de gráficos e exclusão de documentos mais seguras

  • As edições manuais de gráficos (criar/editar/excluir/mesclar entidades e relações, insert_custom_kg) agora são serializadas umas contra as outras e contra o pipeline de ingestão em NetworkXStorage.
  • A ordem de confirmação para criação, edição, mesclagem e renomeação de entidade/relação foi reformulada para evitar perda de dados quando uma operação é interrompida.
  • As exclusões interrompidas de documentos são visíveis e podem ser repetidas.
  • A nova ferramenta lightrag-repair-chunk-tracking remove linhas órfãs de rastreamento de blocos deixadas para trás por uma exclusão interrompida.

**3. Padrões de armazenamento PostgreSQL ** O assistente de configuração agora gera PostgreSQL a partir da imagem oficial pgvector/pgvector e oferece PGTableGraphStorage (tabelas simples, sem Apache AGE) para o gráfico. PGGraphStorage (AGE) e os armazenamentos Redis (RedisKVStorage, RedisDocStatusStorage) estão obsoletos. Eles continuam trabalhando e registram um aviso na inicialização.

4. Reforço da segurança e novo provedor

  • As rotas /api/* compatíveis com Ollama são protegidas por LIGHTRAG_API_KEY (consulte Alterações recentes).
  • A extração de PDF executa o pypdf em um processo filho com recursos limitados.
  • As linhas de erro transmitidas não ecoam mais o texto bruto de exceção do provedor.
  • Nova ligação openai_responses LLM para as respostas OpenAI API.

Mudanças importantes

  • Python 3.11 ou posterior é necessário. Python 3.10 não é mais compatível. As imagens Docker (Python 3.12) não são afetadas.
  • Alterar o modelo de incorporação em um espaço de trabalho existente agora recusa a inicialização, onde costumava fornecer resultados errados ou vazios. Restaure o EMBEDDING_MODEL / EMBEDDING_DIM anterior ou execute lightrag-rebuild-vdb para reincorporá-lo ao novo modelo.
  • A alteração de LIGHTRAG_KV_STORAGE após a primeira inicialização de v1.5.8 é recusada enquanto LIGHTRAG_CONFIG_STORAGE não estiver configurado, porque o armazenamento de configuração se moveria silenciosamente com ele. Defina LIGHTRAG_CONFIG_STORAGE explicitamente para o back-end ancorado ou mova a configuração com lightrag-migrate-config.
  • As rotas Ollama requerem a chave API. Quando LIGHTRAG_API_KEY está definido e WHITELIST_PATHS não está definido, as solicitações /api/* sem a chave agora obtêm HTTP 403. No Open WebUI, o modelo lightrag:latest desaparece da lista. Correção: insira a chave como chave API da conexão Ollama (enviada como Authorization: Bearer <key>) ou defina WHITELIST_PATHS=/health,/api/* para manter o comportamento antigo.
  • POST /documents/clear_cache foi removido. Use DELETE /documents?clear_llm_cache=true. A limpeza do cache LLM agora acontece junto com a limpeza destrutiva.
  • Nomes de espaços de trabalho começando com $ são reservados. O servidor usado para servir WORKSPACE=$team como _team. Defina WORKSPACE=_team (o nome sob o qual seus dados já estão armazenados) e nenhum dado será movido.

Notas de atualização

  1. Faça backup primeiro e depois interrompa todas as instâncias antigas antes de iniciar o v1.5.8. Isso inclui todos os trabalhadores, servidores que compartilham o armazenamento e ferramentas de manutenção. A primeira inicialização cria o contêiner de configuração e vincula a âncora. Não faça uma atualização contínua que deixe um gravador antigo em execução.
  2. WORKING_DIR deve persistir, mesmo que todo armazenamento seja um banco de dados. Agora ele contém config_storage_anchor.json, e para configuração JSON também <workspace>/kv_workspace_config.json. No Docker, mantenha-o em um volume montado. No Helm, mantenha persistence.enabled: true. Um WORKING_DIR efêmero perde a âncora e a configuração JSON a cada reinicialização. Inclua-o em seus backups.
  3. O serviço de incorporação deve estar acessível durante a primeira inicialização, para que a sonda de adoção possa registrar as linhas de base. Verifique o log de inicialização de um WARNING cuja linha de base não pôde ser estabelecida. Se a inicialização for recusada com uma incompatibilidade de espaço de incorporação, seus vetores armazenados não correspondem ao modelo configurado: corrija a configuração ou execute lightrag-rebuild-vdb.
  4. Usuários de Redis: com LIGHTRAG_KV_STORAGE=RedisKVStorage, o armazenamento de configuração é padronizado para arquivos JSON em WORKING_DIR (ver nota 2). O armazenamento Redis está obsoleto; planeje uma mudança para PostgreSQL.
  5. Usuários do PGGraphStorage: sua implementação continua funcionando e o assistente mantém a imagem habilitada para AGE para ela. Para sair do AGE, migre primeiro o gráfico (python -m lightrag.tools.migrate_graph_storage --apply, sem necessidade de reindexação) e depois mude para PGTableGraphStorage e a imagem pgvector.
  6. Opcional: para manter a configuração em seu banco de dados em vez dos arquivos JSON, execute lightrag-migrate-config --target-backend PGKVStorage (ou MongoKVStorage / OpenSearchKVStorage) com todos os servidores parados. Em seguida, defina LIGHTRAG_CONFIG_STORAGE para esse backend.
  7. Para recomeçar com um novo modelo de incorporação, use lightrag-clear-storage em vez de excluir arquivos manualmente. Se você excluir arquivos manualmente, remova também kv_workspace_config.json e config_storage_anchor.json. Caso contrário, a linha de base registrada rejeitará o novo modelo.
  8. TOKEN_SECRET deve ser um valor aleatório de pelo menos 32 bytes (por exemplo, openssl rand -hex 32). O PyJWT atualizado alerta sobre segredos mais curtos.
  9. As mensagens de erro transmitidas são genéricas. Uma falha no meio de um fluxo em /query/stream, /api/generate ou /api/chat agora lê Internal server error (error_id: …) e não contém mais o texto de exceção do provedor LLM. O formato do fluxo permanece inalterado. Procure os detalhes no log do servidor daquele error_id. Um client que analisou o texto de erro do provedor do fluxo (por exemplo, para detectar limites de taxa) precisa ser atualizado.
