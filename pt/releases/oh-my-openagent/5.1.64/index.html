oh-meu-agente aberto v5.1.64

A sincronização de memória do desktop agora começa assim que o mecanismo é inicializado, sem esperar por uma sessão. Um mecanismo iniciado por omo host ensure carrega extensões somente quando uma sessão é aberta, enquanto o desktop não abre nenhuma até que o mecanismo tenha enviado o handshake de bootstrap de sincronização de memória, então os dois esperaram um pelo outro. O omo compilado e o lançador npm agora iniciam aquela reivindicação antes que o mecanismo seja carregado sempre que a inicialização de um mecanismo RPC declara um canal memory-sync; a primeira sessão o reutiliza. Uma declaração que falha ainda relata a sincronização de memória como indisponível e nunca retorna às credenciais CLI. (#12702) (#12704)

Interno (somente testes): a aquisição do macOS trust lê /etc/ssl/cert.pem por meio do leitor de pacote já injetável, e um teste agora prova que um arquivo padrão malformado produz a entrada de eliminação estruturada openssl-default-file-malformed (arquivo, causa, índice de bloco, estreitamento). (#12633)

Interno (somente testes): os testes do importador de arquivo padrão do OpenSSL agora fixam que qualquer byte alto em uma linha BEGIN, não apenas um BOM, elimina o arquivo inteiro. (#12632)

Interno (ferramentas de liberação): o chicote de mutação trust omo-nativo conta um mutante como morto apenas quando um teste nomeado falha por uma afirmação; um mutante que apenas gera um erro de tempo de execução ou trava durante o carregamento agora é relatado como crashed e falha na execução. (#12631)

Corrigido

  • A sincronização de memória não perde mais uma edição quando dois dispositivos alteram a mesma linha de um arquivo de memória ao mesmo tempo. Os dispositivos nesta versão mantêm ambas as edições como linhas inteiras e todos os dispositivos convergem. Antes, as edições eram mescladas caractere por caractere em um texto que não correspondia a nenhum dos dois (#12279).
    • Entre dispositivos nesta versão, uma edição não perturba uma linha que ninguém editou. A exceção é uma reescrita muito grande: quando um dispositivo adiciona e remove mais de 2.000 linhas de uma nota em um salvamento, esse salvamento é mesclado caractere por caractere, como antes desta correção, portanto, uma edição simultânea na mesma linha ainda pode ser unida.
    • Quando o corpo da nota ou o novo texto não termina com uma nova linha, a edição ainda é mesclada caractere por caractere, como antes, portanto, duas edições simultâneas na última linha ainda podem ser unidas.
    • Com um dispositivo que ainda executa uma versão mais antiga, a fusão de caracteres antigos ainda pode dar errado das seguintes maneiras:
      • Linhas adjacentes podem se fundir. O dispositivo mais antigo reescreve a linha logo após uma linha editada nesta versão. Dependendo dos IDs internos dos dois dispositivos, as duas edições podem se fundir em uma linha seguida por uma linha vazia. Medido: de head, one, two, tail, esta versão escreve ONE e o dispositivo mais antigo escreve TWO, e o resultado pode ser head, TWOONE, uma linha vazia, tail. Dois dispositivos mais antigos fornecem head, ONE, TWO, tail.
      • O texto restante é movido. O dispositivo mais antigo edita uma linha que esta versão exclui. Seu texto restante se junta a uma linha vizinha.
      • Sua própria diferença toca outras linhas. A mesclagem de caracteres do dispositivo mais antigo cruza para uma linha que seu usuário não editou. Isso também acontece entre dois dispositivos mais antigos.
    • Dois dispositivos mais antigos mantêm a fusão de caracteres antigos até serem atualizados. (#12597)
  • Sincronização de memória: a fase push de um grande conjunto de memória não precisa mais de memória proporcionalmente a todo o conjunto. Cada etapa push é usada para reler e reescrever um arquivo de diário contendo os dados de cada item pendente, várias vezes por lote. Um dispositivo que envia alguns milhares de arquivos de memória atingiu o pico de 2 GiB ou mais (#12286). O diário agora mantém um pequeno índice de itens pendentes com seus dados em arquivos separados, e um push lê apenas o lote que está enviando. Capturar o conjunto antes do push ainda retém o texto de cada arquivo capturado até que a captura termine. Um diário escrito por uma compilação mais antiga é convertido na primeira vez que é lido, incluindo aquele em que uma compilação mais antiga adicionou itens próximos ao novo índice. (#12597)
  • Sincronização de memória: um dispositivo que recebe um grande conjunto de memória não fica mais lento a cada arquivo que chega. A etapa de renderização costumava reler cada registro de renderização do ciclo para cada arquivo, de modo que a primeira extração de alguns milhares de arquivos de memória demorava dezenas de minutos (#12285). Cada arquivo agora custa o mesmo e o comportamento de reinicialização do travamento permanece inalterado. (#12597)
  • A memória git não aceita mais core.hooksPath, core.fsmonitor, include.path ou includeIf.*.path de um par GIT_CONFIG_COUNT herdado ou entrada GIT_CONFIG_PARAMETERS, portanto, um par exportado como core.hooksPath=/dev/null não pode mais ignorar silenciosamente os ganchos e o push de espelho do repositório de memória. Todos os outros pares injetados (url.*.insteadOf, http.extraHeader, credenciais, safe.directory, ...) ainda se aplicam, renumerados; uma lista injetada que o próprio git não pode analisar é descartada por completo. A memória git também não herda mais o redirecionamento de repositório (GIT_DIR, GIT_WORK_TREE, GIT_COMMON_DIR, GIT_OBJECT_DIRECTORY, GIT_NAMESPACE, GIT_CONFIG, ...), portanto não pode mais ser apontada para outro repositório; GIT_INDEX_FILE, GIT_CONFIG_GLOBAL e GIT_CONFIG_NOSYSTEM são mantidos. (#12360, corrige #12354) (#12597)
  • A sincronização de memória não interrompe mais cada envio de um dispositivo quando a alteração de um arquivo de memória é maior que o limite de lote de 8 MiB: esse arquivo é retido e nomeado no status de sincronização com o que fazer, todas as outras memórias continuam sincronizando e o arquivo sincroniza sozinho quando cabe. Uma alteração que outro dispositivo faz em um arquivo retido é mantida e chega à cópia desse dispositivo assim que o arquivo cabe, e uma alteração que uma compilação mais antiga já havia enfileirado para esse arquivo é recuperada da mesma maneira, em vez de permanecer travada. O rodapé da TUI mostra sync held e o aviso informa que o arquivo está sendo retido, e uma entrada recusada que pausa a sincronização nunca fica oculta atrás de um arquivo retido. (#12284) (#12597)
  • A abertura de um repositório de memória inicia até seis processos git a menos: os padrões de configuração local são lidos com um git config --list em vez de um git config --get por chave, e o reparo de final de linha é ignorado enquanto o repositório não rastreia nada. Cada sessão que abre memória paga isso e, em uma máquina carregada, cada processo git custa centenas de milissegundos. Os próprios testes do Memory-Core agora são executados sob o orçamento de teste canônico de 20 s, em vez dos limites de 5 a 15 s por arquivo, o que os fez falhar apenas em hosts ocupados. (#12104, corrige #12103) (#12597)
  • thread_send não reporta mais uma mensagem como queued quando nada irá captá-la. Quando a sessão do thread de destino não tem dreno em execução, o envio agora responde queued_offline: a mensagem é mantida e a sessão a aceita na próxima vez que for executada, para que o chamador saiba que nenhum turno foi iniciado e possa agir em vez de esperar. O dreno também relata uma mensagem que está retendo atrás do rascunho não enviado do usuário, de modo que um dreno ativo nunca seja confundido com um que está faltando. (#12488, corrige #12486)
  • Verifique se a remoção recursiva (sincronizada e assíncrona) realmente removeu seu caminho, tente novamente as sobras silenciosas limitadas e junte-se aos removedores de teste de varredura antes de excluir seus pais de fixação. (#11834)

Adicionado

  • As versões do Windows agora trazem omo-git-job-helper.exe, um pequeno auxiliar nativo que executa cada comando git de memória dentro de seu próprio objeto de trabalho kill-on-close, para que um escritor posterior possa provar que o git de um escritor morto desapareceu antes de recuperar um bloqueio encalhado. Nada usa o auxiliar ainda: o núcleo da memória mantém o comportamento atual do Windows até que um acompanhamento o conecte, e nenhuma versão reivindica o novo protocolo até que sua linha de estresse de criação em andamento tenha passado no Windows CI. (#12105, parte de #10391) (#12597)
