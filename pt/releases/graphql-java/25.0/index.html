#grafql-java v25.0

Principais mudanças

Carregador de dados

Estratégia de refatoração

O PerLevelDataLoaderStrategy existente foi refatorado, o que leva a simplificações e melhorias de desempenho.

Novas estratégias

Duas novas estratégias foram introduzidas: CHAINED e EXHAUSTED. Ambos podem ser configurados via UnusalConfiguration (ver próxima seção).

CHAINED permite que DataLoaders encadeados sejam usados ​​enquanto mantém estratégias de despacho por nível.

EXHAUSTED é uma estratégia completamente nova que funciona com base no despacho quando o motor não está ocupado. Ele reflete a estratégia de despacho do carregador de dados JS, mas para um sistema multithread.

Configuração incomum

Um mecanismo de configuração mais generalizado foi adicionado para "configuração incomum". Com isso queremos dizer configuração que não esperamos que muitas pessoas usem, mas se o fizerem, será agora em um lugar mais comum

Por exemplo, se você quiser alterar a profundidade máxima que o analisador de documentos aceitará, você poderá chamar os seguintes métodos.

        var parserOptions = newParserOptions().maxRuleDepth(99).build()
        GraphQL.unusualConfiguration().parsing().setDefaultParserOptions(parserOptions)

Anotações JSpecify

A equipe está começando a adotar as anotações https://jspecify.dev/ como forma de indicar campos anuláveis e não anuláveis. Muitas classes importantes tiveram essas anotações adicionadas para ajudar a tornar mais claro semanticamente quando um valor pode ser nulo ou não.

Mudanças importantes

Um objeto FetchedValue de empacotamento nem sempre é retornado em buscadores de campo por motivos de desempenho. Isso significa que graphql.execution.instrumentation.parameters.InstrumentationFieldCompleteParameters#getFetchedObject foi criado para substituir o método getFetchedValue mais antigo e o objeto de retorno às vezes pode ser um FetchedValue ou às vezes um simples valor POJO.

Melhorias de desempenho

Uma série de melhorias de desempenho foram feitas para reduzir o consumo de memória da biblioteca. Além disso, o operador Java .stream() pode ser mais lento que um loop mais direto e muitas dessas chamadas foram alteradas por motivos de desempenho.
