Mudanças notáveis

Mudanças na pontuação de desempenho

No lançamento do 8.0, [descrevemos o papel em declínio do TTI] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/v8-perf-faq.md#whats-the-story-with-tti) e hoje temos o acompanhamento. O Time to Interactive (TTI) não contribui mais para a pontuação de desempenho e não é exibido no relatório. Porém, ainda está acessível no resultado do Lighthouse JSON. Sem o TTI, a ponderação da Mudança Cumulativa de Layout (CLS) aumentou de 15% para 25%. Consulte a documentação para obter uma análise completa de como a pontuação de desempenho é calculada em 10.0 ou brincar com a calculadora de pontuação.

Tipos para o pacote Node

O Lighthouse agora inclui declarações de tipo! Nosso [exemplo de receita TypeScript] (https://github.com/GoogleChrome/lighthouse/tree/main/docs/recipes/type-checking) demonstra como obter a segurança de tipo adequada com o Lighthouse.

Classificação de entidade terceirizada

Desde o Lighthouse 5.3, o conjunto de dados third-party-web conduzido pela comunidade tem sido usado para resumir como cada terceiro encontrado em uma página contribui para o tempo total de bloqueio do JavaScript, por meio da auditoria third-party-summary. Com o Lighthouse 10.0, estamos adicionando uma nova propriedade ao resultado JSON (entities) para fazer uso adicional deste conjunto de dados. Cada origem encontrada em uma página agora é classificada como primária ou de terceiros dentro do entities. No 10.0, esta classificação é usada para alimentar a caixa de seleção de filtro de terceiros existente. Em uma versão futura do Lighthouse, isso será usado para agrupar os itens da tabela de cada auditoria com base na entidade de origem e agregar o impacto dos itens dessa entidade específica.

🆕 Novas auditorias

Cache de retrocesso/avançamento

O cache de retrocesso/avanço (abreviadamente bfcache) é uma otimização do navegador que fornece páginas de instantâneos totalmente serializados ao navegar para trás ou para frente no histórico da sessão. Existem mais de 100 razões diferentes pelas quais uma página pode não ser elegível para esta otimização, portanto, para ajudar os desenvolvedores, o Lighthouse agora tenta acionar uma resposta do bfcache e listará tudo o que impediu o navegador de usar o bfcache. #14465 Para obter mais informações sobre bfcache, consulte o artigo web.dev. Observação: esta auditoria inicialmente não estará disponível para PageSpeed ​​Insights.

Evitando colar em entradas

A auditoria password-inputs-can-be-pasted-into agora é paste-preventing-inputs. A lógica desta auditoria funciona como antes, mas em vez de considerar apenas as entradas [type=password], ela agora falha se qualquer elemento de entrada não somente leitura impedir o usuário de colar. #14313

A documentação do Lighthouse agora está em developer.chrome.com

Nossa documentação não está mais hospedada em web.dev. Para obter os documentos de auditoria mais atualizados, acesse developer.chrome.com/docs/lighthouse/

💥 Mudanças importantes

Nos bastidores, o Lighthouse agora usa a nova infraestrutura de suporte ao fluxo do usuário por padrão, mesmo para execuções de navegação tradicionais. Você pode cancelar isso: no CLI, use --legacy-navigation; no DevTools: marque “Navegação Legada” no menu de configurações. Se você tiver um caso de uso que exija essa saída de emergência, registre um problema. Planejamos remover esse caminho legado no 11.0.

Para usuários do resultado do farol JSON (LHR)

URLs de páginas no resultado do Lighthouse

Até agora, havia dois campos de URL para descrever uma execução do Lighthouse:

  • requestedUrl: o URL fornecido pelos usuários, para o qual o Lighthouse instrui o Chrome a navegar
  • finalUrl: o URL após qualquer redirecionamento iniciado por HTTP e JS iniciado pelo servidor Esta taxonomia não pode levar em conta cenários mais complexos, como redirecionamentos iniciados por JS, uso do Histórico API ou navegações suaves. Eles também estavam mal definidos para os modos intervalo de tempo e instantâneo. Para compensar isso, o Lighthouse 10.0 agora tem estes campos de URL:
  • (alterado) requestedUrl: A URL para a qual o Lighthouse navegou inicialmente antes dos redirecionamentos. É o mesmo que era antes para o modo de navegação, mas agora será undefined no intervalo de tempo/instantâneo.
  • (novo) mainDocumentUrl: URL do último documento solicitado durante uma navegação. Ele não leva em consideração navegações suaves ou eventos históricos API feitos após o carregamento da página. Está disponível apenas no modo de navegação e será indefinido nos modos intervalo de tempo e instantâneo.
  • (novo) finalDisplayedUrl: O URL exibido na caixa de combinação do navegador no final de uma execução do Lighthouse. Ele é responsável por navegações suaves e eventos históricos do API. Disponível nos modos de navegação, intervalo de tempo e instantâneo.
  • (obsoleto) finalUrl: Mesmo valor de mainDocumentUrl.

Alterações de auditoria

  • password-inputs-can-be-pasted-into -> paste-preventing-inputs
  • preload-lcp-image -> prioritize-lcp-image
  • third-party-summary não usa mais um valor link para item.entity, em vez disso usa um valor bruto text
  • full-page-screenshot não é mais uma auditoria, mas sim armazenado em lhr.fullPageScreenshot. Para suprimir a coleta da captura de tela de página inteira no CLI, você deve migrar de --skip-audits full-page-screenshot para --disable-full-page-screenshot.

Para usuários do Node

  • O Nó 14 não é mais suportado, o mínimo agora é o Nó 16
  • Caso você importe caminhos dentro do pacote do nó lighthouse: as pastas lighthouse-core/ e lighthouse-cli/ agora são simplesmente core/ e cli/
  • Convertido de módulos CommonJS para ES. Você ainda pode usar o lighthouse no CommonJS usando uma importação dinâmica: await import('lighthouse'). Para acessar apenas a função lighthouse no CommonJS, você também pode usar require('lighthouse/core/index.cjs')
  • A saída CSV do Lighthouse é muito mais útil agora. Consulte o PR para um exemplo do novo formato
  • LHError agora é LighthouseError. Se você estiver tentando detectar um erro gerado pelo Lighthouse, certifique-se de levar isso em consideração!

Mudanças no nó API

A função lighthouse agora tem melhor integração com o Puppeteer. Use lighthouse(url, flags, config, page) para executar o Lighthouse, passando um identificador Puppeteer.Page existente como page. O fluxo do usuário api foi movido para o ponto de entrada do nó de nível superior e pode ser importado com import {startFlow} from 'lighthouse'. As novas funções flow.startNavigation() e flow.endNavigation() permitem definir uma navegação acionada pelo usuário sem qualquer função de retorno de chamada. Consulte a documentação do fluxo do usuário para um exemplo. Para alterar as configurações para uma única etapa de fluxo do usuário, defina as substituições de configurações nas opções de sinalizadores de nível superior flow.snapshot({skipAduits: ['uses-http2']}) em vez de na propriedade settingsOverride. Para atribuir um nome personalizado a uma etapa de fluxo, use flow.snapshot({name: 'Custom name'}). Anteriormente isso era feito via stepName.

Para personalização do Lighthouse (configuração personalizada, coletores, auditorias)

  • Para trabalhar no Lighthouse 10.0, os coletores customizados precisarão implementar a nova interface Gatherer (um exemplo). Caso contrário, eles funcionarão apenas no [modo de navegação legado] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/configuration.md#using-legacy-configs-in-100) e em versões mais antigas do Lighthouse
  • O Lighthouse não pode mais usar passes para carregar a página várias vezes no modo de navegação. Se precisar carregar a página várias vezes, recomendamos usar um fluxo de usuário. Consulte nossos documentos de configuração para obter instruções sobre como converter para o novo formato de configuração
  • O artefato ScriptElements agora é Scripts, com um formato ligeiramente diferente
  • Audit.makeOpportunityDetails e Audit.makeTableDetails agora aceitam um objeto de opções como terceiro parâmetro. Isso acaba sendo uma mudança radical apenas para Audit.makeOpportunityDetails.
