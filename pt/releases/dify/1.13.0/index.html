#difícil 1.13.0

🚀 Novos recursos

Humano no Loop (HITL)

Estamos apresentando o nó Entrada Humana, uma grande atualização que transforma a forma como a IA e os humanos colaborar nos fluxos de trabalho do Dify.

Antecedentes

Anteriormente, os fluxos de trabalho eram binários: totalmente automatizados ou totalmente manuais. Isso criou uma "lacuna trust" em cenários de alto risco onde a velocidade da IA é necessária, mas o julgamento humano é essencial. Com HITL, estamos fazendo h supervisão humana, uma parte nativa da arquitetura do fluxo de trabalho, permitindo incorporar revise as etapas diretamente no gráfico de execução.

Principais capacidades

  • Pausa do fluxo de trabalho nativo: Insira um nó "Entrada humana" para suspender a execução do fluxo de trabalho em pontos de decisão críticos.
  • Revisar e editar: O nó gera uma UI onde os humanos podem revisar os resultados da IA ​​e modificar variáveis ​​(por exemplo, editar um rascunho ou corrigir dados) antes que o processo continue.
  • Roteamento baseado em ação: Configure botões personalizados (como "Aprovar", "Rejeitar" ou "Escalar") que determinam o caminho subsequente do fluxo de trabalho.
  • Métodos de entrega flexíveis: Os formulários de entrada humana podem ser entregues via Webapp ou E-mail. Em ambientes de nuvem, a disponibilidade de entrega de e-mail pode depender das configurações do plano/recurso.

🛠 Atualizações de arquitetura

Para oferecer suporte ao mecanismo de pausa/retomada com estado exigido pelo HITL e fornecer APIs de assinatura de eventos, refatoramos o mecanismo de execução: Execuções de streaming baseadas em fluxo de trabalho e execuções de bate-papo avançado agora são executadas em trabalhadores do Celery, enquanto execuções de WORKFLOW sem streaming ainda são executadas no processo API. Todos os caminhos de pausa/retomada (por exemplo, HITL) são retomados via Celery e os eventos são transmitidos de volta por meio do Redis Pub/Sub.

Para grandes implantações e usuários auto-hospedados:

Introduzimos uma nova fila do Celery chamada workflow_based_app_execution. Embora as configurações padrão funcionem imediatamente, os ambientes de alto rendimento devem considerar as seguintes otimizações para garantir estabilidade e desempenho:

  1. Escalar trabalhadores: ajuste o número de trabalhadores que consomem a fila workflow_based_app_execution com base na sua carga de trabalho específica.
  2. Redis dedicado (opcional): Para implantações em grande escala, recomendamos configurar a nova variável de ambiente PUBSUB_REDIS_URL para apontar para uma instância Redis dedicada. O uso do modo Redis Cluster com Sharded PubSub é altamente recomendado para garantir a escalabilidade horizontal.

⚠️ Nota importante sobre atualização

Nova fila de aipo necessária: workflow_based_app_execution

Certifique-se de que sua configuração de implantação (Docker Compose, Helm Chart, etc.) inclua trabalhadores ouvindo a nova fila workflow_based_app_execution.
Essa fila é necessária para execuções de streaming baseadas em fluxo de trabalho e todos os fluxos de retomada (por exemplo, HITL); caso contrário, as execuções de streaming e as tarefas de retomada não serão processadas.

🔧 Nota Operacional

Fila de aipo adicional: api_token

Se for ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK=true, certifique-se de que sua implantação também tenha trabalhadores ouvindo api_token. Essa fila é usada pela tarefa de atualização em lote agendada para carimbos de data/hora do token API last_used_at.

⚙️ Mudanças de configuração

Introduzimos diversas novas variáveis de ambiente para dar suporte às mudanças arquitetônicas. Grandes implantações devem prestar atenção especial às configurações do PubSub Redis para garantir escalabilidade.

  • PUBSUB_REDIS_URL (Crítico): especifica o URL Redis usado para comunicação PubSub entre os trabalhadores API e Celery. Se deixado em branco, o padrão é a configuração padrão do REDIS_*.
  • PUBSUB_REDIS_CHANNEL_TYPE (Crítico): Define o tipo de canal para eventos de streaming. As opções são pubsub (padrão) ou sharded. É altamente recomendável usar sharded para ambientes de alto rendimento.
  • PUBSUB_REDIS_USE_CLUSTERS (Crítico): Defina como true para ativar o modo de cluster Redis para PubSub. Combinado com o PubSub fragmentado, isso é essencial para o dimensionamento horizontal.

Outras adições:

  • WEB_FORM_SUBMIT_RATE_LIMIT_MAX_ATTEMPTS: Número máximo de envios de formulários web permitidos por IP dentro da janela de limite de taxa (Padrão: 30).
  • WEB_FORM_SUBMIT_RATE_LIMIT_WINDOW_SECONDS: Janela de tempo em segundos para limitação da taxa de envio de formulários web (Padrão: 60).
  • HUMAN_INPUT_GLOBAL_TIMEOUT_SECONDS: Máximo de segundos que uma execução de fluxo de trabalho pode permanecer pausada aguardando a entrada humana antes do tempo limite global (Padrão: 604800, 7 dias).
  • ENABLE_HUMAN_INPUT_TIMEOUT_TASK: Habilita a tarefa em segundo plano que verifica solicitações de entrada humana expiradas (Padrão: true).
  • HUMAN_INPUT_TIMEOUT_TASK_INTERVAL: Define o intervalo (em minutos) para a tarefa de verificação de timeout (Padrão: 1).
  • ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK: Ativa a tarefa periódica em segundo plano que atualiza em lote os carimbos de data e hora do token API last_used_at (Padrão: true).
  • API_TOKEN_LAST_USED_UPDATE_INTERVAL: Define o intervalo (em minutos) para atualização em lote dos carimbos de data e hora do token API last_used_at (Padrão: 30).
  • SANDBOX_EXPIRED_RECORDS_CLEAN_BATCH_MAX_INTERVAL: Atraso aleatório máximo (em milissegundos) entre lotes de limpeza de retenção para reduzir picos de pressão do banco de dados (Padrão: 200).

  • Estabilidade aprimorada de tarefas de grandes dados com sessões de banco de dados divididas, execução de limpeza em lote, ajuste de índice e otimização configurável entre lotes para trabalhos de limpeza de retenção.

  • Integração aprimorada da ferramenta MCP extraindo e relatando metadados de uso (por exemplo, campos de token/custo) de respostas MCP.

Segurança

  • Removida a avaliação dinâmica new Function da análise de ECharts e agora retorna erros de análise explícitos para código de gráfico não suportado.

Localização

Docker Compor implantações

  1. Faça backup de seu arquivo YAML composto por docker personalizado (opcional)

    cd docker
cp docker-compose.yaml docker-compose.yaml.$(date +%s).bak

  2. Obtenha o código mais recente da ramificação principal

    git checkout main
git pull origin main

  3. Pare o serviço. Por favor execute no diretório docker

    docker compose down

  4. Faça backup dos dados

    tar -cvf volumes-$(date +%s).tgz volumes

  5. Serviços de atualização

    docker compose up -d
