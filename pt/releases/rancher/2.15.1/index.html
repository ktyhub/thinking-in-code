#fazendeiro v2.15.1

Liberar v2.15.1

[!IMPORTANTE]

  • Se você estiver usando o AD FS (Serviço de Federação do Active Directory), a atualização para o Rancher v2.10.1 ou posterior poderá causar problemas de autenticação, exigindo intervenção manual. Esses problemas ocorrem porque a parte confiável Trust do AD FS não consegue obter um certificado de verificação de assinatura dos metadados. Para obter mais informações, consulte #48655. Esses problemas podem ser corrigidos por um dos dois métodos:

  • Atualizando as informações da Parte Confiante Trust dos metadados da federação (Parte Confiante Trust → Atualização dos Metadados da Federação…​).

  • Adicionar diretamente o certificado (Parte Confiável Trust → Propriedades → guia Assinatura → Adicionar → Selecionar o certificado).

Rancher v2.15.1 é o patch mais recente do Rancher. Este é um lançamento da versão comunitária que apresenta atualizações de manutenção e correções de bugs.

Para obter mais informações sobre novos recursos na versão secundária geral, consulte v2.15.0 release notes.

Correções de segurança para vulnerabilidades

Esta versão aborda os seguintes problemas de segurança:

Fazendeiro

  • Corrigida uma vulnerabilidade de segurança no manipulador de autenticação SAML do Rancher, onde a proteção de repetição de asserção era ineficaz em implantações de alta disponibilidade (múltiplas réplicas). Como cada réplica rastreada consumia IDs de asserção em um cache separado na memória, uma asserção SAML capturada poderia ser reproduzida em outras réplicas para criar sessões autenticadas adicionais como vítima. A correção rastreia IDs de asserção consumidos em todas as réplicas. Todos os provedores SAML foram afetados. Para obter mais informações, consulte CVE-2026-75034.
  • Corrige uma vulnerabilidade de segurança no secretsController com escopo do projeto Rancher, onde os segredos do projeto se propagam para namespaces com base apenas na anotação field.cattle.io/projectId sem validar que o projeto referenciado pertence ao mesmo cluster. Um usuário autenticado com permissões de criação de namespace em um cluster downstream poderia falsificar essa anotação para vazar segredos do projeto de um projeto não autorizado em um cluster diferente. O controlador agora valida se a anotação faz referência a um projeto dentro do mesmo cluster antes de propagar segredos. Para obter mais informações, consulte CVE-2026-75033.
  • Corrigida uma vulnerabilidade de segurança no token ext imperativo Rancher API (tokens ext.cattle.io/v1), onde qualquer usuário autenticado pode listar e observar os tokens de outros usuários, fornecendo um seletor de rótulo criado, divulgando metadados do token e o hash do token do portador armazenado. O armazenamento agora impõe o escopo por usuário incondicionalmente para que os chamadores vejam apenas seus próprios tokens e as respostas de leitura não retornem mais o hash do token armazenado. Para obter mais informações, consulte CVE-2026-75035.
  • Corrigida uma vulnerabilidade de segurança no controlador GlobalRole do Rancher, onde um usuário com permissões delegadas create ou update para recursos GlobalRole poderia definir a anotação authz.management.cattle.io/cr-name para direcionar um ClusterRole existente arbitrário (como o cluster-admin integrado). O controlador então sobrescreve as regras sem uma verificação de propriedade, removendo permissões de todos os principais vinculados e causando um bloqueio RBAC persistente em todo o cluster no cluster de gerenciamento local. Para obter mais informações, consulte CVE-2026-71404.
  • Corrigida uma vulnerabilidade de segurança no SUSE Rancher Norman /v3/users API em que o caminho de atualização não impunha a imutabilidade dos campos username, principalIds e displayName em um recurso User. Um chamador com permissões update em users poderia religar a identidade principal externa de um usuário, permitindo o controle da conta durante o próximo login externo ou criando uma condição de negação de serviço que deixava as ligações de função existentes inacessíveis. As camadas de armazenamento API e webhook de admissão foram atualizadas para rejeitar alterações pós-criação nesses campos de identidade. Para obter mais informações, consulte CVE-2026-71403.

Frota

  • Corrigida uma vulnerabilidade de segurança no pré-processamento de modelos Helm do Fleet, onde os modelos avaliados pelo controlador do Fleet poderiam alcançar recursos da rede. Um usuário que pode fornecer conteúdo do pacote untrusted pode expor metadados de cluster e informações sobre hosts acessíveis a partir do controlador. O Fleet agora rejeita pacotes cujos valores de modelo do Helm exigem acesso à rede, relatando um erro para o GitRepo correspondente. Para obter mais informações, consulte CVE-2026-75036.
  • Corrigida uma vulnerabilidade de segurança no Fleet onde rótulos de cluster fornecidos por um agente durante o registro de cluster iniciado pelo agente eram aplicados ao objeto Cluster resultante, incluindo rótulos management.cattle.io/ reservados usados ​​para direcionamento de pacote. Em implantações em que vários domínios trust compartilham um namespace de espaço de trabalho Fleet, isso permitiu que um cluster de registro correspondesse aos destinos Bundle ou GitRepo de outro locatário e recebesse os manifestos e segredos de valores resolvidos desse locatário. O Fleet agora descarta rótulos reservados fornecidos no registro iniciado pelo agente. As implantações autônomas do Rancher não são afetadas em sua configuração padrão, pois o Rancher usa o registro iniciado pelo gerente. Para obter mais informações, consulte CVE-2026-93538.
  • Corrigida uma vulnerabilidade de segurança no Fleet onde rótulos de namespace e anotações solicitadas por um pacote por meio de namespaceLabels e namespaceAnnotations eram aplicadas sem a autorização da conta de serviço à qual o pacote estava fixado. Em implantações multilocatários, isso permitiu que um pacote modificasse metadados de namespace que sua própria identidade não tinha permissão para alterar. A atualização do namespace agora é executada como a conta de serviço da implantação e é governada pelo RBAC Kubernetes downstream. Para obter mais informações, consulte CVE-2026-93540.

Provisionamento K3s e RKE2

Problemas conhecidos

  • Existe um problema conhecido relacionado aos provedores de infraestrutura CAPI dentro da estrutura de provisionamento V2 do Rancher. A criação ou edição de clusters v2prov com provedores de infraestrutura nativa (como CAPA ou CAPV) a partir da UI pode, sob algumas condições de falha, deixar recursos de infraestrutura órfãos e não utilizados (por exemplo, AWSMachineTemplate ou AWSCluster) no cluster de gerenciamento que precisam ser limpos manualmente. Consulte #55752.

Notas de instalação/atualização

Se você estiver instalando o Rancher pela primeira vez, seu ambiente deverá atender aos requisitos de instalação.

[!IMPORTANTE]

  • O Rancher agora exige que o cluster em que ele é executado tenha a Camada de agregação Kubernetes API habilitada. Isso ocorre porque o Rancher estende Kubernetes com APIs adicionais registrando seu próprio servidor de extensão API. Observe que todas as versões do Kubernetes suportadas nestas distribuições K8s das versões Rancher (RKE2/K3s) terão a camada de agregação configurada e habilitada por padrão.

  • Consulte a documentação do servidor de extensão API e #50400 para obter mais informações.

  • O motor Rancher Kubernetes (RKE/RKE1) atingiu o fim de sua vida útil em 31 de julho de 2025. As versões Rancher 2.12.0 e posteriores não suportam mais o provisionamento ou o gerenciamento de clusters RKE1 downstream. Recomendamos a replataforma de clusters RKE1 para RKE2 para garantir suporte contínuo e atualizações de segurança. Saiba mais sobre a transição aqui.

  • O Rancher agora tem uma verificação de validação de pré-atualização para recursos RKE1 que falha e lista os recursos RKE1, se presentes. Consulte #50286 para obter mais informações.

  • É crucial que você revise o espaço em disco disponível em seus nós e planeje adequadamente antes de atualizar para o Rancher v2.12.0 e posteriormente para evitar possíveis problemas de pressão de disco e de despejo de pod.

  • Para obter informações adicionais, consulte a documentação UI Server Side Pagination - Disk Space.

  • O Rancher agora tem uma opção de ativação chamada AUDIT_LOG_ENABLED para registros de auditoria API para uma instalação do Rancher.

  • Nas versões Rancher 2.11.x e anteriores, apenas o AUDIT_LEVEL poderia ser definido e o nível de log padrão (0) desabilitaria o log de auditoria. Nas versões Rancher 2.12.x e posteriores, o nível de log padrão (0) agora contém apenas a solicitação de log e os metadados de resposta e pode ser definido ao configurar AUDIT_LOG_ENABLED. Se estiver instalando ou atualizando via Helm, você pode ativar os logs de auditoria API e especificar o nível de log aplicando a seguinte configuração ao comando do Helm: --set auditLog.enabled=true --set auditLog.level=0. Consulte a documentação Ativando o log de auditoria do API para registrar eventos do sistema e #48941.

Mudanças em artefatos de imagem

Os resumos de artefatos de imagem foram renomeados em Rancher v2.12.0, v2.11.4 e v2.10.8. Até essa mudança, arquivos de resumo de imagem separados para cada sistema operacional e arquitetura eram mantidos por motivos de compatibilidade. Com esta alteração, apenas um arquivo para cada sistema operacional deverá ser fornecido:

  • Os arquivos rancher-images-digests-linux-amd64.txt e rancher-images-digests-linux-arm64.txt devem ser renomeados para rancher-images-digests-linux.txt.

  • Os arquivos rancher-images-digests-windows-ltsc2019.txt e rancher-images-digests-windows-ltsc2022.txt devem ser renomeados para rancher-images-digests-windows.txt.

Requisitos de atualização

  • Criando backups: Crie um backup antes de atualizar o Rancher. Para reverter o Rancher após uma atualização, você deve primeiro fazer backup e restaurar o Rancher para a versão anterior do Rancher. Como o Rancher será restaurado para o mesmo estado de quando o backup foi criado, quaisquer alterações pós-atualização não serão incluídas após a restauração.

  • Requisitos da versão do Helm:

    • Para gerenciar o Rancher 2.12.x e posterior, você deve atualizar seu Helm client para a versão 3.18 ou mais recente.

    • Esta alteração é necessária para refletir a adição de suporte Kubernetes 1.33 nesta versão.

    • Atualmente, a Política de Suporte à Versão do Helm oficial determina que apenas o Helm 3.18 suporta o intervalo de versões Kubernetes adequado para o Rancher 2.12.

  • Requisitos CNI:

  • Para Kubernetes v1.19 e posterior, desative o firewalld, pois é incompatível com vários plug-ins CNI. Consulte #28840.

    • Ao atualizar ou instalar uma distribuição Linux que usa nf_tables como filtro de pacotes de back-end, como SLES 15, RHEL 8, Ubuntu 20.10, Debian 10 ou posterior, atualize para RKE v1.19.2 ou posterior para obter Flannel v0.13.0. Flanela v0.13.0 suporta nf_tables. Consulte Flanela #1317.

  • Requisitos para ambientes isolados:

    • Ao usar um proxy na frente de uma instância do Rancher sem ar, você deve passar parâmetros adicionais para NO_PROXY. Consulte a documentação e a edição #2725.

    • Ao instalar o Rancher com Docker em um ambiente air gap, você deve fornecer um arquivo registries.yaml customizado para o comando docker run, conforme mostrado na documentação do K3s. Se o registro tiver certificados, você também precisará fornecê-los. Consulte #28969.

Versões do gráfico do leme do Rancher

No Rancher v2.6.0 e versões posteriores, na IU de Apps e Marketplace, muitos gráficos do Rancher Helm são nomeados com uma versão principal que começa com 100. Isso evita que alterações simultâneas no upstream e alterações no Rancher causem incrementos de versão conflitantes. Isso também está em conformidade com o versionamento semântico (SemVer), que é um requisito do Helm. Você pode ver o número da versão upstream de um gráfico nos metadados de construção, por exemplo: 100.0.0+up2.1.0. Consulte #32294.

Mudanças anteriores no comportamento do fazendeiro

Mudanças anteriores no comportamento do fazendeiro - Rancher General

  • Fazendeiro v2.15.0:

    • Rancher v2.15 remove suporte para Kubernetes v1.33. Consulte #55306.

Mudanças anteriores no comportamento do Rancher - Aplicativo Rancher (IU global)

  • Fazendeiro v2.15.0:

    • A opção de desabilitar o sinalizador de recurso ui-sql-cache / Vai / Server-Side Pagination (SSP) na UI do Rancher foi removida em preparação para o Rancher v2.16, onde o recurso estará sempre habilitado. Consulte #16822.

    • Remoção: O suporte para plug-ins de UI baseados em Ember para drivers de cluster e nó (obsoleto desde o Rancher v2.11.0) foi removido no Rancher v2.15.0. Migre seus plug-ins para o UI Extensions Framework. Para obter detalhes, consulte #14005.

Mudanças anteriores no comportamento do fazendeiro - Provisão K3s e RKE2

  • Fazendeiro v2.15.0:

    • Por padrão, as permissões globais Standard User e Create Clusters agora permitem criar e atualizar objetos de infraestrutura CAPI no namespace fleet-default. Observe que os objetos de identidade do provedor de infraestrutura criados manualmente, como AWSClusterStaticIdentity ou VSphereClusterIdentity, que têm como destino o namespace fleet-default podem ser usados ​​por meio de objetos de infraestrutura CAPI, como AWSCluster ou VsphereCluster. Consulte #53777.

    • Ao usar provedores de infraestrutura CAPI nativos com v2prov, o Rancher agora gerará o bootstrap cloud-config no formato Jinja. Os dados do usuário para drivers de nó regulares com v2prov não são afetados. Consulte #53777.

Mudanças anteriores no comportamento do fazendeiro - Entrega contínua (frota)

  • Fazendeiro v2.15.0:

  • Descontinuação: o Fleet removerá o suporte para GitRepoRestriction em uma versão futura, tornando o uso do recurso Policy para configuração de ambientes multilocatários a única opção. Consulte #55652.

    • Descontinuação: o suporte de frota para chamadas de webhook não autenticadas será removido em uma versão futura, tornando a configuração de um segredo de webhook a única opção. Consulte #55633.

Problemas conhecidos de longa data

Problemas conhecidos de longa data – Rancher General

  • Fazendeiro v2.15.0:

  • Existe um problema conhecido com clusters Rancher v2.15.0 e Kubernetes v1.36 em que Rancher Backups não está listado em Cluster Tools devido a um problema no gráfico de backups. Consulte #1055.

Problemas conhecidos de longa data: provisionamento de cluster

  • Nem todas as ferramentas de cluster podem ser instaladas em um cluster protegido.

  • Fazendeiro v2.8.1:

    • Quando você tenta registrar um novo nó etcd/controlplane em um cluster gerenciado por CAPR após uma falha na restauração do instantâneo etcd, o nó pode ficar preso em um estado de pausa perpétua, exibindo a mensagem de erro [ERROR] 000 received while downloading Rancher connection information. Sleeping for 5 seconds and trying again. Como solução alternativa, você pode retomar o cluster executando kubectl edit clusters.cluster clustername -n fleet-default e configurando spec.unpaused como false. Consulte #43735.

Problemas conhecidos de longa data - Provisionamento RKE2

  • Fazendeiro v2.7.7:

    • Devido à lógica de espera em vários componentes, os clusters K3s e RKE2 provisionados downstream podem levar mais tempo para recuperar o status Ativo após uma migração. Se você perceber que um cluster downstream ainda está sendo atualizado ou em estado de erro imediatamente após uma migração, deixe-o tentar se resolver sozinho. Isso pode levar até uma hora para ser concluído. Consulte #34518 e #42834.

  • Fazendeiro v2.7.6:

    • O provisionamento de clusters RKE2/K3s com drivers de nó personalizados adicionados (não integrados) causa falha no provisionamento. Como solução alternativa, corrija os drivers de nó adicionados após a ativação. Consulte #37074.

Problemas conhecidos de longa data - Provisionamento de K3s

  • Fazendeiro v2.7.6:

    • O provisionamento de clusters RKE2/K3s com drivers de nó personalizados adicionados (não integrados) causa falha no provisionamento. Como solução alternativa, corrija os drivers de nó adicionados após a ativação. Consulte #37074.

  • Fazendeiro v2.7.2:

    • Os clusters permanecem no estado Updating mesmo quando contêm nós no estado Error. Consulte #39164.

Problemas conhecidos de longa data - Aplicativo Rancher (IU global)

  • Fazendeiro v2.10.0:

    • Depois de excluir um Namespace ou Projeto na UI do Rancher, o Namespace ou Projeto permanece visível. Como solução alternativa, atualize a página. Consulte #12220.

  • Fazendeiro v2.9.2:

    • Embora os pools de nós do modo de sistema devam ter pelo menos um nó, a IU do Rancher permite uma contagem mínima de nós igual a zero. Inserir uma contagem mínima de nós zero por meio da IU pode causar falha na criação do cluster devido a um erro de parâmetro inválido. Para evitar que esse erro ocorra, insira uma contagem mínima de nós pelo menos igual à contagem de nós. Consulte #11922.

  • Fazendeiro v2.7.7:

    • Ao criar um cluster na UI do Rancher não é permitido o uso do sublinhado _ no campo Cluster Name. Consulte #9416.

  • Fazendeiro v2.6.4:

    • A seção securityContext de implantação está ausente quando uma nova carga de trabalho é criada. Isso evita que os pods sejam iniciados quando o suporte à política de segurança do pod estiver ativado. Consulte #4815.

Problemas conhecidos de longa data - EKS

  • Fazendeiro v2.7.0:

    • Clusters EKS em Kubernetes v1.21 ou inferiores em Rancher v2.7 não podem ser atualizados. Consulte #39392.

Problemas conhecidos de longa data – Autenticação

  • Fazendeiro v2.9.0:

    • Existem alguns problemas conhecidos com o suporte do provedor OpenID Connect:

      • Quando o provedor de autenticação OIDC genérico está habilitado e você tenta adicionar usuários do provedor de autenticação a um cluster ou projeto, os usuários não são preenchidos na barra de pesquisa suspensa. Este é o comportamento esperado, pois o provedor de autenticação OIDC sozinho não é pesquisável. Consulte #46104.

      • Quando o provedor de autenticação OIDC genérico está habilitado, os usuários do provedor de autenticação que são adicionados a um cluster/projeto por seu nome de usuário não são capazes de acessar recursos ao efetuar login. Um usuário só terá acesso aos recursos após o login se o usuário for adicionado por seu ID de usuário. Consulte #46105.

      • Quando o provedor de autenticação OIDC genérico estiver habilitado e um usuário do provedor de autenticação em um grupo aninhado estiver conectado ao Rancher, o usuário verá o seguinte erro ao tentar criar um projeto: projectroletemplatebindings.management.cattle.io is forbidden: User "u-gcxatwsnku" cannot create resource "projectroletemplatebindings" in API group "management.cattle.io" in the namespace "p-9t5pg". No entanto, o projeto ainda está criado. Consulte #46106.

Problemas conhecidos de longa data - Rancher Webhook

  • Fazendeiro v2.7.2:

    • Um webhook está instalado em todos os clusters downstream. Existem vários problemas que os usuários podem encontrar com esta funcionalidade:

      • Se você reverter de uma versão do Rancher v2.7.2 ou posterior para uma versão do Rancher anterior a v2.7.2, os webhooks permanecerão em clusters downstream. Como o webhook foi projetado para ser compatível 1:1 com versões específicas do Rancher, isso pode causar comportamentos inesperados no downstream. A equipe do Rancher desenvolveu um script que deve ser usado após a conclusão da reversão (ou seja, após uma versão do Rancher anterior à v2.7.2 estar em execução). Isso remove o webhook dos clusters downstream afetados. Consulte #40816.

Problemas conhecidos de longa data - Gerenciamento de virtualização (Harvester)

  • Fazendeiro v2.13.1:

    • Ao atualizar para o Rancher v2.13.1 ou superior ao usar o Harvester v1.6.1, os usuários podem encontrar um problema com seus balanceadores de carga em clusters downstream usando o Harvester Cloud Provider e devem executar a seguinte solução alternativa para instruir o Calico a não usar nenhum IP/interface gerenciado pelo kube-vip. Consulte #9767.

  • Fazendeiro v2.7.2:

    • Se estiver usando o Rancher v2.7.2 com clusters Harvester v1.1.1, você não poderá selecionar o provedor de nuvem Harvester ao implantar ou atualizar clusters convidados. Os Harvester release notes contêm instruções sobre como resolver isso. Consulte #3750.

Problemas conhecidos de longa data - Backup/Restauração

  • Ao migrar para um cluster com o recurso Rancher Backup, a URL do servidor não pode ser alterada para um local diferente. Deve continuar a usar o mesmo URL.

  • Fazendeiro v2.13.0:

    • Ao executar uma reversão do Rancher v2.13.0 para v2.12.3 usando o operador de backup e restauração (BRO), a restauração não é concluída com êxito. Consulte #844. Para contornar esse problema, você deve reduzir a implantação do Rancher e desinstalar o gráfico Webhook antes de executar a restauração. Para obter detalhes, consulte este artigo da Base de Conhecimento.

  • Fazendeiro v2.7.7:

  • Devido à lógica de espera em vários componentes, os clusters K3s e RKE2 provisionados downstream podem levar mais tempo para recuperar o status Ativo após uma migração. Se você perceber que um cluster downstream ainda está sendo atualizado ou em estado de erro imediatamente após uma migração, deixe-o tentar se resolver sozinho. Isso pode levar até uma hora para ser concluído. Consulte #34518 e #42834.
