codebase-memory-mcp v0.12.1

#v0.12.1

Cada caminho de instalação funciona novamente e os gráficos do Helm se juntam ao gráfico.

v0.12.1 corrige as instalações de pacotes do v0.12.0 e os outros caminhos de instalação que encontramos quebrados ao verificar cada canal. Ele também vincula os gráficos do Helm ao que eles implantam e impede que o gráfico invente um registro para imagens de contêiner.

Atualizando? O primeiro índice de cada projeto existente após a atualização é uma reconstrução completa, uma vez (identidades de imagem alteradas; veja abaixo).

Corrigido: instalações

  • instalações npm, PyPI e Go. npm i, pnpm add, pip install e o wrapper Go não puderam instalar v0.12.0 em nenhuma plataforma. Cada wrapper recusou um membro do arquivo acima de 256 MiB e cada binário v0.12.0 tem 331-335 MB. Os limites de tamanho desapareceram de todos os três invólucros. O arquivo ainda é verificado em relação ao checksums.txt da versão antes de ser descompactado, seu conteúdo deve ser exatamente os arquivos esperados e o binário deve responder --version. Obrigado, @hydroplexus, pelo relatório preciso (#2657).
  • Homebrew. A fórmula ainda estava em 0.10.3, e no Linux instalou a compilação vinculada dinamicamente, que precisa de glibc 2.38 (Ubuntu 22.04, Debian 12 e RHEL 9 não possuem). Agora ele instala a versão atual e, no Linux, a compilação estática -portable que roda em qualquer distribuição.
  • go install. Um go install .../pkg/go/cmd/codebase-memory-mcp@vX.Y.Z fixado nunca funcionou e @latest instalou uma versão obsoleta. As versões agora carregam tags pkg/go/vX.Y.Z e o wrapper instala a versão correspondente à sua própria versão.
  • npm next. A tag dist next não aponta mais para um release candidate antigo; uma versão estável o move.
  • Docs. winget e Chocolatey foram listados como canais de instalação, mas não foram publicados; eles são removidos até que sejam. As compilações do Windows arm64 são enviadas e agora estão listadas.

Testes de fumaça do caminho de instalação. Cada solicitação pull e cada versão agora instala os wrappers npm, PyPI e Go, da mesma forma que o gerenciador de pacotes do usuário, nos arquivos de lançamento reais, e executa o binário de cada um instalado. Uma versão é publicada somente depois que essas instalações são concluídas, portanto, um instalador que não consegue instalar o que enviamos não poderá mais entrar em contato com você.

Gráficos Helm no gráfico

Um gráfico Helm costumava ser um nó isolado. Agora ele está vinculado ao que ele implanta (#2663):

  • Gráfico → objetos (DEPLOYS, via: chart): todo objeto Kubernetes renderizado a partir do templates/ do gráfico (os objetos de um subgráfico pertencem ao subgráfico).
  • arquivo de valores → Gráfico (CONFIGURES): values.yaml e values-<x>.yaml ao lado de Chart.yaml.
  • Gráfico → imagens (DEPLOYS, ref: image): cada imagem tem seu nome de objeto literalmente (uma imagem modelo não nomeia nenhum).

HelmRelease → Chart → Deployment → Image agora é um caminho percorrível. Em 20 repositórios de infraestrutura, gráficos sem borda de saída caíram de 238 de 260 para 109, e apareceram 2.511 links gráfico-objeto; todas as outras arestas permaneceram idênticas.

As imagens mantêm no registro os codinomes

Uma imagem sem um host de registro costumava ser armazenada em um docker.io/library/... inventado (#2654). Docker Hub é apenas o padrão do Docker: Podman e CRI-O resolvem nomes curtos por meio de uma lista de pesquisa, os espelhos os reescrevem e uma tag de construção local pode não existir em nenhum registro. Uma imagem agora mantém seu nome como está escrito, com registry: unknown quando nenhum host é informado; um host declarado é mantido (a grafia do Hub Docker passa a ser docker.io). FROM nginx e image: docker.io/library/nginx agora são dois nós de imagem. Isso altera as identidades das imagens, e é por isso que cada projeto é reconstruído uma vez após a atualização.

Notas de atualização

  • O primeiro índice de cada projeto existente após a atualização é uma reconstrução completa, uma vez.
  • Os nós de imagem sem registro declarado agora carregam registry: unknown e o nome conforme escrito, em vez de docker.io/library/....
