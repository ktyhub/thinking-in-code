Ce qui a changé

Nouvelles fonctionnalités

Outil de saisie à sélection multiple

  • Les nœuds de l'outil Workflow prennent désormais en charge les entrées déroulantes à sélection multiple, permettant aux utilisateurs de choisir plusieurs valeurs dans une liste prédéfinie lors de la configuration des paramètres de l'outil. (#39346)

Localisateur de nœuds de flux de travail

  • Vous pouvez désormais click un node_id dans les journaux d'exécution du workflow ou les messages d'erreur pour localiser et mettre en surbrillance le nœud correspondant dans le canevas de l'éditeur de workflow. (#38187)

Améliorations du sélecteur de blocs de workflow

  • Le panneau de sélection de blocs propose désormais une navigation au clavier améliorée, des aperçus de catégories et une expérience de recherche plus intuitive lors de l'ajout de nœuds aux flux de travail. (#39212)

Exporter l'agent DSL depuis la barre latérale

  • Les applications d'agent peuvent désormais être exportées au format DSL YAML directement à partir du menu de la barre latérale de l'application, ce qui facilite la sauvegarde ou le contrôle de version des configurations d'agent. (#39299)

Traçage des connaissances

  • Ajout de plus de traces d'observabilité aux opérations de traitement des documents Knowledge/RAG, améliorant ainsi la visibilité sur les pipelines d'indexation. (#38959)

Améliorations de la sécurité

  • Le sandbox local de l'agent s'exécute désormais derrière un proxy de transfert Squid dédié avec des règles ACL strictes, empêchant le sandbox d'atteindre directement les services internes. Seuls les points de terminaison /files/ sur API et /agent-stub/ sur agent_backend sont autorisés, tous deux protégés par des jetons d'accès de courte durée. Cela réduit considérablement le rayon d’action de l’exécution de code arbitraire dans le bac à sable de l’agent. (#39544)
  • La communication entre le Dify API et le backend de l'agent utilise désormais l'authentification basée sur des jetons via DIFY_AGENT_API_TOKEN / AGENT_BACKEND_API_TOKEN, renforçant ainsi les limites du service interne. (#39622)
  • Changement du rendu du modèle Jinja2 pour utiliser SandboxedEnvironment, empêchant les attaques par injection de modèle dans les nœuds de code de workflow (#39609)
  • Vulnérabilité DoS des composants du serveur React corrigée (# 39539)
  • Utilisation de re.fullmatch dans le validateur de courrier électronique pour rejeter les nouvelles lignes de fin, empêchant ainsi les attaques de contournement (#39320)
  • Statut du compte validé avant d'accepter les invitations à l'espace de travail (# 39438)

Nouvelles variables

| Variables | Par défaut | Descriptif | |--------------|---------|-------------| | DIFY_AGENT_API_TOKEN | dify-agent-run-token-for-dev-only | Jeton de porteur partagé pour API → authentification agent_backend. Modifiez cela en production. | | AGENT_BACKEND_API_TOKEN | dify-agent-run-token-for-dev-only | Même jeton côté backend de l’agent. Doit correspondre à DIFY_AGENT_API_TOKEN. | | PLUGIN_MODEL_PROVIDERS_CACHE_ENABLED | true | Définissez sur false si les plugins sont installés en externe et que le cache ne peut pas être invalidé. |

[!IMPORTANT] DIFY_AGENT_API_TOKEN est une nouvelle variable obligatoire pour une communication sécurisée entre le Dify API et le backend de l'agent. La valeur par défaut (dify-agent-run-token-for-dev-only) n'est pas sécurisée et doit être remplacée en production. Générez-en un avec :

python -c 'import secrets; print(secrets.token_urlsafe(32))'

Définissez la même valeur que AGENT_BACKEND_API_TOKEN côté backend de l'agent.

Guide de mise à niveau

Migration des types de modèles

[!IMPORTANT]

Migration unique du type de modèle hérité pour les mises à niveau auto-hébergées

Si ce déploiement a été mis à niveau à partir d'une version de Dify antérieure à 1.15.0 et que cette migration n'a pas déjà été appliquée, exécutez-la après la mise à niveau.

Cette migration n'est pas incluse dans flask db upgrade. Sans cela, les enregistrements de modèles existants peuvent entraîner l'échec des requêtes API liées au modèle avec des erreurs, empêchant ainsi le chargement ou l'utilisation des modèles concernés.

Sauvegardez la base de données avant d'appliquer la migration. La commande s'exécute en mode d'exécution à sec par défaut ; examinez la sortie avant de la réexécuter avec --apply. La migration est idempotente et peut être réexécutée en toute sécurité.

Docker Composer

Exécuté à partir du répertoire docker.

# Apply after reviewing the dry-run output
docker compose exec -T api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Déploiement du code source

Exécutez à partir de la racine du référentiel après avoir terminé flask db upgrade.

# Apply after reviewing the dry-run output
uv run --project api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Après avoir appliqué la migration, exécutez à nouveau la commande d'exécution à sec. S'il ne signale aucune mise à jour ou suppression de lignes supplémentaires, redémarrez les services concernés et vérifiez que les modèles existants peuvent être chargés et appelés avec succès.

Docker Composer (recommandé)

cd docker
docker compose down
git pull origin main
docker compose pull
docker compose up -d

Les migrations de bases de données s'exécuteront automatiquement au démarrage.

[!IMPORTANT] Vérifiez la nouvelle variable DIFY_AGENT_API_TOKEN dans .env. La valeur par défaut est non sécurisée : générez un jeton sécurisé pour la production :

python -c 'import secrets; print(secrets.token_urlsafe(32))'
