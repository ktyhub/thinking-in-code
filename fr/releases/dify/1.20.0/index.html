dify 1.20.0

Mineure Publié18 nov. 2026 Sourcelanggenius/dify Anglais original

Cette page est traduite automatiquement. Le texte anglais original fait foi.

modifier 1.20.0

Dify 1.20.0 assure la fluidité de vos traces et la sécurité de vos bases de connaissances. Exportez les traces vers n'importe quel collecteur OpenTelemetry, laissez Langfuse fonctionner après le retrait de son ancien point de terminaison d'ingestion et analysez les fichiers de connaissances téléchargés à la recherche de logiciels malveillants avant qu'ils ne soient indexés. Les chatflows peuvent afficher l'activité de l'outil Agent au fur et à mesure, et les jetons d'accès personnels permettent aux scripts et aux agents d'appeler le Dify OpenAPI en votre nom. Le démon du plugin fourni est mis à niveau vers 0.6.15-local. Nouvelles fonctionnalités · Modifications de configuration et d'intégration · Migrations de bases de données · Guide de mise à niveau

Nouvelles fonctionnalités

Nouveau HITL : intégrez les approbations dans les outils de messagerie de votre équipe

Intégrez la révision humaine dans vos flux de travail par e-mail et les outils de messagerie que votre équipe utilise déjà. Le nouveau HITL introduit des canaux partagés, des contacts centralisés, des modèles de notification et des formulaires d'approbation vérifiés, permettant à votre équipe de configurer les destinataires une seule fois et de les réutiliser sur les nœuds de saisie humaine, et est désormais activé par défaut (NEXT_PUBLIC_ENABLE_HITL_IM=true). (#44864, #45945)

  • Atteignez les approbateurs là où ils travaillent. Configurez la messagerie électronique et une plateforme de messagerie instantanée (Slack, Feishu/Lark, Microsoft Teams, DingTalk ou WeCom) pour envoyer des demandes de révision de flux de travail via les canaux existants de votre équipe.
  • Gérez les destinataires dans Contacts. Synchronisez les répertoires de messagerie instantanée et sélectionnez les approbateurs dans une liste de contacts partagée. Les workflows peuvent également s'adresser à l'initiateur ou utiliser des destinataires de courrier électronique uniques et dynamiques.
  • Approuver dans des cartes ou des formulaires. Les destinataires peuvent examiner les demandes directement dans les cartes de messagerie instantanée prises en charge ou ouvrir des formulaires autonomes, avec une connexion Dify ou une vérification par e-mail pour vérifier leur identité.
  • Personnalisez les notifications avec le contexte du workflow. Utilisez des modèles et des variables de workflow pour inclure le contexte essentiel dans les sujets et les corps des notifications.
  • Testez et suivez la livraison. Envoyez des notifications de test pour vérifier votre configuration et inspectez les enregistrements de livraison pour résoudre les demandes qui ne sont pas arrivées comme prévu.
  • Adoptez le nouveau HITL dans les flux de travail existants. Utilisez la migration volontaire pour mettre à niveau les anciens nœuds de saisie humaine lorsque votre flux de travail est prêt. Les exigences de déploiement sont répertoriées sous [Modifications de configuration et d'intégration] (#user-content-configuration-and-integration-changes).

Exporter les traces vers n'importe quel collecteur OpenTelemetry

Intégrez les traces d'exécution de Dify dans votre pile d'observabilité existante. Le nouveau fournisseur OpenTelemetry exporte les traces des applications et des agents vers n'importe quel collecteur compatible, vous permettant ainsi de suivre ensemble les étapes du flux de travail, les appels de modèle et l'activité des outils sur votre plateforme préférée. Utilisez ces traces pour inspecter l'exécution des requêtes et diagnostiquer les échecs sans nécessiter une intégration Dify spécifique au fournisseur. (#45659) Le traçage Langfuse prend désormais en charge Langfuse v4 et le service d'ingestion Langfuse Cloud actuel. Les configurations Langfuse existantes continuent de fonctionner. (#45606)

[!IMPORTANT] Langfuse Cloud a retiré son ancien point de terminaison d'ingestion le 16 novembre 2026, et Langfuse v4 auto-hébergé rejette les événements qui lui sont envoyés. Passez à 1.20.0 pour continuer à fournir des traces à ces déploiements.

Analyser les téléchargements de connaissances à la recherche de logiciels malveillants

Protégez vos bases de connaissances en analysant les fichiers téléchargés à la recherche de logiciels malveillants avant qu'ils ne soient extraits ou indexés. Lorsqu'il est activé (FILE_SCAN_ENABLED=true), les propriétaires et les administrateurs de l'espace de travail peuvent configurer les analyseurs une fois sous Intégrations → Analyse de sécurité des fichiers, puis définir la manière dont chaque base de connaissances les utilise. Les scanners pris en charge incluent Cloudmersive, Scanii, OPSWAT MetaDefender Cloud et un Custom Endpoint. (#46090, #46492)

  • Choisissez la protection par base de connaissances. Sélectionnez un scanner et configurez le comportement de secours lorsque l'analyse n'est pas disponible ou qu'un fichier ne peut pas être analysé.
  • Protégez les téléchargements de connaissances dans Dify. L'analyse couvre les bases de connaissances classiques, les sources de fichiers locaux du pipeline RAG et les téléchargements de la base de connaissances des agents.
  • Découvrez pourquoi les fichiers ont été bloqués. Les échecs d'analyse apparaissent dans la liste des documents pour examen.

Les outils Watch Agent fonctionnent dans Chatflow

Lorsqu'un Chatflow délègue des tâches à un nœud Agent v2 (nécessite NEXT_PUBLIC_ENABLE_AGENT_V2_IN_CHATFLOW=true), les utilisateurs peuvent désormais voir quels outils il appelle en temps réel. L'activité de l'outil apparaît à côté de la réponse dans les aperçus et les discussions publiées, ce qui facilite le suivi de la progression de l'agent. Développez n’importe quelle fiche outil pour inspecter ce qu’elle a demandé et renvoyé. (#46220)

Automatisez les appels OpenAPI avec des jetons d'accès personnels

Accordez aux scripts, aux tâches CI et aux agents personnels l'accès au Dify OpenAPI en votre nom sans partager votre session de console. Créez un jeton d'accès personnel à partir de votre page Compte et étendez-le à des espaces de travail et à des ressources spécifiques. Vous pouvez définir une date d'expiration facultative, mettre à jour sa portée à mesure que votre automatisation évolue ou la révoquer lorsqu'elle n'est plus nécessaire. (#45540, #46606)

Choisissez les sources de connaissances GitHub dans une arborescence

Parcourez et sélectionnez le contenu GitHub que vous souhaitez ajouter à une base de connaissances à partir d'une arborescence extensible de référentiels, de répertoires, de problèmes et de demandes d'extraction. Explorez la structure source et choisissez les pages exactes à importer, que vous créiez une nouvelle base de connaissances ou que vous ajoutiez une source à une source existante. (#45990)

Recherchez et naviguez sur des écrans plus petits

Effectuez des recherches dans le contenu et affinez les résultats à l'aide de champs d'application sélectionnables dans Goto Anything. Sur les écrans plus petits, la recherche et la navigation s'ouvrent dans des tiroirs pour préserver l'espace pour la page en cours. (#45675, #45650) Les liens directs peuvent désormais ouvrir les flux de création d'applications vierges ou de modèles de Studio. (#45717)

Des descriptions de connaissances et des métadonnées plus flexibles

  • Descriptions de bases de connaissances plus longues. Des limites de longueur de description plus longues vous permettent de fournir plus de contexte pour chaque base de connaissances. (#45075)
  • Métadonnées de connaissances externes. La récupération de connaissances externes renvoie désormais les métadonnées du document aux côtés du contenu. (#22496)

Améliorations

Réduction des frais de base de données et de démarrage. Les mises à jour d'exécution des nœuds évitent de recharger les lignes stockées, les politiques d'informations d'identification sont évaluées une fois par configuration de fournisseur, les valeurs par défaut du modèle utilisent des sessions de courte durée et les appels d'intégration ne maintiennent plus ouvertes une session de base de données. Les dépendances des fonctionnalités Web se chargent également plus paresseusement. (#46410, #46441, #45806, #45788, #46145) Échecs de documents plus clairs et mises en page plus stables. Les documents de connaissances signalent désormais les raisons d'échec et les étapes de traitement spécifiques. Les boîtes de dialogue s'adaptent aux fenêtres d'affichage étroites et maintiennent des cycles de vie cohérents entre les comptes, les connaissances, les applications, les compétences et les flux de travail. Les pages d'authentification se chargent plus rapidement, s'adaptent à des écrans plus petits et maintiennent la mise au point du clavier accessible. Les commandes segmentées s'animent de manière fluide tout en préservant les dispositions compactes et en respectant les préférences de réduction de mouvement. (#45128, #46487, #45686, #45668, #45634, #45600, #45640, #45974)

Corrections de bugs

  • Aperçus de fichiers et liens signés plus sûrs. Aperçus SVG en ligne dans Sandbox et vérification de la signature originale avant de renouveler les liens de fichiers expirés. (#46505)
  • Protection d'accès renforcée. Supprimez les détails des nouvelles tentatives de nœud des flux publics, empêchez la réutilisation des rappels OAuth, appliquez les autorisations des rôles de membre et étendez la suppression des vecteurs à l'ensemble de données cible. (#46517, #46001, #46053, #45586)
  • Mises à jour des dépendances de sécurité. Mettez à niveau github.com/klauspost/compress dans dify-agent-runtime pour résoudre CVE-2026-116591 et mettez à jour Node.js dans les images d'exécution vers la version de sécurité 24.22.3. (#46544, #46206, #46064)
  • Flux de travail de blocage fiables. Libérez les connexions à la base de données avant l'exécution et renvoyez immédiatement les échecs de préparation, évitant ainsi l'épuisement du pool de connexions et les demandes suspendues qui attendent l'expiration du délai d'attente. (#46254)
  • Travailleurs plus stables. Résolvez la boucle occupée Redis BRPOP et évitez les contrôles de mise à niveau du plugin qui se chevauchent, en plafonnant la concurrence à 20 contrôles entre les travailleurs. (#45940, #46500)
  • Terminez les flux Chatflow. Fermez correctement les flux après des réponses directes et réinitialisez le budget de reconnexion lorsqu'un flux reprend. (#45552, #46110)
  • Exécution correcte de l'agent. Préservez les appels parallèles vers le même outil de plug-in, transmettez les entrées d'application déclarées aux exécutions de l'agent et fournissez les images téléchargées aux modèles de vision. (#45207, #45425, #45745)
  • Récupération précise des connaissances. Restaurez les résultats des mots-clés/hybrides Weaviate en renvoyant les scores BM25 et continuez à intégrer les vecteurs alignés lorsqu'un élément de lot est supprimé. (#45642, #45569)
  • Outils API personnalisés fiables. Résolvez les variables du serveur OpenAPI, les paramètres de chemin d'encodage en pourcentage et prenez en charge les unions nullables OpenAPI 3.1. (#46504, #45965, #45895)

Configuration du proxy inverse et du travailleur

  • Nouvelle route API : En mode WEBHOOK, transférez /callbacks/human-input/v2/im/ au service API (api:5001 dans Docker Compose), en préservant le chemin de la requête, le corps brut et les en-têtes de signature du fournisseur. Le modèle nginx fourni inclut déjà cette règle ; ajoutez son équivalent à nginx personnalisé, Ingress ou à d'autres configurations de proxy inverse. Configurez le fournisseur de messagerie instantanée avec l'URL de rappel générée par le canal. (#44864)
  • Nouvelles files d'attente Celery : Inclut human_input_delivery pour le traitement asynchrone des rappels de messagerie instantanée et les mises à jour des cartes après soumission, et human_input_contact_sync pour la synchronisation du répertoire de contacts de messagerie instantanée. La liste de travailleurs Docker par défaut inclut les deux. Les listes personnalisées CELERY_QUEUES, CELERY_WORKER_QUEUES ou Celery --queues doivent fournir un consommateur actif pour chaque file d'attente aux côtés des abonnements existants. (#44864)

Fichiers d'environnement Docker

docker/envs/core-services/shared.env n'est plus chargé. Déplacez les paramètres communs API, Worker et Beat vers api-worker.env avant de recréer les conteneurs. Conservez tous les paramètres spécifiques au service dans le fichier de remplacement utilisé par ce service. (#46497) Les URL publiques sont partagées par Web, API et les collaborateurs via le nouveau envs/core-services/urls.defaults et le urls.env en option : *CONSOLE_API_URL *CONSOLE_WEB_URL *SERVICE_API_URL *APP_API_URL *APP_WEB_URL Définissez des URL de base accessibles par navigateur sans suffixes /console/api, /api ou /v1. Les valeurs explicites dans urls.env remplacent les paramètres d'URL spécifiques au service ; La racine docker/.env remplace les deux. Le SERVER_CONSOLE_API_URL interne du Web reste dans le web.env. Cela résout également un problème où les liens d'icônes générés pointaient vers 127.0.0.1:5001 sur les nouvelles installations. (#46497)

Guide de mise à niveau

[!IMPORTANT] Déplacez les paramètres du shared.env retiré avant de recréer les conteneurs. Examinez les URL publiques, le routage de rappel HITL personnalisé et les abonnements des collaborateurs. Les déploiements OpenShell nécessitent une mise à niveau de passerelle compatible et ne restaurent plus les instantanés d'accueil. Le démon du plugin fourni est mis à jour vers 0.6.15-local.

Préparer le déploiement

  1. Sauvegardez les données et la configuration. Sauvegardez votre base de données, les données du magasin vectoriel, les fichiers téléchargés, le stockage du démon de plug-in, le stockage de l'espace de travail de l'agent, les secrets de déploiement et les fichiers d'environnement. Planifiez une fenêtre de maintenance pour une mise à niveau à pile unique.
  2. Mettez à niveau les composants Dify ensemble. Utilisez les images correspondantes 1.20.0 API, Worker, Web, Agent Backend et Local sandbox, aux côtés du démon de plug-in 0.6.15-local. Conservez inchangés SECRET_KEY, tout PASSWORD_PEPPER configuré et le jeton d'authentification du bac à sable local. Les jetons d'accès personnels dépendent de SECRET_KEY ; assurez-vous que la même valeur est utilisée dans toutes les répliques API. Si vous effectuez une mise à niveau à partir d'une version antérieure à 1.19.0, suivez également le [Guide de mise à niveau 1.19.0] (https://github.com/langgenius/dify/releases/tag/1.19.0).
  3. Migrez shared.env. Si envs/core-services/api-worker.env n'existe pas, renommez envs/core-services/shared.env avec ce chemin. Si les deux existent, fusionnez uniquement les paramètres manquants et conservez les valeurs api-worker.env existantes, y compris les affectations vides intentionnelles. Conservez les paramètres spécifiques au service dans le fichier de remplacement de service approprié. Les déploiements sans shared.env ne nécessitent aucune migration.
  4. Consolidez les URL publiques. Créez envs/core-services/urls.env à partir de urls.defaults uniquement s'il n'existe pas déjà. Déplacez-y les valeurs d'URL publiques prévues, puis supprimez les attributions en double des fichiers de service individuels. Les valeurs racine .env existantes conservent la priorité. Conservez le routage Web interne API dans web.env.
  5. Appliquer les modifications d'environnement, d'itinéraire et de file d'attente. Suivez les Modifications de configuration et d'intégration, y compris les nouveaux paramètres HITL, l'itinéraire de rappel IM et les deux files d'attente Celery.
  6. Laissez l'initialisation du stockage du plugin s'exécuter. init_permissions prépare désormais également ./volumes/plugin_daemon pour l'UID 1001 du démon, et le démon attend qu'il se termine. Recréez le déploiement avec docker compose up -d pour que le service init s'exécute. (#45615)

Déploiements OpenShell

Mettez à niveau la passerelle OpenShell et le SDK ensemble vers 0.1.3 ou version ultérieure dans la gamme 0.1.x prise en charge, et mettez à niveau le Dify API et le backend de l'agent ensemble. La passerelle doit prendre en charge l'exposition du service natif et le relais du support, en préservant le jeton d'autorisation par bac à sable dérivé de DIFY_AGENT_OPENSHELL_SHELLCTL_AUTH_TOKEN. Conservez ce secret principal identique dans toutes les répliques du backend de l'agent. (#45862) Créez l'image d'exécution OpenShell à partir de la récupération de la version et définissez DIFY_AGENT_OPENSHELL_SANDBOX_IMAGE sur la référence d'image exacte disponible pour les nœuds de calcul de la passerelle. L'image doit inclure à la fois shellctl et iproute2 ; une ancienne image d’exécution mise en cache peut ne pas disposer des outils réseau requis. Lors de la mise à niveau à partir du jeton shellctl partagé à l'échelle du déploiement précédent, générez un nouveau secret principal à haute entropie et mettez à jour toutes les répliques du backend de l'agent ensemble. Videz le travail actif, puis arrêtez et redémarrez les sandbox existants afin que shellctl redémarre avec les informations d'identification dérivées. La réacquisition d’un bac à sable déjà sain n’actualise pas ses informations d’identification. Les instantanés personnels du volume partagé et le DIFY_AGENT_OPENSHELL_SHARED_MOUNT_PATH sont supprimés. Les sandbox en cours d'exécution existants conservent leur état pendant les cycles d'arrêt/redémarrage, tandis que les liaisons nouvellement créées démarrent à partir de l'accueil par défaut de l'image. DIFY_AGENT_OPENSHELL_DRIVER_CONFIG est désormais facultatif. Consultez le [Guide de déploiement OpenShell] (https://github.com/langgenius/dify/blob/1.20.0/dify-agent/docs/dify-agent/guide/openshell.md), y compris ses exigences en matière d'image d'exécution, avant la mise à niveau. Les autres backends sandbox ne sont pas affectés.

Docker Composer

Une fois la balise et les images 1.20.0 publiées, arrêtez le déploiement en douceur, passez à la version, migrez les fichiers de configuration locaux, puis extrayez et démarrez les services mis à jour :

cd dify/docker
docker compose stop -t -1
git fetch --tags
git checkout 1.20.0
# Migrate shared.env, public URLs, and any custom proxy/worker configuration.
docker compose pull
docker compose up -d

Gardez les migrations de démarrage API activées (MIGRATION_ENABLED=true) ou appliquez la chaîne de migration complète via votre processus de migration géré avant de démarrer de nouveaux travailleurs. Utilisez docker compose up -d après avoir modifié les fichiers d'environnement ; un simple redémarrage ne les recharge pas.

Déploiements sources

Utilisez Python 3.13, Node.js 24.22.3 ou version ultérieure dans la ligne 24.x et pnpm 12.18.0. Après avoir arrêté les services et basculé vers la version, exécutez les commandes suivantes à partir de la racine du référentiel :

uv sync --project api --frozen
uv run --directory api flask db upgrade
pnpm install --frozen-lockfile

Reconstruisez Web et redémarrez les services API, Workers, Planificateur et Agent à partir de la même version.
