débit d'air 3.3.0

📦PyPI : https://pypi.org/project/apache-airflow/3.3.0/ 📚 Documents : https://airflow.apache.org/docs/apache-airflow/3.3.0/ 🛠 Release Note : https://airflow.apache.org/docs/apache-airflow/3.3.0/release_notes.html 🐳 Docker Image : "docker pull apache/airflow :3.3.0" 🚏 Contraintes : https://github.com/apache/airflow/tree/constraints-3.3.0

Changements importants

Partitionnement des actifs (#64571, #65447, #66030, #66848, #67184, #67475, #67716, #68978)

S'appuyant sur le partitionnement des actifs introduit dans le 3.2.0, Airflow 3.3.0 étend considérablement la façon dont un Un événement d'actif unique en amont se diffuse vers des exécutions Dag en aval partitionnées. Nouveaux mappeurs de partition — RollupMapper (many-to-one), FanOutMapper (one-to-many), and FixedKeyMapper + SegmentWindow (cumul catégoriel) — composez avec des fenêtres temporelles (jour/semaine/mois/trimestre/année) et un wait_policy (WaitForAll or MinimumCount(n)) pour contrôler le moment où les exécutions partitionnées se déclenchent. Fenêtres peut se déployer vers l'avant ou vers l'arrière dans le temps, et la diffusion totale par événement en amont est limitée par le nouveau Configuration [scheduler] partition_mapper_max_downstream_keys (configurable par mappeur). Flux d'air 3.3.0 ajoute également le calendrier PartitionedAtRuntime, qui permet à un Dag de déclarer que sa ou ses clés de partition sont attribués au démarrage de l'exécution plutôt que mappés à partir d'un événement en amont.

Pour des instructions d'utilisation détaillées, voir :doc:/authoring-and-scheduling/assets.

Magasin d'état des tâches et des actifs (#65759, #66073, #66160, #66463, #66586, #66859, #67041, #67292, #67319)

Airflow 3.3.0 introduit un magasin d'état de première classe pour les tâches et les actifs (AIP-103). Les tâches peuvent persister état clé-valeur arbitraire qui survit à travers les tentatives et s'exécute via un nouvel accesseur task_state_store, et les actifs peuvent porter leur propre état via asset_state_store — tous deux disponibles à partir de la tâche SDK. L'état est conservé dans la base de données de métadonnées par défaut, ou dans un backend personnalisé côté travailleur ([workers] state_store_backend), prend en charge la conservation par clé avec un garbage collection périodique et un facultatif clear_on_success, et est entièrement gérable via le Core API et l'Execution API.

Pour des instructions d'utilisation détaillées, voir :doc:/core-concepts/task-and-asset-state-store.

Politiques de nouvelle tentative enfichables (#65474)

Le comportement de nouvelle tentative de tâche est désormais connectable (AIP-105). En plus d'un nombre fixe de retries, vous pouvez attachez une politique de nouvelle tentative personnalisée qui décide si et quand une tâche est réessayée, permettant des stratégies telles que comme réessayer uniquement sur des exceptions spécifiques ou reculer en fonction d'une logique personnalisée.

Pour des instructions d'utilisation détaillées, voir :ref:concepts:retry-policies.

Tâche de langage SDK (Java et Go) (#65958, #67161, #67635, #67699)

Airflow 3.3.0 ajoute une couche de coordinateur (AIP-108) qui permet d'écrire des implémentations de tâches individuelles dans des langues non Python tandis que le Dag et sa planification restent en Python. Une tâche est déclarée dans le Dag avec @task.stub(queue=...) ; le travailleur l'achemine vers un coordinateur configuré (JavaCoordinator for JVM languages, ExecutableCoordinator pour les binaires natifs autonomes tel que Go) qui exécute la tâche dans un environnement d'exécution de langage et renvoie les variables, les connexions et les XCom par proxy via l'exécution API.

.. avertissement ::

La couche coordinatrice et les SDK Java/Go sont expérimentaux dans 3.3.0 et pourraient changer à l'avenir. versions basées sur les commentaires des utilisateurs.

Pour des instructions d'utilisation détaillées, voir :doc:/authoring-and-scheduling/language-sdks/index.

Version du bundle Dag pour l'effacement, la réexécution et le remplissage (#63884)

Le nouveau paramètre « rerun_with_latest_version » contrôle si une exécution Dag effacée, réexécutée ou remplie. utilise la dernière version du bundle ou la version originale de l'exécution initiale. Le défaut est résolu par priorité : un paramètre de requête explicite/drapeau CLI, puis le niveau Dag rerun_with_latest_version, puis [core] rerun_with_latest_version, and finally False for clear/rerun and True pour remblayages (préservation du comportement historique). Airflow 2.x est toujours réexécuté avec le dernier code ; 3.x introduit la gestion des versions du bundle par défaut sur la version originale, et ce paramètre donne le contrôle aux utilisateurs.

Voir :doc:/administration-and-deployment/dag-bundles pour plus de détails.

Exemple de fournisseur Dags sous forme de bundles dédiés (#66161)

Les exemples de Dags expédiés par les distributions des fournisseurs sont désormais découverts via ProvidersManager et enregistrés comme leurs propres forfaits Dag - un par fournisseur, nommé apache-airflow-providers-<distribution>-example-dags (or <distribution>-example-dags pour fournisseurs tiers). L'option [core] load_examples détermine toujours s'ils sont enregistrés. REST API clients qui a filtré bundle_name by "dags-folder" pour les exemples de Dags fournis par le fournisseur doit être mis à jour vers les nouveaux noms de bundles par fournisseur ; Les identifiants du jour sont inchangés.

Résolution de journalisation à distance découplée de airflow.logging_config (#67056)

La résolution du gestionnaire de journaux de tâches à distance appartient désormais au « airflow_shared.logging.factory » partagé. module et applique une priorité unique et bien définie :

  1. un [logging] logging_config_class exporting REMOTE_TASK_LOG défini par l'utilisateur / DEFAULT_REMOTE_CONN_ID (les configurations personnalisées existantes continuent de fonctionner) ;
  2. ProvidersManager scheme dispatch — the scheme of [logging] remote_base_log_folder sélectionne un méthode de classe du fournisseur RemoteLogIO class, instantiated via a no-argument from_config() ;
  3. une solution de secours héritée de transition indiquant « airflow_local_settings.py » (à supprimer dans Airflow 4.0).

airflow.logging_config.load_logging_config is deprecated (it now emits DeprecationWarning et délègue à de nouveaux assistants privés), et configure_logging ne résout plus avec empressement le problème à distance gestionnaire - la résolution est paresseuse lors de la première utilisation. Les fournisseurs qui ont enregistré un bloc remote-logging: mais qui le font qui n'implémentent pas from_config sont ignorés avec un avertissement et passent au chemin hérité.

Migration : remplacez les appels directs vers airflow.logging_config.load_logging_config() par le nouveau helpers, et demander aux classes de gestionnaire de journaux distants du fournisseur d'implémenter un from_config sans argument méthode de classe qui lit airflow.providers.common.compat.sdk.conf.

Les métriques du minuteur OpenTelemetry utilisent désormais l'histogramme (#64207)

La minuterie et les mesures de synchronisation du OpenTelemetry sont désormais enregistrées sous forme d'histogrammes au lieu de jauges, préservant ainsi le nombre, la somme et la répartition des compartiments entre les enregistrements.

La métrique de traitement des données "il y a quelques secondes" est désormais balisée (#62487)

dag_processing.last_run.seconds_ago.{dag_file} est désormais une métrique héritée. Le nouveau dag_processing.last_run.seconds_ago is emitted with file_path, bundle_name et file_name tags (file_path + bundle_name identifie de manière unique le fichier Dag). La métrique héritée est toujours émis par défaut et peut être désactivé via [metrics] legacy_names_on.

Nouvelle page de délais sous Parcourir (#67586)

Une nouvelle page Délais est disponible dans le menu Parcourir, accessible à tout rôle ayant déjà can_read and menu_access sur Dag Runs.
