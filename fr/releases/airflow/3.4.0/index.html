Changements importants

Boucles de tâches (#73005, #74222, #74275, #74345)

Airflow 3.4.0 introduit les boucles de tâches (AIP-111) : un groupe de tâches décoré peut être répété plusieurs fois. heures décidées au moment de l'exécution à l'aide de la boucle .loop(). A conditional loop works like a do ... while - le corps s'exécute au moins une fois et une condition « until » décide quand s'arrêter, délimitée par max_iterations. Chaque itération peut utiliser le résultat de l'itération précédente et les itérations en exécutent un les unes après les autres (les tâches d'une itération peuvent toujours s'exécuter en parallèle). Les tentatives répétées sont conservées sous un UUID par tentative afin que les données de chaque itération soient préservées et puissent être effacées de manière sélective.

Pour des instructions d'utilisation détaillées, voir :doc:/authoring-and-scheduling/loops.

.. remarque :  La mise à niveau vers une version antérieure à 3.4.0 peut être lente, en fonction du nombre de Lignes XCom écrites après la mise à niveau. La mise à niveau a été testée sur un Table XCom de 300 m de rangée, alors ne vous inquiétez pas du temps de mise à niveau (nous nous sommes assurés que les données XCom n'ont pas été touchées ou lues pendant la migration pour les conserver rapide).

En effet, cette version contient une migration qui commence à stocker les nouveaux XCom lignes dans une table xcom_v2, et pour rétrograder, nous devons les déplacer à l'ancienne table, et il n'y a aucun moyen de le faire sans copier le valeurs xcom écrites.

La rétrogradation refuse de continuer lorsqu'elle trouve des données qu'elle ne peut pas cartographier en toute sécurité. Chaque migration est validée séparément, donc les migrations 3.4.0 ultérieures ont déjà été annulés à ce stade : corrigez les données et réexécutez le rétrogradez ou exécutez airflow db migrate pour revenir à 3.4.

Sur MySQL un échec après ces vérifications laisse le schéma partiellement dégradé, car MySQL ne peut pas restaurer DDL. Faire une sauvegarde avant de tenter le Il est conseillé de rétrograder le MySQL afin qu'il puisse être restauré dans ce cas.

Importateur de Dags pour les Dags non-Python (#72369, #73728, #73853, #74020, #74084, #74333, #74586)

Airflow 3.4.0 peut créer un Dag complet (horaire, tâches et dépendances) dans une langue autre que Python. L'AIP-85 ajoute un importateur Dag enfichable dans la tâche SDK qui apprend au processeur Dag à reconnaître les formats source au-delà de .py : chaque format enregistre un importateur, le processeur exécute le le langage d'exécution correspondant et les Dags résultants apparaissent dans Airflow comme Python Dags. Les formats qui y atterrissent sont les langages TypeScript, Go et Java SDK et un format natif YAML Dag (un Marqueur .yaml file with a $schema, validé par rapport à un schéma et intégré à des opérateurs réels, avec un modèle explicite). Le framework Dag Importer et le langage SDKs sont expérimentaux dans 3.4 et leurs API peuvent changer.

Pour des instructions d'utilisation détaillées, voir :doc:/administration-and-deployment/dag-importers.

psycopg3 est désormais le pilote Postgres par défaut (#68496)

psycopg3 (psycopg) est désormais le pilote par défaut pour la base de données de métadonnées, à la fois pour la synchronisation et le moteur asynchrone, remplaçant psycopg2 et asyncpg. Un postgresql:// nu (ou un héritage postgres:// / postgres+psycopg2://) sql_alchemy_conn est réécrit dans postgresql+psycopg://, and the derived async URL uses postgresql+psycopg_async:// lorsque psycopg3 est installé (sinon, on revient à asyncpg). Airflow désactive également les psychopg3 préparation des instructions côté serveur (prepare_threshold = None) pour que la base de données de métadonnées fonctionne de la boîte derrière le mode transaction PgBouncer, la configuration de production recommandée. Pour conserver psycopg2 ou asyncpg, installez le supplément apache-airflow-providers-postgres[psycopg2] / [asyncpg] et configurer la connexion explicitement ; voir #68496 et #69469 pour plus de détails, y compris comment réactiver préparation des déclarations.

Noms qui restent invalides pour une autre raison, telle que contenant les sorties __, are migrated as they are; they keep working, but airflow teams sync différent de zéro jusqu'à ce qu'ils soient renommés.

Modifications de la façon dont les événements d'actifs en attente déclenchent l'exécution de Dag (#70972)

La suppression des enregistrements d'événements d'actifs avec airflow db clean supprime désormais également tous les événements d'actifs qui sont toujours en attente d'un Dag en aval. Cela affecte principalement les Dags en attente d'une condition multi-actifs, où un événement en attente peut être purgé avant que la condition ne soit remplie. Supprimer un événement d'actif maintenant signifie systématiquement que cela ne déclenchera pas d'exécution ; auparavant, un tel déclencheur en attente pouvait toujours se déclencher après que l'événement ait été purgé.

Auparavant, ils étaient abandonnés en silence.

L'effacement d'une tâche supprime désormais ses entrées de magasin d'état de tâche par défaut (#72100)

La suppression d'une instance de tâche supprime désormais ses entrées task_state_store, donc la prochaine tentative démarre depuis le début au lieu de reprendre depuis un point de contrôle ou de se reconnecter à un travail externe enregistré par la tentative autorisée. Les tentatives ne sont pas affectées et conservent l’état de la tâche comme avant. Ceci s'applique pour effacer les instances de tâches individuelles (le point de terminaison/la boîte de dialogue d'effacement et les jours airflowctl tasks/ clair); l'effacement d'une exécution Dag entière conserve toujours l'état de la tâche (suivi dans #72929 <https://github.com/apache/airflow/issues/72929>_). [core] execute_tasks_new_python_interpreter s'applique désormais aux processus de tâches Airflow 3 (#72164)

Sur Airflow 3, l'option n'avait aucun effet sur l'exécution de la tâche (seul le travailleur Edge la lisait). Lorsqu'il est réglé sur True, the task supervisor now exec\ est un nouvel interprète juste après avoir exécuté la tâche processus, qui empêche le fork d'hériter d'un verrou détenu par un thread superviseur (un se bloquer au premier appel TLS de la tâche). Suspendez gracieusement les Dags en drainant les exécutions actives (#72407, #73225, #73055, #73763)

Airflow prend désormais en charge un état de planification « draining » pour les Dags. La vidange arrête le planificateur de créer de nouvelles exécutions Dag planifiées ou déclenchées par des actifs tout en autorisant les Dag déjà en file d'attente et en cours d'exécution court pour continuer. Les exécutions explicitement déclenchées restent autorisées.

Une fois les exécutions Dag en suspens terminées, le Dag passe automatiquement à « paused ». Les utilisateurs peuvent annulez la vidange pour ramener le Dag à active.

Les exécutions manuelles, les remplissages et les matérialisations d'actifs sur un Dag en pause peuvent drainer le Dag au lieu de pour le reprendre : choisissez Drain dans l'interface utilisateur ou définissez drain_dag dans la requête REST API. Vidange permet aux exécutions inachevées du Dag de démarrer ou de reprendre, à l'exception de celles retenues par les remplissages en pause, ne crée aucun exécutions planifiées et met à nouveau le Dag en pause une fois que toutes les exécutions inachevées sont terminées. Les remplissages suspendus restent mis en pause et doivent être repris pour que leurs courses se terminent et que leur épuisement soit terminé.

L'interface utilisateur, REST API et la planification airflowctl expose the active, draining, and paused États, et la liste des Dags peut mettre en pause, drainer ou reprendre plusieurs Dags sélectionnés à la fois. Existant is_paused API usage remains supported; use scheduling_state lorsque l'état de vidange doit être sélectionnés ou signalés explicitement.

Les battements de cœur de tâche ne sont plus réessayés par [workers] execution_api_retries (#73244)

Heartbeats avait deux mécanismes de nouvelle tentative qui se chevauchaient : la tâche SDK API client réessayait chaque requête, y compris les battements de cœur, et le superviseur a compté séparément les échecs de battements de cœur consécutifs par rapport à [workers] max_failed_heartbeats. Les tentatives du client ont également eu pour effet secondaire indésirable de bloquant la boucle de surveillance du superviseur pendant qu'il reculait, ainsi lors d'une panne du serveur API, le le superviseur serait retardé dans la transmission des journaux de tâches et/ou remarquerait que le sous-processus de tâche avait sorti.

Les tentatives de pulsation sont désormais régies uniquement par « max_failed_heartbeats », dont la valeur par défaut a été ajusté à partir de 3 to 30 pour conserver à peu près la même tolérance pour un serveur API inaccessible que les deux mécanismes combinés ont donné avant.

Si vous avez défini explicitement [workers] max_failed_heartbeats, vous souhaiterez peut-être reconsidérer la valeur que vous avez choisie. ont choisi. C'est maintenant tout le budget de nouvelle tentative : avec la valeur par défaut [workers] min_heartbeat_interval of 5 seconds, the worker tolerates roughly 5 * max_failed_heartbeats secondes d'indisponibilité du API avant de terminer une tâche en cours d'exécution. Vous devriez probablement conserver le valeur résultante inférieure à tout [scheduler] task_instance_heartbeat_timeout configuré (par défaut 300 secondes).

Rappels d'alertes de date limite validés au moment de l'analyse ; intervalles numériques obsolètes (#73294)

DeadlineAlert now refuses a callback that is not exactly AsyncCallback ou SyncCallback, donc une sous-classe échoue lorsque le Dag est analysé plutôt que lorsque le planificateur lit il revient. Le planificateur décode les rappels stockés par nom de classe exact, donc aucune classe nommée par un Dag l'auteur y est importé ou instancié, ce qui signifie qu'une sous-classe pourrait être écrite et ensuite jamais lire.

Passer un numéro sous la forme interval is deprecated and now emits RemovedInAirflow4Warning. Il est toujours accepté et pris en compte en secondes, mais les types pris en charge sont timedelta et VariableInterval. A timedelta subclass such as pendulum.duration(...) est accepté et normalisé en un simple timedelta, où auparavant il avait réussi la validation, puis a échoué pendant sérialisation. sous-classe interval=True is refused, because bool is an int et sinon, elle sera considérée comme une seconde.

Le point de terminaison POST /assets/{asset_id}/materialize nécessite désormais un corps de requête JSON (#73328)

Auparavant, une requête sans corps était acceptée et le bien était matérialisé avec des valeurs par défaut. Le point final nécessite désormais un corps JSON explicite, cohérent avec les autres points finaux en mutation : un la requête sans corps est rejetée avec 422, et un formulaire HTML vide n'est pas une entrée valide plus. Tous les champs du corps restent facultatifs, donc un objet vide ({}) est un corps valide.

Le nombre d'essais de TaskInstance augmente désormais avant le début de l'essai suivant (#73554)

.. remarque : 

Si vous disposez de systèmes externes qui examinent les journaux de tâches ou l'état de TI pour une TI avec réessai, vous vous devrez être conscient de ce changement et mettre à jour votre code.

Par exemple, si vous avez fait une requête à GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id} s'attend à obtenir des informations sur l'essai raté, vous devrez maintenant regarder GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id}/tries/{try_number - 1}

Lorsqu'une tâche est up_for_retry, try_number identifie désormais l'essai à venir. Pour récupérer l'essai a échoué, demandez /tries/{try_number - 1}. L'interface utilisateur affiche l'essai en attente et fournit un lien vers les journaux de l'essai précédent.

Airflow alloue désormais l'UUID d'une instance de tâche et essaie de numéroter ensemble de manière immuable afin qu'ils soient cohérents identifier le même essai.

Auparavant, lorsqu'une tâche entrait dans la période de récupération des nouvelles tentatives, elle recevait un nouvel UUID, mais continuez. essayez le numéro N et ayez l'état UP_FOR_RETRY jusqu'à ce que cette période soit écoulée (à ce moment-là, cet essai serait marqué FAILED et le numéro d'essai serait incrémenté). Au lieu de cela, la tentative ratée est immédiatement marqué de l'état FAILED et d'un nouvel essai créé dans l'état UP_FOR_RETRY.

Déprécier les dépendances cyclic TaskGroup (#73746)

Un Dag dont les TaskGroups dépendent les uns des autres dans un cycle, lorsque chaque TaskGroup est traité comme un seul unité, émet désormais un TaskGroupCycleDeprecationWarning au moment de l'analyse et affiche un avertissement Dag dans l'interface utilisateur qui nomme les groupes de tâches et les tâches impliquées. Ces Dags analysent et s'exécutent toujours, car leur les dépendances de tâches sont acyclic, mais Airflow 3.5 est prévu de les rejeter au moment de l'analyse.

Une dépendance vers ou hors d'une tâche dans un TaskGroup compte comme une dépendance de l'ensemble du groupe, donc un le chemin qui quitte un TaskGroup et y revient est un cycle. Par exemple, a >> bridge >> b, avec a and b in the same TaskGroup and bridge à l'extérieur, rend le groupe dépendant de « bridge`` and ``bridge`` depend on the group, even if ``a >> b » est également défini.

  • Déplacez les tâches entre les groupes de tâches ou hors d'eux, de sorte que chaque groupe dépende des autres dans un seul groupe. direction uniquement. Dans l'exemple ci-dessus, déplacez « bridge`` into the group, or move ``b » hors de celui-ci.
  • Pour récupérer ces Dags dans CI, lancez vos tests Dag avec -W erreur :: airflow.sdk.exceptions.TaskGroupCycleDeprecationWarning. Le contrôle s'exécute lorsqu'un Dag est ajouté à un DagBag, so only tests that load your Dags into a DagBag et affirmer qu'il y a aucune erreur d'importation ne les détecte ; un test qui importe uniquement un fichier Dag ne le fait pas.

Voir « Dépendances Cyclic TaskGroup » dans la documentation Dags.

La prise en charge de Python 3.10 a été supprimée (#74151)

Airflow nécessite désormais Python 3.11 ou plus récent. Python 3.10 arrive en fin de vie en octobre 2026, et Airflow abandonne la prise en charge d'une version Python dans « main » dès qu'elle atteint la fin de sa vie. Le apache-airflow distribution, the Task SDK, airflowctl et tous les fournisseurs publiés à partir de "main`` declare ``requires-python = ">=3.11"".

Déprécier l'attribut required_kwargs pour les références de délais personnalisées (#70714)

Implémentez plutôt le paramètre _evaluate_with() with a dagrun.

Les images CI et de production sont désormais basées sur les images renforcées Docker et Debian 13 (#73038)

Les images CI et de production d'Airflow sont désormais basées sur Docker Hardened Images <https://dhi.io>_ pour Python et Debian 13 "trixie".

Python n'est plus compilé à partir des sources lors de la création de l'image : il provient de la base renforcée. image à la place, qui supprime le téléchargement de la source, sa vérification de signature et la compilation lui-même à partir de la construction. Python réside toujours dans /usr/python, qui est désormais un lien symbolique vers le Emplacement « /opt/python » utilisé par l'image de base, donc les chemins à l'intérieur de l'image restent inchangés.

L'argument de construction BASE_IMAGE est désormais par défaut ghcr.io/apache/airflow/base/python:<version>-debian13-dev, le miroir public d'Airflow du Image dhi.io/python en amont, donc la création d'une image ne nécessite aucune information d'identification de registre. N'importe qui le remplacement de l'image BASE_IMAGE with a plain debian:bookworm-slim doit passer à une image qui fournit déjà Python, ou créez la version legacy.

Le système d'exploitation de base est passé de Debian 12 « bookworm » à Debian 13 « trixie ». Packages de bibliothèque renommés en trixie time_t transition (for example libssl3 is now libssl3t64) doivent être mis à jour dans la version personnalisée RUNTIME_APT_DEPS / ADDITIONAL_RUNTIME_APT_DEPS et compatible MySQL client vient désormais de MariaDB 11.8.

Pour la gamme 3.4.x, les images de production construites de la manière précédente - Python compilées à partir de sources sur Saveur debian:bookworm-slim - are still published as the deprecated legacy, sélectionnée avec le nouvel argument de construction AIRFLOW_IMAGE_FLAVOR="legacy". Ils seront supprimés dans Airflow 3.5.0.

Le PYTHON_LTO build argument is gone. To build a FIPS-compliant image, point BASE_IMAGE à un Variante FIPS de l'image renforcée à la place, par exemple dhi.io/python:3.13.16-debian13-fips-dev.

Tâche SDK API client trusts le magasin de certificats système au lieu de certifi (#73116)

Avec [api] client_use_public_certs activé (valeur par défaut), la tâche SDK client qui communique avec le Exécution de API trust envoie désormais le magasin de certificats du système d'exploitation via truststore au lieu de les certifi CA bundle. CAs from [api] ssl_ca_file and [api] ssl_cert sont toujours trusted en plus du magasin système, et certifi n'est plus une dépendance de la tâche SDK.

Les travailleurs doivent avoir les autorités de certification publiques dont ils dépendent installées dans le magasin système (par exemple, le ca-certificates sur les images basées sur Debian). Sur macOS et Windows, validation du certificat est délégué au système d'exploitation, qui peut rejeter les certificats de serveur acceptés par OpenSSL, tels que les certificats d'autorité de certification privée sans l'utilisation étendue de la clé « serverAuth ».

Les travailleurs plus âgés ne peuvent plus reprendre les tâches différées dont next_kwargs contient des classes personnalisées (#73577)

Lorsqu'une tâche différée reprend sur un travailleur avec une tâche SDK plus ancienne, le serveur API ne reconstruit plus les classes arbitraires à partir du contenu next_kwargs to convert them to the legacy format. Built-in value types, assets and asset aliases (including asset access control) are still converted, without constructing them. A deferred task whose next_kwargs stocké. Toute autre classe échoue désormais sur un tel travailleur avec une erreur nommant le type et demandant de mettre à niveau la tâche SDK, au lieu de planter sur une charge utile qu'il ne peut pas décoder.

Que faire : si vous exécutez des travailleurs avec apache-airflow-task-sdk 1.1.x or older and your deferrable operators or triggers pass instances of custom classes in next_kwargs (for example via self.defer(..., kwargs=...) or in the trigger event payload), upgrade the Task SDK on those workers to 1.2.0 or later. Newer workers receive next_kwargs unchanged and are not affected. Until all workers are upgraded, pass only built-in values, assets and asset aliases in next_kwargs de tâches qui peuvent reprendre sur les travailleurs plus âgés.

Les kwargs de rappel d'alerte de date limite sont décodés à l'endroit où le rappel s'exécute (#74830)

Les arguments mot-clé des rappels Deadline Alert ne sont plus décodés par le planificateur. Ils sont conservés sous leur forme sérialisée et décodés là où le rappel s'exécute : par le déclencheur pendant un "AsyncCallback``, and by the callback runner on the worker for a ``SyncCallback".

Les travailleurs qui exécutent les alertes d'échéance « SyncCallback » ont besoin d'une tâche SDK qui inclut ce changement, donc mettez à niveau apache-airflow and apache-airflow-task-sdk sur les travailleurs ensemble. Un travailleur avec un apache-airflow mis à niveau et une ancienne tâche SDK échouent à ces rappels avec une erreur à la place de les diriger. Les rappels créés avant la mise à niveau s'exécutent comme avant.

Backends XCom personnalisés qui remplacent serialize_value must implement store_value pour prendre en charge les boucles de tâches (#74858)

Chaque itération d'une tâche à l'intérieur d'une boucle est sa propre instance de tâche, mais serialize_value reçoit le même dag_id, run_id, task_id, map_index and key pour tous eux, donc un backend qui construit son emplacement de stockage à partir de ceux-ci rend le XCom de chaque itération relire comme valeur de la dernière itération. Les backends doivent remplacer « store_value » et 'load_value`` instead, and build the storage location with ``XComCoordinate.build_path', qui est unique par instance de tâche ou par écriture lorsque l'écriture ne peut pas connaître l'instance de tâche.

Un Dag qui utilise une boucle échoue au démarrage lorsque le backend XCom configuré stocke toujours des valeurs via serialize_value, même s'il écrit déjà dans un emplacement unique. Cela comprend XComObjectStorageBackend from apache-airflow-providers-common-io 1.10.1 et versions antérieures ; mettez à niveau le fournisseur avant d'utiliser des boucles de tâches avec lui.

Les backends du Custom Task State Store devront également inclure scope.region_id dans leur clé de stockage pour prendre en charge les tâches mappées dans une boucle et itérations de boucle régénérées par effacement.

airflow.utils.email est obsolète au profit du fournisseur SMTP (#75414)

Les fonctions dans airflow.utils.email (send_email, send_email_smtp, send_mime_email, build_mime_message and get_email_address_list) est désormais disponible dans "airflow.providers.smtp.utils.emailer``. The old names still work and raise a ``DeprecatedImportWarning". Airflow nécessite désormais « apache-airflow-providers-smtp>=3.2.0 ».

Conservez « [email] email_backend`` set to ``airflow.utils.email.send_email_smtp ». Airflow traite cette valeur comme "envoyer des e-mails de tâches avec SmtpNotifier", qui lit tous les paramètres SMTP de la connexion. Le changer en le chemin du fournisseur envoie à la place les paramètres « [smtp] ».

Si vous appelez ces fonctions directement :

  • La connexion SMTP est recherchée avec BaseHook.get_connection. Un script qui s'exécute en dehors d'Airflow les processus ont besoin de la connexion dans une variable d'environnement ou dans un backend de secrets, pas seulement dans les métadonnées base de données.
  • Les paramètres sont lus via la configuration de la tâche SDK, donc les valeurs ont été modifiées au moment de l'exécution avec airflow.configuration.conf.set() are not seen. airflow.cfg et les variables d'environnement fonctionnent comme avant.
  • Les tests qui patch airflow.utils.email.send_mime_email n'interceptent plus l'appel effectué par send_email_smtp. Patch airflow.providers.smtp.utils.emailer.send_mime_email à la place.

  • Le serveur API utilise un deuxième pool de connexions à la base de données

    Les serveurs du serveur API exécutent désormais certains travaux de base de données sur le moteur asynchrone ainsi que sur celui de synchronisation, et chaque moteur possède son propre pool de connexions, dimensionné par le même [database] sql_alchemy_pool_size and [database] sql_alchemy_max_overflow settings. What uses the async pool depends on the --apps option of airflow api-server :

    • execution : battements de cœur de tâche et plusieurs lectures d'exécution API.
    • core : l'entrée du journal d'audit enregistrée pour chaque demande d'écriture via le REST API ou l'UI.
    • all (la valeur par défaut) : les deux ci-dessus.

    Dans chaque mode, un travailleur peut donc ouvrir jusqu'à deux fois « sql_alchemy_pool_size + sql_alchemy_max_overflow`` connections (30 with the defaults) and keep up to twice ``sql_alchemy_pool_size`` of them idle. Account for this, per ``[api] workers``, when sizing PgBouncer or the database's ``max_connections ». Le pool asynchrone est utilisé depuis #67800, #73403, #73407 et #76416. (#76430)
