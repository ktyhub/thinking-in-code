#consul v2.1.0

2.1.0 (21 octobre 2026)

CHANGEMENTS DE RUPTURE :

  • agent : (Enterprise uniquement) Les corps de requête HTTP API de l'agent sont désormais limités à 512 Ko par défaut, y compris les requêtes fragmentées et les requêtes avec une méthode non prise en charge, et les requêtes surdimensionnées renvoient HTTP 413 avant que le corps ne soit lu dans son intégralité. Les écritures /v1/config très volumineuses qui réussissaient auparavant peuvent désormais échouer. Augmentez la limite avec le nouveau paramètre limits.http_max_request_body_size si nécessaire.
  • agent : (Entreprise uniquement) Les corps de requête de ressource API (/api/...) sont désormais soumis à la même limite limits.http_max_request_body_size (512 Ko par défaut), et les requêtes surdimensionnées renvoient HTTP 413.
  • agent : (Entreprise uniquement) GET /v1/agent/connect/ca/leaf/:service nécessite désormais service:write sur le service demandé pour chaque demande, y compris les demandes servies à partir du certificat feuille mis en cache de l'agent. Les requêtes sans jeton ou avec un jeton sans cette autorisation reçoivent désormais HTTP 403 au lieu du certificat mis en cache. Les appelants doivent présenter un jeton avec service:write pour le service.
  • catalogue : (Entreprise uniquement) Catalog.Register nécessite désormais une autorisation en écriture sur le nœud ou le service d'une vérification de l'état existante lors de sa mise à jour. Les jetons qui mettaient précédemment à jour les contrôles sans cette autorisation reçoivent désormais une erreur d'autorisation refusée.
  • cli : migration de la commande consul connect redirect-traffic de iptables/ip6tables vers nftables (nft). La commande utilise désormais le package sdk/nftables, qui applique toutes les règles IPv4 et IPv6 de manière atomique en un seul passage via la famille d'adresses nftables inet, au lieu d'appels iptables et ip6tables séparés. [GH-23785]
  • cli : les exclusions de proxy transparentes sont désormais validées avant l'application des règles : les ID utilisateur doivent être numériques et les exclusions sortantes doivent être des adresses IP ou des CIDR. iptables acceptait auparavant également les noms d'utilisateur, les plages d'UID et les noms d'hôte. [GH-23785]
  • cli : consul connect redirect-traffic ne supprime pas les règles iptables/ip6tables créées par les versions antérieures de Consul. Cela n'a d'importance que lors de la mise à niveau d'un hôte existant ou d'une VM en place. Avant d'exécuter la nouvelle commande sur un hôte ou une machine virtuelle existante, supprimez d'abord toutes les règles iptables gérées par Consul (voir le guide de mise à niveau du proxy transparent pour un script de nettoyage de référence). Laisser les deux ensembles de règles en place peut entraîner un double NAT ou une redirection de trafic incohérente. [GH-23785]
  • docker : les images officielles du conteneur Consul incluent désormais nftables au lieu de iptables. Les scripts qui exécutent iptables dans l'image Consul doivent être mis à jour. [GH-23785]
  • sdk : remplacement du package iptables par un nouveau package nftables pour une redirection transparente du trafic proxy. La redirection du trafic nécessite désormais le binaire nft et un noyau Linux avec prise en charge du NAT dynamique dans les chaînes de la famille nftables inet, disponibles en amont à partir de la version du noyau Linux 5.2 (certaines distributions rétroportent cette prise en charge sur une version nominale antérieure du noyau, par exemple RHEL 8+, le noyau 4.18+ et ses dérivés). Il n'y a pas de repli automatique vers iptables/ip6tables, donc les hôtes sans cette prise en charge du noyau ne parviendront pas à configurer une redirection proxy transparente. [GH-23785]
  • feature-gates : Gate API Gateway HTTPRoute composition de routage en amont (PR #23294) derrière la fonctionnalité expérimentale api-gateway-upstream-routing. Lorsqu'elle est désactivée (par défaut), la forme héritée HTTPRoute-to-router est conservée exactement. Lorsqu'elles sont activées par un opérateur après une mise à niveau complète du centre de données, les règles de routeur de service sont composées de correspondances HTTPRoute, les définitions de sous-ensembles de résolveur sont préservées et les surveillances de chaîne de découverte utilisent le remplacement correct du protocole HTTP. Les états proxy de la passerelle API sans agent existants sont automatiquement reconstruits lorsque la valeur effective de la porte change.

CARACTÉRISTIQUES :

  • acl : Ajout d'une déconnexion IdP initiée par OIDC RP pour les jetons créés via une méthode d'authentification oidc : consul logout imprime l'URL de déconnexion du fournisseur d'identité pour que l'utilisateur puisse l'ouvrir (ou l'ouvre dans le navigateur par défaut avec le nouvel indicateur -open-browser ou la variable d'environnement CONSUL_LOGOUT_OPEN_BROWSER), et l'interface utilisateur Web l'ouvre lors de la déconnexion, mettant ainsi fin à la session IdP. S'active automatiquement lorsque l'IdP annonce un end_session_endpoint dans son document de découverte OIDC, ou lorsque le point de terminaison de déconnexion est configuré explicitement avec le nouveau paramètre de méthode d'authentification OIDCLogoutURL pour les fournisseurs qui n'en annoncent pas. [GH-23739]
  • agent : (Entreprise uniquement) Ajoutez un bloc ai en ligne aux définitions de service, permettant à une charge de travail de déclarer son rôle AI (inference-model, mcp-server ou ai-agent) et sa configuration spécifique au rôle en un seul enregistrement via des fichiers de configuration et des API HTTP. [GH-13032]
  • Passerelle api : ajoutez http2 et grpc en tant que protocoles d'écoute de passerelle API valides, permettant HTTP/2 et gRPC de bout en bout de client au backend. Auparavant, seuls les http et tcp étaient acceptés ; la passerelle rétrograderait silencieusement le trafic gRPC/HTTP2 vers HTTP/1.1 sur le saut en amont. Les nouveaux protocoles restituent le gestionnaire de connexion HTTP en aval correct (codec HTTP/2, h2,http/1.1 ALPN) et alignent le cluster en amont sur HTTP/2, comblant ainsi l'écart de parité avec Ingress Gateway. [GH-23784]
  • Passerelle api : enregistrement automatique du DNS pour les services exposés via une passerelle API, résoluble sur <service>.api-gateway.consul. Remplit le mappage du catalogue gateway-services pour les passerelles API et ajoute des SAN DNS au certificat feuille API Gateway Connect, amenant la passerelle API à la parité avec la passerelle Ingress. La fonctionnalité est dépendante de la version et remplit automatiquement les passerelles préexistantes une fois que tous les serveurs sont mis à niveau. [GH-23647]
  • Passerelle api : prend en charge la terminaison TLS en aval sans contact. Lorsque TLS { Enabled = true } est défini sur une entrée de configuration api-gateway sans certificat en ligne/système de fichiers/SDS, la passerelle met fin à TLS en aval à l'aide de son certificat feuille Connect CA (avec les SAN DNS *.api-gateway.consul). Les certificats configurés explicitement continuent d'avoir la priorité et sont servis en tant que remplacements SNI aux côtés de la chaîne feuille par défaut. [GH-23647]
  • Passerelle api : ajoutez PassiveHealthCheck aux limites en amont par défaut au niveau de la passerelle et acheminez les remplacements de limites au niveau du service, afin que la vérification de l'état passif (détection des valeurs aberrantes Envoy) puisse être configurée pour les services acheminés via une passerelle API. [GH-23783]
  • cli : (Enterprise uniquement) consul connect envoy -gateway=inference lance le processeur de stratégie aux côtés d'Envoy et applique une version minimale d'Envoy pour la passerelle d'inférence. Le socket ext_proc est dérivé par instance de proxy ; -ext-proc-socket-dir remplace son répertoire (/var/run/consul par défaut).
  • connect : (Enterprise uniquement) Ajout d'un cycle de vie OAuth client géré par agent pour les services avec ai.role de ai-agent ou mcp-server, y compris l'enregistrement dynamique de client avec IBM Security Verify, la rotation des clés, la publication JWKS et la livraison SDS des informations d'identification OAuth client aux side-cars ai-agent Envoy.
  • connect : (Enterprise uniquement) Délivrez les informations d'identification side-car OAuth sous forme d'enveloppes AES-256-GCM. Les clés de chiffrement de contenu sont conservées dans KV et servies via WorkloadKeyService.FetchKey afin que consul-obo-outbound puisse déchiffrer sans devenir un SDS client.
  • connect : (Enterprise uniquement) Câblez les filtres ext_proc consul-obo-outbound et consul-obo-inbound dans connect-proxy xDS pour un échange de jetons au nom de hop-bound.
  • connect : (Entreprise uniquement) Enregistrez les services avec ai.role de ai-agent ou mcp-server avec IBM Security Verify à l'aide de private_key_jwt, conservez DCR/JWKS dans KV et fournissez les informations d'identification client à Envoy en tant que SDS GenericSecret JSON pour les charges de travail ai-agent. Cluster IAM est une méthode d'authentification OIDC ACL avec EnableServiceDCR=true (l'agent oauth.iam HCL est rejeté).
  • Connect : ajoutez ecdh_curves aux entrées de configuration mesh (MeshDirectionalTLSConfig) et tls_ecdh_curves à la configuration de l'agent TLS (TLSProtocolConfig) pour prendre en charge la configuration des courbes ECDH/KEM autorisées pour le side-car mTLS et l'agent RPC/HTTPS/gRPC, avec injection automatique de courbe hybride Post-Quantum X25519MLKEM768 lorsque tls_min_version est réglé sur TLSv1_3. [GH-23884]
  • Portes de fonctionnalités : ajoutez un cadre de portes de fonctionnalités dynamiques soutenu par Raft (phase 1). Un nouveau bloc de configuration du serveur feature_gates { bootstrap = { ... } } amorce la première stratégie Raft. Le leader concilie en permanence la politique souhaitée, l’éligibilité à la version minimale et les valeurs par défaut du registre dans un statut résolu résolu. Chaque serveur exécute un cache atomique alimenté uniquement à partir de l'état FSM validé ; les agents consomment un instantané résolu indexé et échouent jusqu'à ce que la première génération soit livrée. Les nouvelles commandes d'opérateur CLI consul operator feature list, get et set permettent une inspection et un contrôle sécurisés par CAS et protégés par ACL des portes de fonctionnalités.
  • Opérateur : ajoutez les points de terminaison HTTP GET /v1/operator/features, GET /v1/operator/feature/:name et PUT /v1/operator/feature/:name pour lire et mettre à jour l'état de la porte de fonctionnalité. Les lectures nécessitent operator:read ; les écritures nécessitent operator:write. Toutes les lectures sont capables de bloquer les requêtes. [GH-23791]
  • inference-gateway : (Enterprise uniquement) Acheminez les modèles d'inférence externes activés via une passerelle de terminaison. Les modèles marqués avec la sortie de la passerelle de terminaison sont découverts à partir du catalogue, résolus via la chaîne de découverte de maillage et équilibrés en charge sur des réplicas de passerelle de terminaison sains, avec des niveaux de priorité de pool de capacités et un comportement de fermeture en cas d'échec lorsqu'aucun transport valide n'est disponible. Un pool de capacités contenant un modèle externe est rejeté et son itinéraire de capacités renvoie 503, lorsque deux de ses modèles affichent la même adresse de point de terminaison ou que ses pondérations de modèle ne peuvent pas être représentées exactement.
  • inference-gateway : (Enterprise uniquement) Ajoutez le type de service inference-gateway et l'entrée de configuration. La passerelle met fin au mTLS de maillage entrant, applique les intentions et applique les informations personnelles et la politique de routage via un filtre ext_proc à un processeur de politique colocalisé. Les modèles en amont sont des services enregistrés auprès de ai.role = "inference-model" que les intentions autorisent et qui sont accessibles via le maillage (connecté ou derrière une passerelle de terminaison). La passerelle s'y connecte via mTLS et les sélectionne par capacité, en basculant entre les fournisseurs par priorité.
  • télémétrie : (Entreprise uniquement) Ajout de métriques d'utilisation du produit côté serveur pour le nombre de méthodes d'authentification ACL (OIDC, Kubernetes, JWT) et la configuration de la journalisation d'audit.
  • télémétrie : (Entreprise uniquement) Ajout de métriques d'utilisation des produits côté serveur pour le nombre de modes de passerelle maillée : consul.usage.mesh_gateway_remote.count et consul.usage.mesh_gateway_local.count signalent le nombre d'instances de service configurées pour utiliser chaque mode de passerelle maillée, et consul.usage.mesh_gateway_none.count signale le nombre d'instances de service sans mode de passerelle maillée explicite (non défini ou none).
  • télémétrie : (Entreprise uniquement) Ajout de métriques d'utilisation des produits côté serveur pour la stratégie par défaut d'intention de service, les intentions de service L7 et les nombres JWT
  • télémétrie : (Entreprise uniquement) Ajout de la métrique d'utilisation du produit côté serveur consul.usage.mesh_gateway_enabled, qui indique si une instance de passerelle maillée est enregistrée dans le cluster. Il est indépendant du nombre de modes de passerelle maillée : ceux-ci comptent les side-cars de connexion-proxy en fonction de leur mode de routage en amont, tandis que celui-ci indique si la capacité de passerelle est déployée ou non.
  • passerelle de terminaison : (Entreprise uniquement) Ajoutez une injection d'informations d'identification basée sur Vault à la sortie de la passerelle de terminaison. Une entrée de configuration TerminatingGateway comporte désormais un bloc CredentialInjection (chemin UDS du processeur ext_proc et délai d'expiration du message) et chaque service lié peut déclarer une liaison Credential (Mode: "inject" avec un BindingID). À la sortie, un filtre ext_proc appelle un processeur colocalisé qui injecte les informations d'identification liées (par exemple, une clé de fournisseur API provenant de Vault) dans la requête en amont, de sorte que les informations d'identification ne soient jamais stockées dans la configuration de maillage ni exposées aux clients.
  • xds : ajoutez un écouteur UDP « DNS virtuel » en ligne (127.0.0.1:8653) qui sert une table FQDN vers VIP en mémoire dérivée de l'instantané du proxy. Il annonce les VIP pour les amonts explicites, les amonts autorisés intentionnellement en mode proxy transparent et les amonts d'appairage de cluster, tout en ignorant les VIP entre partitions, les chaînes de découverte périmées/non autorisées et les entrées vides ou non IP afin que les réponses DNS restent synchronisées avec ce que l'écouteur proxy transparent va réellement intercepter. Ajoutez un écouteur UDP « DNS de sortie » facultatif (127.0.0.1:8654) qui transmet les requêtes aux récurseurs DNS configurés par l'agent via c-ares lorsque des récurseurs sont présents. Étendez l'interface xDS ConfigFetcher (et l'implémentation de l'agent) pour exposer les récurseurs DNS. [GH-23698]

  • agent : (Entreprise uniquement) Correction de PUT /v1/kv/ afin que les corps de requêtes fragmentés soient délimités par kv_max_value_size, correspondant à la vérification Content-Length existante.
  • proxycfg : Correction d'une fuite de goroutine et de mémoire où les surveillances d'un proxy continuaient de fonctionner après l'arrêt inattendu de son état, car le remplacement, la désinscription ou la fermeture d'un état arrêté ne les annulait pas. [GH-23990]
  • proxycfg : Correction d'une fuite de goroutine et de mémoire où les proxys transparents enregistraient une nouvelle surveillance de santé pour chaque service appairé importé à chaque fois que la liste des services importés changeait, et n'arrêtaient jamais la surveillance des services en amont supprimés. [GH-23990]
  • télémétrie : restaurez les métriques Raft, Serf et Memberlist dans les artefacts de version en créant avec la balise hashicorpmetrics. [GH-23813]
  • agent/xds : correction d'un problème où les requêtes inter-clusters et appairées provenant d'une passerelle API étaient rejetées avec HTTP 403 interdit par les intentions RBAC du service en aval. Les champs séparés par des points-virgules dans le composant de certificat client de l'en-tête x-forwarded-client-cert (XFCC) (tels que les SAN DNS auto-enregistrés) sont désormais correctement acceptés par l'expression régulière principale RBAC. [GH-23920]
  • cli : (Entreprise uniquement) consul intention create crée et remplace désormais les intentions via l'intention exacte (entrée de configuration) API utilisée par l'interface utilisateur, qui prend en charge les partitions d'administration autres que celles par défaut (par exemple -partition team-a). Les métadonnées par source (-meta) continuent d'utiliser l'intention héritée obsolète API et ne sont prises en charge que dans la partition par défaut ; la combinaison de -meta avec une partition autre que celle par défaut échoue désormais avec une erreur claire et exploitable. Pour attacher des métadonnées aux intentions dans une partition d'administration, utilisez une entrée de configuration service-intentions avec Meta d'entrée de gamme via consul config write.
  • connect : (Entreprise uniquement) Attachez l'OBO sortant uniquement pour les plans d'identité en amont (ai-agent / mcp-server). Les amonts HTTP explicites vers les destinations de passerelle d'inférence ou de modèle d'inférence ne reçoivent plus de consul-obo-outbound et échouent avec « Audience OBO non configurée ».
  • Connect : correction d'un bug où les serveurs Consul ignoraient le default_intention_policy configuré pour trois surfaces côté serveur – la vérification d'intention API (consul intention check, GET /v1/connect/intentions/check), la vue de la topologie du service (Internal.ServiceTopology) et la découverte transparente en amont du proxy (Internal.IntentionUpstreams) – et revenaient à la place à acl.default_policy. Cela ne change le comportement que lorsque default_intention_policy et acl.default_policy sont définis sur des valeurs opposées ; lorsqu'ils sont d'accord (ou que default_intention_policy n'est pas défini), il n'y a aucun changement. Avec default_intention_policy=deny et acl.default_policy=allow, la vérification API et la topologie signalaient précédemment les connexions comme autorisées même si elles avaient été refusées ; avec default_intention_policy=allow et acl.default_policy=deny, les side-cars proxy transparents sous-provisionnaient leurs amonts et pouvaient ne pas parvenir à atteindre les services qu'ils étaient autorisés à atteindre. L’application du RBAC de l’Envoy n’a pas été affectée et a déjà honoré default_intention_policy.
