Pour les déploiements non-Kubernetes, transmettez <code>--cache-embedded-node-name=<name></code> avec une valeur qui identifie de manière unique chaque nœud.</p> </div> </div> <div classe="sect3"> <h4 id="_automatic_non_blocking_index_creation_for_large_tables">Création automatique d'index non bloquant pour les grandes tables</h4> <div class="paragraphe"> <p>Lors de la mise à niveau de Keycloak avec de grandes tables de base de données, la création d'index était auparavant ignorée lors de la migration du schéma pour éviter de bloquer le démarrage. Les opérateurs devaient créer manuellement les index manquants.</p> </div> <div class="paragraphe"> <p>Keycloak crée désormais automatiquement les index ignorés en arrière-plan après le démarrage à l'aide de la création d'index non bloquante sur PostgreSQL, Oracle, MySQL/MariaDB et les éditions Microsoft SQL Server prises en charge. Les index PostgreSQL non valides laissés par des tentatives précédentes infructueuses sont détectés et recréés automatiquement. Sur les bases de données sans support non bloquant, Keycloak continue de consigner le SQL pour une exécution manuelle.</p> </div> </div> <div classe="sect3"> <h4 id="_vert_x_based_outbound_http_client_experimental">HTTP sortant basé sur Vert.x client (expérimental)</h4> <div class="paragraphe"> <p>Keycloak utilise Apache HTTP Client pour toutes les connexions sortantes vers des services externes tels que les fournisseurs d'identité, les répondeurs OCSP et les points de terminaison de déconnexion du canal arrière. Comme Keycloak s'exécute déjà sur Vert.x/Netty pour le trafic entrant, l'utilisation d'une pile HTTP distincte pour les connexions sortantes ajoute une complexité et une surcharge de dépendance inutiles.</p> </div> <div class="paragraphe"> <p>Keycloak fournit désormais un HTTP client expérimental basé sur Vert.x qui remplace le HTTP Apache Client par Vert.x/Netty pour toutes les connexions sortantes. Pour l'activer, démarrez Keycloak avec <code>--features=http-client:v2</code>.</p> </div> <div class="paragraphe"> <p>Lorsque cette option est activée, tout le trafic HTTP sortant utilise le Vert.x HTTP client. Les options de configuration existantes fonctionnent de la même manière.</p> </div> <div class="paragraphe"> <p>Pour plus de détails, consultez le guide <a href="https://www.keycloak.org/server/outgoinghttp">Configurer les requêtes HTTP sortantes</a>.</p> </div> </div> <div classe="sect3"> <h4 id="_helm_chart_operator_install_experimental">Installation de Helm Chart Operator (expérimental)</h4> <div class="paragraphe"> <p>Keycloak publie désormais une charte Helm expérimentale pour installer l'opérateur.</p> </div> <div class="paragraphe"> <p>Pour les instructions d'installation, consultez le <a href="https://www.keycloak.org/guides#operator">Guide de l'opérateur</a>.</p> </div> </div> </div> <div classe="sect2"> <h3 id="_organizations">Organisations</h3> <div classe="sect3"> <h4 id="_shared_identity_providers_across_organizations">Fournisseurs d'identité partagés entre les organisations</h4> <div class="paragraphe"> <p>Les fournisseurs d'identité peuvent désormais être liés à plusieurs organisations, ce qui permet des scénarios tels qu'un seul fournisseur d'identité d'entreprise au service des utilisateurs de différentes unités commerciales ou filiales, chacune représentée comme une organisation distincte. Chaque domaine peut spécifier indépendamment quel fournisseur d'identité gère l'authentification et si les utilisateurs sont automatiquement redirigés. La porte de domaine garantit une isolation inter-organisations  :  un utilisateur est automatiquement ajouté automatiquement à une organisation qui revendique son domaine de messagerie, même lorsque plusieurs organisations partagent le même fournisseur d'identité.</p> </div> <div class="paragraphe"> <p>Nouveaux liens de fournisseur d'identité créés après la mise à niveau par défaut vers le type d'adhésion non géré.
