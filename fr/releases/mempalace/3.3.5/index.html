mempalace v3.3.5

3.3.5 est une version de correctifs. Aucune nouvelle fonctionnalité destinée aux utilisateurs : l'énergie du cycle a été consacrée à l'intégrité des données, à la récupération et à l'exactitude de tous les processus. Si votre palais a déjà atteint Internal error: Error finding id après une grosse mine, ou si un triple graphe de connaissances a disparu silencieusement dans le vide, ou si vous utilisez Windows/un hôte multi-tenant, cette version est pour vous. Le titre corrige :

  • mempalace repair --mode from-sqlite récupère les palais bloqués sur apply_logs. Lorsque l'écrivain de segment HNSW de ChromaDB se coince (la classe de corruption signalée en amont et dans #1308), --mode legacy et la réparation en ligne appellent tous deux Collection.count() comme première lecture - ce qui est exactement l'appel qui se déclenche. L'ancien mode d'échec était une impression de réparation Cannot recover — palace may need to be re-mined from source files même si les tables SQLite étaient entièrement intactes. Le nouveau mode lit (id, document, metadata) directement à partir de chroma.sqlite3 via la jointure de segment de métadonnées, n'ouvre jamais de chromadb client contre le palais corrompu et réinsère le tout dans un nouveau palais sous votre fonction d'intégration configurée. Vérifié de bout en bout sur un palais corrompu réel de 52 300 rangées. (#1308)
  • Deux classes de perte silencieuse dans le graphe de connaissances sont désormais des erreurs de temps d'écriture. Les triples avec valid_to < valid_from étaient auparavant stockés de manière durable mais inaccessibles (le filtre temporel ne correspondait à aucun as_of) ; add_triple() rejette désormais les intervalles inversés au moment de l'écriture. Et les chaînes de date transmises à SQLite sont validées à l'avance via sanitize_iso_temporal() (alias sanitize_iso_date()), qui accepte YYYY-MM-DD et les dates-heures canoniques UTC (YYYY-MM-DDTHH:MM:SSZ / +00:00) et rejette tout le reste - les entrées en langage naturel comme "yesterday" ne produisent plus silencieusement des ensembles de résultats vides. Changement de comportement : les entrées de date partielle qui fonctionnaient dans 3.3.4 ("2026", "2026-05") génèrent désormais une erreur ; transmettez plutôt une date complète ou une date/heure UTC canonique. (#1214, #1164, #1167, #1374, #1417)
  • EntityRegistry.save() est désormais sécurisé en cas de crash. La carte des personnes/projets contient des mois de données d'exploration de données, et l'ancien code générait un Path.write_text() non atomique — une perte de puissance, un MOO ou un kill -9 entre tronquer et vider complètement l'effacerait silencieusement (le load() du registre avale JSONDecodeError). Enregistrer écrit maintenant dans un fichier temporaire frère, les fsync et les os.replace() en place. Le registre précédent reste intact en cas de crash avant le retour du changement de nom. (#1215)
  • Le MCP tool_search traverse la fenêtre de vidage HNSW post-mine en masse. Après une mine CLI, les métadonnées du segment HNSW de ChromaDB peuvent être dévidées pendant environ 30 à 60 s ; La recherche MCP à l'échelle de l'aile frappait Internal error: Error finding id pendant toute cette fenêtre. tool_search détecte désormais ce transitoire spécifique, supprime les caches MCP-local et backend partagé pour le palais, dort 2 secondes et réessaye une fois. Les tentatives réussies sont marquées avec index_recovered: true afin que les appelants puissent observer le moment où il s'est déclenché. Correctif partiel pour le cluster #1315 plus large : tool_check_duplicate et d'autres outils de toucher d'index ont toujours besoin du même wrapper. (#1396)
  • Correction des processus croisés sur Windows et les hôtes multi-tenants. ChromaBackend.close_palace() libère désormais correctement le verrouillage de fichier SQLite côté rust de ChromaDB — rouvrant le même chemin de palais après l'échec de shutil.rmtree avec SQLITE_READONLY_DBMOVED. Et le _kg du serveur MCP n'est plus un singleton au niveau du module : les hôtes multi-locataires faisant tourner MEMPALACE_PALACE_PATH entre les appels d'outils accèdent désormais au bon fichier SQLite via un cache paresseux par chemin. (#1067, #1105, #1136, #1160)
  • Windows stdio est UTF-8 dans tous les domaines. Les invocations mempalace search > out.txt et canalisées fact_checker ne mojibakent plus le texte du tiroir cyrillique/CJK à la limite du processus. mcp_server, hooks_cli et cli/fact_checker se reconfigurent tous de manière identique. (#1282)
  • Correction de routage miner.detect_room pour monorepos. La vérification de sous-chaîne était bidirectionnelle, donc tout jeton qui était une sous-chaîne d'un nom de salle ou vice versa correspondait — views/billing-page/src/Foo.test.tsx acheminé vers une salle interviews car "views" in "interviews" correspondait en premier. Utilise désormais la correspondance de jetons délimitée par un séparateur (-, _, ., /). (#1004, ferme le #1002)
  • mempalace compress ne plante plus sur les palais de plus de 32 000 tiroirs. La récupération des tiroirs est désormais paginée, reflétant le correctif #851 dans miner.py. (#1073, #1107) Interne : la fiabilité des tests a également été réussie — tests/test_palace_locks.py et tests/test_chroma_collection_lock.py sont passés de fork à spawn pour la génération de sous-processus (Python 3.13 + parent multithread = blocage sous fork, et macOS interdit le fork sans exécution via CoreFoundation), et plusieurs fichiers de test enveloppent désormais sqlite3.connect(...) dans contextlib.closing() afin que les connexions soient libérées. le chemin de l’échec aussi. (#1430, #1431) Les promesses n'ont pas bougé. Chaque mot stocké exactement. Tout reste sur votre machine. Pas de télémétrie. Pas de solutions de repli vers les cloud API dont nous ne vous avons pas parlé. Chaque version affine ce qui existe déjà.
