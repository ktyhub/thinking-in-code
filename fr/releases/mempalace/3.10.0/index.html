mempalace v3.10.0

Les agents disposent de moyens plus simples : un serveur MCP à 3 outils avec Palace Query Language, des règles de cerveau partagé pour les identités host:harness:project et une recherche de vecteur exact native en option. Les nouvelles installations suivent XDG et les correctifs de stockage ferment un chemin de perte d'écriture silencieux, un refus d'intégrité macOS et plusieurs blocages.

Notes de mise à niveau

  • mempalace rules n'accepte plus --agent. Passez --host, --harness et --project, puis restituez tout bloc de cerveau partagé installé. (#2508)
  • get_collection() refuse les noms que MemPalace ne lit jamais. Tout nom autre que la collection de tiroirs configurée ou mempalace_closets déclenche CollectionNameMismatchError ; les scripts de maintenance peuvent transmettre _skip_name_check=True. (#2446)
  • La liste des événements MCP renvoie les événements les plus récents en premier lorsqu'aucun curseur n'est donné. mempalace_event_list et palace_coordinate sont désormais par défaut les plus récents en premier, à moins que since_event_id ou order ne soient transmis ; mempalace logstream list et Logstream.list_events() sont toujours par défaut le plus ancien en premier. (#2497)
  • Les nouvelles installations conservent la configuration et le palais sous ~/.config/mempalace (ou $XDG_CONFIG_HOME/mempalace). Les installations ~/.mempalace existantes restent inchangées. (#148)

Performances et architecture (moteur Rust à double piste)

  • Accélération vectorielle exacte native Rust en option (rust_exact). Lit le format SQLite existant dans un tampon flottant contigu, utilise Rayon pour les analyses volumineuses, et lance le Python GIL. Écritures locales et externes invalider le cache natif. Le chargement s'étend à la collection et décode les blobs en toute sécurité ; les analyses en série et en parallèle préservent l'ordre déterministe des liens. Les filtres complexes et les extensions natives absentes reviennent à Python.

  • Vecteur natif autonome CLI et roues en option. Les versions GitHub incluent des roues natives et des exécutables de plate-forme. Le CLI accepte les vecteurs d'intégration JSON via --vector ou stdin ; il n'intègre pas envoyez un SMS ou nécessitez Python. Les bibliothèques d'exécution de la plateforme peuvent toujours être requises.

  • Optimisation NumPy top-k. Cachez les normes vectorielles et les distances de partition avant de trier les éléments sélectionnés résultats, en préservant les liens d’ordre des lignes à la coupure.

  • Les opérations de recherche en lecture seule cessent de rivaliser avec les baux des écrivains du palais. searcher.py et _open_search_collection ouvrent désormais explicitement les collections avec read_only=True. Les requêtes en lecture seule se connectent en mode lecteur SQLite WAL sans tenter d'initialisation de schéma ou de verrouillage de bail d'écriture, permettant aux recherches CLI et d'agent de s'exécuter simultanément avec un serveur MCP ou un processus d'écriture en arrière-plan actif sans déclencher MineAlreadyRunning.

Refacteurs

  • Le serveur MCP est un package, pas un module de 8 000 lignes. mempalace.mcp_server reste le chemin d'importation public (TOOLS, handle_request, main, chaque gestionnaire tool_* et les noms globaux du processus testent Monkeypatch). L'implémentation réside dans les fichiers de domaine sous mempalace/mcp_server/ afin que les PR puissent cibler les tiroirs, KG, la coordination, le protocole ou HTTP sans entrer en collision avec un seul fichier divin. Les fragments s'exécutent dans l'espace de noms du package - une division physique, pas un changement de comportement.
  • CLI est un package, pas un module de 4 000 lignes. mempalace.cli reste le chemin d'importation public (main, chaque gestionnaire cmd_* et les noms des tests singepatch). L'implémentation réside dans les fichiers de domaine sous mempalace/cli/ afin que les PR puissent cibler init, mine, rechercher, réparer, logstream ou argparse sans entrer en collision avec un seul fichier divin. Les fragments s'exécutent dans l'espace de noms du package - une division physique, pas un changement de comportement.
  • Les tests du serveur MCP sont divisés par domaine. tests/test_mcp_server.py est désormais tests/mcp/ (protocole, lecture, recherche, écriture, journal, KG, gardes, bibliothèque obsolète) afin que les PR MCP communautaires n'entrent pas en collision sur un fichier de test de 8 600 lignes. Les aides partagées vivent dans tests/_mcp_server_helpers.py.
  • Searcher est un package, pas un module de 2 200 lignes. mempalace.searcher reste le chemin d'importation public (search, search_memories, SearchError et les assistants testent Monkeypatch). L'implémentation se déroule sous mempalace/searcher/ (classement, filtres, sqlite BM25, candidats, requête, CLI, rendu) afin que les PR puissent cibler une seule couture. Les fragments s'exécutent dans l'espace de noms du package - une division physique, pas un changement de comportement.
  • Palace ops est un package, pas un module de 1 800 lignes. mempalace.palace reste le chemin d'importation public (get_collection, mine_lock, mine_palace_lock, les assistants de placard et les noms tests Monkeypatch). L'implémentation se déroule sous mempalace/palace/ (collection, backend, placards, serrures de mine, ensemble miné) afin que les PR puissent cibler une couture. Les fragments s'exécutent dans l'espace de noms du package - une division physique, pas un changement de comportement.

Fonctionnalités

  • Les règles de cerveau partagé utilisent une identité host:harness:project et peuvent nommer l'une ou l'autre des surfaces d'outils MCP. mempalace rules prend --host, --harness et --project (jetons minuscules stables) au lieu de --agent, plus --mcp full|light : full (par défaut) nomme les outils mempalace-mcp à 45 outils, et light nomme les outils mempalace-mcp. Triade palace_query / palace_exec / palace_coordinate à prose identique. Le bloc rendu permet aux agents de composer l'identité à partir de leur espace de travail actuel, de parcourir la boîte de réception lorsqu'ils commencent à collaborer au lieu d'armer un observateur au début de la session, et d'armer le logstream watch uniquement lorsqu'on leur demande d'écouter, après avoir revendiqué une tâche ou après avoir délégué. logstream watch --agent définit désormais par défaut --state-file sur ~/.mempalace/watch/<agent>.json avec _ doublé et : nettoyé en _, de sorte que les identités Windows host:harness:project n'ont pas besoin de chemin privé. (#2508)
  • mempalace-light-mcp : un serveur MCP à 3 outils avec Palace Query Language. palace_query, palace_exec et palace_coordinate couvrent la recherche, la taxonomie, KG, les graphiques, les agendas, les tiroirs, l'exploitation minière, les tunnels et la coordination RFC 003 via une chaîne PQL d'une ligne (FIND "oauth" IN backend/auth LIMIT 5) ou un dict structuré, soit environ un quart du schéma de 45 outils. (10.6 Ko contre 41.6 Ko). Les écritures passent par les mêmes gestionnaires de nettoyage, de sorte que le texte du tiroir reste textuel ; le classement de recherche est inchangé, stdio est le hub en premier et --read-only refuse palace_exec et palace_coordinate. Enregistrez-le à côté du serveur complet plutôt qu'à sa place : claude mcp add mempalace-light -- mempalace-light-mcp. (#2412)
  • La configuration suit la spécification du répertoire de base XDG sur les nouvelles installations. L'ordre de résolution est $MEMPALACE_CONFIG_DIR, puis un ~/.mempalace existant contenant config.json, people_map.json ou palace/chroma.sqlite3, puis $XDG_CONFIG_HOME/mempalace (valeurs absolues uniquement), puis ~/.config/mempalace. Les installations existantes conservent ~/.mempalace et palace_path est par défaut <config_dir>/palace. (#148)
  • CLI écrit en respectant la politique de routage d'écriture du démon. mine, sweep, sync et la mine post-installation dans init suivent direct / prefer / require de MEMPALACE_CLI_WRITE_ROUTING ou write_routing.cli dans config.json, avec --daemon / --direct comme remplacements par commande. La valeur par défaut reste direct, donc rien ne change sauf si vous l'acceptez. Une fois qu'un travail est soumis au démon, il n'est jamais réexécuté directement en cas d'erreur, puisque le démon l'a peut-être déjà accepté. sweep est désormais un travail démon. (#2033)
  • Les flottes pgvector peuvent partager un ensemble de tables sur plusieurs machines. L'opt-in pgvector_shared_namespace (clé de configuration, MEMPALACE_PGVECTOR_SHARED_NAMESPACE ou option backend shared_namespace) remplace le hachage du chemin du palais dans le préfixe de la table, de sorte que les nœuds avec des chemins de palais locaux différents lisent et écrivent les mêmes tables. Non définis, les préfixes restent inchangés octet par octet ; la valeur est strictement normalisée et enregistrée dans le marqueur backend. (#2167)
  • Les poids de rang hybride sont configurables. MEMPALACE_HYBRID_VECTOR_WEIGHT / MEMPALACE_HYBRID_BM25_WEIGHT, ou hybrid_rank_vector_weight / hybrid_rank_bm25_weight dans config.json. Les valeurs par défaut restent 0.6 / 0.4, et les valeurs mal formées y reviennent. (#2430)
  • Tiroirs last_modified. Nouveaux tiroirs à partir de filed_at ; chaque update_drawer qui change de contenu, d'aile ou de pièce le tamponne à nouveau tandis que filed_at conserve l'heure de création. Les anciens tiroirs signalent filed_at comme leur last_modified. (#2147)
  • Les résultats de recherche indiquent d'où viennent leurs dates. Les résultats vectoriels, syndicaux et lexicaux uniquement renvoient filed_at, authored_at_source, content_date et content_date_source (filename, frontmatter, body, mtime ou unknown). La provenance est enregistrée à l’époque de moi et n’a jamais été reconstituée pour les tiroirs hérités. (#2453)
  • mempalace_kg_timeline pagine. limit / offset suivent la convention list_drawers ; le plafond des 100 premiers codés en dur a disparu. (#2406)
  • Les listes Logstream présentent par défaut les événements les plus récents lorsqu'aucun curseur n'est donné. mempalace_event_list et palace_coordinate renvoient les événements les plus récents en premier lorsque order est omis et qu'aucun since_event_id n'est transmis, et conservent l'ordre croissant lors de la reprise à partir d'un curseur ; un order explicite gagne toujours et est insensible à la casse. Le schéma palace_coordinate du serveur léger expose désormais order, limit, preview et since_created_at. (#2497)
  • dynamics.effective_strength() calcule la dégradation de la connexion au moment de la lecture. Il est pur, donc la lecture d'une force ne peut pas la modifier et les passes de maintenance répétées ne peuvent pas aggraver la dégradation comme le fait le apply_decay. Le module docstring ne revendique plus les couloirs et les tunnels déjà potentialisés ou délabrés. (#2416)
  • Plugin MemPalace pour DeepSeek Harness (.dsh-plugin/). Un plugin bundle DSH avec trois lignes, construit sur les points d'extension DSH 0.1.5. mempalace-recall place mempalace wake-up pour l'aile du projet dans l'invite système de chaque session de niveau supérieur à partir de son premier appel de modèle ; DSH résout le texte d'invite avant que les plugins puissent attendre quoi que ce soit d'autre, de sorte que la ligne ne contient que le premier assembly, pendant une durée limitée, et n'échoue jamais à l'étape. mempalace-autosave conserve une transcription en annexe uniquement par session sous $DSH_HOME/mempalace/transcripts/, contenant uniquement ce que l'utilisateur a écrit et le texte de l'assistant (ne jamais exploiter le contexte, les résultats de l'outil, les résumés de raisonnement ou de compactage), et exécute les propres crochets stop, precompact et session-end de MemPalace via le nouveau harnais dsh. mempalace-mcp dessert le palais via le MCP client de DSH avec mempalace-light-mcp : ses 3 outils coûtent environ 2 100 jetons de schéma par étape de modèle, contre environ 7 700 pour le serveur de 45 outils. Une suite node --test couvre le plugin et tests/test_dsh_plugin.py l'exécute sous pytest.

Améliorations

  • repair indique quand il declines une guérison FTS5 sur place, et nomme le SQLite qui a décidé. Declining était un return silencieux sur deux chemins, donc l'opérateur a vu la bannière ABORT sans aucun signe indiquant qu'une reconstruction avait été envisagée ; --dry-run a retenu la même explication. Tous l'impriment maintenant et la copie --dry-run est marquée comme aperçu afin qu'elle ne puisse pas être lue comme l'exécution qu'elle prédit. sqlite3.sqlite_version accompagne chaque verdict de ces chemins - la bannière d'abandon, les deux branches --dry-run, la ligne de résultat de la guérison, la vérification après récupération, les trois formes de la charge utile d'intégrité MCP, la charge utile de refus d'outil, la ligne de journal d'intégrité et le message de MineValidationError - car un résultat propre d'une construction qui ne peut pas détecter une erreur FTS5 donnée se lit exactement comme celui d'une construction qui le peut. Le validateur post-mine signale à warning plutôt qu'à info, le niveau qui survit sur le chemin mempalace mine, qui ne configure aucune journalisation. (#2240, #2254)
  • Une sonde d'intégrité de démarrage ignorée n'est plus signalée comme un verdict sans équivoque. Au-dessus de MEMPALACE_STARTUP_INTEGRITY_MAX_MB, aucun quick_check ne s'exécute, mais la charge utile MCP a répondu à checked: true, ok: true. Il renvoie maintenant la forme non applicable avec le saut comme reason, et cette raison indique les tailles suffisamment précisément pour montrer la comparaison qu'elle rapporte - une base de données 1.4 Mo par rapport à une limite de 1 Mo utilisée pour lire comme "est 1 Mo, au-dessus de la limite de 1 Mo". Écrivez la porte des outils sur les erreurs enregistrées plutôt que sur ok, donc rien n'est nouvellement refusé, et /statusz ne transforme plus un verdict manquant en un échec - ok n'est faux que lorsqu'une vérification est revenue sale, ce qui empêche également un backend non-chroma de se signaler malsain (#1931). (#2240, #2254)
  • Le classificateur FTS5 est ancré au début de la ligne quick_check. sqlite_integrity_errors signale un échec de sonde comme PRAGMA quick_check failed: <error>, et une correspondance non ancrée lit une telle ligne comme une erreur FTS5 isolée — autorisant une reconstruction sur une base de données dont l'état n'a jamais été établi. fts5: checksum mismatch, émis par SQLite 3.51.2, reste délibérément inégalé : il ne nomme pas quel côté est endommagé, et une reconstruction lit à partir de la table de contenu. (#2240, #2254)
  • list_drawers et graph_stats parcourent une collection Qdrant en un seul parchemin. BaseCollection.get_all_rows() rejoint get_all_metadata() lors de la lecture groupée portant les identifiants ; sa valeur par défaut passe toujours par get(limit=, offset=), et Qdrant le remplace par un seul parchemin où la boucle décalée avait coûté 275 s et 292 s sur un palais de 126 000 tiroirs. Le wrapper d’intégration transfère l’appel afin que le remplacement soit atteint. (#2452, #2474)
  • Le recalcul du couloir ne lit que l'aile minée. compute_hallways_for_wing a récupéré tous les tiroirs du palais sur chaque mine ; il parcourt désormais get(where={"wing": ...}) dans des pages délimitées, en conservant la protection à limite variable #1619, de sorte que le coût suit l'aile plutôt que le palais. Sur Qdrant, dont le get() fait toujours défiler les lignes du offset + limit pour chaque page, une aile plus grande qu'une page relit ses pages précédentes. (#2466, #2477)
  • CLI status lit les métadonnées du backend en un seul passage lorsque le décompte direct SQLite n'est pas disponible. Les palais Chroma sont toujours comptabilisés directement à partir de chroma.sqlite3. Sur le chemin de collection, utilisé par les backends tels que Qdrant, status() appelle désormais get_all_metadata() lorsque la collection l'expose au lieu de paginer avec get() : 1 min 46 s jusqu'à 3.4 s sur un palais Qdrant de 160 000 tiroirs. (#2153, #2154)

Corrections de bugs

  • Le chemin de transcription de secours ne donne plus à chaque arbre de travail git sa propre aile. Le chemin principal de _wing_from_transcript_path (lecture de cwd à partir du JSONL) a déjà réduit un segment <project>/.claude/worktrees/<wt> avant de dériver l'aile ; le chemin de repli, utilisé chaque fois que cwd est absent, n'avait pas de bande équivalente, donc le segment aplati --claude-worktrees-<wt> a survécu dans le nom de l'aile. J'ai appliqué le même effondrement là-bas. (#2388, #2454)
  • mempalace mine --daemon n'exploite plus le propre répertoire de travail du démon au lieu de celui de l'appelant. Le démon est un processus d'arrière-plan de longue durée qui conserve le cwd avec lequel il a commencé, donc une source relative (mempalace mine .) qui lui a été soumise a résolu ce cwd périmé plutôt que le répertoire à partir duquel l'appel CLI a réellement été exécuté, exploitant silencieusement le mauvais projet dans la mauvaise aile à chaque appel ultérieur piloté par hook. cmd_mine résout désormais la source en un chemin absolu avant qu'elle n'entre dans la charge utile du travail du démon, ce qui correspond à la résolution que _forward_mine_to_hub fait déjà pour le chemin de transfert du hub. (#2441, #2467)
  • mempalace init ne remplace plus un known_entities.json qu'il n'a pas pu lire avec les entités de cette exécution. La fusion lit le registre, revient à un dict vide lorsque la lecture ne se termine pas et réécrit le fichier dans son intégralité, de sorte qu'un registre contenant quatre catégories est devenu un contenant people: 1, mesuré, avec _load_known_entities passant de 10 noms à 1 et get_topics_by_wing de deux ailes à aucun, tandis que la commande s'imprimait. Registry updated. Rien de tout cela ne nécessite une écriture interrompue : via le CLI, un mempalace init a remplacé un tableau JSON de 28 octets et un objet tronqué de 172 octets, et un registre réenregistré dans un codage hérité a mis fin à l'exécution dans un traçage avant tout cela. Le rédacteur tronque également le fichier et le sérialise ensuite, de sorte qu'une exécution interrompue ou un disque plein laisse les mêmes types de fichiers. Les lectures traitent désormais uniquement FileNotFoundError comme un registre absent. Celui qui n'analyse pas, qu'il s'agisse d'une écriture tronquée, d'un octet qui n'est pas UTF-8, d'une édition manuelle qui a perdu une accolade ou d'un tableau JSON, est renommé de côté et son nouveau nom imprimé avant qu'un nouveau registre ne soit écrit, et celui qui existe mais ne peut pas être lu est laissé seul avec un message plutôt que écrasé. L'écriture elle-même passe par un fichier temporaire et un changement de nom, comme migrate._apply_topics_by_wing_renames l'a déjà fait pour ce même fichier, donc une exécution interrompue laisse l'octet de registre précédent pour octet. Un octet qui n'est pas UTF-8 a également cessé de laisser UnicodeDecodeError hors de l'appel, où mempalace init l'a rendu comme traceback. L'appel répond à None alors qu'il n'écrit rien, donc mempalace init n'imprime plus Registry updated sur un registre qu'il a laissé seul ; un registre atteint via un lien symbolique est écrit via celui-ci plutôt que remplacé ; un répertoire qui n'acceptera pas de fichier temporaire met en place la fusion avec un message plutôt qu'un traçage ; et une marque d'ordre d'octet UTF-8 n'est plus lue comme un échec d'analyse. (#2358, #2359)
  • repair-status ne signale plus une base de données qu'il n'a pas pu atteindre comme étant une base de données que le palais n'a jamais eue. repair.status a tracé cette ligne avec os.path.isfile, qui suit les liens symboliques et plie OSError et ValueError en False, donc Palace dir at … exists but has no chroma.sqlite3 yet et status: "uninitialized" sont revenus pour un palais dont la base de données était intacte derrière une autorisation de répertoire, pour celui dont le nom était devenu un lien symbolique brisé, et pour une boucle de lien symbolique - mot pour mot ce que dit un palais qui n'a vraiment pas de base de données. Ce que cette phrase invite, c'est une re-mine, qui, sur la forme du lien symbolique brisé, construit une deuxième base de données à côté de la première intacte et laisse derrière elle tout tiroir qui n'a pas de fichier source à dériver. L'absence est désormais décidée par ENOENT seul, le prédicat _integrity_target_is_absent #2290 a été ajouté, et une base de données inaccessible n'accepte plus ce retour anticipé : le rapport de capacité en dessous répond pour le palais à la place, imprimant sqlite count: (unreadable) et UNKNOWN. Une base de données vraiment absente rapporte toujours uninitialized. Passer cette porte place un état supplémentaire devant la lecture : un canal nommé, que os.path.isfile avait l'habitude de détourner et dont l'ouverture se gare dans le noyau jusqu'à ce qu'un écrivain arrive - à l'intérieur de sqlite3, où la réponse O_NONBLOCK utilisée par miner._read_text_no_follow n'est pas disponible. Ce qui empêche la lecture du stationnement est une vérification de type à côté de l'ouverture elle-même, dans sqlite_drawer_count ; la porte ci-dessus le répète uniquement pour que l'opérateur sache dans quel état il s'agit, au lieu du (unreadable), une autorisation produit également, et une vérification à la porte seule ne suffirait pas, car sous un répertoire, ce processus ne peut pas entrer dans son stat échoue et répond Faux par conception. Aucun autre type n'a besoin d'un cas : un répertoire, un socket, un périphérique bloc et un périphérique caractère ont chacun répondu par une erreur en moins d'une seconde et ont atterri dans ce même rapport illisible. La réponse imprimée et le dict renvoyé sont ce qui change ; le code de sortie était 0 pour tout cela avant et l'est toujours. (#2293, #2393)
  • Le réveil de la couche 1 récupère les tiroirs les plus récents au lieu d'une fenêtre d'analyse arbitraire. BaseCollection.get_recent() renvoie le N le plus récent de filed_at ; pgvector le remplace par un pushdown ORDER BY ... DESC LIMIT n (jeton de capacité supports_recency_order), et les backends sans pushdown conservent le comportement d'analyse et de tri précédent. Sur les palais plus grands que le plafond de numérisation de 2 000 tiroirs, le réveil ne mène plus avec le remplissage le plus ancien. La commande se fait sur le texte filed_at stocké, la même comparaison que la couche 1 a utilisée depuis #1630. (#1630, #2168)
  • Les points de contrôle résument la conversation, pas le harnais. Le texte injecté par l'outil avec role: "user" (expansion des commandes slash, blocs de commandes locales, notifications de tâches, préambules de compétences, espaces réservés d'images collées, enregistrements d'interruption) ne devient plus la ligne recent: du point de contrôle. La correspondance est ancrée à l'ouverture du message, donc un véritable message qui cite l'un de ces wrappers n'importe où après le premier caractère est toujours résumé. (#2170)
  • Le reniflage d'en-tête backend ne supprime plus les verrous POSIX du rédacteur WAL. detect() et _database_signature() ont ouvert la base de données du palais avec un simple open() sur presque tous les appels MCP ; sur POSIX, la fermeture de ce descripteur a libéré chaque verrou fcntl du processus détenu sur le fichier, y compris le verrou PARTAGÉ de l'écrivain WAL, de sorte que la fermeture propre d'une connexion externe pourrait contrôler et dissocier le -wal / -shm en direct de dessous. Le sniff ne perturbe plus les verrous du processus. (#2471, #2472)
  • macOS ne refuse plus tous les outils sur un palais WAL sain. SQLite d'Apple échoue à la première instruction d'une connexion en lecture seule lorsque les side-cars -wal / -shm sont absents, ce qui est l'état normal avant qu'un processus n'ouvre le palais, donc la porte d'intégrité a signalé le palais illisible. Cette affaire prend désormais un cours normal ; tout le reste conserve mode=ro. (#2489, #2490)
  • Une requête JSON-RPC mal formée qui transporte un id obtient une réponse au lieu du silence. Un method sans chaîne ou un params sans objet déclenché à l'intérieur du dispatch, donc stdio n'a rien écrit et HTTP a fermé le socket, laissant le client attendre ce id pour toujours. Les enveloppes mal formées renvoient désormais -32601 / -32602, et un échec d'envoi renvoie -32603. Les méthodes notifications/* ne reçoivent toujours jamais de réponse, comme auparavant. (#2231, #2232)
  • get_collection refuse un nom de collection que MemPalace ne lit jamais. Tout nom autre que la collection de tiroirs configurée et mempalace_closets génère CollectionNameMismatchError (un ValueError) au lieu de créer silencieusement un magasin orphelin que la recherche, le MCP et la réparation ne peuvent pas voir. Les scripts de maintenance peuvent transmettre _skip_name_check=True. (#2347, #2446)
  • Un index HNSW bloqué n'est plus signalé comme flush-lag. Lorsque index_metadata.pickle est absent, deux états qui ne se résolvent jamais d'eux-mêmes sont désormais nommés. Un hnsw:sync_threshold que la collection ne peut jamais atteindre est signalé comme flush_unreachable, avec la façon de forcer un vidage, et la recherche vectorielle reste activée. Un stub de remplacement dont la charge utile ne peut pas contenir le nombre SQLite est signalé comme diverged, avec mempalace repair comme correctif. Les deux nécessitent au moins 2 000 intégrations (dans le cas du stub, un déficit d'au moins 2 000), de sorte que les collections plus petites reçoivent toujours le rapport de décalage de vidage. (#2435)
  • Les décomptes impossibles dans un HNSW header.bin sont rejetés. Les capacités astronomiques et le nombre d'éléments supérieurs à la capacité alimentent désormais l'état du segment, la quarantaine de démarrage et le rapport de capacité avant que le lecteur natif de Chroma n'ouvre le segment. (#2146)
  • Les collections Chroma de vecteur appelant sont créées sans fonction d'intégration. Chroma a attaché DefaultEmbeddingFunction alors qu'aucun n'a été transmis et l'a conservé dans le schéma, donc une écriture de document uniquement sur une collection en 3 dimensions a tenté d'être intégrée à 384 dimensions. Les collections sont désormais créées et rouvertes sans EF, et échouent si elles sont toujours exposées. (#2141)
  • Les systèmes Chroma appartenant au backend sont arrêtés avant que le cache partagé ne soit vidé. Lors d'un changement d'inode externe ou de mtime, le backend a effacé le cache système global de processus de Chroma avant de fermer ses propres clients, de sorte que le System.stop() déplacé n'a jamais fonctionné. Les Clients que le backend ne possède pas, comme un PersistentClient directement construit, ne sont pas concernés par ce correctif. (#2421)
  • pgvector se reconnecte une fois lorsque Postgres abandonne la connexion groupée. Un redémarrage du serveur coûtait à chaque cli de longue durée une erreur terminating connection due to administrator command. SQLSTATE classe 57 et un handle fermé réessayent une fois sur une nouvelle connexion ; les erreurs au niveau des instructions se propagent toujours dès la première tentative. (#2084)
  • CLI search --wing / --room récupère du Error finding id de Chroma. Il utilise désormais la même solution de secours de requête filtrée que la recherche MCP. (#2373, #2380)
  • Un déploiement Codex non analysé n'est plus importé en tant que JSON brut. Un déploiement avec session_meta que l'analyseur installé ne peut pas normaliser est ignoré avec une raison enregistrée et reste éligible pour une nouvelle tentative après une mise à jour de l'analyseur ; les tiroirs existants sont intacts. (#2469)
  • mempalace_diary_read voit les entrées au-delà des 10 000 premiers. Il feuillette le journal de l'agent et conserve le last_n le plus récent, et total n'est plus plafonné. (#563, #2464)
  • Un backend qui ne parvient pas à s'initialiser n'est plus signalé en tant qu'écrivain homologue. Les échecs d'installation sont signalés séparément des conflits de bail, avec des instructions de récupération, et le MCP léger client transfère les écritures vers un hub en direct au lieu d'essayer d'abord de prendre le bail de l'écrivain local. (#2465)
  • Un démon occupé conserve son enregistrement. start_daemon a supprimé endpoint.json et le fichier pid après l'échec d'une sonde de santé, bloquant un démon vivant qui possédait toujours la serrure du palais. (#2442, #2473)
  • La suppression d'un PYTHONPATH divulgué conserve les propres packages de site de l'interpréteur en cours d'exécution. Un hôte d'intégration qui a placé le propre purelib / platlib du venv sur PYTHONPATH a perdu ses dépendances lors de l'importation. (#2484, #2496)
  • Un canal nommé sur chroma.sqlite3 n'empêche plus le serveur MCP de répondre. La sonde d'intégrité a ouvert le canal en lecture, qui attend l'arrivée d'un rédacteur, et les appels d'outils bloqués, mempalace_status, mempalace_reconnect et /statusz l'exécutent tous ou attendent derrière lui. Sur stdio, le premier appel de ce type a quitté la session sans répondre, y compris ping, jusqu'à ce que le chien de garde inactif mette fin au processus ; via HTTP, ces appels étaient suspendus tandis que ping et /healthz continuaient de répondre. La sonde refuse désormais le canal par type avant toute ouverture, comme le fait déjà repair-status, et le signale comme une erreur d'intégrité : les appels d'outils bloqués obtiennent le refus de -32002 le nommant, et python -m mempalace.repair rebuild s'arrête à la bannière d'abandon au lieu de se bloquer. (#2498)
  • Les hooks fonctionnent sur de nouvelles installations qui conservent leur configuration sous ~/.config/mempalace. Depuis #148, une nouvelle installation écrit sa configuration et son palais dans le répertoire de configuration XDG et ne crée jamais ~/.mempalace, mais le kill-switch des hooks n'a recherché que ~/.mempalace, donc les hooks Stop, PreCompact et SessionEnd ont renvoyé {} sans rien enregistrer : un nouveau mempalace init suivi d'un PreCompact. crochet a classé 0 tiroirs, contre 20 une fois que ~/.mempalace existait. Le kill-switch dans hooks_cli et dans les hooks du shell Antigravity accepte désormais également le répertoire de configuration résolu, et les hooks du shell lisent hooks.auto_save à partir de celui-ci. Les installations existantes se comportent exactement comme avant.
  • mempalace wake-up ne signale plus un palais sain comme manquant lorsqu'un hub est en cours d'exécution. Les couches L1 à L3 ont ouvert le palais en écriture, et sur le backend sqlite_exact, un accès en écriture prend le verrou de la mine du palais pour initialiser son schéma. Avec un hub, un démon ou une mine détenant ce verrou, l'ouverture a échoué, et l'exception avalée a imprimé "Aucun palais trouvé. Exécuter: mempalace mine <dir>", invitant à une nouvelle mine inutile. Les couches demandent maintenant une ouverture en lecture seule, que sqlite_exact sert sans le verrou ; ChromaDB ignore l'option, mais sa collection ouverte n'a jamais pris le verrou de la mine. Un conflit de verrouillage qui fait surface reçoit son propre message au lieu de celui du palais manquant.
  • Un mempalace serve inscriptible attend un bail d'écriture occupé au lieu de redémarrer une boucle. Démarrage refusé avec le statut 2 au moment où un autre processus détenait le bail d'écriture du palais, et sous le Restart=always du modèle systemd qui est devenu une boucle qui n'a jamais démarré, n'a jamais abandonné et n'a jamais atteint failed. Le serveur réessaye désormais avec interruption pour MEMPALACE_MCP_WRITER_WAIT_SECONDS (par défaut 120, 0 refuse immédiatement) et se connecte une fois lorsque l'attente commence ; une défaillance du backend ou du répertoire de verrouillage refuse toujours immédiatement. L'unité définit RestartPreventExitStatus=2, de sorte qu'une attente qui s'écoule atterrit dans failed avec la raison dans le journal, et le chien de garde inactif exécute le nettoyage enregistré avant de quitter, de sorte que serverinfo.json n'annonce plus un PID mort. (#2500, #2501)
  • mempalace daemon start et stop se rétablissent d'un enregistrement obsolète. Le garde #2442 a refusé de démarrer alors que le pid enregistré était en vie, et après un crash, ce pid peut appartenir à un processus sans rapport, donc démarrage refusé pour toujours ; le mempalace daemon stop suggéré a utilisé la même sonde de santé défaillante et n'a rien fait. Un pid enregistré qui est mort, ou dont le processus a démarré après l'écriture de l'enregistrement, est désormais traité comme périmé : start le remplace et stop le supprime. Un démon live qui ne répond pas conserve son enregistrement, un démarrage en premier plan refuse à côté de lui comme en arrière-plan, et les deux commandes nomment le processus à arrêter. (#2522)
