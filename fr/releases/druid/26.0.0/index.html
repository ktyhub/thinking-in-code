<a name="26.0.0-highlights-auto-type-column-schema-%28experimental%29" href="#26.0.0-highlights-auto-type-column-schema-%28experimental%29">#</a> Schéma de colonne de type automatique (expérimental)

Un nouveau schéma de colonne de type « auto » et un nouveau indexeur ont été ajoutés à l'ingestion native en tant que prochaine itération logique de la fonctionnalité de colonne imbriquée. Cet indexeur de colonnes de type automatique produit la colonne la plus appropriée pour les entrées données, produisant des colonnes STRING, ARRAY<STRING>, LONG, ARRAY<LONG>, DOUBLE, ARRAY<DOUBLE> ou COMPLEX<json>, partageant toutes un format « imbriqué » commun.

Toutes les colonnes produites par 'auto' ont des index pour faciliter un filtrage rapide (contrairement aux colonnes classiques LONG et DOUBLE) et utilisent des seuils basés sur la cardinalité pour tenter d'utiliser ces index uniquement lorsque cela est susceptible d'accélérer la requête (contrairement aux colonnes STRING classiques).

Les colonnes COMPLEX<json> produites par cet indexeur « automatique » stockent les tableaux de types scalaires simples différemment de leurs homologues « json » (v4), en les stockant sous forme de colonnes typées ARRAY. Cela signifie que la fonction JSON_VALUE peut désormais extraire des tableaux entiers, par exemple JSON_VALUE(nested, '$.array' RETURNING BIGINT ARRAY). Il n’y a aucun changement dans la façon dont les tableaux d’objets complexes sont stockés pour le moment.

Cette amélioration ajoute également une toute nouvelle fonctionnalité aux colonnes typées Druid, ARRAY, qui, contrairement aux colonnes STRING multi-valeurs classiques, se comportent avec la sémantique ARRAY. Ces colonnes ne peuvent actuellement être créées via l'indexeur de type 'auto' que lorsque toutes les valeurs sont des tableaux avec le même type d'éléments.

Un type de données tableau est un type de données qui vous permet de stocker plusieurs valeurs dans une seule colonne d'une table de base de données. Les tableaux sont généralement utilisés pour stocker des ensembles de données associées facilement accessibles et manipulables en tant que groupe.

Cette version ajoute la prise en charge du stockage de tableaux de valeurs primitives telles que ARRAY<STRING>, ARRAY<LONG> et ARRAY<DOUBLE> en tant que colonnes imbriquées spécialisées au lieu de les diviser en colonnes d'éléments distinctes.

<a name="26.0.0-highlights-auto-type-column-schema-%28experimental%29-schema-auto-discovery-%28experimental%29" href="#26.0.0-highlights-auto-type-column-schema-%28experimental%29-schema-auto-discovery-%28experimental%29">#</a> Découverte automatique de schéma (expérimental)

Nous ajoutons la découverte automatique de schéma avec inférence de type à Druid. Avec cette fonctionnalité, le type de données de chaque champ entrant est détecté lorsque le schéma est disponible. Pour les données entrantes pouvant contenir des champs ajoutés, supprimés ou modifiés, vous pouvez choisir de rejeter les données non conformes (« la base de données est toujours correcte - rejeter les mauvaises données ! »), ou vous pouvez laisser la découverte automatique du schéma modifier la source de données pour qu'elle corresponde aux données entrantes (« les données sont toujours correctes - changez la base de données ! »). La découverte automatique de schéma est recommandée pour les nouveaux cas d'utilisation et les ingestions. Pour les cas d'utilisation existants, soyez prudent en passant à la découverte automatique de schéma, car Druid ingèrera des valeurs de type tableau (par exemple ["tag1", "tag2]) sous forme de colonnes de type ARRAY<STRING> au lieu de chaînes à valeurs multiples (MV), cela pourrait entraîner des problèmes dans les applications en aval répondant au comportement MV. Attendez de changer jusqu'à ce qu'un chemin de migration officiel soit disponible.

Pour utiliser cette fonctionnalité, définissez spec.dataSchema.dimensionsSpec.useSchemaDiscovery sur true dans votre spécification de tâche ou de superviseur ou, si vous utilisez le chargeur de données dans la console, décochez la bascule Explicitly define schema à l'étape Configure schema. Druid peut déduire l'intégralité du schéma ou une partie de celui-ci si vous répertoriez explicitement les dimensions dans votre liste de dimensions.

La découverte automatique de schéma est disponible pour l’ingestion native par lots et par streaming.

<a name="26.0.0-highlights-unnest-arrays-%28experimental%29-" href="#26.0.0-highlights-unnest-arrays-%28experimental%29-">#</a> Tableaux UNNEST (expérimental)

Une partie de ce qui est intéressant avec UNNEST réside dans la façon dont il permet un plus large éventail d’opérations qui n’étaient pas possibles sur les types de données Array. Vous pouvez désimbriquer les tableaux avec la fonction UNNEST (SQL) ou la source de données unnest (native).

Unnest convertit les tableaux ou tableaux imbriqués en lignes individuelles. La fonction UNNEST est particulièrement utile lorsque vous travaillez avec des types de données complexes contenant des tableaux imbriqués, tels que JSON.

Par exemple, supposons que vous ayez un tableau appelé « commandes » avec une colonne appelée « articles » qui contient un tableau de produits pour chaque commande. Vous pouvez utiliser unnest pour extraire les produits individuels ("each_item") comme dans l'exemple SQL suivant :

SELECT order_id, each_item FROM orders, UNNEST(items) as unnested(each_item)

Cela produit un ensemble de résultats avec une ligne pour chaque article de chaque commande, avec des colonnes pour l'ID de commande et l'article individuel.

Notez la virgule après la table/source de données de gauche (orders dans l'exemple). C'est obligatoire.

<a name="26.0.0-highlights-sort-merge-join-and-hash-shuffle-join-for-msq" href="#26.0.0-highlights-sort-merge-join-and-hash-shuffle-join-for-msq">#</a> Jointure par fusion et tri et jointure par hachage aléatoire pour MSQ

Nous pouvons maintenant effectuer des jointures aléatoires en définissant le paramètre de contexte sqlJoinAlgorithm sur sortMerge pour l'algorithme de tri-fusion ou en l'omettant pour effectuer des jointures de diffusion (par défaut).

Les requêtes à plusieurs étapes peuvent utiliser un algorithme de jointure-tri-fusion. Avec cet algorithme, chaque jointure par paire est planifiée dans sa propre étape avec deux entrées. Cette approche est généralement moins performante mais plus évolutive que la diffusion.

Définissez le paramètre de contexte sqlJoinAlgorithm sur sortMerge pour utiliser cette méthode.

Les jointures de hachage de diffusion sont similaires à la façon dont les requêtes de jointure natives sont exécutées.

<a name="26.0.0-highlights-storage-improvements-on-dictionary-compression--" href="#26.0.0-highlights-storage-improvements-on-dictionary-compression--">#</a> Améliorations du stockage sur la compression du dictionnaire

Le passage à l'utilisation de la compression par dictionnaire de frontcoding (expérimental) peut permettre d'économiser jusqu'à 30 % avec peu ou pas d'impact sur les performances des requêtes.

Cette amélioration est rétrocompatible avec Druid 25.0. Ajout d'une nouvelle option formatVersion, qui correspond par défaut à la version actuelle 0. Définissez formatVersion sur 1 pour commencer à utiliser la nouvelle version.

<a name="26.0.0-upgrade-notes-and-incompatible-changes--incompatible-changes-firehose-ingestion-removed" href="#26.0.0-upgrade-notes-and-incompatible-changes--incompatible-changes-firehose-ingestion-removed">#</a> L'ingestion Firehose a été supprimée

La spécification Firehose/analyseur utilisée par les anciens formats de streaming Druid est supprimée. L’ingestion Firehose est obsolète dans la version 0.17 et la prise en charge de cette ingestion a été supprimée dans la version 24.0.

#12852

<a name="26.0.0-upgrade-notes-and-incompatible-changes--incompatible-changes-information-schema-now-uses-numeric-column-types-" href="#26.0.0-upgrade-notes-and-incompatible-changes--incompatible-changes-information-schema-now-uses-numeric-column-types-">#</a> Le schéma d'information utilise désormais des types de colonnes numériques

La table système Druid (INFORMATION_SCHEMA) utilise désormais des types SQL au lieu des types Druid pour les colonnes. Ce changement fait que la table INFORMATION_SCHEMA se comporte davantage comme du SQL standard. Vous devrez peut-être mettre à jour vos requêtes dans les scénarios suivants afin d'éviter des résultats inattendus si vous dépendez de l'un des éléments suivants :

  • Les champs numériques étant traités comme des chaînes.
  • Numérotation des colonnes commençant à 0. La numérotation des colonnes est désormais basée sur 1.

#13777

<a name="26.0.0-upgrade-notes-and-incompatible-changes--incompatible-changes-%60frontcoded%60-segment-format-change" href="#26.0.0-upgrade-notes-and-incompatible-changes--incompatible-changes-%60frontcoded%60-segment-format-change">#</a> Changement de format de segment frontCoded

Le type frontCoded de stringEncodingStrategy sur indexSpec avec une nouvelle version de format de segment, qui offre généralement des vitesses de lecture plus rapides et une taille de segment réduite. Cette amélioration est rétrocompatible avec Druid 25.0.

Pour plus d’informations, consultez le point culminant de la stratégie de codage de chaîne frontCoded.

<a name="26.0.0-upgrade-notes-and-incompatible-changes-developer-notes" href="#26.0.0-upgrade-notes-and-incompatible-changes-developer-notes">#</a> Notes des développeurs

<a name="26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-null-value-coercion-moved-out-of-expression-processing-engine-" href="#26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-null-value-coercion-moved-out-of-expression-processing-engine-">#</a> La coercition sur les valeurs nulles a été retirée du moteur de traitement des expressions

Les valeurs nulles entrées et créées par le moteur de traitement d'expression natif Druid ne contraignent plus null à la valeur « par défaut » appropriée au type si druid.generic.useDefaultValueForNull=true. Cela ne devrait pas avoir d'impact sur le comportement existant puisque cela a été transféré au consommateur et qu'en interne, les opérateurs utiliseront toujours les valeurs par défaut dans ce mode. Cependant, il peut y avoir des changements de comportement subtils autour de la gestion des valeurs null. Les appelants directs peuvent obtenir les valeurs par défaut en utilisant la nouvelle méthode valueOrDefault() de ExprEval, au lieu de value().

#13809

<a name="26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-simplified-dependencies" href="#26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-simplified-dependencies">#</a> Dépendances simplifiées

Les modules druid-core, extendedset et druid-hll ont été regroupés dans druid-processing pour simplifier les dépendances. Toutes les extensions y faisant référence doivent être mises à jour pour utiliser druid-processing à la place. Les binaires d'extension existants devraient continuer à fonctionner normalement lorsqu'ils sont utilisés avec des versions plus récentes de Druid.

Ce changement n'a aucun impact sur les utilisateurs finaux. Cela a un impact sur tous ceux qui développent des extensions pour Druid.
