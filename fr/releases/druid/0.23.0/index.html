<a name="0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays" href="#0.23.0-new-features-query-engine-grouping-on-arrays-without-exploding-the-arrays">#</a> Regroupement sur des tableaux sans éclater les tableaux

Vous pouvez désormais regrouper sur une dimension à valeurs multiples sous forme de tableau. Pour une source de données nommée "test" :

{"timestamp": "2011-01-12T00:00:00.000Z", "tags": ["t1","t2","t3"]}  #row1
{"timestamp": "2011-01-13T00:00:00.000Z", "tags": ["t3","t4","t5"]}  #row2
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": ["t5","t6","t7"]}  #row3
{"timestamp": "2011-01-14T00:00:00.000Z", "tags": []}                #row4

La requête suivante :

{
  "queryType": "groupBy",
  "dataSource": "test",
  "intervals": [
    "1970-01-01T00:00:00.000Z/3000-01-01T00:00:00.000Z"
  ],
  "granularity": {
    "type": "all"
  },
  "virtualColumns" : [ {
    "type" : "expression",
    "name" : "v0",
    "expression" : "mv_to_array(\"tags\")",
    "outputType" : "ARRAY<STRING>"
  } ],
  "dimensions": [
    {
      "type": "default",
      "dimension": "v0",
      "outputName": "tags"
      "outputType":"ARRAY<STRING>"
    }
  ],
  "aggregations": [
    {
      "type": "count",
      "name": "count"
    }
  ]
}

Renvoie ce qui suit :

[
 {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "[]"
    }
  },
  {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "["t1","t2","t3"]"
    }
  },
  {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 1,
      "tags": "[t3","t4","t5"]"
    }
  },
  {
    "timestamp": "1970-01-01T00:00:00.000Z",
    "event": {
      "count": 2,
      "tags": "["t5","t6","t7"]"
    }
  }
]

(#12078) (#12253)

<a name="0.23.0-new-features-query-engine-specify-a-column-other-than-__time-column-for-row-comparison-in-first%2Flast-aggregators" href="#0.23.0-new-features-query-engine-specify-a-column-other-than-__time-column-for-row-comparison-in-first%2Flast-aggregators">#</a> Spécifiez une colonne autre que __time pour la comparaison des lignes dans les premier/dernier agrégateurs

Vous pouvez transmettre la colonne de temps dans les agrégateurs *first/*last en utilisant les fonctions SQL LATEST_BY/EARLIEST_BY. Cela prend en charge les cas où l'heure est stockée dans le cadre d'une colonne différente de "__time". Vous pouvez également spécifier une autre colonne d'heure logique. (#11949) (#12145)

<a name="0.23.0-new-features-query-engine-improvements-to-querying-user-experience" href="#0.23.0-new-features-query-engine-improvements-to-querying-user-experience">#</a> Améliorations de l'expérience utilisateur des requêtes

Cette version inclut plusieurs améliorations pour les requêtes :

  • Ajout de l'ID de requête SQL à l'en-tête de réponse pour la requête SQL ayant échoué pour faciliter la localisation des messages d'erreur (#11756)
  • Ajout de la validation du type d'entrée pour DataSketches HLL (#12131)
  • Journalisation JDBC améliorée (#11676)
  • Ajout des fonctions SQL MV_FILTER_ONLY et MV_FILTER_NONE pour filtrer les lignes de dimensions de chaîne à valeurs multiples afin d'inclure uniquement la liste de valeurs fournie ou aucune d'entre elles respectivement (#11650)
  • Ajout de ARRAY_CONCAT_AGG pour regrouper les entrées du tableau en un seul tableau (#12226)
  • Ajout de la possibilité d'autoriser l'utilisation des paramètres de contexte de requête (#12396)
  • ID de requête améliorés pour faciliter la liaison des requêtes et des sous-requêtes pour une visibilité de bout en bout des requêtes (#11809)
  • Ajout d'une fonction de division sécurisée pour se protéger contre la division par 0 (#11904)
  • Vous pouvez désormais ajouter un contexte de requête à la requête SegmentMetadata générée en interne (#11429)
  • Ajout de la prise en charge des types complexes Druid au système de traitement d'expression natif pour rendre toutes les données Druid utilisables dans les expressions (#11853, #12016)
  • Vous pouvez contrôler la taille du dictionnaire au niveau du segment sur le tas via druid.query.groupBy.maxSelectorDictionarySize lors du regroupement sur des expressions à valeur de chaîne ou de tableau qui n'ont pas de dictionnaires préexistants.
  • Vous bénéficiez d'une meilleure protection contre l'explosion du filtre lors de la conversion CNF (#12314) (#12324)
  • Vous pouvez obtenir la requête native complète expliquant la requête SQL en définissant useNativeQueryExplain sur true dans le contexte de la requête (#11908)
  • Vous pouvez demander au courtier d'ignorer les nœuds en temps réel ou des niveaux historiques spécifiques. (#11766) (#11732)

Nous avons introduit un format d'entrée Kafka afin que vous puissiez ingérer des données d'en-tête en plus du contenu du message. Par exemple :

<a name="0.23.0-new-features-streaming-ingestion-kinesis-ingestion---améliorations" href="#0.23.0-new-features-streaming-ingestion-kinesis-ingestion---améliorations">#</a> Ingestion Kinesis - Améliorations

Nous avons apporté les améliorations suivantes à l'ingestion de kinesis

  • Le re-sharding peut affecter et ralentir l'ingestion car de nombreux fragments vides intermédiaires sont créés. Ces fragments sont affectés à des tâches provoquant un déséquilibre dans l'attribution des charges. Vous pouvez définir skipIgnorableShards sur true dans la configuration de réglage de l'ingestion Kinesis pour ignorer ces fragments. (#12235)
  • Actuellement, l'ingestion de Kinesis utilise DescribeStream pour récupérer la liste des fragments. Cet appel est obsolète et plus lent. Dans cette version, vous pouvez passer à un API listShards plus récent en définissant useListShards sur true dans la configuration de réglage de l'ingestion Kinesis. (#12161)

<a name="0.23.0-new-features-native-batch-ingestion" href="#0.23.0-new-features-native-batch-ingestion">#</a> Ingestion par lots natifs

<a name="0.23.0-new-features-native-batch-ingestion-multi-dimension-range-partitioning" href="#0.23.0-new-features-native-batch-ingestion-multi-dimension-range-partitioning">#</a> Partitionnement de plages multidimensionnelles

Le partitionnement de plages multidimensionnelles permet aux utilisateurs de partitionner leurs données sur des plages de n'importe quel nombre de dimensions. Il développe davantage les concepts derrière le partitionnement « single-dim » et constitue désormais sans doute le partitionnement secondaire le plus préférable, à la fois pour les performances des requêtes et l'efficacité du stockage. (#11848) (#11973)

<a name="0.23.0-new-features-native-batch-ingestion-improved-replace-data-behavior" href="#0.23.0-new-features-native-batch-ingestion-improved-replace-data-behavior">#</a> Comportement de remplacement des données amélioré

Dans les versions précédentes de Druid, en cas d'ingestion de données avec l'indicateur dropExisting pour remplacer les données, Druid conservait les données existantes pendant une période de temps s'il n'y avait pas de nouvelles données pour les remplacer. Désormais, si vous définissez dropExisting sur true dans votre ioSpec et que vous ingérez des données pour une plage horaire qui inclut une tranche de temps sans données, Druid utilise une pierre tombale pour éclipser les données existantes dans la tranche de temps vide. (#12137) Cette version inclut plusieurs améliorations pour l'ingestion native par lots :

  • Druid émet désormais une nouvelle métrique lorsqu'une tâche batch termine d'attendre la disponibilité du segment. (#11090)
  • Ajout de segmentAvailabilityWaitTimeMs, la durée en millisecondes pendant laquelle une tâche attend que ses segments soient transmis aux nœuds historiques, à IngestionStatsAndErrorsTaskReportData (#11090)
  • Ajout d'une fonctionnalité pour préserver les métriques existantes lors de l'ingestion (#12185)
  • Les tâches par lots natives parallèles peuvent désormais fournir des rapports de tâches pour le mode séquentiel et monophasé (par exemple, utilisé avec le partitionnement dynamique) ainsi que pour les sous-tâches en mode monophasé (#11688).
  • Ajout de la prise en charge de RowStats dans druid/indexer/v1/task/{task_id}/reports API pour la tâche d'indexation parallèle multiphase (#12280)
  • Correction des échecs du MOO dans la phase de distribution des dimensions de l'indexation parallèle (#12331)
  • Ajout de la prise en charge de la gestion des valeurs de dimension nulles lors de la création de limites de partition (#11973)

<a name="0.23.0-new-features-sql" href="#0.23.0-new-features-sql">#</a> SQL

<a name="0.23.0-new-features-sql-human-readable-and-actionable-sql-error-messages" href="#0.23.0-new-features-sql-human-readable-and-actionable-sql-error-messages">#</a> Messages d'erreur SQL lisibles et exploitables

Jusqu'à la version 0.22.1, si vous émettez une requête SQL non prise en charge, Druid enverrait des messages d'erreur très énigmatiques et inutiles. Avec ce changement, les messages d'erreur incluent exactement la partie de la requête SQL qui n'est pas prise en charge dans Druid. Par exemple, si vous exécutez une requête d'analyse ordonnée sur une dimension autre que la colonne de temps. (#11911)

<a name="0.23.0-new-features-sql-cancel-api-for-sql-queries" href="#0.23.0-new-features-sql-cancel-api-for-sql-queries">#</a> Annuler API pour les requêtes SQL

Nous avons ajouté un nouveau API pour annuler les requêtes SQL, vous pouvez donc désormais annuler les requêtes SQL tout comme vous pouvez annuler les requêtes natives. Vous pouvez utiliser le API depuis la console Web. Dans les versions précédentes, l'annulation depuis la console fermait uniquement la connexion client pendant que la requête SQL continuait à s'exécuter sur Druid. (#11643) (#11738) (#11710)

<a name="0.23.0-new-features-sql-improved-sql-compatibility" href="#0.23.0-new-features-sql-improved-sql-compatibility">#</a> Compatibilité SQL améliorée

Nous avons apporté des modifications aux expressions afin de rendre l'évaluation des expressions plus conforme à SQL. Ce nouveau comportement est désactivé par défaut. <a name="0.23.0-security-fixes" href="#0.23.0-security-fixes">#</a> Correctifs de sécurité

<a name="0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts" href="#0.23.0-security-fixes-support-for-access-control-on-setting-query-contexts">#</a> Prise en charge du contrôle d'accès lors de la définition des contextes de requête

Aujourd'hui, tous les paramètres de contexte sont autorisés aux utilisateurs. Cela peut provoquer 1) une mauvaise UX si le paramètre de contexte n'est pas encore arrivé à maturité ou 2) même un échec de requête ou une erreur système dans le pire des cas si un paramètre sensible est abusé, ex) maxSubqueryRows. Druid a désormais la possibilité de limiter les paramètres de contexte par rôle d'utilisateur. Cela signifie qu'une requête échouera si un paramètre de contexte est défini dans la requête qui ne vous est pas autorisé. L'autorisation du paramètre de contexte peut être activée à l'aide de Druid.auth.authorizeQueryContextParams. Ceci est désactivé par défaut pour permettre une expérience de mise à niveau plus fluide. (#12396)

<a name="0.23.0-upgrading-to-0.23.0-autokill" href="#0.23.0-upgrading-to-0.23.0-autokill">#</a> Suppression automatique des segments

Dans 0.23.0, la suppression automatique des segments est désormais activée par défaut (#12187). Les nouvelles valeurs par défaut devraient supprimer tous les segments inutilisés datant de plus de 90 jours. Si les utilisateurs ne souhaitent pas ce comportement lors d’une mise à niveau, ils doivent explicitement le désactiver. Il s'agit d'un changement risqué car, en fonction de l'intervalle, les segments seront supprimés immédiatement après avoir été marqués comme inutilisés. ce comportement sera annulé ou modifié dans la prochaine version de Druid. Veuillez consulter (#12693) pour plus de détails.

<a name="0.23.0-upgrading-to-0.23.0-other-changes" href="#0.23.0-upgrading-to-0.23.0-other-changes">#</a> Autres modifications

  • L'ingestion Kinesis nécessite un accès listShards API sur le flux.
  • Les bibliothèques Kafka clients ont été mises à niveau vers 3.0.0 (#11735)
  • La configuration du coordinateur dynamique, percentOfSegmentsToConsiderPerMove, est obsolète et sera supprimée dans une prochaine version de Druid. Elle est remplacée par une nouvelle stratégie de sélection de segments introduite dans (#11257). Cette nouvelle stratégie est actuellement désactivée par défaut, mais peut être activée si vous définissez la configuration du coordinateur dynamique useBatchedSegmentSampler sur true. Définir cela comme tel désactivera l’utilisation du percentOfSegmentsToConsiderPerMove obsolète. Dans une prochaine version, useBatchedSegmentSampler deviendra définitivement vrai. (#11960)

<a name="0.23.0-developer-notices" href="#0.23.0-developer-notices">#</a> Avis aux développeurs

<a name="0.23.0-developer-notices-updated-airline-dependency-to-2.x" href="#0.23.0-developer-notices-updated-airline-dependency-to-2.x">#</a> mise à jour de la dépendance des compagnies aériennes vers 2.x

https://github.com/airlift/airline n'est plus maintenu et Druid a donc mis à niveau vers https://github.com/rvesse/airline (Airline 2) pour utiliser activement un version maintenue, tout en minimisant les modifications avec rupture. Il s'agit d'une modification rétrocompatible, et les extensions personnalisées reposant sur le point d'extension CliCommandCreator devront également être mises à jour. 12270

<a name="0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks" href="#0.23.0-developer-notices-return-404-instead-of-400-for-unknown-supervisors-or-tasks">#</a> Renvoie 404 au lieu de 400 pour les superviseurs ou les tâches inconnus

Le point de terminaison superviseur/tâche précédent renvoie 400 lorsqu’un superviseur ou une tâche n’est pas trouvé. Ce code d'état n'est pas convivial et prête à confusion pour le 3ème système. Et selon la définition du code d'état HTTP, 404 est le bon code pour un tel cas. Nous avons donc modifié le code de statut de 400 à 404 pour éliminer toute ambiguïté. Tous les clients de ces points de terminaison doivent modifier la gestion du code de réponse en conséquence. 11724

<a name="0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned" href="#0.23.0-developer-notices-return-400-instead-of-500-when-sql-query-cannot-be-planned">#</a> Renvoie 400 au lieu de 500 lorsque la requête SQL ne peut pas être planifiée

Toute requête SQL qui ne peut pas être planifiée par Druid n'est pas considérée comme une mauvaise requête. Pour de telles requêtes, nous renvoyons désormais 400. Les développeurs utilisant SQL API doivent modifier la gestion du code de réponse si nécessaire. 12033

<a name="0.23.0-developer-notices-responsecontext-refactoring" href="#0.23.0-developer-notices-responsecontext-refactoring">#</a> Refactorisation de ResponseContext

0.23.0 change le ResponseContext et ses touches de manière révolutionnaire. La version précédente du contexte de réponse suggérait que les clés soient définies dans une énumération, puis enregistrées. Cette version suggère que les clés soient définies comme des objets, puis enregistrées. Voir la classe ResponseContext elle-même pour les détails. (#11828)

<a name="0.23.0-developer-notices-other-changes" href="#0.23.0-developer-notices-other-changes">#</a> Autres modifications

  • SingleServerInventoryView a été supprimé. (#11770)
  • LocalInputSource ne permet pas d'ingérer plusieurs fois le même fichier. (#11965)
  • getType() dans PostAggregator est obsolète au profit de getType(ColumnInspector) (#11818)
