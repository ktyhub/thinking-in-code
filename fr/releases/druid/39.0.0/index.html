Fonctionnalités, modifications et dépréciations importantes

Cette section contient des informations importantes sur les fonctionnalités nouvelles et existantes. ###Java La prise en charge de Java 21 a été abandonnée. Vous devez effectuer une mise à niveau vers Java 25.

Instructions DDL pour le catalogue (expérimental)

Druid prend désormais en charge les instructions CREATE et ALTER pour gérer les métadonnées dans le catalogue. Utilisez-les pour déclarer les colonnes d'une table, le partitionnement temporel, le clustering, les projections globales et la disposition physique, au lieu de les définir dans chaque spécification d'ingestion. Cette fonctionnalité est désactivée par défaut. Pour l'activer, définissez druid.sql.planner.enableCatalogDdl sur true. Pour plus d'informations, voir Catalogue. #19830 #20377 #20452 #19770 #19711

Filtrage basé sur l'en-tête Kafka

Les superviseurs Kafka peuvent désormais filtrer les enregistrements par leurs en-têtes. Cela réduit l'utilisation du processeur et de la mémoire par ingestion lorsque vous n'avez besoin que de certains enregistrements d'un sujet. Pour utiliser le filtre, ajoutez headerBasedFilterConfig au ioConfig du superviseur. Utilisez un filtre in où dimension est le nom de l'en-tête et values répertorie les valeurs d'en-tête à ingérer. Les enregistrements dont la valeur d'en-tête ne figure pas dans la liste sont supprimés et les décalages continuent d'avancer. Le filtrage est permissif : les enregistrements sont ingérés s'ils n'ont pas d'en-tête, si la valeur de l'en-tête est nulle, vide ou ne peut pas être décodée, ou si l'évaluation échoue. La nouvelle métrique ingest/events/filtered indique le nombre de filtrages d'en-têtes d'enregistrements supprimés. #18525

Paramètres de contexte de requête typés

Les paramètres de contexte de requête courants répertoriés dans [Référence du contexte de requête] (https://druid.apache.org/docs/39.0.0/querying/query-context-reference) et [Requêtes d'analyse] (https://druid.apache.org/docs/39.0.0/querying/scan-query) sont désormais des descripteurs typés QueryContextParameter. Les modifications suivantes s'appliquent à la gestion du contexte de requête :

  • Les paramètres entiers et longs rejettent les valeurs qui ne sont pas des entiers exacts au lieu de les tronquer ou de les envelopper. Par exemple 1.5 et valeurs hors limites. Les valeurs intégrales telles que 5.0 ou "5.0" sont toujours acceptées. Les valeurs non valides échouent désormais avec un message d'erreur : "Le paramètre de contexte de requête [x] devrait être ..."
  • Une valeur null dans le contexte de requête, ou SET x = NULL, n'efface plus une valeur par défaut configurée avec druid.query.default.context ou la configuration dynamique Broker. La valeur par défaut s'applique comme si la clé n'était pas définie. Auparavant, la valeur null atteignait les lecteurs qui utilisaient la valeur par défaut intégrée. Pour remplacer une valeur par défaut configurée, définissez une valeur explicite.
  • maxSubqueryBytes est un paramètre de chaîne typé qui accepte un nombre d'octets automatique, désactivé ou non négatif, comme le fait le garde-corps de sous-requête. Les valeurs non valides telles que SET maxSubqueryBytes = TRUE échouent désormais lors de la validation et les nombres tels que 1e9 sont désormais acceptés. #20555

Pilote JDBC Druide

Druid fournit désormais son propre pilote JDBC qui utilise le point de terminaison /druid/v2/sql/. Nous vous recommandons de passer du pilote Avatica à ce pilote. Le nouveau pilote offre les avantages suivants : gestion des connexions côté pilote qui ne nécessite pas d'équilibrage de charge persistant, diffusion des résultats en continu, prise en charge des instructions SET et prise en charge des moteurs SQL non natifs. #19951 ###Netty4.2 Druid utilise désormais Netty 4.2 pour son HTTP client. Auparavant, Druid utilisait Netty 3. Il s'agit d'un changement substantiel dans les caractéristiques de la mémoire :

  • Mémoire directe : Le HTTP client consomme désormais de la mémoire directe. Les opérateurs qui approchent de leur budget -XX:MaxDirectMemorySize devront peut-être l'augmenter.
  • Tampons regroupés : les tampons sont désormais regroupés, de sorte que la mémoire résidente peut apparaître plus élevée que sous Netty 3, même lorsqu'elle est inactive. C'est normal pour un allocateur mutualisé. Il existe de nouvelles configurations qui contrôlent le comportement du HTTP client : druid.global.http.connectTimeout, druid.global.http.allocator, druid.broker.http.connectTimeout et druid.broker.http.allocator. Vous pouvez également définir directement certaines configurations du Netty. #19567

Filtrage de la qualité de service pour le coordinateur

Vous pouvez désormais activer le filtrage QoS pour le coordinateur afin d'empêcher une rafale de requêtes API lentes d'épuiser le pool de threads et de bloquer les vérifications de l'état. Utilisez druid.coordinator.server.maxConcurrentRequests pour configurer cette fonctionnalité (default: max(1, max(serverHttpNumThreads - 4, serverHttpNumThreads * 0.8))). Définissez cette propriété sur 0 pour la désactiver. Les points de terminaison de statut leader sont exclus du plafond afin que les équilibreurs/moniteurs de charge ne soient pas affectés. #19271

Domaine fonctionnel et changements associés

Cette section contient des release note détaillés séparés par zones.

Ingestion

  • Ajout de la prise en charge des expressions régulières RE2/J pour le format d'entrée regex #19514
  • Modification du S3 client pour utiliser la stratégie de nouvelle tentative standard recommandée par AWS. Vous pouvez personnaliser la stratégie de nouvelle tentative à l'aide de druid.s3.retryMode et druid.s3.maxAttempts #19892
  • L'ingestion Protobuf conserve désormais la valeur par défaut des champs proto3 qui ne sont pas marqués comme facultatifs. Auparavant, un champ int32 contenant 0 (ou une chaîne contenant "", un bool contenant false, un enum contenant sa première valeur) était ingéré comme nul. Ces champs sont désormais ingérés comme leur valeur réelle. #20485

Ingestion basée sur SQL

  • Les travailleurs transmettent désormais uniquement le contexte de travail nécessaire au lieu de l'intégralité du contexte de travail au contexte de tâche. #20650

Ingestion de flux

Ingestion à partir des partitions sélectionnées

Les superviseurs Kafka acceptent désormais ioConfig.partitionIds, qui vous permet d'ingérer uniquement les partitions sélectionnées d'un sujet. Par exemple, vous pouvez l'utiliser pour une ingestion de diagnostic indépendante. #20474 ##### Améliorations de l'autoscaler basées sur les coûts

  • Vous pouvez désormais simuler l'autoscaler basé sur les coûts pour Kafka afin de déterminer le nombre de tâches optimal pour différentes quantités de décalage. #19687
  • Vous pouvez désormais définir un seuil de décalage critique pour l'autoscaler basé sur les coûts. Lorsque le décalage atteint 75 % du seuil, l'autoscaler contourne la limite de mise à l'échelle. Lorsque le décalage atteint 100 %, l'autoscaler évolue jusqu'au nombre maximal de tâches. #19655
  • Vous pouvez désormais choisir de configurer le temps de recharge pour l'autoscaler basé sur les coûts pour un superviseur de l'une des deux manières suivantes :
    • Haute sensibilité : Réglez minScaleUpDelay / minScaleDownDelay < taskDuration. Par exemple, si minScaleUpDelay = taskDuration / 2, il y aurait au plus 1 événement de mise à l'échelle entre 2 basculements de tâches
    • Faible sensibilité : Réglez minScaleUpDelay / minScaleDownDelay > taskDuration. Dans ce cas, le temps de recharge est effectivement ignoré et la mise à l'échelle se produit uniquement lors du renouvellement de la tâche. #20706
  • L'autoscaler basé sur les coûts utilise désormais des moyennes glissantes au lieu des valeurs instantanées des métriques de tâches pour prendre des décisions pour l'autoscaler basé sur les coûts. Cela conduit à une mise à l’échelle plus fluide, mais peut parfois se faire au prix de réponses légèrement retardées aux changements de tendances métriques qui se produisent vers la fin du cycle de vie de la tâche. Pour une plus grande sensibilité aux tendances changeantes, définissez minScaleUpDelay et minScaleDownDelay pour qu'ils soient plus petits que taskDuration.
Autres améliorations de l'ingestion de streaming
  • Correction d'un bug où une tâche d'indexation Kafka signalait un taux d'inactivité d'interrogation de 1.0 (c'est-à-dire complètement inactif) avant qu'un échantillon ne soit réellement disponible, ce qui pouvait fausser le taux d'inactivité moyen de l'autoscaler du superviseur entre les tâches. #20783

Interrogation

Temps de planification des requêtes

Vous pouvez désormais limiter le temps passé par le Broker à planifier une requête SQL avec la nouvelle propriété d'exécution druid.sql.planner.maxPlanningTimeMs. Vous pouvez également le définir par requête à l'aide du paramètre de contexte de requête maxPlanningTimeMs. Lorsque la planification dépasse le budget configuré, la requête échoue avec une erreur d'expiration de délai de requête HTTP 504 au lieu de bloquer un thread Broker. La valeur par défaut est 0, qui désactive le délai d'attente. #20314

Correction des échecs JDK HTTP client causés par les bandes-annonces de réponse aux requêtes

Les courtiers et les historiques envoient désormais les trailers HTTP X-Druid-Response-Complete et X-Error-Message uniquement lorsque la requête inclut l'en-tête TE: trailers. Clients qui lisent ces bandes-annonces doivent envoyer cet en-tête. Cela corrige les échecs de requête (java.net.ProtocolException: CR expected) dans java.net.http.HttpClient-based clients, y compris le pilote Druid JDBC, sur JDK 17.0.21, 21.0.13 et 25.0.5. #20717

Autres améliorations des requêtes

  • Vous pouvez désormais utiliser Dart pour interroger des tables de métadonnées telles que celles du schéma sys #19952
  • CAST(x AS LONG) est désormais accepté comme alias pour CAST(x AS BIGINT) dans Druid SQL #20402
  • Ajout du filtre déroulant datasource à la table sys.segments #19718
  • Ajout du support de cadrage aux fonctions de fenêtre FIRST_VALUE et LAST_VALUE #19301
  • Amélioration des performances des requêtes de séries temporelles, timeBoundary et d'analyse exécutées par ordre décroissant #19947
  • Amélioration des performances de COALESCE #18400
  • Amélioration de l'efficacité d'utilisation du S3 API pour les tâches MSQ utilisant le stockage durable et l'exportation MSQ #19893
  • Amélioration de la validation des types de catalogue et de l'analyse des chaînes de types natifs #19769
  • Mise à niveau vers Calcite 1.42.0 #19976 #19370

Gestion des clusters

Étiquettes de nœud Kubernetes

L'extension druid-kubernetes-extensions prend désormais en charge un fournisseur de configuration dynamique k8sNodeLabel, qui résout les valeurs de configuration à partir des étiquettes du nœud Kubernetes sur lequel un processus Druid s'exécute. #20404

Modèle de gousse Peon

Vous pouvez désormais récupérer les noms de modèles de pods Peon actuellement configurés sur Overlord à l'aide du nouveau point de terminaison GET /druid/indexer/v1/k8s/taskrunner/podTemplates. Il renvoie le nom de chaque modèle configuré. Le point de terminaison nécessite l'autorisation de lecture CONFIG et renvoie 404 lorsque l'Overlord n'utilise pas l'adaptateur de pod de modèle personnalisé. #19712

Variables d'environnement

Le fournisseur de configuration dynamique environment omet désormais les variables qui ne sont pas définies dans l'environnement au lieu de produire une valeur nulle qui fait échouer les consommateurs tels que le superviseur Kafka avec un NullPointerException. Une variable ignorée est enregistrée au niveau information. #20381

Pools de connexions

Vous pouvez désormais configurer la manière dont le pool de connexions Druid suit la demande de connexion à l'aide de druid.global.http.poolImplementation. La valeur par défaut est retaining. Avec le retaining, la piscine conserve chaque connexion qu'elle ouvre et remplace chaque connexion obsolète ou cassée par une nouvelle, de sorte que la piscine reste à sa ligne d'eau haute. #20542 #20273

En-têtes de réponse HTTP

Druid peut désormais éventuellement renvoyer X-Druid-Server, X-Druid-Service et X-Druid-Version sur les réponses HTTP, permettant aux opérateurs d'identifier le processus et la version qui ont servi une requête directe ou mandatée par le routeur. Ces en-têtes exposent les informations sur la topologie et la version du cluster. Activez-les donc uniquement si tous les clients sont autorisés à les recevoir. Pour les activer, définissez druid.server.http.enableResponseIdentityHeaders sur true. #20268

Prise en charge LDAP améliorée

Ajout de la prise en charge de l'autorisation basée sur les groupes LDAP sur les serveurs qui ne renvoient pas l'attribut memberOf (tels qu'OpenLDAP). Configurez groupBaseDn et groupSearch sur le validateur d'informations d'identification LDAP pour activer une recherche de groupe inversée qui résout automatiquement les appartenances aux groupes. #19432

Visibilité du tableau

Les utilisateurs qui interrogent des tables pour lesquelles ils ne disposent pas de l'autorisation READ voient actuellement une erreur « introuvable » au lieu d'une erreur « interdite ». Pour restaurer le comportement précédent, définissez druid.sql.planner.authorizeTableVisibility sur false. De plus, lorsqu'ils sont définis sur true, INSERT et REPLACE nécessitent un accès READ et WRITE à la table cible. Si cette propriété est définie sur false, elles nécessitent uniquement l’autorisation WRITE. Quelle que soit la valeur de cette propriété, les tables n'apparaissent dans INFORMATION_SCHEMA que si l'utilisateur y a un accès en LECTURE. Il s’agit d’un changement radical qui affecte les autorisations dont vous avez besoin. Pour plus d’informations, consultez modifications des autorisations pour l’ingestion basée sur SQL. #20075

Variable d'accueil Java

Les middle managers honorent désormais JAVA_HOME lorsqu'ils utilisent le script bin/java, qui doit être présent dans le répertoire de travail. Druid utilise la logique suivante

  • Si vous avez spécifié une commande (par exemple si config.getJavaCommand n'est pas nul), utilisez-la.
  • Si bin/run-java existe, utilisez-le
  • Utiliser Java #19709

Ajouter un filtrage QoS pour les points de terminaison du coordinateur

Ajout d'un filtrage QoS configurable au coordinateur pour empêcher une rafale de requêtes lentes API d'épuiser le pool de threads et de bloquer les vérifications de l'état. Ajout d'une nouvelle configuration : druid.coordinator.server.maxConcurrentRequests (par défaut : max(1, max(serverHttpNumThreads - 4, serverHttpNumThreads * 0.8)), définissez <= 0 pour désactiver). Les points de terminaison de statut leader sont exclus du plafond, de sorte que les équilibreurs de charge et les moniteurs ne sont pas affectés. #19271

Autres améliorations de la gestion des clusters

  • Ajout d'un type de verrouillage de tâche KILL qui peut être utilisé par les tâches d'arrêt intégrées afin que le UnusedSegmentsKiller ne saute pas les intervalles avec les ingestions actives #19921
  • Ajout de la prise en charge de PostgreSQL à l'outil export-metadata #19698
  • Les Peons exécutant des tâches qui ne servent pas de requêtes (par exemple, tâches par lots, de compactage et MSQ) ignorent désormais druid.server.http.unannouncePropagationDelay et s'arrêtent sans attendre. Les tâches de streaming en temps réel respectent toujours le délai #20444
  • Liaison de port améliorée. Les nœuds Druid peuvent désormais annoncer un port en texte clair différent pour la découverte d'homologues tout en liant Jetty au port de service réel #19598
  • Réduction de l'empreinte du tas des segments chargés #20467
  • Correction du shutdownAllTasks Overlord API (POST /druid/indexer/v1/datasources/{datasource}/shutdownAllTasks), qui renvoyait une erreur 404 depuis le Druid 32.0.0. #20824

Gestion des données

Ignorer les intervalles pendant le compactage

Le compactage automatique prend désormais en charge un paramètre skipIntervals dans la configuration de compactage de la source de données, permettant d'exclure des intervalles spécifiques du compactage en plus du comportement skipOffsetFromLatest existant. Ceci est utile, par exemple, pour exclure un intervalle dans lequel une tâche de remplissage écrit activement, ou un intervalle qui échoue systématiquement au compactage. #19792

Meilleure visibilité pour les fichiers de segments volumineux

Druid signale désormais lorsque vos paramètres de partitionnement de plage ou de hachage produisent des fichiers de segments trop volumineux (partitions chaudes) dans un intervalle de temps. L'ingestion par lots natifs avec partitionnement de hachage ou de plage enregistre désormais un avertissement et émet la métrique ingest/segments/oversized. La métrique compte les segments publiés avec plus du double des lignes maxRowsPerSegment, ou plus du triple targetRowsPerSegment pour le partitionnement de plage. Le rapport d'achèvement des tâches inclut également ce décompte sous la forme oversizedSegments. #20173

Recherches de segments plus rapides

Vous pouvez désormais accélérer les recherches de segments dans la chronologie en mémoire en activant la recherche à intervalles rapides. Cette fonctionnalité utilise un index [arborescence d'intervalles] (https://en.wikipedia.org/wiki/Interval_tree) pour organiser la chronologie en mémoire afin d'accélérer le chargement et la recherche de segments. Pour utiliser cette fonctionnalité, définissez druid.segment.timeline.fastIntervalSearch sur true. #19138 #19861

Chargement partiel du segment

Druid prend désormais en charge le chargement partiel de segments pour le stockage virtuel (activé par défaut). Pour le désactiver, définissez l'une des options suivantes sur false :

  • la propriété d'exécution druid.indexer.task.virtualStoragePartialDownloadsEnabled
  • le paramètre de contexte de requête virtualStoragePartialDownloadsEnabled #19739

Autres améliorations de la gestion des données

  • Ajout de la prise en charge des sommes de contrôle des requêtes MD5 pour le stockage compatible S3. Pour activer cette fonctionnalité, définissez druid.s3.enableLegacyMd5 sur true #20055
  • Ajout de la prise en charge de l'envoi, de l'extraction et de la suppression de segments dans le stockage profond Azure et Google Cloud sans compression zip #20454 #20327 #20382 #20380
  • Amélioration de l'algorithme de chargement pour mieux disperser les requêtes entre les niveaux historiques lors de l'utilisation du stockage virtuel #20155
  • Amélioration de l'efficacité des tâches de suppression intégrées #19772

Métriques et surveillance

Métriques de stockage de niveau

Les métriques de stockage de niveau offrent désormais une meilleure observabilité des historiques, avec ou sans stockage virtuel. Deux métriques, tier/required/capacity et tier/total/capacity, sont obsolètes et seront supprimées dans une prochaine version. Utilisez plutôt tier/storage/required et tier/storage/capacity. #20199

Métrique task/run/time

Les émetteurs statsd et prometheus émettent désormais la dimension taskStatus sur task/run/time. Il s’agit d’un changement radical. Pour plus d’informations, consultez alertes sur task/run/time. #20122

Autres mesures et améliorations de la surveillance

  • Les métriques de tâches Peon pour les clusters qui utilisent l'extension Kubernetes Overlord incluent désormais une dimension podTemplate. Cela facilite la surveillance des clusters qui mappent différentes tâches à différents modèles de pods #20001
  • Ajout de mergeBuffer/maxSpillProximity qui mesure la proximité avec laquelle une requête groupBy unique s'est produite pendant la période d'émission, sous forme de fraction dans [0.0, 1.0] #19627
  • Ajout de taskType aux différentes mesures du nombre de tâches, afin que vous puissiez les filtrer par type de tâche #20123

Extensions des contributeurs

Iceberg

L'ingestion Apache Iceberg prend désormais en charge un lecteur vectorisé opt-in soutenu par iceberg-arrow. Activez-le avec "useArrowReader": true ; régler le traitement par lots avec arrowBatchSize (par défaut 1024). Le chemin Arrow prend en charge les fichiers de données Parquet, les valeurs codées dans un dictionnaire, l'évolution du schéma, les instantanés de voyage dans le temps, la projection de colonnes et le refoulement des prédicats. Les instantanés contenant des fichiers de suppression de position ou d'égalité ne sont pas pris en charge et Druid les rejette avec une erreur ; utilisez le lecteur standard prenant en charge la suppression pour ces instantanés. Le chemin Arrow n’est pas divisible, alors laissez-le désactivé lorsqu’un débit par lots parallèle est requis. Le lecteur par défaut reste inchangé et les deux chemins coexistent sous le même type de source d'entrée Iceberg. #19510

Ouvrir l'agent de stratégie

Ajout de l'extension de contributeur druid-opa-authorizer, qui permet l'autorisation via Open Policy Agent (OPA). Vous pouvez écrire des politiques Rego pour contrôler l'accès aux ressources Druid en fonction de l'identité de l'utilisateur, de l'action et du type de ressource. L'extension prend en charge les flux de travail d'authentification de base et d'authentification LDAP. #19670 ## Notes de mise à niveau et modifications incompatibles

Cela corrige les échecs de requête (java.net.ProtocolException: CR expected) dans java.net.http.HttpClient-based clients, y compris le pilote Druid JDBC, sur JDK 17.0.21, 21.0.13 et 25.0.5. #20717

Paramètres de contexte de requête typés

Les paramètres de contexte de requête courants répertoriés dans [Référence du contexte de requête] (https://druid.apache.org/docs/39.0.0/querying/query-context-reference) et [Requêtes d'analyse] (https://druid.apache.org/docs/39.0.0/querying/scan-query) sont désormais des descripteurs typés QueryContextParameter. Les modifications suivantes s'appliquent à la gestion du contexte de requête :

  • Les paramètres entiers et longs rejettent les valeurs qui ne sont pas des entiers exacts au lieu de les tronquer ou de les envelopper. Par exemple 1.5 et valeurs hors plage. Les valeurs intégrales telles que 5.0 ou "5.0" sont toujours acceptées. Les valeurs non valides échouent désormais avec un message d'erreur : "Le paramètre de contexte de requête [x] devrait être ..."
  • Une valeur null dans le contexte de requête, ou SET x = NULL, n'efface plus une valeur par défaut configurée avec druid.query.default.context ou la configuration dynamique Broker. La valeur par défaut s'applique comme si la clé n'était pas définie. Auparavant, la valeur null atteignait les lecteurs qui utilisaient la valeur par défaut intégrée. Pour remplacer une valeur par défaut configurée, définissez une valeur explicite.
  • maxSubqueryBytes est un paramètre de chaîne typé qui accepte un nombre d'octets automatique, désactivé ou non négatif, comme le fait le garde-corps de sous-requête. Les valeurs non valides telles que SET maxSubqueryBytes = TRUE échouent désormais lors de la validation et les nombres tels que 1e9 sont désormais acceptés. [#20555][https://github.com/apache/druid/pull/20555/]

Variable d'accueil Java

Les middle managers honorent désormais JAVA_HOME lorsqu'ils utilisent le script bin/java, qui doit être présent dans le répertoire de travail. Druid utilise la logique suivante

  • Si vous avez spécifié une commande (par exemple si config.getJavaCommand n'est pas nul), utilisez-la.
  • Si bin/run-java existe, utilisez-le
  • Utiliser Java #19709

Filtrage de la qualité de service pour le coordinateur

Vous pouvez désormais activer le filtrage QoS pour le coordinateur afin d'empêcher une rafale de requêtes lentes API d'épuiser le pool de threads et de bloquer les vérifications de l'état. Utilisez druid.coordinator.server.maxConcurrentRequests pour configurer cette fonctionnalité (default: max(1, max(serverHttpNumThreads - 4, serverHttpNumThreads * 0.8))). Définissez cette propriété sur 0 pour la désactiver. Les points de terminaison de statut leader sont exclus du plafond afin que les équilibreurs/moniteurs de charge ne soient pas affectés. #19271

Modifications incompatibles

Modifications des autorisations pour l'ingestion basée sur SQL

Les modifications de visibilité de la table affectent les autorisations requises pour l'ingestion basée sur SQL. INSERT et REPLACE nécessitent désormais un accès READ (en plus de WRITE) sur la table cible. Pour restaurer le comportement précédent, définissez druid.sql.planner.authorizeTableVisibility sur false. #20075

Alertes sur task/run/time

Les émetteurs statsd et prometheus émettent désormais la dimension taskStatus sur task/run/time. Il s'agit d'un changement radical pour les tableaux de bord et les alertes sur task/run/time :

  • statsd (mode non-DogStatsD) : les valeurs de dimension sont jointes dans le nom de la métrique en pointillés, donc druid.overlord.task.run.time.DATASOURCE.TASKTYPE devient druid.overlord.task.run.time.DATASOURCE.TASKSTATUS.TASKTYPE. Les requêtes portant sur l'ancien nom cessent de recevoir des données.
  • statsd (mode DogStatsD) : Une balise taskStatus est ajoutée. Les requêtes existantes continuent de fonctionner et se regroupent dessus.
  • prometheus : Une étiquette taskStatus est ajoutée. Mettez à jour toutes les requêtes qui sélectionnent sur un jeu d’étiquettes exact et toutes les règles d’enregistrement qui supposent l’ancien jeu d’étiquettes. Pour conserver le comportement précédent, épinglez l'ancienne liste de dimensions avec druid.emitter.statsd.dimensionMapPath ou druid.emitter.prometheus.dimensionMapPath. #20122

SysMonitor supprimé

SysMonitor a été supprimé après avoir été obsolète dans Druid 27. Utilisez plutôt OshiSysMonitor. #20200

MariaDB Connector/J 3.x modifie le comportement de l'URI de connexion

Le connecteur MariaDB JDBC a été mis à niveau de 2.7.3 vers 3.5.10, ce qui a l'impact suivant :

  • Pour druid.metadata.storage.connector.connectURI avec org.mariadb.jdbc.Driver, utilisez jdbc:mariadb:. Un ancien URI jdbc:mysql: reste utilisable uniquement s’il inclut permitMysqlScheme. Par exemple, jdbc:mysql://<host>/druid?permitMysqlScheme, car le stockage des métadonnées transmet l'URI directement au pilote.
  • Pour les sources d'entrée SQL basées sur MariaDB et les recherches JDBC avec le druid.access.jdbc.enforceAllowedProperties=true par défaut, utilisez jdbc:mariadb:. La validation de la propriété JDBC de Druid n'achemine pas jdbc:mysql: vers l'analyseur Connector/J 3.x, et permitMysqlScheme n'est pas dans le druid.access.jdbc.allowedProperties par défaut. L'ajout de l'option seule n'est pas suffisant.
  • Les utilisateurs qui continuent à fournir Connector/J 2.x n'ont pas besoin de modifier les URI jdbc:mysql: ou jdbc:mariadb: existants. Les utilisateurs du connecteur MySQL/J ne sont pas concernés.
  • Les images reconstruites à partir de distribution/docker/Dockerfile.mariadb installent désormais Connector/J 3.5.10 et doivent suivre les instructions 3.x ci-dessus. #20036

Notes du développeur

Éditeur de code de la console Web

Les éditeurs de code de la console Web sont passés d'Ace (ace-builds et react-ace) à Code Mirror 6. Tous les éditeurs partagent désormais un seul composant CodeEditor, y compris l'atelier, les entrées SQL de la vue d'exploration, les entrées JSON, les boîtes de dialogue de spécifications et de valeurs, l'historique et l'explication. Deux grammaires Lezer, une pour DruidSQL et une pour Hjson, pilotent la mise en évidence et les complétions. #20507

Mises à jour des dépendances

Druid 39.0.0 inclut une variété de mises à jour de dépendances telles que Calcite. Pour une liste complète, consultez la Zone - Étiquette de dépendances dans le jalon.
