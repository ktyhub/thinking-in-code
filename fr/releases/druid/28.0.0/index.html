druide druide-28.0.0

Apache Druid 28.0.0 contient plus de 420 nouvelles fonctionnalités, corrections de bugs, améliorations des performances, améliorations de la documentation et couverture de tests supplémentaire de 57 contributeurs.

Consultez l'ensemble complet de modifications pour plus de détails, y compris les corrections de bogues.

<a name="28.0.0-important-changes-and-deprecations" href="#28.0.0-important-changes-and-deprecations">#</a> Fonctionnalités, modifications et dépréciations importantes

Dans Druid 28.0.0, nous avons apporté des améliorations substantielles aux requêtes pour rendre le système plus compatible avec ANSI SQL. Cela inclut des changements dans la gestion des valeurs NULL et booléennes ainsi que dans la logique booléenne. Parallèlement, la bibliothèque Apache Calcite a été mise à niveau vers la dernière version. Bien que nous ayons documenté les changements connus de comportement des requêtes, veuillez lire attentivement la section notes de mise à niveau. Testez votre application avant de la déployer dans de vastes scénarios de production tout en surveillant de près l'état de la requête.

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility" href="#28.0.0-important-changes-and-deprecations-sql-compatibility">#</a> Compatibilité SQL

Druid continue de rendre l'exécution des requêtes SQL plus cohérente avec le comportement du SQL standard. Cependant, des indicateurs de fonctionnalités sont disponibles pour restaurer l'ancien comportement si nécessaire.

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility-three-valued-logic" href="#28.0.0-important-changes-and-deprecations-sql-compatibility-three-valued-logic">#</a> Logique à trois valeurs

Les filtres natifs de Druid observent désormais SQL [logique à trois valeurs] (https://en.wikipedia.org/wiki/Three-valued_logic#SQL) (true, false ou unknown) au lieu de la logique classique à deux états de Druid par défaut, lorsque les paramètres par défaut suivants s'appliquent :

*druid.generic.useThreeValueLogicForNativeFilters = true *druid.expressions.useStrictBooleans = true *druid.generic.useDefaultValueForNull = false

#15058

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility-strict-booleans" href="#28.0.0-important-changes-and-deprecations-sql-compatibility-strict-booleans">#</a> Booléens stricts

druid.expressions.useStrictBooleans est désormais activé par défaut. Druid gère désormais les booléens strictement en utilisant 1 (vrai) ou 0 (faux). Auparavant, vrai et faux pouvaient être représentés respectivement par true et false ainsi que par 1 et 0. De plus, Druid renvoie désormais une valeur nulle pour les comparaisons booléennes comme True && NULL.

Si vous ne configurez pas explicitement cette propriété dans runtime.properties, les clusters utilisent désormais les types LONG pour toutes les valeurs booléennes ingérées et dans la sortie des fonctions booléennes pour les transformations et les opérations de temps de requête. Pour plus d'informations, consultez Compatibilité SQL dans les notes de mise à niveau.

<a name="28.0.0-important-changes-and-deprecations-sql-compatibility-null-handling" href="#28.0.0-important-changes-and-deprecations-sql-compatibility-null-handling">#</a> Gestion des NULL

druid.generic.useDefaultValueForNull est désormais désactivé par défaut. Druid fait désormais la différence entre les enregistrements vides et les enregistrements nuls. Auparavant, Druid pouvait traiter les enregistrements vides comme vides ou nuls. Pour plus d'informations, consultez Compatibilité SQL dans les notes de mise à niveau.

<a name="28.0.0-important-changes-and-deprecations-sql-planner-improvements" href="#28.0.0-important-changes-and-deprecations-sql-planner-improvements">#</a> Améliorations du planificateur SQL

Druid utilise Apache Calcite pour la planification et l'optimisation SQL. À partir de Druid 28.0.0, la version Calcite a été mise à niveau de 1.21 à 1.35. Cette mise à niveau apporte de nombreuses corrections de bugs dans la planification SQL de Calcite.

<a name="28.0.0-important-changes-and-deprecations-sql-planner-improvements-dynamic-parameters" href="#28.0.0-important-changes-and-deprecations-sql-planner-improvements-dynamic-parameters">#</a> Paramètres dynamiques

Dans le cadre de la mise à niveau de Calcite, le comportement de l'inférence de type pour les paramètres dynamiques a changé. Pour éviter tout problème d'interférence de type, CAST explicite tous les paramètres dynamiques en tant que type de données spécifique dans les requêtes SQL. Par exemple, utilisez :

SELECT (1 * CAST (? as DOUBLE))/2 as tmp

Ne pas utiliser :

SELECT (1 * ?)/2 as tmp

<a name="28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage" href="#28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage">#</a> Requête asynchrone et requête à partir du stockage profond

Requête à partir du stockage profond n'est plus une fonctionnalité expérimentale. Lorsque vous effectuez une requête à partir du stockage profond, davantage de données sont disponibles pour les requêtes sans avoir à faire évoluer vos services historiques pour accueillir davantage de données. Pour bénéficier de l'économie d'espace qu'offre cette requête grâce au stockage profond, configurez vos règles de chargement pour décharger les données de vos services historiques.

<a name="28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage-support-for-multiple-result-formats" href="#28.0.0-important-changes-and-deprecations-async-query-and-query-from-deep-storage-support-for-multiple-result-formats">#</a> Prise en charge de plusieurs formats de résultats

Les requêtes à partir du stockage profond prennent désormais en charge plusieurs formats de résultats. Auparavant, le point de terminaison /druid/v2/sql/statements/ prenait uniquement en charge les résultats au format object. Désormais, les résultats peuvent être écrits dans n'importe quel format spécifié dans le paramètre resultFormat. Pour plus d'informations sur les paramètres de résultat pris en charge par Druid SQL API, voir [Réponses] (https://druid.apache.org/docs/latest/api-reference/sql-api#responses).

La fonction UNNEST n'est plus expérimentale.

Druid prend désormais en charge UNNEST dans l'ingestion par lots basée sur SQL et les requêtes à partir du stockage profond, afin que vous puissiez facilement aplatir les tableaux. Pour plus d'informations, consultez UNNEST et Désimbriquer les tableaux dans une colonne.

<a name="28.0.0-important-changes-and-deprecations-sql-unnest-and-ingestion-flattening-recommended-syntax-for-sql-unnest" href="#28.0.0-important-changes-and-deprecations-sql-unnest-and-ingestion-flattening-recommended-syntax-for-sql-unnest">#</a> Syntaxe recommandée pour SQL UNNEST

La syntaxe recommandée pour SQL UNNEST a changé. Nous vous recommandons d'utiliser CROSS JOIN au lieu des virgules pour la plupart des requêtes afin d'éviter les problèmes de priorité. Par exemple, utilisez :

SELECT column_alias_name1 FROM datasource CROSS JOIN UNNEST(source_expression1) AS table_alias_name1(column_alias_name1) CROSS JOIN UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

Ne pas utiliser :

SELECT column_alias_name FROM datasource, UNNEST(source_expression1) AS table_alias_name1(column_alias_name1), UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

<a name="28.0.0-important-changes-and-deprecations-window-functions-%28experimental%29" href="#28.0.0-important-changes-and-deprecations-window-functions-%28experimental%29">#</a> Fonctions de fenêtre (expérimentales)

Vous pouvez utiliser des [fonctions de fenêtre] (https://druid.apache.org/docs/latest/querying/sql-window-functions) dans Apache Druid pour produire des valeurs basées sur la relation d'une ligne dans une fenêtre de lignes avec les autres lignes de la même fenêtre. Une fenêtre est un groupe de lignes liées dans un jeu de résultats. Par exemple, des lignes avec la même valeur pour une dimension spécifique.

Activez les fonctions de fenêtre dans votre requête avec le paramètre de contexte enableWindowing: true.

<a name="28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29" href="#28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29">#</a> Ajout et remplacement simultanés (expérimental)

Druid 28.0.0 ajoute une prise en charge expérimentale pour l'ajout et le remplacement simultanés. Cette fonctionnalité vous permet de remplacer en toute sécurité les données existantes dans un intervalle d'une source de données pendant que de nouvelles données sont ajoutées à cet intervalle. L'une des applications les plus courantes consiste à ajouter de nouvelles données à un intervalle alors que le compactage de cet intervalle est déjà en cours. Pour plus d'informations, voir [Ajout et remplacement simultanés] (https://druid.apache.org/docs/latest/data-management/automatic-compaction#concurrent-append-and-replace).

Le verrouillage des segments sera obsolète et supprimé au profit de l'ajout et du remplacement simultanés dont la conception est beaucoup plus simple. Avec l'ajout et le remplacement simultanés, Druid ne verrouille pas les tâches de compactage en raison d'une ingestion active en temps réel.

<a name="28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-task-locks-for-append-and-replace-batch-ingestion-jobs" href="#28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-task-locks-for-append-and-replace-batch-ingestion-jobs">#</a> Verrouillages de tâches pour l'ajout et le remplacement de tâches d'ingestion par lots

Les tâches d’ingestion par lots d’ajout peuvent désormais partager des verrous. Cela vous permet d'exécuter plusieurs tâches d'ingestion par lots d'ajout en même temps en interne. Les tâches de remplacement d’ingestion par lots nécessitent toujours un verrou exclusif. Cela signifie que vous pouvez exécuter plusieurs tâches d’ingestion par lots d’ajout et une tâche d’ingestion par lots de remplacement pour un intervalle donné.

<a name="28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-streaming-ingestion-with-concurrent-replace" href="#28.0.0-important-changes-and-deprecations-concurrent-append-and-replace-%28experimental%29-streaming-ingestion-with-concurrent-replace">#</a> Ingestion de streaming avec remplacement simultané

Les tâches de streaming lisant depuis Kafka et Kinesis avec les verrous APPEND peuvent désormais être ingérées simultanément avec le compactage exécuté avec les verrous REPLACE. La granularité des segments de la tâche de streaming doit être égale ou supérieure à celle de la tâche de remplacement simultanée.

<a name="28.0.0-functional-area-and-related-changes-ingestion-sql-based-ingestion-ability-to-ingest-array-types" href="#28.0.0-functional-area-and-related-changes-ingestion-sql-based-ingestion-ability-to-ingest-array-types">#</a> Possibilité d'ingérer des types ARRAY

L'ingestion basée sur SQL prend désormais en charge le stockage des valeurs typées ARRAY dans des [colonnes typées ARRAY] (https://druid.apache.org/docs/latest/querying/arrays), ainsi que le stockage des tableaux typés VARCHAR et numériques. Auparavant, le moteur de tâches MSQ stockait les valeurs typées ARRAY sous forme de [dimensions à valeurs multiples] (https://druid.apache.org/docs/latest/querying/multi-value-dimensions) au lieu de colonnes typées ARRAY.

Le moteur de tâches MSQ inclut désormais le paramètre de contexte de requête arrayIngestMode, qui contrôle la façon dont Les types ARRAY sont stockés dans les segments Druid. Définissez le paramètre de contexte de requête arrayIngestMode sur array pour ingérer les types ARRAY.

Dans Druid 28.0.0, le mode par défaut pour arrayIngestMode est mvd pour une compatibilité ascendante, qui prend uniquement en charge les tableaux typés VARCHAR et les stocke sous forme de dimensions à valeurs multiples. Cette valeur par défaut est susceptible d'être modifiée dans les versions futures.

Pour plus d'informations sur la façon de migrer vers le nouveau comportement, consultez les [Options d'ingestion pour les colonnes typées ARRAY dans les notes de mise à niveau] (#ingestion-options-for-array-typed-columns). Pour plus d'informations sur le comportement d'insertion, de filtrage et de regroupement des colonnes typées ARRAY, voir [Colonnes de tableau] (https://druid.apache.org/docs/latest/querying/arrays).

<a name="28.0.0-functional-area-and-related-changes-querying-functions-for-evaluating-distinctness" href="#28.0.0-functional-area-and-related-changes-querying-functions-for-evaluating-distinctness">#</a> Fonctions d'évaluation de la distinction

De nouvelles fonctions SQL et de requêtes natives vous permettent d'évaluer si deux expressions sont distinctes ou non. Les expressions sont distinctes si elles ont des valeurs différentes ou si l'une d'elles est NULL. Les expressions ne sont pas distinctes si leurs valeurs sont identiques ou si les deux sont NULL.

Étant donné que les fonctions traitent les valeurs NULL comme des valeurs connues lorsqu'elles sont utilisées comme opérateur de comparaison, elles renvoient toujours vrai ou faux même si l'une ou les deux expressions sont NULL.

Le tableau suivant montre la différence de comportement entre le signe égal (=) et IS [NOT] DISTINCT FROM :

| Un | B | A = B | A N'EST PAS DISTINCT DE B| |---|---|-----|---------------------------------------| | 0 | 0 | vrai | vrai | | 0 | 1 | faux | faux | | 0 | nul | inconnu | faux | | nul | nul | inconnu | vrai |

De nouvelles fonctions SQL et de requêtes natives vous permettent d'évaluer si une condition est vraie ou fausse. Ces fonctions sont différentes de x == true et x != true dans la mesure où elles ne renvoient jamais null même lorsque la variable est nulle.

Vous pouvez maintenant régler le garde-corps maxSubqueryBytes sur l'un des éléments suivants :

  • disabled : paramètre par défaut. Druid n'applique pas de garde-fou autour du nombre d'octets qu'une sous-requête peut générer.

  • auto : Druid calcule la quantité de mémoire à utiliser pour la matérialisation des résultats comme une partie de la mémoire fixe du tas.
    Dans le contexte d'une requête, Druid utilise la formule suivante pour déterminer la limite supérieure du nombre d'octets qu'une sous-requête peut générer :

    ((total JVM space - memory occupied by lookups) * 0.5) / maximum queries that the system can handle concurrently

  • INTEGER : nombre d'octets à utiliser pour matérialiser les résultats de la sous-requête. Définissez une valeur spécifique si vous comprenez les modèles de requête et souhaitez optimiser l'utilisation de la mémoire.
    Par exemple, définissez le paramètre maxSubqueryBytes sur 300000000 (300 * 1000 * 1000) pour une limite de 300 Mo. Définissez le paramètre maxSubqueryBytes sur 314572800 (300 * 1024 * 1024) pour une limite de 300 Mio.

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-recommended-syntax-for-sql-unnest" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-recommended-syntax-for-sql-unnest">#</a> Syntaxe recommandée pour SQL UNNEST

La syntaxe recommandée pour SQL UNNEST a changé. Nous vous recommandons d'utiliser CROSS JOIN au lieu des virgules pour la plupart des requêtes afin d'éviter les problèmes de priorité. Par exemple, utilisez :

SELECT column_alias_name1 FROM datasource CROSS JOIN UNNEST(source_expression1) AS table_alias_name1(column_alias_name1) CROSS JOIN UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

Ne pas utiliser :

SELECT column_alias_name FROM datasource, UNNEST(source_expression1) AS table_alias_name1(column_alias_name1), UNNEST(source_expression2) AS table_alias_name2(column_alias_name2), ...

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-dynamic-parameters" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-dynamic-parameters">#</a> Paramètres dynamiques

La version Apache Calcite a été mise à niveau de 1.21 vers 1.35. Dans le cadre de la mise à niveau de Calcite, le comportement de l'inférence de type pour les paramètres dynamiques a changé. Pour éviter tout problème d'interférence de type, CAST explicite tous les paramètres dynamiques en tant que type de données spécifique dans les requêtes SQL. Par exemple, utilisez :

SELECT (1 * CAST (? as DOUBLE))/2 as tmp

Ne pas utiliser :

SELECT (1 * ?)/2 as tmp

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-nested-column-format" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-nested-column-format">#</a> Format de colonnes imbriquées

Les colonnes de type json créées avec Druid 28.0.0 ne sont pas rétrocompatibles avec les versions Druid antérieures à 26.0.0. Si vous effectuez une mise à niveau à partir d'une version antérieure à Druid 26.0.0 et que vous utilisez des colonnes json, effectuez une mise à niveau vers Druid 26.0.0 avant de passer à Druid 28.0.0. De plus, pour rétrograder vers une version antérieure à Druid 26.0.0, tous les nouveaux segments créés dans Druid 28.0.0 doivent être réingérés à l'aide de Druid 26.0.0 ou 27.0.0 avant une nouvelle rétrogradation.

Lors d'une mise à niveau à partir d'une version précédente, vous pouvez continuer à écrire des colonnes imbriquées dans un format rétrocompatible (version 4).

Dans une tâche d'ingestion par lots classique, incluez formatVersion dans la liste dimensions de la propriété dimensionsSpec. Par exemple :

      "dimensionsSpec": {
        "dimensions": [
          "product",
          "department",
          {
            "type": "json",
            "name": "shipTo",
            "formatVersion": 4
          }
        ]
      },

Pour définir la version de colonne imbriquée par défaut, définissez la version de format souhaitée dans les propriétés d'exécution communes. Par exemple :

druid.indexing.formats.nestedColumnFormatVersion=4

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-sql-compatibility" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-sql-compatibility">#</a> Compatibilité SQL

À partir de Druid 28.0.0, la manière par défaut dont Druid traite les valeurs nulles et les booléens a changé.

Pour les valeurs nulles, Druid fait désormais la différence entre une chaîne vide et un enregistrement sans données ainsi qu'entre un enregistrement numérique vide et 0.
Vous pouvez revenir au comportement précédent en définissant druid.generic.useDefaultValueForNull sur true.

Cette propriété affecte à la fois le stockage et les requêtes, et doit être définie sur tous les types de services Druid pour être disponible à la fois au moment de l'ingestion et au moment de la requête. Le rétablissement de l'ancienne valeur de ce paramètre restaure le comportement précédent sans réingestion.

Pour les booléens, Druid utilise désormais strictement 1 (vrai) ou 0 (faux). Auparavant, vrai et faux pouvaient être représentés respectivement par true et false ainsi que par 1 et 0. De plus, Druid renvoie désormais une valeur nulle pour les comparaisons booléennes comme True && NULL.

Vous pouvez revenir au comportement précédent en définissant druid.expressions.useStrictBooleans sur false. Cette propriété affecte à la fois le stockage et les requêtes, et doit être définie sur tous les types de services Druid pour être disponible à la fois au moment de l'ingestion et au moment de la requête. Le rétablissement de l'ancienne valeur de ce paramètre restaure le comportement précédent sans réingestion.

<a name="28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-ingestion-options-for-array-typed-columns" href="#28.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-ingestion-options-for-array-typed-columns">#</a> Options d'ingestion pour les colonnes typées ARRAY

À partir de Druid 28.0.0, le moteur de tâches MSQ peut détecter et ingérer des tableaux en tant que colonnes typées ARRAY lorsque vous définissez le paramètre de contexte de requête arrayIngestMode sur array. Le paramètre contextuel arrayIngestMode contrôle la manière dont les valeurs de type ARRAY sont stockées dans les segments Druid.

Lorsque vous définissez arrayIngestMode sur array (recommandé pour la conformité SQL), le moteur de tâches MSQ stocke toutes les valeurs typées ARRAY dans [colonnes typées ARRAY] (https://druid.apache.org/docs/latest/querying/arrays) et prend en charge le stockage des tableaux de type VARCHAR et numérique.

Pour des raisons de compatibilité ascendante, arrayIngestMode est par défaut mvd. Lorsque "arrayIngestMode":"mvd", Druid ne prend en charge que les tableaux typés VARCHAR et les stocke sous forme de [colonnes de chaîne à valeurs multiples] (https://druid.apache.org/docs/latest/querying/multi-value-dimensions).

Lorsque vous définissez arrayIngestMode sur none, Druid lève une exception lorsque vous essayez de stocker n'importe quel type de tableaux.

Pour plus d'informations sur la manière d'ingérer des colonnes typées ARRAY avec une ingestion basée sur SQL, consultez Types de données SQL et Colonnes de tableau.
