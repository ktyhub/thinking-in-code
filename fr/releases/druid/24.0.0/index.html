druide druide-24.0.0

Apache Druid 24.0.0 contient plus de 300 nouvelles fonctionnalités, corrections de bugs, améliorations des performances, améliorations de la documentation et couverture de tests supplémentaire de 67 contributeurs. [Voir l'ensemble complet des modifications pour plus de détails] (https://github.com/apache/druid/milestone/46).

<a name="24.0.0-new-features" href="#24.0.0-major-version">#</a> Modification majeure de la version

À partir de cette version, nous avons supprimé le premier 0 de la version commerciale et avons promu tous les autres chiffres une place vers la gauche. Druid est maintenant à la version majeure 24, un bond en avant par rapport à la version précédente 0.23.0. En termes de compatibilité ascendante ou de modifications majeures, cette version n'est pas significativement différente des autres versions majeures précédentes telles que 0.23.0 ou 0.22.0. Nous maintenons la même politique que celle utilisée dans les versions précédentes : minimiser le nombre de modifications nécessitant une attention particulière lors de la mise à niveau et signaler celles qui existent dans les release note. Pour cette version, veuillez vous référer à la section [Mise à niveau vers 24.0.0] (#24.0.0-upgrading-to-24.0) pour obtenir la liste des modifications rétrocompatibles dans cette version.

<a name="24.0.0-new-features" href="#24.0.0-new-features">#</a> Nouvelles fonctionnalités

<a name="24.0.0-new-features-multi-stage-query-task-engine" href="#24.0.0-new-features-multi-stage-query-task-engine">#</a> Moteur de tâches de requête en plusieurs étapes

[Ingestion basée sur SQL] (https://druid.apache.org/docs/latest/multi-stage-query/index.html) pour Apache Druid utilise une architecture de requête distribuée à plusieurs étapes, qui comprend un moteur de requête appelé moteur de tâches de requête à plusieurs étapes (moteur de tâches MSQ). Le moteur de tâches MSQ étend les capacités de requête de Druid, de sorte que vous pouvez écrire des requêtes faisant référence à des données externes ainsi qu'effectuer une ingestion avec SQL INSERT et REPLACE. Essentiellement, vous pouvez effectuer une ingestion basée sur SQL au lieu d'utiliser les spécifications d'ingestion JSON utilisées par l'ingestion native de Druid. En plus de la syntaxe facile à utiliser, l'interface SQL vous permet d'effectuer des transformations impliquant plusieurs mélanges de données. L'ingestion basée sur SQL à l'aide du moteur de tâches de requête en plusieurs étapes est recommandée pour l'ingestion par lots à partir de Druid 24.0.0. L'ingestion par lots natifs et basée sur Hadoop continue également d'être prise en charge. Nous vous recommandons de consulter les [problèmes connus] (https://druid.apache.org/docs/latest/multi-stage-query/known-issues.html) et de tester la fonctionnalité dans un environnement intermédiaire avant de la déployer en production. L'utilisation du moteur de tâches de requête en plusieurs étapes avec des instructions simples SELECT (et non INSERT ... SELECT ou REPLACE ... SELECT) est expérimentale. Si vous effectuez une mise à niveau à partir d'une version antérieure de Druid ou si vous utilisez Docker, vous devrez ajouter l'extension druid-multi-stage-query à druid.extensions.loadlist dans votre fichier common.runtime.properties. Pour plus d'informations, reportez-vous à la documentation [Présentation] (https://druid.apache.org/docs/latest/multi-stage-query/index.html) pour l'ingestion basée sur SQL. #12524 #12386 #12523 #12589

<a name="24.0.0-new-features-nested-columns-" href="#24.0.0-new-features-nested-columns-">#</a> Colonnes imbriquées

Druid prend désormais en charge le stockage direct des structures de données imbriquées dans un type de colonne COMPLEX<json> nouvellement ajouté. Les colonnes COMPLEX<json> stockent une copie des données structurées au format JSON ainsi que des colonnes et index internes spécialisés pour les valeurs littérales imbriquées : types STRING, LONG et DOUBLE. Une colonne virtuelle optimisée permet à Druid de lire et de filtrer ces valeurs à des vitesses compatibles avec les colonnes Druid standard LONG, DOUBLE et STRING. Druid SQL nouvellement ajouté, les fonctions natives JSON et la colonne virtuelle vous permettent d'extraire, de transformer et de créer des valeurs COMPLEX<json> au moment de la requête. Vous pouvez également utiliser les fonctions JSON dans les instructions INSERT et REPLACE dans une ingestion basée sur SQL, ou dans un transformSpec dans une ingestion native, au lieu d'utiliser un objet flattenSpec pour « aplatir » les données imbriquées pour l'ingestion. Voir Fonctions SQL JSON, Fonctions natives JSON, Colonnes imbriquées, colonnes virtuelles columns et le résumé des fonctionnalités pour plus de détails. #12753 #12714 #12753 #12920

<a name="24.0.0-query-engine-updates" href="#24.0.0-query-engine-updates">#</a> Mises à jour du moteur de requête

<a name="24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters" href="#24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters">#</a> Index de colonnes mis à jour et traitement des requêtes des filtres

Les index de colonnes retravaillés pour être extraordinairement flexibles, ce qui nous permettra à terme de modéliser un large éventail de types d'index. Ajout de machines pour créer les filtres qui utilisent les index mis à jour, tout en permettant également à d'autres implémentations de colonnes d'implémenter les types d'index intégrés pour fournir des adaptateurs permettant d'utiliser l'indexation dans l'ensemble de filtres actuel fourni par Druid. #12388

<a name="24.0.0-query-engine-updates-time-filter-operator" href="#24.0.0-query-engine-updates-time-filter-operator">#</a> Opérateur de filtre temporel

Vous pouvez désormais utiliser l'opérateur Druid SQL TIME_IN_INTERVAL pour filtrer les résultats de la requête en fonction du temps. Préférez TIME_IN_INTERVAL à l'opérateur SQL BETWEEN pour filtrer à temps. Pour plus d'informations, consultez Fonctions de date et d'heure. #12662

<a name="24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter" href="#24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter">#</a> Valeurs nulles et filtre "in"

Si un tableau values contient null, le filtre « in » correspond aux valeurs nulles. Cela diffère du filtre SQL IN, qui ne correspond pas aux valeurs nulles. Pour plus d'informations, consultez Filtres de requête et Types de données SQL. #12863

<a name="24.0.0-query-engine-updates-virtual-columns-in-search-queries" href="#24.0.0-query-engine-updates-virtual-columns-in-search-queries">#</a> Colonnes virtuelles dans les requêtes de recherche

Auparavant, une requête de recherche ne pouvait effectuer une recherche que sur les dimensions qui existaient dans la source de données. Les requêtes de recherche prennent désormais en charge les colonnes virtuelles en tant que paramètre dans la requête. #12720

<a name="24.0.0-query-engine-updates-optimize-simple-min-%2F-max-sql-queries-on-__time" href="#24.0.0-query-engine-updates-optimize-simple-min-%2F-max-sql-queries-on-__time">#</a> Optimiser les requêtes SQL simples MIN/MAX à __time

Les requêtes simples telles que select max(__time) from ds s'exécutent désormais comme des requêtes timeBoundary pour tirer parti du tri des dimensions temporelles dans un segment. Vous pouvez définir un indicateur de fonctionnalité pour activer cette fonctionnalité. #12472 #12491

<a name="24.0.0-query-engine-updates-string-aggregation-results" href="#24.0.0-query-engine-updates-string-aggregation-results">#</a> Résultats de l'agrégation de chaînes

Le premier/dernier agrégateur de chaînes compare désormais uniquement en fonction des valeurs. Auparavant, les valeurs du premier/dernier agrégateur de chaînes étaient comparées d'abord en fonction de la colonne _time, puis des valeurs. Si vous disposez de requêtes existantes et souhaitez continuer à utiliser à la fois la colonne et les valeurs _time, mettez à jour vos requêtes pour utiliser ORDER BY MAX(timeCol). #12773

<a name="24.0.0-query-engine-updates-reduced-allocations-due-to-jackson-serialization" href="#24.0.0-query-engine-updates-reduced-allocations-due-to-jackson-serialization">#</a> Allocations réduites en raison de la sérialisation de Jackson

Introduction et implémentation de nouvelles fonctions d'assistance dans JacksonUtils pour permettre la réutilisation de Objets SerializerProvider. De plus, la compatibilité ascendante est désactivée par défaut pour les lignes basées sur une carte dans le GroupByQueryToolChest, ce qui élimine le besoin de copier le ObjectMapper lourd. Introduction d'une option de configuration pour permettre aux administrateurs d'activer explicitement la compatibilité ascendante. #12468

<a name="24.0.0-query-engine-updates-updated-ipaddress-java-library-" href="#24.0.0-query-engine-updates-updated-ipaddress-java-library-">#</a> Bibliothèque Java IPAddress mise à jour

Ajout d'une nouvelle dépendance de bibliothèque Java IPAddress pour gérer les adresses IP. La bibliothèque inclut la prise en charge IPv6. De plus, les fonctions IPv4 ont migré pour utiliser la nouvelle bibliothèque. #11634

<a name="24.0.0-query-engine-updates-query-performance-improvements" href="#24.0.0-query-engine-updates-query-performance-improvements">#</a> Améliorations des performances des requêtes

Opérations et fonctions SQL optimisées comme suit :

  • Derniers agrégateurs numériques vectorisés (#12439)
  • isEmpty() et equals() optimisés sur RangeSets (#12477)
  • Réutilisation optimisée des objets Yielder (#12475)
  • Les opérations sur les colonnes numériques avec index sont désormais plus rapides (#12830)
  • GroupBy optimisé en réduisant les allocations. Allocations réduites en réutilisant les entrées et les détenteurs de clés (#12474)
  • Ajout d'une version vectorisée du dernier agrégateur de chaînes (#12493)
  • Ajout d'un accès direct UTF-8 pour les filtres IN (#12517)
  • Activation des colonnes virtuelles pour mettre en cache leurs sorties au cas où Druid les appellerait plusieurs fois sur la même ligne sous-jacente (#12577)
  • Druid réécrit désormais une jointure en tant que filtre lorsque cela est possible dans les jointures IN (#12225)
  • Ajout du dimensionnement automatique pour les dictionnaires GroupBy (#12763)
  • Druid distribue désormais les connexions JDBC de manière plus équitable entre les courtiers (#12817)

<a name="24.0.0-improvements-to-ingestion-in-general" href="#24.0.0-improvements-to-ingestion-in-general">#</a> Améliorations de l'ingestion en général

Cette version inclut les améliorations suivantes pour l’ingestion en général.

<a name="24.0.0-improvements-to-ingestion-in-general-increased-robustness-for-task-management" href="#24.0.0-improvements-to-ingestion-in-general-increased-robustness-for-task-management">#</a> Robustesse accrue pour la gestion des tâches

Ajout de setNumProcessorsPerTask pour empêcher divers pools de threads dimensionnés automatiquement de devenir déraisonnablement grands. Il n'est pas idéal que chaque tâche dimensionne ses pools comme s'il s'agissait du seul processus sur l'ensemble de la machine. Sur les grandes machines, cela résout une cause courante de OutOfMemoryError due à "l'impossibilité de créer un thread natif". #12592

<a name="24.0.0-improvements-to-ingestion-in-general-avatica-jdbc-driver" href="#24.0.0-improvements-to-ingestion-in-general-avatica-jdbc-driver">#</a> Pilote JDBC Avatica

Le pilote JDBC suit désormais la norme JDBC et utilise deux types d'instructions, Statement et PreparedStatement. #12709

<a name="24.0.0-improvements-to-ingestion-in-general-eight-hour-granularity" href="#24.0.0-improvements-to-ingestion-in-general-eight-hour-granularity">#</a> Granularité de huit heures

Druid accepte désormais la granularité EIGHT_HOUR. Vous pouvez segmenter les données entrantes dans des compartiments EIGHT_HOUR ainsi que regrouper les résultats des requêtes selon une granularité de huit heures. #12717

<a name="24.0.0-ingestion-general" href="#24.0.0-ingestion-general">#</a> Ingestion générale

<a name="24.0.0-ingestion-general-updated-avro-extension" href="#24.0.0-ingestion-general-updated-avro-extension">#</a> Extension Avro mise à jour

L'extension Avro précédente a divulgué des objets de l'analyseur. Si ces objets ont été divulgués dans votre ingestion, vos objets étaient stockés sous forme de colonne de chaîne avec la valeur .toString(). Cette colonne de chaîne restera après la mise à niveau mais renverra Map.toString() au lieu de GenericRecord.toString. Si vous vous êtes appuyé sur le comportement précédent, vous pouvez utiliser l'extension Avro d'une version antérieure. #12828

<a name="24.0.0-ingestion-general-sampler-api" href="#24.0.0-ingestion-general-sampler-api">#</a> Échantillonneur API

Le sampler API a des limites supplémentaires : maxBytesInMemory et maxClientResponseBytes. Ces options complètent les options existantes numRows et timeoutMs. Le maxBytesInMemory peut être utilisé pour contrôler l'utilisation de la mémoire sur l'Overlord pendant l'échantillonnage. maxClientResponseBytes peut être utilisé par clients pour spécifier la taille maximale de réponse qu'ils préféreraient gérer. #12947

<a name="24.0.0-sql" href="#24.0.0-sql">#</a> SQL

<a name="24.0.0-sql-column-order" href="#24.0.0-sql-column-order">#</a> Ordre des colonnes

Les propriétés DruidSchema et SegmentMetadataQuery conservent désormais l'ordre des colonnes au lieu de les trier par ordre alphabétique. Cela signifie que l’ordre des requêtes correspond mieux à l’ordre d’ingestion. #12754

<a name="24.0.0-sql-converting-joins-to-filter" href="#24.0.0-sql-converting-joins-to-filter">#</a> Conversion des JOIN en filtre

Vous pouvez améliorer les performances en poussant les JOIN partiellement ou entièrement vers la table de base en tant que filtre au moment de l'exécution en définissant le paramètre de contexte enableRewriteJoinToFilter sur true pour une requête. Druid abaisse désormais les filtres de jointure au cas où la jointure informatique de requête ferait référence à des colonnes du côté droit. #12749 #12868

<a name="24.0.0-sql-add-is_active-to-sys.segments" href="#24.0.0-sql-add-is_active-to-sys.segments">#</a> Ajouter is_active à sys.segments

Ajout de is_active comme raccourci pour (is_published = 1 AND is_overshadowed = 0) OR is_realtime = 1). Cela représente "tous les segments qui devraient être interrogeables, qu'ils le soient ou non actuellement". #11550

<a name="24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true" href="#24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true">#</a> useNativeQueryExplain est désormais true par défaut

La propriété useNativeQueryExplain est désormais par défaut true. Cela signifie que EXPLAIN PLAN FOR renvoie le plan d'explication sous la forme d'une représentation JSON de requêtes natives équivalentes par défaut. Pour plus d'informations, consultez Supplémentation de configuration des requêtes générées par le courtier. #12936

<a name="24.0.0-inline-query-engine" href="#24.0.0-inline-query-engine">#</a> Exécution de requêtes avec des données en ligne à l'aide du moteur de requête Druid

Certaines requêtes qui ne font référence à aucune table, comme select 1, sont désormais toujours traduites en requête Druid native avec InlineDataSource avant exécution. Si la traduction n'est pas possible, pour des requêtes telles que SELECT (1, 2), une erreur se produit. Dans les versions antérieures, cette requête était toujours exécutée. #12897

<a name="24.0.0-coordinator%2Foverlord" href="#24.0.0-coordinator%2Foverlord">#</a> Coordinateur/Overlord

<a name="24.0.0-coordinator%2Foverlord-you-can-configure-the-coordinator-to-kill-segments-in-the-future" href="#24.0.0-coordinator%2Foverlord-you-can-configure-the-coordinator-to-kill-segments-in-the-future">#</a> Vous pouvez configurer le coordinateur pour qu'il tue des segments à l'avenir

Vous pouvez maintenant définir druid.coordinator.kill.durationToRetain sur une période négative pour configurer le cluster Druid pour tuer les segments dont interval_end est une date dans le futur. Par exemple, PT-24H permettrait la suppression de segments si leur date de fin d'intervalle était de 24 heures ou moins dans le futur au moment où la tâche de suppression est générée par le système. Un opérateur de cluster peut également ignorer complètement le druid.coordinator.kill.durationToRetain en définissant une nouvelle configuration, druid.coordinator.kill.ignoreDurationToRetain=true. Cela ignore la date interval_end lors de la recherche de segments à supprimer et peut à la place tuer tout segment marqué comme inutilisé. Cette nouvelle configuration est désactivée par défaut et un opérateur de cluster doit pleinement comprendre et accepter les risques avant de l'activer.

<a name="24.0.0-coordinator%2Foverlord-improved-overlord-stability" href="#24.0.0-coordinator%2Foverlord-improved-overlord-stability">#</a> Amélioration de la stabilité d'Overlord

Réduction des conflits entre le thread de gestion et la réception des mises à jour d'état du cluster. Cela améliore la stabilité d'Overlord et de toutes les tâches d'un cluster lorsqu'il y a un grand nombre de tâches (plus de 1 000). #12099

<a name="24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging" href="#24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging">#</a> Journalisation améliorée des segments du coordinateur

Mise à jour de la journalisation des règles de chargement du coordinateur pour inclure les niveaux de réplication actuels. Ajout d'un ID de segment manquant et d'informations sur les niveaux dans certains messages du journal. #12511

<a name="24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage" href="#24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage">#</a> Utilisation optimisée de la mémoire des tâches overlord GET

Correction de la surcharge de mémoire importante causée par la console Web appelant indirectement les tâches GET d'Overlord API. Cela pourrait entraîner une absence de réponse ou un échec d'Overlord lorsque l'onglet d'ingestion était ouvert plusieurs fois. #12404

<a name="24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals" href="#24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals">#</a> Temps réduit pour créer des intervalles

Afin d'optimiser le temps de calcul du coût des segments en réduisant le temps nécessaire à la création de l'intervalle, stockez l'intervalle de segment au lieu de le créer à chaque fois à partir de primitives et réduisez la surcharge de mémoire liée au stockage des intervalles en les internant. L'ensemble d'intervalles pour les segments est de faible cardinalité. #12670

<a name="24.0.0--brokers%2Foverlord" href="#24.0.0--brokers%2Foverlord">#</a> Courtiers/Overlord

Les courtiers disposent désormais d'une limite par défaut de 25 Mo maximum en file d'attente par requête. Auparavant, il n'y avait pas de limite par défaut. En fonction de votre cas d'utilisation, vous devrez peut-être augmenter la valeur, surtout si vous disposez de grands ensembles de résultats ou de grandes quantités de données intermédiaires. Pour ajuster la mémoire maximale disponible, utilisez la propriété druid.broker.http.maxQueuedBytes. Pour plus d'informations, consultez Référence de configuration.

Les requêtes exécutées avec le moteur de tâches de requête à plusieurs étapes sont des tâches. Cela permet d'afficher les requêtes en cours d'exécution et celles qui ont été exécutées dans un passé récent. Pour toute requête dans le panneau Tâches de requête récentes, vous pouvez afficher les détails d'exécution de celle-ci et vous pouvez également la joindre en tant que nouvel onglet et continuer à itérer sur la requête. Il est également possible de télécharger « l'archive des détails de la requête », un fichier JSON contenant tous les détails importants d'une requête donnée à utiliser pour le dépannage.

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-connect-external-data-flow" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-connect-external-data-flow">#</a> Connecter le flux de données externe

Le flux de données externe Connect vous permet d'utiliser l'échantillonneur pour échantillonner vos données sources, déterminer leur schéma et générer une requête SQL entièrement formée que vous pouvez modifier pour l'adapter à votre cas d'utilisation avant de lancer votre tâche d'ingestion. Ce flux pointer-et-click vous fera économiser beaucoup de saisie.

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-preview-button" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-preview-button">#</a> Bouton Aperçu

Le bouton Aperçu apparaît lorsque vous saisissez une requête SQL INSERT ou REPLACE. Clicliquez sur le bouton pour supprimer la clause INSERT ou REPLACE et exécutez votre requête en tant que requête "en ligne" avec une limi). Cela vous donne une idée de la forme de vos données une fois que Druid a appliqué toutes vos transformations à partir de votre requête SQL.

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-results-table" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-results-table">#</a> Tableau des résultats

Le tableau des résultats de la requête a été amélioré en termes de style et de fonctionnalité. Il vous montre désormais des icônes de saisie pour les types de colonnes et prend en charge la possibilité de manipuler facilement les colonnes imbriquées.

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-helper-queries" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-helper-queries">#</a> Requêtes d'assistance

La console Web propose désormais certaines fonctionnalités d'interface utilisateur pour les utilisateurs d'ordinateurs portables et de CTE. Vous pouvez référencer des requêtes d'assistance, des éléments réductibles contenant une requête, à partir de la requête principale, tout comme ils ont été définis avec une instruction WITH. Lorsque vous composez une requête complexe, il est utile de la diviser en plusieurs requêtes pour prévisualiser les parties individuellement.

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-additional-web-console-tools" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-additional-web-console-tools">#</a> Outils supplémentaires de la console Web

<a name="24.0.0--brokers%2Foverlord-web-console-new-sql-based-data-loader" href="#24.0.0--brokers%2Foverlord-web-console-new-sql-based-data-loader">#</a> Nouveau chargeur de données basé sur SQL

Le chargeur de données existe sous la forme d'un assistant graphique pour aider les utilisateurs à créer une spécification d'ingestion JSON à l'aide de points et click et d'aperçus rapides. Le chargeur de données SQL en est l'analogue d'ingestion basé sur SQL. Comme le chargeur de données natif, le chargeur de données basé sur SQL stocke tout l'état dans la requête SQL elle-même. <a name="24.0.0-upgrading-to-24.0-behavior-for-unused-segments" href="#24.0.0-upgrading-to-24.0-behavior-for-unused-segments">#</a> Comportement des segments inutilisés

Druid conserve automatiquement tous les segments marqués comme inutilisés. Auparavant, Druid supprimait définitivement les segments inutilisés du magasin de métadonnées et du stockage profond après leur durée pour les conserver. Ce comportement a été annulé depuis 0.23.0. #12693

<a name="24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60" href="#24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60">#</a> Valeur par défaut pour druid.processing.fifo

La valeur par défaut pour druid.processing.fifo est désormais vraie. Cela signifie que les tâches d’égale priorité sont traitées de manière FIFO. Dans la plupart des cas d'utilisation, cette modification peut améliorer les performances sur les clusters fortement chargés. #12571

<a name="24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure" href="#24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure">#</a> Mise à jour de la fermeture de l'instruction JDBC

Dans les versions précédentes, Druid fermait automatiquement l'instruction JDBC lorsque le ResultSet était fermé. Druid a fermé le ResultSet sur EOF. Druid a clôturé la déclaration à toute exception. Ce comportement n’est cependant pas standard. Dans cette version, le pilote JDBC de Druid suit de plus près les normes JDBC : Le ResultSet se ferme automatiquement sur EOF, mais ne ferme pas l'instruction ou le PreparedStatement. Votre code doit fermer ces instructions, peut-être en utilisant un bloc try-with-resources. Le PreparedStatement peut désormais être utilisé plusieurs fois avec différents paramètres. (Auparavant, ce n'était pas vrai puisque la fermeture du ResultSet fermait le PreparedStatement.) Si un appel à une instruction ou à un PreparedStatement génère une erreur, le code client doit toujours fermer explicitement l'instruction. Selon les normes JDBC, les instructions ne sont pas fermées automatiquement en cas d'erreur. Cela vous permet d'obtenir des informations sur une instruction ayant échoué avant de la fermer. Si votre code dépend de l'ancien comportement, vous devrez peut-être modifier votre code pour ajouter l'instruction de fermeture requise. #12709
