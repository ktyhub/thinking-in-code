Fonctionnalités, modifications et dépréciations importantes

Cette section contient des informations importantes sur les fonctionnalités nouvelles et existantes.

Prise en charge de Java 11

La prise en charge de Java 11 est obsolète depuis Druid 32.0, et la prise en charge officielle sera supprimée dès Druid 35.0.0

Ingestion basée sur Hadoop

L'ingestion basée sur Hadoop est obsolète depuis Druid 32.0 et sera supprimée dès Druid 35.0.0. Nous recommandons l'une des autres méthodes d'ingestion prises en charge par Druid, telles que l'ingestion basée sur SQL ou l'ingestion sans MiddleManager à l'aide de Kubernetes.

Dans le cadre de ce changement, vous devez désormais choisir d'utiliser le type de tâche obsolète index_hadoop. Si vous ne le faites pas, vos tâches d'ingestion basées sur Hadoop échoueront.

Pour vous inscrire, définissez druid.indexer.task.allowHadoopTaskExecution sur true dans votre fichier common.runtime.properties.

#18239

Utiliser les instructions SET pour les paramètres de contexte de requête

Vous pouvez désormais utiliser les instructions SET pour définir les paramètres de contexte de requête pour une requête via la console Druid ou la API.

#17894 #17974

Instructions SET dans la console Druid

La console Web prend désormais en charge l'utilisation des instructions SET pour spécifier les paramètres de contexte de requête. Par exemple, si vous incluez SET timeout = 20000; dans votre requête, le paramètre de contexte de requête d'expiration est défini :

SET timeout = 20000;
SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2

#17966

Instructions SET avec le API

Les requêtes SQL émises vers /druid/v2/sql peuvent désormais inclure plusieurs instructions SET pour créer le contexte de l'instruction finale. Par exemple, les résultats de requête SQL suivants incluent les paramètres de contexte de requête timeout, useCache, populateCache, vectorize et engine :

SET timeout = 20000;
SET useCache = false;
SET populateCache = false;
SET vectorize = 'force';
SET engine = 'msq-dart'
SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2

L'appel API pour cette requête ressemble à ce qui suit :

curl --location 'http://HOST:PORT/druid/v2/sql' \
--header 'Content-Type: application/json' \
--data '{
  "query": "SET timeout=20000; SET useCache=false; SET populateCache=false; SET engine='\''msq-dart'\'';SELECT  user,  commentLength,COUNT(*) AS \"COUNT\" FROM wikipedia GROUP BY 1, 2 ORDER BY 2 DESC",
  "resultFormat": "array",
  "header": true,
  "typesHeader": true,
  "sqlTypesHeader": true
}'

Cette amélioration fonctionne également pour les requêtes INSERT et REPLACE utilisant le moteur de tâches MSQ. Notez que JDBC n'est pas pris en charge.

Points de terminaison HTTP améliorés

Vous pouvez désormais utiliser du SQL brut dans le corps HTTP pour les points de terminaison /druid/v2/sql. Vous pouvez définir Content-Type sur text/plain au lieu de application/json, afin de pouvoir fournir du texte brut qui n'est pas échappé.

#17937

Historiques de clonage (expérimental)

Vous pouvez désormais configurer des clones pour les historiques à l'aide de la configuration dynamique du coordinateur cloneServers. Les historiques clonés sont utiles dans des situations telles que les mises à jour progressives dans lesquelles vous souhaitez lancer un nouvel historique en remplacement d'un historique existant.

Définissez la configuration sur une carte du serveur historique cible vers l'historique source :

  "cloneServers": {"historicalClone":"historicalOriginal"}

Le clone ne participe pas à l’affectation ou à l’équilibrage régulier des segments. Au lieu de cela, le coordinateur reflète toute affectation de segment effectuée à l'historique d'origine sur le clone, de sorte que le clone devienne une copie exacte de la source. Les segments sur le clone historique ne sont pas non plus pris en compte dans le nombre de répliques. Si l'historique d'origine disparaît, le clone reste dans le dernier état connu du serveur source jusqu'à ce qu'il soit supprimé de la configuration cloneServers.

Lorsque vous interrogez vos données à l'aide du moteur de requête natif, vous pouvez préférer (preferClones), exclure (excludeClones) ou inclure (includeClones) des clones en définissant le paramètre de contexte de requête cloneQueryMode. Par défaut, les clones sont exclus.

Dans le cadre de ce changement, de nouveaux coordinateurs API sont disponibles. Pour plus d’informations, consultez Coordinateur APIs pour les clones.

#17863 #17899 #17956

Tâches d'élimination intégrées sur l'Overlord (expérimental)

Vous pouvez désormais exécuter des tâches de mise à mort directement sur l'Overlord lui-même. Les tâches d'arrêt intégrées offrent plusieurs avantages : ils :

  • Tuez les segments dès qu'ils sont éligibles
  • Ne prends pas de place pour les tâches
  • terminent plus vite puisqu'ils utilisent des requêtes de métadonnées optimisées et ne lancent pas de nouveau JVM
  • Tuez un petit nombre de segments par tâche, garantissant que les verrous sur un intervalle ne sont pas maintenus trop longtemps
  • Sautez les intervalles verrouillés pour éviter le blocage en tête de ligne
  • Nécessite une configuration minimale
  • Peut suivre un grand nombre de segments inutilisés dans le cluster

Cette fonctionnalité est contrôlée par les configurations suivantes :

  • druid.manager.segments.killUnused.enabled - Si la fonctionnalité est activée ou non (par défaut : false)
  • druid.manager.segments.killUnused.bufferPeriod - La durée pendant laquelle un segment doit être inutilisé avant de pouvoir être définitivement supprimé des métadonnées et du stockage profond. Cela peut servir de période tampon pour éviter la perte de données si les données finissent par être nécessaires après avoir été marquées comme inutilisées (par défaut : P30D).

Pour utiliser les tâches d'élimination intégrées, vous devez activer le cache de métadonnées de segment.

Dans le cadre de cette fonctionnalité, de nouvelles métriques ont été ajoutées.

#18028 #18124

Sélection du niveau préféré

Vous pouvez désormais configurer le service Broker pour privilégier les historiques sur un niveau spécifique. Ceci est utile pour le déploiement dans toute la zone de disponibilité. Les courtiers d'une AZ sélectionnent par défaut les historiques dans la même AZ, mais conservent la possibilité de sélectionner des nœuds historiques dans une autre AZ si les historiques dans la même AZ ne sont pas disponibles.

Pour l'activer, définissez la propriété druid.broker.select.tier sur perferred dans les propriétés d'exécution du courtier. Vous pouvez ensuite configurer druid.broker.select.tier.preferred.tier sur le niveau que vous souhaitez que chaque courtier préfère (c'est-à-dire pour les courtiers de AZ1, vous pouvez définir ce niveau sur le nom de niveau de vos serveurs historiques AZ1).

#18136

Améliorations des fléchettes

Le moteur de requête Dart utilise désormais le point de terminaison /druid/v2/sql comme les autres moteurs de requête SQL. L'ancien point de terminaison spécifique à Dart n'est plus pris en charge. Pour utiliser Dart pour une requête, incluez le paramètre de contexte de requête engine et définissez-le sur msq-dart.

#18003 #18003

L'activation de Dart reste la même, ajoutez la ligne suivante à vos fichiers broker/runtime.properties et historical/runtime.properties :

druid.msq.dart.enabled = true

De plus, Dart interroge désormais par défaut les tâches en temps réel. Vous pouvez contrôler ce comportement en définissant le paramètre de contexte de requête includeSegmentSource sur REALTIME (par défaut) ou NONE, de la même manière que pour les tâches MSQ. Vous pouvez également exécuter des requêtes synchrones ou asynchrones.

Gestion des clusters

Délai d'expiration configurable pour les sous-tâches

Vous pouvez désormais configurer un timeout pour les tâches de type index_parallel et compact. Définissez le paramètre de contexte subTaskTimeoutMillis sur la durée maximale en millisecondes que vous souhaitez attendre avant qu'une sous-tâche ne soit annulée. Par défaut, il n'y a pas de délai d'attente.

L'utilisation de cette configuration aide les tâches parentes à échouer plus tôt au lieu de rester bloquées en exécutant des sous-tâches zombies.

## Notes de mise à niveau et modifications incompatibles

Notes de mise à niveau

Ingestion basée sur Hadoop

L'ingestion basée sur Hadoop est obsolète depuis Druid 32.0 et sera supprimée dès Druid 35.0.0.

Nous recommandons l'une des autres méthodes d'ingestion prises en charge par Druid, telles que l'ingestion basée sur SQL ou l'ingestion sans MiddleManager à l'aide de Kubernetes. Dans le cadre de ce changement, vous devez désormais choisir d'utiliser le type de tâche obsolète index_hadoop. Si vous ne le faites pas, vos tâches d'ingestion basées sur Hadoop échoueront. Pour vous inscrire, définissez druid.indexer.task.allowHadoopTaskExecution sur true dans votre fichier common.runtime.properties. #18239

Requêtes groupBy et topN

Druid utilise désormais le type de requête natif groupBy, plutôt que topN, pour les requêtes SQL qui regroupent par et commande par la même colonne, j'ai LIMIT et je n'ai pas HAVING. Cela accélère l'exécution de telles requêtes puisque groupBy est vectorisé alors que topN ne l’est pas.

Vous pouvez restaurer le comportement précédent en définissant le paramètre de contexte de requête useLexicographicTopN sur true. Le comportement de useApproximateTopN est inchangé et la valeur par défaut reste true.

#18074

Configuration IS_INCREMENTAL_HANDOFF_SUPPORTED supprimée

Suppression de la référence de contexte IS_INCREMENTAL_HANDOFF_SUPPORTED des superviseurs, car la publication incrémentielle est le comportement par défaut depuis la version 0.16.0. Ce contexte a été initialement introduit pour prendre en charge la restauration vers LegacyKafkaIndexTaskRunner dans les versions antérieures à 0.16.0, qui a depuis été supprimée.

Configuration useMaxMemoryEstimates supprimée

Suppression de la configuration useMaxMemoryEstimates. Lorsqu'il est défini sur false, Druid a utilisé une estimation de mémoire beaucoup plus précise qui a été introduite dans Druid 0.23.0. Cette méthode plus précise est la seule méthode disponible actuellement. La configuration est par défaut sur false pour plusieurs versions.
