druide druide-37.0.0

Apache Druid 37.0.0 contient plus de 255 nouvelles fonctionnalités, corrections de bogues, améliorations des performances, améliorations de la documentation et couverture de tests supplémentaire de 29 contributeurs.

Consultez l'ensemble complet de modifications pour plus de détails, y compris les corrections de bogues.

Consultez les notes de mise à niveau et les modifications incompatibles avant de procéder à la mise à niveau vers Druid 37.0.0. Si vous effectuez une mise à niveau sur plusieurs versions, consultez la page [Notes de mise à niveau] (upgrade-notes.md), qui répertorie les notes de mise à niveau pour les versions de Druid les plus récentes.

Fonctionnalités, modifications et dépréciations importantes

Cette section contient des informations importantes sur les fonctionnalités nouvelles et existantes.

Ingestion basée sur Hadoop

La prise en charge de l'ingestion basée sur Hadoop a été supprimée. La fonctionnalité était obsolète dans Druid 34.

Utilisez l’une des autres méthodes d’ingestion prises en charge par Druid, telles que l’ingestion basée sur SQL ou l’ingestion sans MiddleManager à l’aide de Kubernetes.

#19109

Liste de blocage des requêtes

Vous pouvez désormais utiliser le courtier API (/druid/coordinator/v1/config/broker) pour créer une liste de blocage de requêtes afin de bloquer dynamiquement les requêtes par source de données, type de requête ou contexte de requête. La liste de blocage prend effet sans redémarrage du Druide. Les règles de blocage utilisent la logique AND, ce qui signifie que tous les critères doivent correspondre.

L'exemple suivant bloque toutes les requêtes groupBy sur la source de données wikipedia avec un paramètre de contexte de requête priority égal à 0 :

POST /druid/coordinator/v1/config/broker
  {
    "queryBlocklist": [
      {
        "ruleName": "block-wikipedia-groupbys",
        "dataSources": ["wikipedia"],
        "queryTypes": ["groupBy"],
        "contextMatches": {"priority": "0"}
      }
    ]
  }

#19011

Compactage mineur pour le compactage basé sur Overlord (expérimental)

Vous pouvez désormais configurer un compactage mineur pour compacter uniquement les segments nouvellement ingérés tout en mettant à niveau les segments compactés existants. Lorsque Druid met à niveau les segments, il met à jour les métadonnées au lieu d'utiliser des ressources pour les compacter à nouveau. Vous pouvez utiliser le moteur de compactage natif ou le moteur de tâches MSQ.

Utilisez la stratégie de compactage mostFragmentedFirst et définissez un pourcentage de seuil basé sur les lignes ou sur les octets pour un compactage mineur.

#19059 #19205 #19016

Réindexation en cascade (expérimentale)

Grâce à la réindexation en cascade, vous pouvez désormais définir des règles basées sur l'âge pour appliquer automatiquement différentes configurations de compactage en fonction de l'âge de vos données. Alors que le compactage automatique standard applique une seule configuration plate sur l'ensemble d'une source de données, la réindexation en cascade vous permet d'adapter vos paramètres de compactage aux caractéristiques de vos données.

Par exemple, vous pouvez conserver les données récentes dans des segments horaires tout en les reportant automatiquement aux segments quotidiens après 90 jours pour réduire le nombre de segments. Vous pouvez également appliquer une suppression de lignes basée sur l'âge (par exemple en supprimant le trafic de robots à partir de données plus anciennes), modifier les paramètres de compression ou passer au cumul avec une granularité de requête plus grossière à mesure que les données vieillissent. Les règles sont définies en ligne dans la spécification du superviseur.

Vous devez utiliser des superviseurs de compactage avec le moteur de tâches MSQ pour utiliser la réindexation en cascade.

#18939 #19213 #19106 #19078

Ingestion multi-superviseur

L’ingestion multi-superviseur est désormais généralement disponible. Vous pouvez exécuter plusieurs superviseurs de flux qui ingèrent dans la même source de données.

#18983

Autorisateur en lecture seule

Ajout d'un autorisateur ReadOnly à Druid. Il s'agit du premier autorisateur mondial pour Druid. L'autorisateur applique une restriction globale sur toutes les opérations non READ, les refusant quelles que soient les autorisations individuelles des utilisateurs. Vous pouvez utiliser cette fonctionnalité pour garantir que tous les utilisateurs d'un mécanisme d'autorisation spécifique sont limités à l'accès READ.

Il existe une limitation connue selon laquelle certains points de terminaison nécessitent actuellement un accès en ÉCRITURE bien qu'ils soient en LECTURE seule, comme GET /druid/indexer/v1/supervisor. Ces opérations échoueront.

#19243

Format d'entrée d'épargne

Dans le cadre de l'extension de contributeur Thrift, Druid prend désormais en charge les données codées Thrift pour l'ingestion de streaming Kafka et Kinesis à l'aide de InputFormat. Auparavant, Druid prenait en charge cela via des analyseurs, qui ont été supprimés dans Druid 37.

Cache incrémentiel

Le cache de métadonnées de segment incrémentiel (useIncrementalCache) est désormais généralement disponible et sa valeur par défaut est ifSynced. Druid bloque les lectures à partir du cache jusqu'à ce qu'il soit synchronisé avec le magasin de métadonnées au moins une fois après être devenu leader.

#19128

Contexte de requête dynamique par défaut

Vous pouvez désormais ajouter des paramètres de contexte de requête par défaut en tant que configuration dynamique au Broker. Cela vous permet de remplacer les valeurs statiques par défaut définies dans vos propriétés d'exécution sans redémarrer votre déploiement ni avoir à mettre à jour plusieurs requêtes individuellement. Druid applique les paramètres de contexte de requête en fonction de la priorité suivante :

  1. Le contexte de requête inclus dans la requête
  2. Le contexte de requête défini en configuration dynamique sur le Broker
  3. Les paramètres de contexte de requête définis dans les propriétés d'exécution
  4. Les valeurs par défaut fournies avec Druid

Notez que, comme pour les autres configurations dynamiques du Broker, il s'agit d'un effort optimal. Les paramètres peuvent ne pas être appliqués dans certains cas, par exemple lorsqu'un courtier a récemment démarré et n'a pas encore reçu la configuration, ou si le Le courtier ne peut pas contacter le coordonnateur. Si un paramètre de contexte de requête est critique pour toutes vos requêtes, définissez-le dans les propriétés d'exécution.

#19144

Table sys.queries (expérimentale)

Le nouveau tableau des requêtes système fournit des informations sur les requêtes en cours d'exécution et récemment terminées qui utilisent le moteur Dart. Ce tableau est désactivé par défaut. Pour activer la table, définissez les éléments suivants :

druid.sql.planner.enableSysQueriesTable = true

Dans le cadre de ce changement, le /druid/v2/sql/queries API prend désormais en charge un paramètre includeComplete qui affiche les requêtes récemment terminées.

#18923

Auto-compaction avec des superviseurs de compactage

Le compactage automatique à l'aide de superviseurs de compactage a été amélioré, désormais généralement disponible et constitue la valeur par défaut recommandée. Les tâches de compactage automatique portent désormais le préfixe auto au lieu de coordinator-issued.

Dans le cadre de l'amélioration, les états de compactage sont désormais stockés dans un emplacement central, une nouvelle table indexingStates. Les segments individuels doivent uniquement stocker une référence unique (indexing_state_fingerprint) pour leur état de compactage complet.

Étant donné que de nombreux segments d’une même source de données partagent le même état de compactage sous-jacent, cela réduit considérablement les besoins en stockage de métadonnées pour le compactage automatique.

Pour des raisons de compatibilité ascendante, Druid continue de conserver l'état de compactage détaillé dans chaque segment. Cette fonctionnalité sera supprimée dans une prochaine version. Vous pouvez arrêter de stocker l'état de compactage détaillé en définissant storeCompactionStatePerSegment sur false dans la configuration de compactage du cluster. Si vous le désactivez et devez rétrograder, Druid doit recompacter tous les segments qui ont été compactés depuis que vous avez modifié la configuration.

Ce changement a des impacts de mise à niveau sur le stockage et la mise en cache des métadonnées. Pour plus d’informations, consultez la note de mise à niveau Stockage de métadonnées pour le compactage automatique avec des superviseurs de compactage.

Vous souhaiterez peut-être procéder ainsi s'il existe des courtiers qui n'ont pas de visibilité sur certains niveaux de données et que vous savez que vous interrogez des données disponibles uniquement sur un certain niveau.

Interrogation

configuration de la requête groupBy

Ajout d'une nouvelle propriété de configuration de requête groupBy druid.query.groupBy.maxSpillFileCount pour limiter le nombre maximum de fichiers auxiliaires créés par requête. #19141

Gestion améliorée des agrégats imbriqués

Druid peut désormais fusionner deux agrégats avec une projection entre eux. Par exemple, la requête suivante :

SELECT
  hr,
  UPPER(t1.x) x,
  SUM(t1.cnt) cnt,
  MIN(t1.mn) mn,
  MAX(t1.mx) mx
FROM (
  SELECT
    floor(__time to hour) hr,
    dim2 x,
    COUNT(*) cnt,
    MIN(m1 * 5) mn,
    MAX(m1 + m2) mx
  FROM druid.foo
  WHERE dim2 IN ('abc', 'def', 'a', 'b', '')
  GROUP BY 1, 2
) t1
WHERE t1.x IN ('abc', 'foo', 'bar', 'a', '')
GROUP BY 1, 2

peut être simplifié comme suit :

SELECT
  FLOOR(__time TO hour) hr,
  UPPER(dim2) x,
  COUNT(*) cnt,
  MIN(m1 * 5) mn,
  MAX(m1 + m2) mx
FROM druid.foo
WHERE dim2 IN ('abc', 'a', '')
GROUP BY 1, 2

Gestion des clusters

Stratégies de sélection de nouveaux niveaux de courtier

Les opérateurs peuvent désormais configurer deux nouvelles implémentations du Broker TierSelectorStrategy :

  • strict - Sélectionne uniquement les serveurs dont les priorités correspondent à la liste configurée. Exemple de configuration : druid.broker.select.tier=strict et druid.broker.select.tier.strict.priorities=[1].
  • pooled - Regroupe les serveurs selon les priorités configurées et sélectionne parmi elles, permettant aux requêtes d'utiliser plusieurs niveaux de priorité pour une disponibilité améliorée. Exemple de configuration : druid.broker.select.tier=pooled et druid.broker.select.tier.pooled.priorities=[2,1].

Vous pouvez également utiliser druid.broker.realtime.select.tier pour configurer ces stratégies pour les serveurs en temps réel.

Gestion des données

Configuration du délai d'expiration par segment

Vous pouvez désormais définir un délai d'expiration pour les segments d'une source de données spécifique à l'aide d'une configuration dynamique :

POST /druid/coordinator/v1/config/broker
  {
    "perSegmentTimeoutConfig": {
      "my_large_datasource": { "perSegmentTimeoutMs": 5000, "monitorOnly": false },
      "my_new_datasource": { "perSegmentTimeoutMs": 3000, "monitorOnly": true }
    }
  }

Ceci est utile lorsque différentes sources de données ont des caractéristiques de performances différentes, par exemple en autorisant des délais d'attente plus longs pour des ensembles de données plus volumineux.

#19221

Nettoyant de stockage durable

Le nettoyeur de stockage durable prend désormais en charge la conservation configurable basée sur le temps pour les résultats des requêtes MSQ. Auparavant, les résultats des requêtes étaient conservés pour toutes les tâches connues, ce qui n'était pas fiable pour les tâches terminées. Avec cette modification, les résultats de la requête sont conservés pendant une période configurable en fonction de l'heure de création de la tâche.

La nouvelle propriété de configuration druid.msq.intermediate.storage.cleaner.durationToRetain contrôle la période de conservation des résultats de requête. La période de conservation par défaut est de 6 heures.

La source d'entrée Iceberg prend désormais en charge les entrepôts GCS. Pour utiliser cette fonctionnalité, vous devez charger l'extension druid-google-extensions en plus de l'extension Iceberg. #19137

Filtres

Vous pouvez désormais configurer des filtres résiduels pour les colonnes non partitionnées lorsque vous utilisez la source d'entrée Iceberg. Réglez residualFilterMode dans la source d'entrée Iceberg sur l'un des éléments suivants :

  • ignore : (par défaut) Ingère les lignes résiduelles avec un journal d'avertissement à moins qu'elles ne soient filtrées par transformSpec.
  • fail : échec de la tâche d'ingestion lorsque des filtres résiduels sont détectés. Utilisez ceci pour garantir que les filtres ciblent uniquement les colonnes de partition.

#18953

Stockage HDFS

Ajout de la prise en charge de la compression lz4. Dans le cadre de ce changement, les métriques suivantes sont désormais disponibles :

-hdfs/pull/size -hdfs/pull/duration -hdfs/push/size -hdfs/push/duration

#18982

## Notes de mise à niveau et modifications incompatibles

Notes de mise à niveau

Ingestion basée sur Hadoop

La prise en charge de l'ingestion basée sur Hadoop a été supprimée. La fonctionnalité était obsolète dans Druid 34.

Utilisez l’une des autres méthodes d’ingestion prises en charge par Druid, telles que l’ingestion basée sur SQL ou l’ingestion sans MiddleManager à l’aide de Kubernetes.

#19109

AWS SDK v2

Druid utilise désormais AWS SDK version 2.40.0 puisque la v1 du SDK est en fin de vie.

#18891

Cache de métadonnées de segment activé par défaut

À partir de Druid 37, le cache des métadonnées des segments est activé par défaut. Cette fonctionnalité permet au courtier de mettre en cache les métadonnées des segments interrogées auprès du coordinateur, plutôt que d'avoir à récupérer les métadonnées pour chaque requête sur la table sys.segments. Cela améliore les performances mais augmente l'utilisation de la mémoire sur les courtiers.

La configuration druid.sql.planner.metadataSegmentCacheEnable contrôle cette fonctionnalité.

#19075

Modifications de l'analyseur

Ingestion de flux parser

La prise en charge du parser obsolète a été supprimée pour les tâches d'ingestion de streaming telles que Kafka et Kinesis. Les opérateurs doivent désormais spécifier inputSource/inputFormat sur le ioConfig de la spécification du superviseur, et le dataSchema ne doit pas spécifier d'analyseur. Faites-le avant de passer à Druid 37 ou une version plus récente.

#19173 #19166

Suppression de ParseSpec et des analyseurs obsolètes

L'analyseur pour les tâches par lots natives et les services d'indexation d'ingestion de streaming a été supprimé. Dans la mesure du possible, utilisez plutôt le format d’entrée. Notez que JavascriptParseSpec et JSONLowercaseParseSpec n’ont pas d’équivalents InputFormat.

Druid prend en charge les formats de données texte personnalisés et peut utiliser le format d'entrée Regex pour les analyser. Cependant, soyez conscient de faire cela pour l'analyse des données est moins efficace que l'écriture d'une extension Java InputFormat native ou l'utilisation d'un processeur de flux externe. Nous apprécions les contributions de nouveaux formats d’entrée.

#19239

Mises à jour progressives des versions Druid antérieures à la version 0.23

Vous ne pouvez pas effectuer de mise à niveau continue à partir de versions antérieures à Druid 0.23.

#18961

Stockage de métadonnées pour l'auto-compactage avec les superviseurs de compactage

Le compactage automatique avec les superviseurs nécessite une mise en cache incrémentielle des métadonnées de segment sur Overlord et une nouvelle table de stockage de métadonnées ; aucune action n'est requise si vous utilisez les paramètres par défaut pour les configurations suivantes :

-druid.manager.segments.useIncrementalCache -druid.metadata.storage.connector.createTables

Si druid.manager.segments.useIncrementalCache est défini sur never, mettez-le à jour vers ifSynced ou always. Pour plus d'informations sur la configuration, consultez [Cache de métadonnées de segment] (https://druid.apache.org/docs/latest/configuration/#segment-metadata-cache-experimental).

Si vous définissez la configuration druid.metadata.storage.connector.createTables sur false, vous devez modifier manuellement la table des segments et créer la table compactionStates. Le DDL Postgres est fourni ci-dessous à titre indicatif :

-- create the indexing states lookup table and associated indices
CREATE TABLE druid_indexingStates (
    created_date VARCHAR(255) NOT NULL,
    datasource VARCHAR(255) NOT NULL,
    fingerprint VARCHAR(255) NOT NULL,
    payload BYTEA NOT NULL,
    used BOOLEAN NOT NULL,
    pending BOOLEAN NOT NULL,
    used_status_last_updated VARCHAR(255) NOT NULL,
    PRIMARY KEY (fingerprint),
  );

  CREATE INDEX idx_druid_compactionStates_used ON druid_compactionStates(used, used_status_last_updated);

-- modify druid_segments table to have a column for storing compaction state fingerprints
ALTER TABLE druid_segments ADD COLUMN indexing_state_fingerprint VARCHAR(255);

Vous devrez peut-être adapter la syntaxe pour l'adapter au préfixe de dénomination de votre table et au backend du magasin de métadonnées.

#18844

Verrouillage des segments

Le verrouillage de segment et NumberedOverwriteShardSpec sont obsolètes et seront supprimés dans une prochaine version. Utilisez plutôt le verrouillage des tranches de temps. Vous pouvez vous assurer que seul le verrouillage des blocs de temps est utilisé en définissant druid.indexer.tasklock.forceTimeChunkLock sur true, qui est la valeur par défaut.

#19050

Modifications incompatibles

Configuration defaultProcessingRate supprimée

Cette configuration a permis de commencer les actions de mise à l'échelle avant que les premières métriques ne soient disponibles.

#19028

Format de codage frontal

Druid utilise désormais par défaut la version 1 du format codé au lieu de la version 0 s'il est activé. La version 1 a été introduite dans Druid 26. La rétrogradation ou la mise à niveau à partir d'une version de Druid antérieure à 26 peut nécessiter une réindexation si le codage frontal est activé avec la version 0.
