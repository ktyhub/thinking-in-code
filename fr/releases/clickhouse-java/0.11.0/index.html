Guide de migration des versions

Modifications cassantes

  • [client-v2, jdbc-v2] Les options de tampon de socket socket_rcvbuf et socket_sndbuf n'a plus de valeur par défaut. Désormais, les options ne sont appliquées que lorsque l'application les définit (Client.Builder#setSocketRcvbuf, Client.Builder#setSocketSndbuf, ou les propriétés du même nom). Ceci est fait pour permettre le réglage automatique de la pile TCP du système d'exploitation valeurs. Ne les réglez pas avant d’en avoir absolument besoin. (https://github.com/ClickHouse/clickhouse-java/issues/3121)

  • [client-v2, jdbc-v2] L'erreur du serveur 159 (TIMEOUT_EXCEEDED) n'est plus réessayée par défaut. Il a le sien cause de nouvelle tentative, ClientFaultCause.ServerTimeoutExceeded, que ServerRetryable n'inclut pas et qui n'est pas dans la liste client_retry_on_failures par défaut. Ajoutez ServerTimeoutExceeded à la liste pour réessayer cette erreur. (https://github.com/ClickHouse/clickhouse-java/issues/3072)

  • [r2dbc] L'artefact pré-1.0.0 n'est plus pris en charge car R2DBC API a atteint la version stable 1.0.0.

  • [jdbc-v2] DatabaseMetaData#getTables renvoie désormais null dans REMARKS (commentaire du tableau) et TYPE_SCHEM par par défaut, car les métadonnées sont lues avec les instructions SHOW (voir l'entrée jdbc_metadata_use_show_statements dans New Caractéristiques). Définissez jdbc_metadata_use_show_statements=false pour obtenir les commentaires du tableau. (https://github.com/ClickHouse/clickhouse-java/issues/2907)

  • [client-v2,jdbc-v2] Ajout de la prise en charge de la compression ZSTD pour le flux de compression Block et utilisé par défaut pour ne pas compresser les requêtes client. Auparavant, seul LZ4 était pris en charge dans ce cas. Remarque : Ajout de la bibliothèque ZSTD et native bibliothèques vers le package JDBC -all car il est désormais requis pour fonctionner avec le serveur. (https://github.com/ClickHouse/clickhouse-java/issues/3105).

  • [client-v2, jdbc-v2] L'en-tête User-Agent utilise désormais le format standard ClickHouse client, <client name> clickhouse-java-v2/<version> (lv:java/<java.version>; os:<os.name>; hc:ahc_<version>) : jvm:<version> est maintenant lv:java/<version>, le système d'exploitation est l'entrée os: et la fin Apache-HttpClient/<version> est remplacé par l'entrée hc:ahc_<version> (la version Apache HttpClient que le client est construit avec). Ajout de Client.Builder#setClientName(String, Map) (propriété client_id_metadata) à ajouter paires clé/valeur au groupe de commentaires. Les paires peuvent définir lv, os et hc pour remplacer les valeurs du client. Les espaces de début et de fin sont supprimés du nom client et d’une valeur User-Agent personnalisée. Une valeur vide défini pour une opération compte comme non défini. Le client enregistre un avertissement si la valeur User-Agent du client la configuration comporte plus de 200 caractères. Les requêtes qui analysent http_user_agent dans system.query_log doivent utiliser le nouveau format. (https://github.com/ClickHouse/clickhouse-java/issues/3202)

Changements importants

  • [client-v2] com.clickhouse.client.api.observability.SpanSupport utilise désormais les opérations QUERY et INSERT constantes (noms de span QUERY <database> et INSERT <database>.<table>). L'attribut db.operation.name est défini sur INSERT pour les opérations d'insertion et laissé non défini pour les requêtes car les instructions SQL ne sont pas analysées sur le client.

  • [client-v2] com.clickhouse.client.api.metrics.OperationMetrics possède désormais un seul constructeur, OperationMetrics(ClientStatisticsHolder, OperationType) ; le constructeur sans type d'opération a été supprimé. Les métriques sont créées par le client, qui connaît toujours le type d'opération qu'il exécute, et le constructeur prend un type interne (com.clickhouse.client.api.internal.ClientStatisticsHolder), donc le code d'application n'est pas attendu pour l'appeler. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

Nouvelles fonctionnalités

Types de données

  • [client-v2, jdbc-v2] Ajout de la prise en charge du type de données géographiques MultiPoint (ClickHouse 26.8+). Auparavant, le type était inconnu du client, donc la lecture ou l'écriture d'une colonne MultiPoint a échoué avec Unknown data type: MultiPoint, et une valeur MultiPoint à l'intérieur d'une colonne Geometry a échoué avec un discriminateur de variante hors plage. MultiPoint est Array(Point) sur le fil, exactement comme Ring et LineString, il est donc lu et écrit comme double[][] via enregistrements génériques, lecteurs binaires, liaison POJO et formatage des paramètres SQL, et est lu à partir des colonnes Dynamic. Dans le pilote JDBC (jdbc-v2) MultiPoint correspond à java.sql.Types.ARRAY et est renvoyé sous la forme double[][] par getObject et comme java.sql.Array de getArray, et est signalé par ResultSetMetaData et DatabaseMetaData. ClickMaison 26.8 ajoute également MultiPoint au Geometry variante ; le serveur l'ajoute après les six variantes existantes au lieu de le trier par nom de type, donc le client maintenant conserve cet ordre et décode un MultiPoint détenu dans une colonne Geometry. Parce que MultiPoint partage son Java représentation (double[][]) avec Ring et LineString, elle n'est pas sélectionnable via le Geometry basé sur la forme chemin d'écriture - une valeur 2D continue de se résoudre en Ring comme avant, et l'écriture de MultiPoint nécessite un MultiPoint concret colonne. (https://github.com/ClickHouse/clickhouse-java/issues/3048)

  • [client-v2, jdbc-v2] Ajout de la prise en charge du type de données BFloat16 (ClickHouse 24.11+). Les colonnes BFloat16 sont lues comme Valeurs Java float (l'élargissement est sans perte) et écrites à partir des valeurs float/Float, y compris via des enregistrements génériques, POJO valeurs de liaison, Nullable(BFloat16) et BFloat16 conservées dans les colonnes Dynamic/Variant. En écriture, le client conserve le 16 bits élevés du float, correspondant à la propre conversion Float32 → BFloat16 du serveur ClickHouse. Dans le pilote JDBC (jdbc-v2) BFloat16 correspond à java.sql.Types.FLOAT / java.lang.Float et est lu et écrit via la norme Accesseurs getFloat/setFloat et getObject, et signalés comme tels par ResultSetMetaData et DatabaseMetaData. La lecture ou l'écriture précédente d'une colonne BFloat16 a échoué avec un erreur de type de données non pris en charge. (https://github.com/ClickHouse/clickhouse-java/issues/2279)

  • [client-v2, jdbc-v2] Ajout de la prise en charge du type de données vectorielles expérimental QBit(element_type, dimension[, stride]) (ClickHouse 25.10+ ; le paramètre du serveur allow_experimental_qbit_type est requis pour créer une colonne). Le nom du type l'analyseur accepte deux ou trois paramètres (le troisième facultatif est la foulée) et reconnaît les types d'éléments documentés Int8, BFloat16, Float32 et Float64 ; un type d'élément en dehors de cet ensemble est analysé avec un avertissement plutôt que rejeté, donc un type d'élément côté serveur plus récent continue à être analysé. Une valeur QBit est transmise sur RowBinary exactement comme Array(element_type), il est donc lu et écrit sous la forme d'un tableau Java du type élément (float[] pour BFloat16/Float32, double[] pour Float64) via des enregistrements génériques, des lecteurs binaires et une liaison POJO, via un Chemin de lecture/sérialisation QBit dédié. Un QBit contenu dans une colonne Dynamic/Variant/JSON est également décodé (son le codage de type binaire est relu au type concret QBit(...)). Dans le Pilote JDBC (jdbc-v2) QBit est mappé à java.sql.Types.ARRAY et est renvoyé en tant que java.sql.Array par getObject/getArray. Auparavant, QBit était une constante de type non implémentée et la lecture ou l'écriture d'une telle colonne échoué. Une colonne QBit simple de niveau supérieur avec un type d'élément Float32, Float64 ou BFloat16 est également lue. le format de sortie Native : là, le serveur le transmet en utilisant son plan de bits interne transposé Disposition Tuple(FixedString(...)), et le client inverse cette transposition pour reconstruire la même Vecteur float[]/double[] comme RowBinary. Un QBit qui est foulé (QBit(element_type, dimension, stride)), enveloppé dans Nullable/LowCardinality, imbriqué dans un autre type (par exemple Array/Tuple/Map(String, QBit(...))), ou transportant tout autre type d'élément n'est pas encore décodé sur Native et échoue rapidement avec une erreur claire vous dirigeant à un format RowBinary tel que RowBinaryWithNamesAndTypes. (https://github.com/ClickHouse/clickhouse-java/issues/2610)

Observabilité

  • [client-v2, jdbc-v2] Ajout d'une implémentation Micrometer des métriques SPI. Client.Builder.setMetricsRecorder(new MicrometerMetricsRecorder(meterRegistry)) rapporte les mesures de chaque client opération à un Micromètre MeterRegistry : un temporisateur db.client.operation.duration par opération terminée, un temporisateur clickhouse.client.operation.serialization.duration lorsque le client mesurait l'étape de sérialisation, un compteur clickhouse.client.operation.count par opération terminée, et un compteur clickhouse.client.operation.retries par nouvelle tentative. Auparavant, le client pouvait lier uniquement ses jauges de pool de connexion au Micrometer, exportant ainsi le les mesures des opérations elles-mêmes étaient laissées à l’application. Les noms des compteurs, les unités, les descriptions et les clés d'étiquette sont les standards du SPI - l'enregistreur les dérive via MetricsSupport, ce sont donc les noms de MetricName et les touches du MetricAttribute ont la même signification que pour tout autre enregistreur. Une opération réussie ne porte aucune balise error.type et une balise échouée en porte, donc les résultats sont des séries chronologiques distinctes du même compteur et un l'échec signalé par le serveur porte également db.response.status_code ; une durée que le client n'a pas mesurée n'est pas enregistrée, aucune opération n'est donc signalée avec une durée inventée. Les secondes du SPI sont transmises au registre comme nanosecondes, car un minuteur micrométrique conserve sa propre unité de temps, donc un backend publie la durée dans l'unité dans laquelle il attend. Le constructeur sans argument rend compte à Metrics.globalRegistry, ce que jdbc-v2 La propriété jdbc_metrics_recorder a besoin, donc une connexion JDBC exporte ses métriques vers Micrometer en nommant la classe - jdbc_metrics_recorder=com.clickhouse.client.api.observability.micrometer.MicrometerMetricsRecorder - sans code d'application. micrometer-core reste une dépendance facultative de client-v2 et n'est pas ombré dans all artefacts, donc un client qui n'utilise pas cet enregistreur n'a pas besoin de micromètre sur le chemin de classe. (https://github.com/ClickHouse/clickhouse-java/issues/2975)

  • [client-v2, jdbc-v2] Ajout d'un SPI de métriques qui permet à une application d'exporter les métriques des opérations client vers n'importe quel back-end de métriques. Client.Builder.setMetricsRecorder(MetricsRecorder) enregistre un enregistreur indépendant du back-end à partir du Package com.clickhouse.client.api.observability et la propriété jdbc-v2 jdbc_metrics_recorder nomme l'enregistreur classe une connexion s'enregistre avec son propre client. Auparavant, le client collectait les métriques de fonctionnement mais ne les renvoyait que à l'appelant, leur exportation était donc laissée à l'application. Chaque opération terminée rapporte exactement un succès ou un événement d'échec, et chaque nouvelle tentative signale un événement de nouvelle tentative, qui donne la durée de l'opération, le la durée de sérialisation, le nombre d'opérations par résultat et le nombre de tentatives. Le SPI suit le modèle de le span SPI : une implémentation étend la classe de base DefaultMetricsRecorder et remplace uniquement ce qui l'intéresse à propos, donc il continue de fonctionner lorsque le client commence à signaler un événement dont il ne connaît pas, et le réutilisable La classe MetricsSupport dérive les valeurs standard des mêmes structures, sa logique est donc facultative et remplaçable. Les noms de métriques, les unités et les clés d'attribut suivent les conventions sémantiques OpenTelemetry pour la base de données clients où un la convention existe et sont placées sous clickhouse. là où elle n'existe pas ; ils sont définis par le MetricName et MetricAttribute énumére, les durées sont signalées en secondes et une durée que le client n'a pas mesurée est signalée comme MetricsSupport.DURATION_UNKNOWN au lieu d'une valeur inventée. Les attributs métriques sont délibérément un ensemble plus petit que les attributs span, car un attribut d'une métrique devient une série temporelle : le texte de l'instruction, l'identifiant de la requête et les paramètres de l'instruction restent sur les étendues. Rien n'est enregistré et aucun travail lié aux métriques n'est effectué lorsqu'aucun enregistreur n'est enregistré. (https://github.com/ClickHouse/clickhouse-java/issues/2975)

  • [client-v2] Ajout d'une implémentation OpenTelemetry du SPI d'observabilité. Client.Builder.setSpanRecorder(new OpenTelemetrySpanRecorder(openTelemetry)) signale chaque opération client et chaque demande de transport comme une travée OpenTelemetry CLIENT : une travée d'opération est démarré en tant qu'enfant du contexte OpenTelemetry actuel, il rejoint donc la propre trace de l'application, et chaque requête span - dont un par nouvelle tentative - est un enfant de son opération span. Les noms de span et les clés d'attribut sont les standards du SPI (l'enregistreur les dérive via SpanSupport), chaque valeur est enregistrée avec l'attribut OpenTelemetry type qui lui correspond, et un échec définit l'état du span sur ERROR et est enregistré comme une exception OpenTelemetry événement à côté des attributs error.type et db.response.status_code. L'enregistreur fait rapport à un instance OpenTelemetry, à un Tracer donné à new OpenTelemetrySpanRecorder(Tracer), ou à GlobalOpenTelemetry - lu lorsqu'un span est démarré - lorsqu'il est construit sans arguments. Auparavant, une application qui voulait des travées OpenTelemetry devait écrire ce mappage lui-même. Le OpenTelemetry API est une dépendance de compilation uniquement de client-v2 : l'enregistreur est utilisé uniquement par une application qui fournit déjà opentelemetry-api au moment de l'exécution, donc rien n'est ajouté au chemin de classe d'un client qui ne l'utilise pas. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

  • [client-v2] Ajout d'un SPI d'observabilité qui permet à une application d'observer les opérations client sous forme d'étendues. Client.Builder.setSpanRecorder(SpanRecorder) enregistre un enregistreur indépendant du backend du nouveau Package com.clickhouse.client.api.observability : chaque opération (une requête, une commande ou une insertion - incluant le Les appels ping et getTableSchema, qui exécutent une requête) démarrent une période d'opération et chaque demande de transport effectuée pour il - y compris chaque nouvelle tentative - démarre une période de requête enfant. SpanRecorder et Span sont des interfaces simples ; un la mise en œuvre étend la DefaultSpanRecorder et remplace uniquement ce qui l'intéresse, de sorte qu'il continue de fonctionner lorsque le client démarre un une sorte de durée dont il ne connaît pas l'existence. L'enregistreur enregistré est appelé en premier et reçoit tout ce que le client sait sur l'opération (son QuerySettings/InsertSettings, l'instruction, la table cible, la taille du lot, le point final, les mesures de l'opération terminée et de l'échec), il est donc libre d'enregistrer tout ce dont il a besoin et dans quelle que soit sa forme ; la classe réutilisable SpanSupport dérive les noms de travée standard et les valeurs d'attribut de ces mêmes structures et est appelé par une implémentation d'enregistreur qui les souhaite, sa logique est donc facultative et remplaçable. Portée les noms et les clés d'attribut suivent les conventions sémantiques OpenTelemetry pour les étendues de base de données et HTTP client ; les clés sont définis par l'énumération SpanAttribute et les valeurs sont dérivées de SpanSupport, donc tous les enregistreurs qui l'utilisent rapportent les mêmes informations (texte de la déclaration, base de données et table cible, ID de requête, paramètres d'instruction, taille du lot, premier point de terminaison configuré sur la durée de l'opération et par tentative adresse du serveur et port sur les étendues de requêtes, statut HTTP, lignes renvoyées, type d'erreur et code d'erreur ClickHouse en cas d'échec). Le résultat d'une opération terminée est rapporté par type d'opération - recordQuerySuccess pour une lecture et recordInsertSuccess pour une insertion - car les métriques qui décrivent une lecture ne sont pas celles qui décrire une écriture : une requête rapporte db.response.returned_rows, clickhouse.response.read_rows et clickhouse.response.read_bytes, un encart rapporte clickhouse.response.written_rows et clickhouse.response.written_bytes. La même distinction est disponible sur les métriques elles-mêmes grâce au nouveau OperationMetrics#getOperationType(), qui renvoie le nouveau com.clickhouse.client.api.metrics.OperationType - le type d'appel effectué par l'application, donc une commande qui écrit est signalée comme une requête. Une période d'opération est démarrée sur le thread appelant, il rejoint donc la trace ambiante de l'appelant même lorsque l'opération s'exécute sur l'exécuteur du client, et il se termine exactement une fois pour chaque opération qui commence. Auparavant, le client n'exposait aucun crochet pour le traçage, donc un L'application n'a pas pu attribuer une requête ou une nouvelle tentative à sa propre trace. Lorsqu'aucun enregistreur n'est enregistré, rien est enregistré et aucun travail lié à l'étendue n'est effectué, le chemin par défaut reste donc inchangé. Une implémentation OpenTelemetry du SPI est disponible sous le nom de OpenTelemetrySpanRecorder. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

Dans jdbc-v2, une colonne Nested(...) non aplatie est exposée en tant que JDBC ARRAY dont le type d'élément est Tuple(f1 T1, ..., fN TN) : il peut être inséré via Connection#createArrayOf/setArray ou setObject et relisez getArray/getObject, et java.sql.Array#getResultSet() itère les lignes imbriquées comme (INDEX, VALUE) paires où chaque VALUE est le tuple. (https://github.com/ClickHouse/clickhouse-java/issues/2477)

  • [client-v2, jdbc-v2] Ajout de la journalisation sur les chemins d'erreur et de diagnostic précédemment silencieux (aucun fonctionnel ou public-API changement). (https://github.com/ClickHouse/clickhouse-java/issues/2969)

  • [jdbc-v2] DatabaseMetaData#getSchemas, #getTables et #getColumns lisent désormais les métadonnées avec SHOW DATABASES, SHOW TABLES et DESCRIBE TABLE au lieu des tables system.databases, system.tables et system.columns. Le le serveur n'affiche pas certaines tables dans les tables système par défaut (par exemple, les tables de DataLakeCatalog bases de données), donc les outils qui utilisent DatabaseMetaData ne les ont pas trouvés. La nouvelle propriété du pilote jdbc_metadata_use_show_statements (true par défaut) sélectionne l'implémentation ; réglez-le sur false pour utiliser le système tableaux. Avec les instructions SHOW, getTables() renvoie null dans REMARKS (commentaire de table) et TYPE_SCHEM ; getColumns() envoie une requête DESCRIBE TABLE pour chaque table qui correspond et ignore une table qui a été supprimée en attendant, que l'utilisateur ne peut pas décrire, ou dont les métadonnées du lac de données ne peuvent pas être lues. Toutes les autres colonnes et valeurs sont le même. (https://github.com/ClickHouse/clickhouse-java/issues/2907)

Corrections de bugs

  • [jdbc-v2] Correction d'une instruction INSERT ... VALUES dont la liste de valeurs contient un littéral, une expression (par exemple ? + 1) ou, avec l'analyseur JAVACC, une séquence d'échappement JDBC ou un paramètre de requête, écrit avec le rédacteur RowBinary lorsque beta.row_binary_for_simple_insert est activé. Le rédacteur prend une valeur liée par colonne, donc les valeurs liées ont été déplacés vers d'autres colonnes : l'instruction a échoué avec une erreur trompeuse ou a stocké des données erronées sans erreur. Le Les analyseurs n'ont pas signalé de telles valeurs : l'analyseur JAVACC a rejeté le résultat de sa vérification de la liste de valeurs et le Les analyseurs ANTLR4 ont signalé uniquement les appels de fonction. Désormais, l'écrivain est utilisé uniquement pour une liste de valeurs d'espaces réservés ?, et d'autres instructions utilisent le chemin standard PreparedStatement. (https://github.com/ClickHouse/clickhouse-java/issues/3083)

  • [client-v2,jdbc-v2] - Remplacement de la compression HTTP LZ4 lente par la compression du flux de Bibliothèque lz4-java. Client utilise Apache Compress pour gérer la compression HTTP (car il dispose d'une usine pratique pour de nombreux méthodes de compression. Cependant, Apache Compress utilise une implémentation lente de LZ4, ce qui entraîne des insertions très lentes. Maintenant lz4-java utilisé pour l'insertion. La requête est toujours lente mais sera corrigée dans les prochaines versions (nécessite une refactorisation et une personnalisation mise en œuvre pour le résoudre). L'utilisation de ZSTD pour les requêtes devrait résoudre le problème. (https://github.com/ClickHouse/clickhouse-java/issues/2273).

  • [client-v2] Correction de l'écriture d'une valeur String dans une colonne UUID (également en tant qu'élément Array/Tuple ou Map clé) en échec avec ClassCastException. La chaîne est maintenant analysée avec UUID.fromString ; une chaîne qu'il ne peut pas analyser est rejeté sur le client avec un IllegalArgumentException. (https://github.com/ClickHouse/clickhouse-java/issues/3132)

  • [client-v2] Correction de l'échec de la lecture d'une colonne Nullable au format Native avec Échec de lecture du bloc... Fin du flux atteinte avant la lecture de toutes les données, ou renvoi des valeurs des mauvaises lignes. Le lecteur a consommé un nul marqueur avant chaque valeur, qui est la disposition RowBinary. Native` est en colonnes : il stocke une carte nulle d'un octet par ligne avant les valeurs de la colonne entière, et une ligne nulle a toujours une valeur d'espace réservé. Les marqueurs étaient donc extrait des octets de valeur et la colonne a été lue hors alignement. La carte nulle est désormais lue comme un bloc. (https://github.com/ClickHouse/clickhouse-java/issues/3137)

  • [client-v2] Colonnes géographiques fixes (Point, Ring, LineString, MultiPoint, Polygon, MultiLineString, MultiPolygon) mal lu à partir du format Native. Le lecteur a décodé une colonne géographique ligne par ligne avec le RowBinary décodeurs, tandis que Native l'écrit en colonne majeure : un bloc Point est revenu avec ses coordonnées brouillées sur les lignes et aucune erreur, et tous les autres types géographiques ont désynchronisé le bloc et ont échoué avec Non-empty typeName is required. Une colonne géo est désormais décodée de la mise en page Native - les deux Float64 les sous-colonnes d'un point et les décalages cumulés ainsi que les éléments aplatis pour les niveaux du tableau - et renvoie la même chose valeurs comme RowBinaryWithNamesAndTypes, qui restent inchangées. (https://github.com/ClickHouse/clickhouse-java/issues/3088)

  • [client-v2, jdbc-v2] Correction d'un type de colonne avec un élément JSON suivi d'un type paramétré, par exemple exemple Tuple(JSON, FixedString(3)), mal analysé. JSON est valide avec et sans liste de paramètres, et l'analyseur a recherché le crochet ouvrant de cette liste n'importe où après le mot-clé, il a donc pris les crochets du suivant élément pour les paramètres de l'élément JSON. Deux fils pourraient tous les deux vider et muter le même tampon en attente avant que le lecteur ne le consomme, en remplaçant silencieusement la charge utile par un vide tampon et en exécutant l'action post-fermeture deux fois. Exactement un appelant vide désormais les données en attente, met le marqueur de fin de flux et exécute l'action post-fermeture ; Les appels close() simultanés ou répétés reviennent immédiatement. (https://github.com/ClickHouse/clickhouse-java/issues/3057)

  • [jdbc-v2] Correction du traitement d'échappement JDBC réécrivant le texte à l'intérieur des littéraux de chaîne et des identifiants entre guillemets. Parce que PreparedStatement intègre les paramètres liés dans le texte de l'instruction, une valeur liée contenant {fn (ou {d '...'} / {ts '...'}) a été relu selon la syntaxe SQL : le {fn a été supprimé avec le prochain } trouvé n'importe où dans le instruction - généralement l'accolade fermante d'un littéral Map/Tuple sans rapport dans une autre valeur ou ligne - corrompant l'instruction données insérées ou échec avec un SYNTAX_ERROR côté serveur. Les séquences d'échappement ne sont désormais reconnues qu'en dehors des guillemets texte, et un échappement {fn ...} est déroulé au niveau de son accolade fermante correspondante, donc des accolades imbriquées (par exemple une requête {name:Type} paramètre ou un échappement imbriqué) restent équilibrés. (https://github.com/ClickHouse/clickhouse-java/issues/2995)

  • [jdbc-v2] Correction des instructions préparées perdant les marqueurs de paramètres après une ligne de commentaire -- vide ou après SELECT * EXCEPT (...), qui a provoqué l'échec de la liaison des paramètres avec ArrayIndexOutOfBoundsException pour le Backends de l'analyseur SQL. (https://github.com/ClickHouse/clickhouse-java/issues/3052)

  • [client-v2] Correction des flux d'entrée LZ4 ne fermant pas leur flux de réponse HTTP sous-jacent. Fermeture d'un flux LZ4 renvoyé par QueryResponse.getInputStream() libère désormais le flux de transport encapsulé, y compris après une lire. (https://github.com/ClickHouse/clickhouse-java/issues/2985)

  • [jdbc-v2] Correction de l'abandon de l'analyseur SQL JavaCC par défaut sur une chaîne héréditaire ($$body$$, $tag$body$tag$) dont le corps contient un caractère qui n'est pas un jeton SQL valide en soi, tel que !, &, | ou ~. Le lexer avait aucun jeton héréditaire, donc un tel organisme a généré une erreur lexer qui a laissé la déclaration classée comme UNKNOWN — un INSERT a été signalé comme une instruction portant un ensemble de résultats sans nom de table ni position dans la liste de valeurs, ce qui désactive le modèle de valeurs de lot et les chemins basés sur le nom de la table. Un hérdoc est maintenant lexé comme une seule chaîne littéral. (https://github.com/ClickHouse/clickhouse-java/issues/3029)

  • [client-v2, jdbc-v2] Réduction du bruit et de la journalisation potentiellement sensible ; Le SQL qui ne parvient pas à analyser n'est plus enregistré sur WARN (il pourrait contenir des informations d'identification/PII). (https://github.com/ClickHouse/clickhouse-java/issues/2970)

  • [client-v2] Correction des valeurs BigDecimal écrites dans une colonne Dynamic étant tronquées silencieusement lorsque la valeur est l'échelle dépassait l'échelle maximale de la largeur déduite et générait une erreur de débordement lorsque la valeur portait un entier pièce (par exemple 19.99). L'inférence de type Dynamic dimensionne désormais la largeur Decimal pour contenir à la fois les chiffres entiers et l'échelle de la valeur, maintient l'échelle aussi large que la largeur le permet sans voler de place à la partie entière et écrit l'échelle de colonne réelle dans la balise de type Dynamic. Les valeurs qui ont déjà fait un aller-retour sans perte restent inchangées. (https://github.com/ClickHouse/clickhouse-java/issues/2966)

  • [client-v2] Correction du lancement du graveur RowBinary UnsupportedOperationException: Unsupported data type: SimpleAggregateFunction lors de l'insertion dans un Colonne SimpleAggregateFunction(func, T) (le lecteur supportait déjà ces colonnes). La valeur est maintenant sérialisée de manière identique à son type sous-jacent T, en écrivant l'octet de marqueur nul Nullable lorsque le type sous-jacent est nullable (par exemple SimpleAggregateFunction(anyLast, Nullable(String))), reflétant le chemin de lecture. (https://github.com/ClickHouse/clickhouse-java/issues/2477)

  • [client-v2] Correction de la balise de type Dynamic pour un type SimpleAggregateFunction écrit sous forme nue Octet 0x2E. Le codage de type binaire porte également le nom de la fonction, ses paramètres et ses types d'arguments, donc le le serveur a lu le nom de la fonction à partir des octets de valeur qui ont suivi et a échoué avec ATTEMPT_TO_READ_AFTER_EOF. Puisque le client ne déduit jamais un SimpleAggregateFunction à partir d'une valeur Java et que le Le lecteur ne peut pas relire une colonne Dynamic, cela échoue maintenant rapidement avec un message clair ClientException au lieu de produire un flux RowBinary corrompu (le même traitement que QBit reçoit déjà). (https://github.com/ClickHouse/clickhouse-java/issues/3007)

  • [client-v2, jdbc-v2] Correction de plusieurs défauts de la couche de journalisation. Dans client-v2, HttpAPIClientHelper.shouldRetry a lancé un ClassCastException lorsqu'un ServerException réessayable a été enveloppé comme cause d'une autre exception (le branche correspondant à la cause mais le casting a utilisé l'exception externe) ; la décision de réessayer est désormais prise, quel que soit le l'exception est le ServerException. Également dans client-v2, un échec de création de la chaîne de version HTTP client est désormais présent. connecté à WARN avec le jetable attaché au lieu d'un simple message INFO qui écartait la cause. Dans jdbc-v2, un échec de fermeture de la réponse après une erreur de requête enregistre désormais l'échec de fermeture lui-même au lieu du exception externe déjà propagée. (https://github.com/ClickHouse/clickhouse-java/issues/2968)

  • [client-v2] Correction des paramètres de requête scalaire String contenant une tabulation (0x09), une nouvelle ligne (0x0a) ou une barre oblique inverse étant mal géré via l'interface param_<name> du serveur. Un {name:String} la valeur du paramètre est analysée par le serveur avec deserializeTextEscaped, qui a traité un onglet brut ou une nouvelle ligne comme un champ délimiteur (en cas d'échec de la requête avec BAD_QUERY_PARAMETER: ... isn't parsed completely) et une barre oblique inverse brute comme début d'une séquence d'échappement (corrompant silencieusement la valeur, par exemple C:\temp est devenu C:<tab>emp). Client.query(sql, params, ...) échappe désormais à la barre oblique inverse, à la tabulation et à la nouvelle ligne dans un String scalaire paramètre donc toute valeur aller-retour ; tous les autres caractères que le serveur lit textuellement, y compris les guillemets simples et retour chariot — reste inchangé, donc les valeurs Identifier et les littéraux Array/Map préformatés sont transmis en tant que String toujours aller-retour. Le pilote JDBC (jdbc-v2), qui intègre les paramètres sous forme de littéraux SQL et déjà échappés la barre oblique inverse et le guillemet simple, sont inchangés et couverts par un nouveau test de régression. (https://github.com/ClickHouse/clickhouse-java/issues/2781)

  • [client-v2] Correction d'une valeur de paramètre de requête null envoyée sous forme de chaîne littérale "null", donc Client.query(sql, params, ...) liant un Java null à un espace réservé scalaire tel que {x:Nullable(Decimal128(8))} a été rejeté par le serveur avec BAD_QUERY_PARAMETER (Value null cannot be parsed as Nullable(...)). Un scalaire de haut niveau null est désormais envoyé sous le nom de ClickHouse \N Sentinelle NULL donc elle lie SQL NULL ; un null imbriqué dans une valeur de paramètre Array/Map continue d'être rendu comme mot clé SQL NULL. (https://github.com/ClickHouse/clickhouse-java/issues/2977)

  • [client-v2] Correction du décodage de tableau binaire pour les types d'éléments nullables donc Array(Nullable(Float64)) et similaires les colonnes renvoient désormais des tableaux encadrés tels que Double[] au lieu de Object[]. Cela maintient les tableaux prenant en charge les valeurs nulles alignés avec leur type d'élément tout en préservant la solution de repli Object[] existante pour les tableaux Variant/Dynamique/Géométrie. (https://github.com/ClickHouse/clickhouse-java/issues/2846)

  • [client-v2] Correction des colonnes Float32/Float64 lançant ClassCastException lorsqu'une valeur d'une boîte ne correspondant pas le type numérique a été fourni via la surface d'insertion typée Object - par exemple un Double (le type naturel de littéral Java comme 1.5) pour une colonne Float32, ou un Float pour un Colonne Float64. Le sérialiseur RowBinary réduit désormais tous les Number (et, comme les colonnes Int*, un String/ Boolean) à Number#floatValue()/Number#doubleValue(), de sorte que les colonnes float acceptent les mêmes types de valeurs que celles les colonnes entières l'ont déjà fait. (https://github.com/ClickHouse/clickhouse-java/issues/2930)

  • [client-v2] Correction d'un NullPointerException lors de la sérialisation d'une valeur null dans une valeur non nullable Colonne Enum8/Enum16. SerializerUtils.serializeEnumData n'avait pas de garde null, donc un null dans une énumération non nullable La colonne a atteint value.getClass() et a échoué le chemin d'insertion RowBinary avec un NPE déroutant au lieu d'une erreur claire. Il lance désormais IllegalArgumentException en nommant la colonne, conformément au IllegalArgumentException existant. pour d'autres valeurs d'énumération non prises en charge. Les colonnes d'énumération nullables ne sont pas affectées. (https://github.com/ClickHouse/clickhouse-java/issues/2931)

  • [client-v2] Correction de la corruption silencieuse des données lors de la sérialisation d'un Java null dans un fichier non nullable Colonne Array(...) via RowBinaryFormatWriter. RowBinaryFormatSerializer.writeValuePreamble Array à boîtier spécial, émettant un octet marqueur parasite au-dessus de la longueur du tableau ; le serveur lit l'octet supplémentaire comme un ligne supplémentaire fantôme (insertions d'une seule colonne) ou comme décalage de colonne qui a échoué à l'insertion avec CANNOT_READ_ALL_DATA (inserts multi-colonnes). Un Array non nullable ne peut pas représenter un null, il lance donc désormais IllegalArgumentException nommer la colonne - conformément à tous les autres types non nullables - dans le RowBinary et Chemins RowBinaryWithDefaults. Les tableaux vides ([]) sont toujours sérialisés correctement et les colonnes Dynamic, qui peuvent contenir un null, tout comme le type implicite Nothing, ne sont pas affectés. (https://github.com/ClickHouse/clickhouse-java/issues/2938)

  • [client-v2] Correction de la classification des erreurs d'insertion POJO afin que les échecs d'écriture du transport tels que java.net.SocketException : Les tuyaux cassés (échec d'écriture) sont désormais signalés comme des erreurs de transfert/réseau au lieu d'être encapsulés comme des erreurs de transfert/réseau. DataSerializationException. Cela modifie uniquement le type d'exception signalé pour les échecs de transport du corps de la requête pendant Les échecs réels de réflexion/sérialisation POJO de Client.insert (...); sont toujours signalés sous le nom DataSerializationException. (https://github.com/ClickHouse/clickhouse-java/issues/2729)

  • [client-v2] Correction du décodage de variantes binaires pour les champs de longueur et de nombre afin que les valeurs débordantes ou trop longues échouent avec un IOException au lieu d'être décodé en valeurs int corrompues ou négatives. (https://github.com/ClickHouse/clickhouse-java/issues/2902)

  • [client-v2] Correction des paramètres de requête de conteneur envoyés sans guillemets, donc liaison Client.query(sql, params, settings) un List<LocalDate> (ou un tableau/Map) vers un espace réservé comme {ids:Array(Date)} a été rejeté par le serveur avec CANNOT_PARSE_INPUT_ASSERTION_FAILED. Les valeurs des paramètres sont désormais formatées par DataTypeConverter#convertParameterToString(Object) avant d'être envoyé : transmettre la valeur brute Java et le rendu client dans le texte attendu par l'interface param_<name> du serveur : un Collection, un tableau (objet ou primitif) ou Map devient ClickHouse Array (['2026-05-13']) / Map ({'k':'v'}) texte avec String/feuilles temporelles entre guillemets simples et les feuilles numériques/booléennes sont laissées sans guillemets, tandis qu'un scalaire est passé sans guillemets comme auparavant. Pas de manuel un préformatage des paramètres du conteneur est nécessaire. (https://github.com/ClickHouse/clickhouse-java/issues/2897)

  • [client-v2] Correction des colonnes DateTime/DateTime64 déclarées avec un nom de fuseau horaire synthétique à décalage fixe (Fixed/UTC±HH:MM:SS, par exemple Fixed/UTC+05:30:00) étant lu silencieusement en UTC au lieu du décalage déclaré. Le Le lecteur RowBinary récupère désormais le décalage du type déclaré de la colonne. (https://github.com/ClickHouse/clickhouse-java/issues/2876)

  • [jdbc-v2] Correction des backends de l'analyseur SQL ANTLR4 (jdbc_sql_parser=ANTLR4 et ANTLR4_PARAMS_PARSER) lexant le corps d'une chaîne héréditaire ($$body$$, $tag$body$tag$) en SQL ordinaire. Le lexer n'avait pas de jeton héréditaire, donc chaque $ a été supprimé en tant que caractère non reconnu et le corps a été analysé en tant qu'identifiants, opérateurs et séparateurs d'instructions : a le corps qui ressemblait toujours à du SQL valide a été mal analysé en silence (nom de table et positions dans la liste VALUES incorrects), et un corps contenant ; — ainsi que l'hérdoc vide $$$$ — a été signalé comme une erreur d'analyse, qui classe un INSERT comme un instruction portant un ensemble de résultats sans position dans la liste de valeurs. Un hérdoc est maintenant lexé comme une chaîne littérale unique et accepté comme valeur littérale (listes INSERT ... VALUES, expressions de colonnes, paramètres), et un $ à l'intérieur d'un identifiant (a$b, ou une balise non terminée telle que $foo$bar) fait partie de l'identifiant, tel que le lit le serveur. (https://github.com/ClickHouse/clickhouse-java/issues/3031)

  • [jdbc-v2] Correction du lancement de la version bêta de l'écrivain RowBinary (DriverProperties.BETA_ROW_BINARY_WRITER) NoSuchColumnException pour les instructions INSERT dont les noms de colonnes sont entre guillemets, en particulier les instructions canoniques Forme de fil de sous-colonne Nested `directory`.`id`. The SQL parser now unescapes each backtick-quoted INSERT composant de nom de colonne avant la recherche par nom du schéma de serveur, correspondant à la façon dont les identifiants de table et de base de données sont déjà traité. (https://github.com/ClickHouse/clickhouse-java/issues/2896)

  • [client-v2, jdbc-v2] Correction de ResultSet#close(), QueryResponse#close(), et fermeture d'un lecteur ou de la réponse stream lorsque le résultat n'a pas été lu jusqu'à la fin, ce qui pourrait échouer avec Fin prématurée du corps du message codé en bloc : morceau de fermeture attendu. Pour fermer une réponse partiellement lue, le HTTP client lit et supprime le reste du corps. Lorsqu'une requête échoue après le début de la réponse, le serveur termine le corps plus tôt et cette lecture échoue. Quand le résultat Le flux a été ouvert, cet échec à la fermeture est désormais enregistré sur DEBUG et n'est pas renvoyé. Erreurs lors de la lecture de la réponse ne sont pas modifiés, et une commande ou mise à jour qui ne lit pas le résultat (Client#execute, Statement#executeUpdate`) signale toujours l'échec. (https://github.com/ClickHouse/clickhouse-java/issues/3203)
