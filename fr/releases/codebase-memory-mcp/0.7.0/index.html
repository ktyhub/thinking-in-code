v0.7.0 — LSP hybride dans six langues, contributions de la communauté, validation complète de la plateforme

🧠 Le titre : LSP hybride

Cette version est celle où le graphique d'appel cesse d'être une supposition.

Pour chaque langage pris en charge, nous proposons désormais un LSP hybride Light-Semantic-Pass — un résolveur par fichier et sensible au type qui exécute l'extraction à l'intérieur. Il suit les portées, déduit les types d'expression, suit les importations, parcourt l'héritage et réécrit l'appelé résolu sur chaque bord CALLS. Le passe simple Tree-Sitter vous donne le graphique structurel ; le pass LSP vous donne le bon appelé. Six langues en bénéficient désormais : quatre d'entre elles ont obtenu le LSP pour la première fois dans cette version.

L'architecture Tier 1/2/3 (c'est la partie qui la rend traitable)

Le travail LSP est vraiment coûteux : naïvement, chaque travailleur de résolution reconstruirait un contexte de saisie par fichier. Au lieu de cela, il fonctionne sur trois niveaux :

  • Niveau 1 — LSP par fichier dans cbm_extract_file : étendues, typage d'expression, résolution locale.
  • Niveau 2 — registre LSP multilingue pré-construit : une base partagée en lecture seule construite une fois à partir de chaque définition de projet, puis chaînée à partir de superpositions par fichier via un pointeur de secours. Résolvez que les travailleurs le partagent ; pas de réexamen par fichier de l'ensemble du registre. (Maintenant câblé pour les six langues.)
  • Niveau 3 — cross-LSP basé sur les métadonnées (Go) : consomme les métadonnées lsp_unresolved émises par le passage par fichier et ignore entièrement le re-parcours AST inter-fichiers.

Fabriqué en O(n) sur des fichiers larges

Chaque marcheur LSP par fichier – process_node, ast_sweep_shapes, apply_jsdoc_signatures, infer_implicit_returns, *_resolve_calls_in_node, ainsi que les sept marcheurs DFS côté extrait – utilisaient l'idiome for (i=0; i<count; i++) ts_node_child(node, i). C'est O(i) par appel dans tree-sitter, donc O(n²) sur une racine large. Des luminaires comme reallyLargeFile.ts de TypeScript (583 000 lignes, presque tous les commentaires) ont rendu cela catastrophique. Un nouvel assistant de curseur cbm_lsp_collect_children O(n) + un ts_nstack_push_children partagé pour le DFS d'extrait s'appliquent désormais aux six LSP et aux extracteurs. Chiffres issus de la validation à sec :

lsp_overrides correspond aux "appels dont l'appelé a été réattribué par le LSP à une cible plus précise que celle déduite par le résolveur textuel". Pour les langages richement typés (C#, Go, TS, PHP), cela représente des dizaines de milliers de corrections.

Deux vrais bugs corrigés en cours de route

  • process_node a indexé le param_types[] terminé par NULL par le nombre d'arguments de l'appel ; un appel avec plus d'arguments que la fonction déclare les paramètres lus après le terminateur → deref d'une poubelle CBMType* → crash. Maintenant délimité par un scan param_count.
  • return_type_of a construit des types de retour de tuple via cbm_type_tuple(NULL, …). Les signatures à retours multiples enchaînent désormais ctx->arena.

Toujours activé

CBM_MODE_ADVANCED est supprimé. La résolution LSP s'exécute dans tous les modes d'index (full, moderate, fast) — à ce stade, les marcheurs sont O(n), la qualité (~ 4 % des appels réattribués sur TS, ~ 14 % en Go) vaut la latence dans chaque mode. Les requêtes "mode":"advanced" reviennent à full (comportement identique à l'ancien mode avancé, donc pas de changement avec rupture). Autre avantage secondaire, les 104 échecs du test_incremental.c provoqués silencieusement par une exécution incrémentielle avec LSP gated off ont désormais disparu.

⚡ Performances (au-delà du LSP)

  • Cache regex search_graph + pré-filtre LIKE + nombre bon marché et une sous-requête FTS5 en deux étapes pour tuer la latence de plusieurs minutes de search_graph query=, par Austen Constable (@awconstable) (#300 et suivis).
  • Table de hachage polyvalente v2.2.1 (par Jackson Allan) vendue comme nouveau moteur CBMHashTable — accélération de la résolution du hot-path ; 14 appelants de production (graph_buffer, registre, pipeline passes, watcher, semantic, …) obtiennent le nouvel impl de manière transparente.
  • Extraire O(n²) éliminé sur sept marcheurs DFS d'arbre entier (appels, canaux, accès env, importations, attributions de type, variables) — le même idiome ts_node_child(node, i) qui a mordu le LSP. microsoft/TypeScript mode complet : 5 097 s → 50 s (102×).
  • Remplissage du tampon source Tree-sitter à chaque passe d'analyse — élimine une sur-lecture latente bénigne aux limites de l'analyse.

🔍 Divulgations (transparence sur la préparation à la publication)

Certains changements apportés au programme d’écologisation de l’IC étaient des décisions de jugement et non de simples solutions. Les signaler afin que les évaluateurs puissent deviner :

  1. Repères LSP (pylsp_bench_resolution_ratio, cslsp_bench_resolution_ratio) — placés derrière CBM_SKIP_PERF pour l'essai à sec ; dans la version CI (skip_perf=false), ils fonctionnent avec des budgets de temps compatibles ASan (×10 sous les désinfectants) et libèrent le résultat avant de s'affirmer afin que tout manquement de budget futur ne fuit pas. La qualité du rapport résolution-appel est également affirmée par les suites non-bench test_py_lsp et test_cs_lsp qui fonctionnent toujours en CI.
  2. Extensions de la liste autorisée pour les audits de sécurité (chacune examinée ; documentée en ligne) :
    • Liste autorisée d'URL : https://www.sqlite.org/c3ref/c_checkpoint_full.html — une référence de document dans un commentaire store.c, pas un appel réseau.
    • Seuil de lecture de fichier mcp.c augmenté 12 → 13. La 13ème lecture est la réponse HTTP de vérification de mise à jour + le corps de la requête HTTP – tous deux délimités ; préexistant à partir des commits de recherche/ADR/support Windows.
    • Liste verte fopen("w") étendue pour inclure src/foundation/diagnostics.c (.tmp atomique + vidage des métriques de renommage).
  3. CBM_MODE_ADVANCED supprimé. Les requêtes "mode":"advanced" reviennent désormais à full (qui exécute toujours LSP) — comportement identique, donc les appelants existants ne sont pas affectés.

⬆️ Mise à niveau

Les appelants existants passant par "mode":"advanced" continuent de travailler (repli silencieux vers full). Après avoir mis à niveau le binaire dans ~/.local/bin/codebase-memory-mcp, redémarrez Claude Code pour que le serveur MCP récupère le nouveau binaire.
