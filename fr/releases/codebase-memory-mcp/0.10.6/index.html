codebase-memory-mcp v0.10.6

codebase-memory-mcp v0.10.6

Deux histoires dans une seule version : le ralentissement de l'indexation du 0.10.x a disparu et l'installation les échecs qui ont survécu à v0.10.5 sont corrigés - y compris chaque construction des configurations que vous avez nous a envoyé. Si cbm est devenu plus lent pour vous depuis 0.9.0, ou si install a toujours refusé votre Hermès, configuration goose, OpenCode ou Codex, c'est la version à prendre.

Le programme de régression d'indexation (#1669)

Depuis 0.10.0, l'indexation des dépôts volumineux était passée de plus lente à inutilisable - Java 6 × pire, C# 2.6×, TypeScript 2×. La cause n'était pas un bug mais une famille : un travail par fichier évolutif avec tout le corpus. Tout cela est fixe, mesuré sur le même hôte par rapport au même corpus comme les rapports :

  • Java 477 s → 86 s (elasticsearch) : résolution multi-fichiers reconstruit un registre de chaque définition dans le corpus par fichier. Il est désormais construit une seule fois et partagé, avec un fichier par fichier superposition pour les symboles locaux.
  • C# 1211 s → 450 s (dotnet/runtime), désormais avec 48 % d'arêtes en plus que 0.9.0 : trois les analyses proportionnelles au corpus ont été éliminées, plus un bug de contexte d'importation qui avait été silencieusement suppression des limites d'utilisation de C# - un fichier généré de 147 Ko est passé de 490 s à 6.8 s.
  • TypeScript 37 s → ~24 s (microsoft/TypeScript) : l'évaluateur de type expression sous-expressions partagées réévaluées une fois par alternative englobante - 2 ^ n sur tsc-compilé chaînes de propagation. Un mémo par nœud en fait une évaluation par nœud ; le dossier pathologique de la suite de conformité TS est passé de 20 s à effectivement zéro.
  • Explosion de mémoire Linux corrigée (#1654) : v0.10.4 pourrait MOO sur une machine de 36 Go indexant une arborescence v0.9.0 traité en 13 minutes. La valeur par défaut du commit d'arène Linux de mimalloc est restaurée.
  • Cela reste fixe : une nouvelle suite de protection contre la complexité s'exécute en CI sur chaque plateforme et voyage sur les ratios du compteur (jamais de temps de mur) si un passage de pipeline redevient superlinéaire, et CBM_PROFILE=1 imprime désormais les timings par passe à partir de n'importe quel binaire de production.

Install : les constructions de vos vraies configurations

Hermes (#1631, rapporté par @iandol et Galaxy-VN, causé par une reproduction isolée par @rg6304) : quatre morceaux de YAML ordinaire ont fait échouer le install de façon permanente - flux vide collections (plugins: [], tool_choice: {}), séquences de blocs à la colonne 0, entre guillemets les chaînes se poursuivaient avec un \ final et des apostrophes au milieu du mot (LET'S GO dans un personnage chaîne a ouvert une "quote" qui ne s'est jamais fermée). Tous les quatre sont acceptés maintenant ; des citations et les ancres ne sont des indicateurs que là où commence une valeur, la même règle que le correctif * utilisée dans v0.10.4. Les configurations complètes des deux journalistes (15 Ko chacune) s'installent de bout en bout avec chaque octet d'origine conservé.

Les entrées que nous avons écrites nous-mêmes sont à nouveau reconnues. Les anciennes versions de CBM écrivaient command: non cité; le bloc d'oie a gagné un champ requis ; votre entrée a alors été déclarée "étrangère" pour toujours. Une entrée sous notre clé qui correspond à une forme écrite par une version précédente - ou dont la commande est notre binaire sur un chemin déplacé — est réparé sur place. Des entrées véritablement étrangères sont toujours refusés sans modification des octets.

goose (#1673 + #1675) : le bloc d'extension porte désormais l'analyseur de l'oie des champs name nécessite - avant cela, Goose a silencieusement supprimé l'entrée et l'installation "réussie" a été invisible. envs: {} dans un frère n'interrompt plus l'écriture (correctif communautaire par @pcristin — une contribution modèle, fusionnée telle quelle). Réparation des anciens blocs lors de la mise à niveau. OpenCode / Entrées MCP annotées (#1630, #1582) : lorsqu'un client ajoute des clés à notre entrée ("enabled": true et amis), les réparations remplacent désormais uniquement la valeur de la commande — commentaires et Les clés client survivent textuellement. Et la comparaison de propriété est insensible au séparateur : une entrée le stockage de C:\...\codebase-memory-mcp.exe est le même binaire que celui de l'installateur C:/.../codebase-memory-mcp.exe. La configuration publiée par @gotspatel était le fichier qui s'est craqué celui-ci après persistance sur quatre versions.

Configurations créées par Windows avec une nomenclature UTF-8 (#1656) : le Set-Content de PowerShell écrit un marque d'ordre des octets, et chaque modification YAML a échoué sur ces fichiers, quel que soit leur contenu - le Le journaliste a prouvé son indépendance du contenu avec un fichier de 26 octets, et ces 26 octets étaient leur Contrôle de 23 octets plus exactement la nomenclature. Il est désormais traité comme un prologue : ignoré pendant structure, conservée à l’écriture.

Codex (#1633, fermeture du résidu de @spam0115 du #1580) : le réconciliateur de hook accepte la paire de hooks gérés v0.10.2 a écrit (y compris la variante Windows CRLF+BOM) et réécrit il est en place ; les refus nomment désormais leur raison au lieu d'échouer de manière générique.

Windows : la DACL arrête de vous combattre

Le descripteur de sécurité du répertoire d'exécution a été ré-estampillé à chaque démarrage de processus, si quelque chose n'allait pas ou non. #1601 a compté onze "Changement de sécurité" sans opération USN enregistrements sur un seul fichier par jour ; #1620 publications atomiques perdues dans la fenêtre de réécriture. Le nouveau tampon se déclenche désormais uniquement lorsque le répertoire n'est pas déjà dans le propriétaire exact uniquement. état - et les répertoires endommagés par le régime DACL pré-v0.10.3 (les journaux DACL vides dossier @patxisan trouvé, qui expliquait un mois de journaux de travail illisibles de 0 octet à travers six rapports) sont détectés et réparés sur place. (#1416, #1601, #1620)

Également livré : CBM_RUNTIME_DIR est transmis dans les configurations Codex générées (#1664 — un le démon déplacé était invisible pour les serveurs générés par le Codex), une nouvelle ligne finale manquante n'est pas n'est plus signalé comme une analyse partielle et update ne nomme plus un programme d'installation qui n'est pas là (#1653).
