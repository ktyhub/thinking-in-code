codebase-memory-mcp v0.12.1

#v0.12.1

Chaque chemin d'installation fonctionne à nouveau et les graphiques Helm rejoignent le graphique.

v0.12.1 corrige les installations de packages de v0.12.0 et les autres chemins d'installation que nous avons trouvés défectueux lors de la vérification de chaque canal. Il relie également les graphiques Helm à ce qu'ils déploient et empêche le graphique d'inventer un registre pour les images de conteneurs.

Mise à niveau ? Le premier index de chaque projet existant après la mise à niveau est une reconstruction complète, une fois (les identités des images ont été modifiées ; voir ci-dessous).

Corrigé : installations

  • Installations npm, PyPI et Go. npm i, pnpm add, pip install et le wrapper Go n'ont pu installer v0.12.0 sur aucune plate-forme. Chaque wrapper a refusé un membre d'archive supérieur à 256 Mo, et chaque binaire v0.12.0 fait 331 à 335 Mo. Les limites de taille ont disparu pour les trois wrappers. L'archive est toujours vérifiée par rapport au checksums.txt de la version avant d'être décompressée, son contenu doit être exactement les fichiers attendus et le binaire doit répondre à --version. Merci, @hydroplexus, pour le rapport précis (#2657).
  • Homebrew. La formule était toujours à 0.10.3, et sous Linux, elle installait la version liée dynamiquement, qui nécessite la glibc 2.38 (Ubuntu 22.04, Debian 12 et RHEL 9 ne l'ont pas). Il installe désormais la version actuelle et, sous Linux, la version statique -portable qui s'exécute sur n'importe quelle distribution.
  • go install. Un go install .../pkg/go/cmd/codebase-memory-mcp@vX.Y.Z épinglé n'a jamais fonctionné et @latest a installé une version obsolète. Les versions portent désormais les balises pkg/go/vX.Y.Z et le wrapper installe la version correspondant à sa propre version.
  • npm next. La balise dist next ne pointe plus vers une ancienne version candidate ; une version stable le déplace.
  • Docs. winget et Chocolatey ont été répertoriés comme canaux d'installation mais ne sont pas publiés ; ils sont supprimés jusqu'à ce qu'ils le soient. Les versions de Windows arm64 sont livrées et sont maintenant répertoriées.

Tests de fumée du chemin d'installation. Chaque demande d'extraction et chaque version installe désormais les wrappers npm, PyPI et Go, comme le fait le gestionnaire de packages d'un utilisateur, par rapport aux archives de version réelle, et exécute le binaire de chacune d'entre elles installée. Une version n'est publiée qu'après la réussite de ces installations, de sorte qu'un installateur qui ne peut pas installer ce que nous livrons ne peut plus vous joindre.

Graphiques Helm dans le graphique

Un graphique Helm était autrefois un nœud isolé. Maintenant, il est lié à ce qu'il déploie (#2663) :

  • Graphique → objets (DEPLOYS, via: chart) : chaque objet Kubernetes rendu à partir du templates/ du graphique (les objets d'un sous-graphique appartiennent au sous-graphique).
  • fichier de valeurs → Graphique (CONFIGURES) : values.yaml et values-<x>.yaml à côté de Chart.yaml.
  • Graphique → images (DEPLOYS, ref: image) : chaque image nomme littéralement ses objets (une image modélisée n'en nomme aucun).

HelmRelease → Chart → Deployment → Image est désormais un chemin traversable. Sur 20 référentiels d'infrastructure, les graphiques sans bord sortant sont passés de 238 sur 260 à 109, et 2 511 liens graphique-objet sont apparus ; tous les autres bords sont restés identiques.

Les images conservent dans le registre les noms de code

Une image sans hôte de registre était stockée sous un docker.io/library/... inventé (#2654). Docker Hub est uniquement la valeur par défaut de Docker : Podman et CRI-O résolvent les noms courts via une liste de recherche, les miroirs les réécrivent et une balise de construction locale peut exister sur aucun registre. Une image conserve désormais son nom tel qu'écrit, avec registry: unknown lorsqu'aucun hôte n'est indiqué ; un hôte déclaré est conservé (les orthographes de Docker Hub deviennent docker.io). FROM nginx et image: docker.io/library/nginx sont désormais deux nœuds Image. Cela modifie les identités des images, c'est pourquoi chaque projet est reconstruit une fois après la mise à niveau.

Notes de mise à niveau

  • Le premier index de chaque projet existant après la mise à niveau est une reconstruction complète, une fois.
  • Les nœuds d'image sans registre indiqué portent désormais registry: unknown et le nom tel qu'écrit, au lieu de docker.io/library/....
