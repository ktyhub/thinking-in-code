codebase-memory-mcp v0.10.1

codebase-memory-mcp v0.10.1

Une version de correctif à suivre rapidement. Si vous utilisez cbm via un MCP client — Claude Code, Codex ou tout autre client conforme aux spécifications — mettez à niveau maintenant : dans v0.10.0, le format de sortie par défaut des principaux outils de découverte rendu sous la forme d'un {} vide exactement dans ces clients. Le graphique allait bien, le démon allait bien, les données étaient dans la réponse - mais la partie de la réponse que votre client lit réellement était vide. L'utilisation du CLI n'a pas été affectée, c'est précisément pourquoi il a échappé aux portes de libération.

Un immense merci à @Navier8, dont #1522 a signalé cela quelques heures après la sortie du v0.10.0 — avec une qualité de reproduction que nous souhaitons que chaque rapport de bogue ait : même binaire, même index, tables d'appels format par format qui ont localisé la faute sur le chemin de réponse MCP avant même que nous ayons lu le code. Le rapport a nommé deux bugs ; le balayage de vérification qu’il a déclenché en a trouvé un troisième. Tous les trois sont corrigés ici, et tous les trois sont livrés dans v0.10.0 partageant une forme d'échec : un résultat vide avec un statut de réussite — le pire mode d'échec possible pour un LLM client, ​​qui ne peut pas distinguer « vide » de « rien trouvé » et tire silencieusement de fausses conclusions au lieu de voir une erreur.

Qu'est-ce qui était cassé et qu'est-ce qui a changé

1. Les réponses des outils au format arborescent sont rendues sous la forme {} dans MCP clients (le format par défaut – le chemin principal). Une optimisation de la taille du fil v0.10.0 a arrêté la duplication des charges utiles de l'outil dans structuredContent, laissant un objet vide à sa place – alors que chaque outil déclarait toujours un outputSchema permissif. La spécification MCP indique à clients : lorsqu'un outil déclare un schéma de sortie, structuredContent est le résultat. Ainsi, search_graph, trace_path, query_graph, get_architecture, search_code et detect_changes ont tous renvoyé {} aux clients respectant les schémas sur chaque plate-forme. Le contrat est désormais véridique de bout en bout : aucun outil ne déclare un outputSchema (la sortie de l'outil varie légitimement en fonction du paramètre format, donc aucun schéma statique n'a jamais été honnête), les charges utiles d'objet JSON portent leur structuredContent analysé, les enveloppes d'erreur conservent leur structuredContent.error lisible par machine, et les charges utiles en forme de texte ne portent simplement aucune clé structuredContent - ce qui préserve également le v0.10.0 gagne en ne jamais expédier la charge utile deux fois.

2. Sept requêtes pipeline ou plus ont carrément tué le serveur MCP. Trouvé lors de la vérification de la surface de l'outil pour cette version : l'écriture de plus de 7 requêtes sur le serveur en une seule rafale (ce qui est exactement ce que fait un agent émettant des appels d'outil parallèles) a fait déborder une file d'attente d'entrée de 8 images et le gestionnaire de débordement a détruit toute la session : code de sortie 1, zéro octet de sortie, chaque réponse déjà calculée perdue. Une file d'attente pleine est désormais une contre-pression : le lecteur cesse simplement d'accepter les entrées jusqu'à ce que le travailleur rattrape son retard et que chaque demande obtienne sa réponse. Vérifié avec des rafales de 7, 24 et 64.

3. config get a répondu à chaque question avec une chaîne vide et a quitté 0. Les touches non définies n'imprimaient rien (tandis que config list affichait joyeusement leurs valeurs par défaut), tout comme les touches mal orthographiées - une faute de frappe était impossible à distinguer d'un paramètre correctement lu. config get imprime désormais la valeur stockée ou la valeur par défaut d'exécution réelle de la clé, et les clés inconnues sont une erreur (sortie 1, avec les clés connues répertoriées) sur get, set et reset.

Pourquoi les portes l'ont manqué – et qu'est-ce qui le garde maintenant

La partie honnête : notre propre test pour le changement de structuredContent a identifié le comportement défectueux comme correct, à la fois au niveau de l'unité et dans la suite de fumée binaire expédiée - un rappel qu'un test affirmant le mauvais contrat est pire que l'absence de test. Le pipeline de versions était vert car il acceptait le bug. Cette classe est maintenant fermée dans trois directions : la suite d'unités énumère la table d'outils entière et lie les trois branches d'enveloppe (objet absent / analysé / erreur) pour chaque outil enregistré, la suite frontale affirme que l'entrée pipeline en surcapacité reçoit une réponse sans perte, et la suite smoke pilote le ** binaire réel livré ** comme le fait un MCP honorant le schéma client - affirmant qu'une réponse au format par défaut ne peut jamais être rendue comme {}, que non L'outil annonce un outputSchema, qu'une rafale pipeline de 24 profondeurs obtient 24 réponses et que config get renvoie des valeurs réelles. Chacun d'entre eux a été vérifié en rouge par rapport à v0.10.0 avant le correctif et à nouveau rouge une fois le correctif annulé.

Mise à niveau

  • Installations binaires : téléchargez ci-dessous ou réexécutez install.sh / install.ps1 — la réexécution du programme d'installation est la mise à jour.
  • npm / PyPI : mettez à jour via votre gestionnaire de packages comme d'habitude.
  • Pas de migration d'index, de cache ou de configuration ; Les graphiques v0.10.0 sont entièrement compatibles.
