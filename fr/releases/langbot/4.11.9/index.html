LangBot v4.11.9

LangBot est une plate-forme de chatbot et d'agent IA open source qui prend en charge plusieurs plates-formes de messagerie instantanée, de grands modèles de langage, des bases de connaissances et des plug-ins pour vous aider à créer, déployer et gérer des assistants IA. LangBot est une plate-forme d'agent et de chatbot IA open source qui connecte des plates-formes de messagerie, de grands modèles de langage, des bases de connaissances et des plugins pour vous aider à créer, déployer et gérer des assistants IA.

LangBot v4.11.9

Le bac à sable Box fonctionne désormais sur les hôtes Windows, les agents peuvent lire les fichiers téléchargés à la demande et publier les fichiers qu'ils produisent, et les nouvelles installations conservent les compétences et les téléchargements dans la base de données. Cette version permet au bac à sable Box de s'exécuter sur des hôtes Windows ; l'agent peut lire les fichiers téléchargés à la demande et publier ses propres fichiers générés ; les nouvelles installations enregistrent par défaut les compétences et le contenu téléchargé dans la base de données.

Remarque de mise à niveau/Conseil de mise à niveau : Cette version contient une nouvelle migration de base de données (0049–0053). Veuillez sauvegarder le répertoire data/ avant la mise à niveau (sauvegarder la base de données en même temps lorsque vous utilisez PostgreSQL) ; vous devez utiliser cette sauvegarde pour restaurer lors de la rétrogradation. Les paramètres de stockage, de compétence et de boîte déjà déployés dans config.yaml restent inchangés. Cette version ajoute les migrations de bases de données 0049 à 0053. Sauvegardez data/ (et PostgreSQL, le cas échéant) avant la mise à niveau ; la restauration nécessite cette sauvegarde. Les déploiements existants conservent les paramètres de stockage, de compétence et de boîte dans leur config.yaml.

Faits saillants

  • Windows host Box / Windows host sandbox : Le plug-in SDK 0.7.26 permet au backend host de supporter Windows : la commande est d'abord exécutée avec Git Bash, sinon elle retourne dans PowerShell, et toute l'arborescence des processus est nettoyée à la fin. Remarque : le host n'effectue aucune isolation (DANGEREUX). La commande est exécutée directement en tant qu'utilisateur exécutant LangBot. Les utilisateurs non fiables de la discussion de groupe peuvent exécuter la commande via une injection de mot rapide. Il n'est pas automatiquement sélectionné et doit être explicitement défini sur box.backend: host dans config.yaml, ou écrit par l'installation native de lbctl (à partir de lbctl v0.5.14). La compétence ne peut pas être exécutée sur la boîte hôte Windows sous box.file_transfer_mode: network ; veuillez utiliser legacy lorsque LangBot et Box sont sur la même machine (lbctl écrira automatiquement). Le backend host fonctionne désormais sous Windows (Git Bash, retour à PowerShell ; toute l'arborescence des processus est nettoyée). host n'a pas d'isolation et exécute des commandes en tant qu'utilisateur LangBot, de sorte que les utilisateurs de discussion de groupe non rust peuvent exécuter des commandes via une injection rapide. Il n'est jamais sélectionné automatiquement : définissez explicitement box.backend: host ou laissez lbctl (v0.5.14+) l'écrire pour les installations natives. Les Skills ne peuvent pas s'exécuter sur une Box hôte Windows en mode de transfert network ; lorsque LangBot et Box partagent une machine, utilisez box.file_transfer_mode: legacy (lbctl le définit pour vous).
  • Fichiers pour agents / Fichiers d'agent : les fichiers téléchargés sont enregistrés en tant qu'actifs de fichiers avec autorisations. L'agent obtient d'abord la référence du fichier, puis lit le texte, l'image ou le PDF segment par segment via l'outil si nécessaire ; le Runner peut publier le fichier généré vers le destinataire désigné, et il peut toujours être téléchargé une fois l'exécution terminée ou le redémarrage du Core. Les fichiers de la base de connaissances et le plug-in SDK sont également connectés au même ensemble d'actifs de fichiers. Les téléchargements deviennent des fichiers autorisés : les agents obtiennent des références et lisent du texte, des images ou des pages PDF à la demande via des outils, et les Runners peuvent publier des fichiers de sortie qui restent téléchargeables après la fin de l'exécution ou le redémarrage du Core. Les fichiers de la base de connaissances et le plugin SDK utilisent les mêmes ressources.
  • Compétences et téléchargements basés sur la base de données par défaut / Stockage de la base de données par défaut nouvellement installée : les compétences nouvellement installées (y compris les versions historiques) et le contenu téléchargé sont stockés dans la base de données par défaut. Box transfère les fichiers via le réseau par défaut. Core et Box n'ont plus besoin de partager des répertoires. Lorsqu'un déploiement existant passe à ce mode, Core importera l'ancienne compétence et les fichiers locaux avant de démarrer et d'ouvrir HTTP, qui peuvent être interrompus et restaurés. Une fois l’importation terminée, elle ne s’appuiera plus sur l’ancien répertoire. Le Docker Box en mode réseau peut monter des ensembles de données locales en lecture seule. Les nouvelles installations stockent les compétences (avec leur historique de versions) et les téléchargements dans la base de données, et Box déplace les fichiers sur le réseau au lieu d'un répertoire partagé. Lorsqu'un déploiement existant bascule, Core importe les anciennes compétences et les fichiers locaux avant de diffuser HTTP, de manière probable. Les boîtiers en mode réseau Docker peuvent monter des ensembles de données locaux en lecture seule.
  • Opérations API / Opération API : Ajout de l'interface /api/v1/operations (répertoire, description, exécution, flux SSE), la clé API peut également confirmer les autorisations du plug-in, et les clients tels que lbctl peuvent utiliser la clé API pour confirmer les autorisations du plug-in. Nouvelles routes /api/v1/operations (catalogue, description, exécution, SSE) et confirmation des autorisations du plugin avec une clé API, afin que API clients tels que lbctl puissent confirmer les autorisations du plugin.
  • WebUI : La boîte de dialogue de mise à jour affiche directement le journal de mise à jour sur langbot.app ; la page de détails du plug-in affiche la version installée et peut être directement mise à niveau ; après avoir installé le plug-in, l'étape suivante est proposée en fonction du type de composant. La boîte de dialogue de mise à jour affiche les release note de langbot.app ; les pages de détails du plugin affichent la version installée et proposent des mises à niveau ; l'installation d'un plugin suggère l'étape suivante.
  • Démarrage/Démarrage : pip install ne détecte plus automatiquement les dépendances manquantes au démarrage, mais répertorie les packages manquants et invite à réinstaller puis à quitter. LangBot n'installe plus les packages manquants au démarrage ; il les répertorie et se termine avec des instructions de réinstallation.
  • Corrections / Correctifs : les processus de plug-in qui ne parviennent pas à démarrer à plusieurs reprises reculeront et réessayeront et n'actualiseront plus l'écran ; L'édition en streaming de télégrammes ignore « le message n'est pas modifié » ; MulticaAgent réessayera lorsqu'il rencontrera une erreur temporaire et les réponses perdues lors du redémarrage seront réémises ; Le service client d'entreprise WeChat analyse automatiquement open_kfid lors de l'envoi de messages au nu external_userid ; les alarmes sur LangBot Cloud doivent toujours être activées manuellement ; E2B Le quota d'espace de travail prend effet ; Le packaging du plug-in exclut le répertoire de l'environnement virtuel. Les plugins défaillants reculent ; Le streaming de télégrammes ignore « le message n'est pas modifié » ; MulticaAgent réessaye les erreurs transitoires et récupère les réponses perdues lors des redémarrages ; Le service client WeCom résout open_kfid pour les cibles nues external_userid ; les alertes restent opt-in sur LangBot Cloud ; Les limites de l'espace de travail E2B sont appliquées ; les packages de plugins excluent virtualenvs.
  • SDK：langbot-plugin et 0.7.25 et 0.7.26。Broches centrales langbot-plugin==0.7.26.

Vérification de la version

  • Libérer le commit 826bf580ff42bbf10dac52203f1171f63b97b52a. Il ne diffère du candidat testé dfa3c743c que par le numéro de version ; toutes les vérifications de demande d'extraction ont été réussies sur la version PR.
  • Avant le marquage, le candidat a été installé deux fois sur de nouveaux répertoires de données et exécuté des opérations de routine :
    • Docker (docker compose avec le runtime du plugin et Box, image construite à partir du commit candidat) ;
    • uvx (uvx --from <wheel> langbot, dépendances de PyPI : SDK 0.7.26, SQLAlchemy 2.1.9). Les deux ont réussi : configuration du compte et WebUI ; Installation Marketplace de LocalAgent, EssentialCommands, WebSearch, LangRAG et HelloPlugin avec confirmation d'autorisation, activation/désactivation par pipeline et désinstallation ; fournisseur de modèles et test de modèles ; un pipeline LocalAgent sur HTTP Bot, comprenant un appel à un outil de recherche Web ; !help !cmd !func !plugin !version ; l'ingestion et la récupération de bases de connaissances ; créer une compétence et la faire utiliser par l'agent ; et les données, plugins, base de connaissances et compétences intactes après un redémarrage. Docker a exécuté une commande dans un conteneur sandbox Box ; uvx en a exécuté un via le backend de la host Box.
  • Concurrency : 8 conversations simultanées sur un modèle complétées sur Docker. Sur uvx (SQLite), certaines conversations ont dépassé la fenêtre de réponse du HTTP Bot 60 sur un hôte de test très chargé et quelques-unes ont atteint database is locked ; Les v4.11.8 se sont comportés de la même manière côte à côte sous la même charge, ce n'est donc pas nouveau dans cette version.
  • Windows : la roue de publication a été installée avec uvx sur Windows 11 (build 26300, page de codes 936, Python 3.11, Git Bash installé ; SDK 0.7.26, SQLAlchemy 2.1.9) et a passé la même liste de contrôle avec un modèle simulé local, comprenant 8 conversations simultanées (8/8, pas de database is locked). Avec box.backend: host et file_transfer_mode: legacy, l'agent a exécuté une commande (exec) et a écrit et relu un fichier via la boîte hôte Windows. Un plugin imprimant du chinois et des emoji a maintenu le runtime connecté, et avec les téléchargements de tokenizer bloqués, la première conversation LocalAgent a répondu en 2 s (pas de délai d'attente count_tokens).
  • Migrations de bases de données : les bases de données créées par v4.11.8 (révision 0048), v4.10.11 (0023) et v4.10.6 (0008, avant les espaces de travail) ont été mises à niveau vers cette version sur SQLite et PostgreSQL. Chaque mise à niveau a atteint la révision 0053 et a démarré deux fois proprement ; aucune ligne n'a été perdue, les vérifications d'intégrité SQLite et de clé étrangère ont été réussies, et le fournisseur, le modèle, le bot et le pipeline prédéfinis ont été relus. Des copies de trois bases de données SQLite réelles (révisions 0042, 0040 et 0008, jusqu'à 33 Mo) ont également été mises à niveau proprement. Les schémas mis à niveau correspondent à une nouvelle installation, mis à part les différences de nom d'index sur les bases de données démarrées avant 0024, ce que possède également v4.11.8.
