éleveur v2.15.1

Sortie v2.15.1

[!IMPORTANT]

  • Si vous utilisez Active Directory Federation Service (AD FS), la mise à niveau vers Rancher v2.10.1 ou version ultérieure peut entraîner des problèmes d'authentification, nécessitant une intervention manuelle. Ces problèmes sont dus au fait que la partie utilisatrice AD ​​FS Trust n'est pas en mesure de récupérer un certificat de vérification de signature à partir des métadonnées. Pour plus d’informations, consultez #48655. Ces problèmes peuvent être corrigés de deux manières :

  • Mise à jour des informations de la partie de confiance Trust à partir des métadonnées de la fédération (Partie de confiance Trust → Mise à jour des métadonnées de la fédération…​).

  • Ajout direct du certificat (Relying Party Trust → Propriétés → onglet Signature → Ajouter → Sélectionner le certificat).

Rancher v2.15.1 est la dernière version du correctif de Rancher. Il s'agit d'une version communautaire qui introduit des mises à jour de maintenance et des corrections de bogues.

Pour plus d'informations sur les nouvelles fonctionnalités de la version mineure générale, consultez les v2.15.0 release notes.

Correctifs de sécurité pour les vulnérabilités

Cette version résout les problèmes de sécurité suivants :

Éleveur

  • Correction d'une vulnérabilité de sécurité dans le gestionnaire d'authentification SAML de Rancher où la protection contre la relecture des assertions était inefficace dans les déploiements à haute disponibilité (multi-réplicas). Étant donné que chaque réplica suivait les ID d'assertion consommés dans un cache en mémoire distinct, une assertion SAML capturée pouvait être relue sur d'autres réplicas pour créer des sessions authentifiées supplémentaires en tant que victime. Le correctif suit les ID d’assertion consommés sur toutes les répliques. Tous les fournisseurs SAML ont été concernés. Pour plus d'informations, reportez-vous à CVE-2026-75034.
  • Corrige une vulnérabilité de sécurité dans le secretsController à l'échelle du projet Rancher où les secrets du projet se propagent aux espaces de noms basés uniquement sur l'annotation field.cattle.io/projectId sans valider que le projet référencé appartient au même cluster. Un utilisateur authentifié disposant d'autorisations de création d'espace de noms sur un cluster en aval pourrait usurper cette annotation pour divulguer les secrets de projet d'un projet non autorisé dans un autre cluster. Le contrôleur vérifie désormais que l'annotation fait référence à un projet au sein du même cluster avant de propager les secrets. Pour plus d'informations, voir CVE-2026-75033.
  • Correction d'une vulnérabilité de sécurité dans le jeton d'extension impératif Rancher API (jetons ext.cattle.io/v1) où tout utilisateur authentifié peut répertorier et surveiller les jetons d'autres utilisateurs en fournissant un sélecteur d'étiquettes spécialement conçu, divulguant les métadonnées du jeton et le hachage du jeton du porteur stocké. Le magasin applique désormais la portée par utilisateur sans condition afin que les appelants ne voient que leurs propres jetons et que les réponses lues ne renvoient plus le hachage du jeton stocké. Pour plus d'informations, voir CVE-2026-75035.
  • Correction d'une vulnérabilité de sécurité dans le contrôleur GlobalRole de Rancher où un utilisateur disposant d'autorisations déléguées create ou update pour les ressources GlobalRole pouvait définir l'annotation authz.management.cattle.io/cr-name pour cibler un ClusterRole existant arbitraire (tel que le cluster-admin intégré). Le contrôleur écrase ensuite les règles sans vérification de propriété, supprimant les autorisations de tous les principaux liés et provoquant un verrouillage RBAC persistant à l'échelle du cluster sur le cluster de gestion local. Pour plus d'informations, reportez-vous à CVE-2026-71404.
  • Correction d'une vulnérabilité de sécurité dans SUSE Rancher Norman /v3/users API où le chemin de mise à jour n'imposait pas l'immuabilité des champs username, principalIds et displayName sur une ressource User. Un appelant détenant les autorisations update sur users pourrait relier l'identité principale externe d'un utilisateur, permettant ainsi la prise de contrôle du compte lors de la prochaine connexion externe ou créant une condition de déni de service qui rendrait inaccessibles les liaisons de rôle existantes. Les couches de magasin API et de webhook d'admission ont été mises à jour pour rejeter les modifications post-création apportées à ces champs d'identité. Pour plus d'informations, voir CVE-2026-71403.

Flotte

  • Correction d'une vulnérabilité de sécurité dans le prétraitement du modèle Fleet's Helm où les modèles évalués par le contrôleur de flotte pouvaient atteindre les ressources réseau. Un utilisateur qui peut fournir le contenu du bundle untrusted peut exposer les métadonnées du cluster et les informations sur les hôtes accessibles depuis le contrôleur. Fleet rejette désormais les bundles dont les valeurs du modèle Helm nécessitent un accès au réseau, signalant une erreur pour le GitRepo correspondant. Pour plus d'informations, reportez-vous à CVE-2026-75036.
  • Correction d'une vulnérabilité de sécurité dans Fleet où les étiquettes de cluster fournies par un agent lors de l'enregistrement du cluster initié par l'agent étaient appliquées à l'objet Cluster résultant, y compris les étiquettes management.cattle.io/ réservées utilisées pour le ciblage des bundles. Dans les déploiements où plusieurs domaines trust partagent un espace de noms d'espace de travail Fleet, cela permettait à un cluster d'enregistrement de correspondre aux cibles Bundle ou GitRepo d'un autre locataire et de recevoir les manifestes et les valeurs résolues de ce locataire. Fleet supprime désormais les étiquettes réservées fournies lors de l’inscription initiée par l’agent. Les déploiements Standalone Rancher ne sont pas affectés dans leur configuration par défaut, car Rancher utilise l'enregistrement initié par le gestionnaire. Pour plus d'informations, reportez-vous à CVE-2026-93538.
  • Correction d'une vulnérabilité de sécurité dans Fleet où les étiquettes d'espace de noms et les annotations demandées par un bundle via namespaceLabels et namespaceAnnotations étaient appliquées sans l'autorisation du compte de service auquel le bundle était épinglé. Dans les déploiements mutualisés, cela permettait à un bundle de modifier les métadonnées de l'espace de noms que sa propre identité n'était pas autorisée à modifier. La mise à jour de l'espace de noms s'exécute désormais en tant que compte de service du déploiement et est régie par le RBAC Kubernetes en aval. Pour plus d'informations, reportez-vous à CVE-2026-93540.

Notes d'installation/mise à niveau

Si vous installez Rancher pour la première fois, votre environnement doit répondre aux [exigences d'installation] (https://ranchermanager.docs.rancher.com/v2.15/getting-started/installation-and-upgrade/installation-requirements).

[!IMPORTANT]

  • Rancher exige désormais que le cluster sur lequel il s'exécute ait la [couche d'agrégation Kubernetes API] (https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/) activée. En effet, Rancher étend Kubernetes avec des API supplémentaires en enregistrant son propre serveur d'extension API. Veuillez noter que toutes les versions de Kubernetes prises en charge dans ces distributions Rancher versions K8 (RKE2/K3) auront la couche d'agrégation configurée et activée par défaut.

  • Reportez-vous à la Documentation du serveur d'extension API et #50400 pour plus d'informations.

  • Le moteur Rancher Kubernetes (RKE/RKE1) a atteint la fin de sa durée de vie au 31 juillet 2025. Les versions Rancher 2.12.0 et ultérieures ne prennent plus en charge le provisionnement ou la gestion des clusters RKE1 en aval. Nous vous recommandons de remplacer les clusters RKE1 par RKE2 pour garantir une prise en charge continue et des mises à jour de sécurité. Apprenez-en davantage sur la transition ici.

  • Rancher dispose désormais d'un contrôle de validation avant mise à niveau pour les ressources RKE1 qui échoue et répertorie les ressources RKE1 si elles sont présentes. Reportez-vous à #50286 pour plus d'informations.

  • Il est essentiel que vous examiniez l'espace disque disponible sur vos nœuds et que vous planifiiez en conséquence avant de passer à Rancher v2.12.0 et versions ultérieures pour éviter d'éventuels problèmes de pression sur le disque et d'expulsion de pods.

  • Pour plus d'informations, reportez-vous à la [Documentation UI Server Side Pagination - Disk Space] (https://ranchermanager.docs.rancher.com/v2.15/how-to-guides/advanced-user-guides/ui-server-side-pagination#disk-space).

  • Rancher dispose désormais d'une option d'activation appelée AUDIT_LOG_ENABLED pour les journaux d'audit API pour une installation Rancher.

  • Dans les versions Rancher 2.11.x et antérieures, seul le AUDIT_LEVEL pouvait être défini et le niveau de journalisation par défaut (0) désactiverait le journal d'audit. Dans les versions Rancher 2.12.x et ultérieures, le niveau de journalisation par défaut (0) contient désormais uniquement les métadonnées de demande de journal et de réponse et peut être défini lors de la configuration de AUDIT_LOG_ENABLED. Lors de l'installation ou de la mise à niveau via Helm, vous pouvez activer les journaux d'audit API et spécifier le niveau de journalisation en appliquant le paramètre suivant à votre commande Helm : --set auditLog.enabled=true --set auditLog.level=0. Consultez la documentation Activation du journal d'audit API pour enregistrer les événements système et #48941.

Modifications des artefacts d'image

Les résumés d'artefacts d'image sont renommés dans Rancher v2.12.0, v2.11.4 et v2.10.8. Jusqu'à ce changement, des fichiers de résumés d'images distincts pour chaque système d'exploitation et architecture ont été conservés pour des raisons de compatibilité. Avec ce changement, un seul fichier pour chaque système d'exploitation doit être fourni :

  • Les fichiers rancher-images-digests-linux-amd64.txt et rancher-images-digests-linux-arm64.txt doivent être renommés en rancher-images-digests-linux.txt.

  • Les fichiers rancher-images-digests-windows-ltsc2019.txt et rancher-images-digests-windows-ltsc2022.txt doivent être renommés en rancher-images-digests-windows.txt.

Exigences de mise à niveau

  • Création de sauvegardes : [Créer une sauvegarde] (https://ranchermanager.docs.rancher.com/v2.15/how-to-guides/new-user-guides/backup-restore-and-disaster-recovery/back-up-rancher) avant de mettre à niveau Rancher. Pour restaurer Rancher après une mise à niveau, vous devez d'abord sauvegarder et restaurer Rancher à la version précédente de Rancher. Étant donné que Rancher sera restauré dans le même état que lors de la création de la sauvegarde, toutes les modifications postérieures à la mise à niveau ne seront pas incluses après la restauration.

  • Exigences de la version Helm :

    • Pour gérer Rancher 2.12.x et versions ultérieures, vous devez mettre à niveau votre Helm client vers la version 3.18 ou une version plus récente.

    • Cette modification est nécessaire pour refléter l'ajout de la prise en charge de Kubernetes 1.33 avec cette version.

    • Actuellement, la [Politique de prise en charge de la version Helm] officielle (https://helm.sh/docs/topics/version_skew/) stipule que seul Helm 3.18 prend en charge la gamme de versions Kubernetes appropriée pour Rancher 2.12.

  • Exigences CNI :

  • Pour Kubernetes v1.19 et versions ultérieures, désactivez firewalld car il est incompatible avec divers plugins CNI. Voir #28840.

    • Lors de la mise à niveau ou de l'installation d'une distribution Linux qui utilise nf_tables comme filtre de paquets backend, telle que SLES 15, RHEL 8, Ubuntu 20.10, Debian 10 ou version ultérieure, effectuez une mise à niveau vers RKE v1.19.2 ou version ultérieure pour obtenir Flannel v0.13.0. La flanelle v0.13.0 prend en charge nf_tables. Voir Flanelle #1317.

  • Exigences pour les environnements à air isolé :

    • Lorsque vous utilisez un proxy devant une instance Rancher isolée, vous devez transmettre des paramètres supplémentaires à NO_PROXY. Consultez la documentation et le numéro #2725.

    • Lors de l'installation de Rancher avec Docker dans un environnement isolé, vous devez fournir un fichier registries.yaml personnalisé à la commande docker run, comme indiqué dans la [documentation K3s] (https://docs.k3s.io/installation/private-registry). Si le registre dispose de certificats, vous devrez également les fournir. Voir #28969.

Versions des graphiques de barre Rancher

Dans Rancher v2.6.0 et versions ultérieures, dans l'interface utilisateur Applications et Marketplace, de nombreuses cartes Rancher Helm sont nommées avec une version majeure qui commence par 100. Cela évite que les modifications simultanées en amont et les modifications de Rancher provoquent des incréments de version conflictuels. Ceci est également conforme au versioning sémantique (SemVer), qui est une exigence pour Helm. Vous pouvez voir le numéro de version en amont d'un graphique dans les métadonnées de build, par exemple : 100.0.0+up2.1.0. Voir #32294.

Problèmes connus de longue date

Problèmes connus de longue date - Rancher General

  • Éleveur v2.15.0 :

  • Il existe un problème connu avec les clusters Rancher v2.15.0 et Kubernetes v1.36 où Rancher Backups n'est pas répertorié sous Cluster Tools en raison d'un problème de graphique de sauvegardes. Voir #1055.

Problèmes connus de longue date – Approvisionnement du cluster

  • Tous les outils de cluster ne peuvent pas être installés sur un cluster renforcé.

  • Éleveur v2.8.1 :

    • Lorsque vous tentez d'enregistrer un nouveau nœud etcd/plan de contrôle dans un cluster géré par CAPR après l'échec de la restauration d'un instantané etcd, le nœud peut rester bloqué dans un état de pause perpétuelle, affichant le message d'erreur [ERROR] 000 received while downloading Rancher connection information. Sleeping for 5 seconds and trying again. Pour contourner ce problème, vous pouvez réactiver le cluster en exécutant kubectl edit clusters.cluster clustername -n fleet-default et en définissant spec.unpaused sur false. Voir #43735.

Problèmes connus de longue date – Approvisionnement RKE2

  • Éleveur v2.7.7 :

    • En raison de la logique d'attente dans divers composants, les clusters K3 et RKE2 provisionnés en aval peuvent prendre plus de temps pour retrouver le statut Actif après une migration. Si vous constatez qu'un cluster en aval est toujours en cours de mise à jour ou dans un état d'erreur immédiatement après une migration, laissez-le tenter de se résoudre. Cela peut prendre jusqu'à une heure. Voir #34518 et #42834.

  • Éleveur v2.7.6 :

    • Le provisionnement des clusters RKE2/K3s avec des pilotes de nœuds personnalisés ajoutés (non intégrés) entraîne l'échec du provisionnement. Pour contourner ce problème, corrigez les pilotes de nœud ajoutés après l'activation. Voir #37074.

Problèmes connus de longue date – Approvisionnement K3s

  • Éleveur v2.7.6 :

    • Le provisionnement des clusters RKE2/K3s avec des pilotes de nœuds personnalisés ajoutés (non intégrés) entraîne l'échec du provisionnement. Pour contourner ce problème, corrigez les pilotes de nœud ajoutés après l'activation. Voir #37074.

  • Éleveur v2.7.2 :

    • Les clusters restent dans un état Updating même lorsqu'ils contiennent des nœuds dans un état Error. Voir #39164.

Problèmes connus de longue date – Application Rancher (interface utilisateur globale)

  • Éleveur v2.10.0 :

    • Après avoir supprimé un espace de noms ou un projet dans l'interface utilisateur de Rancher, l'espace de noms ou le projet reste visible. Pour contourner le problème, actualisez la page. Voir #12220.

  • Éleveur v2.9.2 :

    • Bien que les pools de nœuds en mode système doivent avoir au moins un nœud, l'interface utilisateur de Rancher autorise un nombre minimum de nœuds de zéro. La saisie d'un nombre minimum de nœuds nul via l'interface utilisateur peut entraîner l'échec de la création du cluster en raison d'une erreur de paramètre non valide. Pour éviter que cette erreur ne se produise, entrez un nombre minimum de nœuds au moins égal au nombre de nœuds. Voir #11922.

  • Éleveur v2.7.7 :

    • Lors de la création d'un cluster dans l'interface utilisateur de Rancher, l'utilisation du trait de soulignement _ dans le champ Cluster Name n'est pas autorisée. Voir #9416.

  • Éleveur v2.6.4 :

    • La section securityContext de déploiement est manquante lorsqu'une nouvelle charge de travail est créée. Cela empêche les pods de démarrer lorsque la prise en charge des politiques de sécurité des pods est activée. Voir #4815.

Problèmes connus de longue date – EKS

  • Éleveur v2.7.0 :

    • Les clusters EKS sur Kubernetes v1.21 ou inférieur sur Rancher v2.7 ne peuvent pas être mis à niveau. Voir #39392.

Problèmes connus de longue date – Authentification

  • Éleveur v2.9.0 :

    • Il existe certains problèmes connus avec la prise en charge du fournisseur OpenID Connect :

      • Lorsque le fournisseur d'authentification OIDC générique est activé et que vous tentez d'ajouter des utilisateurs du fournisseur d'authentification à un cluster ou un projet, les utilisateurs ne sont pas renseignés dans la barre de recherche déroulante. Il s’agit d’un comportement attendu car le fournisseur d’authentification OIDC seul n’est pas consultable. Voir #46104.

      • Lorsque le fournisseur d'authentification OIDC générique est activé, les utilisateurs du fournisseur d'authentification qui sont ajoutés à un cluster/projet par leur nom d'utilisateur ne peuvent pas accéder aux ressources lors de la connexion. Un utilisateur n'aura accès aux ressources lors de la connexion que s'il est ajouté par son ID utilisateur. Voir #46105.

      • Lorsque le fournisseur d'authentification OIDC générique est activé et qu'un utilisateur du fournisseur d'authentification dans un groupe imbriqué est connecté à Rancher, l'utilisateur verra l'erreur suivante lorsqu'il tentera de créer un projet : projectroletemplatebindings.management.cattle.io is forbidden: User "u-gcxatwsnku" cannot create resource "projectroletemplatebindings" in API group "management.cattle.io" in the namespace "p-9t5pg". Cependant, le projet est toujours créé. Voir #46106.

Problèmes connus de longue date – Rancher Webhook

  • Éleveur v2.7.2 :

    • Un webhook est installé dans tous les clusters en aval. Les utilisateurs peuvent rencontrer plusieurs problèmes avec cette fonctionnalité :

      • Si vous revenez d'une version de Rancher v2.7.2 ou ultérieure à une version de Rancher antérieure à v2.7.2, les webhooks resteront dans les clusters en aval. Étant donné que le webhook est conçu pour être compatible 1:1 avec des versions spécifiques de Rancher, cela peut entraîner des comportements inattendus en aval. L'équipe Rancher a développé un [script] (https://github.com/rancher/webhook/wiki/Remove-Webhook-from-downstream-clusters) qui doit être utilisé une fois la restauration terminée (c'est-à-dire après l'exécution d'une version Rancher antérieure à v2.7.2). Cela supprime le webhook des clusters en aval concernés. Voir #40816.

Problèmes connus de longue date – Gestion de la virtualisation (Harvester)

  • Éleveur v2.13.1 :

    • Lors de la mise à niveau vers Rancher v2.13.1 ou version ultérieure tout en utilisant Harvester v1.6.1, les utilisateurs peuvent rencontrer un problème avec leurs équilibreurs de charge dans les clusters en aval à l'aide du fournisseur Cloud Harvester et doivent effectuer la [solution de contournement] suivante (https://docs.harvesterhci.io/latest/troubleshooting/rancher#guest-cluster-loadbalancer-ip-is-not-reachable) pour demander à Calico de n'utiliser aucune des IP/interfaces gérées par kube-vip. Voir #9767.

  • Éleveur v2.7.2 :

    • Si vous utilisez Rancher v2.7.2 avec des clusters Harvester v1.1.1, vous ne pourrez pas sélectionner le fournisseur cloud Harvester lors du déploiement ou de la mise à jour des clusters invités. Les Harvester release note contiennent des instructions sur la manière de résoudre ce problème. Voir #3750.

Problèmes connus de longue date – Sauvegarde/Restauration

  • Lors de la migration vers un cluster avec la fonctionnalité Rancher Backup, l'URL du serveur ne peut pas être modifiée vers un emplacement différent. Il doit continuer à utiliser la même URL.

  • Éleveur v2.13.0 :

    • Lors d'une restauration de Rancher v2.13.0 vers v2.12.3 à l'aide de l'opérateur de sauvegarde et de restauration (BRO), la restauration ne se termine pas correctement. Voir #844. Pour contourner ce problème, vous devez réduire votre déploiement Rancher et désinstaller la carte Webhook avant d'effectuer la restauration. Pour plus de détails, reportez-vous à cet [article de la base de connaissances] (https://support.scc.suse.com/s/kb/Rolling-back-from-Rancher-v2-13-0-to-v2-12-3?language=en_US).

  • Éleveur v2.7.7 :

  • En raison de la logique d'attente dans divers composants, les clusters K3 et RKE2 provisionnés en aval peuvent prendre plus de temps pour retrouver le statut Actif après une migration. Si vous constatez qu'un cluster en aval est toujours en cours de mise à jour ou dans un état d'erreur immédiatement après une migration, laissez-le tenter de se résoudre. Cela peut prendre jusqu'à une heure. Voir #34518 et #42834.
