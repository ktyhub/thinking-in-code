caddy v2.10.0

#caddie v2.10.0 Le Caddy 2.10 est là ! Outre les corrections de bugs, cette version comprend :

  • ClientHello crypté (ECH) : Cette nouvelle technologie crypte la dernière partie de texte en clair d'une connexion TLS : le ClientHello, qui inclut le nom de domaine auquel vous vous connectez. Le [projet de spécification] (https://www.ietf.org/archive/id/draft-ietf-tls-esni-24.html) pour ECH est presque finalisé, nous pouvons donc désormais prendre en charge cette fonctionnalité de confidentialité pour TLS. Il s’agit d’une capacité puissante mais nuancée ; nous vous recommandons fortement de lire [la documentation ECH] (https://caddyserver.com/docs/automatic-https#encrypted-clienthello-ech) sur notre site Web.
  • Échange de clés post-quantique (PQC) : Caddy prend désormais en charge par défaut le groupe cryptographique standardisé x25519mlkem768.
  • Profils ACME : Les profils ACME sont une ébauche expérimentale qui vous permet de choisir les propriétés de vos certificats avec plus de flexibilité que les méthodes CSR traditionnelles. Par exemple, [Let's Encrypt émettra des certificats de 6 jours] (https://letsencrypt.org/2025/01/16/6-day-and-ip-certs/) sous un certain profil. Caddy pourra éventuellement utiliser ce profil par défaut.
  • En-tête Via : Le proxy inverse définit désormais un en-tête Via au lieu d'un en-tête de serveur en double.
  • Fournisseur DNS global : Vous pouvez désormais spécifier un module DNS « global » par défaut à utiliser au lieu de devoir le configurer localement dans chaque partie de votre configuration qui nécessite un fournisseur DNS (par exemple, les défis DNS ACME et ECH). Il s'agit de l'option globale dns dans le Caddyfile, ou dans la configuration JSON, c'est le paramètre dns dans la configuration de l'application tls.
  • Caractères génériques utilisés par défaut : Auparavant, Caddy obtenait littéralement des certificats individuels pour chaque domaine de votre configuration ; désormais, les caractères génériques, s'ils sont présents, seront utilisés pour les sous-domaines, plutôt que pour obtenir des certificats individuels. Ce changement a été motivé par la nouvelle possibilité de confidentialité des sous-domaines offerte par ECH. Il peut être remplacé par tls force_automate dans le Caddyfile. L'option expérimentale auto_https prefer_wildcard a été supprimée.
  • libdns 1.0 APIs : Beaucoup d'entre vous utilisent des modules de fournisseur DNS pour résoudre les problèmes DNS ACME ou pour activer le DNS dynamique. Ils implémentent des interfaces définies par libdns pour obtenir, définir, ajouter et supprimer des enregistrements DNS. Après 5 ans d'expérience en production, y compris les leçons apprises avec ECH, les libdns API ont été mises à jour et la version bêta de 1.0 a été étiquetée. Les packages des fournisseurs DNS devront mettre à jour leur code pour être compatibles, ce qui contribuera à garantir la stabilité et une sémantique bien définie pour l'avenir. Plusieurs packages ont déjà été mis à jour ou sont en cours de mise à jour (cloudflare, rfc2136 et desec pour n'en citer que quelques-uns).
  • Configuration globale dns : Maintenant que plusieurs composants de la configuration de Caddy peuvent affecter les enregistrements DNS (défis ACME, publication ECH, etc.), il existe une nouvelle option globale dns qui peut être utilisée pour spécifier la configuration de votre fournisseur DNS en un seul endroit. Cela empêche la répétition des informations d'identification pour les serveurs dont tous les domaines sont gérés par un seul fournisseur DNS. Merci aux nombreux contributeurs qui ont contribué à rendre cela possible ! :tada: :partying_face: :champagne: :avertissement : Bien que nous prenions traditionnellement en charge les 2 dernières versions mineures de Go pour s'adapter à certaines politiques de distribution/gestionnaire de packages, nous ne prenons désormais en charge que la dernière version mineure de Go. Les avantages en matière de confidentialité et de sécurité ajoutés dans les nouvelles versions de Go (comme la cryptographie post-quantique) méritent d'être mis à la disposition de tous dès que possible, plutôt que de retenir l'ensemble de la base d'utilisateurs ou de maintenir plusieurs configurations de compilation de code.

Détails cryptés de ClientHello (ECH)

(Ceci est un bref aperçu. Nous vous recommandons de lire [la documentation complète] (https://caddyserver.com/docs/automatic-https#encrypted-clienthello-ech).) En règle générale, les noms de serveur (noms de domaine ou « SNI ») sont envoyés en clair ClientHello lors de l'établissement de connexions TLS. Avec ECH, le vrai nom du serveur est crypté (et encapsulé) par un ClientHello "externe" qui a un SNI générique de votre choix. Avec de nombreux sites sur le même serveur partageant le même SNI externe, clients et le serveur bénéficient d'une plus grande confidentialité liée aux noms de domaine. Caddy implémente ECH entièrement automatisé, ce qui signifie qu'il génère (et [bientôt] (https://github.com/golang/go/issues/71920), effectue une rotation), publie et sert des configurations ECH simplement en spécifiant un fournisseur DNS et le nom de domaine externe/public à utiliser. ECH entièrement automatisé nécessite un module DNS intégré à votre binaire Caddy. Pour qu'un client, ​​tel qu'un navigateur, sache qu'il peut utiliser ECH et quels paramètres utiliser, la configuration ECH du serveur doit être publiée. Cette configuration inclut le nom public, les paramètres cryptographiques et une clé publique pour chiffrer le ClientHello interne. Par convention, les navigateurs lisent l'enregistrement DNS standardisé de type HTTPS contenant une SvcParamKey ech. Caddy définit cet enregistrement DNS pour tous les domaines protégés, mais il a besoin que le module de fournisseur DNS soit branché et configuré pour ce faire. Si vous utilisez déjà le challenge DNS ACME, vous devriez déjà avoir un fournisseur DNS branché. Si vous préférez construire Caddy à partir des sources avec un module DNS, c'est simple avec xcaddy, par exemple : $ xcaddy build --with github.com/caddy-dns/cloudflare La configuration minimale requise pour activer ClientHello est également la configuration recommandée, car elle maximise les avantages en matière de confidentialité dans la plupart des situations. Vous avez juste besoin de l'option globale ech et d'un fournisseur DNS spécifié. Voici un exemple utilisant Cloudflare comme serveur de noms : Fichier Caddy :

{
	debug  # not required; recommended while testing
	dns cloudflare {env.CLOUDFLARE_API_KEY}
	ech ech.example.net
}

example.com {
	respond "Hello there!"
}

Cela protège tous vos sites (example.com dans ce cas) derrière le nom public de ech.example.net. (Comme autre exemple, Cloudflare utilise cloudflare-ech.com pour tous les sites qu'il dessert. Nous vous recommandons de choisir un seul domaine public et de l'utiliser pour protéger tous vos sites.) Le nom externe/public que vous choisissez doit pointer vers votre serveur. Caddy obtiendra un certificat pour ce nom afin de faciliter des connexions sûres et fiables pour les clients en cas de besoin. Sans certificat, les clients peuvent être obligés de se connecter de manière non sécurisée, voire ne pas se connecter du tout, dans certains cas, ce qui non seulement les rend vulnérables, mais risque également d'exposer les noms des sites de votre serveur. Caddy utilise ensuite le fournisseur DNS spécifié pour publier la ou les configurations ECH pour vos différents noms de sites. Il crée (ou augmente) des enregistrements de type HTTPS pour les domaines de vos sites (et non votre nom public ECH). Notez que les modules du fournisseur DNS sont gérés indépendamment et peuvent ne pas avoir été testés pour leur compatibilité avec les enregistrements de type HTTPS. Veuillez contacter les responsables de votre module si vous rencontrez des problèmes. Si vous avez des besoins de configuration plus avancés, vous pouvez utiliser la configuration JSON (plus de détails à venir ; pour l'instant, voir #6862 ou regardez le code source ; ou utiliser caddy adapt pour convertir un Caddyfile en JSON).

Test et vérification du ClientBonjour chiffré

Assurez-vous d'abord que Caddy fonctionne correctement avec ECH activé (et un module DNS) dans la configuration. Vous devriez voir des journaux indiquant qu'il génère une configuration ECH et la publie sur votre (vos) nom(s) de domaine. Vous devrez utiliser un client prenant en charge ECH. Certaines versions personnalisées de curl le font, ainsi que Firefox et les navigateurs modernes basés sur Chrome, mais vous devez d'abord activer DNS-over-HTTPS ou DNS-over-TLS (puisque, évidemment, interroger DNS en clair pour un nom de domaine protégé exposera le domaine et annulera l'objectif d'ECH). Si vous réutilisez un nom de domaine existant, videz votre cache DNS. Firefox a un moyen de le faire pour son cache sur about:networking#dns. Une fois que vous disposez d'un client approprié, utilisez Wireshark pour capturer les paquets réseau lorsque vous chargez votre site. Vous devriez voir uniquement le nom externe/public sous forme de valeurs SNI (ServerName Indicator) dans la capture de paquets. Si à tout moment vous voyez le vrai nom du site, ECH ne fonctionne pas correctement. Il peut s'agir d'un problème de client ou de serveur. Avant de signaler un bug, essayez d'abord de l'identifier comme un problème de serveur. Mais signalez certainement les bugs du serveur ! Merci! (Notez qu'ECH n'est pas automatiquement publié pour les domaines CNAME et que le domaine doit déjà avoir un enregistrement dans la zone.)
