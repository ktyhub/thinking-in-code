agent-lightning v0.3.0

Agent-lightning v0.3.0 est une version majeure qui introduit plusieurs nouvelles fonctionnalités et corrections de bugs. Cette version est le fruit d'un effort de collaboration entre les équipes principales d'Agent-Lightning et la communauté. Merci à tous les contributeurs qui ont rendu cette version possible.

Faits saillants

  • Intégration Tinker : prend en charge Tinker comme backend alternatif pour l'apprentissage par renforcement (#226 #245 #264 #269 #327). Voir exemple de code, blog 1 et blog 2.
  • Intégration Azure OpenAI : prise en charge d'Azure OpenAI en tant que backend pour l'inférence LLM et le réglage fin supervisé (#256 #327). Exemple de code.
  • Le Lightning Store basé sur MongoDB est ajouté comme backend alternatif pour Lightning Store (#323). Documentation.
  • Package Contrib : ajoutez un package de contribution pour les projets communautaires. Search-R1 est intégré en tant que recette de contribution. Plus à venir. (#239 #396 #410 #412 #417).
  • RESTful API : stabilisez et documentez RESTful API pour Lightning Store (#241 #275). Documentation.
  • Conventions sémantiques OTel spécialement conçues pour les domaines d'optimisation des agents (#340). Documentation.
  • [Aperçu] Le tableau de bord Agent-Lightning est maintenant disponible (#288 #289 #291 #296 #371 #375). Il s'agit de l'application Web officielle permettant d'inspecter et de déboguer les expériences Agent-Lightning. Voir les détails [ici] (https://microsoft.github.io/agent-lightning/0.3.0/tutorials/debug/).
  • [Aperçu] Exemple multimodalité mettant en vedette VERL et un agent LangGraph sur l'ensemble de données ChartQA (#379). Exemple de code.
  • [Aperçu] Intégrez Claude Code en tant que LitAgent et soutenez la formation sur SWE-Bench (#332 #346 #348). Exemple de code.
  • [Aperçu] Weave tracer en remplacement du traceur AgentOps (#277 #411 #420 #423). Documentation.
  • [Aperçu] Agrégation de niveaux de trajectoire pour une formation plus efficace avec VERL. Voir blog et documentation.

## Analyse de référence du magasin

Dans cette version, le cœur du Lightning Store a été repensé pour une efficacité et une évolutivité nettement supérieures (#315 #318 #328 #342 #344 #356 #380 #388 #418 #421). Les résultats de référence ci-dessous démontrent l'impact : avec un grand nombre d'exécuteurs simultanés, v0.3.0 offre un débit jusqu'à 15 fois supérieur à celui de v0.2.2.

| Débit (#déploiement/s) | v0.2.2 | v0.3.0 (en mémoire) | v0.3.0 (Mongo) | | :---- | :---- | :---- | :---- | | Minimal (lot, #runner=32, #turns=6) | 8.73 | 9.06 | 8.71 | | Moyen (lot, #runners=100, #turns=10) | 12.03 | 23.26 | 32.79 | | Moyen-haut (lot, #runners=300, #turns=6) | 10.61 | 24.42 | 40.24 | | Grand (lot, #runners=1000, #turns=3) | 3.36 | 14.60 | 50.05 | | Longue file d'attente (file d'attente, #runners=256, #turns=4) | 7.42 | 30.86 | 57.01 | | Trace lourde (file d'attente, #runners=512, #turns=20) | 5.93 | 13.28 | 29.41 |

Remarques :

  1. Les tests de performance ont été exécutés sur une seule machine virtuelle Azure Standard_D32as_v4 (tests de trace volumineux et lourds utilisés Standard_D64ads_v5), exécutés via les actions GitHub.
  2. Deux modèles d'algorithme sont évalués : le modèle par lots soumet un groupe de déploiements et attend que tous soient terminés avant de démarrer le groupe suivant, tandis que le modèle de file d'attente maintient un nombre défini de déploiements en vol, en en soumettant de nouveaux dès que la capacité se libère. Les détails de configuration sont disponibles [ici] (https://github.com/microsoft/agent-lightning/blob/v0.3.0/.github/workflows/benchmark.yml).
  3. Le nombre de tours est directement proportionnel au nombre de travées générées par chaque déploiement.
