DeepTutor v1.3.2

DeepTutor v1.3.2 Release Note

Date de sortie : 2026.04.29 v1.3.2 est une version de stabilité ciblée après v1.3.1. Il resserre l'intégration contrat de point final, permet à LlamaIndex RAG de récupérer plus proprement des fichiers périmés ou index non valides et empêche la sortie du bloc-notes du modèle de raisonnement de fuir dans la mémoire à long terme.

Faits saillants

URL de point de terminaison d'intégration transparente

La configuration de l'intégration est désormais explicite quant à l'URL exacte que DeepTutor appellera. Cela supprime l'ambiguïté cachée « URL de base par rapport à l'URL du point de terminaison » qui pourrait créer un problème. Un test de paramètres réussi se comporte différemment d'une réindexation de la base de connaissances.

  • Les paramètres affichent désormais l'URL du point de terminaison pour les intégrations - la page des paramètres Web étiquette les URL intégrant des URL en tant qu'URL de point de terminaison et explique que DeepTutor publie sur l'URL visible exactement, sans ajouter /embeddings ou /api/embed à demande de temps.
  • Les valeurs par défaut du fournisseur sont des points de terminaison complets - OpenAI, OpenRouter, Jina, vLLM/LM Studio et SiliconFlow sont par défaut /embeddings ; Ollama par défaut /api/embed; Cohere est par défaut /embed ; DashScope conserve son natif point de terminaison d’intégration multimodale.
  • Les URL de base héritées sont migrées en toute sécurité - Profils d'intégration enregistrés à l'aide des bases à l'ancienne telles que https://api.openai.com/v1, https://openrouter.ai/api/v1 ou http://localhost:11434 sont normalisés à le formulaire de point de terminaison complet et conservé dans le catalogue de modèles. Personnalisé Les URL compatibles OpenAI restent intactes.
  • Les points de terminaison mal configurés échouent prématurément - l'intégration client est désormais rejetée URL de fournisseurs connus qui pointent vers un chemin racine/base au lieu du chemin réel intégration du point de terminaison, avec un message exploitable avant le début de l'indexation.
  • L'intégration OpenRouter utilise l'URL exacte HTTP - Fournisseurs d'intégration publics non un itinéraire plus long à travers le comportement d'ajout de chemin caché de l'OpenAI SDK. custom_openai_sdk reste disponible pour les configurations héritées, mais est masqué la liste déroulante du fournisseur de paramètres.
  • Les diagnostics de test de connexion correspondent au comportement d'exécution - intégration des tests maintenant rapport "POSTé exactement comme indiqué dans les paramètres", correspondant au comportement de l'adaptateur utilisé par l'indexation et la récupération RAG.

RAG Réindexation et résilience à la récupération

Le pipeline LlamaIndex actualise désormais l'état d'intégration de manière plus agressive et transforme les vecteurs persistants invalides en conseils de réindexation clairs au lieu de bruts Erreurs Python ou NumPy. - Les pipelines mis en cache récupèrent les modifications des paramètres - initialisation, recherche et les chemins d'ajout incrémentiel reconfigurent LlamaIndex avant utilisation, donc une longue durée de vie Le pipeline ne continue pas à intégrer les paramètres de modèle, de dimension ou de point de terminaison à partir de une ancienne session Paramètres.

  • L'intégration de clients est actualisée lorsque la configuration change - l'intégration partagée client est recréé lorsque la configuration d'exécution résolue change et que le L'adaptateur LlamaIndex CustomEmbedding prend les empreintes digitales de la configuration active avant réutilisation d'un client mis en cache.
  • Les vecteurs d'index persistants sont validés avant la récupération - LlamaIndex Le stockage vérifie désormais le magasin de vecteurs enregistré pour les valeurs nulles, non numériques, non finies, vecteurs abandonnés ou incohérents avant d’exécuter une recherche de similarité.
  • Les index invalides renvoient un indice de réindexation - échecs connus tels que unsupported operand type(s) for *: 'NoneType' and 'float', forme vectorielle les incompatibilités et les vecteurs persistants non valides nouvellement détectés reviennent désormais needs_reindex: true avec une explication destinée à l'utilisateur.
  • Les contrôles de connectivité intégrés utilisent le même chemin de validation - le Le test de fumée pré-index valide la sortie du fournisseur avec le même validateur de lots utilisé lors de l’indexation et de la récupération.
  • Les journaux d'erreurs RAG sont plus silencieux lorsque le correctif est connu - classé invalide les échecs d'intégration/d'indexation sont enregistrés sous forme d'avertissements exploitables au lieu d'être bruyants retraçages complets.

Nettoyage de la mémoire pour les modèles de réflexion

L'actualisation de la mémoire supprime désormais les blocs de raisonnement privés avant qu'ils ne puissent devenir mémoire utilisateur durable.

  • Les balises de réflexion sont supprimées avant les écritures - Les réécritures de profil et de résumé sont exécutées via l'assistant partagé clean_thinking_tags() après le nettoyage du code-fence, donc Les blocs <think> / <thinking> des modèles de raisonnement ne sont pas enregistrés dans PROFILE.md ou SUMMARY.md.
  • Les fichiers mémoire existants s'auto-réparent lors de la lecture - s'il s'agit d'un fichier mémoire plus ancien contient déjà des balises de réflexion fermées ou non fermées, la lecture de l'instantané nettoie le contenu et réécrit la version réparée sur le disque lorsque cela est possible.
  • Les modifications manuelles de la mémoire utilisent le même nettoyage - les écritures directes en mémoire réussissent également via le nettoyeur, en gardant les modifications, les actualisations et les lectures d'exécution de l'interface utilisateur alignées.

Paramètres et polissage du runtime

  • Les choix du fournisseur d'intégration sont moins déroutants - Les paramètres n'offrent plus l'ancien fournisseur custom_openai_sdk dans la liste déroulante publique, tout en existant les profils enregistrés continuent à être résolus pour une compatibilité ascendante.
  • La normalisation du catalogue de modèles est conservée - Les chargements du catalogue sont désormais enregistrés lorsque la normalisation modifie les ID de profil/modèle actifs ou l'intégration des URL de point de terminaison, empêchant la même migration de se répéter à chaque démarrage.
  • Les erreurs d'intégration compatibles OpenAI sont plus claires - non-JSON ou HTML l'intégration des réponses pointe désormais vers de mauvaises paires point de terminaison/modèle sans suggérant à tort une seule cause spécifique à la passerelle.
  • Les appels Deep Solve ReAct sont à nouveau alignés - la boucle du solveur n'est plus transmet un mot clé attachments obsolète dans SolverAgent.process(), évitant ainsi un runtime TypeError tout en conservant le transfert des pièces jointes sur le planificateur et replanifier les appels là où cela est pris en charge. ## Tests
  • Ajout d'une couverture de migration des points de terminaison pour OpenAI, OpenRouter, Ollama et personnalisé intégration de profils.
  • Ajout de la couverture Paramètres API pour les choix complets de fournisseurs de points de terminaison et masqués custom_openai_sdk.
  • Ajout de l'intégration de la couverture client pour la validation des points de terminaison, le HTTP brut d'OpenRouter chemin de l'adaptateur, actualisation client lors des modifications de configuration et transparence exacte de l'URL.
  • Ajout de la couverture LlamaIndex pour l'intégration obsolète-client rafraîchissement, répété reconfiguration des paramètres, détection de vecteur persistant non valide et réindexation conseils pour les index invalides.
  • Ajout d'une couverture mémoire pour les balises de réflexion fermées et non fermées, ainsi que réparation de fichiers de mémoire existants lors des lectures.
  • Réalisation de tests de capacité Deep Solve/RAG ciblés couvrant le câblage d'exécution du solveur après le correctif de l'argument obsolète attachments.

Notes de mise à niveau

  • Les URL intégrées dans les paramètres doivent désormais être des URL de point de terminaison complètes. Existant connu les profils de fournisseur sont migrés automatiquement, mais les passerelles personnalisées doivent être examinés manuellement s’ils utilisent des chemins non standard.
  • Si la recherche dans la base de connaissances signale toujours des vecteurs d'intégration non valides, réindexez le Base de connaissances affectée après avoir confirmé le fournisseur d'intégration actif, le modèle, la dimension, et l'URL du point de terminaison.
  • Les fichiers mémoire contenant d'anciens blocs <think> seront nettoyés lors du prochain La page mémoire ou le service mémoire les lit ; cette lecture peut mettre à jour le sous-jacent Fichier PROFILE.md ou SUMMARY.md pour conserver la version nettoyée.
