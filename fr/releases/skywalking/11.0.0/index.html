Projet

  • Déplacez la machinerie de chargement de classe DSL sous core/dsl. core/classloader ne contenait que les types DSL — RuleClassLoader, DSLClassLoaderManager, ClassLoaderGc, UnloadProbePayload et BytecodeClassDefiner — il s'appelle donc désormais core/dsl/classloader, et Catalog passe à core/dsl car une taxonomie de fichier de règles n'est pas un problème de chargement de classe. Trois copies de la répartition « définir une classe générée dans le bon chargeur » (MAL, LAL, MeterSystem) se transforment en un BytecodeClassDefiner.define statique, ce qui donne également au JDK 17 --add-opens la logique d'un emplacement au lieu de quatre. Trois des quatre copies de la recherche du répertoire de vidage de classe générée deviennent DslGeneratedFileWriter.resolveClassDumpDir ; OAL conserve le sien, car son indicateur de débogage est réglable indépendamment de la variable d'environnement et deux tests s'appuient sur cela. Aucun changement de comportement.
  • Étendez l'administrateur GET /inspect/entities API pour inspecter une métrique conservée par n'importe quel OAP, même celui que ce nœud ne définit pas localement. Lorsque la métrique est inconnue du registre local, l'appelant fournit valueColumn + valueType et le backend de stockage résout l'index/table/groupe physique à partir de sa propre configuration en cours d'exécution (aucun schéma de base de données/métadonnées de table lu) : ES utilise l'index fusionné metrics-all + le discriminateur metric_table, JDBC sonde les tables de fonctions du nœud par le discriminateur table_name et BanyanDB synthétise un schéma de mesure en lecture seule. La portée n'est plus nécessaire — le entity_id est décodé structurellement (service/2ème niveau/relations) avec une feuille générique name. Les métriques définies localement conservent les noms de champs, la portée et mqeEntity exacts comme auparavant.
  • Ajoutez l'administrateur POST /inspect/values API — lisez la série de valeurs d'une métrique conservée par un autre OAP (celui que ce nœud ne définit pas localement) en fournissant son {valueColumn, valueType}. Le véritable moteur MQE s'exécute sur une superposition InspectQueryContext au niveau de la requête (provide-if-absent — le catalogue local gagne toujours) qui donne à la métrique étrangère l'apparence d'être enregistrée dans chaque chemin de lecture : ValueColumnMetadata résout sa colonne de valeur/type/portée, et les registres d'emplacement de stockage résolvent son emplacement (MetadataRegistry synthétise un schéma de mesure BanyanDB, IndexController résout l'index ES metrics-all, TableHelper sonde les tables de fonctions JDBC), de sorte que la lecture renvoie le MQE ExpressionResult natif sans casse spéciale par DAO. Administrateur uniquement (une lecture forcée que cet OAP ne peut pas valider) ; non reflété sur la surface publique REST / GraphQL. Voir le Inspecter API.
  • Supprimez la conversion alarme-événement toujours active (EventHookCallback). Une alarme déclenchée n'est plus synthétisée dans le pipeline d'événements en tant qu'événement Alarm/AlarmRecovery ; les événements proviennent désormais uniquement de sources d'événements réelles (agents, SkyWalking CLI, Kubernetes Event Exporter). Les alarmes restent disponibles via le magasin d'alarmes (getAlarm/queryAlarms) et les crochets d'alarme configurés. Cela supprime un « événement connu » documenté et supprime 1 à 2 enregistrements d'événements synthétiques par incendie d'alarme.
  • TLS pour tous les serveurs HTTP/REST OAP, avec rechargement à chaud du certificat. Ajoute la structure de configuration restSSLEnabled / restSSLKeyPath / restSSLCertChainPath à chaque serveur HTTP OAP — REST principal, serveur de partage, administrateur, PromQL, LogQL, TraceQL et requête/récepteur Zipkin — chacun avec ses propres variables d'environnement dédiées (SW_CORE_REST_SSL_*, SW_RECEIVER_SHARING_REST_SSL_*, SW_ADMIN_SERVER_REST_SSL_*, SW_PROMQL_REST_SSL_*, SW_LOGQL_REST_SSL_*, SW_TRACEQL_REST_SSL_*, SW_QUERY_ZIPKIN_REST_SSL_*, SW_RECEIVER_ZIPKIN_REST_SSL_*). L'Armeria HTTPServer partagé recharge la paire de clés à partir du disque lors de la rotation (via TlsProvider.ofScheduled) afin que les certificats actualisés soient récupérés sans redémarrer l'OAP, ce qui correspond au comportement de rechargement à chaud SSL existant du gRPC. HTTP TLS est uniquement côté serveur (pas de mTLS).
  • Nouvelle requête queryAlarms GraphQL — filtres d'entités/couches/règles pour les alarmes. Ajoute une requête d'alarme complète API aux côtés de l'ancien getAlarm. Le nouveau queryAlarms(condition: AlarmQueryCondition!): Alarms accepte un seul type d'entrée regroupant chaque filtre stocké par l'enregistrement d'alarme : entities: [Entity!] (réutilise la forme MQE Entity — épingle à des services/instances/points de terminaison/processus spécifiques ou à leurs relations, comparé à l'alarme id0 OU id1) ; layer: String (filtrage par couche de l'entité alarmée — correspondance unique, puisque les lignes d'alarme persistent sur une couche) ; ruleNames: [String!] (filtre par lequel la règle d'alarme s'est déclenchée) ; plus keyword, tags, duration, paging. L'ancien getAlarm est marqué @deprecated mais est toujours acheminé vers le même DAO - pas de casse client. Ajouts backend : une nouvelle colonne layer sur AlarmRecord remplie au moment de l'alarme via MetadataQueryService.getService(serviceId).getLayers() ; les colonnes id0/id1 existantes sont passées de storageOnly = true à indexées afin que le filtre d'entité soit transféré vers le stockage. IAlarmQueryDAO.queryAlarms(condition, limit, from) est une nouvelle méthode abstraite : les backends de stockage tiers échouent à la compilation s'ils manquent le remplacement (modèle SWIP-14). Les trois backends fournis l'implémentent : BanyanDB / Elasticsearch / JDBC. Sémantique de l'opérateur : (1) Les entités de relation correspondent exactement. La transmission de {scope: ServiceRelation, serviceName: A, destServiceName: B} correspond uniquement à l'alarme où id0=serviceId(A) AND id1=serviceId(B), et non à toute alarme qui touche A ou B de chaque côté. Les requêtes plus larges "tout ce qui implique A" devraient plutôt transmettre l'entité individuelle sans relation ({scope: Service, serviceName: A} - qui s'étend à id0=A OR id1=A). (2) Une seule couche par ligne d'alarme. La colonne persistante stocke UNE couche (la première entrée de la liste des couches résolues de l'entité — la source en premier pour les relations). Un service dans [GENERAL, K8S_SERVICE] dont les métadonnées sont d'abord résolues en GENERAL est classé sous GENERAL ; interroger layer: "K8S_SERVICE" le manquera. Remarque sur la migration de l'opérateur : les lignes d'alarme existantes avant la mise à niveau continuent d'être filtrables par les anciens champs getAlarm ; les nouveaux filtres d'entité/couche/règle dans queryAlarms s'appliquent uniquement aux alarmes écrites après la mise à niveau (les index de stockage existants ne font pas la transition index: false → true en place ; les nouveaux index générés quotidiennement récupèrent les colonnes indexées). Les ajouts de schéma ne sont pas bloquants : le bootstrap ignore silencieusement les modifications des attributs de colonne sur les index existants.

Les modèles d'interface utilisateur sont désormais créés et mis à jour via la nouvelle surface REST /ui-management/templates/* sur le serveur d'administration (voir ci-dessous). Toutes les mutations et requêtes GraphQL liées à l'interface utilisateur (UIConfigurationManagement : addTemplate, changeTemplate, disableTemplate, getAllTemplates, getDashboardConfiguration, getMenuItems) sont retirées du schéma GraphQL public, ainsi que l'indicateur SW_ENABLE_UPDATE_UI_TEMPLATE. Le backend OAP ne stocke ni ne sert plus le menu de la barre latérale : UIMenuManagementService, UIMenuManagementDAO, UIMenu, MenuItem, et les outils de stockage sont tous supprimés ; Horizon UI possède le menu client-side et utilise listServices(layer:...) pour le contrôle dynamique « la couche a des services ». Tous les points de terminaison d'état/de débogage (/status/*, /debugging/*) sont également transférés vers l'administrateur uniquement : la double liaison publique REST pour l'état est supprimée dans la même version.

  • Nouveau module admin-server — hôte partagé pour les API d'administrateur/d'écriture à la demande. Fonctionne sur deux ports : une surface HTTP REST (17128 par défaut) pour les points de terminaison côté opérateur, et un bus gRPC interne à l'administrateur (17129 par défaut) pour les RPC de cluster peer-to-peer (suspension / reprise / règle d'exécution). Transférer ; installation de débogage DSL/collecte/arrêt/stopByClientId). Le bus interne à l'administrateur est un transport dédié distinct du port gRPC de l'agent/cluster public (core.gRPCPort, 11800 par défaut), de sorte que les RPC d'administrateur privilégiés restent en dehors du rayon de souffle du réseau d'agents — les opérateurs lient gRPCHost à une interface peer-to-peer privée uniquement. Le plug-in de règles d'exécution et le nouveau DSL Debug API (ci-dessous) sont montés sur cet hôte partagé. Activé par défaut afin que le module de fonctionnalité d'état soit accessible immédiatement ; l'hôte se lie à 0.0.0.0:17128 et n'a pas d'authentification intégrée et doit être protégé par passerelle avec des listes vertes IP, jamais exposé à l'Internet public (voir l'avis de sécurité Admin API). Réglez SW_ADMIN_SERVER= (vide) pour le désactiver entièrement. Le bloc de configuration des règles d'exécution perd ses clés restHost/restPort/restContextPath/restIdleTimeOut/restAcceptQueueSize/httpMaxRequestHeaderSize (et les variables d'environnement SW_RECEIVER_RUNTIME_RULE_REST_* correspondantes) ; les boutons au niveau de l'hôte se déplacent sous le nouveau bloc admin-server (SW_ADMIN_SERVER_HOST / SW_ADMIN_SERVER_PORT / SW_ADMIN_SERVER_GRPC_HOST / SW_ADMIN_SERVER_GRPC_PORT / SW_ADMIN_SERVER_INTERNAL_COMM_TIMEOUT etc.).
  • Mise à jour à chaud des règles d'exécution pour MAL et LAL. Les opérateurs peuvent désormais envoyer les modifications des règles de métrique (MAL) et de journal (LAL) sans redémarrer OAP. Un push vers un nouveau point de terminaison d'administrateur conserve la règle dans le backend de stockage configuré, et chaque nœud du cluster converge vers le nouveau contenu dans un délai d'environ 30 secondes. Flux de travail courants :
    • addOrUpdate — crée ou remplace une règle. Le corps est le YAML brut que vous livreriez normalement avec les fichiers de règles statiques d'OAP. Renvoie 200 une fois que la règle est appliquée localement et persistante ; les pairs le récupèrent lors de leur prochaine analyse périodique (≤ 30 s).
    • inactivate — mise en pause douce d'une règle. L'OAP cesse d'émettre des métriques pour cette règle mais la mesure backend (et son historique) est préservée, donc un addOrUpdate ultérieur vers le même (catalog, name) est sans perte. L'intention « off » est durable lors des redémarrages ; les règles regroupées sur le disque ne ressuscitent pas automatiquement lorsqu'un inactivate supprime le remplacement d'exécution. C'est le moyen sûr de mettre une règle hors ligne.
  • delete — supprime une ligne INACTIVE (les règles actives renvoient 409 requires_inactivate_first). Pour les règles d'exécution uniquement sans YAML groupé sur le disque, la ligne est supprimée ; la mesure backend (le cas échéant) est laissée en place en tant qu'artefact inerte, correspondant à la sémantique de suppression des règles groupées (la suppression d'un YAML de otel-rules/ sur le disque ne supprime pas non plus sa mesure). Pour les règles qui ont un jumeau YAML groupé, delete simple renvoie 409 requires_revert_to_bundled — laisser le bundle prendre en charge silencieusement le (catalog, name) est un changement d'état significatif qui nécessite une décision explicite de l'opérateur. Réémettez avec ?mode=revertToBundled pour revenir au bundle : ce chemin exécute le pipeline de changement de schéma (réhydrate le DSL d'exécution localement, puis applique le YAML groupé via le pipeline d'application standard afin que le delta d'exécution → groupé supprime les métriques d'exécution uniquement, enregistre les métriques groupées uniquement et réutilise les métriques partagées groupées à la forme correspondante) avant de supprimer la ligne. Renvoie 400 no_bundled_twin lorsque ?mode=revertToBundled est utilisé sans YAML fourni sur le disque.
    • get / bundled / list / dump — points de terminaison côté lecture pour récupérer le YAML d'une seule règle (avec prise en charge de ETag ; ?source=bundled lit le YAML fourni sur disque même lorsqu'un remplacement d'exécution est en place), répertoriant la superposition d'exécution groupée par catalogue, inspectant État des règles à l'échelle du cluster sous la forme d'une enveloppe JSON ({generatedAt, loaderStats, rules} — chaque ligne contient status/localState/loaderKind/bundled/bundledContentHash afin qu'une interface utilisateur puisse restituer les badges de remplacement sans deuxième aller-retour) et exporter toutes les règles sous forme de tar.gz pour la sauvegarde/DR. Les mises à jour à chaud survivent au redémarrage d'OAP : au démarrage, OAP fusionne les fichiers de règles groupés avec les règles d'exécution persistantes, de sorte que le cluster ne régresse jamais silencieusement vers les valeurs par défaut groupées. Toutes les écritures d'administrateur pour un cluster de règles d'exécution sont sérialisées sur un seul OAP "principal" (premier homologue trié déterministe, pas d'élection de leader) - les nœuds non principaux qui reçoivent une écriture HTTP la transmettent de manière transparente au principal via le bus gRPC interne à l'administrateur, de sorte qu'un équilibreur de charge L7 devant le port d'administration peut acheminer n'importe quelle demande d'opérateur vers n'importe quel OAP. La convergence du cluster lors du tick d'actualisation périodique est configurable via receiver-runtime-rule.refreshRulesPeriod (30 s par défaut). Le point de terminaison est désactivé par défaut et écoute sur le port 17128 (HTTP) lorsqu'il est activé. Il n'a pas d'authentification intégrée : les opérateurs doivent le protéger par passerelle avec des listes d'autorisation IP et ne jamais l'exposer à l'Internet public. Les routes sont montées sur le nouvel hôte HTTP admin-server, qui est activé par défaut ; activez la fonctionnalité de règle d'exécution avec SW_RECEIVER_RUNTIME_RULE=default.
  • Débogueur en direct pour MAL / LAL / OAL — implémente SWIP-13 Live Debugger pour MAL / LAL / OAL. Débogueur d'exécution basé sur des exemples qui capture les entrées/sorties par étape pendant que les trois DSL traitent l'ingestion en direct. Le coût du chemin d'inactivité correspond à une lecture de code volatile par site d'appel de sonde que JIT élimine après l'échauffement ; les sessions actives sont distribuées à chaque homologue du cluster via le bus gRPC interne à l'administrateur afin que chaque homologue capture sa propre tranche. La distribution est LB-safe : n'importe quel nœud peut servir n'importe quel verbe (POST crée sessionId sur le nœud de réception, diffuse l'installation aux pairs, renvoie 404 rule_not_found uniquement lorsqu'aucun nœud ne possède la règle), donc un équilibreur de charge L7 devant le port d'administration achemine les demandes de l'opérateur librement. Se monte sur l'hôte admin-server partagé (/dsl-debugging/* pour le plan de contrôle de session, /runtime/oal/* pour le sélecteur de règles OAL). Désactivé par défaut ; activer avec SW_DSL_DEBUGGING=default (le serveur d'administration lui-même est activé par défaut). injectionEnabled est un commutateur de codegen au démarrage par défaut true : une fois le module activé, les sondes se déclenchent et les sessions enregistrent des échantillons ; définissez false uniquement si la surface REST est souhaitée mais qu'aucune surcharge de sonde côté codegen n'est acceptable. Les limites par session appliquent des plafonds stricts (recordCap ≤ 10 000, retentionMillis ≤ 1 heure) — les requêtes hors plage renvoient 400 invalid_limits. Les sessions LAL acceptent un indicateur granularity=block|statement par session : le mode bloc capture les étapes analyseur/extracteur/récepteur ; Le mode instruction enregistre en outre une entrée line par instruction d'extracteur individuelle, portant le numéro de ligne source et le texte DSL textuel afin que l'interface utilisateur puisse mettre en évidence quelle instruction a été déclenchée. Les captures MAL restituent la carte SampleFamily survivante du filtre au niveau fichier ({"families": N, "items": [...]}), de sorte que les expressions multimétriques affichent un rétrécissement du filtre inter-familles dans la charge utile capturée. Les charges utiles de capture incluent les corps de journaux bruts et les cartes analysées : traitez le port d'administration comme une infrastructure authentifiée conformément à l'[avis de sécurité Admin API] (../setup/backend/admin-api/readme.md). Références par opérateur DSL : MAL, OAL, LAL.

Étant donné que la configuration de BanyanDB a été déplacée vers un fichier séparé dans 10.2.0, un déploiement de BanyanDB montrait auparavant un bloc storage.banyandb vide dans le dump ; ses valeurs post-résolution d'environnement sont désormais fusionnées dans la même réponse sous storage.banyandb.* (règles TopN sous storage.banyandb.topN.*), masquées par la même liste de mots-clés secrets, via un SPI générique ConfigDumpExtension sur ServerStatusService que tout module chargeant la configuration à partir d'un fichier secondaire peut implémenter.
  • Correctif : une requête MQE top_n(metric, N, order, attrX='value') dont l'attribut n'est pas une colonne de la métrique cible renvoie désormais une erreur MQE descriptive au lieu d'un stockage brut IOException affiché comme Internal IO exception, query metrics error.. Les colonnes d'attributs (attr0..attrN) existent uniquement sur les métriques décorées (service_* / endpoint_* / kubernetes_service_*, définies sur le nom de la couche via OAL .decorator(...)) et la base de compteur MAL ; les métriques telles que les relations ou l'accès à la base de données/au cache/mq n'en comportent aucune, donc la transmission d'une condition d'attribut a déjà atteint le moteur de stockage avec une balise qu'il ne définit pas et y a échoué. MQEVisitor valide désormais chaque clé d'attribut par rapport aux colonnes interrogeables enregistrées de la métrique avant l'appel de stockage et déclenche IllegalExpressionException (en nommant l'attribut et la métrique) lorsqu'elle est absente.
  • Migrez toutes les requêtes de lecture de stockage BanyanDB du générateur de requêtes typé API vers BydbQL.
  • Correctif : les requêtes BanyanDB ne sont plus tronquées silencieusement au niveau de la limite de ligne implicite du moteur de stockage. BanyanDB applique sa propre limite par défaut à toute requête qui n'en comporte aucune (100 lignes pour les mesures, 20 pour les flux/traces) et l'applique après GROUP BY, de sorte qu'un ensemble de résultats trop long est écourté plutôt que rejeté. OAP n'a jamais envoyé de limite sur plusieurs chemins de lecture, donc une requête de métriques a renvoyé au maximum 100 points de données, quelle que soit la plage demandée : une lecture par pas de 4 heures n'a rendu que ses 100 premières minutes et le reste s'est affiché comme vide, même si DurationUtils autorise jusqu'à 500 pas. Le même capuchon a raccourci silencieusement les cartes de relations topologiques, les listes de métadonnées d'instance/processus, les instantanés de thread de profilage et les listes de tâches eBPF. Chaque requête BydbQL laisse désormais OAP avec un LIMIT explicite : la lecture des métriques à l'échelle de l'entité envoie le nombre exact de points de durée assemblés (correspondant à la ligne définie par les DAO ES/JDBC récupérés par identifiant), le SELECT TOP ad hoc envoie son propre N, et tout ce qui ne se pagine pas revient au resultWindowMaxSize configuré (10000 par défaut) au lieu du moteur par défaut. Le stockage ES et JDBC n’a jamais été affecté.
  • Prise en charge du pipeline de rétention de trace à l'échelle du groupe de BanyanDB dans bydb.yml. Les groupes trace et zipkinTrace gagnent un bloc pipeline (enabled, enabledEvents, mergeGraceSeconds, finalizeGraceSeconds et une chaîne plugins ordonnée) que OAP pousse sur le groupe BanyanDB en tant que TracePipelineConfig, permettant à un plugin d'échantillonneur de déposer des traces à l'intérieur du nœud de données pendant le compactage en phase chaude - après le stockage, il récupère l'espace déjà écrit et décide par trace entière, contrairement au côté ingestion [échantillonnage de trace côté serveur] (../setup/backend/trace-sampling.md). Désactivé par défaut, car il supprime les traces stockées. Même lorsqu'il est activé, il est inerte à moins que le nœud de données exécute l'image BanyanDB compatible avec le plugin avec l'échantillonneur .so monté - un nœud sans ce support ignore la configuration, et celui qui ne peut pas charger le plugin enregistre une erreur et fusionne sans filtre, donc rien n'est supprimé de manière inattendue. Les deux fenêtres de grâce utilisent -1 pour « hériter de la valeur par défaut du nœud de données » (fusion de 30 s / finalisation de 5 minutes) car le nœud traite toute grâce non positive comme non définie. enabledEvents accepte une chaîne séparée par des virgules afin qu'elle puisse être définie à partir de l'environnement (SW_STORAGE_BANYANDB_TRACE_PIPELINE_ENABLED_EVENTS et sa variante ZIPKIN_) ainsi qu'une liste de blocage YAML ; une valeur vide revient à PIPELINE_EVENT_MERGE, donc PIPELINE_EVENT_FINALIZE ne s'exécute que lorsqu'il est nommé explicitement. Le config de chaque plugin est transmis textuellement en tant que protobuf Struct : les listes et les objets imbriqués (par exemple keepTagRules) survivent désormais au chargeur de configuration et sont sérialisés comme de vrais ListValue/Struct plutôt que d'être aplatis en une chaîne. Notez qu'un flottant écrit comme espace réservé ${ENV:default} atteint toujours le plugin sous forme de chaîne JSON, car le résolveur d'espace réservé partagé ne préserve que String/Integer/Long/Boolean ; les échantillonneurs propriétaires acceptent un numéro cité exactement pour cette raison. Voir Trace Tail Sampling pour savoir comment une trace est jugée, et BanyanDB storage pour les clés de configuration.
  • Correction : une valeur vide dans bydb.yml (key: sans rien après) a interrompu le démarrage OAP avec un NullPointerException opaque de java.util.Properties, qui rejette les valeurs nulles. Le chargeur de configuration BanyanDB ignore désormais les entrées vides et laisse le champ par défaut, ce qui équivaut à omettre la ligne.
  • Acheminez les règles LAL au sein d'une couche en fonction de leur type d'entrée, afin qu'une seule couche puisse héberger des règles sur différentes entrées de proto. Chaque règle compilée porte désormais son type d'entrée effectif (la classe proto vers laquelle ses getters parsed.* sont castés, ou null pour les règles basées sur un analyseur/non typées), et LogFilterListener ignore toute règle dont le type ne correspond pas au journal entrant au lieu d'exécuter toutes les règles de la couche. Cela corrige un ClassCastException latent (capté et enregistré par journal) qui se déclenchait chaque fois qu'un journal MESH d'une forme atteignait une règle compilée pour une autre - par ex. un journal d'accès Envoy TCP ou un LogData de profilage réseau répondant à la règle HTTP envoy-als. Ajoute une règle envoy-als-tcp (inputType: TCPAccessLogEntry) aux côtés du HTTP envoy-als existant ; les deux partagent la couche MESH et chacun ne voit désormais que son propre type d'entrée.
  • Correction du hook d'alarme PagerDuty pour que son point de terminaison d'événements API v2 soit par défaut https://events.pagerduty.com/v2/enqueue.
  • Correction du HttpAlarmCallback enregistrant une transmission d'alarme réussie comme un échec. L'assistant de hook HTTP partagé n'a traité que 200 et 204 comme un succès, de sorte que tout autre 2xx — notamment le 202 Accepted renvoyé par des API d'admission asynchrone tels que les événements API v2 de PagerDuty — a produit send to ... failure. Response code: 202 au niveau ERREUR à chaque alarme délivrée. L'alarme était toujours donnée ; l'entrée du journal était erronée. Le contrôle accepte désormais toute la gamme 2xx, pour tous les crochets d'alarme.
  • Rendre le point de terminaison PagerDuty Events API v2 configurable via un nouveau paramètre facultatif events-api-url sur chaque hook pagerduty, par défaut sur le point de terminaison de la région de service américaine. Un compte dans la région de service de l'UE de PagerDuty peut désormais pointer directement vers https://events.eu.pagerduty.com/v2/enqueue plutôt que de compter sur PagerDuty pour transmettre la demande - et la clé de routage et la charge utile d'alarme d'un compte de la région de l'UE ne transitent plus par la région des États-Unis.
  • Faites passer la version par défaut du serveur compatible BanyanDB API (SW_STORAGE_BANYANDB_COMPATIBLE_SERVER_API_VERSIONS) de 0.10 à 0.11.
