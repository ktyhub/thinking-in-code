Projet

  • Présentation du moteur OAL V2 :
    • Modèles AST immuables pour la sécurité des threads et un comportement prévisible
    • Énumérations de type sécurisé remplaçant les opérateurs de filtre basés sur des chaînes
    • Rapport précis sur l'emplacement des erreurs avec les numéros de fichiers, de lignes et de colonnes
    • Séparation nette entre les phases d'analyse et de génération de code
    • Testabilité améliorée avec des modèles qui peuvent être construits sans analyse
  • Introduction du moteur MAL/LAL/Hierarchy V2 — remplacez le runtime DSL basé sur Groovy par l'analyseur ANTLR4 + la génération de bytecode Javassist :
    • Supprimer la dépendance d'exécution Groovy du backend OAP
    • Compilation rapide au démarrage — les erreurs de syntaxe et de type sont détectées immédiatement au lieu de la première exécution
    • Classes générées thread-safe sans ThreadLocal ou état mutable partagé
    • Modèles AST immuables pour les trois DSL (MAL, LAL, règles de hiérarchie)
    • Le passage de contexte explicite remplace la capture de liaison/fermeture Groovy
    • Le vérificateur de versions croisées v1 (Groovy) et v2 (ANTLR4+Javassist) valide l'équivalence comportementale dans plus de 1 290 expressions
    • Les benchmarks JMH confirment les accélérations d'exécution de la v2 : MAL exécute ~ 6,8x, LAL compile ~ 39x / exécute ~ 2,8x, la hiérarchie s'exécute ~ 2,6 fois plus rapidement que Groovy v1
    • Les noms de classe générés suivent le modèle {yamlFileName}_L{lineNo}_{ruleName} pour tous les DSL (MAL/LAL/Hiérarchie) pour la traçabilité de la trace de la pile
  • Breaking Change — LAL : supprimez les sous-DSL slowSql {} et sampledTrace {} de la grammaire. Ceux-ci sont remplacés par le mécanisme configurable outputType :
    • Définissez outputType au niveau de la règle dans la configuration YAML pour spécifier la classe d'entité de sortie. Utilisez le nom court enregistré par LALOutputBuilder SPI (par exemple, outputType: SlowSQL, outputType: SampledTrace) ou un nom de classe complet comme solution de secours.
    • Les implémentations de LALOutputBuilder sont découvertes via ServiceLoader et exposent une méthode name() pour la résolution de noms courts. Types intégrés : SlowSQL (DatabaseSlowStatementBuilder), SampledTrace (SampledTraceBuilder).
    • Les champs de sortie (par exemple, id, statement, latency) sont désormais des affectations de champs régulières dans le bloc extracteur, et non plus encapsulées dans des blocs sous-DSL.
    • Les champs de sortie personnalisés sont validés par rapport aux paramètres du type de sortie au moment de la compilation.
    • Un bloc sink {} explicite est désormais obligatoire pour que les données soient conservées. Sans sink {}, aucune donnée n'est enregistrée — cela s'applique à toutes les règles LAL, y compris celles utilisant outputType. Dans la version 1, slowSql {} et sampledTrace {} diffusaient des données comme effet secondaire à l'intérieur de l'extracteur ; dans la v2, la persistance est toujours gérée par le pipeline récepteur.
    • Ordre de résolution du type de sortie : par règle YAML outputType (nom court via SPI ou FQCN) > LALSourceTypeProvider SPI par défaut > Log.class.
    • Tous les scripts LAL groupés (mysql-slowsql.yaml, pgsql-slowsql.yaml, redis-slowsql.yaml, envoy-als.yaml, k8s-service.yaml, mesh-dp.yaml) ont été mis à jour.
    • Les utilisateurs disposant de scripts LAL personnalisés utilisant slowSql {} ou sampledTrace {} doivent migrer vers la nouvelle syntaxe. Voir Documentation LAL.
    • Renommez ExtractorSpec en MetricExtractor — ne gère désormais que les blocs LAL metrics {}. Les setters de champs standard (service, couche, horodatage, etc.) sont compilés sous forme d'appels directs au setter sur le générateur de sortie.
  • Ajout du support des variables locales def dans l'extracteur LAL (et niveau de filtre). Prend en charge les fonctions intégrées toJson() et toJsonArray() pour convertir des chaînes, des cartes et du protobuf Struct en objets Gson JSON. Les variables prennent en charge la navigation null-safe (?.), le chaînage de méthodes avec inférence de type au moment de la compilation et la conversion de type explicite via as (types intégrés ou noms de classe complets, par exemple def resp = parsed?.response as io.envoyproxy.envoy.data.accesslog.v3.HTTPResponseProperties).
    • Changement radical — La signature LALOutputBuilder.init() est passée de init(LogData, NamingControl) à init(LogData, Optional<Object> extraLog, NamingControl). Le paramètre extraLog transporte l'objet d'entrée saisi (par exemple, HTTPAccessLogEntry pour les journaux d'accès des envoyés) afin que les générateurs de sortie puissent accéder aux champs spécifiques au protocole. Les implémentations personnalisées de LALOutputBuilder doivent mettre à jour leur signature de méthode init().

  • Correction de la vérification des métriques de test E2E : faites-en un échec si les valeurs métriques sont toutes nulles.

  • Prise en charge de la création, des tests et de la publication avec Java 25.

  • Ajoutez CLAUDE.md comme guide assistant AI pour le projet.

  • Mettez à niveau Byte Buddy vers 1.18.7 et configurez -javaagent explicite pour Mockito/Byte Buddy dans Surefire afin d'éviter les avertissements de chargement de l'agent dynamique JDK 25.

  • Mettez à niveau Groovy vers 5.0.3 dans le backend OAP.

  • Augmentez nodejs vers v24.13.0 pour la dernière compilation de l'interface utilisateur (booster-ui).

  • Supprimez Elasticsearch 7.x (EOL) et OpenSearch 1.x des tests E2E, mettez à niveau tous les tests ES vers 8.18.8 et mettez à jour skywalking-helm pour utiliser ECK 8.18.8.

  • Ajoutez le module library-batch-queue — une file d'attente partitionnée et auto-drainante avec répartition basée sur le type, partitionnement adaptatif, intervalle d'inactivité et rééquilibrage des drains pondérés en fonction du débit (DrainBalancer). Conçu pour remplacer DataCarrier dans les scénarios à forte diffusion.

  • Remplacez DataCarrier par BatchQueue pour l'agrégation de métriques L1, la persistance des métriques L2, la persistance TopN, les trois exportateurs (métriques gRPC, trace Kafka, journal Kafka) et gRPC distant client. Tous les types de métriques (OAL + MAL) partagent désormais des files d'attente unifiées au lieu de pools OAL/MAL séparés. Chaque exportateur conserve sa propre file d'attente dédiée avec 1 thread, préservant les stratégies de tampon d'origine. Comparaison du nombre de threads sur une machine à 8 cœurs (gRPC distant client exclu — inchangé 1 thread par homologue) :

  • Retirez le module library-datacarrier-queue. Toutes les utilisations ont été remplacées par library-batch-queue.

  • Activer le rééquilibrage des drains pondérés en fonction du débit pour les files d'attente d'agrégation L1 et de persistance L2 (intervalle de 10 s). Réaffecte périodiquement les partitions entre les threads de drainage pour égaliser la charge lorsque les types de métriques ont un débit faussé.

  • Ajout d'un framework de référence sous benchmarks/ avec des environnements Kubernetes basés sur Kind, vidage de thread automatisé collecte et analyse. Premier cas : thread-analysis sur environnement istio-cluster_oap-banyandb.

  • Ajout de la prise en charge des threads virtuels (JDK 25+) pour les threads du gestionnaire de serveur HTTP gRPC et Armeria. Réglez SW_VIRTUAL_THREADS_ENABLED=false pour désactiver.

    | Piscine | Sujets (JDK < 25) | Sujets (JDK 25+) | |---|---|---| | Gestionnaire de serveur gRPC (core-grpc, receiver-grpc, als-grpc, ebpf-grpc) | Plateforme mise en cache (illimitée) | Fils virtuels | | Blocage HTTP (core-http, receiver-http, promql-http, logql-http, zipkin-query-http, zipkin-http, firehose-http) | Plateforme mise en cache (max 200) | Fils virtuels | | Threads porteurs VT (ForkJoinPool) | N/A | ~9 partagés |

    Sur JDK 25+, les 11 pools de threads ci-dessus partagent environ 9 threads porteurs au lieu de plus de 1 400 threads de plate-forme.

  • Remplacez l'image de base Docker par défaut par JDK 25 (eclipse-temurin:25-jre). JDK 11 conservé comme variante -java11.

  • Comparaison du nombre de threads : cluster OAP à 2 nœuds sur JDK 25 avec BanyanDB, trafic Istio bookinfo (Machine à 10 cœurs, threads internes JVM exclus) :

    | Piscine | Fils v10.3.0 | Filetages v10.4.0 | Remarques | |---------------------------------------|----------|-----------------|------------------------------------------------------------| | Agrégation L1 (OAL + MAL) | 26 (Porteur de données) | 10 (file d'attente par lots) | OAL + MAL unifiés | | Persistance L2 (OAL + MAL) | 3 (Porteur de données) | 4 (file d'attente par lots) | OAL + MAL unifiés | | Persistance TopN | 4 (Porteur de données) | 1 (file d'attente par lots) | | | gRPC Télécommande Client | 1 (Porteur de données) | 1 (file d'attente par lots) | Par pair | | Boucle d'événements HTTP Armeria | 20 | 5 | Groupe partagé min(5, cores) | | Gestionnaire HTTP Armeria | plateforme à la demande (augmentant avec la charge utile) | - | Discussions virtuelles sur JDK 25+ | | Boucle d'événements gRPC | 10 | 10 | Inchangé | | Gestionnaire gRPC | plateforme à la demande (augmentant avec la charge utile) | - | Discussions virtuelles sur JDK 25+ | | ForkJoinPool (support de fil virtuel) | 0 | ~10 | Planificateur de threads virtuels JDK 25+ | | HttpClient-SelectorManager | 4 | 2 | PartagéKubernetesClient | | Planificateurs + autres | ~24 | ~24 | Presque inchangé | | Total (thèmes OAP) | 150+ | ~72 | ~50 % de réduction, stable en cas de charge utile élevée. |

  • Remplacez PowerMock Whitebox par Java Reflection standard dans server-library, server-core et server-configuration pour prendre en charge JDK 25+.

  • Le correctif /debugging/config/dump peut divulguer des informations sensibles s'il existe des propriétés de deuxième niveau dans la configuration.

  • Corrigez BrowserWebVitalsPerfData clsTime à cls et faites-en un double type.

  • Échec rapide si SampleFamily est vide après l'expression du filtre MAL.

  • Ajoutez LatestLabeledFunction pour le compteur.

  • Ajout de la prise en charge de l'authentification par certificat OpenSearch/ElasticSearch client.

  • Correction de la requête de pagination des journaux BanyanDB.

  • Remplacez BanyanDB Java client par une implémentation native.

  • Supprimez bydb.dependencies.properties et définissez le numéro de version compatible BanyanDB API dans ${SW_STORAGE_BANYANDB_COMPATIBLE_SERVER_API_VERSIONS}.

  • Correction de la condition de plage horaire de la requête de profilage de trace.

  • Correction du dépassement de plage horaire BanyanDB dans la requête d'instantané du fil de profil.

  • BrowserErrorLog, le serveur OAP a généré un UUID pour remplacer l'ID latéral client d'origine, car les scripts du navigateur ne peuvent pas garantir que les ID générés sont globalement uniques.

  • MQE : corrigez plusieurs requêtes de métriques étiquetées et assurez-vous qu'aucun résultat n'est renvoyé si aucune combinaison de valeurs d'étiquette ne correspond.

  • Correction de l'ordre des requêtes de stockage BrowserErrorLog BanyanDB.

  • BanyanDB Client : prise en charge des requêtes de propriété Order By.

  • MQE : supprimez la condition des valeurs d'étiquette pour la requête de métriques étiquetées afin d'améliorer la lisibilité.

  • Service PromQL : correction du problème d'analyse de l'heure lors de l'utilisation du format d'heure RFC3339 pour les requêtes.

  • Récepteur du service Envoy metrics : prend en charge les métriques d'écoute de l'adaptateur.

  • Récepteur du service Envoy metrics : prend en charge les fichiers de règles de configuration MAL.

  • Correction de HttpAlarmCallback créant un nouveau HttpClient à chaque appel d'alarme post(), provoquant une fuite des threads du sélecteur NIO. Remplacez par un singleton statique partagé.

  • Ajoutez un singleton SharedKubernetesClient dans library-kubernetes-support pour remplacer 9 séparés KubernetesClientBuilder().build() appelle sur 7 fichiers. Corrige la fuite KubernetesCoordinator client (jamais fermé, le thread du sélecteur NIO a persisté). Utilise KubernetesHttpClientFactory avec des threads virtuels sur JDK 25+ ou un seul thread d'exécution fixe sur JDK <25.

  • Réduisez les threads de boucle d'événements du serveur HTTP Armeria. Les 7 serveurs HTTP partagent désormais un groupe de boucles d'événements au lieu que chacun crée le sien (Armeria par défaut : cores * 2 par serveur = 140 sur 10 cœurs). Boucle d'événements : min(5, cores) partagé – le multiplexage d'E/S non bloquant nécessite peu de threads. Exécuteur de blocage : JDK 25+ utilise des threads virtuels ; JDK <25 conserve le pool mis en cache par défaut d'Armeria (jusqu'à 200 threads à la demande) car les gestionnaires HTTP bloquent les longues requêtes de stockage/base de données.

  • Ajoutez les composants spring-ai et la couche GenAI.

  • Passez de netty à 4.2.10.Final.

  • Augmentez log4j en 2.25.3 et jackson en 2.18.5.

  • Supprimez la dépendance PowerMock. Remplacez Whitebox par ReflectUtil (réflexion Java standard + sun.misc.Unsafe pour les champs finaux) dans tous les modules pour prendre en charge JDK 25+.

  • Prise en charge de TraceQL et Tempo API pour les requêtes de trace natives Zipkin et SkyWalking.

  • Supprimez initExp de la configuration MAL. Il s'agissait d'un mécanisme interne de validation du démarrage de Groovy, et non d'une fonctionnalité destinée à l'utilisateur final. Le compilateur v2 ANTLR4 effectue une validation rapide au démarrage de manière native.

  • Mise à jour de la documentation sur les règles hiérarchiques : auto-matching-rules dans hierarchy-definition.yml n'utilise plus de scripts Groovy. Les règles utilisent désormais une grammaire d'expression dédiée prenant en charge l'accès aux propriétés, les méthodes String, if/else, les comparaisons et les opérateurs logiques. Toutes les règles expédiées sont entièrement compatibles.

  • Activez le gestionnaire otlp-traces dans receiver-otel par défaut.

  • Mettre à jour les versions de test Istio E2E : supprimez EOL 1.20.0, ajoutez 1.25.0–1.29.0 pour les tests ALS/Metrics/Ambient. Mettez à jour Rover avec le test Istio Process de 1.15.0 à 1.28.0 avec Kubernetes 1.28.

  • Prise en charge de la surveillance Virtual-GenAI.

  • Correction de l'échec de l'analyse du journal des pods à la demande en remplaçant le modèle DateTimeFormatter non valide par ISO_OFFSET_DATE_TIME.

  • Correction de la compatibilité du récepteur Zipkin avec application/x-protobuf Content-Type.

  • Prise en charge de l'observabilité Envoy AI Gateway (SWIP-10) : nouvelle couche ENVOY_AI_GATEWAY avec règles MAL/LAL pour les métriques GenAI (utilisation des jetons, latence, TTFT, TPOT) et l'échantillonnage des journaux d'accès via OTLP.

  • Récepteur métrique OTel : convertissez les points d'attribut de point de données en traits de soulignement (conformes aux attributs de ressource et noms de métriques). Les mappages d'étiquettes sont désormais uniquement de secours : job_name explicite dans les attributs de ressource prend priorité sur la solution de secours service.name.

  • Gestionnaire de journaux OTel : préférez service.instance.id (spécification OTel) à service.instance avec solution de repli.

  • Ajoutez SampleFamily.debugDump() pour le débogage MAL.

  • Prise en charge de l'analyse virtuelle GenAI pour les traces otlp et zipkin.
