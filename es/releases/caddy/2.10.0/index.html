carrito v2.10.0

¡Caddy 2.10 ya está aquí! Además de las correcciones de errores, esta versión incluye:

  • ClientHello cifrado (ECH): Esta nueva tecnología cifra la última parte de texto sin formato de una conexión TLS: ClientHello, que incluye el nombre de dominio al que se está conectando. El borrador de especificación para ECH está casi finalizado, por lo que ahora podemos admitir esta función de privacidad para TLS. Esta es una capacidad poderosa pero matizada; Recomendamos encarecidamente leer [la documentación de ECH] (https://caddyserver.com/docs/automatic-https#encrypted-clienthello-ech) en nuestro sitio web.
  • Intercambio de claves post-cuántico (PQC): Caddy ahora admite el grupo criptográfico estandarizado x25519mlkem768 de forma predeterminada.
  • Perfiles ACME: Los perfiles ACME son un borrador experimental que le permite elegir propiedades de sus certificados con más flexibilidad que los métodos CSR tradicionales. Por ejemplo, Let's Encrypt emitirá certificados de 6 días bajo un perfil determinado. Caddy puede llegar a utilizar ese perfil de forma predeterminada.
  • Vía encabezado: El proxy inverso ahora establece un encabezado Vía en lugar de un encabezado de servidor duplicado.
  • Proveedor de DNS global: Ahora puede especificar un módulo DNS "global" predeterminado para usar en lugar de tener que configurarlo localmente en cada parte de su configuración que requiera un proveedor de DNS (por ejemplo, desafíos de DNS de ACME y ECH). Esta es la opción global dns en Caddyfile, o en la configuración JSON, es el parámetro dns en la configuración de la aplicación tls.
  • Comodines utilizados de forma predeterminada: Anteriormente, Caddy obtenía certificados individuales para cada dominio en su configuración literalmente; ahora los comodines, si están presentes, se utilizarán para los subdominios, en lugar de obtener certificados individuales. Este cambio fue motivado por la novedosa posibilidad de privacidad de subdominios que ofrece ECH. Se puede anular con tls force_automate en Caddyfile. Se ha eliminado la opción experimental auto_https prefer_wildcard.
  • libdns 1.0 APIs: Muchos de ustedes usan módulos de proveedor de DNS para resolver los desafíos de DNS de ACME o para habilitar DNS dinámico. Implementan interfaces definidas por libdns para obtener, configurar, agregar y eliminar registros DNS. Después de 5 años de experiencia en producción, incluidas las lecciones aprendidas con ECH, se actualizaron los libdns API y se etiquetó la versión beta de 1.0. Los paquetes de proveedores de DNS deberán actualizar su código para que sean compatibles, lo que ayudará a garantizar la estabilidad y una semántica bien definida para el futuro. Varios paquetes ya se han actualizado o están en proceso de actualización (cloudflare, rfc2136 y desec, por nombrar algunos).
  • Configuración global de dns: Ahora que varios componentes de la configuración de Caddy pueden afectar los registros DNS (desafíos ACME, publicación ECH, etc.), existe una nueva opción global dns que se puede usar para especificar la configuración de su proveedor de DNS en un solo lugar. Esto evita la repetición de credenciales para servidores donde todos los dominios son administrados por un único proveedor de DNS. ¡Gracias a todos los contribuyentes que han ayudado a hacer esto posible! :tada: :partying_face: :champagne: :advertencia: Si bien tradicionalmente hemos admitido las últimas 2 versiones menores de Go para adaptarse a algunas políticas de distribución/administrador de paquetes, ahora solo admitimos la última versión menor de Go. Vale la pena poner a disposición de todos los beneficios de privacidad y seguridad agregados en las nuevas versiones de Go (como la criptografía poscuántica) lo antes posible, en lugar de frenar a toda la base de usuarios o mantener múltiples configuraciones de compilación de código.

Detalles cifrados de ClientHello (ECH)

(Esta es una breve descripción general. Recomendamos leer la documentación completa.) Normalmente, los nombres de los servidores (nombres de dominio o "SNI") se envían en texto sin formato ClientHello al establecer conexiones TLS. Con ECH, el verdadero nombre del servidor está cifrado (y empaquetado) mediante un ClientHello "externo" que tiene un SNI genérico de su elección. Dado que muchos sitios en el mismo servidor comparten el mismo SNI externo, tanto clients como el servidor tienen más privacidad relacionada con los nombres de dominio. Caddy implementa ECH totalmente automatizado, lo que significa que genera (y pronto, rota), publica y ofrece configuraciones ECH simplemente especificando un proveedor de DNS y el nombre de dominio público/externo que se utilizará. El ECH completamente automatizado requiere un módulo DNS integrado en su binario Caddy. Para que un client, ​​como un navegador, sepa que puede usar ECH y qué parámetros usar, se debe publicar la configuración de ECH del servidor. Esta configuración incluye el nombre público, los parámetros criptográficos y una clave pública para cifrar el ClientHello interno. Por convención, los navegadores leen el registro DNS estandarizado de tipo HTTPS que contiene una SvcParamKey ech. Caddy establece este registro DNS para todos los dominios que se están protegiendo, pero necesita que el módulo del proveedor de DNS esté conectado y configurado para poder hacerlo. Si ya está utilizando el desafío DNS ACME, ya debería tener un proveedor de DNS conectado. Si prefiere compilar Caddy desde la fuente con un módulo DNS, es fácil con xcaddy, por ejemplo: $ xcaddy build --with github.com/caddy-dns/cloudflare La configuración mínima necesaria para habilitar ClientHello es también la configuración recomendada, ya que maximiza los beneficios de privacidad en la mayoría de las situaciones. Sólo necesita la opción global ech y un proveedor de DNS especificado. Aquí hay un ejemplo que utiliza Cloudflare como servidor de nombres: Archivo Caddy:

{
	debug  # not required; recommended while testing
	dns cloudflare {env.CLOUDFLARE_API_KEY}
	ech ech.example.net
}

example.com {
	respond "Hello there!"
}

Esto protege todos sus sitios (example.com en este caso) detrás del nombre público de ech.example.net. (Como otro ejemplo, Cloudflare usa cloudflare-ech.com para todos los sitios a los que presta servicios. Recomendamos elegir un único dominio público y usarlo para proteger todos sus sitios). El nombre externo/público que elija debe apuntar a su servidor. Caddy obtendrá un certificado para este nombre para facilitar conexiones seguras y confiables para clients cuando sea necesario. Sin un certificado, clients puede verse obligado a conectarse de forma insegura o no poder conectarse en absoluto, en algunos casos, lo que no sólo los deja vulnerables, sino que también corre el riesgo de exponer los nombres de los sitios de su servidor. Luego, Caddy utiliza el proveedor de DNS especificado para publicar las configuraciones de ECH para los distintos nombres de su sitio. Crea (o aumenta) registros de tipo HTTPS para los dominios de sus sitios (no su nombre público ECH). Tenga en cuenta que los módulos del proveedor de DNS se mantienen de forma independiente y es posible que no se haya probado su compatibilidad con registros de tipo HTTPS. Comuníquese con los encargados del mantenimiento de su módulo si tiene problemas. Si tiene necesidades de configuración más avanzadas, puede usar la configuración JSON (más detalles próximamente; por ahora, consulte el n.° 6862 o consulte el código fuente; o use caddy adapt para convertir un Caddyfile a JSON).

Prueba y verificación de ClientHello cifrado

Primero asegúrese de que Caddy se ejecute correctamente con ECH habilitado (y un módulo DNS) en la configuración. Debería ver registros que indiquen que está generando una configuración ECH y publicándola en su(s) nombre(s) de dominio. Necesitará utilizar un client que admita ECH. Algunas versiones personalizadas de curl lo hacen, y Firefox y los navegadores modernos basados ​​en Chrome también lo hacen, pero primero debe habilitar DNS sobre HTTPS o DNS sobre TLS (ya que, obviamente, consultar DNS en texto sin formato para un nombre de dominio protegido expondrá el dominio y frustrará el propósito de ECH). Si reutiliza un nombre de dominio existente, borre su caché de DNS. Firefox tiene una manera de hacer esto para su caché en about:networking#dns. Una vez que tenga un client adecuado, use Wireshark para capturar paquetes de red mientras carga su sitio. Debería ver solo el nombre externo/público como valores SNI (Indicador de nombre de servidor) en la captura de paquetes. Si en algún momento ve el nombre verdadero del sitio, ECH no está funcionando correctamente; podría ser un problema de client o del servidor. Antes de informar un error, primero intente identificarlo como un problema del servidor. ¡Pero definitivamente informe errores del servidor! ¡Gracias! (Tenga en cuenta que ECH no se publica automáticamente para dominios con CNAME y el dominio ya debe tener un registro en la zona).
