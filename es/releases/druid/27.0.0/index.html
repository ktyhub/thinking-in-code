Apache Druid 27.0.0 contiene más de 316 funciones nuevas, correcciones de errores, mejoras de rendimiento, mejoras de documentación y cobertura de pruebas adicionales de 50 contribuyentes.

Consulte el conjunto completo de cambios para obtener detalles adicionales, incluidas correcciones de errores.

<a name="27.0.0-highlights-new-explore-view-in-the-web-console-%28experimental%29" href="#27.0.0-highlights-new-explore-view-in-the-web-console-%28experimental%29">#</a> Nueva vista Explorar en la consola web (experimental)

La vista Explorar es una vista de exploración de datos simple, sin estado y respaldada por SQL para la consola web. Permite a los usuarios explorar datos en Druid con interacciones y visualizaciones de apuntar y click (en lugar de escribir SQL y mirar una tabla). <a name="27.0.0-highlights-query-from-deep-storage-%28experimental%29" href="#27.0.0-highlights-query-from-deep-storage-%28experimental%29">#</a> Consulta desde almacenamiento profundo (experimental)

Druid ahora admite la consulta de segmentos que se almacenan solo en almacenamiento profundo. Cuando realiza consultas desde el almacenamiento profundo, puede consultar datos más grandes disponibles para consultas sin tener que escalar necesariamente sus procesos históricos para acomodar más datos. Para aprovechar los posibles ahorros de almacenamiento, asegúrese de configurar sus reglas de carga para no cargar todos sus segmentos en procesos históricos.

Tenga en cuenta que al menos un segmento de una fuente de datos debe cargarse en un proceso histórico para que el corredor pueda planificar la consulta. Sin embargo, puede ser cualquier segmento.

Para obtener más información, consulte lo siguiente:

  • Consulta desde almacenamiento profundo
  • Tutorial de consulta desde almacenamiento profundo

<a name="27.0.0-highlights-schema-auto-discovery-and-array-column-types" href="#27.0.0-highlights-schema-auto-discovery-and-array-column-types">#</a> Descubrimiento automático de esquemas y tipos de columnas de matriz

El descubrimiento automático de esquemas basados en tipos ahora está disponible de forma generalizada. Druid puede determinar el esquema para los datos que ingiere en lugar de tener que definir el esquema manualmente.

Druid puede determinar los tipos de columnas para su esquema y asignarlos a estos tipos de columnas de matriz cuando ingiere datos utilizando el descubrimiento automático de esquemas con reconocimiento de tipos con el tipo de columna auto.

<a name="27.0.0-highlights-smart-segment-loading" href="#27.0.0-highlights-smart-segment-loading">#</a> Carga de segmentos inteligente

El Coordinador ahora es mucho más estable y fácil de usar. En el nuevo modo smartSegmentLoading, calcula dinámicamente valores para varias configuraciones que maximizan el rendimiento. El Coordinador ahora puede priorizar la carga de segmentos más recientes y segmentos que no están disponibles en absoluto sobre la carga de segmentos que ya tienen algunas réplicas cargadas en el clúster. También puede reevaluar decisiones tomadas en ejecuciones anteriores y cancelar operaciones que ya no sean necesarias. Además, las operaciones de movimiento iniciadas mediante el equilibrio de segmentos no compiten con la carga de segmentos no disponibles, lo que reduce el tiempo de reacción ante cambios en el clúster y acelera las decisiones de asignación de segmentos.

Además, los cambios de liderazgo tienen menos impacto ahora y el Coordinador no se queda estancado incluso si la reelección ocurre mientras hay una candidatura de Coordinador en progreso.

Por último, la estrategia del equilibrador cost funciona mucho mejor ahora y es capaz de mover más segmentos en una sola ejecución del Coordinador. Estas mejoras se realizaron tomando prestadas ideas de la estrategia cachingCost. Recomendamos utilizar cost en lugar de cachingCost ya que cachingCost ahora está en desuso.

Para obtener más información, consulte lo siguiente:

  • Nota de actualización para cambios de configuración relacionados con la carga de segmentos inteligentes
  • Nuevas métricas del coordinador
  • Documentación de carga de segmentos inteligentes

<a name="27.0.0-highlights-smart-segment-loading-new-query-filters" href="#27.0.0-highlights-smart-segment-loading-new-query-filters">#</a> Nuevos filtros de consulta

Druid ahora admite los siguientes filtros:

  • Igualdad: Utilizar en lugar del filtro selector. Nunca coincide con valores nulos.
  • Nulo: coincide con valores nulos. Úselo en lugar del filtro selector.
  • Rango: filtrar por rangos de valores de dimensiones. Úselo en lugar del filtro encuadernado. Nunca coincide con valores nulos

Tenga en cuenta que el planificador SQL de Druid utiliza estos nuevos filtros en lugar de sus homólogos anteriores de forma predeterminada siempre que druid.generic.useDefaultValueForNull=false o si sqlUseBoundAndSelectors se establece en falso en el contexto de consulta SQL.

Puede utilizar estos filtros para filtrar igualdad y rangos en columnas ARRAY en lugar de solo cadenas con el selector anterior y los filtros vinculados.

Para obtener más información, consulte Filtros de consulta.

Druid ahora falla en la planificación de consultas si una columna CLUSTERED BY contiene orden descendente. Anteriormente, las consultas se planificaban correctamente si alguna de las columnas CLUSTERED BY contenía orden descendente.

<a name="27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations" href="#27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations">#</a> Nueva configuración de Broker para migraciones de esquemas SQL

Ahora puede controlar mejor cómo reacciona Druid a los cambios de esquema entre segmentos. Esto puede hacer que las consultas sean más resistentes cuando los segmentos más nuevos introducen tipos diferentes, como si una columna anteriormente contenía valores LONG y los segmentos más nuevos contienen STRING.

Utilice la nueva configuración de Broker, druid.sql.planner.metadataColumnTypeMergePolicy, para controlar cómo se calculan los tipos de columnas para el esquema de tabla SQL cuando se enfrentan diferencias entre segmentos.

Configúrelo en uno de los siguientes:

  • leastRestrictive: el esquema solo se actualiza una vez que todos los segmentos se reindexan al nuevo tipo.
  • latestInterval: el esquema SQL se actualiza tan pronto como el primer trabajo con el nuevo esquema publica segmentos en el último intervalo de tiempo de los datos.

leastRestrictive puede tener un mejor comportamiento en el tiempo de consulta y elimina algunos errores de tiempo de consulta que pueden ocurrir al usar latestInterval.

<a name="27.0.0-additional-features-and-improvements-developer-notes" href="#27.0.0-additional-features-and-improvements-developer-notes">#</a> Notas del desarrollador

Se introdujo una nueva excepción unificada, DruidException, para errores de aparición. Es parcialmente compatible con la antigua forma de informar mensajes de error. Los códigos de respuesta siguen siendo los mismos, todos los campos que existían anteriormente en la respuesta seguirán existiendo y llenándose, incluido errorMessage. Algunos mensajes de error han cambiado para que los humanos puedan consumirlos más y en algunos casos se ha reestructurado el mensaje. No debería haber ningún impacto en los códigos de respuesta.

org.apache.druid.common.exception.DruidException está obsoleto en favor de org.apache.druid.error.DruidException, más completo.

org.apache.druid.metadata.EntryExistsException está obsoleto y se eliminará en una versión futura. #14004 #14554

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes">#</a> Notas de actualización

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-hadoop-2-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-hadoop-2-deprecated">#</a> Hadoop 2 en desuso

Muchas de las bibliotecas dependientes importantes que utiliza Druid ya no son compatibles con Hadoop 2. Para que Druid se mantenga actualizado y tenga vías para mitigar las vulnerabilidades de seguridad, la comunidad ha decidido dejar de admitir las versiones de Hadoop 2.x a partir de esta versión. A partir de Druid 28.x, Hadoop 3.x es la única versión compatible de Hadoop.

Considere migrar a la ingesta basada en SQL o a la ingesta nativa si actualmente utiliza Hadoop 2.x para la ingesta. Si no es posible migrar a la ingestión de Druid, planee actualizar su infraestructura de Hadoop antes de actualizar a la próxima versión de Druid.

Tenga en cuenta que druid 27 no es compatible con Hadoop 2. Debe actualizar su clúster Hadoop a 3.x antes de actualizar a 27.0.0. O puede crear una distribución compatible con Hadoop 2 seleccionando explícitamente el perfil de Hadoop 2 del artefacto fuente de druid 27.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-worker-input-bytes-for-sql-based-ingestion" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-worker-input-bytes-for-sql-based-ingestion">#</a> Bytes de entrada del trabajador para la ingesta basada en SQL

El máximo de bytes de entrada para cada trabajador para la ingesta basada en SQL es ahora de 512 MiB (anteriormente 10 GiB).

#14307

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-parameter-execution-changes-for-kafka" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-parameter-execution-changes-for-kafka">#</a> Cambios en la ejecución de parámetros para Kafka

Cuando se utiliza el FileConfigProvider integrado para Kafka, las interpolaciones ahora son interceptadas por el JsonConfigurator en lugar de pasarse al proveedor de Kafka. Esto rompe las implementaciones existentes.

Para obtener más información, consulte KIP-297.

#13023

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-groupby-v1-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-groupby-v1-deprecated">#</a> GroupBy v1 en desuso

Las consultas GroupBy que utilizan el motor heredado v1 han quedado obsoletas. Se eliminará en versiones futuras. Utilice v2 en su lugar. Tenga en cuenta que v2 ha sido el motor GroupBy predeterminado.

Para obtener más información, consulte Consultas GroupBy.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-push-based-real-time-ingestion-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-push-based-real-time-ingestion-deprecated">#</a> La ingesta en tiempo real basada en push está obsoleta

La compatibilidad con la ingesta en tiempo real basada en push ha quedado obsoleta. Se eliminará en versiones futuras.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60cachingcost%60-segment-balancing-strategy-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60cachingcost%60-segment-balancing-strategy-deprecated">#</a> cachingCost estrategia de equilibrio de segmentos en desuso

La estrategia cachingCost ha quedado obsoleta y se eliminará en versiones futuras. Utilice en su lugar una estrategia de equilibrio de segmentos alternativa, como cost.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-segment-loading-config-changes" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-segment-loading-config-changes">#</a> Cambios en la configuración de carga del segmento

Las siguientes configuraciones relacionadas con el segmento ahora están obsoletas y se eliminarán en versiones futuras:

  • maxSegmentsInNodeLoadingQueue
  • maxSegmentsToMove
  • replicationThrottleLimit
  • useRoundRobinSegmentAssignment
  • replicantLifetime
  • maxNonPrimaryReplicantsToLoad
  • decommissioningMaxPercentOfMaxSegmentsToMove

Utilice en su lugar el modo smartSegmentLoading, que calcula los valores de estas variables automáticamente.

Además, los valores predeterminados para las siguientes configuraciones dinámicas del Coordinador han cambiado:

  • maxsegmentsInNodeLoadingQueue : 500, anteriormente 100
  • maxSegmentsToMove: 100, anteriormente 5
  • replicationThrottleLimit: 500, antes 10

Estos nuevos valores predeterminados pueden mejorar el rendimiento en la mayoría de los casos de uso.

#13197 #14269

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60sysmonitor%60-support-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60sysmonitor%60-support-deprecated">#</a> Soporte de SysMonitor en desuso

Cambie a OshiSysMonitor ya que SysMonitor ahora está obsoleto y se eliminará en versiones futuras.

<a name="27.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes" href="#27.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes">#</a> Cambios incompatibles

<a name="27.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-property-for-setting-max-bytes-for-dimension-lookup-cache" href="#27.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-property-for-setting-max-bytes-for-dimension-lookup-cache">#</a> Propiedad eliminada para establecer el máximo de bytes para la caché de búsqueda de dimensiones

druid.processing.columnCache.sizeBytes se eliminó porque proporcionaba una utilidad limitada después de una serie de cambios internos. Dejar esta configuración es inofensivo, pero no hace nada.

#14500

<a name="27.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-coordinator-dynamic-configs" href="#27.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-removed-coordinator-dynamic-configs">#</a> Se eliminaron las configuraciones dinámicas del Coordinador

Se han eliminado las siguientes configuraciones dinámicas del Coordinador:

  • emitBalancingStats: Siempre se emitirán estadísticas de errores encontrados durante el equilibrio. No se emitirán otras estadísticas de depuración, pero se pueden registrar configurando el debugDimensions apropiado.
  • useBatchedSegmentSampler y percentOfSegmentsToConsiderPerMove: el muestreo de segmentos por lotes ahora es el estándar y siempre estará activado.

En su lugar, utilice el nuevo modo carga de segmento inteligente.
