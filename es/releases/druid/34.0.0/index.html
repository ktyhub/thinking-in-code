Funciones importantes, cambios y obsolescencias

Esta sección contiene información importante sobre funciones nuevas y existentes.

Compatibilidad con Java 11

La compatibilidad con Java 11 ha quedado obsoleta desde Druid 32.0, y la compatibilidad oficial se eliminará tan pronto como Druid 35.0.0

Ingestión basada en Hadoop

La ingestión basada en Hadoop ha quedado obsoleta desde Druid 32.0 y se eliminará tan pronto como Druid 35.0.0. Recomendamos uno de los otros métodos de ingesta admitidos por Druid, como [ingesta basada en SQL] (../multi-stage-query/index.md) o [ingesta sin MiddleManager usando Kubernetes] (../development/extensions-core/k8s-jobs.md).

Como parte de este cambio, ahora debe optar por utilizar el tipo de tarea obsoleto index_hadoop. Si no hace esto, sus tareas de ingesta basadas en Hadoop fallarán.

Para participar, configure druid.indexer.task.allowHadoopTaskExecution en true en su archivo common.runtime.properties.

#18239

Utilice declaraciones SET para parámetros de contexto de consulta

Ahora puede usar declaraciones SET para definir parámetros de contexto de consulta para una consulta a través de la Consola Druid o API.

#17894 #17974

declaraciones SET en la consola Druid

La consola web ahora admite el uso de declaraciones SET para especificar parámetros de contexto de consulta. Por ejemplo, si incluye SET timeout = 20000; en su consulta, se establece el parámetro de contexto de consulta de tiempo de espera:

SET timeout = 20000;
SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2

#17966

declaraciones SET con el API

Las consultas SQL enviadas a /druid/v2/sql ahora pueden incluir múltiples declaraciones SET para crear contexto para la declaración final. Por ejemplo, los siguientes resultados de la consulta SQL incluyen los parámetros de contexto de consulta timeout, useCache, populateCache, vectorize y engine:

SET timeout = 20000;
SET useCache = false;
SET populateCache = false;
SET vectorize = 'force';
SET engine = 'msq-dart'
SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2

La llamada API para esta consulta tiene el siguiente aspecto:

curl --location 'http://HOST:PORT/druid/v2/sql' \
--header 'Content-Type: application/json' \
--data '{
  "query": "SET timeout=20000; SET useCache=false; SET populateCache=false; SET engine='\''msq-dart'\'';SELECT  user,  commentLength,COUNT(*) AS \"COUNT\" FROM wikipedia GROUP BY 1, 2 ORDER BY 2 DESC",
  "resultFormat": "array",
  "header": true,
  "typesHeader": true,
  "sqlTypesHeader": true
}'

Esta mejora también funciona para consultas INSERT y REPLACE utilizando el motor de tareas MSQ. Tenga en cuenta que JDBC no es compatible.

Puntos finales HTTP mejorados

Ahora puede utilizar SQL sin formato en el cuerpo HTTP para los puntos finales /druid/v2/sql. Puede configurar Content-Type en text/plain en lugar de application/json, para poder proporcionar texto sin formato que no tenga escape.

#17937

Históricos de clonación (experimental)

Ahora puede configurar clones para históricos utilizando la configuración dinámica del Coordinador cloneServers. Los históricos clonados son útiles para situaciones como actualizaciones continuas en las que desea lanzar un nuevo histórico como reemplazo de uno existente.

Establezca la configuración en un mapa desde el servidor histórico de destino al histórico de origen:

  "cloneServers": {"historicalClone":"historicalOriginal"}

El clon no participa en la asignación ni en el equilibrio de segmentos regulares. En cambio, el Coordinador refleja cualquier asignación de segmento realizada al Histórico original en el clon, de modo que el clon se convierta en una copia exacta de la fuente. Los segmentos del historial de clones tampoco cuentan para el recuento de réplicas. Si el histórico original desaparece, el clon permanece en el último estado conocido del servidor de origen hasta que se elimine de la configuración cloneServers.

Cuando consulta sus datos utilizando el motor de consulta nativo, puede preferir (preferClones), excluir (excludeClones) o incluir clones (includeClones) configurando el parámetro de contexto de consulta cloneQueryMode. De forma predeterminada, los clones están excluidos.

Como parte de este cambio, hay nuevos Coordinadores API disponibles. Para obtener más información, consulte Coordinador APIs para clones.

#17863 #17899 #17956

Tareas de muerte integradas en Overlord (Experimental)

Ahora puedes ejecutar tareas de eliminación directamente en el Overlord. Las tareas de eliminación integradas proporcionan varios beneficios; ellos:

  • Elimina segmentos tan pronto como sean elegibles.
  • No ocupar espacio para tareas
  • terminan más rápido ya que utilizan consultas de metadatos optimizadas y no lanzan un nuevo JVM
  • Elimina una pequeña cantidad de segmentos por tarea, asegurando que los bloqueos en un intervalo no se mantengan por mucho tiempo.
  • Saltar intervalos bloqueados para evitar el bloqueo del encabezado de línea
  • Requiere una configuración mínima
  • Puede mantenerse al día con una gran cantidad de segmentos no utilizados en el clúster

Esta característica está controlada por las siguientes configuraciones:

  • druid.manager.segments.killUnused.enabled: si la función está habilitada o no (el valor predeterminado es false)
  • druid.manager.segments.killUnused.bufferPeriod: la cantidad de tiempo que un segmento debe permanecer sin uso antes de poder eliminarse permanentemente de los metadatos y el almacenamiento profundo. Esto puede servir como un período de búfer para evitar la pérdida de datos si los datos terminan siendo necesarios después de haber sido marcados como no utilizados (el valor predeterminado es P30D).

Para utilizar tareas de eliminación integradas, debe tener habilitada la caché de metadatos de segmento.

Como parte de esta función, se han agregado nuevas métricas.

#18028 #18124

Selección de nivel preferido

Ahora puede configurar el servicio Broker para que prefiera los históricos en un nivel específico. Esto es útil para la implementación en varias zonas de disponibilidad. Los corredores en una AZ seleccionan históricos en la misma AZ de forma predeterminada, pero aún conservan la capacidad de seleccionar nodos históricos en otra AZ si los históricos en la misma AZ no están disponibles.

Para habilitarlo, establezca la propiedad druid.broker.select.tier en perferred en las propiedades de tiempo de ejecución del Broker. Luego puede configurar druid.broker.select.tier.preferred.tier en el nivel que desea que prefiera cada corredor (es decir, para los corredores en AZ1, puede configurar esto con el nombre de nivel de sus servidores históricos de AZ1).

#18136

Mejoras en dardos

El motor de consultas Dart ahora utiliza el punto final /druid/v2/sql como otros motores de consultas SQL. El antiguo punto final específico de Dart ya no es compatible. Para utilizar Dart para una consulta, incluya el parámetro de contexto de consulta engine y configúrelo en msq-dart.

#18003 #18003

La habilitación de Dart sigue siendo la misma, agregue la siguiente línea a sus archivos broker/runtime.properties y historical/runtime.properties:

druid.msq.dart.enabled = true

Además, Dart ahora consulta tareas en tiempo real de forma predeterminada. Puede controlar este comportamiento configurando el parámetro de contexto de consulta includeSegmentSource en REALTIME (predeterminado) o NONE, de forma similar a las tareas MSQ. También puede ejecutar consultas sincrónicas o asincrónicas.

Ingestión de streaming

Supervisores de flujo múltiple (experimental)

Ahora puede utilizar más de un supervisor para incorporar datos en la misma fuente de datos. Utilice el campo id para distinguir entre supervisores que ingieren la misma fuente de datos (identificada por spec.dataSchema.dataSource para supervisores de transmisión).

Cuando utilice esta función, asegúrese de configurar useConcurrentLocks en true para el campo context en las especificaciones del supervisor.

#18149 #18082

Supervisores y el flujo de entrada subyacente

Los supervisores de flujos buscables (Kafka, Kinesis y Rabbit) ya no se pueden actualizar para ingerir desde un flujo de entrada diferente (como un tema para Kafka). Dado que dicho cambio no es totalmente compatible con el sistema subyacente, una solicitud para realizar dicho cambio generará un error 400.

Consultando

Consulta de metadatos para segmentos

Puede utilizar una consulta de metadatos de segmento para encontrar la lista de proyecciones adjuntas a un segmento.

#18119 #18223

Mejora json_merge()

json_merge() ahora es compatible con SQL cuando los argumentos son nulos. La función ahora devuelve nulo si algún argumento es nulo. Por ejemplo, consultas como SELECT JSON_MERGE(null, null) y SELECT JSON_MERGE(null, '{}') devolverán null en lugar de generar un error.

  • Ahora puede realizar agregaciones decimales grandes usando el motor de tareas MSQ #18164
  • Las funciones modificadas de MV_OVERLAP y MV_CONTAINS ahora se alinean más estrechamente con el filtro nativo inType #18084
  • Manejo de consultas mejorado cuando faltan segmentos temporalmente en los históricos pero los corredores no los detectan. Druid no devuelve resultados parciales incorrectos en tales casos. #18025

Gestión de clústeres

Tiempo de espera configurable para subtareas

Ahora puede configurar un tiempo de espera para tareas de tipo index_parallel y compact. Establezca el parámetro de contexto subTaskTimeoutMillis en el tiempo máximo en milisegundos que desea esperar antes de que se cancele una subtarea. De forma predeterminada, no hay tiempo de espera.

El uso de esta configuración ayuda a que las tareas principales fallen antes en lugar de quedarse atascados ejecutando subtareas zombies.

#18039

Coordinador APIs para clones

  • /druid/coordinator/v1/cloneStatus para obtener información sobre operaciones de clonación en curso.
  • /druid/coordinator/v1/brokerConfigurationStatus que devuelve el estado de sincronización del intermediario para las configuraciones dinámicas del coordinador.

Notas de actualización y cambios incompatibles

Notas de actualización

Ingestión basada en Hadoop

La ingesta basada en Hadoop ha quedado obsoleta desde Druid 32.0 y se eliminará tan pronto como Druid 35.0.0.

Recomendamos uno de los otros métodos de ingesta admitidos por Druid, como [ingesta basada en SQL] (../multi-stage-query/index.md) o [ingesta sin MiddleManager usando Kubernetes] (../development/extensions-core/k8s-jobs.md). Como parte de este cambio, ahora debe optar por utilizar el tipo de tarea obsoleto index_hadoop. Si no hace esto, sus tareas de ingesta basadas en Hadoop fallarán. Para participar, configure druid.indexer.task.allowHadoopTaskExecution en true en su archivo common.runtime.properties. #18239

consultas groupBy y topN

Druid ahora usa el tipo de consulta nativa groupBy, en lugar de topN, para consultas SQL que agrupan por y ordenar por la misma columna, tiene LIMIT y no tiene HAVING. Esto acelera la ejecución. de tales consultas ya que groupBy está vectorizado mientras que topN no.

Puede restaurar el comportamiento anterior estableciendo el parámetro de contexto de consulta useLexicographicTopN en true. El comportamiento de useApproximateTopN no ha cambiado y el valor predeterminado sigue siendo true.

#18074

Configuración IS_INCREMENTAL_HANDOFF_SUPPORTED eliminada

Se eliminó la referencia de contexto IS_INCREMENTAL_HANDOFF_SUPPORTED de los supervisores, ya que la publicación incremental ha sido el comportamiento predeterminado desde la versión 0.16.0. Este contexto se introdujo originalmente para admitir la reversión a LegacyKafkaIndexTaskRunner en versiones anteriores a 0.16.0, que desde entonces se eliminó.

Configuración useMaxMemoryEstimates eliminada

Se eliminó la configuración useMaxMemoryEstimates. Cuando se estableció en falso, Druid usó una estimación de memoria mucho más precisa que se introdujo en Druid 0.23.0. Ese método más preciso es el único método disponible ahora. La configuración predeterminada es falsa en varias versiones.
