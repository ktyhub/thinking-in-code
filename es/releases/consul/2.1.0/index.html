cónsul v2.1.0

2.1.0 (21 de octubre de 2026)

CAMBIOS ÚLTIMOS:

  • agente: (solo Enterprise) Los cuerpos de solicitud HTTP API del agente ahora están limitados a 512 KiB de forma predeterminada, incluidas las solicitudes fragmentadas y las solicitudes con un método no admitido, y las solicitudes de gran tamaño devuelven HTTP 413 antes de que el cuerpo se lea en su totalidad. Las escrituras /v1/config muy grandes que antes se realizaban correctamente ahora pueden fallar. Aumente el límite con la nueva configuración limits.http_max_request_body_size si es necesario.
  • agente: (solo Enterprise) Los cuerpos de solicitud del recurso API (/api/...) ahora están sujetos al mismo límite de limits.http_max_request_body_size (512 KiB de forma predeterminada) y las solicitudes de gran tamaño devuelven HTTP 413.
  • agente: (solo Enterprise) GET /v1/agent/connect/ca/leaf/:service ahora requiere service:write en el servicio solicitado para cada solicitud, incluidas las solicitudes atendidas desde el certificado hoja en caché del agente. Las solicitudes sin token o con un token sin ese permiso ahora reciben HTTP 403 en lugar del certificado almacenado en caché. Las personas que llaman deben presentar un token con service:write para el servicio.
  • catálogo: (solo Enterprise) Catalog.Register ahora requiere permiso de escritura en el nodo o servicio de una verificación de estado existente al actualizarlo. Los tokens que anteriormente actualizaban comprobaciones sin ese permiso ahora reciben un error de permiso denegado.
  • cli: Se migró el comando consul connect redirect-traffic de iptables/ip6tables a nftables (nft). El comando ahora utiliza el paquete sdk/nftables, que aplica todas las reglas IPv4 e IPv6 de forma atómica en una sola pasada a través de la familia de direcciones nftables inet, en lugar de invocaciones separadas iptables y ip6tables. [GH-23785]
  • cli: Las exclusiones de proxy transparentes ahora se validan antes de que se apliquen las reglas: los ID de usuario deben ser numéricos y las exclusiones salientes deben ser direcciones IP o CIDR. Anteriormente, iptables también aceptaba nombres de usuario, rangos de UID y nombres de host. [GH-23785]
  • cli: consul connect redirect-traffic no elimina las reglas iptables/ip6tables creadas por versiones anteriores de Consul. Esto solo importa cuando se actualiza un host o VM existente. Antes de ejecutar el nuevo comando en un host o VM existente, primero elimine cualquier regla iptables administrada por Consul (consulte la guía de actualización de proxy transparente para obtener un script de limpieza de referencia). Dejar ambos conjuntos de reglas en su lugar puede provocar una doble NAT o una redirección de tráfico inconsistente. [GH-23785]
  • docker: Las imágenes oficiales del contenedor Consul ahora incluyen nftables en lugar de iptables. Los scripts que ejecutan iptables dentro de la imagen de Consul deben actualizarse. [GH-23785]
  • sdk: se reemplazó el paquete iptables con un nuevo paquete nftables para una redirección transparente del tráfico de proxy. La redirección de tráfico ahora requiere el binario nft y un kernel de Linux con soporte NAT con estado en las cadenas de la familia nftables inet, disponibles en sentido ascendente a partir de la versión del kernel de Linux 5.2 (algunas distribuciones soportan este soporte en una versión nominal anterior del kernel, por ejemplo, RHEL 8+, kernel 4.18+ y sus derivados). No existe un respaldo automático a iptables/ip6tables, por lo que los hosts sin este soporte de kernel no podrán configurar la redirección de proxy transparente. [GH-23785]
  • feature-gates: Composición de enrutamiento ascendente de Gate API Gateway HTTPRoute (PR #23294) detrás de la función experimental api-gateway-upstream-routing. Cuando está deshabilitado (predeterminado), la forma heredada de HTTPRoute-to-router se conserva exactamente. Cuando lo habilita un operador después de una actualización completa del centro de datos, las reglas del enrutador de servicio se componen con coincidencias de HTTPRoute, las definiciones de subconjuntos de resolución se conservan y las vigilancias de la cadena de descubrimiento utilizan la anulación del protocolo HTTP correcto. Los estados del proxy de puerta de enlace API sin agente existentes se reconstruyen automáticamente cuando cambia el valor de puerta efectivo.

CARACTERÍSTICAS:

  • acl: agregue el cierre de sesión de IdP iniciado por OIDC RP para tokens creados mediante un método de autenticación oidc: consul logout imprime la URL de cierre de sesión del proveedor de identidad para que la abra el usuario (o la abre en el navegador predeterminado con el nuevo indicador -open-browser o la variable de entorno CONSUL_LOGOUT_OPEN_BROWSER), y la interfaz de usuario web la abre al cerrar sesión, finalizando la sesión de IdP. Se activa automáticamente cuando el IdP anuncia un end_session_endpoint en su documento de descubrimiento OIDC, o cuando el punto final de cierre de sesión se configura explícitamente con la nueva configuración del método de autenticación OIDCLogoutURL para proveedores que no anuncian uno. [GH-23739]
  • agente: (solo Enterprise) Agregue un bloque ai en línea a las definiciones de servicio, permitiendo que una carga de trabajo declare su función de IA (inference-model, mcp-server o ai-agent) y la configuración específica de la función en un único registro a través de archivos de configuración y HTTP API. [GH-13032]
  • api-gateway: agregue http2 y grpc como protocolos de escucha de puerta de enlace API válidos, lo que permite HTTP/2 de extremo a extremo y gRPC desde client al backend. Anteriormente sólo se aceptaban http y tcp; la puerta de enlace degradaría silenciosamente el tráfico gRPC/HTTP2 a HTTP/1.1 en el salto ascendente. Los nuevos protocolos generan el administrador de conexión HTTP descendente correcto (códec HTTP/2, h2,http/1.1 ALPN) y alinean el clúster ascendente con HTTP/2, cerrando la brecha de paridad con Ingress Gateway. [GH-23784]
  • api-gateway: Registro automático de DNS para servicios expuestos a través de una puerta de enlace API, que se puede resolver en <service>.api-gateway.consul. Completa la asignación del catálogo gateway-services para las puertas de enlace API y agrega SAN DNS al certificado hoja de conexión de la puerta de enlace API, lo que equipara la puerta de enlace API con la puerta de enlace de ingreso. La función está controlada por versiones y rellena automáticamente las puertas de enlace preexistentes una vez que se actualizan todos los servidores. [GH-23647]
  • api-gateway: admite terminación TLS descendente sin intervención. Cuando TLS { Enabled = true } está configurado en una entrada de configuración api-gateway sin certificado en línea/sistema de archivos/SDS, la puerta de enlace termina TLS descendente utilizando su certificado hoja Connect CA (con SAN DNS *.api-gateway.consul). Los certificados configurados explícitamente siguen teniendo prioridad y se sirven como anulaciones de SNI junto con la cadena predeterminada de hoja. [GH-23647]
  • Puerta de enlace api: agregue PassiveHealthCheck a los límites ascendentes predeterminados a nivel de puerta de enlace y anule los límites de nivel de servicio de ruta, de modo que se pueda configurar la verificación de estado pasiva (detección de valores atípicos de Envoy) para los servicios enrutados a través de una puerta de enlace API. [GH-23783]
  • cli: (solo Enterprise) consul connect envoy -gateway=inference inicia el procesador de políticas junto con Envoy y aplica una versión mínima de Envoy para la puerta de enlace de inferencia. El socket ext_proc se deriva por instancia de proxy; -ext-proc-socket-dir anula su directorio (/var/run/consul predeterminado).
  • connect: (solo Enterprise) Se agregó un ciclo de vida OAuth client administrado por agente para servicios con ai.role de ai-agent o mcp-server, incluido el registro dinámico de client con IBM Security Verify, rotación de claves, publicación JWKS y entrega SDS de la credencial OAuth client a los sidecars ai-agent Envoy.
  • conectar: ​​**(solo Enterprise)** Entregue las credenciales sidecar de OAuth como sobres AES-256-GCM. Las claves de cifrado de contenido se conservan en KV y se entregan a través de WorkloadKeyService.FetchKey para que consul-obo-outbound pueda descifrar sin convertirse en una SDS client.
  • connect: (Solo Enterprise) Conecte los filtros ext_proc de cónsul-obo-outbound y consul-obo-inbound a connect-proxy xDS para el intercambio de tokens en nombre de hop-bound.
  • conectar: ​​**(solo Enterprise)** Registre servicios con ai.role de ai-agent o mcp-server con IBM Security Verify usando private_key_jwt, persista DCR/JWKS en KV y entregue la credencial client a Envoy como SDS GenericSecret JSON para cargas de trabajo ai-agent. Cluster IAM es un método de autenticación OIDC ACL con EnableServiceDCR=true (se rechaza el agente oauth.iam HCL).
  • conectar: ​​agregue ecdh_curves a las entradas de configuración de mesh (MeshDirectionalTLSConfig) y tls_ecdh_curves a la configuración de TLS del agente (TLSProtocolConfig) para admitir la configuración de curvas ECDH/KEM permitidas para sidecar mTLS y agente RPC/HTTPS/gRPC, con inyección automática de curva post-cuántica híbrida X25519MLKEM768 cuando tls_min_version está configurado en TLSv1_3. [GH-23884]
  • feature-gates: agregue un marco de puerta de características dinámicas respaldado por Raft (Fase 1). Un nuevo bloque de configuración del servidor feature_gates { bootstrap = { ... } } genera la primera política Raft. El líder concilia continuamente la política deseada, la elegibilidad de la versión mínima y los valores predeterminados del registro en un estado comprometido y resuelto. Cada servidor ejecuta una caché atómica poblada únicamente desde el estado FSM comprometido; los agentes consumen una instantánea resuelta indexada y no se cierran hasta que se entrega la primera generación. Los nuevos comandos del operador CLI, consul operator feature list, get y set brindan inspección y control de puertas de funciones protegido por ACL y seguro para CAS.
  • operador: agregue puntos finales HTTP GET /v1/operator/features, GET /v1/operator/feature/:name y PUT /v1/operator/feature/:name para leer y actualizar el estado de la puerta de funciones. Las lecturas requieren operator:read; las escrituras requieren operator:write. Todas las lecturas tienen capacidad de consulta de bloqueo. [GH-23791]
  • puerta de enlace de inferencia: (solo Enterprise) Enruta los modelos de inferencia externos optativos a través de una puerta de enlace de terminación. Los modelos marcados con la salida de la puerta de enlace de terminación se descubren en el catálogo, se resuelven a través de la cadena de descubrimiento de malla y se equilibra la carga entre réplicas de puerta de enlace de terminación en buen estado, con niveles de prioridad del grupo de capacidades y comportamiento de cierre ante fallas cuando no hay transporte válido disponible. Se rechaza un grupo de capacidades que contiene un modelo externo y su ruta de capacidad devuelve 503, cuando dos de sus modelos representan la misma dirección de punto final o los pesos de su modelo no se pueden representar exactamente.
  • puerta de enlace de inferencia: (solo Enterprise) Agregue el tipo de servicio y la entrada de configuración inference-gateway. La puerta de enlace finaliza el mTLS de malla entrante, hace cumplir las intenciones y aplica PII y política de enrutamiento a través de un filtro ext_proc a un procesador de políticas ubicado en el mismo lugar. Los modelos ascendentes son servicios registrados con ai.role = "inference-model" que las intenciones permiten y a los que se puede acceder a través de la malla (con conexión habilitada o detrás de una puerta de enlace de terminación). La puerta de enlace se conecta a ellos a través de mTLS y los selecciona por capacidad, conmutando por error entre proveedores por prioridad.
  • telemetría: (solo Enterprise) Se agregaron métricas de uso del producto del lado del servidor para recuentos de métodos de autenticación de ACL (OIDC, Kubernetes, JWT) y configuración de registro de auditoría.
  • telemetría: (solo Enterprise) Se agregaron métricas de uso de productos del lado del servidor para recuentos del modo de puerta de enlace de malla: consul.usage.mesh_gateway_remote.count y consul.usage.mesh_gateway_local.count informan la cantidad de instancias de servicio configuradas para usar cada modo de puerta de enlace de malla, y consul.usage.mesh_gateway_none.count informa la cantidad de instancias de servicio sin un modo de puerta de enlace de malla explícito (no configurado o none).
  • telemetría: (solo Enterprise) Se agregaron métricas de uso de productos del lado del servidor para la política predeterminada de intención de servicio, la intención de servicio L7 y los recuentos de JWT.
  • telemetría: (solo Enterprise) Se agregó la métrica de uso del producto del lado del servidor consul.usage.mesh_gateway_enabled, que informa si alguna instancia de puerta de enlace de malla está registrada en el clúster. Es independiente de los recuentos del modo de puerta de enlace de malla: estos cuentan los sidecars de proxy de conexión según su modo de enrutamiento ascendente, mientras que esto informa si la capacidad de puerta de enlace está implementada.
  • puerta de enlace de terminación: (solo Enterprise) Agregue inyección de credenciales respaldadas por Vault en la salida de la puerta de enlace de terminación. Una entrada de configuración TerminatingGateway ahora lleva un bloque CredentialInjection (ruta UDS del procesador ext_proc y tiempo de espera de mensaje) y cada servicio vinculado puede declarar un enlace Credential (Mode: "inject" con BindingID). En la salida, un filtro ext_proc llama a un procesador ubicado en el mismo lugar que inyecta la credencial vinculada (por ejemplo, una clave de proveedor API proveniente de Vault) en la solicitud ascendente, por lo que las credenciales nunca se almacenan en la configuración de malla ni se exponen a clients.
  • xds: agregue un escucha UDP "DNS virtual" en línea (127.0.0.1:8653) que sirve una tabla FQDN a VIP en memoria derivada de la instantánea del proxy. Anuncia VIP para flujos ascendentes explícitos, flujos ascendentes permitidos por intención en modo proxy transparente y flujos ascendentes de emparejamiento de clústeres, mientras omite VIP entre particiones, cadenas de descubrimiento obsoletas/no autorizadas y entradas vacías o sin IP para que las respuestas DNS permanezcan sincronizadas con lo que el oyente del proxy transparente realmente interceptará. Agregue un detector UDP de "DNS de salida" opcional (127.0.0.1:8654) que reenvía consultas a los recursos DNS configurados por el agente a través de c-ares cuando los recursos están presentes. Amplíe la interfaz xDS ConfigFetcher (y la implementación del agente) para exponer los recursos DNS. [GH-23698]

  • agente/xds: se solucionó un problema por el cual las solicitudes entre clústeres y emparejadas que se originaban desde una puerta de enlace API se rechazaban con HTTP 403 Prohibido por las intenciones RBAC del servicio descendente. Los campos finales separados por punto y coma en el componente de certificado client del encabezado x-forwarded-client-cert (XFCC) (como las SAN de DNS registradas automáticamente) ahora son aceptados correctamente por la expresión regular principal de RBAC. [GH-23920]
  • cli: (solo Enterprise) consul intention create ahora crea y reemplaza intenciones mediante la intención exacta (entrada de configuración) API utilizada por la interfaz de usuario, que admite particiones de administración no predeterminadas (por ejemplo, -partition team-a). Los metadatos por fuente (-meta) continúan usando la intención heredada obsoleta API y solo se admiten en la partición predeterminada; La combinación de -meta con una partición no predeterminada ahora falla con un error claro y procesable. Para adjuntar metadatos a intenciones en una partición de administración, use una entrada de configuración service-intentions con Meta de nivel de entrada a través de consul config write.
  • conectar: ​​**(solo Enterprise)** Adjunte OBO saliente solo para flujos ascendentes del plano de identidad (ai-agent / mcp-server). Los flujos ascendentes HTTP explícitos hacia destinos de puerta de enlace de inferencia o modelo de inferencia ya no obtienen salida de cónsul-obo y fallan y se cierran con "audiencia OBO no configurada".
  • conectar: ​​se corrigió un error por el cual los servidores Consul ignoraban el default_intention_policy configurado para tres superficies del lado del servidor: la verificación de intención API (consul intention check, GET /v1/connect/intentions/check), la vista de topología del servicio (Internal.ServiceTopology) y el descubrimiento ascendente de proxy transparente (Internal.IntentionUpstreams), y en su lugar recurrían a acl.default_policy. Esto sólo cambia el comportamiento cuando default_intention_policy y acl.default_policy se establecen en valores opuestos; cuando están de acuerdo (o default_intention_policy no está configurado), no hay cambios. Con default_intention_policy=deny y acl.default_policy=allow, la comprobación API y la topología previamente informaban que las conexiones estaban permitidas aunque fueran denegadas; con default_intention_policy=allow y acl.default_policy=deny, los sidecars proxy transparentes no aprovisionaban sus flujos ascendentes y podían no llegar a los servicios a los que estaban autorizados. La aplicación del Envoy RBAC no se vio afectada y ya cumplió con default_intention_policy.
