LightRAG v1.5.8rc1

Notas importantes

v1.5.8rc1 es un candidato de lanzamiento. Pruébelo en una copia de sus datos antes de actualizar la producción.

Destacados

1. Almacenamiento de configuración: LightRAG ahora recuerda qué modelo de incrustación creó sus vectores

En versiones anteriores, el cambio de EMBEDDING_MODEL o EMBEDDING_DIM en una implementación existente fallaba silenciosamente. Dependiendo del backend, LightRAG mantuvo los vectores antiguos y devolvió vecinos incorrectos, o abrió un nuevo contenedor de vectores vacío (Milvus/Qdrant/PostgreSQL) y entregó un gráfico de conocimiento sin ningún vector.

v1.5.8 agrega un almacenamiento de configuración. Es un pequeño espacio de nombres KV (config) que contiene las líneas base de incrustación de cada espacio de trabajo: para cada vector objetivo (entidades, relaciones, fragmentos), el espacio de incrustación en el que se escribieron sus vectores. El inicio compara las líneas base con la configuración de incrustación actual. Si el espacio ha cambiado, el servidor se niega a iniciar y nombra el objetivo y la salida, en lugar de ofrecer malos resultados.

  • Backends: JsonKVStorage, PGKVStorage, MongoKVStorage y OpenSearchKVStorage, seleccionados con LIGHTRAG_CONFIG_STORAGE. Si no se configura, sigue LIGHTRAG_KV_STORAGE, por lo que la mayoría de las implementaciones no necesitan una nueva configuración. RedisKVStorage no está admitido, por lo que las implementaciones de Redis tienen por defecto JsonKVStorage, con una advertencia de inicio.
  • No se necesita preparación. En el primer inicio de v1.5.8, una implementación existente registra sus líneas base por sí sola. Una línea de base se registra solo en base a la evidencia: una sonda de adopción vuelve a incorporar algunos registros almacenados (hasta 8 por objetivo) y los compara con los vectores almacenados, o se confirma que el contenedor está vacío. Una sonda que no se puede ejecutar (por ejemplo, el servicio de incorporación no funciona) no registra nada y se vuelve a intentar en el siguiente inicio.
  • Ancla de implementación. El primer inicio también vincula la implementación al contenedor de configuración que abrió, en WORKING_DIR/config_storage_anchor.json (tipo de backend + UUID de contenedor). Cada inicio posterior rechaza un contenedor de otro tipo u otro UUID. Por lo tanto, un LIGHTRAG_KV_STORAGE modificado, una base de datos diferente o un volumen reemplazado ya no mueven silenciosamente su configuración.
  • Nuevas herramientas sin conexión:
    • lightrag-rebuild-vdb vuelve a incrustar un espacio de trabajo con el modelo actual y registra las nuevas líneas base. Ésta es la salida tras un cambio de modelo intencionado.
    • lightrag-migrate-config mueve el almacenamiento de configuración a un backend de otro tipo, por ejemplo de archivos JSON a PostgreSQL.
    • lightrag-clear-storage borra un espacio de trabajo sin conexión, incluidos los registros de configuración.
  • Varios servidores, un WORKING_DIR: admitido cuando cada servidor tiene su propio WORKSPACE y puerto. Se rechaza un segundo servidor en el mismo espacio de trabajo donde el sistema de archivos admite bloqueos de archivos.

Para obtener más información, consulte:

  • docs/LightRAG-API-Server.md: Migración de almacenamiento de configuración entre tipos de backend
  • lightrag/tools/README_REBUILD_VDB.md, README_MIGRATE_CONFIG.md, README_CLEAR_STORAGE.md
  • docs/design/ConfigurationStorageDesign.md: descripción general del diseño

2. Escritura de gráficos y eliminación de documentos más segura

  • Las ediciones manuales de gráficos (crear/editar/eliminar/combinar entidades y relaciones, insert_custom_kg) ahora se serializan entre sí y con la canalización de ingesta en NetworkXStorage.
  • Se modificó el orden de confirmación para la creación, edición, fusión y cambio de nombre de entidades/relaciones para evitar la pérdida de datos cuando se interrumpe una operación.
  • Las eliminaciones de documentos interrumpidas son visibles y reintentables.
  • La nueva herramienta lightrag-repair-chunk-tracking elimina las filas de seguimiento de fragmentos huérfanas que quedan tras una eliminación interrumpida.

3. Valores predeterminados de almacenamiento de PostgreSQL El asistente de configuración ahora genera PostgreSQL a partir de la imagen oficial pgvector/pgvector y ofrece PGTableGraphStorage (tablas simples, sin Apache AGE) para el gráfico. PGGraphStorage (AGE) y los almacenamientos Redis (RedisKVStorage, RedisDocStatusStorage) están obsoletos. Siguen funcionando y registran una advertencia al inicio.

4. Refuerzo de seguridad y nuevo proveedor

  • Las rutas /api/* compatibles con Ollama están protegidas por LIGHTRAG_API_KEY (consulte Cambios importantes).
  • La extracción de PDF ejecuta pypdf en un proceso secundario de recursos limitados.
  • Las líneas de error transmitidas ya no reflejan el texto de excepción del proveedor sin formato.
  • Nuevo enlace openai_responses LLM para OpenAI Responses API.

Cambios importantes

  • Se requiere Python 3.11 o posterior. Python 3.10 ya no es compatible. Las imágenes Docker (Python 3.12) no se ven afectadas.
  • Cambiar el modelo de incrustación en un espacio de trabajo existente ahora rechaza el inicio, donde solía mostrar resultados incorrectos o vacíos. Restaure el EMBEDDING_MODEL/EMBEDDING_DIM anterior o ejecute lightrag-rebuild-vdb para volver a incrustarlo con el nuevo modelo.
  • Se rechaza el cambio de LIGHTRAG_KV_STORAGE después del primer inicio de v1.5.8 mientras LIGHTRAG_CONFIG_STORAGE no está configurado, porque el almacenamiento de configuración se movería silenciosamente con él. Configure LIGHTRAG_CONFIG_STORAGE explícitamente en el backend anclado o mueva la configuración con lightrag-migrate-config.
  • Las rutas de Ollama requieren la clave API. Cuando LIGHTRAG_API_KEY está configurado y WHITELIST_PATHS no está configurado, las solicitudes /api/* sin la clave ahora obtienen HTTP 403. En Open WebUI, el modelo lightrag:latest desaparece de la lista. Solución: ingrese la clave como clave API de la conexión Ollama (enviada como Authorization: Bearer <key>), o configure WHITELIST_PATHS=/health,/api/* para mantener el comportamiento anterior.
  • Se eliminó POST /documents/clear_cache. Utilice DELETE /documents?clear_llm_cache=true en su lugar. El borrado de la caché LLM ahora se realiza junto con el borrado destructivo.
  • Los nombres de los espacios de trabajo que comienzan con $ están reservados. El servidor utilizado para servir WORKSPACE=$team como _team. Configure WORKSPACE=_team (el nombre con el que ya están almacenados sus datos) y no se moverá ningún dato.

Notas de actualización

  1. Primero haga una copia de seguridad y luego detenga todas las instancias antiguas antes de iniciar v1.5.8. Eso incluye a todos los trabajadores, los servidores que comparten el almacenamiento y las herramientas de mantenimiento. El primer inicio crea el contenedor de configuración y vincula el ancla. No realice una actualización continua que deje en ejecución un escritor antiguo.
  2. WORKING_DIR debe persistir, incluso si cada almacenamiento es una base de datos. Ahora contiene config_storage_anchor.json y, para la configuración de JSON, también <workspace>/kv_workspace_config.json. En Docker, manténgalo en un volumen montado. En Helm, mantenga persistence.enabled: true. Un WORKING_DIR efímero pierde el ancla y la configuración JSON en cada reinicio. Inclúyelo en tus copias de seguridad.
  3. Se debe poder acceder al servicio de incorporación durante el primer inicio, para que la sonda de adopción pueda registrar las líneas de base. Verifique el registro de inicio de un WARNING en el que no se pudo establecer una línea de base. Si el inicio se niega debido a una discrepancia en el espacio de incrustación, sus vectores almacenados no coinciden con el modelo configurado: corrija la configuración o ejecute lightrag-rebuild-vdb.
  4. Usuarios de Redis: con LIGHTRAG_KV_STORAGE=RedisKVStorage, el almacenamiento de configuración predeterminado es archivos JSON en WORKING_DIR (consulte la nota 2). El almacenamiento Redis está en desuso; planear una mudanza a PostgreSQL.
  5. Usuarios de PGGraphStorage: su implementación sigue funcionando y el asistente conserva la imagen habilitada para AGE. Para salir de AGE, primero migre el gráfico (python -m lightrag.tools.migrate_graph_storage --apply, no es necesario volver a indexarlo), luego cambie a PGTableGraphStorage y la imagen pgvector.
  6. Opcional: para mantener la configuración en su base de datos en lugar de los archivos JSON, ejecute lightrag-migrate-config --target-backend PGKVStorage (o MongoKVStorage / OpenSearchKVStorage) con cada servidor detenido. Luego configure LIGHTRAG_CONFIG_STORAGE en ese backend.
  7. Para comenzar de nuevo con un nuevo modelo de incrustación, use lightrag-clear-storage en lugar de eliminar archivos manualmente. Si elimina archivos a mano, elimine también kv_workspace_config.json y config_storage_anchor.json. De lo contrario, la línea base registrada rechaza el nuevo modelo.
  8. TOKEN_SECRET debe ser un valor aleatorio de al menos 32 bytes (por ejemplo, openssl rand -hex 32). El PyJWT actualizado advierte sobre secretos más cortos.
  9. Los mensajes de error transmitidos son genéricos. Una falla en medio de una transmisión en /query/stream, /api/generate o /api/chat ahora dice Internal server error (error_id: …) y ya no contiene el texto de excepción del proveedor de LLM. El formato de transmisión no ha cambiado. Busque los detalles en el registro del servidor de ese error_id. Es necesario actualizar un client que analiza el texto de error del proveedor de la transmisión (por ejemplo, para detectar límites de velocidad).
