flujo de aire 3.3.0

📦 PyPI: https://pypi.org/project/apache-airflow/3.3.0/ 📚 Documentos: https://airflow.apache.org/docs/apache-airflow/3.3.0/ 🛠 Release Note: https://airflow.apache.org/docs/apache-airflow/3.3.0/release_notes.html 🐳 Docker Imagen: "docker extrae apache/flujo de aire: 3.3.0" 🚏 Restricciones: https://github.com/apache/airflow/tree/constraints-3.3.0

Cambios significativos

Partición de activos (#64571, #65447, #66030, #66848, #67184, #67475, #67716, #68978)

Sobre la base de la partición de activos introducida en 3.2.0, Airflow 3.3.0 amplía sustancialmente cómo El evento de activo ascendente único se distribuye en ejecuciones de Dag descendentes particionadas. Nuevos mapeadores de particiones: RollupMapper (many-to-one), FanOutMapper (one-to-many), and FixedKeyMapper + SegmentWindow (resumen categórico): compone con ventanas de tiempo (día/semana/mes/trimestre/año) y un wait_policy (WaitForAll or MinimumCount(n)) para controlar cuándo se activa la partición. ventanas puede desplegarse hacia adelante o hacia atrás en el tiempo, y el despliegue total por evento ascendente está limitado por el nuevo Configuración [scheduler] partition_mapper_max_downstream_keys (configurable por asignador). Flujo de aire 3.3.0 También agrega el cronograma PartitionedAtRuntime, que permite a un Dag declarar que su(s) clave(s) de partición se asignan cuando comienza la ejecución en lugar de asignarse desde un evento ascendente.

Para obtener instrucciones de uso detalladas, consulte :doc:/authoring-and-scheduling/assets.

Almacén de estado de activos y tareas (#65759, #66073, #66160, #66463, #66586, #66859, #67041, #67292, #67319)

Airflow 3.3.0 presenta un almacén estatal de primera clase para tareas y activos (AIP-103). Las tareas pueden persistir estado de valor-clave arbitrario que sobrevive a través de reintentos y se ejecuta a través de un nuevo descriptor de acceso task_state_store, y Los activos pueden llevar su propio estado a través de asset_state_store, ambos disponibles en la tarea SDK. el estado se mantiene en la base de datos de metadatos de forma predeterminada, o en un backend personalizado del lado del trabajador ([workers] state_store_backend), admite la retención por clave con recolección de basura periódica y una opción clear_on_success, y es totalmente manejable a través del Core API y Execution API.

Para obtener instrucciones de uso detalladas, consulte :doc:/core-concepts/task-and-asset-state-store.

Políticas de reintento conectables (#65474)

El comportamiento de reintento de tareas ahora es conectable (AIP-105). Además de un recuento fijo de retries, puedes adjunte una política de reintento personalizada que decida si se reintenta una tarea y cuándo, lo que permite estrategias como como reintentar solo en excepciones específicas o retroceder según una lógica personalizada.

Para obtener instrucciones de uso detalladas, consulte :ref:concepts:retry-policies.

Tarea de idioma SDK (Java and Go) (#65958, #67161, #67635, #67699)

Airflow 3.3.0 agrega una capa de Coordinador (AIP-108) que permite escribir implementaciones de tareas individuales en idiomas distintos de Python, mientras que Dag y su programación permanecen en Python. Se declara una tarea en el Dag. con @task.stub(queue=...); el trabajador lo enruta a un coordinador configurado (JavaCoordinator for JVM languages, ExecutableCoordinator para archivos binarios nativos autónomos como Go) que ejecuta la tarea en un tiempo de ejecución de lenguaje y representa variables, conexiones y XComs a través de la Ejecución API.

.. advertencia::

La capa Coordinador y los SDK de Java/Go son experimentales en 3.3.0 y pueden cambiar en el futuro. versiones basadas en los comentarios de los usuarios.

Para obtener instrucciones de uso detalladas, consulte :doc:/authoring-and-scheduling/language-sdks/index.

Versión del paquete Dag para borrar, volver a ejecutar y rellenar (#63884)

La nueva configuración rerun_with_latest_version controla si una ejecución de Dag borrada, repetida o rellenada utiliza la última versión del paquete o la versión original de la ejecución inicial. El defecto se resuelve por precedencia: un parámetro de solicitud explícito/indicador CLI, luego el nivel Dag rerun_with_latest_version, luego [core] rerun_with_latest_version, and finally False for clear/rerun and True para rellenos (preservando el comportamiento histórico). Airflow 2.x siempre se volvía a ejecutar con el código más reciente; 3.x Se introdujo el control de versiones del paquete de forma predeterminada a la versión original, y esta configuración brinda control a los usuarios.

Consulte :doc:/administration-and-deployment/dag-bundles para obtener todos los detalles.

Ejemplo de proveedor Dags como paquetes dedicados (#66161)

Los Dags de ejemplo enviados por distribuciones de proveedores ahora se descubren a través de ProvidersManager y registrados como sus propios paquetes Dag: uno por proveedor, nombrado apache-airflow-providers-<distribution>-example-dags (or <distribution>-example-dags para proveedores externos). La opción [core] load_examples aún controla si están registrados. REST API clients que filtraron bundle_name by "dags-folder" para Dags de ejemplo enviados por el proveedor debe actualizarse a los nuevos nombres de paquetes por proveedor; Los identificadores de Dag no se modifican.

Resolución de registro remoto desacoplada de airflow.logging_config (#67056)

La resolución del controlador de registro de tareas remoto ahora es propiedad del airflow_shared.logging.factory compartido módulo y aplica una precedencia única y bien definida:

  1. un [logging] logging_config_class exporting REMOTE_TASK_LOG / definido por el usuario DEFAULT_REMOTE_CONN_ID (las configuraciones personalizadas existentes siguen funcionando);
  2. ProvidersManager scheme dispatch — the scheme of [logging] remote_base_log_folder selecciona un método de clase proveedor RemoteLogIO class, instantiated via a no-argument from_config();
  3. un respaldo heredado de transición que dice "airflow_local_settings.py" (que se eliminará en Airflow 4.0).

airflow.logging_config.load_logging_config is deprecated (it now emits DeprecationWarning y delega a nuevos ayudantes privados), y configure_logging ya no resuelve con entusiasmo el problema remoto handler: la resolución es lenta en el primer uso. Proveedores que registraron un bloque remote-logging: pero no no implementan from_config se omiten con una advertencia y pasan a la ruta heredada.

Migración: sustituir llamadas directas a airflow.logging_config.load_logging_config() por la nueva ayudantes y hacer que las clases de controlador de registros remotos del proveedor implementen un from_config sin argumentos método de clase que dice "airflow.providers.common.compat.sdk.conf".

Las métricas del temporizador OpenTelemetry ahora usan histograma (#64207)

El temporizador OpenTelemetry y las métricas de tiempo ahora se registran como histogramas en lugar de indicadores, preservando recuento, suma y distribución de depósitos entre grabaciones.

La métrica "hace segundos" de procesamiento de Dag ahora está etiquetada (#62487)

dag_processing.last_run.seconds_ago.{dag_file} es ahora una métrica heredada. el nuevo dag_processing.last_run.seconds_ago is emitted with file_path, bundle_name y file_name tags (file_path + bundle_name identifica de forma única el archivo Dag). La métrica heredada todavía se emite de forma predeterminada y se puede desactivar mediante [metrics] legacy_names_on.

Nueva página de fechas límite en Explorar (#67586)

Una nueva página Plazos límite está disponible en el menú Explorar, a la que puede acceder cualquier rol que ya tenga can_read and menu_access en Dag Runs.
