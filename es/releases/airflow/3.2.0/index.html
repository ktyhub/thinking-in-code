Cambios significativos

Partición de activos

La característica principal de Airflow 3.2.0 es la partición de activos, una importante evolución del reconocimiento de datos. programación. En lugar de activar Dags en función de un activo completo, ahora puede programar en sentido descendente procesamiento basado en particiones específicas de datos. Solo la porción relevante de datos se activa en sentido descendente trabajo, haciendo que la orquestación de tuberías sea mucho más eficiente y precisa.

Esto es importante cuando se trabaja con lagos de datos particionados: rutas S3 particionadas por fecha, tabla Hive particiones, particiones de tablas de BigQuery o cualquier otro almacén de datos particionado. Anteriormente, cualquier actualización a un activo activó todos los Dags posteriores independientemente de qué partición cambió. Ahora solo el derecho el trabajo se activa en el momento adecuado.

Para obtener instrucciones de uso detalladas, consulte :doc:/authoring-and-scheduling/assets.

Implementaciones de varios equipos

Airflow 3.2 presenta soporte para múltiples equipos, lo que permite a las organizaciones ejecutar múltiples equipos aislados dentro de una única implementación de Airflow. Cada equipo puede tener sus propios Dags, conexiones, variables, grupos y ejecutores, lo que permite un verdadero aislamiento de recursos y permisos sin requerir instancias de Airflow separadas por equipo.

Esto es particularmente valioso para los equipos de plataforma que prestan servicios a múltiples equipos de ingeniería o ciencia de datos desde una infraestructura compartida, al tiempo que mantienen límites sólidos entre los recursos y el acceso de los equipos.

Para obtener instrucciones de uso detalladas, consulte :doc:/core-concepts/multi-team.

.. advertencia::

Las implementaciones de equipos múltiples son experimentales en 3.2.0 y pueden cambiar en versiones futuras según comentarios de los usuarios.

Soporte de devolución de llamada sincrónica para alertas de fecha límite

Las alertas de fecha límite ahora admiten devoluciones de llamadas sincrónicas a través de SyncCallback además de las existentes asincrónico AsyncCallback. Las devoluciones de llamada sincrónicas son ejecutadas por el ejecutor (en lugar de el disparador), y opcionalmente puede apuntar a un ejecutor específico a través del parámetro executor.

Un Dag también puede definir múltiples alertas de fecha límite pasando una lista al parámetro deadline, y cada alerta puede utilizar cualquier tipo de devolución de llamada.

.. advertencia::

Las alertas de fecha límite son experimentales en 3.2.0 y pueden cambiar en versiones futuras según comentarios de los usuarios. Las devoluciones de llamada de fecha límite síncronas (SyncCallback) actualmente no Admite conexiones almacenadas en la base de datos de metadatos de Airflow.

Para obtener instrucciones de uso detalladas, consulte :doc:/howto/deadline-alerts.

Mejoras y rendimiento de la interfaz de usuario

  • Virtualización de vista de cuadrícula: La vista de cuadrícula ahora usa virtualización: solo las filas visibles se representan en el DOM. Esto mejora drásticamente el rendimiento al visualizar Dags con una gran cantidad de tareas ejecutadas, lo que reduce el tiempo de renderizado y el uso de memoria para Dags complejos. (#60241)

  • Gestión de XCom en la interfaz de usuario: Ahora puede agregar, editar y eliminar valores de XCom directamente desde la interfaz de usuario de Airflow. Esto hace que sea mucho más fácil depurar y administrar el estado de XCom durante el desarrollo y las operaciones diarias sin necesidad de comandos CLI. (#58921)

  • Historial detallado HITL: La interfaz de aprobación Human-in-the-Loop ahora incluye una vista del historial completo, lo que permite a los operadores y revisores ver el registro de auditoría completo de las aprobaciones y rechazos de cualquier tarea. (#56760, #55952)

  • Mejoras en el diagrama de Gantt:

    • Se muestran todos los intentos de tareas: el diagrama de Gantt ahora muestra cada intento, no solo el último.

  • Nombres para mostrar de tareas en Gantt: se muestra task_display_name para una mejor legibilidad (#61438)

    • Fechas ISO en Gantt: formato de fecha coherente en todos los navegadores (#61250)
    • Se corrigió el fallo de fecha y hora nula: el diagrama de Gantt ya no falla en tareas con campos de fecha y hora nulos.

Nuevo indicador --only-idle para el programador CLI

El indicador airflow scheduler command has a new --only-idle que solo cuenta se ejecuta cuando el El programador está inactivo. Esto ayuda a los usuarios a ejecutar el programador una vez y procesar todos los Dags y tareas en cola. Requiere y complementa el indicador --num-runs para que se pueda establecer un valor pequeño en lugar de adivinar cuántas iteraciones necesita el programador.

Reemplace las solicitudes de resumen de TI por ejecución con una única secuencia NDJSON

Las vistas de cuadrícula, gráfico, Gantt y detalles de tareas ahora obtienen la instancia de tarea resúmenes a través de una única solicitud HTTP de streaming (GET /ui/grid/ti_summaries/{dag_id}?run_ids=...) en lugar de una solicitud por carrera. El servidor emite una línea JSON por ejecución tan pronto como la tarea de esa ejecución las instancias están listas, por lo que las columnas aparecen progresivamente en lugar de todas a la vez.

Qué cambió:

  • GET /ui/grid/ti_summaries/{dag_id}?run_ids=... es ahora el único punto final para resúmenes de TI, devolviendo una secuencia application/x-ndjson donde cada La línea es un objeto GridTISummaries serializado para una ejecución.
  • El antiguo punto final de ejecución única GET /ui/grid/ti_summaries/{dag_id}/{run_id} ha sido eliminado.
  • La estructura Dag serializada se carga una vez y se comparte en todas las ejecuciones que comparte el mismo dag_version_id, evitando la deserialización redundante.
  • Todas las vistas de la interfaz de usuario (cuadrícula, gráfico, Gantt, instancia de tarea, instancia de tarea asignada, grupo instancia de tarea) use el punto final de la secuencia, pasando uno o más run_ids.

Registro estructurado de JSON para toda la salida del servidor API

La nueva sección json_logs option under the [logging] hace que Airflow producir toda su salida como JSON delimitado por nueva línea (registros estructurados) en lugar de registros formateados legibles por humanos. Esto cubre el servidor API (gunicorn/uvicorn), incluidos registros de acceso, advertencias y excepciones no controladas.

No todos los componentes admiten esto todavía, en particular airflow celery worker, pero cualquier salida que no sea JSON cuando json_logs esté habilitado será tratada como un error. (#63365)

Eliminar la metaclase OTel Trace heredada y los contenedores de seguimiento compartidos

Las interfaces y funciones ubicadas en airflow.traces fueron código interno que proporcionó una forma estándar de gestionar tramos en código interno de flujo de aire. No estaban pensados como código orientado al usuario. y nunca fueron documentados. Ya no son necesarios así que elimínelos en 3.2. (#63452)

Mover importaciones de excepciones a nivel de tarea a la tarea SDK

Airflow ahora genera excepciones de tareas (AirflowSkipException, TaskDeferred, etc.) de airflow.sdk.exceptions. airflow.exceptions todavía expone las mismas excepciones, pero son servidores proxy que emiten DeprecatedImportWarning para que los autores de Dag puedan migrar antes de que se elimine la corrección.

Qué cambió:

  • El código de tiempo de ejecución ahora genera constantemente las versiones SDK de excepciones a nivel de tarea.
  • La tarea SDK redefine estas clases para que los trabajadores ya no dependan de airflow-core en tiempo de ejecución.
  • airflow.providers.common.compat.sdk centraliza las importaciones de compatibilidad para proveedores.

Cambios de comportamiento:

  • Los sensores y otros asistentes que validan la entrada del usuario ahora generan "ValueError" (en lugar de Los argumentos AirflowException) when poke_interval/ timeout no son válidos.
  • La importación de nombres de excepción obsoletos desde airflow.exceptions registra una advertencia que dirige a los usuarios a la ruta de importación SDK.

Excepciones ahora proporcionadas por airflow.sdk.exceptions:

  • AirflowException and AirflowNotFoundException
  • AirflowRescheduleException and AirflowSensorTimeout
  • AirflowSkipException, AirflowFailException, AirflowTaskTimeout, AirflowTaskTerminated
  • TaskDeferred, TaskDeferralTimeout, TaskDeferralError
  • DagRunTriggerException and DownstreamTasksSkipped
  • AirflowDagCycleException and AirflowInactiveAssetInInletOrOutletException -ParamValidationError, DuplicateTaskIdFound, TaskAlreadyInTaskGroup, TaskNotFound, XComNotFound -AirflowOptionalProviderFeatureException

Compatibilidad con versiones anteriores:

  • Sin embargo, los Dags/operadores existentes que aún importan desde airflow.exceptions continúan funcionando. registran advertencias.
  • Los proveedores pueden confiar en airflow.providers.common.compat.sdk para mantener una ruta de importación que funcione en todas las versiones compatibles de Airflow.

Migración:

  • Actualice operadores, sensores y extensiones personalizados para importar clases de excepción desde airflow.sdk.exceptions (o del proveedor compatible shim).
  • Ajuste el código de validación personalizado para esperar "ValueError" para argumentos de sensor no válidos si capturado previamente AirflowException.

Admite valores multiplicadores numéricos para el parámetro retry_exponential_backoff

El retry_exponential_backoff parameter now accepts numeric values to specify custom exponential backoff multipliers for task retries. Previously, this parameter only accepted boolean values (True or False), with True using a hardcoded multiplier of 2.0.

Nuevo comportamiento:

  • Los valores numéricos (por ejemplo, 2.0, 3.5) especifican directamente el multiplicador de retroceso exponencial.
  • retry_exponential_backoff=2.0 duplica el retraso entre cada reintento
  • retry_exponential_backoff=0 or False disables exponential backoff (uses fixed retry_delay)

Compatibilidad con versiones anteriores:

Los Dags existentes que utilizan valores booleanos siguen funcionando:

  • retry_exponential_backoff=True → converted to 2.0 (mantiene el comportamiento original)
  • retry_exponential_backoff=False → converted to 0.0 (sin retroceso exponencial)

Cambios API:

El esquema REST API para retry_exponential_backoff has changed from type: boolean to type: number. API clients debe utilizar valores numéricos (se rechazarán los valores booleanos).

Migración:

Si bien los valores booleanos en Python Dags se convierten automáticamente para compatibilidad con versiones anteriores, recomendamos actualizar a valores numéricos explícitos para mayor claridad:

  • Cambiar retry_exponential_backoff=True → retry_exponential_backoff=2.0
  • Cambiar retry_exponential_backoff=False → retry_exponential_backoff=0

Mover la lógica de serialización/deserialización (serde) a la tarea SDK

Airflow ahora obtiene la lógica serde de airflow.sdk.serde en lugar de airflow.serialization.serde. Serializer modules have moved from airflow.serialization.serializers.* a airflow.sdk.serde.serializers.*. The old import paths still work but emit DeprecatedImportWarning para guiar la migración. La capa de compatibilidad con versiones anteriores se eliminará en Airflow 4.

Qué cambió:

  • Código de serialización/deserialización movido del paquete airflow-core to task-sdk
  • Módulos serializadores movidos de airflow.serialization.serializers.* to airflow.sdk.serde.serializers.*
  • Se deben agregar nuevos serializadores al espacio de nombres airflow.sdk.serde.serializers.*

Cambios en la interfaz del código:

  • Importar serializadores desde airflow.sdk.serde.serializers.* instead of airflow.serialization.serializers.*
  • Importar funciones de serialización desde airflow.sdk.serde instead of airflow.serialization.serde

Compatibilidad con versiones anteriores:

  • Los serializadores existentes que se importan desde airflow.serialization.serializers.* continúan funcionando con advertencias de obsolescencia.
  • Todos los serializadores existentes (integrados, datetime, pandas, numpy, etc.) están disponibles en la nueva ubicación

Migración:

  • Para serializadores personalizados existentes: actualice las importaciones para usar airflow.sdk.serde.serializers.*
  • Para serializadores nuevos: agréguelos a airflow.sdk.serde.serializers.* namespace (e.g., create task-sdk/src/airflow/sdk/serde/serializers/your_serializer.py)

Agregue soporte gunicorn para el servidor API con trabajador sin tiempo de inactividad recycling

El servidor API ahora admite gunicorn como servidor alternativo con reinicios continuos de los trabajadores. para evitar la acumulación de memoria en procesos de larga duración.

Beneficios clave:

  • Se reinicia el trabajador rodante: los nuevos trabajadores aparecen y pasan controles de salud antes que los trabajadores antiguos. mueren, lo que garantiza cero tiempo de inactividad durante el reciclaje de trabajadorescling.

  • Compartir memoria: Gunicorn usa precarga + bifurcación, por lo que los trabajadores comparten memoria a través de copiar en escritura. Esto reduce significativamente el uso total de memoria en comparación con el de uvicorn. Modo multiproceso donde cada trabajador carga todo de forma independiente.

  • Manejo correcto de la señal FIFO: SIGTTOU de Gunicorn mata al trabajador más viejo (FIFO), no el más nuevo (LIFO), que es correcto para reinicios continuos.

Configuración:

.. bloque de código:: ini

[api]
# Usa gunicorn en lugar de uvicorn
tipo_servidor = gunicorn

# Habilitar que los trabajadores se reinicien cada 12 horas
intervalo_actualización_trabajador = 43200

# Reiniciar trabajadores uno a la vez
trabajador_refresh_batch_size = 1

O mediante variables de entorno:

.. bloque de código:: bash

exportar AIRFLOW__API__SERVER_TYPE=gunicornio
exportar AIRFLOW__API__WORKER_REFRESH_INTERVAL=43200

Requisitos:

Instale el gunicorn extra: pip install 'apache-airflow-core[gunicorn]'

Nota sobre uvicorn (predeterminado):

El modo uvicorn predeterminado no admite reinicios continuos de trabajadores porque:

  1. Con trabajadores = 1, no existe un proceso maestro al que enviar señales
  2. SIGTTOU de uvicorn mata al trabajador más nuevo (LIFO), frustrando los propósitos de reinicio continuo
  3. Cada trabajador de uvicorn carga todo de forma independiente sin compartir memoria

Si necesita un trabajador recycling o una implementación de varios trabajadores con eficiencia de memoria, utilice gunicorn. (#60921)

Rendimiento mejorado de la limpieza de campos de instancias de tareas renderizadas para Dags con muchas tareas asignadas (~42 veces más rápido)

Los permisos de reposición de AuthManager ahora los maneja requires_access_dag on the DagAccessEntity.Run

Se ha eliminado la interfaz is_authorized_backfill of the BaseAuthManager. Core ya no llamará a este método ni a sus La implementación de la contraparte del proveedor se marcará como obsoleta. Los permisos para operaciones de reabastecimiento ahora se comparan con el permiso DagAccessEntity.Run usando el permiso existente Decorador requires_access_dag. En otras palabras, si un usuario tiene permiso para ejecutar un Dag, puede realizar operaciones de reabastecimiento en él.

Actualice sus políticas de seguridad para garantizar que los usuarios que necesitan realizar operaciones de reposición tengan los permisos "DagAccessEntity.Run" adecuados. (Usuarios tener los permisos de Backfill sin tener los de DagRun ya no podrá realizar operaciones de backfill sin ninguna actualización)
