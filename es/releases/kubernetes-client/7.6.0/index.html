kubernetes-client v7.6.0

Errores

  • Solución #5292: La configuración de Cluster() debe usar tlsServerName
  • Solución #7174: (httpclient) Corrige la prioridad de fábrica HTTP client - VertxHttpClientFactory (predeterminado) ahora tiene prioridad -1, OkHttpClientFactory se restableció a la prioridad 0
  • Solución #7174: (httpclient-vertx-5) Agregue verificación de tiempo de ejecución para las clases de Vert.x 5 para proporcionar un error claro cuando ocurre un conflicto con Vert.x 4/5
  • Solución #7174: (pruebas de caos) Soluciona el conflicto de ruta de clase al realizar pruebas con Vert.x 5 HTTP client
  • Solución #7415: (java-generator) Corrige el borrado de tipo genérico para una serie de enumeraciones con valores predeterminados
  • Solución #7422: (okhttp) Elimine el uso interno de API y corrija las llamadas OkHttp 5 obsoletas
  • Solución #7446: hacer que el tiempo de espera de BaseOperation.createOrReplace() sea configurable

Mejoras

  • Solución #1105: Agregar enlaces cruzados de javadoc para módulos Fabric8 y dependencias externas
  • Solución #5756: Usar interfaz editable en lugar de reflexión para crear instancias de creadores de recursos
  • Solución #7422: pasa okhttp de 4.12.0 a 5.3.2
  • Solución #7252: llame a adicionalConfig al compilar Vert.x HTTP clients con VertxHttpClientFactory

Actualización de dependencia

  • Solución #7374: motor de serpiente yaml de 2.10 a 3.0.1

Nuevas funciones

  • Solución #7385: Soporte para Kubernetes v1.35 (Timbernetes)
  • Solución #7174: Se agregó la implementación Vert.x 5 HTTP client con manejo asíncrono mejorado y separación de WebSocket
  • Solución #7402: Se agregó generación de informes de compatibilidad de nivel de código de bytes semver API usando Revapi

Nota: cambios importantes

  • Solución n.º 5756: los recursos editados con visitantes ahora deben implementar io.fabric8.kubernetes.api.builder.Editable. Todas las clases de modelo proporcionadas por client ya implementan esta interfaz. Los recursos personalizados proporcionados por el usuario que utilizan edición basada en visitantes deberán implementar Editable (trivial cuando ya existe un creador).
  • Solución #7422: pasa okhttp de 4.12.0 a 5.3.2. Las versiones son compatibles binariamente, pero la actualización de la versión principal puede provocar efectos secundarios.

Nota: Compatibilidad con Vert.x HTTP Client (Problema n.º 7174)

Los módulos kubernetes-httpclient-vertx (Vert.x 4.x) y kubernetes-httpclient-vertx-5 (Vert.x 5.x) son mutuamente excluyentes. No deben incluirse juntos en las dependencias de su proyecto. Ambos módulos proporcionan una implementación de HttpClient.Factory y utilizan las mismas coordenadas de artefacto io.vertx pero con versiones principales incompatibles.

-Problema*: Si ambos módulos están presentes en el classpath, la resolución de dependencia de Maven puede seleccionar archivos JAR Vert.x 4.x mientras Vertx5HttpClientFactory está seleccionado en tiempo de ejecución. Esto provoca NoClassDefFoundError para clases específicas de Vert.x 5 como io.vertx.core.impl.SysProps.

-Solución*: Asegúrese de que su proyecto incluya solo UNO de estos módulos:

  • kubernetes-httpclient-vertx (predeterminado, usa Vert.x 4.x) - incluido transitivamente a través de kubernetes-client
  • kubernetes-httpclient-vertx-5 (opcional, usa Vert.x 5.x): requiere dependencia explícita y exclusión de vertx-4

Cuando utilice Vert.x 5, excluya el Vert.x 4 predeterminado client y establezca la propiedad vertx.version:

<properties>
  <vertx.version>${vertx5.version}</vertx.version> <!-- or explicit 5.0.7 -->
</properties>
<dependencies>
  <dependency>
    <groupId>io.fabric8</groupId>
    <artifactId>kubernetes-client</artifactId>
    <exclusions>
      <exclusion>
        <groupId>io.fabric8</groupId>
        <artifactId>kubernetes-httpclient-vertx</artifactId>
      </exclusion>
    </exclusions>
  </dependency>
  <dependency>
    <groupId>io.fabric8</groupId>
    <artifactId>kubernetes-httpclient-vertx-5</artifactId>
  </dependency>
</dependencies>
