dify 1.13.0

🚀 Nuevas funciones

Humano en el circuito (HITL)

Presentamos el nodo Human Input, una actualización importante que transforma la forma en que la IA y los humanos colaborar dentro de los flujos de trabajo de Dify.

Fondo

Anteriormente, los flujos de trabajo eran binarios: completamente automatizados o completamente manuales. Esto creó una "brecha trust" en Escenarios de alto riesgo donde se necesita velocidad de IA pero el juicio humano es esencial. Con HITL, estamos haciendo h La supervisión humana es una parte nativa de la arquitectura del flujo de trabajo, lo que le permite integrar revise los pasos directamente en el gráfico de ejecución.

Capacidades clave

  • Pausa del flujo de trabajo nativo: Inserte un nodo de "Entrada humana" para suspender la ejecución del flujo de trabajo en puntos de decisión críticos.
  • Revisar y editar: El nodo genera una interfaz de usuario donde los humanos pueden revisar los resultados de la IA y modificar variables (por ejemplo, editar un borrador o corregir datos) antes de que continúe el proceso.
  • Enrutamiento basado en acciones: Configure botones personalizados (como "Aprobar", "Rechazar" o "Escalar") que determinan la ruta posterior del flujo de trabajo.
  • Métodos de entrega flexibles: Los formularios de entrada humana se pueden entregar a través de Aplicación web o Correo electrónico. En entornos de nube, la disponibilidad de la entrega de correo electrónico puede depender de la configuración del plan/funciones.

🛠 Actualizaciones de arquitectura

Para admitir el mecanismo de pausa/reanudación con estado requerido por HITL y proporcionar suscripción a eventos API, refactorizamos el motor de ejecución: Las ejecuciones de transmisión basadas en flujo de trabajo y las ejecuciones de chat avanzado ahora se ejecutan en los trabajadores de Celery, mientras que las ejecuciones de FLUJO DE TRABAJO sin transmisión aún se ejecutan en el proceso API. Todas las rutas de pausa/reanudación (por ejemplo, HITL) se reanudan a través de Celery y los eventos se transmiten a través de Redis Pub/Sub.

Para implementaciones grandes y usuarios autohospedados:

Hemos introducido una nueva cola de apio llamada workflow_based_app_execution. Si bien las configuraciones estándar funcionarán de inmediato, los entornos de alto rendimiento deben considerar las siguientes optimizaciones para garantizar la estabilidad y el rendimiento:

  1. Escale trabajadores: Ajuste la cantidad de trabajadores que consumen la cola workflow_based_app_execution según su carga de trabajo específica.
  2. Redis dedicado (opcional): Para implementaciones a gran escala, recomendamos configurar la nueva variable de entorno PUBSUB_REDIS_URL para que apunte a una instancia Redis dedicada. Se recomienda encarecidamente utilizar el modo Redis Cluster con Sharded PubSub para garantizar la escalabilidad horizontal.

⚠️ Nota importante de actualización

Se requiere nueva cola de apio: workflow_based_app_execution

Asegúrese de que su configuración de implementación (Docker Compose, Helm Chart, etc.) incluya trabajadores escuchando la nueva cola workflow_based_app_execution.
Esta cola es necesaria para ejecuciones de streaming basadas en flujos de trabajo y todos los flujos de reanudación (por ejemplo, HITL); de lo contrario, no se procesarán las ejecuciones de streaming ni las tareas de reanudación.

🔧 Nota operativa

Cola adicional de apio: api_token

Si es ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK=true, asegúrese de que su implementación también tenga trabajadores escuchando api_token. Esta cola la utiliza la tarea de actualización por lotes programada para las marcas de tiempo del token API last_used_at.

⚙️ Cambios de configuración

Hemos introducido varias variables de entorno nuevas para respaldar los cambios arquitectónicos. Las implementaciones grandes deben prestar especial atención a las configuraciones de PubSub Redis para garantizar la escalabilidad.

  • PUBSUB_REDIS_URL (Crítico): Especifica la URL de Redis utilizada para la comunicación PubSub entre los trabajadores de API y Celery. Si se deja vacío, el valor predeterminado es la configuración estándar REDIS_*.
  • PUBSUB_REDIS_CHANNEL_TYPE (Crítico): Define el tipo de canal para la transmisión de eventos. Las opciones son pubsub (predeterminada) o sharded. Recomendamos encarecidamente utilizar sharded para entornos de alto rendimiento.
  • PUBSUB_REDIS_USE_CLUSTERS (Crítico): Establezca en true para habilitar el modo de clúster Redis para PubSub. Combinado con PubSub fragmentado, esto es esencial para el escalado horizontal.

Otras adiciones:

  • WEB_FORM_SUBMIT_RATE_LIMIT_MAX_ATTEMPTS: Número máximo de envíos de formularios web permitidos por IP dentro de la ventana de límite de velocidad (predeterminado: 30).
  • WEB_FORM_SUBMIT_RATE_LIMIT_WINDOW_SECONDS: ventana de tiempo en segundos para limitar la tasa de envío de formularios web (predeterminado: 60).
  • HUMAN_INPUT_GLOBAL_TIMEOUT_SECONDS: Número máximo de segundos que una ejecución de flujo de trabajo puede permanecer en pausa esperando la entrada humana antes del tiempo de espera global (predeterminado: 604800, 7 días).
  • ENABLE_HUMAN_INPUT_TIMEOUT_TASK: habilita la tarea en segundo plano que verifica si hay solicitudes de entrada humana vencidas (predeterminado: true).
  • HUMAN_INPUT_TIMEOUT_TASK_INTERVAL: Establece el intervalo (en minutos) para la tarea de verificación de tiempo de espera (predeterminado: 1).
  • ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK: habilita la tarea periódica en segundo plano que actualiza por lotes las marcas de tiempo del token API last_used_at (predeterminado: true).
  • API_TOKEN_LAST_USED_UPDATE_INTERVAL: establece el intervalo (en minutos) para la actualización por lotes de las marcas de tiempo del token API last_used_at (predeterminado: 30).
  • SANDBOX_EXPIRED_RECORDS_CLEAN_BATCH_MAX_INTERVAL: Retraso aleatorio máximo (en milisegundos) entre lotes de limpieza de retención para reducir los picos de presión de DB (predeterminado: 200).

📌 Aspectos destacados adicionales de Changelog

Fiabilidad y corrección

  • Se agregó deduplicación en el momento de la migración y una restricción única para los modelos predeterminados de inquilinos para evitar registros duplicados del modelo predeterminado.
  • Se corrigió un caso extremo de eliminación de herramientas causado por una discrepancia en el tipo de ID del proveedor.
  • Se corrigió una regresión de integración FastOpenAPI donde los usuarios autenticados podían resolverse como anónimos en el archivo remoto API.
  • Se corrigió la detección del tipo de evento de mensaje para respuestas relacionadas con archivos y se ocultó la acción de invitación del espacio de trabajo para usuarios que no son administradores.

Rendimiento y escalabilidad

  • Carga de backend y latencia de consola reducidas con almacenamiento en caché previo del manifiesto del complemento y optimizaciones de consultas AppListApi.
  • Se mejoró la estabilidad de las tareas de datos grandes con sesiones de base de datos divididas, ejecución de limpieza por lotes, ajuste de índice y limitación entre lotes configurable para trabajos de limpieza de retención.

API y capacidades de la plataforma

  • Se agregó un punto final de servicio API para la búsqueda del usuario final con aplicación del alcance del inquilino/aplicación.
  • Se mejoró el comportamiento de actualización del historial de ejecución del flujo de trabajo durante las transiciones del estado de ejecución.
  • Integración mejorada de la herramienta MCP mediante la extracción y generación de informes de metadatos de uso (por ejemplo, campos de token/costo) de las respuestas de MCP.

Seguridad

  • Se eliminó la evaluación dinámica new Function del análisis de ECharts y ahora se devuelven errores de análisis explícitos para código de gráfico no compatible.

Localización

  • Se agregó compatibilidad con el idioma holandés (nl-NL) en los recursos de localización web y mapeo de idiomas del backend.

Guía de actualización

Si es ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK=true, incluya también api_token.

Para conocer antecedentes y detalles, consulte ⚠️ Nota importante de actualización y 🔧 Nota operativa arriba.

Docker Redactar implementaciones

  1. Haga una copia de seguridad de su archivo personalizado docker-compose YAML (opcional)

    cd docker
cp docker-compose.yaml docker-compose.yaml.$(date +%s).bak

  2. Obtenga el código más reciente de la rama principal.

    git checkout main
git pull origin main

  3. Detenga el servicio. Ejecute en el directorio docker

    docker compose down

  4. Hacer una copia de seguridad de los datos

    tar -cvf volumes-$(date +%s).tgz volumes

  5. Servicios de actualización

    docker compose up -d

Implementaciones de código fuente

  1. Detenga el servidor API, el trabajador y el servidor frontend web.

  2. Obtenga el código más reciente de la rama de lanzamiento:

    git checkout 1.13.0

  3. Actualice las dependencias de Python:

    cd api
uv sync

  4. Luego, ejecutemos el script de migración:

    uv run flask db upgrade

  5. Finalmente, ejecute nuevamente el servidor API, el trabajador y el servidor frontend web.
