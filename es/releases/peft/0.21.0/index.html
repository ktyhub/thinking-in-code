Nuevos métodos

Optimizador LoRA precondicional de Riemann

El optimizador LoRA precondicionado de Riemann (#3382), aportado por @smellslikeml, es un nuevo optimizador específico de LoRA similar a LoRA-FA o LoRA+ que aplica un precondicionamiento de Riemann en los gradientes para mejorar el aprendizaje de funciones y evitar ajustes separados de las tasas de aprendizaje para las matrices A y B de LoRA.

Variante de LoRA: Adaptación de valores singulares consciente del conocimiento (KaSA)

KaSA tiene como objetivo identificar valores singulares conscientes del conocimiento a partir del peso base. Luego elimina el conocimiento ruidoso de esos pesos y entrena específicamente los valores singulares más relevantes para la tarea. Implementado en el n.° 3446 por @robbiebusinessacc y @iambogeumkim.

Superajuste (#3518)

Super-Tuning utiliza puntuación de magnitud sin calibración para asignar un presupuesto de ajuste escaso. Con la selección BottomK, Super adapta pesos de baja magnitud, motivado por la idea de que brindan grados de libertad para aprender una nueva tarea mientras deja intactos los pesos previamente entrenados de mayor magnitud. Supra agrega LoRA además de esta escasa actualización. Es una buena opción para explorar la escasez junto con la adaptación de rango superior, particularmente en tareas de ajuste de razonamiento intenso. Gracias a @smellslikeml.

SombraPEFT (#3354)

ShadowPEFT ejecuta una pequeña red de sombra junto al modelo base congelado. Ese estado de sombra se actualiza en cada capa del decodificador, por lo que la adaptación se comparte en toda la pila en lugar de una actualización separada de bajo rango en cada capa lineal específica (como LoRA). Es una buena opción cuando le interesa el rendimiento descendente o OOD y desea permanecer en el mismo rango de parámetros entrenables que LoRA, o cuando desea la pequeña sombra en el borde y la base congelada en la nube. Esto funciona mejor si el modelo de sombra comienza a partir de un modelo pequeño previamente entrenado. Contribuido por @SeanLee97.

Mejoras

  • Acelerar el cálculo de parámetros objetivo de MoE (#3577): para el caso de uso común de un adaptador activo, el cálculo del peso y delta de MoE LoRA se integra en una sola operación baddbmm. Espere ligeras diferencias numéricas en este caso.

  • Admite torchao v0.18.0 al admitir las nuevas subclases de tensor Int8Tensor, Float8Tensor, etc.

  • [Ajuste fino del subespacio ortogonal] (https://huggingface.co/docs/peft/main/en/package_reference/osf) recibió una actualización significativa en el n.° 3524, lo que redujo el uso de memoria en un 22 % y el tiempo de entrenamiento en un 46 % según el punto de referencia MetaMathQA, manteniendo estable la precisión de las tareas y el olvido. Espere ligeras diferencias numéricas, especialmente en fp16, bf16.

  • https://github.com/huggingface/peft/pull/3639: Gracias a @amogh-nagri-11, los métodos de aprendizaje rápido ahora permiten eliminar un adaptador. Para el aviso de adaptación, agregar o cargar un segundo adaptador ya no lo activa automáticamente, de acuerdo con cómo manejan esto otros métodos PEFT.

Cambios

Manejo de dictados de estado refactorizado (#3490)

Un cambio interno movió las rutas de código específicas del método de carga/guardado del dictado de estado a los sintonizadores respectivos. Esto debería ser transparente para el usuario final, se probó exhaustivamente y debería funcionar exactamente igual que antes, pero si sospecha que el modelo se comporta de manera diferente, háganoslo saber.

Capacidad de entrenamiento del adaptador preservada durante la inyección (#3495)

Anteriormente, al cargar o agregar un segundo, tercer adaptador, etc., esto podía afectar el requires_grad del adaptador existente (o modelo base), dependiendo del valor de is_trainable. Este ya no debería ser el caso gracias a @DaoyuanLi2816.

Corrección de errores al combinar el adaptador LoRA (#3111)

La combinación de adaptadores LoRA usando add_weighted_adapter tuvo un error en la ruta SVD que llevó a que la escala LoRA se aplicara dos veces. Esto ya está arreglado.

OFT utiliza backend de cuantificación genérico (#3355)

Pasamos OFT de un backend de cuantificación específico del método al backend de cuantificación genérico. Esto afecta a bitsandbytes, GPT-Q, etc. Esto no debería afectar los puntos de control existentes, pero avísenos si tiene problemas.

Controles más estrictos sobre el manejo del adaptador

  • #3667: inject_adapter_in_model ahora rechaza los métodos PEFT que tienen un estado compartido que viviría en el modelo principal (como VeRA), ya que dicho modelo principal no existe. Contribuido por @CoralGarden52.

  • #3534: Gracias a @LK-maker-007, PEFT ahora arroja un error al agregar un segundo adaptador al modelo PEFT usando add_adapter que apunta a capas no existentes. Antes, el adaptador simplemente no adaptaba nada y guardaba silencio al respecto. peft_model.targeted_module_names y peft_model.targeted_parameter_names ya no contienen duplicados. Todavía están ordenados por orden de inserción (no por conjuntos). Para suprimir posibles errores, capture peft.PeftError.

  • #3504: Al eliminar un adaptador, ahora se verifica si el adaptador está fusionado. Si se fusiona, se genera un error, ya que eliminarlo no eliminaría su efecto. Esto fue contribuido por @DaoyuanLi2816.
