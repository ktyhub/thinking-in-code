clickhouse-java v0.10.0-rc2

Guía de migración de versiones

Además de v0.10.0-rc1

Cambios importantes

  • [client-v2] La interfaz pública ClickHouseBinaryFormatWriter obtuvo dos métodos, setString(String, byte[]) y setString(int, byte[]), para escribir bytes sin formato String/FixedString. El código que solo usa la interfaz no se ve afectado, pero cualquier tercero que implemente ClickHouseBinaryFormatWriter directamente es incompatible con el código fuente y el binario hasta que agregue estos métodos (se requiere recompilar con la nueva versión; de lo contrario, puede ocurrir un AbstractMethodError en tiempo de ejecución).

  • [client-v2] Las respuestas HTTP 503 Service Unavailable ahora aparecen como una falla de estilo de conexión ( java.net.ConnectException) y se reintentan de forma predeterminada. Anteriormente, un 503 se trataba como un error del servidor ( ServerException) y cayó bajo la causa de falla ServerRetryable. Se ha movido a la falla ConnectTimeout. categoría de causa para que las fallas de conectividad/disponibilidad se manejen de manera uniforme con otros errores de conexión. Personas que llaman que excluyó específicamente a ServerRetryable para evitar volver a intentar 503 ahora debería ajustar su Configuración de client_retry_on_failures para excluir ConnectTimeout.

  • [client-v2] Códigos de estado HTTP inesperados/desconocidos (aquellos que client no puede interpretar como una respuesta de ClickHouse) ahora lanza un ClientException en lugar de un ServerException. Dado que el client no puede manejar de manera significativa estas respuestas, se informan como un error del lado cli en lugar de atribuirse al servidor.

Nuevas funciones

  • [client-v2, jdbc-v2] Se agregó compatibilidad con cadenas binarias opcionales a través de la propiedad de configuración binary_string_support (o Client.Builder#binaryStringSupport(boolean)), deshabilitado por defecto. La configuración se resuelve por operación desde la configuración de consulta y client fusionada, por lo que se puede anular para una sola solicitud a través de binary_string_support opción de operación (por ejemplo, QuerySettings#setOption(ClientConfigProperties.BINARY_STRING_SUPPORT.getKey(), true)) independientemente del valor predeterminado de nivel client. Cuando está habilitado, se leen las columnas String y FixedString de nivel superior en un StringValue que conserva los bytes sin procesar en lugar de decodificarlos en un String, lo que permite archivos binarios/no UTF-8. contenido en ida y vuelta byte por byte. StringValue expone los bytes a través de toByteArray()/asByteBuffer() y decodifica perezosamente un String a través de asString() (UTF-8 de forma predeterminada, o un Charset proporcionado por la persona que llama). Valores anidados en el interior Los contenedores (Array, Map, Tuple, Nested, Variant) continúan leyéndose como String, ya que esos tipos no son Se espera que transporte cadenas grandes/binarias. En el lado JDBC, ResultSet#getBinaryStream(int) y ResultSet#getBinaryStream(String) ahora están implementados (anteriormente no soportados) y, junto con getBytes(...), devuelve los bytes de la columna sin formato.

  • [client-v2] Se agregó Client#cancelTransportRequest(String queryId) para cancelar una solicitud en vuelo que aún no se ha realizado. recibió una respuesta del servidor, identificada por la identificación de consulta proporcionada en la configuración de operación. Esto aborta el solicitud en el lado client (cancela la operación IO subyacente) pero no emite un KILL QUERY en el servidor, por lo que una consulta que ya comenzó a ejecutarse puede continuar ejecutándose en el lado del servidor. Se recomienda utilizar el tiempo de espera de operación. entornos donde sea posible; este API está destinado a cancelar explícitamente una solicitud del client.
