clickhouse-java v0.11.0-rc1

Guía de migración de versiones

Cambios importantes

  • [client-v2, jdbc-v2] Las opciones de búfer de socket socket_rcvbuf y socket_sndbuf ya no tiene valor predeterminado. Ahora las opciones se aplican sólo cuando la aplicación las configura. (Client.Builder#setSocketRcvbuf, Client.Builder#setSocketSndbuf, o las propiedades del mismo nombre). Esto se hace para permitir que OS TCP Stack se autoajuste valores. No los configure hasta que sea absolutamente necesario. (https://github.com/ClickHouse/clickhouse-java/issues/3121)

  • [client-v2, jdbc-v2] El error del servidor 159 (TIMEOUT_EXCEEDED) ya no se reintenta de forma predeterminada. Tiene su propio reintentar la causa, ClientFaultCause.ServerTimeoutExceeded, que ServerRetryable no incluye y que no está en la lista predeterminada client_retry_on_failures. Agregue ServerTimeoutExceeded a la lista para volver a intentar este error. (https://github.com/ClickHouse/clickhouse-java/issues/3072)

  • [r2dbc] El artefacto anterior a 1.0.0 ya no es compatible porque R2DBC API alcanzó la versión estable de 1.0.0.

  • [jdbc-v2] DatabaseMetaData#getTables ahora devuelve null en REMARKS (comentario de tabla) y TYPE_SCHEM por predeterminado, porque los metadatos se leen con declaraciones SHOW (consulte la entrada jdbc_metadata_use_show_statements en Nuevo Características). Configure jdbc_metadata_use_show_statements=false para obtener los comentarios de la tabla. (https://github.com/ClickHouse/clickhouse-java/issues/2907)

  • [client-v2,jdbc-v2] Se agregó soporte de compresión ZSTD para el flujo de compresión de bloques y se usa de forma predeterminada para no hacerlo. comprimir solicitudes client. Hasta ahora, en este caso sólo se admitía LZ4. Nota: Biblioteca ZSTD agregada y nativa bibliotecas al paquete JDBC -all porque ahora es necesario trabajar con el servidor. (https://github.com/ClickHouse/clickhouse-java/issues/3105).

Cambios importantes

  • [client-v2] com.clickhouse.client.api.observability.SpanSupport ahora usa la operación QUERY y INSERT constantes (nombres de intervalo QUERY <database> y INSERT <database>.<table>). El atributo db.operation.name está establecido en INSERT para operaciones de inserción y se deja sin configurar para consultas porque las declaraciones SQL no se analizan en client.

  • [client-v2] com.clickhouse.client.api.metrics.OperationMetrics ahora tiene un único constructor, OperationMetrics(ClientStatisticsHolder, OperationType); Se eliminó el constructor sin un tipo de operación. Las métricas son creadas por client, que siempre sabe el tipo de operación que ejecuta y el constructor toma un tipo interno (com.clickhouse.client.api.internal.ClientStatisticsHolder), por lo que no se espera código de aplicación para llamarlo. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

Nuevas características

Tipos de datos

  • [client-v2, jdbc-v2] Se agregó soporte para el tipo de datos geográficos MultiPoint (ClickHouse 26.8+). Anteriormente el tipo era desconocido para el client, por lo que la lectura o escritura de una columna MultiPoint falló con Unknown data type: MultiPoint, y un valor MultiPoint dentro de una columna Geometry falló con un discriminador de variante fuera de rango. MultiPoint es Array(Point) en el cable, exactamente como Ring y LineString, por lo que se lee y escribe como double[][] hasta registros genéricos, lectores binarios, enlace POJO y formato de parámetros SQL, y se lee desde columnas Dynamic. en el controlador JDBC (jdbc-v2) MultiPoint se asigna a java.sql.Types.ARRAY, se devuelve como double[][] desde getObject y como java.sql.Array de getArray, y está reportado por ResultSetMetaData y DatabaseMetaData. ClickCasa 26.8 también agrega MultiPoint al Geometry variante; el servidor lo agrega después de las seis variantes existentes en lugar de ordenarlo por nombre de tipo, por lo que ahora el client mantiene ese orden y decodifica un MultiPoint mantenido en una columna Geometry. Porque MultiPoint comparte su Java representación (double[][]) con Ring y LineString, no se puede seleccionar a través del Geometry basado en formas ruta de escritura: un valor 2D sigue resolviendo en Ring como antes, y escribir MultiPoint requiere un MultiPoint concreto columna. (https://github.com/ClickHouse/clickhouse-java/issues/3048)

  • [client-v2, jdbc-v2] Se agregó soporte para el tipo de datos BFloat16 (ClickHouse 24.11+). Las columnas BFloat16 se leen como Valores Java float (la ampliación no tiene pérdidas) y escritos a partir de valores float/Float, incluso a través de registros genéricos, POJO valores vinculantes, Nullable(BFloat16) y BFloat16 contenidos en las columnas Dynamic/Variant. Al escribir, el client mantiene el 16 bits de alto del float, que coinciden con la conversión Float32 → BFloat16 del propio servidor ClickHouse. En el controlador JDBC (jdbc-v2) BFloat16 se asigna a java.sql.Types.FLOAT / java.lang.Float y se lee y escribe a través del estándar Accesores getFloat/setFloat y getObject, y reportados como tales por ResultSetMetaData y DatabaseMetaData. La lectura o escritura previa de una columna BFloat16 falló con un error de tipo de datos no admitidos. (https://github.com/ClickHouse/clickhouse-java/issues/2279)

  • [client-v2, jdbc-v2] Se agregó soporte para el tipo de datos vectoriales experimental QBit(element_type, dimension[, stride]) (ClickHouse 25.10+; se requiere la configuración del servidor allow_experimental_qbit_type para crear una columna). El nombre del tipo El analizador acepta dos o tres parámetros (el tercero opcional es el paso) y reconoce los tipos de elementos documentados. Int8, BFloat16, Float32 y Float64; un tipo de elemento fuera de ese conjunto se analiza con una advertencia en lugar de rechazado, por lo que se sigue analizando un tipo de elemento del lado del servidor más nuevo. Un valor QBit se transmite a través de RowBinary exactamente como Array(element_type), por lo que se lee y escribe como una matriz Java del tipo de elemento (float[] para BFloat16/Float32, double[] para Float64) a través de registros genéricos, lectores binarios y enlace POJO, a través de un ruta de lectura/serialización dedicada QBit. También se decodifica un QBit contenido dentro de una columna Dynamic/Variant/JSON (su La codificación de tipo binario se vuelve a leer en el tipo concreto QBit(...)). en el Controlador JDBC (jdbc-v2) QBit se asigna a java.sql.Types.ARRAY y se devuelve como java.sql.Array desde getObject/getArray. Anteriormente, QBit era una constante de tipo no implementada y leía o escribía dicha columna. falló. También se lee una columna simple QBit de nivel superior con un tipo de elemento Float32, Float64 o BFloat16. el formato de salida Native: allí el servidor lo transmite utilizando su plano de bits interno transpuesto diseño Tuple(FixedString(...)), y el client invierte esa transposición para reconstruir el mismo Vector float[]/double[] como RowBinary. Un QBit que se pisa a zancadas (QBit(element_type, dimension, stride)), envuelto en Nullable/LowCardinality, anidado dentro de otro tipo (por ejemplo, Array/Tuple/Map(String, QBit(...))), o llevar cualquier otro tipo de elemento aún no está decodificado a través de Native y falla rápidamente con un error claro que le indica a un formato RowBinary como RowBinaryWithNamesAndTypes. (https://github.com/ClickHouse/clickhouse-java/issues/2610)

Observabilidad

  • [client-v2, jdbc-v2] Se agregó una implementación de Micrómetro de las métricas SPI. Client.Builder.setMetricsRecorder(new MicrometerMetricsRecorder(meterRegistry)) informa las métricas de cada client operación a un Micrómetro MeterRegistry: un temporizador db.client.operation.duration por operación completada, un temporizador clickhouse.client.operation.serialization.duration cuando el client midió el paso de serialización, un contador clickhouse.client.operation.count por operación completada y un contador clickhouse.client.operation.retries por intento reintentado. Anteriormente, el client sólo podía vincular sus medidores de grupo de conexiones a Micrómetro, por lo que exportar el Las métricas de las operaciones en sí se dejaron en manos de la aplicación. Los nombres, unidades, descripciones y claves de etiquetas de los medidores son los estándar del SPI - el grabador los deriva a través de MetricsSupport, por lo que son los nombres de MetricName y las teclas de MetricAttribute significan lo mismo que para cualquier otra grabadora. Una operación exitosa no lleva ninguna etiqueta error.type y una fallida sí, por lo que los resultados son series de tiempo separadas del mismo medidor y una la falla que el servidor informó también lleva db.response.status_code; una duración que el client no midió no es se registra, por lo que no se reporta ninguna operación con una duración inventada. Los segundos del SPI se entregan al registro como nanosegundos, debido a que un temporizador Micrometer mantiene su propia unidad de tiempo, por lo que un backend publica la duración en la unidad que espera. El constructor sin argumentos informa a Metrics.globalRegistry, que es lo que jdbc-v2 Se necesita la propiedad jdbc_metrics_recorder, por lo que una conexión JDBC exporta sus métricas a Micrometer nombrando la clase: jdbc_metrics_recorder=com.clickhouse.client.api.observability.micrometer.MicrometerMetricsRecorder - sin código de aplicación. micrometer-core sigue siendo una dependencia opcional de client-v2 y no está sombreado en el all. artefactos, por lo que un client que no utilice esta grabadora no necesita ningún micrómetro en el classpath. (https://github.com/ClickHouse/clickhouse-java/issues/2975)

  • [client-v2, jdbc-v2] Se agregó un SPI de métricas que permite a una aplicación exportar las métricas de las operaciones de client a cualquier back-end de métricas. Client.Builder.setMetricsRecorder(MetricsRecorder) registra una grabadora independiente del backend desde el paquete com.clickhouse.client.api.observability y la propiedad jdbc-v2 jdbc_metrics_recorder nombra la grabadora La conexión clase A se registra con su propio client. Anteriormente, el client recopilaba métricas de operación pero solo devolvía se los entregaba a la persona que llama, por lo que exportarlos quedaba en manos de la aplicación. Cada operación completa reporta exactamente una éxito o un evento de falla, y cada intento reintentado informa un evento de reintento, que proporciona la duración de la operación, el duración de la serialización, el número de operaciones por resultado y el número de reintentos. El SPI sigue el patrón de el span SPI: una implementación extiende la clase base DefaultMetricsRecorder y anula solo lo que le importa acerca, por lo que sigue funcionando cuando el client comienza a informar un evento que no conoce, y el reutilizable La clase MetricsSupport deriva los valores estándar de las mismas estructuras, por lo que su lógica es voluntaria y anulable. Los nombres de métricas, unidades y claves de atributos siguen las convenciones semánticas OpenTelemetry para la base de datos clients donde la convención existe y se colocan bajo clickhouse. donde no existe; están definidos por el MetricName y enumeraciones MetricAttribute, las duraciones se informan en segundos y una duración que el client no midió se informa como MetricsSupport.DURATION_UNKNOWN en lugar de un valor inventado. Los atributos métricos son deliberadamente un conjunto más pequeño. que los atributos de intervalo, porque un atributo de una métrica se convierte en una serie de tiempo: el texto de la declaración, la identificación de la consulta y los parámetros de la declaración permanecen en intervalos. No se registra nada y no se realiza ningún trabajo relacionado con las métricas cuando no hay un registrador registrado. (https://github.com/ClickHouse/clickhouse-java/issues/2975)

  • [client-v2] Se agregó una implementación OpenTelemetry del SPI de observabilidad. Client.Builder.setSpanRecorder(new OpenTelemetrySpanRecorder(openTelemetry)) informa cada operación client y cada solicitud de transporte como un intervalo de OpenTelemetry CLIENT: un intervalo de operación es comenzó como hijo del contexto actual OpenTelemetry, por lo que se une al seguimiento de la aplicación y cada solicitud span, incluido uno por reintento, es hijo de su span de operación. Los nombres de tramo y las claves de atributos son los estándar. del SPI (el registrador los deriva a través de SpanSupport), cada valor se registra con el atributo OpenTelemetry tipo que coincida, y una falla establece el estado del intervalo en ERROR y se registra como una excepción OpenTelemetry evento junto a los atributos error.type y db.response.status_code. La grabadora informa a un suministrado instancia OpenTelemetry, a un Tracer dado a new OpenTelemetrySpanRecorder(Tracer), o a GlobalOpenTelemetry: se lee cuando se inicia un intervalo, cuando se construye sin argumentos. Anteriormente una aplicación que querían tramos OpenTelemetry tenían que escribir ese mapeo ellos mismos. El OpenTelemetry API es una dependencia de sólo compilación de client-v2: la grabadora es utilizada únicamente por una aplicación que ya proporciona opentelemetry-api en tiempo de ejecución, por lo que no se agrega nada al classpath de un client que no lo usa. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

  • [client-v2] Se agregó un SPI de observabilidad que permite a una aplicación observar las operaciones de client como intervalos. Client.Builder.setSpanRecorder(SpanRecorder) registra una grabadora independiente del backend del nuevo Paquete com.clickhouse.client.api.observability: cada operación (una consulta, un comando o una inserción, incluido el llamadas ping y getTableSchema, que ejecutan una consulta) inician un lapso de operación y cada solicitud de transporte realizada para Esto, incluido cada reintento, inicia un período de solicitud secundaria. SpanRecorder y Span son interfaces sencillas; un implementación extiende el clase base DefaultSpanRecorder y anula sólo lo que le importa, por lo que sigue funcionando cuando el client inicia un tipo de lapso que no conoce. Se llama primero al registrador registrado y recibe todo lo que sabe el client. sobre la operación (su QuerySettings/InsertSettings, la declaración, la tabla de destino, el tamaño del lote, el punto final, las métricas de la operación completada y la falla), por lo que es libre de registrar lo que necesite y en cualquier forma; la clase reutilizable SpanSupport deriva los nombres de tramo estándar y los valores de atributos de esos mismos estructuras y es llamado por una implementación de grabadora que las quiere, por lo que su lógica es voluntaria y anulable. lapso los nombres y las claves de atributos siguen las convenciones semánticas OpenTelemetry para bases de datos y intervalos HTTP client; las llaves están definidos por la enumeración SpanAttribute y los valores se derivan de SpanSupport, por lo que todos los registradores que lo utilizan reportan la misma información (texto de declaración, base de datos de destino y tabla, ID de consulta, parámetros de declaración, tamaño de lote, el primer punto final configurado en el intervalo de operación y el número por intento dirección del servidor y puerto en los intervalos de solicitud, estado HTTP, filas devueltas y el tipo de error y código de error ClickHouse en caso de fallo). El resultado de una operación completada se informa por tipo de operación - recordQuerySuccess para una lectura y recordInsertSuccess para una inserción, porque las métricas que describen una lectura no son las que describir una escritura: una consulta informa db.response.returned_rows, clickhouse.response.read_rows y clickhouse.response.read_bytes, un inserto informa clickhouse.response.written_rows y clickhouse.response.written_bytes. La misma distinción está disponible en las propias métricas a través del nuevo OperationMetrics#getOperationType(), que devuelve el nuevo com.clickhouse.client.api.metrics.OperationType - el tipo de llamada que realizó la aplicación, por lo que un comando que escribe se informa como una consulta. Se inicia un lapso de operación en el hilo que llama, por lo que se une al seguimiento ambiental de la persona que llama incluso cuando la operación se ejecuta en el ejecutor del client, y finaliza exactamente una vez por cada operación que comienza. Anteriormente, el client no presentaba ningún gancho para rastrear, por lo que un la aplicación no pudo atribuir una consulta o una solicitud reintentada a su propio seguimiento. Cuando no hay ninguna grabadora registrada nada se registra y no se realiza ningún trabajo relacionado con el intervalo, por lo que la ruta predeterminada no se modifica. Una implementación OpenTelemetry del SPI está disponible como OpenTelemetrySpanRecorder. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

Mejoras

  • [migration-helpers] Se agregó el módulo migration-helpers que contiene ConfigurationMigrationHelper y ConfigPropertyCache para convertir propiedades de configuración y URL de conexión del formato v1 (0.7.1) al v2 (0.9.8+) formato (prefijando automáticamente la configuración del servidor ClickHouse con clickhouse_setting_, encabezados personalizados con http_header_ y asignación de claves de propiedad renombradas).

  • [client-v2, jdbc-v2] Se agregó la selección del conjunto de cifrado TLS. Client.Builder.setSSLCipherSuites(String...) (client-v2) y la propiedad de conexión ssl_cipher_suites separada por comas (client-v2 y jdbc-v2) restringen los conjuntos de cifrado habilitado en conexiones seguras; cuando no está configurado, se utilizan los valores predeterminados de transporte. La selección del conjunto de cifrado es independiente de la configuración trust y ssl_mode. (https://github.com/ClickHouse/clickhouse-java/issues/2882)

  • [client-v2, jdbc-v2] Se agregó soporte para columnas Nested(...) no aplanadas (tablas creadas con flatten_nested = 0). Anteriormente, el autor de RowBinary lanzaba UnsupportedOperationException: No compatible tipo de datos: Nested when inserting such a column. client-v2 now serializes a Nested(f1 T1, ..., fN TN) columna de la misma manera que se lee, de manera idéntica a Array(Tuple(T1, ..., TN)) (un recuento de filas variable seguido de una tupla por fila anidada) - para que pueda escribirse a través de la ruta de inserción / RowBinaryFormatWriter. en jdbc-v2 una columna Nested(...) no aplanada se expone como un JDBC ARRAY cuyo tipo de elemento es Tuple(f1 T1, ..., fN TN): se puede insertar a través de Connection#createArrayOf/setArray o setObject y vuelve a leer getArray/getObject, y java.sql.Array#getResultSet() itera las filas anidadas como Pares (INDEX, VALUE) donde cada VALUE es la tupla. (https://github.com/ClickHouse/clickhouse-java/issues/2477)

  • [client-v2, jdbc-v2] Se agregó registro en rutas de diagnóstico y errores previamente silenciosas (no funcionales ni públicas-API cambio). (https://github.com/ClickHouse/clickhouse-java/issues/2969)

  • [jdbc-v2] DatabaseMetaData#getSchemas, #getTables y #getColumns ahora leen metadatos con SHOW DATABASES, SHOW TABLES y DESCRIBE TABLE en lugar de las tablas system.databases, system.tables y system.columns. el El servidor no muestra algunas tablas en las tablas del sistema de forma predeterminada (por ejemplo, tablas de DataLakeCatalog bases de datos), por lo que las herramientas que utilizan DatabaseMetaData no los encontraron. La nueva propiedad del controlador jdbc_metadata_use_show_statements (true predeterminado) selecciona la implementación; configúrelo en false para usar el sistema mesas. Con las sentencias SHOW, getTables() devuelve null en REMARKS (comentario de tabla) y TYPE_SCHEM; getColumns() envía una consulta DESCRIBE TABLE para cada tabla que coincide y omite una tabla que se eliminó mientras tanto, que el usuario no puede describir, o cuyos metadatos del lago de datos no pueden leerse. Todas las demás columnas y valores son lo mismo. (https://github.com/ClickHouse/clickhouse-java/issues/2907)

Corrección de errores

  • [jdbc-v2] Se corrigió una declaración INSERT ... VALUES cuya lista de valores contiene un literal, una expresión (por ejemplo, ? + 1) o, con el analizador JAVACC, una secuencia de escape JDBC o un parámetro de consulta, escrito con el escritor RowBinary cuando beta.row_binary_for_simple_insert está habilitado. El escritor toma un valor enlazado por columna, por lo que los valores enlazados se cambiaron a otras columnas: la declaración falló con un error engañoso o almacenó datos incorrectos sin ningún error. el Los analizadores no informaron tales valores: el analizador JAVACC descartó el resultado de su verificación de lista de valores y el Los analizadores ANTLR4 solo informaron llamadas a funciones. Ahora el escritor se usa sólo para una lista de valores de marcadores de posición ?, y otras declaraciones utilizan la ruta estándar PreparedStatement. (https://github.com/ClickHouse/clickhouse-java/issues/3083)

  • [client-v2,jdbc-v2] - Se reemplazó la compresión HTTP LZ4 lenta con flujo de compresión desde Biblioteca lz4-java. Client usa Apache Compress para manejar la compresión HTTP (porque tiene una fábrica conveniente para muchos métodos de compresiones. Sin embargo, Apache Compress utiliza una implementación lenta de LZ4, lo que provoca inserciones muy lentas. ahora lz4-java utilizado para inserción. La consulta aún es lenta, pero se solucionará en futuras versiones (es necesario refactorizar y personalizar). implementación para solucionarlo). El uso de ZSTD para consultas debería resolver el problema. (https://github.com/ClickHouse/clickhouse-java/issues/2273).

  • [client-v2] Se corrigió la escritura de un valor String en una columna UUID (también como elemento Array/Tuple o Map). clave) fallando con ClassCastException. La cadena ahora se analiza con UUID.fromString; una cadena que no puede analizar es rechazado en el client con un IllegalArgumentException. (https://github.com/ClickHouse/clickhouse-java/issues/3132)

  • [client-v2] Se corrigió el error de lectura de una columna Nullable en el formato Native con Error al leer el bloque... Se alcanzó el final de la secuencia antes de leer todos los datos o se devolvieron valores de filas incorrectas. El lector consumió un valor nulo. marcador antes de cada valor, que es el diseño RowBinary. Native` es en columnas: almacena un mapa nulo de un byte por fila antes de los valores de toda la columna, y una fila nula todavía tiene un valor de marcador de posición. Por lo tanto, los marcadores fueron tomado de los bytes de valor y la columna se leyó desalineada. El mapa nulo ahora se lee como un bloque. (https://github.com/ClickHouse/clickhouse-java/issues/3137)

  • [client-v2] Columnas geográficas fijas (Point, Ring, LineString, MultiPoint, Polygon, MultiLineString, MultiPolygon) se lee mal desde el formato Native. El lector decodificó una columna geográfica fila por fila con RowBinary decodificadores, mientras que Native lo escribe en columna principal: un bloque Point regresó con sus coordenadas codificadas en filas y no hubo error, y todos los demás tipos geográficos desincronizaron el bloque y fallaron con Non-empty typeName is required. Ahora se decodifica una columna geográfica del diseño nativo: los dos Float64 subcolumnas de un punto y desplazamientos acumulativos más los elementos aplanados para los niveles de la matriz, y devuelve lo mismo valores como RowBinaryWithNamesAndTypes, que no cambia. (https://github.com/ClickHouse/clickhouse-java/issues/3088)

  • [client-v2, jdbc-v2] Se corrigió un tipo de columna con un elemento JSON seguido de un tipo parametrizado, por ejemplo Tuple(JSON, FixedString(3)), analizado incorrectamente. JSON es válido con y sin lista de parámetros, y el analizador buscó el paréntesis de apertura de esa lista en cualquier lugar después de la palabra clave, por lo que tomó los paréntesis de la siguiente elemento para los parámetros del elemento JSON. Todo hasta esos soportes se consumió, lo que redujo el elementos entre ellos, o falló con Unknown data type: <parameter> cuando el siguiente tipo tenía más de un parámetro, por ejemplo Tuple(JSON, Decimal(10, 2)). Leer una columna de este tipo y Client#getTableSchema de una tabla que tiene uno, falló o devolvió un tipo incompleto. Una lista de parámetros ahora se reconoce sólo cuando se activa inmediatamente. sigue la palabra clave JSON. (https://github.com/ClickHouse/clickhouse-java/issues/3098)

  • [jdbc-v1] Se corrigió que WITH RECURSIVE <name> AS (...) no se pudiera analizar. La gramática de JavaCC no conocía la Palabra clave RECURSIVE, por lo que se tomó como el nombre de la primera expresión de tabla común y se rechazó la declaración. La consulta en sí aún se ejecutó, porque el controlador vuelve a enviar el SQL original, pero cada La llamada createStatement/prepareStatement registró un error de análisis WARN y la declaración se clasificó como desconocida. RECURSIVE ahora se acepta después de WITH y sigue siendo utilizable como un identificador normal (columna, alias, tabla o CTE). nombre). (https://github.com/ClickHouse/clickhouse-java/issues/3122)

  • [jdbc-v2] Se corrigió que WITH RECURSIVE <name> AS (...) no se pudiera analizar. Ninguna gramática SQL conocía el RECURSIVE palabra clave, por lo que se tomó como el nombre de la primera expresión de tabla común y la declaración fue rechazada. la consulta todavía se ejecutó, porque el controlador vuelve a enviar el SQL original, pero cada createStatement / La llamada prepareStatement registró un error de análisis (WARN con el backend JavaCC) y la declaración se clasificó como desconocido. RECURSIVE ahora es aceptado después de WITH por las gramáticas JavaCC y ANTLR4, y sigue siendo utilizable como identificador ordinario (columna, alias, tabla o nombre del CTE). El lexer tenía no hay token heredoc, por lo que dicho organismo generó un error de Lexer que dejó la declaración clasificada como UNKNOWN: se informó un INSERT como una declaración que contiene un conjunto de resultados sin nombre de tabla ni posiciones de lista de valores, que deshabilita la plantilla de valores por lotes y las rutas basadas en nombres de tablas. Un heredoc ahora se expresa como una sola cadena. literal. (https://github.com/ClickHouse/clickhouse-java/issues/3029)

  • [client-v2, jdbc-v2] Registros ruidosos y potencialmente sensibles reducidos; El SQL que no se puede analizar ya no se registra en WARN (podría contener credenciales/PII). (https://github.com/ClickHouse/clickhouse-java/issues/2970)

  • [client-v2] Se corrigió que los valores BigDecimal escritos en una columna Dynamic se truncaran silenciosamente cuando el valor la escala excedió la escala máxima del ancho inferido y arrojó un error de desbordamiento cuando el valor llevaba un número entero parte (por ejemplo, 19.99). La inferencia de tipo Dynamic ahora dimensiona el ancho de Decimal para contener tanto los dígitos enteros como los la escala del valor, mantiene la escala tan ancha como lo permita el ancho sin robar espacio a la parte entera, y escribe la escala de columna real en la etiqueta de tipo Dynamic. Los valores que ya han regresado sin pérdidas no se modifican. (https://github.com/ClickHouse/clickhouse-java/issues/2966)

  • [client-v2] Se corrigió el lanzamiento del escritor RowBinary UnsupportedOperationException: Unsupported data type: SimpleAggregateFunction al insertar en un Columna SimpleAggregateFunction(func, T) (el lector ya admitía estas columnas). El valor ahora está serializado. de manera idéntica a su tipo subyacente T, escribiendo el byte de marcador nulo Nullable cuando el tipo subyacente es anulable (por ejemplo, SimpleAggregateFunction(anyLast, Nullable(String))), reflejando la ruta de lectura. (https://github.com/ClickHouse/clickhouse-java/issues/2477)

  • [client-v2] Se corrigió que la etiqueta de tipo Dynamic para un tipo SimpleAggregateFunction se escribiera como simple 0x2Ebyte. La codificación de tipo binario también lleva el nombre de la función, sus parámetros y sus tipos de argumentos, por lo que el El servidor leyó el nombre de la función de los bytes de valor que siguieron y fallaron con ATTEMPT_TO_READ_AFTER_EOF. Dado que el client nunca infiere un SimpleAggregateFunction a partir de un valor de Java y el El lector no puede volver a leer uno de una columna Dynamic, esto ahora falla rápidamente con una clara ClientException en lugar de producir una secuencia RowBinary corrupta (el mismo tratamiento que ya recibe QBit). (https://github.com/ClickHouse/clickhouse-java/issues/3007)

  • [client-v2, jdbc-v2] Se corrigieron varios defectos de la capa de registro. En client-v2, HttpAPIClientHelper.shouldRetry arrojó un ClassCastException cuando se envolvió un ServerException reintentable como la causa de otra excepción (la rama coincidió con la causa pero el elenco usó la excepción externa); la decisión de reintento ahora se toma de cualquier La excepción es el ServerException. También en client-v2, ahora se produce un error al generar la cadena de versión HTTP client. registrado en WARN con el archivo arrojable adjunto en lugar de un mensaje INFO simple que descartó la causa. En jdbc-v2, un error al cerrar la respuesta después de un error de consulta ahora registra el error de cierre en lugar del excepción externa ya propagada. (https://github.com/ClickHouse/clickhouse-java/issues/2968)

  • [client-v2] Se corrigieron los parámetros de consulta escalares String que contenían una pestaña (0x09), una nueva línea (0x0a) o una barra invertida. mal manejado a través de la interfaz param_<name> del servidor. Un {name:String} El valor del parámetro es analizado por el servidor con deserializeTextEscaped, que trata una pestaña sin formato o una nueva línea como un campo. delimitador (fallando la consulta con BAD_QUERY_PARAMETER: ... isn't parsed completely) y una barra invertida sin formato como inicio de una secuencia de escape (corrompendo silenciosamente el valor, por ejemplo, C:\temp se convirtió en C:<tab>emp). Client.query(sql, params, ...) ahora escapa a la barra invertida, tabulación y nueva línea en un escalar String parámetro para que cualquier valor sea de ida y vuelta; todos los demás caracteres que el servidor lee palabra por palabra, incluidas las comillas simples y retorno de carro: no se modifica, por lo que los valores Identifier y los literales Array/Map preformateados se pasan como String sigue siendo de ida y vuelta. El controlador JDBC (jdbc-v2), que alinea los parámetros como literales SQL y ya se ha escapado la barra invertida y las comillas simples no se modifican y están cubiertas por una nueva prueba de regresión. (https://github.com/ClickHouse/clickhouse-java/issues/2781)

  • [client-v2] Se corrigió un valor de parámetro de consulta null que se enviaba como la cadena literal "null", por lo que Client.query(sql, params, ...) vinculando un Java null a un marcador de posición escalar como {x:Nullable(Decimal128(8))} fue rechazado por el servidor con BAD_QUERY_PARAMETER (Value null cannot be parsed as Nullable(...)). Un escalar de nivel superior null ahora se envía como ClickHouse \N centinela NULL por lo que vincula SQL NULL; un null anidado dentro de un valor de parámetro Array/Map continúa renderizándose como la palabra clave SQL NULL. (https://github.com/ClickHouse/clickhouse-java/issues/2977)

  • [client-v2] Se corrigió la decodificación de matriz binaria para tipos de elementos que aceptan valores NULL, por lo que Array(Nullable(Float64)) y similares Las columnas ahora devuelven matrices en cuadros como Double[] en lugar de Object[]. Esto mantiene alineadas las matrices que admiten nulos con su tipo de elemento y al mismo tiempo se conserva el respaldo Object[] existente para matrices variantes/dinámicas/geométricas. (https://github.com/ClickHouse/clickhouse-java/issues/2846)

  • [client-v2] Se corrigieron las columnas Float32/Float64 que arrojaban ClassCastException cuando un valor de un cuadro no coincidía El tipo numérico se suministró a través de la superficie de inserción tipo Object, por ejemplo, un Double (el tipo natural de literal Java como 1.5) para una columna Float32, o Float para una Columna Float64. El serializador RowBinary ahora reduce cualquier Number (y, como las columnas Int*, un String/ Boolean) a Number#floatValue()/Number#doubleValue(), por lo que las columnas flotantes aceptan los mismos tipos de valor que las columnas enteras ya lo hicieron. (https://github.com/ClickHouse/clickhouse-java/issues/2930)

  • [client-v2] Se corrigió un NullPointerException al serializar un valor null en un valor no anulable Columna Enum8/Enum16. SerializerUtils.serializeEnumData no tenía protección null, por lo que un null en una enumeración no anulable La columna alcanzó value.getClass() y falló en la ruta de inserción RowBinary con un NPE confuso en lugar de un error claro. Ahora arroja IllegalArgumentException nombrando la columna, consistente con el IllegalArgumentException existente. para otros valores de enumeración no admitidos. Las columnas de enumeración que admiten valores NULL no se ven afectadas. (https://github.com/ClickHouse/clickhouse-java/issues/2931)

  • [client-v2] Se corrigió la corrupción de datos silenciosa al serializar un Java null en un formato no anulable. Columna Array(...) vía RowBinaryFormatWriter. RowBinaryFormatSerializer.writeValuePreamble Array con carcasa especial, que emite un byte marcador perdido encima de la longitud de la matriz; el servidor lee el byte extra como un fila adicional fantasma (inserciones de una sola columna) o como un cambio de columna que falló la inserción con CANNOT_READ_ALL_DATA (inserciones de varias columnas). Un Array no anulable no puede representar un null, por lo que ahora arroja IllegalArgumentException nombrar la columna, de forma coherente con cualquier otro tipo que no admita valores NULL, tanto en RowBinary como en Caminos RowBinaryWithDefaults. Las matrices vacías ([]) aún se serializan correctamente y las columnas Dynamic, que pueden contener un null como el tipo implícito Nothing no se ven afectados. (https://github.com/ClickHouse/clickhouse-java/issues/2938)

  • [client-v2] Se corrigió la clasificación de errores de inserción de POJO para que se produzcan fallas de escritura en el transporte, como java.net.SocketException: La tubería rota (error de escritura) ahora aparece como errores de transferencia/red en lugar de aparecer como errores Excepción de serialización de datos. Esto solo cambia el tipo de excepción reportado para fallas de transporte del cuerpo de solicitud durante Client.insert (...); Los errores reales de reflexión/serialización de POJO todavía se informan como DataSerializationException. (https://github.com/ClickHouse/clickhouse-java/issues/2729)

  • [client-v2] Se corrigió la decodificación de variantes binarias para los campos de longitud y recuento, por lo que los valores desbordados o demasiado largos fallan un IOException en lugar de ser decodificado en valores int corruptos o negativos. (https://github.com/ClickHouse/clickhouse-java/issues/2902)

  • [client-v2] Se corrigieron los parámetros de consulta del contenedor que se enviaban sin comillas, por lo que se vinculaba Client.query(sql, params, settings) un List<LocalDate> (o una matriz/Map) a un marcador de posición como {ids:Array(Date)} fue rechazado por el servidor con CANNOT_PARSE_INPUT_ASSERTION_FAILED. Los valores de los parámetros ahora están formateados por DataTypeConverter#convertParameterToString(Object) antes de ser enviado: pase el valor Java sin formato y el client representa en el texto que espera la interfaz param_<name> del servidor: un Collection, una matriz (objeto o primitivo) o Map. se convierte en ClickHouse Array (['2026-05-13']) / Map ({'k':'v'}) texto con String/temporal deja comillas simples y las hojas numéricas/booleanas se dejan sin comillas, mientras que un escalar se pasa sin comillas como antes. Sin manual Se necesita un formato previo de los parámetros del contenedor. (https://github.com/ClickHouse/clickhouse-java/issues/2897)

  • [client-v2] Se corrigieron las columnas DateTime/DateTime64 declaradas con un nombre sintético de zona horaria con desplazamiento fijo (Fixed/UTC±HH:MM:SS, por ejemplo, Fixed/UTC+05:30:00) se lee silenciosamente en UTC en lugar del desplazamiento declarado. el El lector RowBinary ahora recupera el desplazamiento del tipo declarado de la columna. (https://github.com/ClickHouse/clickhouse-java/issues/2876)

  • [jdbc-v2] Se corrigieron los backends del analizador SQL ANTLR4 (jdbc_sql_parser=ANTLR4 y ANTLR4_PARAMS_PARSER) que lexaban el cuerpo de una cadena heredoc ($$body$$, $tag$body$tag$) como SQL ordinario. El lexer no tenía token heredoc, por lo que cada $ se eliminó como un carácter no reconocido y el cuerpo se analizó como identificadores, operadores y separadores de declaraciones: El cuerpo que todavía parecía SQL válido fue silenciosamente mal analizado (nombre de tabla incorrecto y posiciones de la lista de VALORES), y un cuerpo que contiene ;, así como el documento heredoc vacío $$$$, se informó como un error de análisis, que clasifica un INSERT como un Declaración que contiene el conjunto de resultados sin posiciones de lista de valores. Un heredoc ahora se expresa como un literal de cadena única y aceptado como un valor literal (listas INSERT ... VALUES, expresiones de columna, configuraciones) y un $ dentro de un identificador (a$b, o una etiqueta sin terminar como $foo$bar) forma parte del identificador, tal como lo lee el servidor. (https://github.com/ClickHouse/clickhouse-java/issues/3031)

  • [jdbc-v2] Se corrigió el lanzamiento del escritor RowBinary beta (DriverProperties.BETA_ROW_BINARY_WRITER). NoSuchColumnException para declaraciones INSERT cuyos nombres de columna están entre comillas invertidas, en particular las canónicas Nested forma de cable de subcolumna `directory`.`id`. The SQL parser now unescapes each backtick-quoted INSERT componente de nombre de columna antes de la búsqueda de esquema de servidor por nombre, que coincide con la forma en que están los identificadores de tabla y base de datos ya manejado. (https://github.com/ClickHouse/clickhouse-java/issues/2896)
