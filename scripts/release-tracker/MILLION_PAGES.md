# 百万页 + 免费：怎么做到

> 结论先说：**能做，但不是靠生成一百万个 HTML 文件。**
> 一百万个 HTML 需要 17.4 GB，构建 13 小时，任何免费平台都装不下。
> 一百万个 URL 只需要 0.68 GB 数据和一台按需渲染的边缘函数。

数据来自 `python plan_million.py`（实测基线，非估算）。

---

## 一、为什么"全静态预渲染"是死路

现有 7 语言 = 5,427 页 / 116.6 MB / 构建 287 秒。按当前每页成本线性外推：

| 指标 | 7 语言（现状） | 249 语言（全量） |
|---|---|---|
| 页面数 | 5,427 | **828,711** |
| 产物体积 | 116.6 MB | **17.4 GB** |
| 构建耗时 | 4.8 分钟 | **13.3 小时** |
| 需要 sitemap 分片 | 1 | **19** |

对照免费平台硬限制：

| 平台 | 硬限制 | 249 语言装得下吗 |
|---|---|---|
| GitHub Pages | 1 GB / 部署 10 分钟 | ❌ 体积超 17 倍，构建超 80 倍 |
| Cloudflare Pages Free | 20,000 个文件 / 构建 20 分钟 | ❌ 文件数超 41 倍 |
| Cloudflare Workers + R2 | 无文件数限制 / R2 免费 10 GB | ✅ 见路线 B |

**体积和构建时间都随页数线性增长，没有任何静态平台能免费承载 80 万页。**

### 静态路线的真实分水岭：35 种语言

很多人会想"那就先扩到 Tier 1+2 的 35 种语言，静态扛得住"。实测不行：

| 语言数 | 只做聚合页 | 含 Release 详情页 |
|---|---|---|
| 7 | 5,427 页 / 0.11 GB ✅ | 5,427 页 / 0.11 GB ✅ |
| 35 | ~12,000 页 / 0.25 GB ✅ | **100,686 页 / 2.1 GB ❌** |
| 249 | ~60,000 页 / 1.3 GB ❌ | **828,711 页 / 17.4 GB ❌** |

只要想让**详情页**进多语言，35 种语言就已经 2.1 GB，超过 GitHub Pages 的 1 GB。
换句话说：静态方案只能承载"多语言导航 + 聚合页"，一旦详情页要翻译就必须换架构。

## 二、关键算术：页面是笛卡尔积，数据才是稀缺资源

这是整个方案的支点。

```
828,711 个页面  =  1,529 篇英文原文  ×  249 种语言  ×  模板
  17.4 GB       =  9.3 MB 原文        ×  249        （gzip 后 0.68 GB）
```

- 要**存**的是 9.3 MB 原文 + 各语言译文 = gzip 后 **0.68 GB**
- 要**发**的是 82.9 万个页面 = **17.4 GB**

差 **25 倍**。所以正确的做法是：存数据，渲染页面，不存页面。

页面 = 数据 × 模板 这个结构，天生适合按需渲染 + 边缘缓存。

## 三、三条路线

### 路线 A · 全静态预渲染

生成全部 82.9 万个 HTML。

- 产物 17.4 GB，构建 13.3 小时
- ❌ GitHub Pages 超 17 倍，CF Pages 文件数超 41 倍
- ❌ 每次改一行模板要重新构建 13 小时
- **不可行**

### 路线 B · 混合：主力语言静态 + 长尾语言边缘渲染 ✅ 推荐

- **Tier 1 的 7 种语言**照现在的样子预渲染成静态文件 → 5,427 页 / 0.11 GB
  - 占 GitHub Pages 1 GB 额度的 **11.4%**
  - 构建 4.8 分钟，CI 完全无压力
- **剩余 242 种语言**的 823,284 个 URL 由 Cloudflare Worker 按需渲染
  - 模板复用同一套 Astro 组件，数据从 R2 读
  - 译文数据 gzip 后 0.68 GB → 占 R2 免费 10 GB 的 **6.8%**
  - R2 egress 免费，Workers 免费 10 万请求/天

### 路线 C · 纯边缘渲染

一个 HTML 都不落盘，全部按需渲染。技术上更纯粹，但把主力语言的稳定性也押在 Worker 上，没必要。

> 按页均月访问 0.5 次估算：82.9 万页 ≈ 41.4 万次月访问，其中 15% 穿透缓存打到
> Worker ≈ 6.2 万请求/月，占免费额度 300 万/月的 **2.1%**。再叠加 Cache Rules
> 让 CDN 在 Worker 之前命中，实际消耗更低。

## 五、翻译为什么也是免费的

`translate.py` 已经是**内容寻址缓存**：key = `sha256(文本 + 目标语言)`。
同一段文本在任何项目、任何版本、任何重跑中都不会被翻第二次。

| 项目 | 数量 |
|---|---|
| 唯一原文 | 1,529 篇 |
| 每篇切块（3,400 字符上限） | 平均 2 块 |
| 一次性总任务（249 语言） | 761,442 块 |
| 实测吞吐（8 并发，5 通道轮询） | 14 块/秒 |
| **一次性总耗时** | **15.1 小时** |
| 日常增量（每天 10 篇新 release） | 4,980 块 ≈ **5.9 分钟** |

多通道全部免费：5 个 Google 免密端点 + DeepL Free / Cloudflare Workers AI / LibreTranslate（配了环境变量自动入池）。

**15 小时是一次性成本，之后每天 6 分钟。** 这是"量大可以轮询"能成立的根本原因。

## 六、百万 URL ≠ 百万收录页（这一节最重要）

技术上能出 82.9 万个页面，不代表应该让 Google 收录。

Google 的 **scaled content abuse** 政策明确把"大批量自动转换/翻译、几乎没有附加价值"的页面定义为垃圾内容。82.9 万个机翻页一次性放开，后果是整站（包括现在表现最好的英文原文页）被降权。

所以把两件事彻底拆开：

| | URL 空间 | 索引空间 |
|---|---|---|
| 谁能访问 | 全部 82.9 万 | — |
| 谁进 sitemap | — | 只进闸门放量的语言 |
| 默认状态 | 全部可访问、可分享 | **noindex** |

实现见 `site/src/data/index-gate.json` + `site/src/lib/gate.ts`：

- 新增语言默认 `noindex`，页面照常生成、照常能访问
- 只有 `status: "index"` 的语言才进 sitemap、才不输出 `noindex`
- 闸门关闭的语言不出现在 hreflang 里（noindex 页上的 hreflang 会被忽略，留着是自相矛盾的信号）
- 放量和回滚都只改这一个 JSON 文件

**这带来的真正好处：URL 空间可以提前铺满百万级，而索引页数量由你控制。**
两条曲线解耦后，扩语言不再是"要么全上、要么不上"的赌博。

### 放量节奏（已写进 index-gate.json）

| 批次 | 语言 | 新增 URL | 前置条件 |
|---|---|---|---|
| 1（已完成） | en, zh, ja, de, fr, es, pt | 5,427 | — |

## 七、已经落地的部分

| 文件 | 作用 |
|---|---|
| `site/src/data/index-gate.json` | 索引闸门配置，7 语言已放量，其余默认关闭 |
| `site/src/lib/gate.ts` | 闸门判定：`isIndexable` / `shouldNoindex` / `gateSnapshot` |
| `site/src/layouts/Shell.astro` | 自动 noindex + hreflang 过滤掉闸门关闭的语言 |
| `site/astro.config.mjs` | sitemap 按闸门过滤，`entryLimit: 45000` 支持百万级分片 |
| `site/src/layouts/DocLayout.astro` | 支持 noindex，旧站占位页统一 noindex |
| `scripts/release-tracker/plan_million.py` | 三条路线的真实账本，改语言数可重算 |
| `scripts/release-tracker/seo_audit.py` | 发布前审计：闸门与产物是否一致、hreflang 是否指向 noindex、薄内容页 |

审计实测（当前构建）：

```
页面总数 5,429
  可索引 5,419（99.8%）   noindex 10
  sitemap 需要 1 个分片
  hreflang 链接 15,175 条，指向 noindex 页面的 0 条
  ✅ 闸门与产物一致
```

noindex 的 10 个页面全部是旧站语言占位页（`/en/chapter_*` 6 个、`/ar` `/ko` `/ru` 各 1 个、
另 1 个 404 兜底页），它们可访问、可分享，但不参与排名。

**已知遗留**：73 个中文章节聚合页（`/zh/chapter_*`）标题直接取自目录名，
短到 "ai" 这种程度，正文只有目录列表。它们有 h1、有面包屑、是真实导航入口，
但标题质量偏低。这属于内容治理，需要人工给每个章节定中文名（补 `.pages` 文件），
不适合用脚本批量猜。

## 八、还没做的一步

路线 B 的边缘渲染层还没搭，这是唯一需要外部资源授权的部分：

1. 创建 R2 bucket，把 249 语言的译文数据（0.68 GB）传上去
2. 写一个 Worker：读 `/{locale}/releases/{project}/{version}` → 取数据 → 套模板 → 返回 HTML
3. 配 Cache Rule 让 HTML 在 CDN 层命中（命中不进 Worker，不消耗请求数）
4. 自定义域名路由：`/ja/*`、`/ko/*` 等长尾语言前缀交给 Worker

**在此之前，先把 Tier 2 的 9 种语言按批次 2 放开，用现有 GitHub Pages 就能跑完**——这是零成本、零风险的下一步。

## 九、口径提醒

- 82.9 万页 ≈ "百万量级"，不是精确 100 万。要真超 100 万，加 tag / topic / 时间归档聚合页即可（每语言再加 200+ 页 × 249 = 5 万页，仍在同一架构内）。
- 所有数字都用 `plan_million.py` 从仓库实测数据推导，改语言数、改页均访问量可重新出账。
- 平台的免费额度会变，脚本里 `QUOTA` 字典集中维护，改一处即可全表重算。
