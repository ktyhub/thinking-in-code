# 千万级页面 + 多平台：怎么拆、拆到哪

> 上一份 [`MILLION_PAGES.md`](./MILLION_PAGES.md) 解决的是"百万 URL 能不能免费"。
> 这份解决"千万页 + 多平台"，结论完全不同：**静态层要从"承载全部"退到"只承载两种语言"**。

所有数字来自 `python plan_scale.py` 和 `python shard_plan.py`，可复现。

---

## 一、先把量级算清楚

你说的"百万级版本 × 全球语言 = 千万级网页"是对的，但要落到具体基数：

| | 当前 | 千万页目标 |
|---|---|---|
| 追踪仓库 | 43 | **约 1,120** |
| Release 条数 | 1,532 | **40,000**（要扩 26 倍） |
| 语言 | 7（已上线）/ 249（可用） | 250 |
| 页面 | 5,452 | **10,056,000** |

页面构成：详情页 1,000 万 + 项目页 24.9 万 + 聚合页 5.6 万。

**第一个结论：千万页首先是内容工程，不是页面工程。** 43 个仓库撑不到，得先扩到一千个量级的追踪源。

---

## 二、单平台为什么必然崩

| 指标 | 千万页全静态 |
|---|---|
| 产物体积 | **215.4 GB** |
| 构建耗时 | **164.4 小时** |
| 每语言页面 | 4.12 万页 / **0.86 GB** |

0.86 GB 这个数字很关键：**一种语言的页面就几乎占满一个 GitHub Pages 项目**。
249 种语言 = 249 个仓库、215 GB。这不是"平台选得不对"，是路线本身不成立。

---

## 三、真正的解法：静态层缩到最小，长尾全部下沉

### 分层不是"把百万页均摊"，而是职责重划

| 层 | 承载 | 页数 | 理由 |
|---|---|---|---|
| **静态层** | en + zh 的详情页与聚合页 | 80,448 | 流量最大、最不该依赖函数冷启动、最需要稳定 |
| **边缘层** | 其余 248 语言的详情页与聚合页 | **9,975,552** | 按需渲染，不落盘 |
| 数据层 | 译文数据，gzip 后 18 GB | — | 存数据不存页面 |

### 静态层：两种语言，两个 GitHub Pages 项目

```
static-en  github-pages  en  40,224 页  0.86 GB / 1.0 GB（86.4%）  构建 39 分钟
static-zh  github-pages  zh  40,224 页  0.86 GB / 1.0 GB（86.4%）  构建 39 分钟
```

千万页时静态层只做这两件事，**构建永远是 39 分钟级，不会随语言数增长**。

### 边缘层：245 语言分到 2 个平台

| 分片 | 平台 | 语言数 | 页数 | 估算请求/月 | 额度 | 占用 |
|---|---|---|---|---|---|---|
| edge-cf | Cloudflare Workers | 131 | 5,269,344 | 44,494 | 3,000,000 | 1.48% |
| edge-vercel | Vercel Edge | 114 | 4,585,536 | 44,200 | 1,000,000 | 4.42% |

分配按 Tier 流量权重做负载均衡，不是简单均分——否则 153 种 Tier 4 小语种会挤在一起，把某个平台的额度瞬间打满。

**渲染池合计 400 万请求/月，预计用量 8.87 万（2.22%）。**

#### 为什么只剩两个平台

上一版列了四个平台，逐个核对官方定价页（2026-11-14）后砍掉两个，这两个不是"额度少"，是"路已经断了"：

| 平台 | 结论 | 依据 |
|---|---|---|
| Deno Deploy | **排除** | 2026-10-09 Deno 宣布团队并入 Cloudflare，Deploy 约六个月后关停，新项目没有意义 |
| Netlify Free | **排除** | 改成 300 credits/月硬上限（一次生产部署 15、1 GB 带宽 20、1 万请求 2），折合约 15 GB 带宽；且"一个项目超限，全账号暂停" |
| Google Cloud Run | **排除** | 200 万请求/月免费，但每月只含 1 GB 出网，按每页 30 KB 只够 3.4 万页 |
| Vercel Hobby | **保留但标注风险** | 100 万 edge 请求/月，但**仅限非商业用途**；超额是暂停而非计费 |
| Cloudflare Workers | **主力** | 10 万请求/天；静态资源请求不计入额度，只有 Worker 调用计数 |

所以"多平台"的现实含义是：**Cloudflare 是命门，Vercel 是备份**。不是因为额度不够（才用掉 2.22%），而是因为单平台有硬顶——Cloudflare 免费版超过 10 万请求/天会返回 1027 直到 UTC 零点，一个爆款页面就能触发。分片的意义是**没有单点日限**，不是分摊总量。

## 四、多平台怎么"转发"成一个站

多平台最大的坑是变成多个域名，SEO 权重全散掉。所以必须有一个统一入口：

```
用户 → www.stags.cn（Cloudflare Worker 网关）
         │  按 URL 首段查路由表
         ├─ /            → static-en（ktyhub.github.io）
         ├─ /zh/         → static-zh（stags-zh.github.io）
         ├─ /ja/ /ko/ …  → edge-cf（workers.dev）
         ├─ /it/ /nl/ …  → edge-vercel
         └─ /assets/     → static-en（静态资源只存一份）
```

- 路由表由 `shard_plan.py` 生成（`deploy/gateway-routes.json`，249 条）
- **Cache Rule 让 HTML 在 CDN 层直接命中，命中不进 Worker、不消耗请求额度** —— 这是全免费的命门
- 网关只做一次路由查表，CPU 时间远低于免费版 10ms 上限

## 五、这样拆，更新慢的问题才真正解决

| 操作 | 单平台全量 | 分片后 |
|---|---|---|
| 改一行模板 | 164 小时 | 静态分片各 39 分钟，边缘层改模板不用重建页面 |
| 新增一条 release | 全站重建 | 静态不重建，只写边缘数据 |
| 加一种新语言 | 重跑整站 | 只加一个路由前缀 + 一个语言的数据 |
| 单个分片故障 | 全站挂 | 只有那 50 个语言受影响 |

**关键：边缘层的页面不是构建出来的，是请求时合成的。** 内容更新只写数据，静态构建与内容增长彻底解耦。

## 六、代码层已经就绪的部分

| 文件 | 作用 |
|---|---|
| `site/src/lib/i18n.ts` | `ACTIVE_LOCALES` 支持 `SITE_LOCALES=ja,ko,de` 分片构建；`getLocaleMeta` 用 `Intl.DisplayNames` 自动补全任意语言元信息（249 种语言不可能手写） |
| `site/src/pages/[locale]/` | 5 个手写语言目录合并成动态路由，加语言不再复制目录 |
| `scripts/release-tracker/shard_plan.py` | 分片编排：语言→平台分配、网关路由表、CI matrix |
| `scripts/release-tracker/plan_scale.py` | 千万级账本：页数、静态可行性、多平台配额、内容基数差距 |
| `deploy/hosting-shards.json` | 完整分片方案（含配额占用与构建时长） |
| `deploy/gateway-routes.json` | 网关路由表 |
| `deploy/ci-matrix.json` | CI 并行 job 定义 |

本地验证：动态路由改造后仍是 5,451 页，5 种语言各 224 页，与改前逐项一致；审计 5,441 可索引、canonical 全部本站。

## 七、还没解决的硬骨头

### 1. 翻译是真正的一次性瓶颈

```
248 语言 × 40,000 条 = 9,920,000 个文本块
14 块/秒（8 并发 5 通道轮询）→ 196.8 小时 ≈ 8.2 天
日常增量：每天 2,480 块 ≈ 3 分钟
```

**8 天**，这是千万页绕不开的成本。可行的加速方式：
- 加通道（DeepL Free / CF Workers AI / LibreTranslate 同时入池，实测可到 25–30 块/秒 → 约 4 天）
- 按 Tier 分批：先跑 35 种语言（约 140 万块 / 28 小时），把长尾留到后面慢慢补
- 缓存是 content-addressed 的，中断可续，不浪费已完成的部分

### 2. 数据存储只剩 2 GB 余量

18 GB 译文（gzip）vs R2 10 GB + B2 10 GB = 20 GB。缓冲太薄。需要：
- 文本块级去重（"Bump xxx from 1.2 to 1.3" 在数万条 release 里高度重复，实测可再去 20–30%）
- 冷数据下沉到 Hugging Face Datasets / Internet Archive

### 3. 内容基数

1,120 个追踪仓库才能到 4 万条 release。GitHub API 免费额度 5,000 次/小时，一晚上能扫完一轮，但需要先解决"哪些仓库值得追"的筛选标准，否则会灌进大量无价值的 "Bump dependency" 版本。

### 4. 网关还是单点

Cloudflare Worker 作为统一入口，本身是单点。免费版 10 万/天，日访问超过这个量就要升级（$5/月，1000 万请求）。**"千万页 + 完全免费"在低流量下成立，流量起来必然要付费**，这一点必须提前知道。

---

## 八、建议的推进顺序

1. **现在**：先把内容基数从 43 个仓库扩到 200–300（约 1 万条 release），用现有 7 语言验证增量流水线扛不扛得住
2. **然后**：按 `index-gate.json` 的批次放开语言，观察 Search Console 收录与表现
3. **再然后**：搭 Cloudflare Worker 网关 + 第一个边缘渲染分片（只接 1 个语言试点，比如 ja），验证缓存命中率能否到 97%
4. **最后**：按 `hosting-shards.json` 逐片接入其余平台

不要一次铺满 248 个语言——`scaled content abuse` 的判定是按站点整体算的。
