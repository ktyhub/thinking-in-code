# 内容策略：从「版本记录」到「有搜索量的页面」

一句话：**页数不等于流量，页面对应的查询才有流量。**

2,051 篇 Release Note 详情页对应的是 `X 1.8.0 更新了什么`——这类查询几乎
没有搜索量，写得再多也不会带来访客。同一批数据换一个切法，就能对上真实
存在的搜索需求。

## 四类内容族

| 内容族 | URL | 对应的真实查询 | 数量（2026-11） |
|---|---|---|---|
| 版本详情 | `/releases/{project}/{version}` | `X 1.8.0 release notes` | 2,051 × 2 语 |
| 项目版本史 | `/releases/{project}` | `X changelog` / `X 最新版本` | 329 |
| **对比** | `/compare/{a}-vs-{b}` | `A vs B` / `A 和 B 哪个好` | 486 × 2 语 |
| **专题** | `/topics/{topic}` | `best open-source X` / `X 有哪些替代品` | 17 × 2 语 |

后两类是新增的，也是唯一有商业意图的部分——读者在选型，不是在考古。

## 生成规则（为什么不是模板内容）

搜索引擎判 `scaled content abuse` 的核心依据是「页面之间除了关键词替换
没有实质差异」。所以每条规则都要求：**页面内容由数据决定，不同页面的
结论必须不同。**

对比页的每一个数字都来自收录的 release 记录：

- 收录版本数、最新版本与日期
- 近 90 天发布数（以数据集最新日期回推，构建可复现）
- 相邻两次发布的间隔中位数
- 预发布版本占比

据此生成「什么时候选哪个」的判断。`OpenHands vs langchain4j` 会得到
「6 天 vs 21 天间隔，前者接口面持续在动」，`AutoMQ vs rocketmq` 得到的是
另一组数字和另一段结论。

**配对单位是专题，不是粗品类。** 早期版本按 `engineering` 大类相邻配对，
产出了 `activiti-vs-grafana`（工作流引擎 vs 监控面板）这种既没有搜索需求、
又一眼看出是机器拼的页面。现在粒度收到「消息队列」「数据库」这一层。

**排除规则**（同样是为了不出垃圾页）：

- `spring-kafka`、`rocketmq-spring` 这类框架子模块 → 不入专题。它们和
  框架本体、和中间件本体都不构成对比。
- `lettuce`、`jetcd` 这类客户端 SDK → 不入专题。`redis vs lettuce` 是
  服务端和客户端的对比，属于误导。
- 项目不足 3 个的专题 → 不出页面。1–2 条内容的列表页是典型薄内容。
- 没有命中任何专题的项目 → 不兜底。兜底会造出大杂烩列表页。

## 索引策略

- **闸门**：`site/src/data/index-gate.json`。语言级别的 noindex 开关，
  URL 空间可以先扩，能不能被收录逐批放开。
- **sitemap**：只列闸门放开的语言，单片上限 45,000。
- **IndexNow**：`indexnow.py` 把新增 URL 推给 Bing / Yandex / Seznam / Naver，
  几小时内来抓。Google 不支持 IndexNow，只能靠 sitemap + 内链，所以这是
  补充而不是替代。必须跑在部署之后（`--remote` 读线上 sitemap），
  否则抓取器会拿到 404。
- **内链**：项目页向下分发到专题页与对比页，保证新页面三次点击内可达。
  抓取预算有限，孤岛页面等于不存在。

## 扩容路线

数量级取决于两个变量，内容层面没有第三条路：

1. **仓库数**：163 → 1,120 才能撑起 4 万条 release（千万页的分母）。
   名单靠 GitHub search 按 topic 拉取 + 逐个核对「真在发 release 且正文
   有实质内容」，不靠拍脑袋。
2. **语言数**：7 → 247。翻译是 content-addressed 缓存，同段文本永不重翻，
   这是「免费翻 247 种语言」唯一成立的原因。

当前节奏：每天三轮采集，每轮 120 条、每仓库最多 8 条历史。刻意不快——
一次性灌几千页进索引，最快的结局是被判成垃圾站，连带拖累已经收录的页面。

## 闭环：让上面这些策略自己收敛

四类内容族和索引策略都是**人的判断**——哪类页面有搜索需求、粒度该收到
专题还是品类，这些机器想不出来。但「已经做出来的东西在该站点的局部最优
在哪」，机器可以迭代出来。这部分见 [LOOP.md](LOOP.md)。

一句话概括：每周跑一次 `loop.py`，它结算上一轮的实验、读最新搜索数据、
在 6 条规则的封闭动作空间里最多改 3 个参数，然后记账等下一轮结算。
失败率超 2/3 的规则自动停用。

不做的是自我改写代码，也不做内容生成。理由在那个文档开头写了：
不可逆的失败模式换不来那 10% 的额外收益。
