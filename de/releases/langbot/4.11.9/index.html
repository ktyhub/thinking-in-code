LangBot v4.11.9

LangBot ist eine Open-Source-KI-Chatbot- und Agentenplattform, die mehrere Instant-Messaging-Plattformen, große Sprachmodelle, Wissensdatenbanken und Plug-ins unterstützt, um Sie bei der Erstellung, Bereitstellung und Verwaltung von KI-Assistenten zu unterstützen. LangBot ist eine Open-Source-KI-Chatbot- und Agentenplattform, die Messaging-Plattformen, große Sprachmodelle, Wissensdatenbanken und Plugins verbindet, um Sie bei der Erstellung, Bereitstellung und Verwaltung von KI-Assistenten zu unterstützen.

LangBot v4.11.9

Die Box-Sandbox läuft jetzt auf Windows-Hosts, Agenten können hochgeladene Dateien bei Bedarf lesen und von ihnen erstellte Dateien veröffentlichen, und bei Neuinstallationen bleiben Skills und Uploads in der Datenbank erhalten. Mit dieser Version kann die Box-Sandbox auf Windows-Hosts ausgeführt werden. Der Agent kann hochgeladene Dateien bei Bedarf lesen und seine eigenen generierten Dateien veröffentlichen. Bei Neuinstallationen werden Fertigkeiten und hochgeladene Inhalte standardmäßig in der Datenbank gespeichert.

Upgrade-Hinweis/Upgrade-Tipp: Diese Version enthält eine neue Datenbankmigration (0049–0053). Bitte sichern Sie das Verzeichnis data/ vor dem Upgrade (sichern Sie gleichzeitig die Datenbank, wenn Sie PostgreSQL verwenden). Sie müssen diese Sicherung zum Wiederherstellen bei einem Downgrade verwenden. Die bereits in config.yaml bereitgestellten Speicher-, Fertigkeits- und Boxeinstellungen bleiben unverändert. In dieser Version werden die Datenbankmigrationen 0049–0053 hinzugefügt. Sichern Sie data/ (und PostgreSQL, falls verwendet) vor dem Upgrade; Für das Zurücksetzen ist dieses Backup erforderlich. Bestehende Bereitstellungen behalten die Speicher-, Skill- und Box-Einstellungen in ihrem config.yaml.

Highlights

  • Windows-Host-Box / Windows-Host-Sandbox: Das Plug-in SDK 0.7.26 ermöglicht dem host-Backend die Unterstützung von Windows: Der Befehl wird zuerst mit Git Bash ausgeführt, andernfalls kehrt er zu PowerShell zurück und am Ende wird der gesamte Prozessbaum bereinigt. Hinweis: host führt keine Isolierung durch (UNSAFE). Der Befehl wird direkt als Benutzer ausgeführt, der LangBot ausführt. Nicht vertrauenswürdige Benutzer im Gruppenchat können den Befehl durch prompte Wortinjektion ausführen. Es wird nicht automatisch ausgewählt und muss in config.yaml explizit auf box.backend: host gesetzt oder von der nativen lbctl-Installation geschrieben werden (ab lbctl v0.5.14). Der Skill kann nicht auf der Windows-Host-Box unter box.file_transfer_mode: network ausgeführt werden; Bitte verwenden Sie legacy, wenn sich LangBot und Box auf demselben Computer befinden (lbctl schreibt automatisch). Das host-Backend funktioniert jetzt unter Windows (Git Bash, Rückgriff auf PowerShell; der gesamte Prozessbaum wird bereinigt). host ist nicht isoliert und führt Befehle als LangBot-Benutzer aus, sodass Gruppenchat-Benutzer mit untrust Befehle durch Prompt-Injection ausführen können. Es wird niemals automatisch ausgewählt: Legen Sie box.backend: host explizit fest oder lassen Sie es von lbctl (v0.5.14+) für native Installationen schreiben. Skills können nicht auf einer Windows-Host-Box im network-Übertragungsmodus ausgeführt werden; Wenn LangBot und Box einen Computer gemeinsam nutzen, verwenden Sie box.file_transfer_mode: legacy (lbctl legt dies für Sie fest).
  • Dateien für Agenten/Agentendateien: Hochgeladene Dateien werden als Datei-Assets mit Berechtigungen gespeichert. Der Agent erhält zunächst die Dateireferenz und liest dann bei Bedarf den Text, das Bild oder die PDF-Datei Segment für Segment über das Tool. Der Runner kann die generierte Datei an den angegebenen Empfänger veröffentlichen und sie kann weiterhin heruntergeladen werden, nachdem der Lauf abgeschlossen ist oder der Core neu gestartet wird. Wissensdatenbankdateien und Plug-in SDK sind ebenfalls mit demselben Satz von Dateiressourcen verbunden. Uploads werden zu autorisierten Dateiressourcen: Agenten erhalten Referenzen und lesen Texte, Bilder oder PDF-Seiten bei Bedarf über Tools, und Runner können Ausgabedateien veröffentlichen, die nach dem Ende des Laufs oder dem Neustart von Core herunterladbar bleiben. Wissensdatenbankdateien und das Plugin SDK verwenden dieselben Assets.
  • Datenbankgestützte Fertigkeiten und Uploads standardmäßig / Neu installierter Standard-Datenbankspeicher: Neu installierte Fertigkeiten (einschließlich historischer Versionen) und hochgeladene Inhalte werden standardmäßig in der Datenbank gespeichert. Box überträgt Dateien standardmäßig über das Netzwerk. Core und Box müssen keine Verzeichnisse mehr gemeinsam nutzen. Wenn eine vorhandene Bereitstellung in diesen Modus umgeschaltet wird, importiert Core die alten Skill- und lokalen Dateien, bevor HTTP gestartet und geöffnet wird, was unterbrochen und wiederhergestellt werden kann. Nach Abschluss des Imports wird nicht mehr auf das alte Verzeichnis zurückgegriffen. Die Docker Box kann im Netzwerkmodus schreibgeschützte lokale Datensätze bereitstellen. Bei Neuinstallationen werden Skills (mit ihrem Versionsverlauf) und Uploads in der Datenbank gespeichert, und Box verschiebt Dateien über das Netzwerk statt in ein freigegebenes Verzeichnis. Wenn eine bestehende Bereitstellung umgestellt wird, importiert Core voraussichtlich alte Skills und lokale Dateien, bevor es HTTP bereitstellt. Docker-Netzwerkmodus-Boxen können schreibgeschützte lokale Datensätze bereitstellen.
  • Operationen API / Operation API: /api/v1/operations-Schnittstelle hinzugefügt (Verzeichnis, Beschreibung, Ausführung, SSE-Fluss), API-Schlüssel kann auch Plug-In-Berechtigungen bestätigen, und Clients wie lbctl können API-Schlüssel verwenden, um Plug-In-Berechtigungen zu bestätigen. Neue /api/v1/operations-Routen (Katalog, Beschreibung, Ausführung, SSE) und Plugin-Berechtigungsbestätigung mit einem API-Schlüssel, sodass API clients wie lbctl Plugin-Berechtigungen bestätigen können.
  • WebUI: Das Update-Dialogfeld zeigt direkt das Update-Protokoll auf langbot.app an; Auf der Plug-in-Detailseite wird die installierte Version angezeigt und kann direkt aktualisiert werden. Nach der Installation des Plug-Ins werden Sie je nach Komponententyp zum nächsten Schritt aufgefordert. Der Update-Dialog zeigt release notes von langbot.app; Plugin-Detailseiten zeigen die installierte Version und bieten Upgrades an; Die Installation eines Plugins schlägt den nächsten Schritt vor.
  • Startup/Startup: pip install erkennt fehlende Abhängigkeiten beim Start nicht mehr automatisch, sondern listet fehlende Pakete auf und fordert zur Neuinstallation und anschließenden Beendigung auf. LangBot installiert fehlende Pakete beim Start nicht mehr per Pip; Es listet sie auf und wird mit Anweisungen zur Neuinstallation beendet.
  • Fixes / Fixes: Plug-in-Prozesse, die wiederholt nicht gestartet werden können, werden zurückgezogen und erneut versucht und der Bildschirm wird nicht mehr aktualisiert. Die Bearbeitung des Telegram-Streamings ignoriert „Nachricht wurde nicht geändert“; MulticaAgent versucht es erneut, wenn ein vorübergehender Fehler auftritt, und während des Neustarts verlorene Antworten werden erneut ausgegeben. Der WeChat-Kundendienst für Unternehmen analysiert automatisch open_kfid, wenn Nachrichten an die bloße external_userid gesendet werden. Alarme in der LangBot Cloud müssen weiterhin manuell aktiviert werden; E2B Das Arbeitsbereichskontingent wird wirksam; Die Plug-in-Verpackung schließt das Verzeichnis der virtuellen Umgebung aus. Fehlerhafte Plugin-Worker ziehen sich zurück; Telegram-Streaming ignoriert „Nachricht wurde nicht geändert“; MulticaAgent wiederholt vorübergehende Fehler und stellt Antworten wieder her, die bei Neustarts verloren gegangen sind. Der WeCom-Kundendienst löst open_kfid für bloße external_userid-Ziele; Benachrichtigungen bleiben in der LangBot Cloud aktiviert; E2B-Arbeitsbereichsbeschränkungen werden durchgesetzt; Plugin-Pakete schließen Virtualenvs aus.
  • SDK:langbot-plugin und 0.7.25 und 0.7.26.Kernstifte langbot-plugin==0.7.26.

Release-Überprüfung

  • Release-Commit 826bf580ff42bbf10dac52203f1171f63b97b52a. Er unterscheidet sich vom getesteten Kandidaten dfa3c743c lediglich in der Versionsnummer; Alle Pull-Request-Prüfungen wurden auf der Release-PR bestanden.
  • Vor dem Markieren wurde der Kandidat zweimal in neuen Datenverzeichnissen installiert und Routinevorgänge durchlaufen:
    • Docker (docker compose mit der Plugin-Laufzeit und Box, Image erstellt aus dem Kandidaten-Commit);
    • uvx (uvx --from <wheel> langbot, Abhängigkeiten von PyPI: SDK 0.7.26, SQLAlchemy 2.1.9). Beides bestanden: Kontoeinrichtung und WebUI; Marketplace-Installation von LocalAgent, EssentialCommands, WebSearch, LangRAG und HelloPlugin mit Berechtigungsbestätigung, Aktivierung/Deaktivierung pro Pipeline und Deinstallation; Modellanbieter und Modelltest; eine LocalAgent-Pipeline über HTTP-Bot, einschließlich eines Websuchtool-Aufrufs; !help !cmd !func !plugin !version; Aufnahme und Abruf von Wissensdatenbanken; Erstellen einer Fertigkeit und Veranlassen, sie vom Agenten zu verwenden; und Daten, Plugins, Wissensdatenbank und Skill bleiben nach einem Neustart erhalten. Docker hat einen Befehl in einem Box-Sandbox-Container ausgeführt. uvx hat einen über das host-Box-Backend ausgeführt.
  • Parallelität: 8 gleichzeitige Konversationen auf einem Modell auf Docker abgeschlossen. Auf uvx (SQLite) überschritten einige Konversationen das Antwortfenster des HTTP Bot 60 auf einem stark ausgelasteten Testhost und einige erreichten database is locked; v4.11.8 verhielten sich nebeneinander unter derselben Last gleich, daher ist dies in dieser Version nichts Neues.
  • Windows: Das Release Wheel wurde mit uvx unter Windows 11 (Build 26300, Codepage 936, Python 3.11, Git Bash installiert; SDK 0.7.26, SQLAlchemy 2.1.9) installiert und hat dieselbe Checkliste mit einem lokalen Mock-Modell bestanden, einschließlich 8 gleichzeitiger Konversationen (8/8, kein database is locked). Bei box.backend: host und file_transfer_mode: legacy führte der Agent einen Befehl (exec) aus und schrieb und las eine Datei über die Windows-Host-Box zurück. Ein Plugin, das Chinesisch und Emoji druckte, hielt die Laufzeit verbunden, und da Tokenizer-Downloads blockiert waren, antwortete die erste LocalAgent-Konversation innerhalb von 2 Sekunden (kein count_tokens-Timeout).
  • Datenbankmigrationen: Datenbanken, die von v4.11.8 (Revision 0048), v4.10.11 (0023) und v4.10.6 (0008, vor Workspaces) erstellt wurden, wurden auf diese Version sowohl auf SQLite als auch auf PostgreSQL aktualisiert. Jedes Upgrade erreichte Revision 0053 und startete zweimal sauber; Es gingen keine Zeilen verloren, die SQLite-Integritäts- und Fremdschlüsselprüfungen wurden bestanden und der gesetzte Anbieter, das Modell, der Bot und die Pipeline wurden zurückgelesen. Kopien von drei echten SQLite-Datenbanken (Revisionen 0042, 0040 und 0008, bis zu 33 MB) wurden ebenfalls sauber aktualisiert. Aktualisierte Schemata entsprechen einer Neuinstallation, abgesehen von Unterschieden bei der Indexbenennung bei Datenbanken, die vor 0024 gestartet wurden, was auch bei v4.11.8 der Fall ist.
