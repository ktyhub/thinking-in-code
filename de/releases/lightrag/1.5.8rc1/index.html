LightRAG v1.5.8rc1

Wichtige Hinweise

v1.5.8rc1 ist ein Release Candidate. Bitte testen Sie es an einer Kopie Ihrer Daten, bevor Sie die Produktion aktualisieren.

Highlights

1. Konfigurationsspeicher: LightRAG merkt sich jetzt, welches Einbettungsmodell Ihre Vektoren erstellt hat

In früheren Versionen schlug das Ändern von EMBEDDING_MODEL oder EMBEDDING_DIM in einer vorhandenen Bereitstellung unbemerkt fehl. Abhängig vom Backend behielt LightRAG entweder die alten Vektoren bei und gab falsche Nachbarn zurück oder öffnete einen neuen, leeren Vektorcontainer (Milvus / Qdrant / PostgreSQL) und stellte einen Wissensgraphen ohne Vektoren bereit.

v1.5.8 fügt einen Konfigurationsspeicher hinzu. Es handelt sich um einen kleinen KV-Namespace (config), der die Einbettungsbasislinien jedes Arbeitsbereichs enthält: für jedes Vektorziel (Entitäten, Beziehungen, Chunks), den Einbettungsraum, in den seine Vektoren geschrieben wurden. Beim Start werden die Basislinien anhand der aktuellen Einbettungskonfiguration überprüft. Wenn sich der Raum geändert hat, verweigert der Server den Start und nennt das Ziel und den Ausweg, anstatt schlechte Ergebnisse zu liefern.

  • Backends: JsonKVStorage, PGKVStorage, MongoKVStorage und OpenSearchKVStorage, ausgewählt mit LIGHTRAG_CONFIG_STORAGE. Wenn es nicht festgelegt ist, folgt es LIGHTRAG_KV_STORAGE, sodass für die meisten Bereitstellungen keine neue Einstellung erforderlich ist. RedisKVStorage ist nicht zugelassen, daher wird bei Redis-Bereitstellungen standardmäßig JsonKVStorage mit einer Startwarnung verwendet.
  • Keine Vorbereitung erforderlich. Beim ersten Start von v1.5.8 zeichnet eine vorhandene Bereitstellung ihre Baselines selbst auf. Eine Basislinie wird nur aufgrund von Beweisen aufgezeichnet: Eine Adoptionssonde bettet einige gespeicherte Datensätze (bis zu 8 pro Ziel) erneut ein und vergleicht sie mit den gespeicherten Vektoren, oder der Container wird als leer bestätigt. Ein Probe, der nicht ausgeführt werden kann (z. B. weil der Einbettungsdienst ausgefallen ist), zeichnet nichts auf und wird beim nächsten Start erneut versucht.
  • Bereitstellungsanker. Der erste Start bindet die Bereitstellung auch an den Konfigurationscontainer, den sie geöffnet hat, in WORKING_DIR/config_storage_anchor.json (Backend-Typ + Container-UUID). Jeder spätere Start lehnt einen Container eines anderen Typs oder einer anderen UUID ab. Ein geänderter LIGHTRAG_KV_STORAGE, eine andere Datenbank oder ein ersetztes Volume verschiebt Ihre Konfiguration daher nicht mehr stillschweigend.
  • Neue Offline-Tools:
    • lightrag-rebuild-vdb bettet einen Arbeitsbereich erneut mit dem aktuellen Modell ein und zeichnet die neuen Basislinien auf. Dies ist der Ausweg nach einem bewussten Modellwechsel.
    • lightrag-migrate-config verschiebt den Konfigurationsspeicher in ein Backend eines anderen Typs, beispielsweise von JSON-Dateien nach PostgreSQL.
    • lightrag-clear-storage löscht einen Arbeitsbereich offline, einschließlich Konfigurationsdatensätzen.
  • Mehrere Server, ein WORKING_DIR: wird unterstützt, wenn jeder Server über einen eigenen WORKSPACE und Port verfügt. Ein zweiter Server im gleichen Arbeitsbereich wird abgelehnt, wenn das Dateisystem Dateisperren unterstützt.

Weitere Informationen finden Sie unter:

  • docs/LightRAG-API-Server.md: Konfigurationsspeichermigration zwischen Backend-Typen
  • lightrag/tools/README_REBUILD_VDB.md, README_MIGRATE_CONFIG.md, README_CLEAR_STORAGE.md
  • docs/design/ConfigurationStorageDesign.md: die Designübersicht

2. Sichereres Schreiben von Diagrammen und Löschen von Dokumenten

  • Manuelle Diagrammbearbeitungen (Entitäten und Beziehungen erstellen/bearbeiten/löschen/zusammenführen, insert_custom_kg) werden jetzt gegeneinander und gegen die Aufnahmepipeline auf NetworkXStorage serialisiert.
  • Die Commit-Reihenfolge für das Erstellen, Bearbeiten, Zusammenführen und Umbenennen von Entitäten/Beziehungen wurde überarbeitet, um Datenverlust zu verhindern, wenn ein Vorgang unterbrochen wird.
  • Unterbrochene Dokumentlöschungen sind sichtbar und können wiederholt werden.
  • Das neue Tool lightrag-repair-chunk-tracking entfernt verwaiste Chunk-Tracking-Zeilen, die durch eine unterbrochene Löschung zurückbleiben.

3. PostgreSQL Speicherstandards Der Setup-Assistent generiert nun PostgreSQL aus dem offiziellen pgvector/pgvector-Image und bietet PGTableGraphStorage (einfache Tabellen, kein Apache AGE) für das Diagramm an. PGGraphStorage (AGE) und die Redis-Speicher (RedisKVStorage, RedisDocStatusStorage) sind veraltet. Sie arbeiten weiter und protokollieren beim Start eine Warnung.

4. Sicherheitshärtung und neuer Anbieter

  • Die Ollama-kompatiblen /api/*-Routen sind durch LIGHTRAG_API_KEY geschützt (siehe Breaking Changes).
  • Bei der PDF-Extraktion wird pypdf in einem untergeordneten Prozess mit begrenzten Ressourcen ausgeführt.
  • Gestreamte Fehlerzeilen geben nicht mehr den rohen Ausnahmetext des Anbieters wieder.
  • Neue openai_responses LLM-Bindung für die OpenAI Responses API.

Breaking Changes

  • Python 3.11 oder höher ist erforderlich. Python 3.10 wird nicht mehr unterstützt. Die Docker-Bilder (Python 3.12) sind nicht betroffen.
  • Das Ändern des Einbettungsmodells in einem vorhandenen Arbeitsbereich verweigert jetzt den Start, wo früher falsche oder leere Ergebnisse geliefert wurden. Stellen Sie entweder das vorherige EMBEDDING_MODEL/EMBEDDING_DIM wieder her oder führen Sie lightrag-rebuild-vdb aus, um es erneut in das neue Modell einzubetten.
  • Das Ändern von LIGHTRAG_KV_STORAGE nach dem ersten Start von v1.5.8 wird abgelehnt, während LIGHTRAG_CONFIG_STORAGE nicht festgelegt ist, da der Konfigurationsspeicher stillschweigend mit verschoben werden würde. Legen Sie entweder LIGHTRAG_CONFIG_STORAGE explizit auf das verankerte Backend fest oder verschieben Sie die Konfiguration mit lightrag-migrate-config.
  • Ollama-Routen erfordern den Schlüssel API. Wenn LIGHTRAG_API_KEY festgelegt und WHITELIST_PATHS nicht festgelegt ist, erhalten /api/*-Anfragen ohne den Schlüssel jetzt HTTP 403. In Open WebUI verschwindet das Modell lightrag:latest aus der Liste. Fix: Geben Sie den Schlüssel als API-Schlüssel der Ollama-Verbindung ein (gesendet als Authorization: Bearer <key>) oder legen Sie WHITELIST_PATHS=/health,/api/* fest, um das alte Verhalten beizubehalten.
  • POST /documents/clear_cache wurde entfernt. Verwenden Sie stattdessen DELETE /documents?clear_llm_cache=true. Das Löschen des LLM-Cache erfolgt nun zusammen mit dem destruktiven Löschen.
  • Arbeitsbereichsnamen, die mit $ beginnen, sind reserviert. Der Server, der WORKSPACE=$team als _team bedient. Legen Sie WORKSPACE=_team fest (den Namen, unter dem Ihre Daten bereits gespeichert sind), und es werden keine Daten verschoben.

Upgrade-Hinweise

  1. Zuerst ein Backup erstellen und dann jede alte Instanz stoppen, bevor v1.5.8 gestartet wird. Dazu gehören alle Worker, Server, die den Speicher gemeinsam nutzen, und Wartungstools. Beim ersten Start wird der Konfigurationscontainer erstellt und der Anker gebunden. Führen Sie kein fortlaufendes Upgrade durch, bei dem ein alter Writer weiter ausgeführt wird.
  2. WORKING_DIR muss bestehen bleiben, auch wenn jeder Speicher eine Datenbank ist. Es enthält jetzt config_storage_anchor.json und für die JSON-Konfiguration auch <workspace>/kv_workspace_config.json. Behalten Sie es in Docker auf einem bereitgestellten Volume. Behalten Sie in Helm persistence.enabled: true. Ein kurzlebiger WORKING_DIR verliert bei jedem Neustart den Anker und die JSON-Konfiguration. Fügen Sie es in Ihre Backups ein.
  3. Der Einbettungsdienst muss beim ersten Start erreichbar sein, damit der Adoption Probe die Baselines aufzeichnen kann. Überprüfen Sie das Startprotokoll auf einen WARNING, der besagt, dass keine Baseline eingerichtet werden konnte. Wenn der Start aufgrund einer Nichtübereinstimmung des Einbettungsraums abgelehnt wird, stimmen Ihre gespeicherten Vektoren nicht mit dem konfigurierten Modell überein: Korrigieren Sie die Konfiguration oder führen Sie lightrag-rebuild-vdb aus.
  4. Redis-Benutzer: mit LIGHTRAG_KV_STORAGE=RedisKVStorage ist der Konfigurationsspeicher standardmäßig auf JSON-Dateien in WORKING_DIR eingestellt (siehe Hinweis 2). Der Speicher Redis ist veraltet. Planen Sie einen Umzug nach PostgreSQL.
  5. PGGraphStorage-Benutzer: Ihre Bereitstellung funktioniert weiterhin und der Assistent behält das AGE-aktivierte Image dafür bei. Um AGE zu verlassen, migrieren Sie zuerst das Diagramm (python -m lightrag.tools.migrate_graph_storage --apply, keine Neuindizierung erforderlich) und wechseln Sie dann zu PGTableGraphStorage und dem pgvector-Bild.
  6. Optional: Um die Konfiguration in Ihrer Datenbank anstelle der JSON-Dateien zu behalten, führen Sie lightrag-migrate-config --target-backend PGKVStorage (oder MongoKVStorage / OpenSearchKVStorage) bei gestopptem Server aus. Stellen Sie dann LIGHTRAG_CONFIG_STORAGE auf dieses Backend ein.
  7. Um mit einem neuen Einbettungsmodell von vorne zu beginnen, verwenden Sie lightrag-clear-storage, anstatt Dateien manuell zu löschen. Wenn Sie Dateien manuell löschen, entfernen Sie auch kv_workspace_config.json und config_storage_anchor.json. Andernfalls lehnt die aufgezeichnete Baseline das neue Modell ab.
  8. TOKEN_SECRET sollte ein Zufallswert von mindestens 32 Bytes sein (z. B. openssl rand -hex 32). Das aktualisierte PyJWT warnt vor kürzeren Geheimnissen.
  9. Gestreamte Fehlermeldungen sind generisch. Ein Fehler mitten in einem Stream auf /query/stream, /api/generate oder /api/chat lautet jetzt Internal server error (error_id: …) und enthält nicht mehr den Ausnahmetext des LLM-Anbieters. Das Streamformat bleibt unverändert. Sehen Sie sich die Details im Serverprotokoll von error_id an. Ein client, ​​der Anbieterfehlertext aus dem Stream analysiert hat (z. B. um Ratenbeschränkungen zu erkennen), muss aktualisiert werden.
