Release-Highlights <a id="v2100-release-highlights"></a>

Secrets Management <a id="v2100-highlight-secrets-management"></a>

Halten Sie Collector-Anmeldeinformationen aus Klartext-Konfigurationsdateien fern. Mit Netdata können Sie jetzt in Collector-Konfigurationen auf Geheimnisse verweisen, anstatt sie direkt zu speichern. Passwörter, Token und API-Schlüssel werden zur Laufzeit aus der von Ihnen gewählten Quelle aufgelöst.

Resolver

Netdata bietet vier Resolver-Typen, von einfach bis für Unternehmen:

| Resolver | Syntax | Am besten für | |:-----------|:---------------------|:------------------------------------------------------------------------------| | Umgebungsvariable | ${env:VAR_NAME} | Geheimnisse, die bereits in die Netdata-Dienstumgebung eingefügt wurden | | Datei | ${file:/absolute/path} | Geheimnisse, die in lokalen Dateien auf der Festplatte gespeichert sind (Docker-Geheimnisse, Kubernetes-Geheimnisse, die als Volumes bereitgestellt sind) | | Befehl | ${cmd:/absolute/path args} | Von einem lokalen trusted-Befehl zurückgegebene Geheimnisse (z. B. 1Password CLI, benutzerdefinierte Skripte) | | Secretstore | ${store:<kind>:<name>:<operand>} | Geheimnisse zentral bei Cloud-Anbietern oder Vault verwaltet |

Unterstützte Secretstore-Backends

Für Organisationen, die Geheimnisse zentral verwalten, lässt sich Netdata in vier Secretstore-Backends integrieren:

| Backend | Freundlich | Operandenformat | Authentifizierungsmodi | |:----------------------------------------------------------------------------|:-------------------------|:---------------------------|:--------------------| | AWS Secrets Manager | aws-sm | secret-name[#key] | Umgebungsanmeldeinformationen, ECS-Aufgabenrolle, EC2-Instanzprofil | | Azure Key Vault | azure-kv | vault-name/secret-name | Dienstprinzipal, verwaltete Identität, Standardanmeldeinformationskette | | Google Secret Manager | gcp-sm | project/secret[/version] | Metadatenserver, Dienstkontodatei | | HashiCorp-Tresor | vault | path#key | Token, Tokendatei |

Konfigurieren Sie Secretstores über die Netdata Dynamic Configuration UI (Collectors → go.d → SecretStores) oder über Konfigurationsdateien unter /etc/netdata/go.d/ss/.

Beispiel

Ein MySQL-Kollektor, der auf sein Passwort aus HashiCorp Vault verweist:

# /etc/netdata/go.d/mysql.conf
jobs:
  - name: mysql_prod
    dsn: "netdata:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

Sie können die Resolvertypen frei mischen. Lesen Sie beispielsweise den Benutzernamen aus einer Umgebungsvariablen und das Passwort aus einem Secretstore im selben Konfigurationswert:

jobs:
  - name: mysql_prod
    dsn: "${env:MYSQL_USER}:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

Wie es funktioniert

– Geheimnisse werden jedes Mal aufgelöst, wenn ein Collector-Job gestartet oder neu gestartet wird. – Durch das Aktualisieren eines Secretstores werden Collector-Jobs, die ihn verwenden, automatisch neu gestartet, damit sie neue Anmeldeinformationen abrufen. – Secretstore-Konfigurationswerte selbst unterstützen auch die Resolver ${env:...}, ${file:...} und ${cmd:...}, sodass Backend-Anmeldeinformationen auch nicht im Klartext gespeichert werden müssen.

[!TIP] Ausführliche Informationen zur Einrichtung, Backend-spezifischen Authentifizierungshandbüchern und zur Fehlerbehebung finden Sie in der Secrets Management-Dokumentation.

Nagios Plugins Collector <a id="v2100-highlight-nagios-plugins"></a>

Führen Sie Nagios-kompatible Plugins und benutzerdefinierte Skripte direkt in Netdata mit dem neuen Nagios-Plugin-Sammler aus. Jede ausführbare Datei, die dem [Nagios-Plugin-Ausgabeformat] (https://nagios-plugins.org/doc/guidelines.html) folgt, funktioniert sofort: gepackte Nagios-Plugins, benutzerdefinierte Shell-Skripte oder kompilierte Binärdateien.

Was Sie bekommen

| Funktion | Einzelheiten | |:------------------------|:------------------------------------------------------------------------------------------------------------- | Statusüberwachung prüfen | Verfolgt die Status „OK“, „WARNUNG“, „KRITISCH“ und „UNBEKANNT“ aus dem Prozess-Exit-Code | | Automatische Leistungsdatendiagramme | Nagios-Leistungsdatenwerte werden automatisch analysiert und grafisch dargestellt | | Schwellenwertbasierte Warnung | Wenn Perfdata Warn-/Kritisch-Schwellenwerte enthält, leitet Netdata ein Schwellenwert-Statusdiagramm (OK/Warnung/Kritisch) ab und erstellt integrierte Warnungen | | Ausführungsmetriken | Misst die Ausführungsdauer, die CPU-Zeit und die Speichernutzung jeder Prüfung | | Planung im Nagios-Stil | Konfigurierbare Prüfintervalle, Wiederholungsintervalle, maximale Prüfversuche und Zeiträume | | Soft/Hard-State-Logik | Nicht-OK-Ergebnisse werden bei retry_interval bis max_check_attempts erneut versucht, bevor Warnungen ausgelöst werden, wodurch Fehlalarme durch vorübergehende Ausfälle verhindert werden |

Integrierte Warnungen

Der Sammler wird mit vier Lagerbestandswarnungen ausgeliefert:

| Warnung | Löst aus, wenn | |:------------------------------------------|:-------------------------------------------------| | nagios_job_execution_state_warn | Ein Scheck befindet sich im harten Zustand WARNUNG | | nagios_job_execution_state_crit | Ein Scheck befindet sich im harten Zustand KRITISCH | | nagios_job_perfdata_threshold_state_warn | Eine Perfdata-Metrik überschreitet ihren Warnschwellenwert | | nagios_job_perfdata_threshold_state_crit | Eine Perfdata-Metrik überschreitet ihren kritischen Schwellenwert |

Alle Bestandswarnungen unterdrücken Soft-Retry-Zustände. Warnungen werden nur nach den konfigurierten max_check_attempts aufeinanderfolgenden Fehlern ausgelöst.

Beispiel

# /usr/local/lib/netdata/checks/check_api.sh
#!/bin/sh
resp=$(curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time 5 "$1" 2>/dev/null)
code=$(echo "$resp" | cut -d' ' -f1)
time=$(echo "$resp" | cut -d' ' -f2)

[ "$code" -ge 500 ] && echo "CRITICAL - HTTP $code | response_time=${time}s;~:2;~:5" && exit 2
[ "$code" -ne 200 ] && echo "WARNING - HTTP $code | response_time=${time}s;~:2;~:5" && exit 1
echo "OK - HTTP $code | response_time=${time}s;~:2;~:5"
exit 0

# /etc/netdata/scripts.d/nagios.conf
jobs:
  - name: api_health
    plugin: /bin/sh
    args: ["/usr/local/lib/netdata/checks/check_api.sh", "http://localhost:8080/health"]
    check_interval: 1m
    retry_interval: 15s
    max_check_attempts: 3

Dadurch werden Prüfzustandsdiagramme und Ausführungsmetriken erstellt. Da das Skript Perfdata mit Schwellenwerten ausgibt (response_time mit Warnung >2 s / Krit >5 s), wird ein automatisches Reaktionszeitdiagramm mit einem Schwellenwertzustandsdiagramm und integrierten Warnungen erstellt.

[!TIP] Die vollständige Einrichtungsanleitung, die exemplarische Vorgehensweise für benutzerdefinierte Skripte und die Konfiguration des Zeitraums finden Sie in der Nagios Plugins Collector-Dokumentation.

Azure Monitor Collector <a id="v2100-highlight-azure-monitor"></a>

Überwachen Sie Ihre gesamte Azure-Infrastruktur von Netdata mit dem neuen Azure Monitor Collector. Es sammelt Plattformmetriken von Azure Monitor Metrics API mit automatischer Ressourcenerkennung: Richten Sie es auf Ihre Abonnements, und es findet Ihre Ressourcen, ordnet sie integrierten Profilen (vorkonfigurierte Metriksätze) zu und beginnt mit der Metrikerfassung.

[!IMPORTANT] Dies ist eine Alpha-Funktion. Das Konfigurationsformat kann sich in kommenden Versionen ändern.

Was Sie bekommen

| Funktion | Einzelheiten | |:---------------------------------|:---------------------------------------------------------------------------------------------------------------| | 38 integrierte Serviceprofile | Über 1.300 Metriken zu Computing, Datenbanken, Netzwerken, Speicher, KI/ML, Analysen, Containern und mehr | | Automatische Erkennung | Ermittelt Ressourcen über Azure Resource Graph und ermöglicht passende Profile ohne Konfiguration pro Ressource | | Mehrfachabonnement | Überwachen Sie Ressourcen über mehrere Azure-Abonnements hinweg in einem einzigen Collector-Auftrag | | Flexibles Discovery-Scoping | Grenzen Sie die Ermittlung nach Ressourcengruppen, Regionen oder Tags ein oder verwenden Sie eine benutzerdefinierte Azure Resource Graph KQL-Abfrage | | Integrierte Warnungen | Vorkonfigurierte Warnungen für kritische Azure-Ressourcenbedingungen | | UI-Konfiguration | Konfigurieren Sie über die Netdata Dynamic Configuration-Benutzeroberfläche ohne Dateibearbeitung |

Unterstützte Dienste

| Kategorie | Dienste über Profile | |:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------| | Berechnen | Virtual Machine, Virtual Machine Scale Set, App Service (inkl. Funktionen), Container Apps, Container-Instanzen | | Kubernetes | AKS | | Datenbanken | SQL-Datenbank, SQL Elastic Pool, SQL Managed Instance, MySQL Flexible, PostgreSQL Flexible, Cosmos DB, Cache für Redis | | Netzwerk | Load Balancer, Application Gateway, Front Door, Firewall, NAT Gateway, VPN Gateway, ExpressRoute Circuit, ExpressRoute Gateway | | Speicherung und Analyse | Speicherkonto, Data Explorer, Data Factory, Stream Analytics, Synapse Analytics, Log Analytics | | Nachrichten | Event Hubs, Service Bus, Event Grid, IoT Hub | | KI & ML | Kognitive Dienste, Maschinelles Lernen, Application Insights | | Integration | API Management, Logic Apps, Key Vault, Container Registry |

[!TIP] Ausführliche Einrichtungsanweisungen, Authentifizierungsoptionen, benutzerdefinierte Profile und Optimierungen finden Sie im [Einrichtungshandbuch für den Azure Monitor-Kollektor] (https://learn.netdata.cloud/docs/collecting-metrics/collectors/cloud-and-devops/azure-monitor#setup).

Support-Optionen <a id="v2100-support-options"></a>

Während wir wachsen, bleiben wir bestrebt, den besten Support zu bieten, den es je bei einer Open-Source-Lösung gab. Sollten Sie ein Problem mit den in dieser Version vorgenommenen Änderungen oder einer Funktion im Netdata Agent haben, können Sie uns gerne über einen der folgenden Kanäle kontaktieren:

  • Premium-Support: Kunden, die einen direkten Kanal mit Netdata und priorisierten Support mit definierten SLAs wünschen, können sich an uns wenden.
  • Netdata Learn: Hier finden Sie Dokumentationen, Anleitungen und Referenzmaterial zur Überwachung und Fehlerbehebung Ihrer Systeme mit Netdata.
  • GitHub-Probleme: Verwenden Sie das Netdata-Repository, um Fehler zu melden oder eine neue Funktionsanfrage zu stellen.
  • GitHub Diskussionen: Nehmen Sie an der Diskussion rund um den Netdata-Entwicklungsprozess teil und seien Sie dabei.
  • Community-Foren: Besuchen Sie die Community-Foren und tragen Sie zur gemeinschaftlichen Wissensdatenbank bei.
  • Discord Server: Steigen Sie in den Netdata Discord ein und treffen Sie sich mit gleichgesinnten Systemadministratoren, DevOps, SREs und anderen Problemlösern. Mehr als 2000 Ingenieure nutzen es bereits!
