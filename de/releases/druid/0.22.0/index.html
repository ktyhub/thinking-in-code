Druide Druide-0.22.0

Apache Druid 0.22.0 enthält über 400 neue Funktionen, Fehlerbehebungen, Leistungsverbesserungen, Dokumentationsverbesserungen und zusätzliche Testabdeckung von 73 Mitwirkenden. Weitere Einzelheiten finden Sie im vollständigen Änderungssatz.

<a name="22-new-features" href="#22-new-features">#</a> Neue Funktionen

<a name="22-query" href="#22-query">#</a> Abfrage-Engine

<a name="22-multi-distinct" href="#22-multi-distinct">#</a> Unterstützung für mehrere unterschiedliche Aggregatoren in derselben Abfrage

Druid kann jetzt mehrere „exakte“ DISTINCT-Zählungen mithilfe des Gruppierungsaggregators unterstützen, der normalerweise bei Gruppierungssätzen verwendet wird. Beachten Sie, dass dies nur für genaue Zählungen gilt – wenn druid.sql.planner.useApproximateCountDistinct falsch ist und durch Setzen von druid.sql.planner.useGroupingSetForExactDistinct auf true aktiviert werden kann. https://github.com/apache/druid/pull/11014

<a name="22-array-agg" href="#22-array-agg">#</a> SQL-Aggregatorfunktionen ARRAY_AGG und STRING_AGG

Die Aggregationsfunktion ARRAY_AGG wurde hinzugefügt, um die Akkumulation von Werten oder unterschiedlichen Werten einer Spalte in einem einzigen Array-Ergebnis zu ermöglichen. Diese Version fügt außerdem STRING_AGG hinzu, das ARRAY_AGG ähnelt, außer dass es die Array-Werte mit einem bereitgestellten „Trennzeichen“ zu einer einzigen Zeichenfolge zusammenfügt und Nullwerte ignoriert. Beide Funktionen akzeptieren einen Parameter für die maximale Größe, um die maximale Ergebnisgröße zu steuern, und schlagen fehl, wenn dieser Wert überschritten wird. Weitere Details finden Sie in der SQL-Dokumentation. https://github.com/apache/druid/pull/11157 https://github.com/apache/druid/pull/11241

<a name="22-bitwise" href="#22-bitwise">#</a> Bitweise mathematische Funktionsausdrücke und Aggregatoren

Mehrere neue SQL-Funktionen zum Ausführen von „bitweiser“ Mathematik (zusammen mit entsprechenden nativen Ausdrücken), einschließlich BITWISE_AND, BITWISE_OR, BITWISE_XOR und so weiter. Darüber hinaus wurden die Aggregationsfunktionen BIT_AND, BIT_OR und BIT_XOR hinzugefügt, um Werte in einer Spalte mit der entsprechenden bitweisen Funktion zu akkumulieren. Ausführliche Informationen finden Sie in der SQL-Dokumentation. https://github.com/apache/druid/pull/10605 https://github.com/apache/druid/pull/10823 https://github.com/apache/druid/pull/11280

<a name="22-human-format" href="#22-human-format">#</a> Für Menschen lesbare Zahlenformatfunktionen

In Druid 0.22.0, HUMAN_READABLE_BINARY_BYTE_FORMAT, HUMAN_READABLE_DECIMAL_BYTE_FORMAT und HUMAN_READABLE_DECIMAL_FORMAT wurden drei neue SQL- und native Ausdrucksnummernformatfunktionen hinzugefügt, die die Umwandlung von Ergebnissen in ein benutzerfreundlicheres Verbrauchsformat für Abfrageergebnisse ermöglichen. Weitere Informationen finden Sie in der SQL-Dokumentation. https://github.com/apache/druid/issues/10584 https://github.com/apache/druid/pull/10635

<a name="22-expr-agg" href="#22-expr-agg">#</a> Ausdrucksaggregator

Druid 0.22.0 fügt eine neue „native“ JSON-Abfrageausdrucksaggregatorfunktion hinzu, mit der Sie native Druid-Ausdrücke verwenden können, um „Fold“-Operationen (auch „Reduzieren“ genannt) durchzuführen, um einen Wert für eine beliebige Anzahl von Eingabespalten zu akkumulieren. Dies erhöht die Flexibilität, die in einem Druid-Aggregator möglich ist, erheblich und ähnelt in vielerlei Hinsicht dem, was mit dem Javascript-Aggregator möglich war, jedoch auf eine viel sicherere Sandbox-Art. Die Möglichkeit, dass Ausdrücke jetzt eine „Faltung“ für Eingabespalten durchführen können, rundet die Fähigkeiten nativer Ausdrücke zusätzlich zu den bisher möglichen Funktionen „Zuordnen“ (virtuelle Ausdrucksspalten), „Filter“ (Ausdrucksfilter) und Nachtransformation (Ausdruck-Post-Aggregatoren) wirklich ab. Da dabei Ausdrücke verwendet werden, ist die Leistung noch nicht optimal und es ist noch nicht direkt dokumentiert, aber es handelt sich um die zugrunde liegende Technologie hinter den SQL-Funktionen ARRAY_AGG, STRING_AGG und den ebenfalls in dieser Version hinzugefügten bitweisen Aggregatorfunktionen. https://github.com/apache/druid/pull/11104

<a name="22-sql-routing" href="#22-sql-routing">#</a> Verbesserungen beim Routing von SQL-Abfragen

Druid 0.22 fügt einige neue Funktionen hinzu, um Erweiterungsautoren eine verbesserte Kontrolle darüber zu bieten, wie Abfragen zwischen Druid-Routern und -Brokern weitergeleitet werden. Die erste fügt dem Druid-Router eine neue manual-Brokerauswahlstrategie hinzu, die es einer Abfrage ermöglicht, manuell anzugeben, an welche Druid-Broker eine Abfrage basierend auf einem Abfragekontextparameter brokerService an jeden in druid.router.tierToBrokerMap definierten Broker-Pool gesendet werden soll (dies entspricht dem „Dienstnamen“ des Broker-Sets, druid.service). Mit der zweiten neuen Funktion kann der Druid-Router SQL-Abfragen analysieren und untersuchen, sodass Broker-Auswahlstrategien auch für SQL-Abfragen funktionieren. Dies kann aktiviert werden, indem druid.router.sql.enable auf true gesetzt wird. Dies hat keine Auswirkungen auf JDBC-Abfragen, die einen anderen Mechanismus verwenden, um „Sticky“-Verbindungen zu einem einzelnen Broker zu ermöglichen. https://github.com/apache/druid/pull/11566 https://github.com/apache/druid/pull/11495

<a name="22-proto-jdbc" href="#22-proto-jdbc">#</a> Avatica protobuf JDBC-Unterstützung

Druid unterstützt jetzt die Verwendung von Avatica Protobuf-JDBC-Verbindungen, beispielsweise für die Verwendung mit dem [Avatica Golang-Treiber] (https://github.com/apache/calcite-avatica-go), und verfügt über einen vom JSON-JDBC-URI getrennten Endpunkt.

String url = "jdbc:avatica:remote:url=http://localhost:8082/druid/v2/sql/avatica-protobuf/;serialization=protobuf";

https://github.com/apache/druid/pull/10543

<a name="22-query-error-log" href="#22-query-error-log">#</a> Verbesserte Protokollierung von Abfragefehlern

Abfrageausnahmen wurden von der Ebene WARN auf die Ebene ERROR geändert, um zusätzliche Informationen in die Protokolle aufzunehmen, die bei der Fehlerbehebung bei Abfragefehlern helfen. Darüber hinaus wurde ein neues Abfragekontextflag, enableQueryDebugging, hinzugefügt, das Stack-Traces in diese Abfragefehlerprotokolle einbezieht, um noch mehr Informationen bereitzustellen, ohne dass Protokolle auf der DEBUG-Ebene aktiviert werden müssen. https://github.com/apache/druid/pull/11519

<a name="22-streaming" href="#22-streaming">#</a> Streaming-Aufnahme

<a name="22-streaming-task-autoscaling" href="#22-streaming-task-autoscaling">#</a> Automatische Aufgabenskalierung für die Streaming-Aufnahme von Kafka und Kinesis

Druid 0.22.0 bietet jetzt experimentelle Unterstützung für die dynamische Kafka- und Kinesis-Aufgabenskalierung. Die enthaltenen Strategien basieren auf der regelmäßigen Messung der Stream-Verzögerung (die bei Kafka auf der Nachrichtenanzahl und bei Kinesis auf dem Altersunterschied zwischen dem Nachrichteniterator und der ältesten Nachricht basiert) und passen die Anzahl der Aufgaben basierend auf dem Ausmaß der „Verzögerung“ und mehreren Konfigurationsparametern an. Vollständige Informationen finden Sie in der Dokumentation zu Kafka und Kinesis. https://github.com/apache/druid/pull/10524 https://github.com/apache/druid/pull/10985

<a name="22-avro-proto-stream" href="#22-avro-proto-stream">#</a> Avro- und Protobuf-Streaming InputFormat- und Confluent Schema Registry-Unterstützung

Die Druid-Streaming-Aufnahme unterstützt jetzt Avro und Protobuf im aktualisierten InputFormat-Spezifikationsformat, das die veraltete Firehose/Parser-Spezifikation ersetzt, die von älteren Druid-Streamingformaten verwendet wird. Daneben gibt es Unterstützung für den Bezug von Schemata für diese Formate von Confluent Schema Registry. Weitere Informationen finden Sie in der Dokumentation zu Datenformaten. https://github.com/apache/druid/pull/11040 https://github.com/apache/druid/pull/11018 https://github.com/apache/druid/pull/10314 https://github.com/apache/druid/pull/10839

<a name="22-kafka-groupid" href="#22-kafka-groupid">#</a> Kafka-Aufnahmeunterstützung für die Angabe von group.id

Die Streaming-Aufnahme von Druid Kafka unterstützt jetzt optional die Angabe von group.id für die Verbindungen, die Druid-Aufgaben zu den Kafka-Brokern herstellen. Dies ist nützlich für den Zugriff auf Cluster, bei denen dies als Teil der Autorisierung festgelegt werden muss, und kann im Abschnitt consumerProperties der Kafka-Supervisor-Spezifikation angegeben werden. Weitere Einzelheiten finden Sie in der Dokumentation zur Kafka-Aufnahme. https://github.com/apache/druid/pull/11147

<a name="22-batch" href="#22-batch">#</a> Native Batch-Aufnahme

<a name="22-shuffle-deep-storage" href="#22-shuffle-deep-storage">#</a> Unterstützung für die Verwendung von Deep Storage für Zwischen-Shuffle-Daten

Druid-native „Perfect Rollup“-2-Phasen-Aufnahmeaufgaben unterstützen jetzt die Verwendung von Deep Storage als Shuffle-Speicherort als Alternative zu lokalen Festplatten auf Middle-Managern oder Indexern. Um diese Funktion zu nutzen, setzen Sie druid.processing.intermediaryData.storage.type auf deepstore, wodurch der konfigurierte Deep-Storage-Typ verwendet wird. Hinweis – Beim Typ „Deepstore“ werden die Daten im Verzeichnis shuffle-data unter dem konfigurierten Deep-Storage-Pfad gespeichert. Die automatische Bereinigung für dieses Verzeichnis wird noch nicht unterstützt. Man kann Cloud-Speicher-Lebenszyklusregeln für die automatische Bereinigung von Daten am Präfixstandort shuffle-data einrichten. https://github.com/apache/druid/pull/11507

<a name="22-batch-memory" href="#22-batch-memory">#</a> Verbesserte Speichernutzung für native Batch-Aufnahmeaufgaben

Die native Batch-Erfassung von Druid hat eine neue Konfigurationsoption, druid.indexer.task.batchProcessingMode, erhalten, die zwei neue Betriebsmodi einführt, die es ermöglichen sollen, die Batch-Erfassung mit einem kleineren und vorhersehbareren Heap-Speicherbedarf zu betreiben. Der CLOSED_SEGMENTS_SINKS-Modus ist der aggressivste und sollte den geringsten Speicherbedarf haben. Er eliminiert die Speicherverfolgung und mmap von Zwischensegmenten, die während der Segmenterstellung erzeugt werden, ist aber zu diesem Zeitpunkt noch nicht besonders gut getestet und wird daher als experimentell angesehen. CLOSED_SEGMENTS, die neue Standardoption, eliminiert mmap von Zwischensegmenten, verfolgt aber weiterhin den gesamten Satz von Segmenten im Heap, obwohl sie zu diesem Zeitpunkt relativ gut getestet wurde und als stabil gilt. OPEN_SEGMENTS verwendet den vorherigen Aufnahmepfad, der mit der Streaming-Aufnahme geteilt wird, führt einen mmap für Zwischensegmente durch und erstellt eine Zeitleiste, damit diese Segmente durch Echtzeitabfragen abgefragt werden können. Dies ist für Batch überhaupt nicht erforderlich, aber der Modus OPEN_SEGMENTS kann ausgewählt werden, wenn Probleme mit den beiden neueren Modi auftreten. https://github.com/apache/druid/pull/11123 https://github.com/apache/druid/pull/11294 https://github.com/apache/druid/pull/11536

<a name="22-batch-wait-for-handoff" href="#22-batch-wait-for-handoff">#</a> Batch-Aufgaben warten lassen, bis die Segmentübergabe abgeschlossen ist, bevor sie abgeschlossen werden

Native Druid-Batch-Aufnahmeaufgaben können jetzt optional so konfiguriert werden, dass sie erst dann beendet werden, wenn die aufgenommenen Segmente vollständig von historischen Servern geladen wurden. Dies kann für Szenarien nützlich sein, in denen es sich lohnt, den Aufgabenstatus als Maß dafür zu verwenden, ob die Aufnahme abgeschlossen ist und Segmente für die Abfrage verfügbar sind. Dies kann durch Hinzufügen von awaitSegmentAvailabilityTimeoutMillis zu tuningConfig in der Aufnahmespezifikation aktiviert werden, was die maximale Zeitspanne angibt, die eine Aufgabe auf das Laden von Segmenten wartet, bevor sie beendet wird. Wenn bis zum Ablauf dieser Zeitüberschreitung nicht alle Segmente verfügbar sind, ist der Auftrag dennoch erfolgreich. Im Aufnahmebericht ist segmentAvailabilityConfirmed jedoch falsch. Dies weist darauf hin, dass die Übergabe nicht erfolgreich war und diese neu indizierten Segmente möglicherweise nicht alle für die Abfrage verfügbar sind. Wenn andererseits alle Segmente vor Ablauf des Zeitlimits für Abfragen in den historischen Diensten verfügbar werden, ist der Wert für diesen Schlüssel im Bericht wahr. Dieser tuningConfig-Wert wird derzeit für Komprimierungsaufgaben nicht unterstützt. Wenn ein Benutzer versucht, einen Wert für awaitSegmentAvailabilityTimeoutMillis für die Komprimierung anzugeben, schlägt die Aufgabe fehl und teilt dem Benutzer mit, dass sie nicht unterstützt wird. https://github.com/apache/druid/pull/10676

<a name="22-compact" href="#22-compact">#</a> Datenlebenszyklusverwaltung

<a name="22-compact-granularity" href="#22-compact-granularity">#</a> Unterstützt die Verwaltung der Segment- und Abfragegranularität für die automatische Komprimierung

Die manuelle und automatische Komprimierung von Druid kann jetzt so konfiguriert werden, dass die Segmentgranularität geändert wird, und die manuelle Komprimierung kann auch die Abfragegranularität ändern. Darüber hinaus bleibt durch die Komprimierung standardmäßig die Segmentgranularität erhalten. Dadurch können Bediener einfacher Optionen wie die Änderung älterer Daten in größere Segmente und Abfragegranularitäten im Austausch für eine geringere Datengröße durchführen. Weitere Informationen finden Sie in den Komprimierungsdokumenten (https://druid.apache.org/docs/0.22.0/ingestion/compaction.html). https://github.com/apache/druid/pull/10843 https://github.com/apache/druid/pull/10856 https://github.com/apache/druid/pull/10900 https://github.com/apache/druid/pull/10912 https://github.com/apache/druid/pull/11009

<a name="22-compact-skip-lock" href="#22-compact-skip-lock">#</a> Erlauben Sie der Komprimierung, gesperrte Intervalle vorübergehend zu überspringen

Die automatische Komprimierung von Druiden überspringt jetzt standardmäßig vorübergehend gesperrte Intervalle, anstatt darauf zu warten, dass die Sperre freigegeben wird, was die Geschwindigkeit verbessern sollte, mit der Datenquellen komprimiert werden können. Dies wird von druid.coordinator.compaction.skipLockedIntervals gesteuert und kann auf „false“ gesetzt werden, wenn dieses Verhalten aus irgendeinem Grund nicht erwünscht ist. https://github.com/apache/druid/pull/11190

<a name="22-config-cleanup" href="#22-config-cleanup">#</a> Unterstützung für zusätzliche automatische Metadatenbereinigung

Sie können die automatische Bereinigung konfigurieren, um Datensätze aus dem Metadatenspeicher zu entfernen, nachdem Sie einige Entitäten aus Druid gelöscht haben:

  • segmentiert Datensätze
  • Prüfaufzeichnungen
  • Aufzeichnungen des Vorgesetzten
  • Regeldatensätze
  • Komprimierungskonfigurationsdatensätze
  • Von Vorgesetzten erstellte Datenquellendatensätze Diese Funktion trägt dazu bei, die Leistung aufrechtzuerhalten, wenn die Abwanderungsrate Ihrer Datenquellen hoch ist, was bedeutet, dass Sie häufig viele kurzlebige Datenquellen oder andere verwandte Entitäten erstellen und löschen. Sie können den Zeitraum für die Aufbewahrung ungenutzter Metadatensätze begrenzen, um zu verhindern, dass Ihr Metadatenspeicher voll wird. Weitere Informationen finden Sie in der Dokumentation zur automatischen Bereinigung. https://github.com/apache/druid/pull/11078 https://github.com/apache/druid/pull/11084 https://github.com/apache/druid/pull/11164 https://github.com/apache/druid/pull/11200 https://github.com/apache/druid/pull/11227 https://github.com/apache/druid/pull/11232 https://github.com/apache/druid/pull/11245

<a name="22-data-cleanup" href="#22-data-cleanup">#</a> Daten werden gelöscht

Eine neue Einstellung, dropExisting, wurde zum ioConfig der nativen Batch-Aufnahmeaufgaben und Komprimierung von Druid hinzugefügt. Wenn sie auf „true“ gesetzt ist (und appendToExist ist „false“), markiert die Aufnahmeaufgabe transaktional alle vorhandenen Segmente im Intervall als ungenutzt und ersetzt sie durch den neuen Satz von Segmenten. Dies kann in Komprimierungsanwendungsfällen nützlich sein, in denen die normale Überschattung einen Satz von Segmenten in einem Intervall nicht vollständig ersetzt, z. B. wenn die Segmentgranularität auf eine kleinere Größe geändert wird und einige der kleineren Granularitätsbereiche keine Daten enthalten würden, sodass die ursprünglichen Segmente nur teilweise überschattet würden. Beachten Sie, dass diese Funktionalität noch experimentell ist und dazu führen kann, dass Daten im komprimierten interval vorübergehend nicht verfügbar sind. Das Ändern dieser Konfiguration führt nicht dazu, dass die Intervalle erneut komprimiert werden. Ebenso wurde markAsUnused als Option zum Druid-Kill-Task hinzugefügt, der alle Segmente im angegebenen Intervall als „unbenutzt“ markiert, bevor alle nicht verwendeten Segmente gelöscht werden. Dies ist nützlich, um zu ermöglichen, dass die Sequenz „Unbenutzt markieren“ -> „Löschen“ mit einem einzelnen API-Aufruf für den Aufrufer ausgeführt wird, und um zu ermöglichen, dass die Aktion „Markierung aufheben“ unter einer Task-Intervallsperre ausgeführt wird. https://github.com/apache/druid/pull/11070 https://github.com/apache/druid/pull/11025 https://github.com/apache/druid/pull/11501

<a name="22-coordinator" href="#22-coordinator">#</a> Koordinator

<a name="22-coord-timeout" href="#22-coord-timeout">#</a> Kontrolle über das Zeitüberschreitungsverhalten beim Laden des Koordinatorsegments mit der auf Apache Zookeeper basierenden Segmentverwaltung

Eine neue dynamische Konfigurationsoption des Druid-Koordinators ermöglicht die Steuerung des Verhaltens bei Zeitüberschreitung einer Segmentladeaktion bei Verwendung der Zookeeper-basierten Segmentverwaltung. Wenn replicateAfterLoadTimeout auf „true“ gesetzt ist, versucht der Koordinator, das Segment, das nicht geladen werden konnte, auf einen anderen historischen Server zu replizieren. Dies trägt dazu bei, die Segmentverfügbarkeit zu verbessern, wenn im Cluster einige langsame historische Server vorhanden sind. Der langsame Verlauf lädt das Segment jedoch möglicherweise später noch und der Koordinator muss möglicherweise Löschanforderungen stellen, wenn das Segment zu stark repliziert wird. https://github.com/apache/druid/pull/10213

<a name="22-coord-balance" href="#22-coord-balance">#</a> Schnellerer Koordinatorsegmentausgleich

Eine weitere neue dynamische Konfigurationsoption für den Koordinator, useBatchedSegmentSampler, kann, wenn sie auf „true“ gesetzt ist, potenziell zu einer erheblichen Leistungssteigerung bei der Geschwindigkeit führen, mit der der Koordinator die Segmentausgleichsphase verarbeiten kann. Dies sollte besonders bei sehr großen Clustergrößen mit vielen Segmenten auffallen, ist aber aus Sicherheitsgründen standardmäßig deaktiviert. https://github.com/apache/druid/pull/11257

<a name="22-coord-replication" href="#22-coord-replication">#</a> Der Ladestatus API wurde verbessert, um optional eine Unterreplikation basierend auf der Clustergröße zu berechnen

Der Druid-Koordinator-Ladestatus API unterstützt jetzt einen neuen optionalen URL-Abfrageparameter, computeUsingClusterView, der bei Angabe dazu führt, dass der Koordinator eine Unterreplikation für Segmente basierend auf der Anzahl der im Cluster verfügbaren Server, auf die das Segment repliziert werden kann, und nicht auf der in der Laderegel konfigurierten Replikationsanzahl verursacht. Wenn die Laderegeln beispielsweise zwei Replikate angeben, es aber nur einen Server gibt, der Segmente speichern kann, würde dieser API nicht als unterrepliziert gemeldet, da die Segmente so repliziert werden, wie es für die gegebene Clustergröße möglich ist. https://github.com/apache/druid/pull/11056

<a name="22-coord-rep-limit" href="#22-coord-rep-limit">#</a> Optionale Begrenzung der Anzahl nicht-primärer Replikanten, die pro Koordinationszyklus geladen werden

Eine neue dynamische Koordinatorkonfiguration, maxNonPrimaryReplicantsToLoad, mit dem Standardwert Integer.MAX_VALUE, ermöglicht es Betreibern, eine feste Obergrenze für die Anzahl nicht-primärer Replikanten zu definieren, die in einem einzelnen Koordinator-Ausführungszyklus geladen werden. Der Standardwert ahmt das heutige Verhalten nach. Beispielverwendung: Wenn Sie diese Konfiguration auf 1000 festlegen, lädt der Koordinator bei jeder Laufzyklusausführung maximal 1000 nicht-primäre Replikanten. Das heißt, wenn Sie 2.000 Segmente mit einem Replikationsfaktor von 2 aufnehmen würden, würde der Koordinator bei der ersten Ausführung 2.000 primäre Replikanten und 1.000 nicht-primäre Replikanten laden. Bei der nächsten Ausführung werden dann die letzten 1000 nicht-primären Replikanten geladen. https://github.com/apache/druid/pull/11135

<a name="22-web" href="#22-web">#</a> Webkonsole

<a name="22-web-general" href="#22-web-general">#</a> Allgemeine Verbesserungen

Auf der Registerkarte „Dienste“ der Druid-Webkonsole wird nun in der Spalte „Detail“ der Tabelle angezeigt, welche Koordinator- und Overlord-Server als Anführer fungieren. Dies soll Betreibern dabei helfen, schneller zu bestimmen, welcher Knoten der Anführer ist und somit wahrscheinlich über die interessanten Protokolle verfügt, die es zu untersuchen gilt. Die Webkonsole unterstützt jetzt auch die Verwendung von ASCII-Steuerzeichen, indem sie diese in der Form \uNNNN eingeben, wobei NNNN der Unicode-Codepunkt für das Zeichen ist. https://github.com/apache/druid/pull/10951 https://github.com/apache/druid/pull/10795

<a name="22-web-query" href="#22-web-query">#</a> Abfrageansicht

Die Abfrageansicht der Webkonsole hat in Druid 0.22.0 eine Reihe von Verbesserungen der Lebensqualität erhalten. Erstens bietet die Abfrageansicht jetzt einen Indikator dafür, wie lange die Ausführung einer Abfrage gedauert hat: Außerdem werden Abfragen beim Öffnen einer neuen Seite nicht mehr automatisch ausgeführt. Um zu verhindern, dass veraltete Abfragen beim Öffnen eines Browsers ausgeführt werden, wird die Seite auf 0 zurückgesetzt, wenn sich das Abfrageergebnis ändert, und das Abfragelimit wird automatisch erhöht, wenn die letzte Seite geladen wird und die Abfrage erneut ausgeführt wird. Die Inline-Dokumentation sollte jetzt auch Informationen zum Druidentyp enthalten: und sollte bessere Vorschläge liefern, wenn ein Abfragefehler auftritt: Schließlich unterstützt die Abfrageansicht der Webkonsole jetzt die Tastenkombination command + enter (auf dem Mac) und ctrl + enter auf Windows und Linux. https://github.com/apache/druid/pull/11158 https://github.com/apache/druid/pull/11128 https://github.com/apache/druid/pull/11203 https://github.com/apache/druid/pull/11365

<a name="22-web-data" href="#22-web-data">#</a> Datenverwaltung

Die Zeitleiste der Segmentansicht der Webkonsole bietet nun die Möglichkeit, ein beliebiges Zeitintervall auszuwählen, statt nur das vorherige Jahr! Die Segmentansicht der Webkonsole wurde ebenfalls verbessert, um bei der Interaktion mit der Tabelle sys.segments hoffentlich leistungsfähiger zu sein. Dazu gehört auch die Möglichkeit, die Webkonsole zu „zwingen“, nur die nativen Methoden JSON API zum Anzeigen von Segmentinformationen zu verwenden: Auch die Nachschlageansicht wurde verbessert, sodass nun „Umfragezeitraum“ und „Zusammenfassung“ als Spalten in der Listenansicht verfügbar sind: Wir haben außerdem eine Validierung des Abfragezeitraums hinzugefügt, um Benutzerfehler zu verhindern, und eine verbesserte Fehlerberichterstattung: https://github.com/apache/druid/pull/11359 https://github.com/apache/druid/pull/10909 https://github.com/apache/druid/pull/11620

<a name="22-metrics" href="#22-metrics">#</a> Metriken

<a name="22-metrics-prometheus" href="#22-metrics-prometheus">#</a> Prometheus Metrik-Emitter

Es wurde eine neue „Contrib“-Erweiterung hinzugefügt, prometheus-emitter, die es ermöglicht, Druid-Metriken direkt an einen Prometheus-Server zu senden. Ausführliche Informationen finden Sie auf der Seite mit der Erweiterungsdokumentation: https://druid.apache.org/docs/0.22.0/development/extensions-contrib/prometheus.html https://github.com/apache/druid/pull/10412 https://github.com/apache/druid/pull/11618

<a name="22-metrics-queue" href="#22-metrics-queue">#</a> ingest/notices/queueSize

ingest/notices/queueSize ist eine neue Metrik, die hinzugefügt wurde, um die Überwachung der Nachrichtenverarbeitungswarteschlangengrößen der Supervisor-Aufzeichnungsaufgabensteuerung zu ermöglichen und dabei zu helfen, festzustellen, ob ein Supervisor möglicherweise durch eine große Menge dieser Hinweise überlastet ist. Diese Metrik wird standardmäßig für jeden laufenden Supervisor ausgegeben. https://github.com/apache/druid/pull/11417

<a name="22-metrics-count" href="#22-metrics-count">#</a> query/segments/count

query/segments/count ist eine neue Metrik, die hinzugefügt wurde, um die Anzahl der Segmente zu verfolgen, die an einer Abfrage teilnehmen. Diese Metrik ist standardmäßig nicht aktiviert und muss daher über eine benutzerdefinierte Erweiterung aktiviert werden, um die ausgegebenen QueryMetrics zu überschreiben, ähnlich wie bei anderen Abfragemetriken, die nicht standardmäßig ausgegeben werden. (Wir wissen, dass dies definitiv nicht freundlich ist, und hoffen, dass wir dies eines Tages einfacher machen können, sorry). https://github.com/apache/druid/pull/11394

<a name="22-clouds" href="#22-clouds">#</a> Cloud-Integrationen

<a name="22-clouds-web-ident" href="#22-clouds-web-ident">#</a> AWS Web Identity/IRSA-Unterstützung

Druid 0.22.0 fügt AWS Web Identity Token-Unterstützung hinzu, die die Verwendung von IAM-Rollen für Dienstkonten auf Kubernetes ermöglicht, wenn es als [AWS-Anmeldeinformationsanbieter] (https://druid.apache.org/docs/0.22.0/development/extensions-core/s3.html#s3-authentication-methods) konfiguriert ist. https://github.com/apache/druid/pull/10541

<a name="22-clouds-assume-role" href="#22-clouds-assume-role">#</a> S3-Ingestion-Unterstützung für die Übernahme einer Rolle

Die native Batch-Aufnahme von Druid aus S3-Eingabequellen kann jetzt die AssumeRole-Funktion in AWS für den kontoübergreifenden Dateizugriff nutzen. Dies kann genutzt werden, indem assumeRoleArn und assumeRoleExternalId in der S3-Eingabequellenspezifikation in einer Batch-Aufnahmeaufgabe festgelegt werden. Weitere Einzelheiten finden Sie in der Dokumentation zu AWS-Dokumentation und zu Native Batch. https://github.com/apache/druid/pull/10995

<a name="22-clouds-gcs-lookup" href="#22-clouds-gcs-lookup">#</a> Google Cloud Storage-Unterstützung für URI-Suchen

Druid-Lookups unterstützen jetzt das Laden über Google Cloud Storage, ähnlich der bestehenden Funktionalität von S3. Dazu muss zusätzlich zu den Lookup-Erweiterungen auch druid-google-extensions geladen werden, aber darüber hinaus ist es so einfach wie die Verwendung eines Google Cloud Storage-URI. https://github.com/apache/druid/pull/11026

<a name="22-odds-and-ends" href="#22-odds-and-ends">#</a> Weitere Änderungen

<a name="22-avro-union-by-type" href="#22-avro-union-by-type">#</a> Extrahieren von Avro-Union-Feldern nach Typ

Die Avro-Aufnahme mittels Druid-Batch- oder Streaming-Aufnahme unterstützt jetzt einen alternativen Mechanismus zum Extrahieren von Daten für Avro Union-Typen. Diese neue Option, extractUnionsByType, funktioniert nur, wenn ein flattenSpec zum Extrahieren verschachtelter Daten aus Union-Typen verwendet wird, und führt dazu, dass die extrahierten Daten mit dem Typ als Teil des Flatten-Pfads verfügbar sind. Wenn diese Option beispielsweise bei einer mehrfach typisierten Union-Spalte someMultiMemberUnion aktiviert ist, wird ein langer Wert von $.someMultiMemberUnion.long statt von $.someMultiMemberUnion extrahiert und es werden nur lange Werte aus der Union extrahiert. Vollständige Informationen finden Sie in der Dokumentation zu Avro. https://github.com/apache/druid/pull/10505

<a name="22-mysql-mariadb" href="#22-mysql-mariadb">#</a> Unterstützung für die Verwendung des MariaDb-Connectors mit MySQL-Erweiterungen

Druid MySQL-Erweiterungen unterstützen jetzt die Verwendung der MariaDB-Connector-Bibliothek als Alternative zum MySQL-Connector. Dies kann durch Festlegen von druid.metadata.mysql.driver.driverClassName auf org.mariadb.jdbc.Driver erfolgen und umfasst die vollständige Unterstützung für JDBC-URI-Parameter-Whitelists, die von JDBC-Suchen und SQL-basierter Aufnahme verwendet werden. https://github.com/apache/druid/pull/11402

<a name="22-dynamic-config" href="#22-dynamic-config">#</a> Umgebungsvariable DynamicConfigProvider hinzufügen

Druid stellt jetzt eine DynamicConfigProvider-Implementierung bereit, die durch Umgebungsvariablen unterstützt wird. Zum Beispiel:

druid.some.config.dynamicConfigProvider={"type": "environment","variables":{"secret1": "SECRET1_VAR","secret2": "SECRET2_VAR"}}

Weitere Informationen finden Sie in der Dokumentation zum Dynamic Config Provider. https://github.com/apache/druid/pull/11377

<a name="22-dynamic-config-schema-registry" href="#22-dynamic-config-schema-registry">#</a> DynamicConfigProvider für Schema Registry hinzufügen

Aufnahmeformate, die Confluent Schema Registry unterstützen, unterstützen jetzt die Bereitstellung dieser Parameter über DynamicConfigProvider, die neuere Alternative zu PasswordProvider. Dadurch können Erfassungsaufgaben den Konfigurationsanbieter verwenden, um diese Informationen bereitzustellen, anstatt sie direkt in den JSON-Spezifikationen bereitzustellen, was das Potenzial für sicherere Methoden zur Bereitstellung von Anmeldeinformationen und anderen vertraulichen Konfigurationsinformationen bietet. Weitere Einzelheiten finden Sie in der Dokumentation zu Datenformat und Dynamic Config Provider. https://github.com/apache/druid/pull/11362

<a name="22-security" href="#22-security">#</a> Sicherheitskorrekturen

<a name="22-security-protos" href="#22-security-protos">#</a> Kontrolle der zulässigen Protokolle für HTTP- und HDFS-Eingabequellen

Druid 0.22.0 fügt neue Funktionen hinzu, um den Satz zulässiger Protokolle zu steuern, die von HTTP- und HDFS-Eingabequellen bei der Stapelaufnahme verwendet werden. druid.ingestion.hdfs.allowedProtocols ist standardmäßig so konfiguriert, dass es hdfs als Protokoll akzeptiert, und druid.ingestion.http.allowedProtocols lässt standardmäßig http und https zu. Dies kann bei bestehenden Bereitstellungen zu Problemen führen, da es restriktiver ist als das aktuelle Standardverhalten in älteren Versionen von Druid, aber insgesamt bietet es den Betreibern mehr Flexibilität bei der Sicherung dieser Eingabequellen. https://github.com/apache/druid/pull/10830

<a name="22-security-ldap" href="#22-security-ldap">#</a> Ablauflogik für den internen LDAP-Anmeldeinformationscache korrigiert

Diese Version von Druid behebt außerdem einen Fehler in der druid-basic-security-Erweiterung bei Verwendung von LDAP, bei dem der Anmeldeinformations-Cache nicht ordnungsgemäß ablief und möglicherweise abgelaufene Anmeldeinformationsinformationen enthielt, nachdem sie abgelaufen sein sollten, bis ein anderer Auslöser ausgelöst oder der Dienst neu gestartet wurde. Druid-Cluster, die LDAP zur Autorisierung verwenden, sollten wann immer möglich auf 0.22.0 aktualisieren, um dieses Problem zu beheben. https://github.com/apache/druid/pull/11395

<a name="22-bug-fixes" href="#22-bug-fixes">#</a> Fehlerbehebungen

Druid 0.22.0 enthält über 80 Fehlerbehebungen, Sie können die vollständige Liste hier sehen.

<a name="22-upgrading-to-22" href="#22-upgrading-to-22">#</a> Upgrade auf 0.22.0

Berücksichtigen Sie beim Upgrade von Druid 0.21.x auf 0.22.0 die folgenden Änderungen und Aktualisierungen. Wenn Sie von einer früheren Version als 0.21.0 aktualisieren, sehen Sie sich die release notes der relevanten Zwischenversionen an.

<a name="22-up-dropped-zk-3.4" href="#22-up-dropped-zk-3.4">#</a> Unterstützung für Apache ZooKeeper 3.4 eingestellt

Im Anschluss an 0.21, das die Unterstützung für Zookeeper 3.4 offiziell eingestellt hat, [das seit einiger Zeit nicht mehr verfügbar ist] (https://mail-archives.apache.org/mod_mbox/zookeeper-user/202004.mbox/%3C41A7EC67-D8F4-4C3A-B2DB-C2741C2EECA3%40apache.org%3E), wird die Unterstützung für ZooKeeper 3.4 nun in 0.22.0 entfernt. Stellen Sie sicher, dass Sie Ihren Zookeeper-Cluster aktualisieren, bevor Sie Ihren Druid-Cluster auf 0.22.0 aktualisieren. https://github.com/apache/druid/issues/10780 https://github.com/apache/druid/pull/11073

<a name="22-up-batch-lineage" href="#22-up-batch-lineage">#</a> Korrektur der Segmentzuordnung für die native Batchaufnahme

Druid 0.22.0 enthält eine wichtige Fehlerbehebung bei der nativen Batch-Indizierung, bei der vorübergehende Fehler bei der Indizierung von Unteraufgaben zu nicht zusammenhängenden Partitionen in den Ergebnissegmenten führen können, die aufgrund der Logik, die nach dem „vollständigen“ Satz prüft, nie abfragbar werden. Dieses Problem wurde in der neuesten Version von Druid behoben, erforderte jedoch eine Änderung des Protokolls, das Batch-Aufgaben zum Zuweisen von Segmenten verwenden. Diese Änderung kann bei rollierenden Downgrades zu Problemen führen, wenn Sie sich für ein Rollback von Druid 0.22.0 auf eine frühere Version entscheiden. Um Aufgabenfehler während eines fortlaufenden Downgrades zu vermeiden, legen Sie fest

druid.indexer.task.default.context={ "useLineageBasedSegmentAllocation" : false }

in den Overlord-Laufzeiteigenschaften und warten Sie, bis alle Aufgaben abgeschlossen sind, bei denen useLineageBasedSegmentAllocation auf „true“ gesetzt ist, bevor Sie das Downgrade einleiten. Nachdem alle diese Aufgaben abgeschlossen sind, sollte das Downgrade keine weiteren Probleme mehr haben und die Einstellung kann aus der Overlord-Konfiguration entfernt werden (empfohlen, da diese Einstellung aktiviert sein soll, wenn Sie Druid 0.22.0 oder neuer verwenden). https://github.com/apache/druid/pull/11189

<a name="22-up-sql-buckets" href="#22-up-sql-buckets">#</a> SQL-Zeitreihen überspringen leere Buckets nicht mehr mit aller Granularität

Vor Druid 0.22 würde eine SQL-Gruppierungsabfrage, die einen einzelnen universellen Gruppierungsschlüssel (z. B. nur Aggregatoren) wie SELECT COUNT(*), SUM(x) FROM y WHERE z = 'someval' verwendet, einen leeren Ergebnissatz anstelle von [0, null] erzeugen, was bei dieser Abfrage zu erwarten wäre, die keine Ergebnisse liefert. Dies lag daran, dass darunter eine Zeitreihenabfrage mit der Granularität „ALL“ geplant werden würde und skipEmptyBuckets im Abfragekontext auf „true“ gesetzt wäre. Diese letztere Option führte dazu, dass die Ergebnisse einer solchen Abfrage keine Ergebnisse zurückgaben, da keine Buckets mit zu aggregierenden Werten vorhanden sind und diese daher übersprungen werden, wodurch ein leerer Ergebnissatz anstelle eines „Null“-Ergebnissatzes entsteht. Dieses Verhalten wurde geändert, um sich im Einklang mit anderen SQL-Implementierungen zu verhalten. Das vorherige Verhalten kann jedoch durch explizites Festlegen von skipEmptyBuckets im Abfragekontext erreicht werden. https://github.com/apache/druid/pull/11188

<a name="22-up-reingest" href="#22-up-reingest">#</a> Inkompatible Änderungen bei der erneuten Aufnahme durch Druiden

Batch-Aufgaben, die eine „Druid“-Eingabequelle zum erneuten Einlesen von Segmentdaten verwenden, akzeptieren die Abschnitte „Dimensionen“ und „Metriken“ ihrer Aufgabenspezifikation nicht mehr und verwenden nun intern einen neuen Spaltenfilter, um anzugeben, welche Spalten aus dem ursprünglichen Segment beibehalten werden sollen. Darüber hinaus wird timestampSpec nicht mehr ignoriert, sodass die Spalte „__time“ geändert oder durch eine andere Spalte ersetzt werden kann. Diese Änderungen beheben außerdem einen Fehler, bei dem transformierte Spalten ignoriert wurden und in den neuen Segmenten nicht verfügbar waren. https://github.com/apache/druid/pull/10267

<a name="22-up-ie11" href="#22-up-ie11">#</a> Die Druid-Webkonsole unterstützt IE11 und andere ältere Browser nicht mehr

Einige Dinge funktionieren möglicherweise noch, es wird jedoch nicht mehr offiziell unterstützt, sodass neuere Javascript-Funktionen zur Entwicklung der Webkonsole verwendet werden können. https://github.com/apache/druid/pull/11357

<a name="22-up-ie11" href="#22-up-ie11">#</a> Die standardmäßige maximale Größe der Segmentladewarteschlange wurde geändert

Die dynamische Konfiguration des Druidenkoordinators maxSegmentsInNodeLoadingQueue wurde von unbegrenzt (0) auf 100 geändert. Dies sollte dazu führen, dass sich der Koordinator in Zeiten der Clustervolatilität, wie z. B. bei einem fortlaufenden Upgrade, viel entspannter verhält, begrenzt jedoch die Gesamtzahl der Segmente, die in einem bestimmten Koordinatorzyklus geladen werden, auf 100 pro Server, was die Geschwindigkeit verlangsamen kann, mit der ein vollständig gestoppter Cluster gestartet und aus dem Deep Storage geladen wird. https://github.com/apache/druid/pull/11540

<a name="22-dev-notes" href="#22-dev-notes">#</a> Entwicklerhinweise

<a name="22-dev-expr-cache-key" href="#22-dev-expr-cache-key">#</a> CacheKeyBuilder wurde von druid-processing nach druid-core verschoben

Die Klasse CacheKeyBuilder, die mit @PublicAPI annotiert ist, wurde von druid-processing nach druid-core verschoben, sodass Ausdrücke die Cacheable-Schnittstelle erweitern können, um Ausdrücken das Generieren von Cache-Schlüsseln zu ermöglichen, die von einem externen Status, z. B. der Suchversion, abhängen. https://github.com/apache/druid/pull/11358

<a name="22-dev-query-processing-pool" href="#22-query-processing-pool">#</a> Die Abfrage-Engine verwendet jetzt direkt das neue QueryProcessingPool anstelle von ExecutorService

Dies wirkt sich auf eine Handvoll Methodensignaturen in der Abfrageverarbeitungs-Engine aus, z. B. QueryRunnerFactory und QuerySegmentWalker, damit Erweiterungen in Zukunft in verschiedene Teile des Abfrageverarbeitungspools und alternative Planungsstrategien für den Verarbeitungspool eingebunden werden können. https://github.com/apache/druid/pull/11382

<a name="22-dev-segment-loader" href="#22-dev-segment-loader">#</a> SegmentLoader ist jetzt erweiterbar und anpassbar

Dadurch können Erweiterungen alternative Implementierungen zum Laden von Segmenten bereitstellen, um anzupassen, wie Druid-Segmente aus dem Deep Storage geladen und der Abfrage-Engine zur Verfügung gestellt werden. Dies sollte als instabiler api betrachtet werden und ist im Code als solcher gekennzeichnet. https://github.com/apache/druid/pull/11398
