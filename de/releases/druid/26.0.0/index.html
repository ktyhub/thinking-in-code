Druide Druide-26.0.0

Apache Druid 26.0.0 enthält über 390 neue Funktionen, Fehlerbehebungen, Leistungsverbesserungen, Dokumentationsverbesserungen und zusätzliche Testabdeckung von 65 Mitwirkenden.

Weitere Einzelheiten finden Sie im vollständigen Änderungssatz.

Lesen Sie die Upgrade-Hinweise und inkompatible Änderungen, bevor Sie ein Upgrade auf Druid 26.0.0 durchführen.

<a name="26.0.0-highlights-auto-type-column-schema-%28experimental%29" href="#26.0.0-highlights-auto-type-column-schema-%28experimental%29">#</a> Spaltenschema automatisch eingeben (experimentell)

Als nächste logische Iteration der Funktionalität verschachtelter Spalten wurde der nativen Aufnahme ein neues Spaltenschema und Indexer vom Typ „Auto“ hinzugefügt. Dieser automatische Spaltenindexer erzeugt die am besten geeignete Spalte für die gegebenen Eingaben und erzeugt entweder die Spalten STRING, ARRAY<STRING>, LONG, ARRAY<LONG>, DOUBLE, ARRAY<DOUBLE> oder COMPLEX<json>, die alle ein gemeinsames „verschachteltes“ Format haben.

Alle von „auto“ erzeugten Spalten verfügen über Indizes, die eine schnelle Filterung unterstützen (im Gegensatz zu den klassischen Spalten LONG und DOUBLE) und verwenden kardinalitätsbasierte Schwellenwerte, um zu versuchen, diese Indizes nur dann zu verwenden, wenn die Abfrage wahrscheinlich tatsächlich beschleunigt wird (im Gegensatz zu klassischen STRING-Spalten).

Von diesem „automatischen“ Indexer erstellte COMPLEX<json>-Spalten speichern Arrays einfacher Skalartypen anders als ihre „json“-(v4)-Gegenstücke und speichern sie als Spalten vom Typ ARRAY. Das bedeutet, dass die Funktion JSON_VALUE nun ganze Arrays extrahieren kann, zum Beispiel JSON_VALUE(nested, '$.array' RETURNING BIGINT ARRAY). Derzeit gibt es keine Änderungen an der Art und Weise, wie Arrays komplexer Objekte gespeichert werden.

Diese Verbesserung fügt Druid auch eine völlig neue Funktionalität hinzu: ARRAY-typisierte Spalten, die sich im Gegensatz zu klassischen mehrwertigen STRING-Spalten mit der ARRAY-Semantik verhalten. Diese Spalten können derzeit nur über den Indexer vom Typ „Auto“ erstellt werden, wenn alle Werte Arrays mit demselben Elementtyp sind.

Ein Array-Datentyp ist ein Datentyp, der es Ihnen ermöglicht, mehrere Werte in einer einzelnen Spalte einer Datenbanktabelle zu speichern. Arrays werden in der Regel zum Speichern zusammengehöriger Datenmengen verwendet, die als Gruppe leicht abgerufen und bearbeitet werden können.

Diese Version bietet Unterstützung für das Speichern von Arrays mit Grundwerten wie ARRAY<STRING>, ARRAY<LONG> und ARRAY<DOUBLE> als spezielle verschachtelte Spalten, anstatt sie in separate Elementspalten aufzuteilen.

Diese Änderungen wirken sich auf zwei zusätzliche neue Funktionen aus, die in 26.0 verfügbar sind: automatische Schemaerkennung und Unnest.

<a name="26.0.0-highlights-auto-type-column-schema-%28experimental%29-schema-auto-discovery-%28experimental%29" href="#26.0.0-highlights-auto-type-column-schema-%28experimental%29-schema-auto-discovery-%28experimental%29">#</a> Automatische Schemaerkennung (experimentell)

Wir fügen Druid die automatische Schemaerkennung mit Typinferenz hinzu. Mit dieser Funktion wird der Datentyp jedes eingehenden Felds erkannt, wenn ein Schema verfügbar ist. Für eingehende Daten, die möglicherweise hinzugefügte, gelöschte oder geänderte Felder enthalten, können Sie die fehlerhaften Daten ablehnen („Die Datenbank ist immer korrekt – schlechte Daten werden abgelehnt!“), oder Sie können die automatische Schemaerkennung die Datenquelle so ändern lassen, dass sie mit den eingehenden Daten übereinstimmt („Die Daten sind immer richtig – ändern Sie die Datenbank!“). Die automatische Schemaerkennung wird für neue Anwendungsfälle und Aufnahmen empfohlen. Seien Sie bei bestehenden Anwendungsfällen vorsichtig, wenn Sie auf die automatische Schema-Erkennung umstellen, da Druid Array-ähnliche Werte (z. B. ["tag1", "tag2]) als Spalten vom Typ ARRAY<STRING> anstelle von Zeichenfolgen mit mehreren Werten (MV) aufnimmt. Dies kann zu Problemen bei der Reaktion nachgelagerter Apps auf das MV-Verhalten führen. Warten Sie mit dem Wechsel, bis ein offizieller Migrationspfad verfügbar ist.

Um diese Funktion zu nutzen, setzen Sie spec.dataSchema.dimensionsSpec.useSchemaDiscovery in Ihrer Aufgaben- oder Supervisor-Spezifikation auf true oder deaktivieren Sie bei Verwendung des Datenladers in der Konsole den Schalter Explicitly define schema im Schritt Configure schema. Druid kann das gesamte Schema oder einen Teil davon ableiten, wenn Sie Dimensionen explizit in Ihrer Dimensionsliste auflisten.

Die automatische Schemaerkennung ist für die native Batch- und Streaming-Aufnahme verfügbar.

<a name="26.0.0-highlights-unnest-arrays-%28experimental%29-" href="#26.0.0-highlights-unnest-arrays-%28experimental%29-">#</a> UNNEST-Arrays (experimentell)

Das Coole an UNNEST ist unter anderem, dass es ein breiteres Spektrum an Operationen ermöglicht, die bei Array-Datentypen nicht möglich waren. Sie können Arrays entweder mit der UNNEST-Funktion (SQL) oder der unnest-Datenquelle (nativ) entschachteln.

Unnest wandelt verschachtelte Arrays oder Tabellen in einzelne Zeilen um. Die UNNEST-Funktion ist besonders nützlich, wenn Sie mit komplexen Datentypen arbeiten, die verschachtelte Arrays enthalten, wie z. B. JSON.

Angenommen, Sie haben eine Tabelle namens „Bestellungen“ mit einer Spalte namens „Artikel“, die eine Reihe von Produkten für jede Bestellung enthält. Sie können unnest verwenden, um die einzelnen Produkte („each_item“) wie im folgenden SQL-Beispiel zu extrahieren:

SELECT order_id, each_item FROM orders, UNNEST(items) as unnested(each_item)

Dadurch wird ein Ergebnissatz mit einer Zeile für jeden Artikel in jeder Bestellung sowie Spalten für die Bestell-ID und den einzelnen Artikel erstellt

Beachten Sie das Komma nach der linken Tabelle/Datenquelle (orders im Beispiel). Es ist erforderlich.

<a name="26.0.0-highlights-sort-merge-join-and-hash-shuffle-join-for-msq" href="#26.0.0-highlights-sort-merge-join-and-hash-shuffle-join-for-msq">#</a> Sort-Merge-Join und Hash-Shuffle-Join für MSQ

Wir können jetzt Shuffle-Joins durchführen, indem wir den Kontextparameter sqlJoinAlgorithm auf sortMerge für den Sortier-Merge-Algorithmus setzen oder ihn weglassen, um Broadcast-Joins durchzuführen (Standard).

Mehrstufige Abfragen können einen Sortier-Zusammenführungs-Join-Algorithmus verwenden. Bei diesem Algorithmus wird jeder paarweise Join in einer eigenen Phase mit zwei Eingaben geplant. Dieser Ansatz ist im Allgemeinen weniger leistungsfähig, aber skalierbarer als Broadcast.

Setzen Sie den Kontextparameter sqlJoinAlgorithm auf sortMerge, um diese Methode zu verwenden.

Broadcast-Hash-Joins ähneln der Ausführung nativer Join-Abfragen.

#13506

<a name="26.0.0-highlights-storage-improvements-on-dictionary-compression--" href="#26.0.0-highlights-storage-improvements-on-dictionary-compression--">#</a> Speicherverbesserungen bei der Wörterbuchkomprimierung

Durch den Wechsel zur Frontcoding-Wörterbuchkomprimierung (experimentell) können bis zu 30 % eingespart werden, ohne dass dies Auswirkungen auf die Abfrageleistung hat.

Diese Version verbessert den frontCoded-Typ von stringEncodingStrategy auf indexSpec weiter mit einer neuen Segmentformatversion, die typischerweise schnellere Lesegeschwindigkeiten und eine reduzierte Segmentgröße bietet. Diese Verbesserung ist abwärtskompatibel mit Druid 25.0. Eine neue Option formatVersion hinzugefügt, die standardmäßig die aktuelle Version 0 verwendet. Setzen Sie formatVersion auf 1, um mit der Verwendung der neuen Version zu beginnen.

Unterstützung für den HTTP-Antwortheader Strict-Transport-Security hinzugefügt. Druid enthält diesen Header standardmäßig nicht. Sie müssen es in den Laufzeiteigenschaften aktivieren, indem Sie druid.server.http.enableHSTS auf true setzen.

Erweitert die OIDC-basierte Authentifizierung in Druid durch Hinzufügen eines JWT-Authentifikators, der mit einer Anfrage verknüpfte ID-Token validiert. Der vorhandene pac4j-Authentifikator dient zur Authentifizierung von Webbenutzern beim Zugriff auf die Konsole, während dieser Authentifikator zur Validierung von Druid-API-Anfragen dient, die von Direct clients gestellt werden. Dienste, die OIDC bereits unterstützen, können ihre ID-Tokens an die Druid-Anfragen anhängen unter der Überschrift Autorisierungsanforderung.

<a name="26.0.0-upgrade-notes-and-incompatible-changes--inkompatible-changes-firehose-ingestion-removed" href="#26.0.0-upgrade-notes-and-incompatible-changes--inkompatible-changes-firehose-ingestion-removed">#</a> Firehose-Aufnahme entfernt

Die von älteren Druid-Streamingformaten verwendete Firehose-/Parser-Spezifikation wird entfernt. Die Firehose-Aufnahme war in Version 0.17 veraltet und die Unterstützung für diese Aufnahme wurde in Version 24.0 entfernt.

#12852

<a name="26.0.0-upgrade-notes-and-incompatible-changes--inkompatible-changes-information-schema-now-uses-numeric-column-types-" href="#26.0.0-upgrade-notes-and-incompatible-changes--inkompatible-changes-information-schema-now-uses-numeric-column-types-">#</a> Das Informationsschema verwendet jetzt numerische Spaltentypen

Die Druid-Systemtabelle (INFORMATION_SCHEMA) verwendet jetzt SQL-Typen anstelle von Druid-Typen für Spalten. Durch diese Änderung verhält sich die Tabelle INFORMATION_SCHEMA eher wie Standard-SQL. In den folgenden Szenarien müssen Sie möglicherweise Ihre Abfragen aktualisieren, um unerwartete Ergebnisse zu vermeiden, wenn Sie von einem der folgenden Faktoren abhängig sind:

– Numerische Felder werden als Zeichenfolgen behandelt.

  • Spaltennummerierung beginnt bei 0. Die Spaltennummerierung basiert jetzt auf 1.

#13777

<a name="26.0.0-upgrade-notes-and-incompatible-changes--inkompatible-changes-%60frontcoded%60-segment-format-change" href="#26.0.0-upgrade-notes-and-incompatible-changes--inkompatible-changes-%60frontcoded%60-segment-format-change">#</a> frontCoded Änderung des Segmentformats

Der frontCoded-Typ von stringEncodingStrategy auf indexSpec mit einer neuen Segmentformatversion, die typischerweise schnellere Lesegeschwindigkeiten und eine reduzierte Segmentgröße bietet. Diese Verbesserung ist abwärtskompatibel mit Druid 25.0.

Weitere Informationen finden Sie im Highlight zur String-Codierungsstrategie frontCoded.

<a name="26.0.0-upgrade-notes-and-incompatible-changes-developer-notes" href="#26.0.0-upgrade-notes-and-incompatible-changes-developer-notes">#</a> Entwicklerhinweise

<a name="26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-null-value-coercion-moved-out-of-expression-processing-engine-" href="#26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-null-value-coercion-moved-out-of-expression-processing-engine-">#</a> Nullwerterzwingung wurde aus der Ausdrucksverarbeitungs-Engine entfernt

Nullwerte, die in die native Druid-Ausdrucksverarbeitungs-Engine eingegeben und von dieser erstellt werden, zwingen null nicht mehr dazu, den typgerechten „Standard“-Wert einzugeben, wenn druid.generic.useDefaultValueForNull=true. Dies sollte sich nicht auf das bestehende Verhalten auswirken, da dies auf den Verbraucher verlagert wurde und die Betreiber intern in diesem Modus weiterhin Standardwerte verwenden. Allerdings kann es bei der Verarbeitung von null-Werten zu geringfügigen Verhaltensänderungen kommen. Direktaufrufer können Standardwerte erhalten, indem sie die neue valueOrDefault()-Methode von ExprEval anstelle von value() verwenden.

#13809

<a name="26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-simplified-dependencies" href="#26.0.0-upgrade-notes-and-incompatible-changes-developer-notes-simplified-dependencies">#</a> Vereinfachte Abhängigkeiten

Die Module druid-core, extendedset und druid-hll wurden in druid-processing konsolidiert, um Abhängigkeiten zu vereinfachen. Alle Erweiterungen, die darauf verweisen, sollten aktualisiert werden, um stattdessen druid-processing zu verwenden. Vorhandene Erweiterungsbinärdateien sollten weiterhin normal funktionieren, wenn sie mit neueren Versionen von Druid verwendet werden.

Diese Änderung hat keine Auswirkungen auf Endbenutzer. Es wirkt sich auf jeden aus, der Erweiterungen für Druid entwickelt.
