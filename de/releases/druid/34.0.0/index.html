[#18239](https://github.com/apache/druid/pull/18239) ### Verwenden Sie SET-Anweisungen für Abfragekontextparameter Sie können jetzt SET-Anweisungen verwenden, um Abfragekontextparameter für eine Abfrage über die [Druid-Konsole](#set-statements-in-the-druid-console) oder die [API](#set-statements-with-the-api) zu definieren. [#17894](https://github.com/apache/druid/pull/17894) [#17974](https://github.com/apache/druid/pull/17974) #### SET-Anweisungen in der Druid-Konsole Die Webkonsole unterstützt jetzt die Verwendung von SET-Anweisungen zum Angeben von Abfragekontextparametern. Wenn Sie beispielsweise `SET timeout = 20000;` in Ihre Abfrage einbeziehen, wird der Kontextparameter der Timeout-Abfrage festgelegt: ```sql SET timeout = 20000; SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2 ``` [#17966](https://github.com/apache/druid/pull/17966) #### SET-Anweisungen mit dem API An `/druid/v2/sql` ausgegebene SQL-Abfragen können jetzt mehrere SET-Anweisungen enthalten, um den Kontext für die endgültige Anweisung aufzubauen. Die folgenden SQL-Abfrageergebnisse umfassen beispielsweise die Abfragekontextparameter `timeout`, `useCache`, `populateCache`, `vectorize` und `engine`: ```sql SET timeout = 20000; SET useCache = false; SET populateCache = false; SET vectorize = 'force'; SET engine = 'msq-dart' SELECT "channel", "page", sum("added") from "wikipedia" GROUP BY 1, 2 ``` Der API-Aufruf für diese Abfrage sieht wie folgt aus: ```curl curl --location 'http://HOST:PORT/druid/v2/sql' \ --header 'Content-Type: application/json' \ --data '{ "query": "SET timeout=20000; SET useCache=false; SET populateCache=false; SET engine='\''msq-dart'\'';SELECT user, commentLength,COUNT(*) AS \"COUNT\" FROM wikipedia GROUP BY 1, 2 ORDER BY 2 DESC", "resultFormat": "array", "header": true, "typesHeader": true, "sqlTypesHeader": true }' ``` Diese Verbesserung funktioniert auch für INSERT- und REPLACE-Abfragen mithilfe der MSQ-Task-Engine. Beachten Sie, dass JDBC nicht unterstützt wird. #### Verbesserte HTTP-Endpunkte Sie können jetzt unformatiertes SQL im HTTP-Body für `/druid/v2/sql`-Endpunkte verwenden. Sie können `Content-Type` auf `text/plain` anstelle von `application/json` setzen, sodass Sie Rohtext bereitstellen können, der nicht maskiert ist. [#17937](https://github.com/apache/druid/pull/17937) ### Historische Daten klonen (experimentell) Sie können jetzt Klone für Historicals mithilfe der dynamischen Koordinatorkonfiguration `cloneServers` konfigurieren. Geklonte Historicals sind nützlich für Situationen wie fortlaufende Updates, bei denen Sie ein neues Historical als Ersatz für ein vorhandenes starten möchten. Legen Sie die Konfiguration auf eine Zuordnung vom historischen Zielserver zum historischen Quellserver fest: ``` "cloneServers": {"historicalClone":"historicalOriginal"} ``` Der Klon nimmt nicht an der regulären Segmentzuweisung oder dem Segmentausgleich teil. Stattdessen spiegelt der Koordinator alle Segmentzuweisungen, die der ursprünglichen historischen Datei vorgenommen wurden, auf den Klon, sodass der Klon eine exakte Kopie der Quelle wird. Segmente auf dem historischen Klon zählen ebenfalls nicht zur Replikatzählung. Wenn der ursprüngliche Verlauf verschwindet, verbleibt der Klon im letzten bekannten Status des Quellservers, bis er aus der `cloneServers`-Konfiguration entfernt wird. Wenn Sie Ihre Daten mit der nativen Abfrage-Engine abfragen, können Sie Klone bevorzugen (`preferClones`), ausschließen (`excludeClones`) oder einschließen (`includeClones`), indem Sie den Abfragekontextparameter `cloneQueryMode` festlegen. Klone sind standardmäßig ausgeschlossen. Im Rahmen dieser Änderung sind neue Coordinator APIs verfügbar. Weitere Informationen finden Sie unter [Koordinator APIs für Klone](#coordinator-apis-for-clones). [#17863](https://github.com/apache/druid/pull/17863) [#17899](https://github.com/apache/druid/pull/17899) [#17956](https://github.com/apache/druid/pull/17956) ### Eingebettete Kill-Aufgaben auf dem Overlord (experimentell) Sie können Kill-Aufgaben jetzt direkt auf dem Overlord selbst ausführen. Eingebettete Kill-Aufgaben bieten mehrere Vorteile; sie: - Töte Segmente, sobald sie geeignet sind - Nehmen Sie keinen Aufgabenplatz in Anspruch - schneller fertig werden, da optimierte Metadatenabfragen verwendet werden und kein neues JVM gestartet wird - Beenden Sie eine kleine Anzahl von Segmenten pro Aufgabe, um sicherzustellen, dass Sperren für ein Intervall nicht zu lange gehalten werden - Überspringen Sie gesperrte Intervalle, um eine Blockierung am Zeilenanfang zu vermeiden - Erfordert eine minimale Konfiguration - Kann mit einer großen Anzahl ungenutzter Segmente im Cluster Schritt halten Diese Funktion wird durch die folgenden Konfigurationen gesteuert: - `druid.manager.segments.killUnused.enabled` – Ob die Funktion aktiviert ist oder nicht (Standard ist `false`) – `druid.manager.segments.killUnused.bufferPeriod` – Die Zeitspanne, die ein Segment ungenutzt bleiben muss, bevor es dauerhaft aus Metadaten und Deep Storage entfernt werden kann. Dies kann als Pufferzeitraum dienen, um Datenverlust zu verhindern, wenn Daten benötigt werden, nachdem sie als nicht verwendet markiert wurden (Standardeinstellung ist `P30D`). Um eingebettete Kill-Aufgaben verwenden zu können, muss der Segmentmetadaten-Cache aktiviert sein. Als Teil dieser Funktion wurden [neue Metriken](#overlord-kill-task-metrics) hinzugefügt. [#18028](https://github.com/apache/druid/pull/18028) [#18124](https://github.com/apache/druid/pull/18124) ### Auswahl der bevorzugten Stufe Sie können den Broker-Dienst jetzt so konfigurieren, dass er historische Daten auf einer bestimmten Ebene bevorzugt. Dies ist nützlich für die Bereitstellung über mehrere Verfügbarkeitszonen hinweg. Broker in einer AZ wählen standardmäßig historische Knoten in derselben AZ aus, behalten jedoch weiterhin die Möglichkeit, historische Knoten in einer anderen AZ auszuwählen, wenn historische Knoten in derselben AZ nicht verfügbar sind. Legen Sie zum Aktivieren die Eigenschaft `druid.broker.select.tier` in den Broker-Laufzeiteigenschaften auf `perferred` fest. Anschließend können Sie `druid.broker.select.tier.preferred.tier` auf die Ebene konfigurieren, die jeder Broker bevorzugen soll (d. h. für Broker in `AZ1` können Sie dies auf den Ebenennamen Ihrer historischen `AZ1`-Server festlegen). [#18136](https://github.com/apache/druid/pull/18136) ### Dart-Verbesserungen Die Dart-Abfrage-Engine verwendet jetzt wie andere SQL-Abfrage-Engines den Endpunkt `/druid/v2/sql`. Der frühere Dart-spezifische Endpunkt wird nicht mehr unterstützt. Um Dart für eine Abfrage zu verwenden, schließen Sie den Abfragekontextparameter `engine` ein und legen Sie ihn auf `msq-dart` fest. [#18003](https://github.com/apache/druid/pull/18003) [#18003](https://github.com/apache/druid/pull/18003) Die Aktivierung von Dart bleibt unverändert. Fügen Sie die folgende Zeile zu Ihren Dateien `broker/runtime.properties` und `historical/runtime.properties` hinzu: ``` druid.msq.dart.enabled = true ``` Darüber hinaus fragt Dart jetzt standardmäßig Echtzeitaufgaben ab. Sie können dieses Verhalten steuern, indem Sie den Abfragekontextparameter `includeSegmentSource` auf `REALTIME` (Standard) oder `NONE` setzen, ähnlich wie bei MSQ-Aufgaben. Sie können auch synchrone oder asynchrone Abfragen ausführen. Aufnahme Die Hadoop-basierte Aufnahme ist seit Druid 32.0 veraltet und wird bereits mit Druid 35.0.0 entfernt. Wir empfehlen eine der anderen unterstützten Erfassungsmethoden von Druid, z. B. [SQL-basierte Erfassung](../multi-stage-query/index.md) oder [MiddleManager-lose Erfassung mit Kubernetes](../development/extensions-core/k8s-jobs.md). Im Rahmen dieser Änderung müssen Sie sich nun für die Verwendung des veralteten Aufgabentyps `index_hadoop` anmelden. Wenn Sie dies nicht tun, schlagen Ihre Hadoop-basierten Aufnahmeaufgaben fehl. Um sich anzumelden, setzen Sie `druid.indexer.task.allowHadoopTaskExecution` in Ihrer `common.runtime.properties`-Datei auf `true`. [#18239](https://github.com/apache/druid/pull/18239) #### `groupBy`- und `topN`-Abfragen Druid verwendet jetzt den nativen Abfragetyp `groupBy` anstelle von `topN` für SQL-Abfragen dieser Gruppe nach und sortieren nach derselben Spalte, haben `LIMIT` und haben nicht `HAVING`. Dies beschleunigt die Ausführung solcher Abfragen, da `groupBy` vektorisiert ist, `topN` jedoch nicht. Sie können das vorherige Verhalten wiederherstellen, indem Sie den Abfragekontextparameter `useLexicographicTopN` auf `true` setzen. Das Verhalten für `useApproximateTopN` bleibt unverändert und die Standardeinstellung bleibt `true`. [#18074](https://github.com/apache/druid/pull/18074) #### `IS_INCREMENTAL_HANDOFF_SUPPORTED`-Konfiguration entfernt Die Kontextreferenz `IS_INCREMENTAL_HANDOFF_SUPPORTED` wurde von Supervisoren entfernt, da inkrementelle Veröffentlichung seit Version 0.16.0 das Standardverhalten ist. Dieser Kontext wurde ursprünglich eingeführt, um das Rollback auf `LegacyKafkaIndexTaskRunner` in Versionen vor 0.16.0 zu unterstützen, der inzwischen entfernt wurde. #### `useMaxMemoryEstimates`-Konfiguration entfernt Die `useMaxMemoryEstimates`-Konfiguration wurde entfernt. Bei der Einstellung „false“ verwendet Druid eine viel genauere Speicherschätzung, die in Druid 0.23.0 eingeführt wurde. Diese genauere Methode ist derzeit die einzige verfügbare Methode. Die Konfiguration ist in mehreren Versionen standardmäßig auf „false“ eingestellt.
