agent-lightning v0.3.0

Agent-Lightning v0.3.0 ist eine Hauptversion, die mehrere neue Funktionen und Fehlerbehebungen einführt. Die Veröffentlichung ist eine Gemeinschaftsarbeit zwischen den Agent-Lightning-Kernteams und der Community. Vielen Dank an alle Mitwirkenden, die diese Veröffentlichung ermöglicht haben.

Highlights

  • Tinker-Integration: Unterstützen Sie Tinker als alternatives Backend für Reinforcement Learning (#226 #245 #264 #269 #327). Siehe Beispielcode, Blog 1 und Blog 2.
  • Azure OpenAI-Integration: Unterstützt Azure OpenAI als Backend für LLM-Inferenz und überwachte Feinabstimmung (#256 #327). Beispielcode.
  • MongoDB-basierter Lightning Store wird als alternatives Backend für Lightning Store hinzugefügt (#323). Dokumentation.
  • Contrib-Paket: Contrib-Paket für Community-Projekte hinzufügen. Search-R1 ist als Contrib-Rezept integriert. Weitere kommen. (#239 #396 #410 #412 #417).
  • RESTful API: Stabilisieren und dokumentieren Sie RESTful API für Lightning Store (#241 #275). Dokumentation.
  • Semantische Konventionen von OTel, die speziell für Bereiche der Agentenoptimierung entwickelt wurden (#340). Dokumentation.
  • [Vorschau] Agent-Lightning-Dashboard ist jetzt verfügbar (#288 #289 #291 #296 #371 #375). Es handelt sich um die offizielle Webanwendung zum Überprüfen und Debuggen von Agent-Lightning-Experimenten. Einzelheiten finden Sie hier.
  • [Vorschau] Multimodalitätsbeispiel mit VERL und einem LangGraph-Agenten im ChartQA-Datensatz (#379). Beispielcode.
  • [Vorschau] Integrieren Sie Claude Code als LitAgent und unterstützen Sie Schulungen zu SWE-Bench (#332 #346 #348). Beispielcode.
  • [Vorschau] Weave Tracer als Ersatz für AgentOps Tracer (#277 #411 #420 #423). Dokumentation.
  • [Vorschau] Trajectory Level Aggregation für effizienteres Training mit VERL. Siehe Blog und Dokumentation.

Store-Benchmark

In dieser Version wurde der Lightning Store-Kern für deutlich höhere Effizienz und Skalierbarkeit neu gestaltet (#315 #318 #328 #342 #344 #356 #380 #388 #418 #421). Die folgenden Benchmark-Ergebnisse veranschaulichen die Auswirkungen: Bei einer großen Anzahl gleichzeitiger Läufer liefert v0.3.0 eine bis zu 15-fache Steigerung des Durchsatzes im Vergleich zu v0.2.2.

| Durchsatz (#rollout/s) | v0.2.2 | v0.3.0 (im Speicher) | v0.3.0 (Mongo) | | :---- | :---- | :---- | :---- | | Minimal (Charge, #runner=32, #turns=6) | 8.73 | 9.06 | 8.71 | | Mittel (Charge, #Läufer=100, #Turns=10) | 12.03 | 23.26 | 32.79 | | Mittelhoch (Charge, #Läufer=300, #Turns=6) | 10.61 | 24.42 | 40.24 | | Groß (Charge, #runners=1000, #turns=3) | 3.36 | 14.60 | 50.05 | | Lange Warteschlange (Warteschlange, #runners=256, #turns=4) | 7.42 | 30.86 | 57.01 | | Schwerer Trace (Warteschlange, #runners=512, #turns=20) | 5.93 | 13.28 | 29.41 |

Anmerkungen:

  1. Benchmarks wurden auf einer einzelnen Standard_D32as_v4-Azure-VM ausgeführt (für große und umfangreiche Trace-Tests wurde Standard_D64ads_v5 verwendet) und über GitHub-Aktionen ausgeführt.
  2. Zwei Algorithmusmuster werden ausgewertet: Das Batch-Muster übermittelt eine Gruppe von Rollouts und wartet, bis alle abgeschlossen sind, bevor die nächste Gruppe gestartet wird, während das Warteschlangenmuster eine festgelegte Anzahl von Rollouts im laufenden Betrieb beibehält und neue einreicht, sobald Kapazität frei wird. Konfigurationsdetails finden Sie hier.
  3. Die Anzahl der Windungen ist direkt proportional zur Anzahl der Spannen, die jeder Rollout erzeugt.

Wartung und Fehlerbehebungen

Kern (Store, Schnittstellen usw.)

  • Trainer-Port-Option für client-Server-Strategien hinzufügen (#198)
  • Die Behandlung von Store-Port-Konflikten wurde behoben (#227)
  • Einheitlicher PythonServerLauncher (#286 #292 #303)
  • Gesundheits-Timeout konfigurierbar machen (#305)
  • Refactor-Protokollierung (#306)
  • Unterstützt OTLP im LightningStore (#313)
  • Zentralisierter Metrik-Helfer (#368)
  • Korrigieren Sie redundante Abbruch-Tracebacks bei Strg+C (#370)

Proxy, Adapter und Algorithmen

  • Korrigieren Sie Trainingsmetriken vor und nach der Verarbeitung in VERL (#145)
  • Streaming-Anfragen für Anthropic und OpenAI APIs weiterleiten (als Nicht-Streaming-Anfragen) (#299)
  • Spuren mit Belohnung für VERL prüfen (#317)
  • Patch LiteLLM Root Span (#341)
  • Behandeln Sie das ref_in_actor-Flag für LoRA-Kompatibilität (#386)
  • Unterstützt with_llm_proxy und with_store in Algorithmen (#398)
  • Unterstützt den Export von Bild-URLs in TracerTraceToTriplets (#400)
  • Korrigieren Sie match_rewards zugewiesene_to-Elemente in TraceTree (#403)
  • Unterstützung beim Anpassen von Trainer und Daemon in VERL (#407)

Läufer, Tracer und Agenten

  • Initialisierung des Refactor-Tracers (#321)
  • Korrigieren Sie die Kompatibilität von OpenAI Agents 0.6 (#322)
  • emit_operation, emit_annotation, Tags und Links (#359)
  • Sunset HTTP-Tracer (#402)

  • Beispiel „room_selector“ behoben, bei dem immer die erste Aufgabe ausgeführt wird (#270)
  • Tippfehler im SQL-Agent-Beispiel behoben (#285)
  • Fügen Sie die README- und Skriptdateien zum Trainieren des SQL-Agenten auf NPU hinzu (#272)
  • Beispielkatalog und Beitragsleitfaden zur Verfeinerung (Nr. 331)
