codebase-memory-mcp v0.12.1

v0.12.1

Jeder Installationspfad funktioniert wieder und Helm-Charts werden dem Diagramm hinzugefügt.

v0.12.1 behebt die Paketinstallationen von v0.12.0 und die anderen Installationspfade, die wir bei der Überprüfung jedes Kanals als fehlerhaft befunden haben. Außerdem verknüpft es Helm-Charts mit dem, was sie bereitstellen, und verhindert, dass der Graph eine Registry für Container-Images erstellt.

Upgrade durchgeführt? Der erste Index jedes vorhandenen Projekts nach dem Upgrade ist einmalig eine vollständige Neuerstellung (Bildidentitäten geändert; siehe unten).

Behoben: wird installiert

  • NPM-, PyPI- und Go-Installationen. npm i, pnpm add, pip install und der Go-Wrapper konnten v0.12.0 auf keiner Plattform installieren. Jeder Wrapper lehnte ein Archivmitglied mit mehr als 256 MiB ab und jede v0.12.0-Binärdatei ist 331–335 MB groß. Für alle drei Verpackungen gelten keine Größenbeschränkungen mehr. Das Archiv wird noch vor dem Entpacken anhand des checksums.txt der Version überprüft, sein Inhalt muss genau den erwarteten Dateien entsprechen und die Binärdatei muss mit --version antworten. Vielen Dank, @hydroplexus, für den genauen Bericht (#2657).
  • Homebrew. Die Formel war immer noch bei 0.10.3 und unter Linux wurde der dynamisch verknüpfte Build installiert, der glibc 2.38 benötigt (Ubuntu 22.04, Debian 12 und RHEL 9 haben ihn nicht). Es installiert nun die aktuelle Version und unter Linux den statischen -portable-Build, der auf jeder Distribution läuft.
  • go install. Ein angehefteter go install .../pkg/go/cmd/codebase-memory-mcp@vX.Y.Z hat nie funktioniert und @latest hat eine veraltete Version installiert. Releases tragen jetzt pkg/go/vX.Y.Z-Tags und der Wrapper installiert das Release entsprechend seiner eigenen Version.
  • npm next. Das Dist-Tag next verweist nicht mehr auf einen alten Release Candidate; eine stabile Veröffentlichung bewegt es.
  • Docs. Winget und Chocolatey wurden als Installationskanäle aufgeführt, aber nicht veröffentlicht; Sie werden entfernt, bis sie entfernt sind. Windows arm64-Builds werden ausgeliefert und sind jetzt aufgelistet.

Install-Path-Smoke-Tests. Bei jeder Pull-Anfrage und bei jedem Release werden nun die npm-, PyPI- und Go-Wrapper auf die Art und Weise installiert, wie es der Paketmanager eines Benutzers tut, gegen die echten Release-Archive und führt die Binärdatei jedes installierten Pakets aus. Eine Veröffentlichung wird erst nach Abschluss dieser Installationen veröffentlicht, sodass ein Installer, der das, was wir liefern, nicht installieren kann, Sie nicht mehr erreichen kann.

Helmdiagramme im Diagramm

Ein Helm-Chart war früher ein isolierter Knoten. Jetzt wird mit dem verknüpft, was es bereitstellt (#2663):

  • Diagramm → Objekte (DEPLOYS, via: chart): jedes Kubernetes-Objekt, das aus dem templates/ des Diagramms gerendert wird (die Objekte eines Unterdiagramms gehören zum Unterdiagramm).
  • Wertedatei → Diagramm (CONFIGURES): values.yaml und values-<x>.yaml neben Chart.yaml.
  • Diagramm → Bilder (DEPLOYS, ref: image): Jedes Bild benennt seine Objekte wörtlich (ein Vorlagenbild benennt keines).

HelmRelease → Chart → Deployment → Image ist jetzt ein überquerbarer Pfad. In 20 Infrastruktur-Repositories sank die Zahl der Diagramme ohne ausgehende Kante von 238 von 260 auf 109, und es erschienen 2.511 Diagramm-zu-Objekt-Links; jede andere Kante blieb identisch.

Bilder behalten in der Registrierung die Codenamen

Ein Image ohne Registry-Host wurde früher unter einem erfundenen docker.io/library/... (#2654) gespeichert. Der Docker-Hub ist nur der Standard von Docker: Podman und CRI-O lösen Kurznamen über eine Suchliste auf, Spiegel schreiben sie neu und ein lokales Build-Tag ist möglicherweise in überhaupt keiner Registrierung vorhanden. Ein Image behält jetzt seinen Namen wie geschrieben, mit registry: unknown, wenn kein Host angegeben ist; Ein angegebener Host wird beibehalten (die Schreibweise des Hubs Docker wird zu docker.io). FROM nginx und image: docker.io/library/nginx sind jetzt zwei Bildknoten. Dadurch ändern sich die Bildidentitäten, weshalb jedes Projekt nach dem Upgrade einmal neu erstellt wird.

Upgrade-Hinweise

– Der erste Index jedes vorhandenen Projekts nach dem Upgrade ist einmalig eine vollständige Neuerstellung. – Image-Knoten ohne angegebene Registrierung tragen jetzt registry: unknown und den Namen wie geschrieben, anstelle von docker.io/library/....
