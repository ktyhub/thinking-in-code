<div> <h2>Highlights</h2> <div class="paragraph"> <p>Diese Version bietet neue Funktionen für Benutzer und Administratoren von Keycloak. Die Highlights dieser Veröffentlichung sind:</p> </div> <div class="ulist"> <ul> <li> <p>Automatisieren Sie die Benutzerbereitstellung mit SCIM API (Vorschau)</p> </li> <li> <p>Vereinfachte Multi-Cluster-Hochverfügbarkeit ohne externe Caches (Vorschau)</p> </li> <li> <p>Verbesserte Reverse-Proxy-Anleitungen mit Blaupausen für HAProxy und Traefik</p> </li> <li> <p>Erweiterte Authentifizierung für SAML clients</p> </li> </ul> </div> <div class="paragraph"> <p>Lesen Sie weiter, um mehr über jede neue Funktion zu erfahren. Der <a href="https://datatracker.ietf.org/doc/html/draft-ietf-oauth-identity-assertion-authz-grant">Identity Assertion JWT Authorization Grant (ID-JAG)</a> löst dieses Problem, indem er einem Autorisierungsserver ermöglicht, einem anderen eine signierte Identitätsbestätigung vorzulegen, der dann ein Zugriffstoken ausstellt, ohne dass sich der Benutzer erneut anmelden muss.</p> </div> <div class="paragraph"> <p>Keycloak bietet teilweise experimentelle Unterstützung für den Identity Assertion JWT Authorization Grant. Es implementiert derzeit nur die Rolle des empfangenden Autorisierungsservers, akzeptiert ID-JAG-Assertionen am Token-Endpunkt und stellt im Gegenzug Zugriffstoken aus. Es ermöglicht Unternehmen, die Bereitstellung und Deprovisionierung von Benutzern mithilfe allgemein verfügbarer Tools zu automatisieren – beispielsweise durch die Integration in Identity-Governance-Plattformen, HR-Systeme oder andere Identitätsanbieter.</p> </div> <div class="paragraph"> <p>Keycloak verfügt über SCIM APIs zum Verwalten von Benutzern und Gruppen innerhalb eines Bereichs. Die Implementierung umfasst vollständige CRUD- und PATCH-Vorgänge, Filterung und Paginierung, Schemaerweiterungen einschließlich der Enterprise User-Erweiterung und Schemaerkennungsendpunkte.</p> </div> <div class="paragraph"> <p>In dieser Version wird der SCIM API zu einer Vorschaufunktion hochgestuft. Im Standardprofil ist es standardmäßig deaktiviert; Um es auszuprobieren, aktivieren Sie die Funktion <code>scim-api</code>.</p> </div> <div class="paragraph"> <p>Weitere Einzelheiten finden Sie in der Dokumentation zum <a href="https://www.keycloak.org/docs/26.7.0/server_admin/#_managing_scim">Verwalten von Benutzern und Gruppen über SCIM</a>.</p> </div> </div> <div class="sect3"> <h4 id="_real_time_security_signals_to_downstream_applications_experimental">Echtzeit-Sicherheitssignale an nachgelagerte Anwendungen (experimentell)</h4> <div class="paragraph"> <p>Wenn sich ein Benutzer abmeldet, Anmeldeinformationen ändert oder in Keycloak deaktiviert wird, erfahren nachgelagerte Anwendungen in der Regel erst bei der nächsten Token-Aktualisierung davon – und es entsteht ein Fenster, in dem veraltete Sitzungen aktiv bleiben. Das <a href="https://openid.net/specs/openid-sharedsignals-framework-1_0-final.html">OpenID Shared Signals Framework (SSF)</a> schließt diese Lücke, indem es Identitätsanbietern ermöglicht, Sicherheitsereignisse nahezu in Echtzeit an vertrauende Parteien weiterzuleiten.</p> </div> <div class="paragraph"> <p>Keycloak kann jetzt als SSF-Sender fungieren und signierte <a href="https://www.rfc-editor.org/info/rfc8417/">Security Event Tokens (SETs)</a> an registrierte Empfänger senden. Es unterstützt <a href="https://openid.net/specs/openid-caep-1_0-final.html">CAEP 1.0</a> und <a href="https://openid.net/specs/openid-risc-1_0-final.html">RISC 1.0</a>-Ereignisprofile mit den Übermittlungsmethoden Push (<a href="https://www.rfc-editor.org/info/rfc8935/">RFC 8935</a>) und Poll (<a href="https://www.rfc-editor.org/info/rfc8936/">RFC 8936</a>). Ereignisse werden in einem dauerhaften Postausgang gespeichert, sodass bei Neustarts kein Signal verloren geht, und ein Cluster-fähiger Hintergrund-Drainer verarbeitet Wiederholungsversuche und exponentielle Backoffs. Jeder Bereich kann sich individuell anmelden und Streams, Themen und Ereignistypen werden über die Admin-Konsole und REST API verwaltet.</p> </div> <div class="paragraph"> <p>Um SSF zu aktivieren, starten Sie Keycloak mit aktivierter Funktion <code>ssf</code>.</p> </div> <div class="paragraph"> <p>Weitere Informationen finden Sie im Leitfaden zum <a href="https://www.keycloak.org/securing-apps/ssf-support">Shared Signals Framework</a>.</p> </div> </div> <div class="sect3"> <h4 id="_standardized_authorization_decisions_with_authzen_experimental">Standardisierte Autorisierungsentscheidungen mit AuthZen (experimentell)</h4> <div class="paragraph"> <p>Anwendungen, die eine differenzierte Autorisierung benötigen, rufen typischerweise die proprietäre Autorisierung von Keycloak API auf und koppeln sie an sein internes Modell. Die <a href="https://openid.net/specs/authorization-api-1_0.html">OpenID AuthZEN-Autorisierung API 1.0</a> definiert ein herstellerneutrales Protokoll zwischen Policy Decision Points (PDPs) und Policy Enforcement Points (PEPs), das es Anwendungen ermöglicht, Autorisierungsentscheidungen über eine Standardschnittstelle anzufordern.</p> </div> <div class="paragraph"> <p>Keycloak implementiert jetzt die AuthZEN-Bewertung API als PDP. Anwendungen senden Bewertungsanfragen, die ein Thema, eine Ressource und eine Aktion beschreiben, und Keycloak gibt basierend auf den konfigurierten Autorisierungsrichtlinien eine Genehmigungs- oder Ablehnungsentscheidung zurück. Es sind sowohl Einzel- als auch Batch-Evaluierungsendpunkte verfügbar.</p> </div> <div class="paragraph"> <p>Um AuthZen zu aktivieren, starten Sie Keycloak mit aktivierter Funktion <code>authzen</code>.</p> </div> <div class="paragraph"> <p>Weitere Informationen finden Sie im <a href="https://www.keycloak.org/securing-apps/authzen-authorization">AuthZen-Autorisierungshandbuch</a>.</p> </div> </div> <div class="sect3"> <h4 id="_authorize_ai_tools_and_mcp_servers">Autorisieren Sie KI-Tools und MCP-Server</h4> <div class="paragraph"> <p>Das Model Context Protocol (MCP) wird zur Standardmethode für KI-Anwendungen, um eine Verbindung zu externen Tools und Datenquellen herzustellen. Diese Version fügt neben der vorhandenen Visual Studio Code-Integration eine Integrationsdokumentation für Claude Code als MCP client hinzu. Beide verwenden OAuth Client ID Metadata Document (CIMD) für die dynamische client-Registrierung mit PKCE-gesicherten öffentlichen client-Flows und Localhost-Rückrufen.</p> </div> <div class="paragraph"> <p>Einrichtungsanweisungen finden Sie im Leitfaden <a href="https://www.keycloak.org/securing-apps/mcp-authz-server">Integration mit Model Context Protocol (MCP)</a>.</p> </div> </div> <div class="sect3"> <h4 id="_delegate_access_across_services_with_token_exchange_delegation_experimental">Delegieren Sie den Zugriff über Dienste hinweg mit Token Exchange Delegation (experimentell)</h4> <div class="paragraph"> <p>In Architekturen mit mehreren Diensten muss ein Back-End-Dienst manchmal im Namen eines Benutzers bei einem anderen Dienst agieren – zum Beispiel, wenn ein Gateway Arbeit an einen nachgeschalteten API delegiert. Der Delegierungsbereich erfordert die Zustimmung des Benutzers und wird bei der Aktualisierung des Tokens automatisch neu bewertet, sodass widerrufene Identitätswechselrechte sofort wirksam werden.</p> </div> <div class="paragraph"> <p>Um die Token-Exchange-Delegation zu aktivieren, starten Sie Keycloak mit aktivierter Funktion <code>token-exchange-delegation</code>.</p> </div> </div> <div class="sect3"> <h4 id="_step_up_authentication_for_saml_clients">Step-up-Authentifizierung für SAML clients</h4> <div class="paragraph"> <p>Durch die Step-up-Authentifizierung können Anwendungen eine stärkere Authentifizierungsebene für vertrauliche Vorgänge erfordern. Diese Version führt dedizierte Administratorrollen und fein abgestufte Administratorberechtigungen für Organisationen ein, sodass Administratoren die Organisationsverwaltung delegieren können, ohne den Zugriff übermäßig bereitzustellen.</p> </div> <div class="paragraph"> <p>Neue Bereichsadministratorrollen bieten eine grobkörnige Delegation:</p> </div> <div class="ulist"> <ul> <li> <p><code>manage-organizations</code> – gewährt vollständigen Lese- und Schreibzugriff auf Organisationen, einschließlich des Erstellens, Aktualisierens und Löschens von Organisationen und ihren Mitgliedern.</p> </li> <li> <p><code>view-organizations</code> – gewährt schreibgeschützten Zugriff auf Organisationen und ihre Mitglieder (erfordert außerdem <code>view-users</code> oder fein abgestufte Administratorberechtigungen für die Benutzersichtbarkeit).</p> </li> <li> <p><code>query-organizations</code> – gewährt die Möglichkeit, Organisationen ohne vollständigen Ansichtszugriff zu suchen und aufzulisten, im Einklang mit dem Muster <code>query-users</code> / <code>query-clients</code> / <code>query-groups</code>.</p> </li> </ul> </div> <div class="paragraph"> <p>Die Rolle <code>manage-realm</code> gewährt aus Gründen der Abwärtskompatibilität weiterhin implizit vollständigen Organisationsverwaltungszugriff.</p> </div> <div class="paragraph"> <p>Für die Granularität pro Organisation sind Organisationen jetzt ein erstklassiger Ressourcentyp in feingranularen Administratorberechtigungen. Wenn differenzierte Administratorberechtigungen aktiviert sind, berücksichtigen Organisationsmitgliederabfragen auch Berechtigungen auf Benutzerebene und geben nur Mitglieder zurück, die der Administrator anzeigen darf.</p> </div> </div> <div class="sect3"> <h4 id="_automatic_role_inheritance_through_organization_groups">Automatische Rollenvererbung durch Organisationsgruppen</h4> <div class="paragraph"> <p>Das Zuweisen von Rollen zu einzelnen Organisationsmitgliedern lässt sich nicht gut skalieren, wenn eine Organisation Hunderte von Benutzern hat, die alle dieselben Berechtigungen benötigen. Organisationsgruppen unterstützen jetzt Realm- und client-Rollenzuweisungen, sodass Administratoren der Organisationsgruppe einmal eine Rolle zuweisen können und diese automatisch in <code>realm_access</code>- und <code>resource_access</code>-Token-Ansprüchen für alle Gruppenmitglieder angezeigt wird.</p> </div> <div class="paragraph"> <p>Darüber hinaus kann der Protokoll-Mapper <strong>Organisationsgruppenmitgliedschaft</strong> (OIDC und SAML) diese Rollen in den <code>Organisation</code>-Anspruch einbeziehen, organisiert nach Organisation, indem die Konfigurationsoption <strong>Gruppenrollenzuordnungen hinzufügen</strong> aktiviert wird.</p> </div> <div class="paragraph"> <p>Weitere Informationen finden Sie im Leitfaden <a href="https://www.keycloak.org/docs/26.7.0/server_admin/#_managing_groups_">Organisationsgruppen verwalten</a>.</p> </div> </div> <div class="sect3"> <h4 id="_better_passkey_compatibility_with_new_webauthn_policy_options">Bessere Passkey-Kompatibilität mit neuen WebAuthn-Richtlinienoptionen</h4> <div class="paragraph"> <p>Passkeys ermöglichen es Benutzern, sich mit biometrischen Daten oder einem Sicherheitsschlüssel anstelle eines Passworts anzumelden. Um ordnungsgemäß zu funktionieren, muss der Server dem Browser mitteilen, ob er erkennbare Anmeldeinformationen (einen auf dem Gerät gespeicherten Passkey) bevorzugt oder nicht – und die vorherige Ja/Nein-Option konnte den immer häufiger vorkommenden <code>bevorzugten</code>-Wert nicht ausdrücken.</p> </div> <div class="paragraph"> <p>Die WebAuthn-Richtlinie und die passwortlose WebAuthn-Richtlinie bieten jetzt eine Option für <code>Erkennbare Anmeldeinformationen</code>, die der aktuellen <a href="https://www.w3.org/TR/webauthn/#dom-authenticatorselectioncriteria-residentkey">WebAuthn-Spezifikation</a> folgt und die Werte <code>erforderlich</code>, <code>bevorzugt</code> und <code>nicht empfohlen</code> unterstützt. Dies verbessert die Kompatibilität mit Passkey-Anbietern wie iCloud Keychain, Google Password Manager und 1Password. Die vorherige Option <code>Auffindbare Anmeldeinformationen erforderlich</code> ist jetzt veraltet und soll in einer zukünftigen Version entfernt werden.</p> </div> </div> <div class="sect3"> <h4 id="_easier_realm_discovery_by_display_name_search">Einfachere Realm-Erkennung durch Suche nach Anzeigenamen</h4> <div class="paragraph"> <p>Administratoren geben Bereichen oft kurze technische Namen (wie <code>acme-prod</code>), legen aber einen für Menschen lesbaren Anzeigenamen fest (wie <code>Acme Corporation</code>). Bisher stimmte die Suche in der Admin-Konsole nur mit dem Namen des technischen Bereichs überein, wodurch es schwieriger wurde, Bereiche in großen mandantenfähigen Bereitstellungen zu finden.</p> </div> <div class="paragraph"> <p>Die Bereichssuche vergleicht jetzt zusätzlich zum Bereichsnamen auch mit dem Anzeigenamen, sodass Administratoren Bereiche anhand des Namens finden können, an den sie sich erinnern.</p> </div> </div> <div class="sect3"> <h4 id="_type_safe_validation_for_parameterized_scopes_experimental">Typsichere Validierung für parametrisierte Bereiche (experimentell)</h4> <div class="paragraph"> <p>Parametrierte Bereiche ermöglichen es OAuth clients, kontextspezifischen Zugriff anzufordern – zum Beispiel <code>project:12345</code>, um Zugriff auf ein bestimmtes Projekt anzufordern, oder <code>account: Savings</code>, um einen Token einem bestimmten Bankkonto zuzuordnen. Bisher wurde der Parameterwert nur durch einen optionalen regulären Ausdruck validiert, was die Übergabe ungültiger oder unerwarteter Werte erleichtert.</p> </div> <div class="paragraph"> <p>Parametrisierte Bereiche können jetzt einen Parametertyp definieren, der den erfassten Wert zum Zeitpunkt der Anforderung validiert. Zu den integrierten Typen gehören <code>string</code>, <code>integer</code>, <code>boolean</code>, <code>username</code> und <code>custom</code> (validiert anhand eines vom Administrator definierten regulären Ausdrucks). Der Typ ist erforderlich, wenn parametrisierte Bereiche mit aktivierter Funktion erstellt werden, um sicherzustellen, dass Token immer wohlgeformte Bereichsparameter enthalten.</p> </div> <div class="paragraph"> <p>Weitere Einzelheiten finden Sie im <a href="https://www.keycloak.org/docs/26.7.0/upgrading/">Upgrade-Leitfaden</a>.</p> </div> </div> <div class="sect3"> <h4 id="_additional_datasources_may_be_excluded_from_health_checks">Zusätzliche Datenquellen können von Gesundheitsprüfungen ausgeschlossen werden</h4> <div class="paragraph"> <p>Bei Verwendung mehrerer Datenquellen kann ein Ausfall einer nicht kritischen Datenquelle dazu führen, dass der Endpunkt für die Integritätsprüfung die gesamte Bereitstellung als fehlerhaft meldet. Einzelne Datenquellen können jetzt von Integritätsprüfungen ausgeschlossen werden, sodass optionale oder sekundäre Datenquellen keine unnötigen Warnungen auslösen oder das Load-Balancer-Routing beeinträchtigen.</p> </div> <div class="paragraph"> <p>Weitere Informationen dazu finden Sie im Leitfaden <a href="https://www.keycloak.org/server/db#multiple-datasources">Konfigurieren mehrerer Datenquellen</a>.</p> </div> </div> </div> <div class="sect2"> <h3 id="_configuring_and_running">Konfigurieren und Ausführen</h3> <div class="sect3"> <h4 id="_enhanced_reverse_proxy_guides_with_blueprints_for_haproxy_and_traefik">Erweiterte Reverse-Proxy-Anleitungen mit Blaupausen für HAProxy und Traefik</h4> <div class="paragraph"> <p>Für die Ausführung von Keycloak in der Produktion ist ein Reverse-Proxy erforderlich, aber die korrekte Konfiguration der TLS-Beendigung, der Zertifikatsweiterleitung und der Administrator-API-Sicherheit über verschiedene Proxys hinweg ist fehleranfällig.</p> </div> <div class="paragraph"> <p>Die Reverse-Proxy-Dokumentation wurde erheblich erweitert und enthält spezielle Schritt-für-Schritt-Anleitungen für HAProxy und Traefik, die sowohl den TLS-Passthrough- als auch den Re-Encrypt-Modus abdecken und die Konzepte erläutern, damit sie auch auf andere Proxys angewendet werden können.</p> </div> <div class="paragraph"> <p>Weitere Informationen finden Sie in der Anleitung <a href="https://www.keycloak.org/server/reverseproxy">Verwenden eines Reverse-Proxys</a>.</p> </div> </div> <div class="sect3"> <h4 id="_simplified_multi_cluster_high_availability_without_external_caches_experimental">Vereinfachte Multi-Cluster-Hochverfügbarkeit ohne externe Caches (Vorschau)</h4> <div class="paragraph"> <p>Das bestehende Multi-Cluster-Setup für Keycloak erfordert die Bereitstellung und Verwaltung eines externen Infinispan-Clusters für die standortübergreifende Sitzungsreplikation sowie einer herstellerspezifischen Fencing-Infrastruktur für automatisiertes Failover. Dies erhöht die betriebliche Komplexität erheblich und schränkt die Bereitstellung auf bestimmte Umgebungen ein.</p> </div> <div class="paragraph"> <p>Multi-Cluster v2 beseitigt die externe Infinispan-Anforderung vollständig. Keycloak-Instanzen stellen über eingebettete Infinispan-Caches eine direkte Verbindung zueinander her und verlassen sich auf die synchron replizierte Datenbank als einzige Quelle der Wahrheit. Die Cache-Ungültigmachung auf allen Websites wird über ein datenbankgestütztes Postausgangsmuster gehandhabt. Der Load Balancer kann die Ausfallzeit einer Site erkennen, ohne dass eine externe Zauninfrastruktur erforderlich ist.</p> </div> <div class="paragraph"> <p>Um dieses Setup zu aktivieren, starten Sie Keycloak mit der Funktion <code>stateless</code>. Einzelheiten zur Architektur und einen Bereitstellungsentwurf finden Sie im <a href="https://www.keycloak.org/high-availability/multi-cluster-v2/introduction">Leitfaden für Multi-Cluster-Bereitstellungen (v2)</a>.</p> </div> </div> <div class="sect3"> <h4 id="_keycloak_operator_kustomize_installation">Keycloak Operator kustomize-Installation</h4> <div class="paragraph"> <p>Die Installation des Keycloak-Operators auf Vanilla-Kubernetes-Clustern erforderte bisher das Herunterladen und Anwenden einzelner Manifestdateien, was die Verwaltung von Upgrades und Anpassungen erschwerte. Der Operator kann jetzt mit kustomize installiert werden und bietet so eine deklarative und reproduzierbare Installationsmethode.</p> </div> <div class="paragraph"> <p>Installationsanweisungen finden Sie im <a href="https://www.keycloak.org/guides#operator">Bedienungsanleitung</a>.</p> </div> </div> <div class="sect3"> <h4 id="_cluster_wide_install_mode_for_the_keycloak_operator_preview">Clusterweiter Installationsmodus für den Keycloak Operator (Vorschau)</h4> <div class="paragraph"> <p>Organisationen, die mehrere Keycloak-Instanzen in verschiedenen Kubernetes-Namespaces ausführen, mussten bisher in jedem Namespace einen separaten Operator installieren. Der Keycloak-Operator stellt nun <code>AllNamespaces</code> als unterstützten OLM-Installationsmodus zur Verfügung, sodass eine einzelne Operator-Instanz benutzerdefinierte <code>Keycloak</code>-Ressourcen über alle Namespaces im Cluster hinweg abgleichen kann. Für Nicht-OLM-Installationen ist die Cluster-weite Bereitstellung über das <code>clusterweite</code> Kustomisierungs-Overlay</p> verfügbar </div> <div class="paragraph"> <p>Die Cluster-weite Installation befindet sich in der Vorschau. Installationsanweisungen und Einschränkungen finden Sie im <a href="https://www.keycloak.org/guides#operator">Bedienungsanleitung</a>.</p> </div> </div> </div> <h2>Aktualisierung</h2> <p>Vor dem
