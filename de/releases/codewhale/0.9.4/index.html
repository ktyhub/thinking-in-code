Codewal v0.9.4

Codewhale ist das öffentliche Produkt von Shannon Labs. Der codewhale Befehls-, NPM-Paket- und Release-Asset-Namen bleiben technisch in Kleinbuchstaben geschrieben Identifikatoren. Das alte NPM-Paket deepseek-tui ist veraltet und erhält keine weiteren Veröffentlichungen. Benutzer aus v0.8.x Legacy deepseek / deepseek-tui-Namen sollten mit docs/REBRAND.md migriert werden.

Installieren

Empfohlen – npm (ein Befehl, alle drei Einstiegspunkte)

npm install -g codewhale

Der Wrapper lädt die passenden Dateien codewhale, codew und codewhale-tui herunter Binärdateien aus dieser Version und legt sie im selben Verzeichnis ab.

Docker / GHCR

docker run --rm -it \
  -e DEEPSEEK_API_KEY="$DEEPSEEK_API_KEY" \
  -v codewhale-home:/home/codewhale/.codewhale \
  ghcr.io/hmbown/codewhale:v0.9.4

Das Image enthält den codewhale-Dispatcher, das codew-Shim und die codewhale-tui-Laufzeit. Das latest-Tag wird bei der Veröffentlichung ebenfalls aktualisiert.

Fracht (Linux / macOS)

cargo install codewhale-cli codewhale-tui --locked

Beide Kisten sind erforderlich – codewhale-cli produziert den codewhale-Dispatcher und das codew-Shim, während codewhale-tui die interaktive Laufzeit produziert, an die der Dispatcher delegiert. Die Installation nur einer Kiste schlägt zur Laufzeit mit dem Fehler MISSING_COMPANION_BINARY fehl.

Behoben

– Das Speicherjournal wird nicht mehr als Speicher indiziert. Es handelt sich um Markdown im Speicherbaum, also sammelte der Quellenspaziergang ihn und jede zurückgezogene Notiz hat den durchsuchbaren Satz unter seiner Zeile before: erneut eingegeben – indem er die eingegeben hat Genaue Fakten, die durch eine Überarbeitung gerade wieder in die Eingabeaufforderung entfernt wurden.

  • memory_path wies auf einen bereits nativen Store hin und leitet keinen mehr ab Darin war ein zweiter Laden verschachtelt, der stillschweigend irgendwo anders schrieb als die vom Benutzer benannte Datei.
  • muse und muse-spark wurden im Agenten zu muse-spark-1.1 aufgelöst Registry, während die Konfiguration standardmäßig auf muse-spark-1.2 eingestellt war, also CLI und Der App-Server hat diese Aliase nie an einen konfigurierten Standard weitergeleitet spitz. Die Registrierung trägt jetzt 1.2 und die Contributor-Variante.
  • Ein explizites type=builder (oder sein implementer-Alias) plus write_authority=read_only schlägt jetzt beim Spawnen fehl, anstatt einen zu starten beschriftete Schreibrolle, die stillschweigend nur Aufklärungswerkzeuge hatte und sich dann selbst BLOCKIERTE nach dem Brennen einer Runde (#5123). Der Scheck ist bewusst schmal gehalten, denn zwei Benachbarte Kombinationen sind legitim und bleiben legal:
    • type=worker + read_only – Worker ist der unbenannte Standard (er wird als gerendert). general) und bezieht seine Fähigkeit von der Autorität, nicht von seinem Namen, also a Der schreibgeschützte Arbeiter ist ein gewöhnliches Allzweck-Kind. Arbeiter, Pfadfinder, Prüfer und Verifizierer bleiben die vier kanonischen schreibgeschützten Flottenrollen.
    • beliebig role + read_only – role ist eine Identität für die Dienstplanauflösung, nicht ein Fähigkeitsanspruch, sodass ein Akzeptanz-Workflow dennoch gelöst werden kann implementer zu seinem gespeicherten Profil hinzufügt, während dieses Kind zur Verifizierung freigegeben wird. Anrufer, die eine schreibgeschützte Eingrenzung buchstabiert haben, wie type: "implementer" sollte Verschieben Sie es nach role: "implementer". – Globale Benutzeranmeldeinformationen bleiben auch in einem expliziten Arbeitsbereich bestehen CODEWHALE_CONFIG_PATH Dadurch wird eine Route ohne lokalen Schlüssel ausgewählt – die Bereitschaft prüft den Benutzer auf globaler Ebene Anbietertabelle vor Abschluss fehlt ein Schlüssel.
