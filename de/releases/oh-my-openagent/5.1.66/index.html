oh-mein-openagent v5.1.66

omo thread sagt, wenn eine fehlerhafte Installation nur auf diesem Gerät verbleibt. Ein Thread client Sidecar, der nicht geladen werden kann, lässt omo thread read <alias> nicht mehr stillschweigend antworten not_found: stderr benennt den Sidecar, den Fehler und den Neuinstallationsschritt. Die eigenen Warnungen der CLI-Anmeldung (ein zurückgezogener trust-Pin, ein fehlgeschlagener Gerätedienst-Vergessen) erreichen jetzt auch stderr. (#12936)

Eine Nachricht an einen ausgelasteten Thread erreicht jetzt standardmäßig die Runde, in der sie gerade ausgeführt wird. thread_send und thread_handoff ohne Zustellungsmodus (und omo thread send ohne --mode) steuern die laufende Runde des Empfängers und starten eine Runde, wenn dieser inaktiv ist, sowohl auf diesem Gerät als auch auf einem anderen Gerät; Eine Nachricht wird nur dann hinter der laufenden Abzweigung in die Warteschlange gestellt, wenn der Anrufer nach follow_up fragt oder wenn die Abzweigung keine Steuerung durchführen kann (eine Wartefrage, eine Verdichtung, eine Engine, die keine Abbiegeepoche meldet). Ein Send, der eine Runde steuert, die genau in diesem Moment endet, fällt auf die Spur zurück, die das Ziel dann hat, anstatt zu scheitern. (#12921, Teil von #12879)

OmO läuft auf senpi 2026.11.9-2. Ein Werkzeug, auf das eine Eval-Zelle wartet, lässt die laufende Zelle nach Abschluss nicht mehr für einen Moment leer: Die gestreamten Zeilen bleiben bestehen, bis die eigene Ausgabe der Zelle oder ihr Ergebnis sie ersetzt (senpi#6257). (#12920)

omo remote send durchläuft jetzt denselben Weg wie der thread_send einer Sitzung zu einem anderen Gerät, und jede Antwort von einem anderen Gerät wird durch eine Zuordnung erklärt. Die Person an einem Terminal, die an eine Sitzung auf einem anderen Gerät sendet, durchläuft den Relay-Transport (derselbe Offline-Check, derselbe Steuer-Preflight gegen den laufenden Turn, eine Quittung im Gateway-Speicher dieses Geräts), während sie ihre eigene Eingabeaufforderungsaufzeichnung führt; Was der Benutzer liest, wenn ein Befehl auf einem anderen Gerät abgelehnt wird (omo remote, die Attach-TUI, die Thread-Tools und SDK), stammt von einem einzigen Modul, sodass ein Gerät, das nicht geantwortet hat, eine fehlende Berechtigung oder ein unsicheres Ergebnis hat, überall das Gleiche liest. (#12911, Teil von #12879, behebt #12885)

OmO läuft auf Senpi 2026.11.9. Es bringt Senpis admit_external_message (eine von der Sitzung eines anderen Geräts weitergeleitete Nachricht wird als normale Zustellung zugelassen) und sorgt dafür, dass eine weitergeleitete Zustellung genau wie eine auf derselben Maschine gelesen wird, wobei das Gerät nur in seinen Metadaten erhalten bleibt. Der einkanalige Relay-Transport (#12879) benötigt beides. (#12904)

Die Schaltfläche „Installieren“ im Header von omo.dev drückt nicht mehr gegen den rechten Rand des Pills oder rutscht darüber hinaus. Die schwebende Navigationsleiste verleiht ihrem letzten Steuerelement den gleichen Einschub wie das Logo auf der linken Seite, und unter 1000 Pixel werden die Abschnittslinks in das Menü verschoben, sodass in keiner Sprache etwas aus dem Pill herausgeschoben wird. (#12893)

Ein Thread, den ein Agent mit thread_create erstellt oder forkt, startet jetzt auch auf diesem Gerät im eigenen Genehmigungsmodus des Erstellers, nicht im Standardmodus des Hosts. Eine auf einem anderen Gerät erstellte Sitzung wurde bereits erstellt (#6189); Die beiden Zweige führen jetzt einen einzigen Körper aus: Ein Name wird mit dem Gerät verglichen, auf dem der Thread landet (ein Name, den das Gerät dort bereits live auflistet, ist dort name_conflict). Beim Öffnen eines Threads, der auf einem anderen Gerät live ist, wird dieser Thread beantwortet, ohne ihn erneut zu öffnen, und die Fakten des erstellten Threads (Name, Arbeitsverzeichnis, Zeitstempel) stammen aus der Antwort der Engine auf beiden Geräten. (#12891, Teil von #12879) Das Anhalten, Schließen, Umbenennen, Neumodellieren, Ändern der Argumentationsebene oder das Lesen eines Threads funktioniert auf die gleiche Weise, unabhängig davon, ob dieser Thread auf diesem Computer oder auf einem anderen Gerät Ihres Kontos ausgeführt wird. thread_set_reasoning erreicht jetzt auch einen Thread auf einem anderen Gerät und eine Sitzung ohne Datei, in der ein anderer client immer noch die gleichen Antworten auf beiden bereithält. (#12890, Teil von #12879)

Eine Nachricht, die ein Agent an eine Sitzung auf einem anderen Gerät sendet, kommt dort nun genau als Nachricht zwischen Sitzungen auf einem Gerät an. Die empfangende Sitzung erhält einen Zustellungseintrag (niemals eine Benutzernachricht) mit derselben Absenderzeile und Autoritätsbenachrichtigung, die eine Zustellung auf demselben Gerät enthält, dedupliziert unter demselben Schlüssel, und sie wird beim Empfang auf die gleiche Weise aktiviert; Eine Antwort ist nur eine weitere Rücksendung. Im übermittelten Text wird das überquerte Gerät nicht genannt, und omo remote send von einem Terminal bleibt unverändert. Ein Versand von omo thread send an eine Sitzung auf einem anderen Gerät wird als Daten abgelehnt (die Engine lässt eine Befehlszeilenübermittlung nur von ihrem eigenen Computer aus zu) und zeigt auf omo remote send. (#12889, Teil von #12879, behebt #12882, behebt #12877, behebt #12346, behebt #12865, behebt #12857)

Das Senden einer Nachricht an eine andere Sitzung durchläuft jetzt eine Übermittlungspipeline, unabhängig davon, ob sich diese Sitzung auf diesem Computer oder auf einem anderen Gerät befindet. Der Geräteunterschied besteht in einem Transportmodul hinter einem Port; Ein Benutzer sieht in dieser Version keine Änderungen. (#12887, Teil von #12879)

Eine Nachricht an eine Sitzung auf einem anderen Gerät liest sich jetzt genauso wie eine Nachricht aus einer Sitzung auf demselben Computer. Der empfangende Agent sieht, von welcher Sitzung sie gesendet wurde, nicht von welchem Gerät, und antwortet wie gewohnt über diese Sitzung. (#12878)

**Ein Subagent, dessen Modell mehr als 90 s benötigt, um mit der Antwort zu beginnen, wird nicht mehr durch einen Laufzeit-Fallback abgebrochen. ** Bei aktiviertem runtime_fallback schnitt der First-Prompt-Watchdog jeden Subagenten ab, der innerhalb einer festgelegten 90 s keinen Fortschritt zeigte, und forderte das Fallback-Modell erneut auf, also begründungsintensive Modelle, die legitimerweise länger nachdenken, bevor ihr erstes Token getötet wurde und ihr Prompt zweimal gesendet wurde. Der Watchdog wartet nun 300 s, die gleiche Stream-Start-Grenze wie die Engines, und runtime_fallback.first_prompt_timeout_seconds legt sie fest (0 deaktiviert sie). (#11893, behebt #11887)

Behoben

– omo thread send zu einem Thread-Alias, der auf diesem Gerät gespeichert ist, erreicht nun diesen Thread, wenn er von einem anderen Arbeitsbereich aus ausgeführt wird, genau wie omo thread read, anstatt zu antworten, dass kein sichtbarer Thread übereinstimmt. (#12860)

  • Speicherverlust beim Herunterfahren: Die Verkabelung zum Herunterfahren der Sitzung behauptet nicht mehr, dass Senpi seinem Handler keine Grenzen setzt. senpi begrenzt einen session_shutdown-Handler mit seinem eigenen Warnschwellenwert, seinem eigenen Zeitlimit pro Handler und seinem gesamten Beendigungsbudget (ausgelieferte Standardwerte sind 2 s / 10 s / 2 s, jeweils vom Benutzer einstellbar und 0-deaktivierbar), und das Drain-Budget von 1500 ms ist unter diesen Standardwerten bemessen und durch einen Test fixiert, der sie vom installierten Senpi liest, sodass eine Host-Version, die einen Standardwert unter den Drain senkt, dort fehlschlägt. Von OmO wurde keine Host-Obergrenze hinzugefügt und nichts umgeht den Host-Abbruch; Eine vom Budget übersprungene Buchungsbereinigung löst immer noch den Fehleralarm aus. (#12795, Refs #10336) – In den Dokumenten und Beispielen des Browser-Skills wird die gemeinsame Kontrolle von BrowserSkill 0.4 für das Omowright vermittelt, das derzeit ausgeliefert wird (^0.3.0): Jede geschlossene Seitenaktion trägt den Kontext eines neuen session.cooperate("sync"), und eine cooperation_sync_required-Ablehnung wartet auf die Person mit session.cooperate("wait"), wird dann erneut synchronisiert und neu geplant. Sie stellen außerdem fest, welche Anrufe gegatet sind, dass eine Gated-Aktion ein TypeError auf eine unbekannte Optionstaste auslöst (mit den beiden Anrufen, die stattdessen Streutasten weiterleiten) und dass page.on("dialog")-Hörer ein Dialog erhalten, das sie beantworten können. Das in dieser Version enthaltene Omowright umfasst die Erkennung laufender Browser über DevToolsActivePort, goto auf Sparse- und Frameset-Seiten, UTF-8-Dekodierung über BrowserSkill-IPC-Chunks und die Wiederherstellung nur eindeutiger veralteter Referenzen (danke @ashmoonori-afk, code-yeongyu/omowright#115 bis #118) und Agent-Registerkarten in einem eigenen Fenster (danke @devxoul, code-yeongyu/omowright#120). (#12494)
  • Der Senpi-Task-Kalt-Wiederbelebungs-Aufenthaltstest ist jetzt durch die eigenen Lebendigkeitsregeln des Produkts begrenzt, statt durch eine pauschale Gesamtdauer von 20 Sekunden (Teil von #10993). Ein Windows-Kind, das während des Startvorgangs für eine Weile blockiert, scheitert nicht mehr, es sei denn, das Produkt würde ebenfalls aufgeben, und ein echter Stillstand schlägt mit der letzten erreichten Stufe und der Stillstandslänge fehl. Das untergeordnete Element des Tests meldet auch die Zeitpunkte der Startphase von Senpi, sodass der nächste Block seine Phase benennt. (#11706)
