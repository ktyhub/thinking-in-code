airflow 3.3.0

Luftstrom 3.3.0

📦 PyPI: https://pypi.org/project/apache-airflow/3.3.0/ 📚 Dokumente: https://airflow.apache.org/docs/apache-airflow/3.3.0/ 🛠 Release Notes: https://airflow.apache.org/docs/apache-airflow/3.3.0/release_notes.html 🐳 Docker Bild: „docker pull apache/airflow:3.3.0“ 🚏 Einschränkungen: https://github.com/apache/airflow/tree/constraints-3.3.0

Wesentliche Änderungen

Asset-Partitionierung (#64571, #65447, #66030, #66848, #67184, #67475, #67716, #68978)

Aufbauend auf der in 3.2.0 eingeführten Asset-Partitionierung erweitert Airflow 3.3.0 die Art und Weise, wie a Ein einzelnes Upstream-Asset-Ereignis verteilt sich auf partitionierte Downstream-Dag-Läufe. Neue Partitions-Mapper – RollupMapper (many-to-one), FanOutMapper (one-to-many), and FixedKeyMapper + „SegmentWindow“ (kategoriales Rollup) – mit Zeitfenstern (Tag/Woche/Monat/Quartal/Jahr) zusammenstellen und a wait_policy (WaitForAll or MinimumCount(n)), um zu steuern, wann Partitionsläufe ausgelöst werden. Windows kann zeitlich vorwärts oder rückwärts aufgefächert werden, und die gesamte Auffächerung pro Upstream-Ereignis ist durch das Neue begrenzt „[scheduler] partition_mapper_max_downstream_keys“-Konfiguration (konfigurierbar pro Mapper). Luftstrom 3.3.0 fügt auch den Zeitplan „PartitionedAtRuntime“ hinzu, der es einem Dag ermöglicht, zu erklären, dass seine(n) Partitionsschlüssel(s) werden zu Beginn des Laufs zugewiesen und nicht von einem Upstream-Ereignis zugeordnet.

Detaillierte Nutzungsanweisungen finden Sie unter :doc:/authoring-and-scheduling/assets.

Aufgaben- und Asset-Statusspeicher (#65759, #66073, #66160, #66463, #66586, #66859, #67041, #67292, #67319)

Airflow 3.3.0 führt einen erstklassigen Zustandsspeicher für Aufgaben und Vermögenswerte ein (AIP-103). Aufgaben können bestehen bleiben beliebiger Schlüsselwertstatus, der über Wiederholungsversuche hinweg überlebt und über einen neuen „task_state_store“-Accessor ausgeführt wird, und Assets können ihren eigenen Status über „asset_state_store“ übertragen – beide sind über die Task SDK verfügbar. Zustand bleibt erhalten standardmäßig in der Metadatendatenbank oder in einem benutzerdefinierten Worker-seitigen Backend („[workers] state_store_backend``), unterstützt die Aufbewahrung pro Schlüssel mit regelmäßiger Speicherbereinigung und einer optionalen „clear_on_success“ und ist vollständig über den Core API und die Ausführung API verwaltbar.

Detaillierte Nutzungsanweisungen finden Sie unter :doc:/core-concepts/task-and-asset-state-store.

Pluggable Retry Policies (#65474)

Das Verhalten bei Aufgabenwiederholungen ist jetzt anpassbar (AIP-105). Zusätzlich zu einer festen „retries“-Anzahl ist dies möglich Fügen Sie eine benutzerdefinierte Wiederholungsrichtlinie hinzu, die entscheidet, ob und wann eine Aufgabe wiederholt wird, und ermöglicht so Strategien wie z B. einen erneuten Versuch nur bei bestimmten Ausnahmen oder einen Rückzug basierend auf benutzerdefinierter Logik.

Ausführliche Gebrauchsanweisungen finden Sie unter :ref:concepts:retry-policies.

Sprachaufgabe SDK (Java und Go) (#65958, #67161, #67635, #67699)

Airflow 3.3.0 fügt eine Koordinatorschicht (AIP-108) hinzu, die das Schreiben einzelner Aufgabenimplementierungen ermöglicht in Nicht-Python-Sprachen, während der Dag und seine Planung in Python bleiben. Eine Aufgabe wird im Dag deklariert mit „@task.stub(queue=...)“; Der Worker leitet es an einen konfigurierten Koordinator weiter („JavaCoordinator`` for JVM languages, ``ExecutableCoordinator“ für eigenständige native Binärdateien (z. B. Go), das die Aufgabe in einer Sprachlaufzeit ausführt und Variablen, Verbindungen und XComs zurückvermittelt durch die Ausführung API.

.. Warnung::

Die Koordinatorschicht und die Java/Go-SDKs sind in 3.3.0 experimentell und können sich in Zukunft ändern Versionen basierend auf Benutzer-Feedback.

Detaillierte Nutzungsanweisungen finden Sie unter :doc:/authoring-and-scheduling/language-sdks/index.

Dag-Bundle-Version zum Löschen, erneuten Ausführen und Auffüllen (#63884)

Die neue Einstellung „rerun_with_latest_version“ steuert, ob ein Dag-Lauf gelöscht, erneut ausgeführt oder aufgefüllt wird Verwendet die neueste Bundle-Version oder die Originalversion aus der ersten Ausführung. Der Standardwert wurde behoben nach Vorrang: ein expliziter Anforderungsparameter/CLI-Flag, dann die Dag-Ebene „rerun_with_latest_version“, dann [core] rerun_with_latest_version, and finally False for clear/rerun and True für Hinterfüllungen (Erhaltung des historischen Verhaltens). Airflow 2.x wurde immer mit dem neuesten Code erneut ausgeführt. 3.x Einführung der Bundle-Versionierung, die standardmäßig auf die Originalversion zurückgreift, und diese Einstellung gibt Benutzern die Kontrolle.

Ausführliche Informationen finden Sie unter :doc:/administration-and-deployment/dag-bundles.

Beispiel-Dags des Anbieters als dedizierte Bundles (#66161)

Beispieldags, die von Anbieterdistributionen geliefert werden, werden jetzt über „ProvidersManager“ und erkannt als eigene Dag-Bundles registriert – eines pro Anbieter, benannt „apache-airflow-providers-<distribution>-example-dags`` (or ``<distribution>-example-dags“ für Drittanbieter). Die Option „[core] load_examples“ bestimmt weiterhin, ob sie registriert sind. REST API clients, die „bundle_name`` by ``"dags-folder"“ nach vom Anbieter bereitgestellten Beispieldags gefiltert haben muss auf die neuen Paketnamen pro Anbieter aktualisiert werden; Dag-Kennungen bleiben unverändert.

Auflösung der Remote-Protokollierung von „airflow.logging_config“ entkoppelt (#67056)

Die Auflösung des Remote-Task-Log-Handlers gehört jetzt dem gemeinsam genutzten „airflow_shared.logging.factory“. Modul und wendet eine einzelne, klar definierte Priorität an:

  1. ein benutzerdefiniertes „[logging] logging_config_class`` exporting ``REMOTE_TASK_LOG“ / „DEFAULT_REMOTE_CONN_ID“ (vorhandene benutzerdefinierte Konfigurationen funktionieren weiterhin);
  2. „ProvidersManager`` scheme dispatch — the scheme of ``[logging] remote_base_log_folder“ wählt a Anbieter „RemoteLogIO`` class, instantiated via a no-argument ``from_config()“ Klassenmethode;
  3. ein vorübergehender Legacy-Fallback mit der Lesung „airflow_local_settings.py“ (muss in Airflow 4.0 entfernt werden).

„airflow.logging_config.load_logging_config`` is deprecated (it now emits ``DeprecationWarning“ und Delegierte an neue private Helfer) und „configure_logging“ löst die Fernbedienung nicht mehr eifrig auf Handler – Die Auflösung ist bei der ersten Verwendung träge. Anbieter, die einen „remote-logging:“-Block registriert haben, dies aber tun „from_config“ nicht implementieren, werden mit einer Warnung übersprungen und fallen auf den Legacy-Pfad.

Migration: Ersetzen Sie direkte Aufrufe von „airflow.logging_config.load_logging_config()“ durch die neuen Helfer und lassen Sie die Remote-Log-Handler-Klassen des Anbieters ein „from_config“ ohne Argumente implementieren Klassenmethode, die „airflow.providers.common.compat.sdk.conf“ lautet.

OpenTelemetry Timer-Metriken verwenden jetzt Histogramm (#64207)

OpenTelemetry-Timer und Timing-Metriken werden jetzt als Histogramme statt als Messgeräte aufgezeichnet, wodurch die Daten erhalten bleiben Anzahl, Summe und Bucket-Verteilung über die Aufzeichnungen hinweg.

Dag-Verarbeitungsmetrik „vor Sekunden“ ist jetzt getaggt (#62487)

„dag_processing.last_run.seconds_ago.{dag_file}“ ist jetzt eine alte Metrik. Das Neue „dag_processing.last_run.seconds_ago`` is emitted with ``file_path``, ``bundle_name“ und „file_name`` tags (``file_path`` + ``bundle_name“ identifiziert die Dag-Datei eindeutig. Die Legacy-Metrik wird weiterhin standardmäßig ausgegeben und kann über „[metrics] legacy_names_on“ deaktiviert werden.

Neue Fristenseite unter Durchsuchen (#67586)

Im Menü „Durchsuchen“ ist eine neue Seite „Fristen“ verfügbar, auf die alle Rollen zugreifen können, die bereits über eine solche Funktion verfügen „can_read`` and ``menu_access“ auf Dag Runs.
