kubernetes-client v7.6.0

Fehler

– Fix #5292: Die Cluster()-Konfiguration sollte tlsServerName verwenden – Fix #7174: (httpclient) HTTP client-Factory-Priorität beheben – VertxHttpClientFactory (Standard) hat jetzt Priorität -1, OkHttpClientFactory wurde auf Priorität 0 zurückgesetzt – Fix #7174: (httpclient-vertx-5) Laufzeitprüfung für Vert.x 5-Klassen hinzugefügt, um einen eindeutigen Fehler bereitzustellen, wenn ein Vert.x 4/5-Konflikt auftritt

  • Fix #7174: (Chaos-Tests) Klassenpfadkonflikt beim Testen mit Vert.x 5 HTTP client behoben
  • Fix #7415: (Java-Generator) Korrigiert das Löschen generischer Typen für Arrays von Aufzählungen mit Standardwerten – Fix #7422: (okhttp) Entfernen Sie die interne API-Nutzung und beheben Sie veraltete OkHttp 5-Aufrufe – Fix #7446: Zeitüberschreitung von BaseOperation.createOrReplace() konfigurierbar machen

Verbesserungen

– Fix Nr. 1105: Javadoc-Vernetzung für Fabric8-Module und externe Abhängigkeiten hinzufügen – Fix #5756: Bearbeitbare Schnittstelle anstelle von Reflektion verwenden, um Ressourcen-Builder zu instanziieren – Fix #7422: okhttp von 4.12.0 auf 5.3.2 erhöhen – Fix #7252: Rufen Sie „additionalConfig“ auf, wenn Sie Vert.x HTTP clients mit VertxHttpClientFactory erstellen

Abhängigkeits-Upgrade

  • Fix #7374: Snakeyaml-Engine von 2.10 auf 3.0.1 erhöhen

Neue Funktionen

  • Fix #7385: Unterstützung für Kubernetes v1.35 (Timbernetes) – Fix #7174: Vert.x 5 HTTP client-Implementierung mit verbesserter asynchroner Handhabung und WebSocket-Trennung hinzugefügt – Fix Nr. 7402: Generierung eines Kompatibilitätsberichts auf Byte-Codeebene Semver API mit Revapi hinzugefügt

Hinweis: Wichtige Änderungen

– Fix #5756: Mit Besuchern bearbeitete Ressourcen müssen jetzt io.fabric8.kubernetes.api.builder.Editable implementieren. Alle vom client bereitgestellten Modellklassen implementieren diese Schnittstelle bereits. Vom Benutzer bereitgestellte benutzerdefinierte Ressourcen, die besucherbasierte Bearbeitung verwenden, müssen Editable implementieren (trivial, wenn bereits ein Builder vorhanden ist). – Fix #7422: okhttp von 4.12.0 auf 5.3.2 erhöhen. Die Versionen sind binärkompatibel, das Hauptversions-Upgrade kann jedoch Nebenwirkungen verursachen.

Hinweis: Vert.x HTTP Client-Kompatibilität (Problem Nr. 7174)

Die Module kubernetes-httpclient-vertx (Vert.x 4.x) und kubernetes-httpclient-vertx-5 (Vert.x 5.x) schließen sich gegenseitig aus. Sie dürfen nicht gemeinsam in Ihren Projektabhängigkeiten enthalten sein. Beide Module stellen eine Implementierung von HttpClient.Factory bereit und verwenden dieselben io.vertx-Artefaktkoordinaten, jedoch mit inkompatiblen Hauptversionen.

-Problem*: Wenn beide Module im Klassenpfad vorhanden sind, wählt Mavens Abhängigkeitsauflösung möglicherweise Vert.x 4.x-JARs aus, während Vertx5HttpClientFactory zur Laufzeit ausgewählt wird. Dies führt zu NoClassDefFoundError für Vert.x 5-spezifische Klassen wie io.vertx.core.impl.SysProps.

-Lösung*: Stellen Sie sicher, dass Ihr Projekt nur EINES dieser Module enthält:

  • kubernetes-httpclient-vertx (Standard, verwendet Vert.x 4.x) – transitiv über kubernetes-client eingebunden – kubernetes-httpclient-vertx-5 (optional, verwendet Vert.x 5.x) – erfordert explizite Abhängigkeit und Ausschluss von Vertx-4

Wenn Sie Vert.x 5 verwenden, schließen Sie den standardmäßigen Vert.x 4 client aus und legen Sie die Eigenschaft vertx.version fest:

<properties>
  <vertx.version>${vertx5.version}</vertx.version> <!-- or explicit 5.0.7 -->
</properties>
<dependencies>
  <dependency>
    <groupId>io.fabric8</groupId>
    <artifactId>kubernetes-client</artifactId>
    <exclusions>
      <exclusion>
        <groupId>io.fabric8</groupId>
        <artifactId>kubernetes-httpclient-vertx</artifactId>
      </exclusion>
    </exclusions>
  </dependency>
  <dependency>
    <groupId>io.fabric8</groupId>
    <artifactId>kubernetes-httpclient-vertx-5</artifactId>
  </dependency>
</dependencies>
