clickhouse-java v0.10.0-rc2

Release-Migrationsleitfaden

Zusätzlich zu v0.10.0-rc1

Breaking Changes

  • [client-v2] Die öffentliche ClickHouseBinaryFormatWriter-Schnittstelle hat zwei Methoden, setString(String, byte[]) und setString(int, byte[]), zum Schreiben roher String/FixedString-Bytes erhalten. Code, der nur die Schnittstelle verwendet, ist nicht betroffen, aber jeder Dritte, der ClickHouseBinaryFormatWriter direkt implementiert, ist quell- und binärinkompatibel, bis er diese Methoden hinzufügt (eine Neukompilierung mit der neuen Version ist erforderlich; andernfalls kann zur Laufzeit ein AbstractMethodError auftreten).

  • [client-v2] HTTP 503 Service Unavailable-Antworten werden jetzt als Verbindungsfehler angezeigt ( java.net.ConnectException) und werden standardmäßig wiederholt. Bisher wurde ein 503 als Serverfehler behandelt ( ServerException) und fiel unter die Fehlerursache ServerRetryable. Es wurde zur Verwerfung ConnectTimeout verschoben Ursachenkategorie, sodass Konnektivitäts-/Verfügbarkeitsfehler einheitlich mit anderen Verbindungsfehlern behandelt werden. Anrufer dass ServerRetryable ausdrücklich ausgeschlossen wurde, um einen erneuten Versuch zu vermeiden, 503 sollte nun angepasst werden client_retry_on_failures-Konfiguration, um stattdessen ConnectTimeout auszuschließen.

  • [client-v2] Unerwartete/unbekannte HTTP-Statuscodes (die der client nicht als ClickHouse-Antwort interpretieren kann) jetzt Wirf einen ClientException anstelle eines ServerException. Da der client diese Antworten nicht sinnvoll verarbeiten kann, Sie werden als client-seitiger Fehler gemeldet und nicht dem Server zugeschrieben.

Neue Funktionen

  • [client-v2, jdbc-v2] Opt-in-Unterstützung für binäre Zeichenfolgen über die Konfigurationseigenschaft binary_string_support hinzugefügt (oder Client.Builder#binaryStringSupport(boolean)), standardmäßig deaktiviert. Die Einstellung wird pro Vorgang ab aufgelöst die zusammengeführten client- und Abfrageeinstellungen, sodass sie für eine einzelne Anfrage über binary_string_support überschrieben werden können Bedienoption (z. B. QuerySettings#setOption(ClientConfigProperties.BINARY_STRING_SUPPORT.getKey(), true)) unabhängig von der client-Level-Standardeinstellung. Wenn diese Option aktiviert ist, werden die Spalten String und FixedString der obersten Ebene gelesen in einen StringValue, der die Rohbytes beibehält, anstatt sie in einen String zu dekodieren, was Nicht-UTF-8/Binär zulässt Inhalt zum Roundtrip Byte für Byte. StringValue stellt die Bytes über toByteArray()/asByteBuffer() und zur Verfügung dekodiert ein String träge über asString() (standardmäßig UTF-8 oder ein vom Anrufer bereitgestelltes Charset). Darin verschachtelte Werte Container (Array, Map, Tuple, Nested, Variant) werden weiterhin als String gelesen, da dies bei diesen Typen nicht der Fall ist Es wird erwartet, dass große/binäre Zeichenfolgen übertragen werden. Auf der JDBC-Seite ResultSet#getBinaryStream(int) und ResultSet#getBinaryStream(String) sind jetzt implementiert (bisher nicht unterstützt) und zusammen mit getBytes(...) Gibt die rohen Spaltenbytes zurück.

  • [client-v2] Client#cancelTransportRequest(String queryId) hinzugefügt, um eine Anfrage während des Flugs zu stornieren, die noch nicht erfolgt ist hat eine Antwort vom Server erhalten, identifiziert durch die in den Vorgangseinstellungen angegebene Abfrage-ID. Dies bricht den Vorgang ab Anfrage auf der client-Seite (bricht den zugrunde liegenden E/A-Vorgang ab), gibt aber kein ein KILL QUERY auf dem Server aus, Daher kann eine Abfrage, deren Ausführung bereits begonnen hat, weiterhin serverseitig ausgeführt werden. Es wird empfohlen, das Betriebszeitlimit zu verwenden Einstellungen wo möglich; Dieser API dient dazu, eine Anfrage vom client explizit abzubrechen.
