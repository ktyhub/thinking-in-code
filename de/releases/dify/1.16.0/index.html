Einführung von Dify Agent (Beta): Eine neue Agentenerfahrung in Dify

[!WARNUNG] Sie sollten Dify Agent-Dienste ⚠️nur für trusted, nicht böswillige Benutzer⚠️ bereitstellen.

Wie viele von Ihnen wissen, hat das Shell-basierte LLM-Agentenparadigma einen großen Sprung in den Fähigkeiten der Agenten gebracht und unsere Einstellung zu Agenten verändert. Mittlerweile bieten Skills eine standardisierte Möglichkeit zum Paketieren und Verteilen von Funktionen, wodurch es einfacher wird, leistungsstarke Agenten zu erstellen.

Heute starten wir Dify Agent. Wie andere führende Agenten läuft es in einer Linux-Sandbox. Diese Version enthält:

  • Ein Builder zum Erstellen von Dify-Agenten

    • Sie können Dify-Agenten über die Benutzeroberfläche erstellen: Legen Sie eine Basisaufforderung fest, laden Sie Fähigkeiten und Dateien hoch und verbinden Sie Tools und Wissen aus dem Dify-Ökosystem.
    • Wir stellen auch einen Agenten zur Verfügung, der Sie bei der Erstellung von Dify-Agenten unterstützt. Durch Konversation kann er die Linux-Sandbox-Umgebung konfigurieren, erforderliche Pakete installieren und neue Fähigkeiten und Dateien erstellen, die Ihr Dify-Agent später verwenden kann.

  • Dify-Workflow-Integration für Dify Agent

    • Sie können einen vorhandenen Dify-Agenten in einem Dify-Workflow verwenden oder vorübergehend einen Inline-Dify-Agenten erstellen. Es führt die vom Workflow-Knoten definierte Aufgabe aus, generiert die erforderliche Ausgabe und übergibt sie an den nächsten Knoten.

  • Ein neues Web-App-Erlebnis

    • Der von Ihnen erstellte Dify Agent kann als Web-App veröffentlicht und verwendet werden. Während die Benutzererfahrung vertraut bleibt, wird sie jetzt von Dify Agent unterstützt.

Dokumente: https://docs.dify.ai/en/self-host/use-dify/build/new-agent/overview

⚠️ Aktion erforderlich

OpenAI GPT-5.6-Kompatibilitätshinweis

Das OpenAI-Plugin verwendete zuvor standardmäßig die Chat Completions API, die Anfang des Jahres von OpenAI veraltet war und neuere Modellserien immer schlechter unterstützt. Die neu veröffentlichte GPT-5.6-Familie weist bei der Verwendung mit Chat Completions viele ungewöhnliche und einzigartige Parameterkombinationsbeschränkungen auf, da OpenAI jetzt nur noch minimale Kompatibilitätsunterstützung für Chat Completions mit neuen Modellen bietet. Dies ist kein Dify-Systemproblem.

Der Standardtyp API für neue Konfigurationen wurde von Chat-Abschlüssen in Antworten geändert. Benutzer, die zuvor einen benutzerdefinierten API-Schlüssel mit der alten Standardeinstellung (Chat-Abschlüsse) gespeichert haben, behalten diese Einstellung jedoch bei, was zu unerwarteten Fehlern führen kann, die scheinbar von Dify stammen.

Wenn Sie zuvor einen benutzerdefinierten OpenAI API-Schlüssel konfiguriert haben, überprüfen Sie bitte Ihre API-Typeinstellung und wechseln Sie zu Antworten, wenn dieser noch auf Chat-Abschlüsse eingestellt ist, insbesondere wenn Sie GPT-5.6 oder neuere Modelle verwenden.

Neue Funktionen

Agent-App (Offene Beta) – Die Agent-App geht in die offene Betaphase und ist jetzt standardmäßig für alle Benutzer aktiviert. Es führt eine integrierte Sandbox für die Codeausführung und Shell-Befehle ein, ein Skill-System, mit dem Agenten Tools und APIs aufrufen können, eine Agentenliste zum Verwalten und Wiederverwenden von Agenten in einem Arbeitsbereich sowie Unterstützung für die Referenzierung neuer Agenten aus Workflow-Agentenknoten.

Intelligentere KI-Workflow-Generierung – Der AI-Workflow-Generator ⌘K → /create und /refine wurde durchgängig verbessert: Das Feld „Ideale Ausgabe“ mit niedrigem Wert wurde entfernt, statische Beispielchips wurden durch KI-generierte Vorschläge ersetzt, die auf Ihrem Arbeitsbereich basieren, und die Knotenkonfigurationsgenerierung ist jetzt für schnellere Ergebnisse parallelisiert. Ein konfigurierbares Timeout (WORKFLOW_GENERATION_TIMEOUT_MS, Standard 180 Sekunden) verhindert, dass lang laufende Generationen hängen bleiben. MCP-Protokoll-Upgrade – Der Workflow-as-MCP-Server unterstützt jetzt das MCP-Protokoll 2025-06-18 mit Versionsaushandlung und strukturierter Tool-Ausgabe und bleibt dabei abwärtskompatibel mit älteren clients. MCPClient-Verbindungen können jetzt dynamische HTTP-Anforderungsheader zur Laufzeit mithilfe von Platzhaltern (z. B. {{request.headers.X-Custom-Auth}}) einfügen und so den Passthrough für die Authentifizierung pro Anforderung ermöglichen.

Web-App-Anpassung – App-Besitzer können jetzt den Chat-Eingabe-Platzhaltertext (bis zu 64 Zeichen) für Chatbot-, Agent- und Chatflow-Web-Apps anpassen. Die Benutzeroberfläche zur Anpassung wurde mit einer klareren Benennung („Custom Frontend“ / „Branding“) und einer besseren Handhabung von Labels verfeinert. App-Beschreibungen werden jetzt auf Chat- und Textgenerierungs-App-Bildschirmen mit einer ausklappbaren Ansicht angezeigt, um zu vermeiden, dass das Eingabeformular vom Bildschirm verschoben wird.

Workflow-Zuverlässigkeit und Betrieb – Workflow-Laufarchive können jetzt exportiert werden und aktive Läufe werden beim warmen Herunterfahren von Celery ordnungsgemäß abgebrochen, um verwaiste Aufgaben zu verhindern. Redis-Verbindungen sind dank TCP-Keepalive-Unterstützung und erweiterter Wiederholungsabdeckung robuster. Modellanbieter erhalten jetzt app_id für die anbieterseitige Kostenzuordnung (z. B. Bedrock requestMetadata, OpenAI-Metadaten, Vertex AI-Labels). OAuth- und SSO-Anmeldeabläufe bewahren Umleitungs-URLs jetzt zuverlässiger, mit einer speziellen Fehleransicht für fehlgeschlagene SSO-Abschlüsse.

Fehlerbehebungen

Workflow & Agent – Mehrere Probleme mit dem Verlust von Referenzen bei Workflow-Entwurfsimporten, der Knotenabrechnung nach Fehlern, der Sichtbarkeit von Wiederholungsdetails und der Wiederherstellung des HITL-Lebenslaufstatus wurden behoben – Die Beschädigung des SSE-Streams mit Unicode-Trennzeichen, das Löschen der endgültigen Antwort des Agenten nach Abschluss des Streams und das Überschreiben des Konversationstitels mit leeren Werten wurden behoben – Die Absicherung von Workflow-Archiv-Wiederholungsversuchen, die Unterstützung für die Zusammenarbeit mit mehreren Mitarbeitern und Chat-Tree-Out-of-Order-Übergeordnete Knoten wurden behoben – Fehler beim Wissensabruf behoben, die Benutzern nicht angezeigt wurden, und Kollisionen mit Namen von Ausgabevariablen in integrierten Vorlagen beendet

Authentifizierung und Zugriffskontrolle – Offene Redirect-Schwachstellen in Post-Login- und Authentifizierungs-Redirect-Flows behoben – Problem behoben, bei dem Anmeldeumleitungen nicht bei der aktuellen Bereitstellung beibehalten wurden, Authentifizierungspräfixe dupliziert wurden und E-Mail-Änderungen nicht funktionierten

  • Probleme mit Editorberechtigungen behoben: Redakteure können jetzt Protokolle anzeigen, Abrechnungsabonnements nicht mehr abfragen und Mitglieder nicht mehr verwalten – Fehler bei der Nachverfolgung von Konfigurationsänderungen behoben, für die kein Bearbeitungszugriff erforderlich war, und Absicherung des Test-App-Zugriffs für empfohlene Apps

Modelle & Plugins – Behoben: Benutzerdefinierter Modell-Cache wurde beim Löschen nicht geleert, Fehler beim Debuggen von Modell-Plugins und Xinference-Anmeldeinformationskontextbehandlung – Problem behoben, bei dem die maximalen Token-Parameter in den Parametern des Folgemodells nicht deaktiviert werden konnten – Fehler beim Plugin-Anbieter-Cache-Ansturm, bei Rückrufen bei der Marktplatz-Installation und bei Plugin-Berechtigungseinstellungen behoben

Web und Benutzeroberfläche

  • App-Erstellung aus Learn Dify, Knotensuchfeldeingabe, Workspace-Avatar-Konsistenz und Navigationsprofilanzeige korrigiert
  • Streamdown-Vollbild-Tabellenaktionen, Jitter der Marktplatz-Seitenkopfzeile und Zugänglichkeit des Installationsdialogs behoben
  • Problem behoben, bei dem Chat-Anhänge nicht mehr sichtbar waren, die Sichtbarkeit der HITL-Eingabe-Speicherschaltfläche und der Meta-Überlauf der App-Karte behoben wurden
  • Die Nullwertanzeige des Überwachungsdiagramms, die Behandlung des Mitgliedseinladungsstatus, der Hintergrund im Dunkelmodus und Unicode-Zeichen in Formularfeldnamen wurden korrigiert – Das Herunterladen von Markdown-Datei-Vorschau-Links, der Notion-Synchronisierungsstatus „leer“ und die Blog-UTM-Attribution unter CSP wurden korrigiert

Andere – Endlosschleife beim Stapellöschen von Dokumenten, ungültige UTF-8-Cache-Nutzlasten und Fehler bei der Indizierung verschluckter Dokumente behoben

  • PostgreSQL 18 native uuidv7()-Unterstützung und ADB-PG 7.0-Kompatibilität behoben – Behoben, dass CAN_REPLACE_LOGO standardmäßig auf „true“ gesetzt ist, nicht unterstützte Sprachfehler in „execute_code“ und CLI --insecure-Flag, das die TLS-Überprüfung nicht überspringt

Verbesserungen

Leistung – N+1-Abfragen in den Ausführungslisten des erweiterten Chat-Workflows und beim Laden von TokenBufferMemory-Nachrichtendateien eliminiert

  • Schnellerer Frontend-Start durch verzögert geladene Vite-Plugins und Konsolenvertrags-Shards – Reduzierte Datenbanklast durch Zwischenspeichern des Setup-Status, Komprimieren großer Plugin-Modellobjekte in Redis mit zstd und Abrufen veröffentlichter Workflows über einen direkten Fremdschlüssel

Architektur und Codequalität – Alle Konsolen-API-Endpunkte wurden auf generierte OpenAPI-Verträge mit BaseModel und die Frontend-Konsolenverträge auf generierte Routen und Typen migriert – Propagierung expliziter Datenbanksitzungen über Backend-Pfade hinweg für Konsistenz und Testbarkeit

  • Legacy-App-Kontextanbieter im gesamten Frontend durch Jotai-Atome ersetzt – Auf TypeScript 7 und Vite+-Toolchain aktualisiert, strenge ESLint-Regeln erzwungen und neue direkte SQLAlchemy in Controllern verboten

Sicherheitsverbesserungen

Diese Version enthält mehrere Korrekturen zur Sicherheitsverstärkung, von denen einige nach der Version 1.16.0-rc1 behoben wurden:

  • SQL-Injection: Eine SQL-Injection-Schwachstelle wurde geschlossen und die SQL-Abfragesicherheit durch Metadatenschlüsselvalidierung verbessert
  • SSRF: Eine SSRF-Umgehung über rohes httpx.get im Schemaabruf des Tools API wurde behoben
  • Offene Weiterleitungen: Offene Weiterleitungen in Post-Login- und Authentifizierungs-Umleitungsabläufen wurden verhindert
  • Sandbox-Erzwingung: Chatflow API überprüft jetzt Workflow_ID und Sandbox-Plan; Der Sandbox-Plan führt keine speziellen Workflows aus
  • Landlock-Schutz: Agent-HOME-Verzeichnis mit Landlock geschützt; Für eine breitere Kernel-Kompatibilität wurde ein Downgrade auf Version 1 durchgeführt
  • CVE-Abhängigkeits-Upgrades: httplib2, setuptools, wandb; python-Motor, python-Sockel; wankelmütig, Kissen, click

Upgrade-Anleitung

Modelltypmigration

[!IMPORTANT]

Einmalige Migration des Legacy-Modelltyps für selbst gehostete Upgrades

Wenn diese Bereitstellung von einer Dify-Version vor 1.15.0 aktualisiert wurde und diese Migration noch nicht angewendet wurde, führen Sie sie nach dem Upgrade aus.

Diese Migration ist nicht in flask db upgrade enthalten. Ohne sie können ältere Modelldatensätze dazu führen, dass modellbezogene API-Anfragen mit Fehlern fehlschlagen und betroffene Modelle nicht geladen oder verwendet werden können.

Sichern Sie die Datenbank, bevor Sie die Migration anwenden. Der Befehl wird standardmäßig im Probelaufmodus ausgeführt. Überprüfen Sie die Ausgabe, bevor Sie sie mit --apply erneut ausführen. Die Migration ist idempotent und kann sicher wiederholt werden.

Docker Verfassen

Aus dem Verzeichnis docker ausführen.

# Apply after reviewing the dry-run output
docker compose exec -T api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Quellcode-Bereitstellung

Nach Abschluss von flask db upgrade vom Repository-Stamm ausführen.

# Apply after reviewing the dry-run output
uv run --project api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Führen Sie nach der Migration den Befehl „Probelauf“ erneut aus. Wenn keine weiteren Zeilenaktualisierungen oder -löschungen gemeldet werden, starten Sie die entsprechenden Dienste neu und überprüfen Sie, ob vorhandene Modelle erfolgreich geladen und aufgerufen werden können.

[!IMPORTANT]

– Diese Version enthält 8 neue Datenbankmigrationen. Führen Sie im Rahmen des Upgrades Datenbankmigrationen durch.

  • 28 neue Umgebungsvariablen, 1 entfernt und 1 geändert. Sehen Sie sich den Abschnitt „Änderungen der Umgebungsvariablen“ an und aktualisieren Sie Ihren .env entsprechend.
  • Docker Compose-Konfiguration erheblich geändert: Zwei neue Dienste (agent_backend, local_sandbox) wurden hinzugefügt. Wenn Sie ein angepasstes docker-compose.yaml verwalten, überprüfen Sie die Änderungen und wenden Sie die lokalen Anpassungen sorgfältig erneut an.
  • DIFY_AGENT_SERVER_SECRET_KEY wird mit einem Entwicklungsstandard ausgeliefert. Sie müssen ihn in der Produktion ersetzen durch einen sicher generierten Schlüssel: python -c 'import secrets; print(secrets.token_urlsafe(32))'
  • ENABLE_AGENT_V2 wurde in NEXT_PUBLIC_ENABLE_AGENT_V2 umbenannt und lautet nun standardmäßig true. Entfernen Sie die alte Variable aus Ihren env-Dateien.
  • OpenAI GPT-5.6-Benutzer: Wenn Sie zuvor einen benutzerdefinierten OpenAI API-Schlüssel konfiguriert haben, stellen Sie sicher, dass Ihr API-Typ auf Antworten (nicht Chat-Abschlüsse) eingestellt ist. Siehe den Abschnitt „Bekannte Probleme“ oben.

Docker Bereitstellungen erstellen

  1. Sichern Sie Ihre benutzerdefinierten docker-compose YAML- und env-Dateien.

    cd docker
cp docker-compose.yaml docker-compose.yaml.$(date +%s).bak
cp .env .env.$(date +%s).bak 2>/dev/null || true

  2. Holen Sie sich den neuesten Code aus dem Release-Zweig oder Tag.

    git fetch --tags
git checkout 1.16.0

  3. Stoppen Sie den Dienst. Bitte im Verzeichnis docker ausführen.

    docker compose down

  4. Daten sichern.

    tar -cvf volumes-$(date +%s).tgz volumes

  5. Überprüfen Sie die neuen Umgebungsvariablen (insbesondere DIFY_AGENT_SERVER_SECRET_KEY) und aktualisieren Sie Ihre .env-Datei. Wenden Sie alle lokalen Anpassungen erneut an.

  6. Upgrade-Dienste.

    docker compose up -d

Quellcode-Bereitstellungen

  1. Stoppen Sie den API-Server, den Worker und den Web-Frontend-Server.

  2. Holen Sie sich den neuesten Code aus dem Release-Tag.

    git fetch --tags
git checkout 1.16.0

  3. Aktualisieren Sie die Python-Abhängigkeiten.

    cd api
uv sync

  4. Führen Sie das Migrationsskript aus.

    uv run flask db upgrade

  5. Konfigurieren Sie den neuen Agent-Backend-Dienst. Informationen zu den erforderlichen Umgebungsvariablen finden Sie im Abschnitt dify-agent in docker/envs/core-services/dify-agent.env.example.

  6. Starten Sie den API-Server, den Worker und den Web-Frontend-Server neu.
