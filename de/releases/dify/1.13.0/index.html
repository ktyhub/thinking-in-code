🚀 Neue Funktionen

Human-in-the-Loop (HITL)

Wir stellen den Knoten Human Input vor, ein großes Update, das die Art und Weise verändert, wie KI und Menschen miteinander umgehen Zusammenarbeit innerhalb von Dify-Workflows.

Hintergrund

Bisher waren Arbeitsabläufe binär: entweder vollständig automatisiert oder vollständig manuell. Dadurch entstand eine „trust-Lücke“. Szenarien mit hohen Einsätzen, in denen KI-Geschwindigkeit erforderlich ist, menschliches Urteilsvermögen jedoch unerlässlich ist. Mit HITL machen wir h uman überwacht einen nativen Teil der Workflow-Architektur und ermöglicht die Einbettung Überprüfen Sie Schritte direkt im Ausführungsdiagramm.

Schlüsselfunktionen

  • Native Workflow-Pausierung: Fügen Sie einen „Human Input“-Knoten ein, um die Workflow-Ausführung an kritischen Entscheidungspunkten anzuhalten.
  • Überprüfen und Bearbeiten: Der Knoten generiert eine Benutzeroberfläche, in der Menschen KI-Ausgaben überprüfen und Variablen ändern können (z. B. einen Entwurf bearbeiten oder Daten korrigieren), bevor der Prozess fortgesetzt wird.
  • Aktionsbasiertes Routing: Konfigurieren Sie benutzerdefinierte Schaltflächen (wie „Genehmigen“, „Ablehnen“ oder „Eskalieren“), die bestimmen den weiteren Pfad des Workflows.
  • Flexible Zustellungsmethoden: Menschliche Eingabeformulare können über Webapp oder E-Mail zugestellt werden. In Cloud-Umgebungen kann die Verfügbarkeit der E-Mail-Zustellung von den Plan-/Funktionseinstellungen abhängen.

🛠 Architektur-Updates

Um den von HITL erforderlichen zustandsbehafteten Pausen-/Fortsetzungsmechanismus zu unterstützen und Ereignisabonnements APIs bereitzustellen, haben wir die Ausführungs-Engine umgestaltet: Workflow-basierte Streaming-Ausführungen und erweiterte Chat-Ausführungen werden jetzt in Celery-Workern ausgeführt, während nicht-streamende WORKFLOW-Ausführungen weiterhin im API-Prozess ausgeführt werden. Alle Pausen-/Fortsetzungspfade (z. B. HITL) werden über Celery fortgesetzt und Ereignisse werden über Redis Pub/Sub zurückgestreamt.

Für große Bereitstellungen und selbstgehostete Benutzer:

Wir haben eine neue Sellerie-Warteschlange mit dem Namen workflow_based_app_execution eingeführt. Während Standard-Setups sofort funktionieren, sollten Umgebungen mit hohem Durchsatz die folgenden Optimierungen in Betracht ziehen, um Stabilität und Leistung sicherzustellen:

  1. Skalierung der Worker: Passen Sie die Anzahl der Worker, die die workflow_based_app_execution-Warteschlange nutzen, basierend auf Ihrer spezifischen Arbeitslast an.
  2. Dedizierte Redis (optional): Für umfangreiche Bereitstellungen empfehlen wir, die neue Umgebungsvariable PUBSUB_REDIS_URL so zu konfigurieren, dass sie auf eine dedizierte Redis-Instanz verweist. Die Verwendung des Redis-Clustermodus mit Sharded PubSub wird dringend empfohlen, um horizontale Skalierbarkeit sicherzustellen.

⚠️ Wichtiger Upgrade-Hinweis

Neue Sellerie-Warteschlange erforderlich: workflow_based_app_execution

Bitte stellen Sie sicher, dass Ihre Bereitstellungskonfiguration (Docker Compose, Helm Chart usw.) Worker umfasst, die auf die neue workflow_based_app_execution-Warteschlange warten.
Diese Warteschlange ist für Workflow-basierte Streaming-Ausführungen und alle Resume-Flows (z. B. HITL) erforderlich. Andernfalls werden Streaming-Ausführungen und Wiederaufnahmeaufgaben nicht verarbeitet.

🔧 Betriebshinweis

Zusätzliche Sellerie-Warteschlange: api_token

Wenn ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK=true, stellen Sie sicher, dass Ihre Bereitstellung auch über Worker verfügt, die api_token überwachen. Diese Warteschlange wird von der geplanten Stapelaktualisierungsaufgabe für API-Token-last_used_at-Zeitstempel verwendet.

⚙️ Konfigurationsänderungen

Wir haben mehrere neue Umgebungsvariablen eingeführt, um die Architekturänderungen zu unterstützen. Bei großen Bereitstellungen sollte den PubSub Redis-Konfigurationen besondere Aufmerksamkeit geschenkt werden, um die Skalierbarkeit sicherzustellen.

  • PUBSUB_REDIS_URL (Kritisch): Gibt die Redis-URL an, die für die PubSub-Kommunikation zwischen den API- und Celery-Workern verwendet wird. Wenn es leer bleibt, wird standardmäßig die Standardkonfiguration REDIS_* verwendet.
  • PUBSUB_REDIS_CHANNEL_TYPE (Kritisch): Definiert den Kanaltyp für Streaming-Ereignisse. Optionen sind pubsub (Standard) oder sharded. Wir empfehlen dringend die Verwendung von sharded für Umgebungen mit hohem Durchsatz.
  • PUBSUB_REDIS_USE_CLUSTERS (Kritisch): Auf true setzen, um den Redis-Clustermodus für PubSub zu aktivieren. In Kombination mit Sharded PubSub ist dies für die horizontale Skalierung unerlässlich.

Weitere Ergänzungen:

  • WEB_FORM_SUBMIT_RATE_LIMIT_MAX_ATTEMPTS: Maximale Anzahl zulässiger Webformulareinreichungen pro IP innerhalb des Ratenbegrenzungsfensters (Standard: 30).
  • WEB_FORM_SUBMIT_RATE_LIMIT_WINDOW_SECONDS: Zeitfenster in Sekunden für die Begrenzung der Webformular-Übermittlungsrate (Standard: 60).
  • HUMAN_INPUT_GLOBAL_TIMEOUT_SECONDS: Maximale Sekunden, die eine Workflow-Ausführung angehalten bleiben kann, bis auf menschliche Eingaben gewartet wird, bevor das globale Zeitlimit überschritten wird (Standard: 604800, 7 Tage).
  • ENABLE_HUMAN_INPUT_TIMEOUT_TASK: Aktiviert die Hintergrundaufgabe, die nach abgelaufenen menschlichen Eingabeanforderungen sucht (Standard: true).
  • HUMAN_INPUT_TIMEOUT_TASK_INTERVAL: Legt das Intervall (in Minuten) für die Zeitüberschreitungsprüfungsaufgabe fest (Standard: 1).
  • ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK: Aktiviert die periodische Hintergrundaufgabe, die die Zeitstempel des API-Tokens last_used_at stapelweise aktualisiert (Standard: true).
  • API_TOKEN_LAST_USED_UPDATE_INTERVAL: Legt das Intervall (in Minuten) für die Stapelaktualisierung der Zeitstempel des API-Tokens last_used_at fest (Standard: 30).
  • SANDBOX_EXPIRED_RECORDS_CLEAN_BATCH_MAX_INTERVAL: Maximale zufällige Verzögerung (in Millisekunden) zwischen Aufbewahrungsbereinigungsstapeln, um DB-Druckspitzen zu reduzieren (Standard: 200).

📌 Zusätzliche Changelog-Highlights

Zuverlässigkeit und Korrektheit

– Deduplizierung während der Migration und eine eindeutige Einschränkung für Mandanten-Standardmodelle hinzugefügt, um doppelte Standardmodelldatensätze zu verhindern. – Es wurde ein Randfall beim Löschen von Tools behoben, der durch eine Nichtübereinstimmung des Anbieter-ID-Typs verursacht wurde. – Es wurde eine FastOpenAPI-Integrationsregression behoben, bei der authentifizierte Benutzer in Remote-Datei-APIs als anonym aufgelöst werden konnten. – Die Erkennung des Nachrichtenereignistyps für dateibezogene Antworten wurde korrigiert und die Arbeitsbereich-Einladungsaktion für Nicht-Manager-Benutzer ausgeblendet.

Leistung und Skalierbarkeit

– Reduzierte Back-End-Last und Konsolenlatenz durch Plugin-Manifest-Vorcaching und AppListApi-Abfrageoptimierungen. – Verbesserte Stabilität von Aufgaben für große Datenmengen durch geteilte DB-Sitzungen, Batch-Bereinigungsausführung, Indexoptimierung und konfigurierbare Inter-Batch-Drosselung für Aufbewahrungsbereinigungsjobs.

API & Plattformfunktionen

– Ein Dienst-API-Endpunkt für die Endbenutzersuche mit Durchsetzung des Mandanten-/App-Bereichs wurde hinzugefügt. – Verbessertes Aktualisierungsverhalten des Workflow-Ausführungsverlaufs bei Ausführungsstatusübergängen. – Verbesserte MCP-Tool-Integration durch Extrahieren und Berichten von Nutzungsmetadaten (z. B. Token-/Kostenfelder) aus MCP-Antworten.

Sicherheit

– Die dynamische new Function-Auswertung wurde aus der ECharts-Analyse entfernt und gibt jetzt explizite Analysefehler für nicht unterstützten Diagrammcode zurück.

Lokalisierung

– Niederländische Sprachunterstützung (nl-NL) für Backend-Sprachzuordnung und Weblokalisierungsressourcen hinzugefügt.

Docker Bereitstellungen erstellen

  1. Sichern Sie Ihre angepasste docker-compose YAML-Datei (optional)

    cd docker
cp docker-compose.yaml docker-compose.yaml.$(date +%s).bak

  2. Holen Sie sich den neuesten Code aus der Hauptniederlassung

    git checkout main
git pull origin main

  3. Stoppen Sie den Dienst. Bitte im Verzeichnis docker ausführen

    docker compose down

  4. Daten sichern

    tar -cvf volumes-$(date +%s).tgz volumes

  5. Upgrade-Dienste

    docker compose up -d

Quellcode-Bereitstellungen

  1. Stoppen Sie den API-Server, den Worker und den Web-Frontend-Server.

  2. Holen Sie sich den neuesten Code aus dem Release-Zweig:

    git checkout 1.13.0

  3. Aktualisieren Sie die Python-Abhängigkeiten:

    cd api
uv sync

  4. Dann führen wir das Migrationsskript aus:

    uv run flask db upgrade

  5. Führen Sie abschließend den API-Server, den Worker und den Web-Frontend-Server erneut aus.
