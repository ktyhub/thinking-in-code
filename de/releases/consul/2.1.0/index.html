Konsul v2.1.0

2.1.0 (21. Oktober 2026)

WICHTIGSTE ÄNDERUNGEN:

  • Agent: (Nur Enterprise) Agent HTTP API-Anfragetexte sind jetzt standardmäßig auf 512 KiB begrenzt, einschließlich Chunk-Anfragen und Anfragen mit einer nicht unterstützten Methode, und übergroße Anfragen geben HTTP 413 zurück, bevor der Text vollständig gelesen wird. Sehr große /v1/config-Schreibvorgänge, die zuvor erfolgreich waren, können jetzt fehlschlagen. Erhöhen Sie das Limit bei Bedarf mit der neuen limits.http_max_request_body_size-Einstellung.
  • Agent: (Nur Enterprise) Anforderungskörper für Ressourcen API (/api/...) unterliegen jetzt demselben limits.http_max_request_body_size-Limit (standardmäßig 512 KiB) und übergroße Anforderungen geben HTTP 413 zurück.
  • Agent: (Nur Enterprise) GET /v1/agent/connect/ca/leaf/:service erfordert jetzt service:write für den angeforderten Dienst für jede Anfrage, einschließlich Anfragen, die vom zwischengespeicherten Blattzertifikat des Agenten bedient werden. Anfragen ohne Token oder ein Token ohne diese Berechtigung erhalten jetzt HTTP 403 anstelle des zwischengespeicherten Zertifikats. Für den Dienst müssen Anrufer einen Token mit service:write vorlegen.
  • Katalog: (Nur Enterprise) Catalog.Register benötigt jetzt Schreibberechtigung für den Knoten oder Dienst einer vorhandenen Integritätsprüfung, wenn diese aktualisiert wird. Token, die zuvor Prüfungen ohne diese Berechtigung aktualisiert haben, erhalten jetzt die Fehlermeldung „Berechtigung verweigert“.
  • cli: Der Befehl consul connect redirect-traffic wurde von iptables/ip6tables auf nftables (nft) migriert. Der Befehl verwendet jetzt das Paket sdk/nftables, das alle IPv4- und IPv6-Regeln atomar in einem einzigen Durchgang über die Adressfamilie nftables inet anwendet, anstelle separater iptables- und ip6tables-Aufrufe. [GH-23785]
  • cli: Transparente Proxy-Ausschlüsse werden jetzt validiert, bevor Regeln angewendet werden: Benutzer-IDs müssen numerisch sein und ausgehende Ausschlüsse müssen IP-Adressen oder CIDRs sein. iptables akzeptierte bisher auch Benutzernamen, UID-Bereiche und Hostnamen. [GH-23785]
  • cli: consul connect redirect-traffic entfernt keine iptables/ip6tables-Regeln, die von früheren Consul-Versionen erstellt wurden. Dies ist nur wichtig, wenn ein vorhandenes Upgrade eines vorhandenen Hosts oder einer vorhandenen VM durchgeführt wird. Bevor Sie den neuen Befehl auf einem vorhandenen Host oder einer vorhandenen VM ausführen, entfernen Sie zunächst alle von Consul verwalteten iptables-Regeln (ein Referenz-Bereinigungsskript finden Sie im transparenten Proxy-Upgrade-Handbuch). Das Belassen beider Regelsätze kann zu doppeltem NAT oder einer inkonsistenten Datenverkehrsumleitung führen. [GH-23785]
  • docker: Die offiziellen Consul-Containerbilder enthalten jetzt nftables anstelle von iptables. Skripte, die iptables im Consul-Image ausführen, müssen aktualisiert werden. [GH-23785]
  • sdk: Das iptables-Paket wurde durch ein neues nftables-Paket für eine transparente Proxy-Verkehrsumleitung ersetzt. Für die Datenverkehrsumleitung sind jetzt die nft-Binärdatei und ein Linux-Kernel mit Stateful-NAT-Unterstützung in den Ketten der nftables- und inet-Familie erforderlich, die ab der Linux-Kernelversion 5.2 im Upstream verfügbar sind (einige Distributionen übertragen diese Unterstützung auf eine frühere nominale Kernelversion, zum Beispiel RHEL 8+, Kernel 4.18+ und seine Derivate). Es gibt keinen automatischen Fallback auf iptables/ip6tables, sodass Hosts ohne diese Kernel-Unterstützung keine transparente Proxy-Umleitung einrichten können. [GH-23785]
  • Feature-Gates: Gate API Gateway HTTPRoute Upstream-Routing-Zusammensetzung (PR #23294) hinter der experimentellen Funktion api-gateway-upstream-routing. Wenn diese Option deaktiviert ist (Standard), wird die alte HTTPRoute-to-Router-Form genau beibehalten. Bei Aktivierung durch einen Betreiber nach einem vollständigen Rechenzentrums-Upgrade werden Service-Router-Regeln mit HTTPRoute-Übereinstimmungen zusammengestellt, Definitionen von Resolver-Teilmengen bleiben erhalten und Erkennungskettenüberwachungen verwenden die korrekte HTTP-Protokollüberschreibung. Vorhandene agentenlose API-Gateway-Proxy-Status werden automatisch neu erstellt, wenn sich der effektive Gate-Wert ändert.

EIGENSCHAFTEN:

  • acl: OIDC RP-initiierte IdP-Abmeldung für Token hinzufügen, die über eine oidc-Authentifizierungsmethode erstellt wurden: consul logout druckt die Abmelde-URL des Identitätsanbieters aus, damit der Benutzer sie öffnen kann (oder öffnet sie im Standardbrowser mit dem neuen -open-browser-Flag oder der neuen Umgebungsvariablen CONSUL_LOGOUT_OPEN_BROWSER), und die Web-Benutzeroberfläche öffnet sie beim Abmelden, wodurch die IdP-Sitzung beendet wird. Wird automatisch aktiviert, wenn der IdP in seinem OIDC-Erkennungsdokument ein end_session_endpoint ankündigt oder wenn der Abmeldeendpunkt explizit mit der neuen OIDCLogoutURL-Authentifizierungsmethodeneinstellung für Anbieter konfiguriert wird, die kein end_session_endpoint ankündigen. [GH-23739]
  • Agent: (Nur Enterprise) Fügen Sie einen Inline-ai-Block zu Dienstdefinitionen hinzu, damit eine Arbeitslast ihre KI-Rolle (inference-model, mcp-server oder ai-agent) und rollenspezifische Konfiguration in einer einzigen Registrierung über Konfigurationsdateien und HTTP-APIs deklarieren kann. [GH-13032]
  • api-gateway: Fügen Sie http2 und grpc als gültige API-Gateway-Listener-Protokolle hinzu und ermöglichen Sie End-to-End-HTTP/2 und gRPC von client zum Backend. Bisher wurden nur http und tcp akzeptiert; Das Gateway würde den gRPC/HTTP2-Verkehr im Upstream-Hop stillschweigend auf HTTP/1.1 herabstufen. Die neuen Protokolle rendern den richtigen Downstream-HTTP-Verbindungsmanager (HTTP/2-Codec, h2,http/1.1 ALPN) und richten den Upstream-Cluster auf HTTP/2 aus, wodurch die Paritätslücke mit Ingress Gateway geschlossen wird. [GH-23784]
  • api-gateway: DNS automatisch für Dienste registrieren, die über ein API-Gateway bereitgestellt werden, auflösbar bei <service>.api-gateway.consul. Füllt die gateway-services-Katalogzuordnung für API-Gateways auf und fügt DNS-SANs zum API Gateway Connect-Blattzertifikat hinzu, wodurch das API-Gateway mit dem Ingress-Gateway auf Parität gebracht wird. Die Funktion ist versioniert und füllt bereits vorhandene Gateways automatisch auf, sobald alle Server aktualisiert wurden. [GH-23647]
  • api-Gateway: Unterstützt Zero-Touch-Downstream-TLS-Terminierung. Wenn TLS { Enabled = true } für einen api-gateway-Konfigurationseintrag ohne Inline-/Dateisystem-/SDS-Zertifikat festgelegt ist, beendet das Gateway Downstream-TLS mithilfe seines Connect CA-Blattzertifikats (mit *.api-gateway.consul-DNS-SANs). Explizit konfigurierte Zertifikate haben weiterhin Vorrang und werden als SNI-Überschreibungen neben der Blatt-Standardkette bereitgestellt. [GH-23647]
  • api-gateway: Fügen Sie PassiveHealthCheck zu den standardmäßigen Upstream-Grenzwerten auf Gateway-Ebene hinzu und leiten Sie Limit-Überschreibungen auf Service-Ebene weiter, damit passive Zustandsprüfungen (Envoy-Ausreißererkennung) für Dienste konfiguriert werden können, die über ein API-Gateway weitergeleitet werden. [GH-23783]
  • cli: (nur Enterprise) consul connect envoy -gateway=inference startet den Richtlinienprozessor zusammen mit Envoy und erzwingt eine Envoy-Mindestversion für das Inferenz-Gateway. Der ext_proc-Socket wird pro Proxy-Instanz abgeleitet; -ext-proc-socket-dir überschreibt sein Verzeichnis (Standard /var/run/consul).
  • connect: (Nur Enterprise) Ein von einem Agenten verwalteter OAuth client-Lebenszyklus für Dienste mit ai.role von ai-agent oder mcp-server hinzugefügt, einschließlich dynamischer client-Registrierung bei IBM Security Verify, Schlüsselrotation, JWKS-Veröffentlichung und SDS-Übermittlung der OAuth client-Anmeldeinformationen an ai-agent Envoy-Sidecars.
  • connect: (nur Enterprise) Stellen Sie OAuth-Sidecar-Anmeldeinformationen als AES-256-GCM-Umschläge bereit. Inhaltsverschlüsselungsschlüssel werden im KV gespeichert und über WorkloadKeyService.FetchKey bereitgestellt, sodass consul-obo-outbound entschlüsseln kann, ohne zu einem SDS client zu werden.
  • connect: (Nur Enterprise) Verdrahten Sie die ext_proc-Filter „consul-obo-outbound“ und „consul-obo-inbound“ mit connect-proxy xDS für den hop-gebundenen Token-Austausch im Auftrag von.
  • Verbinden: (Nur Enterprise) Registrieren Sie Dienste mit ai.role von ai-agent oder mcp-server bei IBM Security Verify mithilfe von private_key_jwt, behalten Sie DCR/JWKS in KV bei und übermitteln Sie die client-Anmeldeinformationen als SDS GenericSecret JSON für ai-agent-Workloads an Envoy. Cluster IAM ist eine OIDC-ACL-Authentifizierungsmethode mit EnableServiceDCR=true (Agent oauth.iam HCL wird abgelehnt).
  • Verbinden: Fügen Sie ecdh_curves zu den mesh-Konfigurationseinträgen (MeshDirectionalTLSConfig) und tls_ecdh_curves zur Agent-TLS-Konfiguration (TLSProtocolConfig) hinzu, um die Konfiguration zulässiger ECDH/KEM-Kurven für Sidecar-mTLS und Agent-RPC/HTTPS/gRPC zu unterstützen, mit automatischer Hybrid-Post-Quantum-X25519MLKEM768-Kurveninjektion, wenn tls_min_version auf TLSv1_3 gesetzt ist. [GH-23884]
  • Feature-Gates: Raft-gestütztes dynamisches Feature-Gate-Framework hinzufügen (Phase 1). Ein neuer feature_gates { bootstrap = { ... } }-Serverkonfigurationsblock legt den Grundstein für die erste Raft-Richtlinie. Der Leiter gleicht kontinuierlich die gewünschte Richtlinie, die Berechtigung zur Mindestversion und die Standardeinstellungen der Registrierung in einen festgeschriebenen, gelösten Status ab. Jeder Server führt einen atomaren Cache aus, der nur aus dem festgeschriebenen FSM-Status gefüllt wird. Agenten verbrauchen einen indizierten, aufgelösten Snapshot und werden erst dann geschlossen, wenn die erste Generation bereitgestellt wird. Die neuen Operator-Befehle CLI consul operator feature list, get und set ermöglichen CAS-sichere, ACL-geschützte Inspektion und Steuerung von Feature-Gates.
  • Operator: Fügen Sie die HTTP-Endpunkte GET /v1/operator/features, GET /v1/operator/feature/:name und PUT /v1/operator/feature/:name zum Lesen und Aktualisieren des Feature-Gate-Status hinzu. Lesevorgänge erfordern operator:read; Schreibvorgänge erfordern operator:write. Alle Lesevorgänge sind blockierende Abfragen möglich. [GH-23791]
  • inference-gateway: (nur Enterprise) Leiten Sie optierte externe Inferenzmodelle über ein abschließendes Gateway weiter. Modelle, die mit „Terminating-Gateway-Egress“ gekennzeichnet sind, werden aus dem Katalog erkannt, über die Mesh-Erkennungskette aufgelöst und über fehlerfreie Replikate des Terminating-Gateways verteilt, mit Fähigkeitspool-Prioritätsstufen und Fail-Closed-Verhalten, wenn kein gültiger Transport verfügbar ist. Ein Fähigkeitspool, der ein externes Modell enthält, wird abgelehnt und seine Fähigkeitsroute gibt 503 zurück, wenn zwei seiner Modelle dieselbe Endpunktadresse wiedergeben oder seine Modellgewichtungen nicht genau dargestellt werden können.
  • inference-gateway: (nur Enterprise) Fügen Sie den inference-gateway-Diensttyp und den Konfigurationseintrag hinzu. Das Gateway beendet eingehendes Mesh-mTLS, erzwingt Absichten und wendet PII- und Routing-Richtlinien über einen ext_proc-Filter auf einen am gleichen Standort befindlichen Richtlinienprozessor an. Modell-Upstreams sind bei ai.role = "inference-model" registrierte Dienste, die die Absichten zulassen und die über das Mesh erreichbar sind (verbindungsfähig oder hinter einem abschließenden Gateway). Das Gateway stellt über mTLS eine Verbindung zu ihnen her und wählt sie nach ihrer Fähigkeit aus, wobei ein Failover zwischen den Anbietern nach Priorität erfolgt.
  • Telemetrie: (Nur Enterprise) Serverseitige Produktnutzungsmetriken für die Anzahl der ACL-Authentifizierungsmethoden (OIDC, Kubernetes, JWT) und die Überwachungsprotokollierungskonfiguration hinzugefügt.
  • Telemetrie: (Nur Enterprise) Serverseitige Produktnutzungsmetriken für die Anzahl der Mesh-Gateway-Modi hinzugefügt: consul.usage.mesh_gateway_remote.count und consul.usage.mesh_gateway_local.count melden die Anzahl der Dienstinstanzen, die für die Verwendung jedes Mesh-Gateway-Modus konfiguriert sind, und consul.usage.mesh_gateway_none.count meldet die Anzahl der Dienstinstanzen ohne expliziten Mesh-Gateway-Modus (nicht festgelegt oder none).
  • Telemetrie: (Nur Enterprise) Serverseitige Produktnutzungsmetriken für die Standardrichtlinie der Serviceabsicht, die Anzahl der Serviceabsichten L7 und JWT hinzugefügt
  • Telemetrie: (Nur Enterprise) Die serverseitige Produktnutzungsmetrik consul.usage.mesh_gateway_enabled hinzugefügt, die meldet, ob eine Mesh-Gateway-Instanz im Cluster registriert ist. Dies ist unabhängig von der Anzahl der Mesh-Gateway-Modi: Diese zählen Connect-Proxy-Sidecars nach ihrem Upstream-Routing-Modus, während dieser meldet, ob die Gateway-Funktion überhaupt bereitgestellt wird.
  • terminating-gateway: (nur Enterprise) Vault-gestützte Anmeldeinformationsinjektion am Ausgang des terminierenden Gateways hinzufügen. Ein TerminatingGateway-Konfigurationseintrag enthält jetzt einen CredentialInjection-Block (ext_proc-Prozessor-UDS-Pfad und Nachrichten-Timeout) und jeder verknüpfte Dienst kann eine Credential-Bindung deklarieren (Mode: "inject" mit einem BindingID). Beim Ausgang ruft ein ext_proc-Filter einen am selben Ort befindlichen Prozessor auf, der die gebundenen Anmeldeinformationen (z. B. einen aus Vault stammenden Provider-Schlüssel API) in die Upstream-Anfrage einfügt, sodass Anmeldeinformationen niemals in der Mesh-Konfiguration gespeichert oder für clients verfügbar gemacht werden.
  • xds: Fügen Sie einen Inline-UDP-Listener für „virtuelles DNS“ (127.0.0.1:8653) hinzu, der eine speicherinterne FQDN-zu-VIP-Tabelle bedient, die aus dem Proxy-Snapshot abgeleitet ist. Es kündigt VIPs für explizite Upstreams, absichtlich zugelassene Upstreams im transparenten Proxy-Modus und Cluster-Peering-Upstreams an und überspringt dabei partitionsübergreifende VIPs, veraltete/unautorisierte Erkennungsketten und leere oder Nicht-IP-Einträge, sodass DNS-Antworten mit dem synchron bleiben, was der transparente Proxy-Listener tatsächlich abfängt. Fügen Sie einen optionalen „egress DNS“-UDP-Listener (127.0.0.1:8654) hinzu, der Abfragen über c-ares an vom Agent konfigurierte DNS-Rekursoren weiterleitet, wenn Rekursoren vorhanden sind. Erweitern Sie die xDS ConfigFetcher-Schnittstelle (und die Agentenimplementierung), um DNS-Rekursoren verfügbar zu machen. [GH-23698]

  • ui: Tab-Inhalte innerhalb seines Tab-Panels rendern, damit unterstützende Technologien ihn mit seinem Tab verknüpfen und den Fokus auf einem Tab behalten können, nachdem er aktiviert wurde [GH-24013]
  • ui: Es werden Fehler beim Laden des Inhalts einer Registerkarte innerhalb der Seite und nicht als zweite verschachtelte Seite angezeigt [GH-24013]
  • acl: (Nur Enterprise) Der Envoy-Escape-Hatch-Schlüsselabgleich in Proxy.Config und pro Upstream-Konfiguration wurde korrigiert, sodass er denselben Regeln zur Groß-/Kleinschreibung folgt wie die Konfigurationsdecoder. Schlüssel, die sich nur durch die Faltung der Unicode-Groß- und Kleinschreibung unterscheiden (zum Beispiel envoy_local_cluſter_json) und Go-Feldnamenformen wie EnvoyListenerJSON erfordern jetzt wie ihre kanonischen Schreibweisen mesh:write.
  • Agent: (Nur Enterprise) Die Überwachungsprotokollierung wurde korrigiert, sodass die Erfassung des Anforderungstexts die Körpergrößenbeschränkung berücksichtigt, den decodierten Anforderungspfad verwendet, wenn KV-Körper ausgeschlossen werden (z. B. /v1/k%76/...), und /v1/txn-Körper überspringt. POST /v1/operator/audit-hash gibt jetzt HTTP 413 für übergroße Körper zurück.
  • Agent: (Nur Enterprise) PUT /v1/kv/ wurde behoben, so dass fragmentierte Anforderungstexte durch kv_max_value_size begrenzt werden und mit der vorhandenen Content-Length-Prüfung übereinstimmen.
  • Proxycfg: Es wurde ein Goroutine- und Speicherleck behoben, bei dem die Überwachungen eines Proxys weiter liefen, nachdem sein Status unerwartet gestoppt wurde, weil das Ersetzen, die Registrierung oder das Schließen eines gestoppten Status sie nicht abbrach. [GH-23990]
  • Proxycfg: Ein Goroutine- und Speicherleck wurde behoben, bei dem transparente Proxys jedes Mal, wenn sich die Liste der importierten Dienste änderte, eine neue Integritätsüberwachung für jeden importierten Peer-Dienst registrierten und die Überwachung für entfernte Upstreams nie stoppten. [GH-23990]
  • Telemetrie: Stellen Sie Raft-, Serf- und Memberlist-Metriken in Release-Artefakten wieder her, indem Sie mit dem hashicorpmetrics-Tag erstellen. [GH-23813]
  • agent/xds: Es wurde ein Problem behoben, bei dem Cluster- und Peering-Anfragen, die von einem API-Gateway stammten, mit HTTP 403 Forbidden by Downstream Service RBAC Intentions abgelehnt wurden. Nachgestellte, durch Semikolons getrennte Felder in der Zertifikatskomponente client des Headers x-forwarded-client-cert (XFCC) (z. B. automatisch registrierte DNS-SANs) werden jetzt vom regulären RBAC-Prinzipalausdruck ordnungsgemäß akzeptiert. [GH-23920]
  • cli: (Nur Enterprise) consul intention create erstellt und ersetzt jetzt Absichten über die genaue (Konfigurationseintrags-) Absicht API, die von der Benutzeroberfläche verwendet wird, die nicht standardmäßige Admin-Partitionen unterstützt (z. B. -partition team-a). Metadaten pro Quelle (-meta) verwenden weiterhin die veraltete Legacy-Intention API und werden nur in der Standardpartition unterstützt; Das Kombinieren von -meta mit einer nicht standardmäßigen Partition schlägt jetzt mit einem eindeutigen, umsetzbaren Fehler fehl. Um Metadaten an Absichten in einer Admin-Partition anzuhängen, verwenden Sie einen service-intentions-Konfigurationseintrag mit der Eintragsebene Meta über consul config write.
  • connect: (nur Enterprise) Ausgehendes OBO nur für Upstreams auf Identitätsebene anhängen (ai-agent / mcp-server). Explizite HTTP-Upstreams zu Inferenz-Gateway- oder Inferenzmodell-Zielen erhalten nicht mehr „consul-obo-outbound“ und werden nicht mit „OBO-Zielgruppe nicht konfiguriert“ geschlossen.
  • connect: Es wurde ein Fehler behoben, bei dem Consul-Server den konfigurierten default_intention_policy für drei serverseitige Oberflächen – die Absichtsprüfung API (consul intention check, GET /v1/connect/intentions/check), die Service-Topologieansicht (Internal.ServiceTopology) und die transparente Proxy-Upstream-Erkennung (Internal.IntentionUpstreams) – ignorierten und stattdessen auf acl.default_policy zurückgriffen. Dies ändert das Verhalten nur, wenn default_intention_policy und acl.default_policy auf entgegengesetzte Werte eingestellt sind; Wenn sie zustimmen (oder default_intention_policy nicht gesetzt ist), gibt es keine Änderung. Bei default_intention_policy=deny und acl.default_policy=allow meldete die Prüfung API und die Topologie zuvor Verbindungen als erlaubt, obwohl sie verweigert wurden; Bei default_intention_policy=allow und acl.default_policy=deny versorgten transparente Proxy-Sidecars ihre Upstreams nicht ausreichend und erreichten möglicherweise nicht die Dienste, für die sie autorisiert waren. Die Durchsetzung der Envoy RBAC war nicht betroffen und wurde bereits berücksichtigt default_intention_policy.
