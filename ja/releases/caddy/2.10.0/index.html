caddy v2.10.0

#キャディv2.10.0 キャディ2.10登場！バグ修正の他に、このリリースの特徴は次のとおりです。

  • 暗号化 ClientHello (ECH): この新しいテクノロジは、TLS 接続の最後の平文部分 (接続先のドメイン名を含む ClientHello) を暗号化します。 ECH の ドラフト仕様 がほぼ完成したため、TLS でこのプライバシー機能をサポートできるようになりました。これは強力ですが微妙な機能です。当社の Web サイトにある ECH ドキュメント を読むことを強くお勧めします。
  • ポスト量子 (PQC) キー交換: Caddy は、標準化された x25519mlkem768 暗号化グループをデフォルトでサポートするようになりました。
  • ACME プロファイル: ACME プロファイルは、従来の CSR 方法よりも柔軟に証明書のプロパティを選択できるようにする実験的なドラフトです。たとえば、Let's Encrypt は、特定のプロファイルで 6 日間の証明書を発行します とします。 Caddy は最終的にそのプロファイルをデフォルトで使用する可能性があります。
  • Via ヘッダー: リバース プロキシは、重複した Server ヘッダーの代わりに Via ヘッダーを設定するようになりました。
  • グローバル DNS プロバイダー: DNS プロバイダー (ACME DNS チャレンジや ECH など) を必要とする構成のすべての部分でローカルに構成する必要がなく、使用するデフォルトの「グローバル」DNS モジュールを指定できるようになりました。これは Caddyfile の dns グローバル オプション、または JSON 構成では、tls アプリ構成の dns パラメーターです。
  • デフォルトで使用されるワイルドカード: 以前は、Caddy は構成内のすべてのドメインに対して文字通り個別の証明書を取得していました。ワイルドカードが存在する場合、個々の証明書を取得するのではなく、サブドメインに使用されるようになりました。この変更は、ECH によって提供されるサブドメイン プライバシーの新しい可能性によって動機付けられました。これは、Caddyfile の tls force_automate でオーバーライドできます。実験的な auto_https prefer_wildcard オプションは削除されました。
  • libdns 1.0 APIs: 多くの人は、ACME DNS の課題を解決したり、ダイナミック DNS を有効にしたりするために DNS プロバイダー モジュール を使用しています。これらは、DNS レコードを取得、設定、追加、削除するために libdns によって定義されたインターフェイスを実装します。 ECH で学んだ教訓を含む 5 年間の制作経験を経て、libdns API が更新され、1.0 ベータ版がタグ付けされました。 DNS プロバイダー パッケージは、互換性を保つためにコードを更新する必要があります。これは、将来の安定性と明確に定義されたセマンティクスを確保するのに役立ちます。いくつかのパッケージはすでに更新されているか、更新中です (いくつか例を挙げると、cloudflare、rfc2136、desec)。
  • グローバル dns 構成: Caddy 構成のいくつかのコンポーネントが DNS レコード (ACME チャレンジ、ECH パブリケーションなど) に影響を与える可能性があるため、DNS プロバイダー構成を 1 か所で指定するために使用できる新しい dns グローバル オプションが追加されました。これにより、すべてのドメインが単一の DNS プロバイダーによって管理されているサーバーの資格情報の繰り返しが防止されます。 これを可能にするために協力してくれた多くの貢献者に感謝します! :tada: :partying_face: :champagne: :警告: 従来、一部のディストリビューション/パッケージ マネージャー ポリシーに対応するために、Go のマイナー バージョンの最後の 2 つをサポートしてきましたが、現在は最新の Go のマイナー バージョンのみをサポートしています。新しい Go バージョンで追加されたプライバシーとセキュリティの利点 (量子後暗号など) は、ユーザー ベース全体を抑制したり、複数のコード コンパイル構成を維持したりするのではなく、できるだけ早く全員が利用できるようにする価値があります。

暗号化された ClientHello (ECH) の詳細

(これは簡単な概要です。完全なドキュメント を読むことをお勧めします。) 通常、TLS 接続を確立するとき、サーバー名 (ドメイン名、または「SNI」) はプレーンテキスト ClientHello で送信されます。 ECH では、実際のサーバー名は、選択した汎用 SNI を持つ「外部」ClientHello によって暗号化 (およびラップ) されます。同じサーバー上の多くのサイトが同じ外部 SNI を共有しているため、clients とサーバーの両方でドメイン名に関するプライバシーが強化されます。 Caddy は完全に自動化された ECH を実装しています。つまり、DNS プロバイダーと使用する外部/パブリック ドメイン名を指定するだけで、ECH 構成を生成 (そして [すぐに] (https://github.com/golang/go/issues/71920)、ローテーション)、発行、提供します。 完全に自動化された ECH には、Caddy バイナリに組み込まれた DNS モジュールが必要です。 ブラウザなどの client が ECH を使用できること、および使用するパラメータを認識するには、サーバーの ECH 構成を公開する必要があります。この構成には、パブリック名、暗号化パラメータ、および内部 ClientHello を暗号化するための公開キーが含まれています。慣例により、ブラウザは ech SvcParamKey を含む標準化された HTTPS タイプの DNS レコードを読み取ります。 Caddy は、保護されているすべてのドメインに対してこの DNS レコードを設定しますが、これを行うには、DNS プロバイダー モジュールが接続され、構成されている必要があります。すでに DNS ACME チャレンジを使用している場合は、すでに DNS プロバイダーがプラグインされているはずです。DNS モジュール を使用してソースから Caddy を構築する場合は、xcaddy を使用すると簡単です。例: $ xcaddy build --with github.com/caddy-dns/cloudflare ClientHello を有効にするために必要な最小限の構成は、ほとんどの状況でプライバシーの利点を最大化するため、_推奨_構成でもあります。必要なのは、ech グローバル オプションと DNS プロバイダーの指定だけです。 Cloudflare をネームサーバーとして使用する例を次に示します。 キャディファイル:

{
	debug  # not required; recommended while testing
	dns cloudflare {env.CLOUDFLARE_API_KEY}
	ech ech.example.net
}

example.com {
	respond "Hello there!"
}

これにより、ech.example.net というパブリック名ですべてのサイト (この場合は example.com) が保護されます。 (別の例として、Cloudflare はサービスを提供するすべてのサイトに cloudflare-ech.com を使用します。単一のパブリック ドメインを選択し、それを使用してすべてのサイトを保護することをお勧めします。) 選択した外部/パブリック名はサーバーを指す必要があります。 Caddy は、必要に応じて client の安全で信頼性の高い接続を促進するために、この名前の証明書を取得します。証明書がないと、client は安全でない接続を強いられるか、場合によってはまったく接続に失敗する可能性があり、脆弱なままになるだけでなく、サーバーのサイトの名前が公開される危険性もあります。 次に、Caddy は指定された DNS プロバイダーを使用して、さまざまなサイト名の ECH 構成を公開します。サイトのドメイン (ECH パブリック名ではない) の HTTPS タイプのレコードを作成 (または拡張) します。 DNS プロバイダー モジュールは独立して保守されており、HTTPS タイプのレコードとの互換性がテストされていない可能性があることに注意してください。問題が発生した場合は、モジュールのメンテナに連絡してください。 より高度な構成が必要な場合は、JSON 構成を使用できます (詳細については近日公開予定です。現時点では #6862 を参照するか、ソース コードを参照してください。または、caddy adapt を使用して Caddyfile を JSON に変換します)。

暗号化された ClientHello のテストと検証

まず、設定で ECH を有効にして (および DNS モジュールを使用して) Caddy が正常に実行されることを確認します。 ECH 構成が生成され、それがドメイン名に公開されていることを示すログが表示されるはずです。 ECH をサポートする client を使用する必要があります。 curl の一部のカスタム ビルドは有効であり、Firefox や最新の Chrome ベースのブラウザでも同様に有効ですが、最初に DNS-over-HTTPS または DNS-over-TLS を有効にする必要があります (明らかに、保護されたドメイン名を平文で DNS にクエリすると、ドメインが公開され、ECH の目的が無効になるためです)。 既存のドメイン名を再利用する場合は、DNS キャッシュをクリアします。 Firefox には、about:networking#dns でキャッシュに対してこれを行う方法があります。 適切な client を入手したら、Wireshark を使用して、サイトをロードするときにネットワーク パケットをキャプチャします。パケット キャプチャには、外部名/パブリック名のみが SNI (ServerName Indicator) 値として表示されるはずです。本当のサイト名が表示される場合は、ECH が正しく動作していません。client またはサーバーに問題がある可能性があります。バグを報告する前に、まずそれがサーバーの問題であることを特定してください。ただし、サーバーのバグは必ず報告してください。ありがとう！ (ECH は CNAME ドメインに対して自動的に公開されないため、ドメインにはゾーン内にレコードがすでに存在している必要があることに注意してください。)
