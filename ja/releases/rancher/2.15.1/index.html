#牧場主v2.15.1

v2.15.1 をリリース

[!重要]

  • Active Directory フェデレーション サービス (AD FS) を使用している場合、Rancher v2.10.1 以降にアップグレードすると認証に問題が発生し、手動介入が必要になる可能性があります。これらの問題は、AD FS 証明書利用者 Trust がメタデータから署名検証証明書を取得できないことが原因で発生します。詳細については、#48655 を参照してください。これらの問題は、次の 2 つの方法のいずれかで修正できます。

  • フェデレーション メタデータから証明書利用者 Trust 情報を更新します (証明書利用者 Trust → フェデレーション メタデータから更新…)。

  • 証明書を直接追加します (証明書利用者 Trust → プロパティ → 署名タブ → 追加 → 証明書を選択)。

Rancher v2.15.1 は、Rancher の最新のパッチ リリースです。これは、メンテナンス更新とバグ修正を導入するコミュニティ バージョン リリースです。

一般マイナー リリースの新機能の詳細については、v2.15.0 release notes を参照してください。

脆弱性に対するセキュリティ修正

このリリースでは、次のセキュリティ問題が解決されています。

牧場主

  • 高可用性 (マルチレプリカ) デプロイメントでアサーション リプレイ保護が無効になる、Rancher の SAML 認証ハンドラーのセキュリティ脆弱性を修正しました。各レプリカは消費されたアサーション ID を個別のメモリ内キャッシュで追跡するため、キャプチャされた SAML アサーションが他のレプリカに対して再生され、追加の認証済みセッションが被害者として作成される可能性があります。この修正により、すべてのレプリカにわたって消費されたアサーション ID が追跡されます。すべての SAML プロバイダーが影響を受けました。詳細については、CVE-2026-75034 を参照してください。
  • 参照されたプロジェクトが同じクラスターに属しているかどうかを検証せずに、プロジェクト シークレットが field.cattle.io/projectId アノテーションのみに基づいて名前空間に伝播する、Rancher プロジェクト スコープの secretsController のセキュリティ脆弱性を修正します。 1 つのダウンストリーム クラスター上で名前空間作成権限を持つ認証済みユーザーが、このアノテーションを偽装して、別のクラスター内の未承認のプロジェクトからプロジェクト シークレットを漏洩する可能性があります。コントローラーは、シークレットを伝播する前に、アノテーションが同じクラスター内のプロジェクトを参照していることを検証するようになりました。詳細については、CVE-2026-75033 を参照してください。
  • Rancher 命令型外部トークン API (ext.cattle.io/v1 トークン) のセキュリティ脆弱性を修正しました。この脆弱性では、認証されたユーザーは、細工されたラベル セレクターを提供し、トークン メタデータと保存されているベアラー トークン ハッシュを公開することで、他のユーザーのトークンを一覧表示して監視できます。ストアはユーザーごとのスコープを無条件に適用するようになり、呼び出し元には自分のトークンのみが表示され、読み取り応答は保存されたトークン ハッシュを返さなくなりました。詳細については、CVE-2026-75035 を参照してください。
  • GlobalRole リソースに対する委任された create または update 権限を持つユーザーが、任意の既存の ClusterRole (組み込み cluster-admin など) をターゲットとする authz.management.cattle.io/cr-name アノテーションを設定できるという、Rancher の GlobalRole コントローラーのセキュリティ脆弱性を修正しました。その後、コントローラーは所有権チェックを行わずにルールを上書きし、バインドされたすべてのプリンシパルからアクセス許可を剥奪し、ローカル管理クラスター上で永続的なクラスター全体の RBAC ロックアウトを引き起こします。詳細については、CVE-2026-71404 を参照してください。
  • 更新パスが User リソースの username、principalIds、および displayName フィールドの不変性を強制しなかった SUSE Rancher Norman /v3/users API のセキュリティ脆弱性を修正しました。 users に対する update アクセス許可を保持している呼び出し元は、ユーザーの外部プリンシパル ID を再バインドして、次回の外部ログイン時にアカウントの乗っ取りを可能にしたり、既存のロール バインディングにアクセス不能なままにするサービス拒否状態を作成したりする可能性があります。 API ストアおよびアドミッション Webhook レイヤーは、これらの ID フィールドに対する作成後の変更を拒否するように更新されました。詳細については、CVE-2026-71403 を参照してください。

フリート

  • フリート コントローラーによって評価されたテンプレートがネットワーク リソースに到達する可能性がある、フリートの Helm テンプレートの前処理におけるセキュリティの脆弱性を修正しました。 untrusted バンドル コンテンツを提供できるユーザーは、クラスターのメタデータと、コントローラーから到達可能なホストに関する情報を公開できます。フリートは、Helm テンプレート値にネットワーク アクセスが必要なバンドルを拒否し、対応する GitRepo のエラーを報告するようになりました。詳細については、CVE-2026-75036 を参照してください。
  • エージェントが開始したクラスター登録中にエージェントによって提供されたクラスター ラベルが、バンドル ターゲティングに使用される予約された management.cattle.io/ ラベルを含む、結果の Cluster オブジェクトに適用されるフリートのセキュリティ脆弱性を修正しました。複数の trust ドメインがフリート ワークスペースの名前空間を共有する展開では、これにより、登録中のクラスターが別のテナントの Bundle または GitRepo ターゲットと一致し、そのテナントのマニフェストと解決された値のシークレットを受信できるようになります。フリートは、エージェントが開始した登録時に提供された予約済みラベルを破棄するようになりました。 Rancher はマネージャーが開始する登録を使用するため、スタンドアロン Rancher デプロイメントはデフォルト構成の影響を受けません。詳細については、CVE-2026-93538 を参照してください。
  • namespaceLabels および namespaceAnnotations を通じてバンドルによって要求された名前空間ラベルと注釈が、バンドルが固定されているサービス アカウントの承認なしに適用されるフリートのセキュリティ脆弱性を修正しました。マルチテナント展開では、これによりバンドルは、自身の ID では変更が許可されていない名前空間メタデータを変更できるようになりました。名前空間の更新は展開のサービス アカウントとして実行され、ダウンストリーム Kubernetes RBAC によって管理されるようになりました。詳細については、CVE-2026-93540 を参照してください。

インストール/アップグレードに関する注意事項

Rancher を初めてインストールする場合は、環境が インストール要件 を満たしている必要があります。

[!重要]

  • Rancher では、実行するクラスターで Kubernetes API 集約レイヤー が有効になっている必要があります。これは、Rancher が独自の拡張 API サーバーを登録することにより、追加の API で Kubernetes を拡張するためです。この Rancher バージョンの K8s ディストリビューション (RKE2/K3s) でサポートされている Kubernetes のすべてのバージョンでは、デフォルトでアグリゲーション レイヤーが構成され有効になっていることに注意してください。

  • 詳細については、Extension API サーバーのドキュメント および #50400 を参照してください。

  • Rancher Kubernetes エンジン (RKE/RKE1) は 2025 年 7 月 31 日をもってサポート終了となりました。 Rancher バージョン 2.12.0 以降では、ダウンストリーム RKE1 クラスターのプロビジョニングまたは管理がサポートされなくなりました。継続的なサポートとセキュリティ更新を確保するために、RKE1 クラスターを RKE2 に再プラットフォーム化することをお勧めします。移行の詳細については、こちら をご覧ください。

  • Rancher には RKE1 リソースのアップグレード前の検証チェックがあり、失敗すると RKE1 リソースが存在する場合はリストされます。詳細については、#50286 を参照してください。

  • Rancher v2.12.0 以降にアップグレードする前に、ノード上の利用可能なディスク容量を確認し、それに応じて計画を立て、潜在的なディスク圧力やポッドのエビクションの問題を回避することが重要です。

  • 詳細については、UI サーバー側のページネーション - ディスク領域のドキュメント を参照してください。

  • Rancher には、Rancher インストールの API 監査ログ用の AUDIT_LOG_ENABLED という有効化オプションが追加されました。

  • Rancher バージョン 2.11.x 以前では、AUDIT_LEVEL のみを設定でき、デフォルトのログ レベル (0) では監査ログが無効になります。 Rancher バージョン 2.12.x 以降では、デフォルトのログ レベル (0) にはログ リクエストとレスポンスのメタデータのみが含まれるようになり、AUDIT_LOG_ENABLED の構成時に設定できるようになりました。 Helm 経由でインストールまたはアップグレードする場合は、Helm コマンド --set auditLog.enabled=true --set auditLog.level=0 の設定を適用することで、API 監査ログを有効にし、ログ レベルを指定できます。 API 監査ログを有効にしてシステム イベントを記録する ドキュメントおよび #48941 を参照してください。

画像アーティファクトの変更

Rancher v2.12.0、v2.11.4、v2.10.8 では、画像アーティファクト ダイジェストの名前が変更されました。この変更が行われるまでは、互換性の理由から、オペレーティング システムおよびアーキテクチャごとに個別のイメージ ダイジェスト ファイルが維持されていました。この変更により、各オペレーティング システムに対して 1 つのファイルのみが提供されるようになります。

  • rancher-images-digests-linux-amd64.txt および rancher-images-digests-linux-arm64.txt ファイルの名前は rancher-images-digests-linux.txt に変更されます。

  • rancher-images-digests-windows-ltsc2019.txt および rancher-images-digests-windows-ltsc2022.txt ファイルの名前は rancher-images-digests-windows.txt に変更されます。

アップグレード要件

  • バックアップの作成: Rancher をアップグレードする前に バックアップを作成 します。アップグレード後に Rancher をロールバックするには、まず Rancher をバックアップし、以前の Rancher バージョンに復元する必要があります。 Rancher はバックアップ作成時と同じ状態に復元されるため、アップグレード後の変更は復元後には含まれません。

  • Helm バージョン要件:

    • Rancher 2.12.x 以降を管理するには、Helm client をバージョン 3.18 以降にアップグレードする必要があります。

    • この変更は、このリリースで追加された Kubernetes 1.33 サポートを反映するために必要です。

    • 現在、公式の Helm バージョン サポート ポリシー では、Helm 3.18 のみが Rancher 2.12 の適切な Kubernetes バージョン範囲をサポートしていると規定しています。

  • CNI 要件:

  • Kubernetes v1.19 以降では、さまざまな CNI プラグインと互換性がないため、firewalld を無効にします。 #28840 を参照してください。

    • バックエンド パケット フィルターとして nf_tables を使用する Linux ディストリビューション (SLES 15、RHEL 8、Ubuntu 20.10、Debian 10 以降など) をアップグレードまたはインストールする場合、Flannel v0.13.0 を入手するには、RKE v1.19.2 以降にアップグレードします。フランネル v0.13.0 は nf_tables をサポートします。フランネル #1317 を参照してください。

  • エアギャップ環境の要件:

    • エアギャップのある Rancher インスタンスの前でプロキシを使用する場合は、追加のパラメータを NO_PROXY に渡す必要があります。 ドキュメント を参照し、#2725 を発行してください。

    • Rancher を Docker とともにエアギャップ環境にインストールする場合、K3s ドキュメント に示されているように、カスタム registries.yaml ファイルを docker run コマンドに指定する必要があります。レジストリに証明書がある場合は、それらも指定する必要があります。 #28969 を参照してください。

Rancher Helm チャートのバージョン

Rancher v2.6.0 以降の Apps & Marketplace UI では、多くの Rancher Helm チャートに 100 で始まるメジャー バージョンの名前が付いています。これにより、アップストリームの変更と Rancher の変更が同時に発生してバージョンの増分が競合することが回避されます。これは、Helm の要件であるセマンティック バージョニング (SemVer) にも準拠しています。チャートのアップストリーム バージョン番号は、ビルド メタデータで確認できます (例: 100.0.0+up2.1.0)。 #32294 を参照してください。

  • ランチャー v2.15.0:

    • v2prov でネイティブ CAPI インフラストラクチャ プロバイダーを使用する場合、Rancher はブートストラップ クラウド構成を Jinja 形式 で生成するようになりました。 v2prov を使用する通常のノード ドライバーのユーザー データは影響を受けません。 #53777 を参照してください。

以前の Rancher の動作変更 - 継続的デリバリー (フリート)

  • ランチャー v2.15.0:

  • 非推奨: フリートは将来のリリースで GitRepoRestriction のサポートを削除し、マルチテナント環境を構成するためのポリシー リソースの使用が唯一のオプションになります。 #55652 を参照してください。

    • 非推奨: 未認証 Webhook 呼び出しのフリート サポートは将来のリリースで削除され、Webhook Secret のセットアップが唯一のオプションになります。 #55633 を参照してください。

長年にわたる既知の問題 - クラスターのプロビジョニング

  • すべてのクラスター ツールを強化されたクラスターにインストールできるわけではありません。

  • ランチャー v2.8.1:

    • etcd スナップショットの復元に失敗した後、CAPR 管理のクラスターに新しい etcd/コントロールプレーン ノードを登録しようとすると、ノードが永続的な一時停止状態になり、エラー メッセージ [ERROR] 000 received while downloading Rancher connection information. Sleeping for 5 seconds and trying again が表示されることがあります。回避策として、kubectl edit clusters.cluster clustername -n fleet-default を実行し、spec.unpaused を false に設定することでクラスターの一時停止を解除できます。 #43735 を参照してください。

長年にわたる既知の問題 - RKE2 プロビジョニング

  • ランチャー v2.7.7:

    • さまざまなコンポーネントのバックオフ ロジックにより、ダウンストリームでプロビジョニングされた K3 および RKE2 クラスターは、移行後に アクティブ ステータスを再達成するまでに時間がかかる場合があります。ダウンストリーム クラスターがまだ更新中であるか、移行直後にエラー状態にあることが確認された場合は、クラスター自体の解決を試行させてください。これが完了するまでに最大 1 時間かかる場合があります。 #34518 および #42834 を参照してください。

  • ランチャー v2.7.6:

    • 追加された (組み込みではない) カスタム ノード ドライバーを使用して RKE2/K3s クラスターをプロビジョニングすると、プロビジョニングが失敗します。回避策として、アクティブ化後に追加されたノードドライバーを修正します。 #37074 を参照してください。

長年にわたる既知の問題 - K3s プロビジョニング

  • ランチャー v2.7.2:

    • クラスターに Error 状態のノードが含まれている場合でも、クラスターは Updating 状態のままになります。 #39164 を参照してください。

    • Rancher UI でネームスペースまたはプロジェクトを削除した後、ネームスペースまたはプロジェクトは表示されたままになります。回避策として、ページを更新します。 #12220 を参照してください。

  • ランチャー v2.9.2:

    • システム モードのノード プールには少なくとも 1 つのノードが必要ですが、Rancher UI では最小ノード数が 0 まで許可されます。 UI を通じてゼロの最小ノード数を入力すると、無効なパラメーター エラーによりクラスターの作成が失敗する可能性があります。このエラーの発生を防ぐには、ノード数と少なくとも等しい最小ノード数を入力します。 #11922 を参照してください。

  • ランチャー v2.7.7:

    • Rancher UI でクラスターを作成する場合、Cluster Name フィールドでアンダースコア _ を使用することはできません。 #9416 を参照してください。

  • ランチャー v2.6.4:

    • 新しいワークロードの作成時に、Deployment securityContext セクションが欠落しています。これにより、ポッド セキュリティ ポリシー サポートが有効になっている場合、ポッドが起動できなくなります。 #4815 を参照してください。

長年にわたる既知の問題 - EKS

  • ランチャー v2.7.0:

    • Rancher v2.7 上の Kubernetes v1.21 以下の EKS クラスターはアップグレードできません。 #39392 を参照してください。

長年にわたる既知の問題 - 認証

  • ランチャー v2.9.0:

    • OpenID Connect プロバイダーのサポートにはいくつかの既知の問題があります。

      • 汎用 OIDC 認証プロバイダーが有効になっており、認証プロバイダー ユーザーをクラスターまたはプロジェクトに追加しようとすると、ドロップダウン検索バーにユーザーが表示されません。 OIDC 認証プロバイダーだけでは検索できないため、これは予期される動作です。 #46104 を参照してください。

      • 汎用 OIDC 認証プロバイダーが有効になっている場合、ユーザー名によってクラスター/プロジェクトに追加された認証プロバイダー ユーザーは、ログイン時にリソースにアクセスできません。ユーザーは、ユーザー ID によって追加された場合にのみ、ログイン時にリソースにアクセスできます。 #46105 を参照してください。

      • 汎用 OIDC 認証プロバイダーが有効で、ネストされたグループ内の認証プロバイダー ユーザーが Rancher にログインしている場合、ユーザーがプロジェクトを作成しようとすると、次のエラーが表示されます: projectroletemplatebindings.management.cattle.io is forbidden: User "u-gcxatwsnku" cannot create resource "projectroletemplatebindings" in API group "management.cattle.io" in the namespace "p-9t5pg"。ただし、プロジェクトはまだ作成中です。 #46106 を参照してください。

長年にわたる既知の問題 - Rancher Webhook

  • ランチャー v2.7.2:

    • Webhook はすべてのダウンストリーム クラスターにインストールされます。この機能では、ユーザーが発生する可能性のあるいくつかの問題があります。

      • Rancher v2.7.2 以降のバージョンから v2.7.2 より前の Rancher バージョンにロールバックすると、Webhook はダウンストリーム クラスターに残ります。 Webhook は Rancher の特定のバージョンと 1 対 1 の互換性があるように設計されているため、ダウンストリームで予期しない動作が発生する可能性があります。 Rancher チームは、ロールバックの完了後 (v2.7.2 より前の Rancher バージョンの実行後) に使用する スクリプト を開発しました。これにより、影響を受けるダウンストリーム クラスターから Webhook が削除されます。 #40816 を参照してください。

長年にわたる既知の問題 - 仮想化管理 (ハーベスター)

  • ランチャー v2.13.1:

    • Harvester v1.6.1 を使用中に Rancher v2.13.1 以降にアップグレードすると、ユーザーは Harvester クラウド プロバイダーを使用するダウンストリーム クラスターのロード バランサーで問題が発生する可能性があるため、次の 回避策 を実行して、kube-vip によって管理される IP/インターフェイスを使用しないように Calico に指示する必要があります。 #9767 を参照してください。

  • ランチャー v2.7.2:

    • Rancher v2.7.2 を Harvester v1.1.1 クラスターとともに使用している場合、ゲスト クラスターの展開または更新時に Harvester クラウド プロバイダーを選択できません。 Harvester release notes には、この問題を解決する方法が記載されています。 #3750 を参照してください。

長年にわたる既知の問題 - バックアップ/復元

  • Rancher バックアップ機能を使用してクラスターに移行する場合、サーバー URL を別の場所に変更することはできません。同じ URL を引き続き使用する必要があります。

  • 牧場主 v2.13.0:

    • バックアップおよびリストア オペレーター (BRO) を使用して Rancher v2.13.0 から v2.12.3 へのロールバックを実行すると、リストアが正常に完了しません。 #844 を参照してください。この問題を回避するには、復元を実行する前に、Rancher デプロイメントをスケールダウンし、Webhook チャートをアンインストールする必要があります。詳細については、こちらのナレッジベース記事を参照してください。

  • ランチャー v2.7.7:

  • さまざまなコンポーネントのバックオフ ロジックにより、ダウンストリームでプロビジョニングされた K3 および RKE2 クラスターは、移行後に アクティブ ステータスを再達成するまでに時間がかかる場合があります。ダウンストリーム クラスターがまだ更新中であるか、移行直後にエラー状態にあることが確認された場合は、クラスター自体の解決を試行させてください。これが完了するまでに最大 1 時間かかる場合があります。 #34518 および #42834 を参照してください。
