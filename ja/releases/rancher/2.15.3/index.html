#牧場主v2.15.3

v2.15.3 をリリース

[!重要]

  • Active Directory フェデレーション サービス (AD FS) を使用している場合、Rancher v2.10.1 以降にアップグレードすると認証に問題が発生し、手動介入が必要になる可能性があります。これらの問題は、AD FS 証明書利用者 Trust がメタデータから署名検証証明書を取得できないことが原因で発生します。詳細については、#48655 を参照してください。これらの問題は、次の 2 つの方法のいずれかで修正できます。

  • フェデレーション メタデータから証明書利用者 Trust 情報を更新します (証明書利用者 Trust → フェデレーション メタデータから更新…)。

  • 証明書を直接追加します (証明書利用者 Trust → プロパティ → 署名タブ → 追加 → 証明書を選択)。

Rancher v2.15.3 は、Rancher の最新のパッチ リリースです。これは、メンテナンス更新とバグ修正を導入するコミュニティ バージョン リリースです。

一般マイナー リリースの新機能の詳細については、v2.15.0 release notes を参照してください。

脆弱性に対するセキュリティ修正

このリリースでは、次のセキュリティ問題が解決されています。

牧場主

  • リクエストの転送を妨げない場所で宛先ホワイトリストが評価される、Rancher メタ プロキシ エンドポイントのセキュリティ脆弱性を修正しました。認証されたユーザーにより、Rancher サーバーがホワイトリストでブロックされる内部サービスにリクエストを送信し、応答を受信する可能性があります。ホワイトリストはリクエスト ハンドラーで強制されるようになり、接続が確立される前に許可されていない宛先を拒否します。詳細については、CVE-2026-88809 を参照してください。
  • GlobalRole の inheritedNamespacedRules フィールドで特権昇格がチェックされなかった Rancher の RBAC 検証のセキュリティ脆弱性を修正しました。グローバル ロールおよびグローバル ロール バインディングを管理するための委任されたアクセス許可を持つユーザーは、自分の権限を超えるアクセス許可をダウンストリーム クラスターに付与する可能性があります。 GlobalRole および GlobalRoleBinding アドミッション Webhook は、他の権限を保持するフィールドと同じ方法でこのフィールドを検証するようになりました。詳細については、CVE-2026-88810 を参照してください。
  • 呼び出し元自身の Rancher 認証情報が、サードパーティのクラウド プロバイダー ホストに転送されるリクエストから一貫して削除されない、Rancher Manager メタ プロキシのセキュリティ脆弱性を修正しました。サインインしているユーザーのセッション資格情報は、プロビジョニング ビューの通常の使用中にクラウド プロバイダーに送信される可能性があり、プロキシの資格情報選択ヘッダーを省略すると、API client の Rancher トークンが送信される可能性があります。プロキシは、すべてのリクエスト パスで呼び出し元の資格情報を削除します。詳細については、CVE-2026-88811 を参照してください。
  • ローカル クラスター シェルを保護する承認チェックが、到達可能なすべての API ルートに適用されなかった Rancher のセキュリティ脆弱性を修正しました。 local クラスターに対する権限を持たないユーザーも含め、認証されたユーザーが管理クラスター上の特権のないシェル ポッドを取得し、予期された管理プレーンの分離が破壊される可能性があります。認可チェックは、すべてのリクエスト フォームに対して一貫して適用されるようになりました。詳細については、CVE-2026-104623 を参照してください。

＃＃＃ 艦隊

  • 一般ユーザーが作成したフリート クラスター オブジェクトが Rancher 管理 (local) クラスターの管理資格情報を参照できるという、フリートのエージェント管理コントローラーの権限昇格の脆弱性を修正しました。これにより、ローカル クラスターに対する権限を持たず、デフォルトの user グローバル ロールのみを保持する認証済みユーザーが、Rancher 管理クラスター、つまりすべての管理対象クラスターに対するクラスター管理者を取得できるようになりました。フリートは、参照元の名前空間で使用するためにシークレットにラベルが付けられている場合にのみ、別の名前空間からの kubeconfig シークレットを受け入れ、独自のシステム クラスターの管理クラスターにのみエージェントをデプロイするようになりました。詳細については、CVE-2026-94290 を参照してください。
  • クラスターの登録中に要求されたクラスター ID が、リクエストに使用された登録トークンにバインドされていなかったフリートのセキュリティ脆弱性を修正しました。別のクラスターの client 識別子を知っている有効なワークスペース登録トークンの所有者は、そのクラスターのフリート管理名前空間の資格情報を取得し、その正規のエージェントを妨害する可能性があります。フリートは、クラスターが登録されている登録トークンを記録し、異なるトークンで同じクラスター ID を要求する登録リクエストを拒否するようになりました。詳細については、CVE-2026-104615 を参照してください。

詳細については、Rancher の ドキュメント または Rancher の GitHub リポジトリ のセキュリティ アドバイザリと CVE ページを参照してください。

牧場主の将軍

主要なバグ修正

  • 環境変数を使用して構成された Rancher 設定で、環境変数が削除された後も古い値と source: env 属性が保持される問題を修正しました。環境変数が削除されると、Rancher は起動時に保存されている環境ソースと値をクリアするようになりました。その後、設定はデフォルト値に戻ります。 #58075 を参照してください。

インストール/アップグレードに関する注意事項

Rancher を初めてインストールする場合は、環境が インストール要件 を満たしている必要があります。

[!重要]

  • Rancher では、実行するクラスターで Kubernetes API 集約レイヤー が有効になっている必要があります。これは、Rancher が独自の拡張 API サーバーを登録することにより、追加の API で Kubernetes を拡張するためです。この Rancher バージョンの K8s ディストリビューション (RKE2/K3s) でサポートされている Kubernetes のすべてのバージョンでは、デフォルトでアグリゲーション レイヤーが構成され有効になっていることに注意してください。

  • 詳細については、Extension API サーバーのドキュメント および #50400 を参照してください。

  • Rancher Kubernetes エンジン (RKE/RKE1) は 2025 年 7 月 31 日をもってサポート終了となりました。 Rancher バージョン 2.12.0 以降では、ダウンストリーム RKE1 クラスターのプロビジョニングまたは管理がサポートされなくなりました。継続的なサポートとセキュリティ更新を確保するために、RKE1 クラスターを RKE2 に再プラットフォーム化することをお勧めします。移行の詳細については、こちら をご覧ください。

  • Rancher には RKE1 リソースのアップグレード前の検証チェックがあり、失敗すると RKE1 リソースが存在する場合はリストされます。詳細については、#50286 を参照してください。

  • Rancher v2.12.0 以降にアップグレードする前に、ノード上の利用可能なディスク容量を確認し、それに応じて計画を立て、潜在的なディスク圧力やポッドのエビクションの問題を回避することが重要です。

  • 詳細については、UI サーバー側のページネーション - ディスク領域のドキュメント を参照してください。

  • Rancher には、Rancher インストールの API 監査ログ用の AUDIT_LOG_ENABLED という有効化オプションが追加されました。

  • Rancher バージョン 2.11.x 以前では、AUDIT_LEVEL のみを設定でき、デフォルトのログ レベル (0) では監査ログが無効になりました。 Rancher バージョン 2.12.x 以降では、デフォルトのログ レベル (0) にはログの要求と応答のメタデータのみが含まれるようになり、AUDIT_LOG_ENABLED の構成時に設定できるようになりました。 Helm 経由でインストールまたはアップグレードする場合は、Helm コマンド --set auditLog.enabled=true --set auditLog.level=0 の設定を適用することで、API 監査ログを有効にし、ログ レベルを指定できます。 API 監査ログを有効にしてシステム イベントを記録する ドキュメントおよび #48941 を参照してください。

画像アーティファクトの変更

Rancher v2.12.0、v2.11.4、v2.10.8 では、画像アーティファクト ダイジェストの名前が変更されました。この変更が行われるまでは、互換性の理由から、オペレーティング システムおよびアーキテクチャごとに個別のイメージ ダイジェスト ファイルが維持されていました。この変更により、各オペレーティング システムに対して 1 つのファイルのみが提供されるようになります。

  • rancher-images-digests-linux-amd64.txt および rancher-images-digests-linux-arm64.txt ファイルの名前は rancher-images-digests-linux.txt に変更されます。

  • rancher-images-digests-windows-ltsc2019.txt および rancher-images-digests-windows-ltsc2022.txt ファイルの名前は rancher-images-digests-windows.txt に変更されます。

アップグレード要件

  • バックアップの作成: Rancher をアップグレードする前に、バックアップを作成してください。アップグレード後に Rancher をロールバックするには、まず Rancher をバックアップし、以前の Rancher バージョンに復元する必要があります。 Rancher はバックアップ作成時と同じ状態に復元されるため、アップグレード後の変更は復元後には含まれません。

  • Helm バージョン要件:

    • Rancher 2.12.x 以降を管理するには、Helm client をバージョン 3.18 以降にアップグレードする必要があります。

    • この変更は、このリリースで追加された Kubernetes 1.33 サポートを反映するために必要です。

    • 現在、公式の Helm バージョン サポート ポリシー では、Helm 3.18 のみが Rancher 2.12 の適切な Kubernetes バージョン範囲をサポートすると規定しています。

  • CNI 要件:

    • Kubernetes v1.19 以降では、さまざまな CNI プラグインと互換性がないため、firewalld を無効にします。 #28840 を参照してください。

    • バックエンド パケット フィルターとして nf_tables を使用する Linux ディストリビューション (SLES 15、RHEL 8、Ubuntu 20.10、Debian 10 以降など) をアップグレードまたはインストールする場合、Flannel v0.13.0 を入手するには、RKE v1.19.2 以降にアップグレードします。フランネル v0.13.0 は nf_tables をサポートします。フランネル #1317 を参照してください。

  • エアギャップ環境の要件:

    • エアギャップのある Rancher インスタンスの前でプロキシを使用する場合は、追加のパラメータを NO_PROXY に渡す必要があります。 ドキュメント を参照し、#2725 を発行してください。

  • When installing Rancher with Docker in an air-gapped environment, you must supply a custom registries.yaml file to the docker run command, as shown in the K3s documentation.レジストリに証明書がある場合は、それらも指定する必要があります。 #28969 を参照してください。

Rancher Helm チャートのバージョン

Rancher v2.6.0 以降の Apps & Marketplace UI では、多くの Rancher Helm チャートに 100 で始まるメジャー バージョンの名前が付いています。 This avoids simultaneous upstream changes and Rancher changes from causing conflicting version increments.これは、Helm の要件であるセマンティック バージョニング (SemVer) にも準拠しています。 You can see the upstream version number of a chart in the build metadata, for example: 100.0.0+up2.1.0. #32294 を参照してください。

長年にわたる既知の問題 - クラスターのプロビジョニング

  • ランチャー v2.15.1:

    • UI からネイティブ CAPI インフラストラクチャ プロバイダを使用して v2prov クラスタを作成または編集すると、障害状況によっては、管理クラスタ内に未使用のインフラストラクチャ リソースが残る可能性があり、手動でクリーンアップする必要があります。 #55705 を参照してください。

  • ランチャー v2.15.0:

    • インポートされたクラスターは、切断中に登録トークンがローテーションされ、再接続する前に猶予期間が終了する場合、Rancher に再接続できません。クラスター エージェントは、応答本文 cluster not found を含む 400 Bad Request をログに記録します。回避策として、ダウンストリーム クラスターの [クラスターの 登録] タブから登録コマンドを再実行します。この問題を回避するには、予想されるダウンタイムをカバーするために crt-default-grace-period-minutes 設定を増やすか、crt-token-ttl-rotation 機能フラグを無効にします。 #57078 を参照してください。

  • すべてのクラスター ツールを強化されたクラスターにインストールできるわけではありません。

  • ランチャー v2.8.1:

    • etcd スナップショットの復元に失敗した後、CAPR 管理のクラスターに新しい etcd/コントロールプレーン ノードを登録しようとすると、ノードが永続的な一時停止状態になり、エラー メッセージ [ERROR] 000 received while downloading Rancher connection information. Sleeping for 5 seconds and trying again が表示されることがあります。回避策として、kubectl edit clusters.cluster clustername -n fleet-default を実行し、spec.unpaused を false に設定することでクラスターの一時停止を解除できます。 #43735 を参照してください。

長年にわたる既知の問題 - RKE2 プロビジョニング

  • ランチャー v2.7.7:

    • さまざまなコンポーネントのバックオフ ロジックにより、ダウンストリームでプロビジョニングされた K3 および RKE2 クラスターは、移行後に アクティブ ステータスを再達成するまでに時間がかかる場合があります。ダウンストリーム クラスターがまだ更新中であるか、移行直後にエラー状態にあることが確認された場合は、クラスター自体の解決を試行させてください。これが完了するまでに最大 1 時間かかる場合があります。 #42834 を参照してください。

  • ランチャー v2.7.6:

長年にわたる既知の問題 - EKS

  • ランチャー v2.7.0:

    • Rancher v2.7 上の Kubernetes v1.21 以下の EKS クラスターはアップグレードできません。 #39392 を参照してください。

長年にわたる既知の問題 - 認証

  • ランチャー v2.9.0:

  • OpenID Connect プロバイダーのサポートにはいくつかの既知の問題があります。

    • 汎用 OIDC 認証プロバイダーが有効になっており、認証プロバイダー ユーザーをクラスターまたはプロジェクトに追加しようとすると、ドロップダウン検索バーにユーザーが表示されません。 OIDC 認証プロバイダーだけでは検索できないため、これは予期される動作です。 #46104 を参照してください。

    • 汎用 OIDC 認証プロバイダーが有効になっている場合、ユーザー名によってクラスター/プロジェクトに追加された認証プロバイダー ユーザーは、ログイン時にリソースにアクセスできません。ユーザーは、ユーザー ID によって追加された場合にのみ、ログイン時にリソースにアクセスできます。 #46105 を参照してください。

    • 汎用 OIDC 認証プロバイダーが有効で、ネストされたグループ内の認証プロバイダー ユーザーが Rancher にログインしている場合、ユーザーがプロジェクトを作成しようとすると、次のエラーが表示されます: projectroletemplatebindings.management.cattle.io is forbidden: User "u-gcxatwsnku" cannot create resource "projectroletemplatebindings" in API group "management.cattle.io" in the namespace "p-9t5pg"。ただし、プロジェクトはまだ作成中です。 #46106 を参照してください。

長年にわたる既知の問題 - Rancher Webhook

  • ランチャー v2.7.2:

    • Webhook はすべてのダウンストリーム クラスターにインストールされます。この機能では、ユーザーが発生する可能性のあるいくつかの問題があります。

      • Rancher v2.7.2 以降のバージョンから v2.7.2 より前のバージョンの Rancher にロールバックすると、Webhook はダウンストリーム クラスターに残ります。 Webhook は Rancher の特定のバージョンと 1 対 1 の互換性があるように設計されているため、ダウンストリームで予期しない動作が発生する可能性があります。 Rancher チームは、ロールバックの完了後 (つまり、v2.7.2 より前の Rancher バージョンの実行後) に使用する スクリプト を開発しました。これにより、影響を受けるダウンストリーム クラスターから Webhook が削除されます。 #40816 を参照してください。

長年にわたる既知の問題 - 仮想化管理 (ハーベスター)

  • ランチャー v2.13.1:

    • Harvester v1.6.1 を使用中に Rancher v2.13.1 以降にアップグレードすると、ユーザーは Harvester クラウド プロバイダーを使用するダウンストリーム クラスターのロード バランサーで問題が発生する可能性があるため、次の 回避策 を実行して、kube-vip によって管理される IP/インターフェイスを使用しないように Calico に指示する必要があります。 #9767 を参照してください。

  • ランチャー v2.7.2:

    • Rancher v2.7.2 を Harvester v1.1.1 クラスターとともに使用している場合、ゲスト クラスターの展開または更新時に Harvester クラウド プロバイダーを選択できません。 Harvester release notes には、この問題を解決する手順が記載されています。 #3750 を参照してください。

長年にわたる既知の問題 - バックアップ/復元

  • Rancher バックアップ機能を使用してクラスターに移行する場合、サーバー URL を別の場所に変更することはできません。同じ URL を引き続き使用する必要があります。

  • ランチャー v2.13.0:

    • バックアップおよびリストア オペレーター (BRO) を使用して Rancher v2.13.0 から v2.12.3 へのロールバックを実行すると、リストアが正常に完了しません。 #844 を参照してください。この問題を回避するには、復元を実行する前に、Rancher デプロイメントをスケールダウンし、Webhook チャートをアンインストールする必要があります。詳細については、こちらのナレッジベース記事を参照してください。

  • ランチャー v2.7.7:

  • さまざまなコンポーネントのバックオフ ロジックにより、ダウンストリームでプロビジョニングされた K3 および RKE2 クラスターは、移行後に アクティブ ステータスを再達成するまでに時間がかかる場合があります。ダウンストリーム クラスターがまだ更新中であるか、移行直後にエラー状態にあることが確認された場合は、クラスター自体の解決を試行させてください。これが完了するまでに最大 1 時間かかる場合があります。 #42834 を参照してください。
