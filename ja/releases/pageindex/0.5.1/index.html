PageIndex v0.5.1

パッチ 公開日2026年11月3日 出典VectifyAI/PageIndex 英語原文

このページは機械翻訳です。内容は必ず英文原文をご確認ください。

ページインデックス v0.5.1

  • ベクター RAG より 安価: インデックスとクエリの両方で。
  • 高速: ツリーはレイアウト統計から作成されます。
  • 統合 SDK: ベクターレス RAG。 ローカル または クラウド、インデックスとチャット用。
  • Claude サブスクリプションで実行されます。 インデックス、チャット、エージェント統合、1 台の client。 ローカル モードでは、サーバー、ベクトル DB、PageIndex API キーは必要ありません。
client = PageIndexClient()
client.submit_document("report.pdf")
client.chat("What does the report conclude?")

ハイライト

  • フラッシュ エンジン: ローカルのデフォルト (mode="standard" は従来の LLM パイプラインを保持します)。埋め込みブックマークは、trustworthy の場合に消費され、ツリーの最適化がデフォルトでオンになっています。optimize="merge" は確定的な LLM フリー パスの場合、"full" (デフォルト) は LLM 拡張を追加します。これにより、一度に 1 往復するのではなくノードのウェーブが同時に実行されます。
  • ローカルとクラウドの 1 つの完全なサーフェス: PageIndexLocalClient(storage_path=...) はクラウドと同じ client です。送信、ツリー、ページ コンテンツ、チャット、およびエージェント ツールはすべて両方のモードに存在するため、コードは変更されずにそれらの間で移動します。
  • クラウド ドキュメント、独自のモデル: api_key はドキュメントの保存場所を決定します。構成されたチャット モデルによって誰が応答するかが決まり、その 2 つが組み合わされます。 PageIndexClient(api_key="pi-...", chat_model="openai/gpt-5.2") は、ライブ クラウド ツール セット上で同じインプロセス ドキュメント QA エンジンを実行します。ページのコンテンツは、認証情報に基づいてプロセスを介してプロバイダーに送信されます。 doc_id はプロンプト レベルをターゲットとします。 enable_citations は管理されたチャットに残ります。
  • エージェント統合: クラウド MCP ツール コントラクト、インプロセス — client.agent_tools() (プレーン関数)、as_openai_tools()、as_anthropic_tools()、as_claude_mcp()、さらにワンコール openai_agent_config() / anthropic_runner_config() / claude_agent_config() バンドルおよびシステム プロンプト用 agent_instructions()。クラウド clients は、MCP ブリッジ経由でライブ サーバー ツール セットを取得します (デフォルトでは読み取り専用エンドポイント)。ローカルの client は、同じスキーマとエンベロープを持つインプロセス サブセットを取得します。エージェント プロンプトのポートは変更されません。
  • チャット サーフェス: chat() — 任意のバックエンドでの質問、回答。 chat(stream=True) は、テキストに織り込まれた思考やツールの呼び出し、または .events を介した入力されたイベントとして、実行が起こったときに表示します。 chat(protocol="responses" | "messages") は、そのプロトコル独自の形状を使用して OpenAI レスポンスまたは Anthropic メッセージ API をネイティブに駆動し、chat_completions() は OpenAI 互換エンベロープを維持します。これらはすべて、doc_id ターゲティング、ストリーミング、正直な使用量アカウンティング、およびターン間のプロンプト キャッシュ継続性を備えています。トランスクリプトは逐語的に追加します。プロトコル レーンの出力は変更されずに次のリクエストに戻ります。
  • モデルと接続ノブ: index_model / chat_model、index_backend / chat_backend (およびコールごとの backend) は各レーンにそのまま渡されます — LiteLLM ルーティングのプロバイダー、キーレス OpenAI 互換サーバー、Azure/Bedrock/Vertex が含まれます。
  • index= / chat= スロット: フラット引数のグループ化されたスペル — 文字列短縮表現またはマッピング (index={"model": ..., "storage_path": ...}、chat={"model": ..., "backend": ...})。 "cloud" / "local" はサイドに名前を付け、オプションの mode= はそれをクロスチェックし、PageIndexLocalClient / PageIndexCloudClient は同じスロットを使用します。 PageIndexCloudClient() は PAGEINDEX_API_KEY と読み取られます。裸の PageIndexClient() は、環境がどのようなものであってもローカルに残ります。
  • 型指定された構成形状: IndexConfig / CloudIndexConfig / LocalIndexConfig / ChatConfig。型チェッカーが認識できるように py.typed が同梱されています。
  • 静かに失敗するものはありません: 未知のキー、混合サイド、空の値、およびモード/コンテンツの競合は、メッセージ内の法的語彙を使用して構築時に拒否されます。資格情報が無効であるか、モデルが欠落していると、空の概要を含むドキュメントが保存される代わりに、インデックス作成の実行に失敗します。すべてのクラウド エラーには HTTP ステータスが含まれます。
  • 依存関係: Python >= 3.10;基本インストール (チャット エンジン) の openai-agents。 SDK の追加の [anthropic] および [claude]。 Pillow >= 9.0 は、highlight_region の必須の依存関係になりました。

0.5.1にもあります

  • Flash は、はるかに少ないメモリで大きな PDF を解析します。 1 つまたは 2 つの CPU を搭載したマシン、または Type-3 フォントを含むドキュメントの場合、Flash のパーサーはドキュメント全体ではなく一度に 1 ページを保持するようになりました。1,665 ページの教科書のピーク時は、3.1 GB ではなく 434 MB になります。木は変わらず。
  • フォント マップが破損しても Flash がハングしなくなりました。 フォントの ToUnicode マップにある )、{、または } により、メモリがなくなるまで解析ループが発生しました。このような PDF はインデックス化されるようになりました。 0.5.0 にも:
  • 推論モデルは推論を保持します。 チャット実行のすべてのリクエストとその後のターンごとに、すべてのルートでモデルに独自の推論が送信されます。クロードの思考、キミ、GLM、Qwen などからの reasoning_content、OpenRouter の reasoning_details、GPT の推論アイテム、Gemini の思考署名、および Bedrock の暗号化された推論。クロードは、OpenRouter などのゲートウェイを介してプロンプト キャッシュも読み取るようになりました。
  • reasoning_effort="none" は、chat() およびインデックス概要で、クロードの思考をオフにします。これがデフォルトです (Sonnet 5.5 はツール呼び出しの合間に思考を続けます)。 Opus 5.5 と Fable (これをオフにすることはできません)、および claude-code/ モデルでは、明示的な "none" が発生し、要約のデフォルトによりそれらが Low で実行されます。
  • LiteLLM のモデル マップより新しいモデル (bedrock/global.openai.gpt-6.1-terra など): LiteLLM が拒否した場合、PageIndex は LiteLLM のパブリッシュされたマップを 1 回フェッチし、再度送信します。 LITELLM_LOCAL_MODEL_COST_MAP=True はこれをオフにします。
  • 再試行は、インデックス作成、チャット、クラウドに関する公式の OpenAI および Anthropic SDK に従っています API: レート制限はサーバーが要求する時間 (最大 60 秒) を待機し、不足している OpenAI キーはすぐに失敗し、402、413、および 422 は再試行されません。 Flash サマリーは一度に 128 個実行されるため、大規模なドキュメントではサマリー ステージが約 4 分の 1 高速になります。
  • クロード サブスクリプションのインデックス付けは、1 つのクロード コード ワークフローとして実行され、一度に 16 件ではなく最大 64 件の概要を実行します。PAGEINDEX_CLAUDE_CODE_WORKFLOW=0 は呼び出しごとに 1 つのプロセスに戻ります。
  • フォークされたワーカーがハングしなくなりました。 client (Linux では multiprocessing、gunicorn --preload、Celery) を使用してプロセスからフォークされたワーカーがハングしたり、別のプロセスの応答を読み取ったりすることがなくなりました。
  • 速報: extra_body はすべてのプロバイダーに到達します。 OpenAI のみが取得するフィールド (store や verbosity など) は、Claude と Gemini では表示されずにドロップされていましたが、現在はライズされています。 litellm.drop_params = True は再びそれらをドロップします。 extra_body は独自の議論を持つ reasoning_effort を拒否します。
  • 速報: クラウド読み取りタイムアウトにより、再試行後にリクエストの ReadTimeout ではなく ConnectionError が発生するため、except requests.Timeout はリクエストを捕捉できなくなりました。
  • Gemini 履歴は model なしで保存されました。0.4.5 から 0.4.7 が返したため、独自の思考署名なしで以前の Gemini ツール呼び出しを送信します。 model で保存された履歴はそれらを保持します。 0.4.7 にも次のようにあります。
  • フォルダーのメタデータ フィールドを読み取り、変更します。 get_metadata_schema(folder_id) はフォルダーのドキュメント (最上位フォルダー、それ以外の場合はアカウント) に適用されるフィールドを返し、delete_metadata_schema(folder_id) はフォルダーが宣言したフィールドを削除するため、create_metadata_schema() で再度宣言できます。ドキュメントはメタデータを保持します。クラウドのみ。 0.4.6 にも次のようにあります。
  • メッセージ レーンは anthropic 2.2 で動作します。 anthropic 2.2.0 は、デフォルトでサーバーが保持するスレッドでツール ランナーを実行するため、OpenRouter の Anthropic エンドポイントなどのプロキシの背後で 2 番目のモデル呼び出しが失敗し、返された messages が最終応答を繰り返しました。 chat(protocol="messages") は、以前のアントロピック リリースと同様に、ターンごとに会話全体を送信し、messages は各ターンを 1 回送信します。 0.4.5 にも:
  • マルチターン チャットはプロンプト キャッシュを保持します。 API チャット モデルでは、chat_completions() および chat(protocol="chat_completions") は実行の新しいメッセージ (ツール呼び出し、ツール結果、回答) を messages で返します (stream_metadata=True によるストリーミング: 終了使用チャンク上)。それらを追加すると (history += r["messages"])、次のターンではモデルが見たものを正確に再送信するため、プロンプト キャッシュはヒットし続けます。 Responses はそのトランスクリプトを messages にも移動します。 items は、今後のリリースで削除されるまで、DeprecationWarning とともに読み取りを続けます。
  • 結果は公式の SDK と同じように読み取られます。 プロトコル レーンは ChatObject を返します。これは依然として辞書であり、公式の SDK が同じ JSON、r.choices[0].message.content を読み取るのと同じように属性によって読み取ることもできます。メッセージ ストリームは get_final_message() / get_final_text() で終わり、応答ストリームは response.created、その後 response.in_progress で始まります。
  • トークンの使用状況、失敗を含む。 ローカル インデックス作成は usage を返し、独自のモデル チャット usage は各モデル呼び出しをリストします (claude-code/ モデルは合計を報告します)。失敗した実行には、PageIndexAPIError.usage で費やした金額が引き継がれ、短くカットされた回答 (長さ、コンテンツ フィルター、拒否) は、回答の半分を返す代わりに、これまでのテキストが partial_answer で発生します。
  • create_metadata_schema(folder_id, fields) は、フォルダーのドキュメントに含まれるメタデータ フィールドを宣言します。チャットのメタデータ検索では、それらによってフィルター、並べ替え、およびカウントが行われます。クラウドのみ。

  • Flash は単語全体を保持します。 単語のギャップは各文字コードのフォント幅から測定されるため、ページのテキストとタイトルが「infe rence」のように単語を分割することがなくなり、章の見出しがそのブックマークと再び一致します。

  • 速報: ローカルとクラウドの 1 つのツリー形状。 get_tree ノードは、両方のモードで start_index、end_index、summary を実行します。 page_index と prefix_summary はなくなりました。新しくインデックス付けされたドキュメントでは、親の範囲と概要がセクション全体をカバーし、最初のサブセクションの前のページが "<title> (intro)" ノードになります。以前にインデックス付けされたドキュメントには、独自の範囲と概要が保持されます。

  • 標準モードは Flash のように要約します。 各セクションの要約はサブセクションが完了するとすぐに開始され、短いノードには独自のテキストが保持されます。 0.2.20 にも次のようにあります。

  • 人里離れたレーンでは、書かれたとおりにモデルが使用されます。 chat(protocol="messages")、anthropic_runner_config()、および claude_agent_config() は、設定した chat_model を使用するため、model= は必要なくなりました。プレフィックスによってルートが選択されます。bedrock/、vertex_ai/、azure_ai/ は Bedrock、Vertex AI、Azure AI Foundry に送信され、その他のものは直接 Anthropic に送信されます。 [anthropic] の追加には anthropic>=0.122.0 が必要になりました。
  • list_documents は limit を最大 10,000 (以前は 100) まで受け入れ、ローカル clients は folder_id="root" を受け入れます。 0.2.19にもあります:
  • 速報: resolve_citations は get_citations に名前変更されました。 0.2.17 で出荷されたリストを返すメソッドは client.get_citations(answer, doc_id=...) になりました。同じ議論、同じ結果。
  • resolve_citations は表示可能な引用を返します。 client.resolve_citations(answer, doc_id=...) は {"answer": ..., "citations": [...]} を返すようになりました。これは、各引用タグが番号付きマークダウン リンク [[1]](#pageindex-citation-01) で置き換えられた回答テキストと、anchor と index で始まる各引用の完全なデータです。
  • highlight_region は、ページ画像上の境界ボックス領域に半透明のハイライトを描画します。 PIL イメージまたは生のバイトを受け入れ、新しい PIL イメージを返します。 pageindexより輸入可能です。
  • get_page_image および get_document_image は、ページ画像および OCR 抽出された埋め込み画像への有効期間の短い URL を返します。クラウドのみ。
  • get_document_path、get_folder_path、get_folder_id は、ID と "Research/Papers/attention.pdf" のような読み取り可能なパスの間で変換します。
  • get_document_id はパスを受け入れます: client.get_document_id("Research/Papers/report.pdf") はフォルダー部分を自動的に削除します。
  • list_documents(recursive=True) はサブフォルダー内のドキュメントを返します。
  • チャットとコンピューティングに合わせた、ドキュメントのアップロードとフォルダー作成のための共有命名規則。 0.2.18 にも:
  • get_document_id(name) は、1 回の API 呼び出しで表示名によってドキュメントの ID を検索します。これは、引用ドキュメント名を ID に解決するのに役立ちます。
  • プロンプトの調整: SDK のローカル引用および検出プロンプトがチャット MCP サーバーと一致するようになりました。作成された「ソース」フッターが削除され、欠落していた言い換えと再試行の永続化ステップが復元され、SDK のみのページネーション チュートリアルが検出手順から削除されました。 0.2.17 にも次のようにあります。
  • 引用はページ座標に解決されます。 client.get_citations(answer, doc_id=...) は、引用された回答内の引用タグ (chat(citations=True) が書き込む <cite doc="…" page="…" block="…"/> タグ、および管理チャットが書き込む <doc=…;page=…;block=…> タグ) を読み取り、文書の ID を含む引用ごとに 1 つのエントリを返します。 beta_headers=["block_reference"] でインデックス付けされたクラウド ドキュメント上のブロック レベルの引用の場合、エントリにはブロックのページ、境界ボックス、タイプ、テキストも含まれます。 doc_id= (chat(doc_id=...) が受け取ったもの) を渡して名前検索の範囲を設定するか、ライブラリに対して解決するために省略します。
  • 1 つのブロック、1 つの呼び出し。 client.get_block(doc_id, block_id) は、API が処理するときに単一のレイアウト ブロックを返します。{doc_id, page, block_id, bbox, block_type, text}、bbox は、ページの幅と高さの 1,000 分の 1 (0 ～ 1000)、原点左上で [x0, y0, x1, y1] として返されます。クラウドのみ。ローカル ページのコンテンツにはブロックがありません。
  • Flash は、すべてのスクリプトのすべてのドキュメントにインデックスを付けます。 スクリプトではなく、レイアウトがツリーを決定します。小さなドキュメント、スライドデッキ、日本語、アラビア語、ヘブライ語、インド語、タイ語、およびスクリプトが混在する PDF は、以前は拒否されたり見出しが失われたりしていましたが、インデックス化されるようになり、同じレイアウトからすべてのスクリプトで同じ見出しが生成されます。階層が検出されない場合、ツリーはページごとに 1 つのノードに戻ります (toc_source="pages")。最後の最初の見出しより前のページは Preface ノードを取得するため、すべてのページは何らかのノードから到達可能です。 toc_source はすべての結果 (detected、bookmarks、hybrid、pages、unreadable) にあります。 フル Changelog: https://github.com/VectifyAI/PageIndex/compare/v0.5.0...v0.5.1
