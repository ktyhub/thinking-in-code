#OCRmyPDF v17.11.0

機能拡張

  • 新しい --max-ocr-image-mpixels は、ページ作成時に OCR に送信される画像をダウンサンプリングします。 指定されたサイズを超えています。これはメモリの最大消費量を制限します。の 表示されているページは決してダウンサンプリングされないため、出力の外観はどのページでも影響を受けません。 モード;引き換えに得られるのは、非常に高解像度のスキャンでの OCR 精度です。 A34 megapixel ページ (ピークは 492 MB、ピークは 325 MB) --max-ocr-image-mpixels 8 と同じテキストを認識します。 「記憶」を参照 メモリ制限のサイズを設定する方法については、パフォーマンス ドキュメントのセクションを参照してください。
  • watcher.py (watcher エクストラ) は、設定可能な出力レイアウトを獲得し、 紛争政策。これらはウォッチャーのみの変更です。それらは影響を与えません ocrmypdf ライブラリ API。
    • 新しい OCR_OUTPUT_STRUCTURE 設定 (--output-structure): FLAT (デフォルトでは、すべての出力は宛先ディレクトリに直接配置されます)、 YEAR_MONTH ({destination}/{year}/{month}/{filename}、同じレイアウト) 古い OCR_OUTPUT_DIRECTORY_YEAR_MONTH=1)、または HIERARCHY、 宛先の下の入力ディレクトリ ツリーをミラーリングします。 input/a/b/c.pdf→output/a/b/c.pdf。
    • 新しい OCR_ON_CONFLICT 設定 (--on-conflict) は何が起こるかを制御します 目的の宛先ファイルがすでに存在する場合: SUFFIX (デフォルト) name (1).pdf、name (2).pdf、...をOSスタイルで書き込みます。 SKIPのログ ファイルは未処理のままになります。 OVERWRITE は古い動作です。 動作の変更: デフォルトは SUFFIX になったので、既存の出力 ファイルがサイレントに上書きされることはなくなりました。
    • 両方の設定が OCR_OUTPUT_DIRECTORY と OCR_ON_SUCCESS_ARCHIVE によって使用されるアーカイブ ディレクトリ。以前は アーカイブ ディレクトリは常にフラットであり、静かに名前が上書きされました 衝突。
    • 出力およびアーカイブのファイル名とディレクトリコンポーネントはサニタイズされます。 入力側よりも制限が厳しいファイルシステムの場合 (SMB など) share): Windows/SMB では不正な文字 (<>:"/\|?* およびコントロール) 文字) は _ に置き換えられ、末尾のドット/スペースは削除されます。 および予約された DOS デバイス名 (CON、PRN、AUX、NUL、COM1-9、 LPT1-9) には、接頭辞 _ が付きます。
    • OCR_OUTPUT_DIRECTORY_YEAR_MONTH は廃止され、代わりに OCR_OUTPUT_STRUCTURE=YEAR_MONTH。それは今でも尊重されており、 非推奨の警告。両方が設定されている場合は、OCR_OUTPUT_STRUCTURE が優先されます。
    • バッチの「watcher.py を使用した監視フォルダー」セクションを参照してください。 注を含む完全な説明のための文書の処理 SMB ユーザー向け、client 側のディレクトリ/ファイル情報キャッシュの遅延について。

パフォーマンス

  • OCR に送信された画像はデコードされなくなり、何も必要ないときに再エンコードされます。 それを変えるために。マスクする既存のテキストがなく、フィルタリングも行われていないページ上 プラグイン -- スキャンされたドキュメントの通常のケース -- ラスタライズされたページ すでに OCR 画像であるため、書き換えられるのではなくリンクされます。生産する 3.3 秒かかり、34 メガ apixel ページのフルサイズのバッファーが必要でした。 ファイル全体で約 15 秒です。マスクの構築は延期されました テキスト領域を実際にブランクにする必要があるまでは、そのステップが強制的なものであるためです。 デコードします。 Pillow の最小バージョンは 12 に引き上げられます。 画像をデコードしたものは、その形状が Pillow 11 に定着した属性を読み取ります。 (pi-heif にはすでに枕 11.1 が必要なので、有効床はほとんど動きません)。
  • 大きな画像を含むファイルのピーク メモリをデフォルトで約 3 分の 1 に削減 設定。 34 megapixel ページでは、プロセス ツリーは 752 MB でピークに達し、現在は ピークは 492 MB です。これは 2 つの変更が原因です: ページのラスタライズが行われなくなりました PDFium の丸めを修正するために 3 番目のフルページ バッファを割り当てます。 レンダリング サイズが 1 ～ 2 ピクセルずつ変更され、解放されたヒープ メモリが OCR エンジンが実行される前に、オペレーティング システムをカウントするのではなく、 エンジンが動作している限り常駐設定されます。ラスタライズも サイズを修正してもページ全体がリサンプリングされなくなるため、より高速になります。
  • 複数の OCR ジョブが単一の Python プロセスで同時に実行できるようになりました。 API 以前は ocrmypdf.ocr() の間ずっとロックを保持していたので、2 番目の 別のスレッドの呼び出しは、最初のスレッドが終了するまで待つ必要がありました。プラグインの状態は 現在はリーダー/ライターのロックで保護されています: プラグイン セットのインストールには時間がかかります 排他的であり、ジョブは実行のために共有を保持します。したがって機内での仕事 依存するプラグイン インフラストラクチャをその下で置き換えることはできません。 一方、インストールが完了したジョブは同時に進行します。
  • プラグイン セットは、インタプリタごとに 1 回インストールされ、再利用されるようになりました。 呼び出しごとに再インストールされます。以前は各 ocrmypdf.ocr() 呼び出し ファイルパスとして指定されたプラグインモジュールを再実行し、それらを再バインドします sys.modules。プラグインはジョブごとに再実行されることに依存してはなりません。 プラグイン マネージャーにジョブごとの状態を保存してはなりません。同時ジョブは 同じプラグイン セットの共有をリクエストしています。
  • 異なるプラグイン セットを要求するジョブは、相互にシリアル化されます。 2 番目のセットをインストールするには、最初のセットのジョブが完了するまで待つ必要があります。使用する 同時実行ジョブまたは個別のプロセス間で同じプラグイン セットを使用します。
  • 大きな画像を含むドキュメントでは、画像の最適化が大幅に高速化されます。 PNG プレディクターを使用して /FlateDecode として保存された画像は、すでに正確に保持されています PNG IDAT チャンクは何を保持しているので、PNG として直接再パッケージ化されるようになりました。 ビットマップにデコードされて再エンコードされるのではなく、 6ページの文書で 1 つの 9000x9000 画像を含む場合、最適化ステップは 3.4 秒から 0.6 秒になりました。 以下の JPEG の変更と合わせて 0.04 秒に変更されます。合計実行時間は次のとおりです 10.0秒から7.0秒。出力は変更されません: 圧縮された データはそのまま再利用されます。直接再パッケージ化できない形式のイメージ まだ前の道をたどります。
  • 画像の最適化中に、コードが パスは、デコードされた JPEG を使用した最適化設定でした。 再エンコードされました（--optimize 2以下）。現在は、次のコード パスのみをデコードします。 デコードされたJPEGを使用します。出力は変化しません。
  • 非圧縮画像 (/Filter を含まない画像) でスプリアスが生成されなくなりました。 「オプティマイザによって処理できませんでした」という警告。そんなイメージが湧きました IndexError 内部的には、オプティマイザーのベストエフォート ハンドラーがキャッチし、 警告として報告されます。現在は認識され、静かにスキップされます。
  • 処理を要求するイメージ オプティマイザーの到達不能なブランチを削除しました。 ICC ベースの色空間のコンポーネント イメージごとに 1 ビット。以前の小切手は送信します 1 bpc ごとのイメージを JBIG2 パスに渡します。JBIG2 パスは、次のように ICC ベースのイメージを処理します。 抽出する前にプロファイルを無力化するので、ブランチは実行できなくなります。
  • すべてのワーカー プールをシリアル化するプロセス全体のロックを削除しました。 Executor インスタンス。 Executor.pool_lock は保持されていますが、取得されなくなりました。 そして廃止されました。将来のメジャー リリースでは削除される予定です。不変条件 それは保護されています - 共有コンソールに表示されるプログレスバーが 1 つだけである - 現在はプログレスバーによって適用され、別のバーがすでに存在する場合にはそれ自体が無効になります コンソールを所有しています。
  • それぞれ jobs=M で構成された N 個の同時ジョブが最大で生成される可能性があることに注意してください。 N*M ワーカー。以前は M にシリアル化されていました。サイズ jobs それに応じて。
  • 同時インプロセスジョブの既知の制限: それらは同じものを使用する必要があります max_image_mpixels。 Pillow の解凍爆弾の制限はインタープリター全体に適用されます そしてそれを設定した最後のジョブが勝ちます。別のプロセスを使用してジョブを実行する 異なる構成。

修正

  • pypdfium2 ラスタライザーの潜在的な use-after-free を修正しました。 to_pil() しましょう 一部のフォーマット用の Pillow エイリアス PDFium のビットマップ バッファ -- グレースケール レンダリング その中にはすべてのモノラルおよびグレースケール ページが含まれます -- そしてバッファは解放されました その直後、PDFiumがリリースしたPillow読書メモリを残しました。
  • Windows: OCRmyPDF で「[WinError 2] システムが見つかりません」と表示されなくなりました。 Ghostscript と Tesseract の検索中に「指定されたファイル」という警告が表示される (#1671)。これら メッセージは、単に存在しないレジストリ キーを調査することによって送信されたものです。 プログラムが Scoop などのパッケージ マネージャーによってインストールされたか、インストールされなかった 全然。その後、検索は他の場所で続行され、通常は成功するため、これらは 失敗は正常であり、場所に名前を付けてデバッグ レベルでログに記録されるようになりました。 それは検索されたものです。プログラムが本当に見つからない場合でも、OCRmyPDF それをエラーとして報告します。
  • Windows: PROGRAMFILES 環境変数が次を指している場合のクラッシュを修正しました。 存在しないフォルダー。
  • --mode strip は OCRmyPDF 自体の OCR テキスト レイヤーを削除できませんでした 生成されました ({issue}1730)。 OCRmyPDF はテキストレイヤーを Form XObject として移植します ストリッピングではページ コンテンツ ストリームのみが検査されるため、非表示のテキストは 決して見つかりませんでした。同じ欠陥により、--mode redo は 2 番目のテキスト レイヤーをスタックしました。 古いものを交換するのではなく、その上に置きます。ストリッピングは次のようになります。 XObject を形成します。 @Anai-Guo ({issue}1732) に感謝します。
  • ストリッピングにより、祖先から継承されたページ /Resources も解決されるようになりました。 ページ自体のリソースだけを調べるのではなく、/Pages ノードを調べます。
  • ストリップ後に空になるテキストレイヤーがページから削除されるようになりました。 Form XObject の形骸として取り残されるのではなく、
  • Python API 内の既存のオプション オブジェクトに clean_final を設定する それ以上長いと、clean は設定されないままになります。 --clean-final は --clean を意味しますが、ルールは オプションオブジェクトが実行されている間のみ実行されるフィールドバリデータに存在していました。 構築されたため、その後の属性への代入は暗黙的にスキップされました。
  • 範囲外またはスペルミスのオプションの検証エラーで、オプションの名前が表示されるようになりました。 彼らはについてであり、その言葉遣いは、実際のものではなく、ピダンティックから来ています。 手書きなので少し変わっています。たとえば、現在は --jobs 999 --jobs: Input should be less than or equal to 256 が報告します。のセット 受け入れられる値は変更されません。
