druid 0.22.0

マイナー 公開日2021年9月22日 出典apache/druid 英語原文

#ドルイドドルイド-0.22.0 Apache Druid 0.22.0 には、400 を超える新機能、バグ修正、パフォーマンス強化、ドキュメントの改善、および 73 人の寄稿者による追加のテスト カバレッジが含まれています。 詳細については、変更の完全なセットを参照してください。

<a name="22-new-features" href="#22-new-features">#</a> 新機能

<a name="22-query" href="#22-query">#</a> クエリ エンジン

<a name="22-multi-distinct" href="#22-multi-distinct">#</a> 同じクエリ内の複数の異なるアグリゲーターのサポート

Druid は、グループ化セットで通常使用されるグループ化アグリゲーターを使用して、複数の DISTINCT の「正確な」カウントをサポートできるようになりました。これは、druid.sql.planner.useApproximateCountDistinct が false の場合の正確なカウントにのみ適用され、druid.sql.planner.useGroupingSetForExactDistinct を true に設定することで有効にできることに注意してください。 https://github.com/apache/druid/pull/11014

<a name="22-array-agg" href="#22-array-agg">#</a> SQL ARRAY_AGG および STRING_AGG アグリゲーター関数

ARRAY_AGG 集計関数が追加され、列の値または個別の値を単一の配列結果に蓄積できるようになりました。このリリースでは、STRING_AGG も追加されています。これは ARRAY_AGG に似ていますが、指定された「区切り文字」を使用して配列値を単一の文字列に結合し、NULL 値を無視する点が異なります。これらの関数は両方とも、結果の最大サイズを制御するために最大サイズ パラメーターを受け入れ、この値を超えると失敗します。詳細については、SQL ドキュメント を参照してください。 https://github.com/apache/druid/pull/11157 https://github.com/apache/druid/pull/11241

<a name="22-bitwise" href="#22-bitwise">#</a> ビット単位の数学関数式とアグリゲータ

BITWISE_AND、BITWISE_OR、BITWISE_XOR など、「ビットごとの」数学を (対応するネイティブ式とともに) 実行するためのいくつかの新しい SQL 関数が機能します。さらに、対応するビットごとの関数を使用して列内の値を累積するための集計関数 BIT_AND、BIT_OR、および BIT_XOR が追加されました。詳細については、SQL ドキュメント を参照してください。 https://github.com/apache/druid/pull/10605 https://github.com/apache/druid/pull/10823 https://github.com/apache/druid/pull/11280

<a name="22-human-format" href="#22-human-format">#</a> 人間が判読できる数値形式関数

3 つの新しい SQL およびネイティブ式数値形式関数が Druid 0.22.0、HUMAN_READABLE_BINARY_BYTE_FORMAT、HUMAN_READABLE_DECIMAL_BYTE_FORMAT、HUMAN_READABLE_DECIMAL_FORMAT に追加され、結果をクエリ結果のより使いやすい形式に変換できるようになりました。詳細については、SQL ドキュメント を参照してください。 https://github.com/apache/druid/issues/10584 https://github.com/apache/druid/pull/10635

<a name="22-expr-agg" href="#22-expr-agg">#</a> 式アグリゲーター

Druid 0.22.0 は、新しい「ネイティブ」JSON クエリ式集計関数を追加します。これにより、Druid ネイティブ式を使用して「フォールド」(「リデュース」とも呼ばれる) 操作を実行し、任意の数の入力列に値を蓄積できるようになります。これにより、Druid アグリゲーターで実行できる内容に大幅な柔軟性が追加され、Javascript アグリゲーターで可能だったことと多くの点で似ていますが、より安全なサンドボックス化された方法で行われます。 式が入力列に対して「フォールド」を実行できるようになったことで、以前は可能であった「マップ」(式の仮想列)、「フィルタ」(式フィルタ)、およびポスト変換(式のポストアグリゲータ)関数に加えて、ネイティブ式の機能も充実しました。 これは式を使用するため、パフォーマンスはまだ最適ではなく、まだ直接文書化されていませんが、これは、このリリースで追加された SQL ARRAY_AGG、STRING_AGG、およびビットごとのアグリゲータ関数の背後にある基礎となるテクノロジです。 https://github.com/apache/druid/pull/11104

<a name="22-sql-routing" href="#22-sql-routing">#</a> SQL クエリ ルーティングの改善

Druid 0.22 は、Druid ルーターとブローカー間でクエリをルーティングする方法に対する拡張制御を拡張機能作成者に提供するためのいくつかの新しい機能を追加します。 1 つ目は、新しい manual ブローカー選択戦略を Druid ルーターに追加します。これにより、クエリは、クエリ コンテキスト パラメーター brokerService に基づいて、druid.router.tierToBrokerMap で定義されたブローカー プール (これはブローカー セット druid.service の「サービス名」に対応します) にクエリを送信する必要がある Druid ブローカーを手動で指定できます。 2 番目の新機能により、Druid ルーターが SQL クエリを解析および検査できるようになり、ブローカー選択戦略が SQL クエリに対しても機能できるようになります。これは、druid.router.sql.enable を true に設定することで有効にできます。これは、単一のブローカーへの「スティッキー」接続を容易にするために別のメカニズムを使用する JDBC クエリには影響しません。 https://github.com/apache/druid/pull/11566 https://github.com/apache/druid/pull/11495

<a name="22-proto-jdbc" href="#22-proto-jdbc">#</a> Avatica protobuf JDBC サポート

Druid は、Avatica Golang Driver での使用など、Avatica Protobuf JDBC 接続の使用をサポートするようになり、JSON JDBC URI とは別のエンドポイントを持ちます。

String url = "jdbc:avatica:remote:url=http://localhost:8082/druid/v2/sql/avatica-protobuf/;serialization=protobuf";

https://github.com/apache/druid/pull/10543

<a name="22-query-error-log" href="#22-query-error-log">#</a> クエリ エラー ログの改善

クエリ例外が WARN レベルから ERROR レベルに変更され、クエリの失敗のトラブルシューティングに役立つ追加情報がログに含まれるようになりました。さらに、新しいクエリ コンテキスト フラグ enableQueryDebugging が追加されました。これらのクエリ エラー ログにスタック トレースが含まれるため、DEBUG レベルでログを有効にする必要なく、さらに多くの情報が提供されます。 https://github.com/apache/druid/pull/11519

<a name="22-streaming" href="#22-streaming">#</a> ストリーミング取り込み

<a name="22-streaming-task-autoscaling" href="#22-streaming-task-autoscaling">#</a> Kafka および Kinesis ストリーミング取り込みのタスク自動スケーリング

Druid 0.22.0 は、動的な Kafka および Kinesis タスク スケーリングの実験的サポートを提供するようになりました。含まれている戦略は、ストリームラグの定期的な測定 (Kafka の場合はメッセージ数、Kinesis の場合はメッセージ反復子と最も古いメッセージの間の経過時間の差に基づいています) によって駆動され、「ラグ」の量といくつかの設定パラメーターに基づいてタスクの数を調整します。詳細については、Kafka および Kinesis のドキュメントを参照してください。 https://github.com/apache/druid/pull/10524 https://github.com/apache/druid/pull/10985

<a name="22-avro-proto-stream" href="#22-avro-proto-stream">#</a> Avro および Protobuf ストリーミング InputFormat および Confluent スキーマ レジストリのサポート

Druid ストリーミング インジェストでは、更新された InputFormat 仕様形式で Avro および Protobuf がサポートされるようになりました。これは、従来の Druid ストリーミング形式で使用されていた非推奨の Firehose/パーサー仕様に代わるものです。これに加えて、Confluent Schema Registry からこれらの形式のスキーマを取得するためのサポートが提供されます。詳細については、データ形式のドキュメント を参照してください。 https://github.com/apache/druid/pull/11040 https://github.com/apache/druid/pull/11018 https://github.com/apache/druid/pull/10314 https://github.com/apache/druid/pull/10839

<a name="22-kafka-groupid" href="#22-kafka-groupid">#</a> group.id を指定するための Kafka 取り込みサポート

Druid Kafka ストリーミング インジェストは、Druid タスクが Kafka ブローカーに対して行う接続での group.id の指定をオプションでサポートするようになりました。これは、認可の一部としてこれを設定する必要があるクラスターにアクセスする場合に便利で、Kafka スーパーバイザー仕様の consumerProperties セクションで指定できます。詳細については、Kafka インジェスト ドキュメント を参照してください。 https://github.com/apache/druid/pull/11147

<a name="22-batch" href="#22-batch">#</a> ネイティブ バッチ インジェスト

<a name="22-shuffle-deep-storage" href="#22-shuffle-deep-storage">#</a> 中間シャッフル データ用のディープ ストレージの使用のサポート

Druid ネイティブの「パーフェクト ロールアップ」2 フェーズ インジェスト タスクは、中間管理者またはインデクサーのローカル ディスクの代わりに、シャッフルの場所としてディープ ストレージの使用をサポートするようになりました。この機能を使用するには、druid.processing.intermediaryData.storage.type を deepstore に設定します。これにより、構成されたディープ ストレージ タイプが使用されます。 注 - 「ディープストア」タイプでは、データは設定されたディープストレージパスの下の shuffle-data ディレクトリに保存されます。このディレクトリの自動クリーンアップはまだサポートされていません。 shuffle-data プレフィックスの場所でデータを自動クリーンアップするためのクラウド ストレージ ライフサイクル ルールを設定できます。 https://github.com/apache/druid/pull/11507

<a name="22-batch-memory" href="#22-batch-memory">#</a> ネイティブ バッチ インジェスト タスクのメモリ使用量の改善

Druid ネイティブ バッチ インジェストに新しい構成オプション druid.indexer.task.batchProcessingMode が追加されました。これにより、バッチ インジェストがより小さく予測可能なヒープ メモリ使用量のフットプリントで動作できるようにする 2 つの新しい動作モードが導入されます。 CLOSED_SEGMENTS_SINKS モードは最も積極的で、メモリ フットプリントが最小になるはずで、セグメントの作成中に生成される中間セグメントのメモリ トラッキングと mmap を削除することで機能しますが、現時点ではあまり十分にテストされていないため、実験的とみなされます。新しいデフォルト オプションである CLOSED_SEGMENTS は、中間セグメントの mmap を削除しますが、現時点では比較的十分にテストされており、安定していると考えられますが、ヒープ内のセグメントのセット全体を追跡します。 OPEN_SEGMENTS は、ストリーミング インジェストと共有される以前のインジェスト パスを使用し、中間セグメントで mmap を実行し、これらのセグメントがリアルタイム クエリでクエリできるようにタイムラインを構築します。これはバッチではまったく必要ありませんが、2 つの新しいモードで問題が発生した場合は、OPEN_SEGMENTS モードを選択できます。 https://github.com/apache/druid/pull/11123 https://github.com/apache/druid/pull/11294 https://github.com/apache/druid/pull/11536

<a name="22-batch-wait-for-handoff" href="#22-batch-wait-for-handoff">#</a> バッチ タスクがセグメントのハンドオフが完了するまで待機できるようにする

Druid ネイティブのバッチ取り込みタスクは、取り込まれたセグメントが履歴サーバーによって完全にロードされるまで終了しないようにオプションで設定できるようになりました。これは、追加のタスク スロットを占有したままにするというトレードオフにより、取り込みが完了し、セグメントがクエリに使用できるかどうかの尺度としてタスクの状態を使用する価値があるシナリオで役立ちます。 これは、取り込み仕様の tuningConfig に awaitSegmentAvailabilityTimeoutMillis を追加することで有効にできます。これは、タスクが終了する前にセグメントのロードを待機する最大時間を指定します。このタイムアウトが経過するまでにすべてのセグメントが使用可能にならなくても、ジョブは成功します。ただし、取り込みレポートでは、segmentAvailabilityConfirmed は false になります。これは、ハンドオフが成功せず、これらの新しくインデックス付けされたセグメントがすべてクエリに使用できるわけではないことを示しています。一方、タイムアウトが経過する前にすべてのセグメントが履歴サービスでクエリに使用できるようになった場合、レポート内のそのキーの値は true になります。 現時点では、この tuningConfig 値は圧縮タスクではサポートされていません。ユーザーが圧縮用に awaitSegmentAvailabilityTimeoutMillis の値を指定しようとすると、タスクは失敗し、それがサポートされていないことがユーザーに通知されます。 https://github.com/apache/druid/pull/10676

<a name="22-compact" href="#22-compact">#</a> データ ライフサイクル管理

<a name="22-compact-granularity" href="#22-compact-granularity">#</a> 自動圧縮のためのセグメントとクエリ粒度の管理をサポートします。

Druid の手動および自動コンパクションを設定してセグメント粒度を変更できるようになりました。また、手動コンパクションではクエリ粒度も変更できます。さらに、圧縮ではデフォルトでセグメントの粒度が維持されます。これにより、オペレーターは、データ サイズを減らす代わりに、古いデータをより大きなセグメントやクエリ粒度に変更するなどのオプションをより簡単に実行できるようになります。詳細については、圧縮ドキュメント を参照してください。 https://github.com/apache/druid/pull/10843 https://github.com/apache/druid/pull/10856 https://github.com/apache/druid/pull/10900 https://github.com/apache/druid/pull/10912 https://github.com/apache/druid/pull/11009

<a name="22-compact-skip-lock" href="#22-compact-skip-lock">#</a> 圧縮でロックされた間隔を一時的にスキップできるようにする

Druid の自動圧縮は、ロックが解放されるのを待つのではなく、デフォルトでロックされた間隔を一時的にスキップするようになりました。これにより、データソースを圧縮できる速度が向上します。これは druid.coordinator.compaction.skipLockedIntervals によって制御され、何らかの理由でこの動作が望ましくない場合は false に設定できます。 https://github.com/apache/druid/pull/11190

<a name="22-config-cleanup" href="#22-config-cleanup">#</a> 追加の自動メタデータ クリーンアップのサポート

Druid から一部のエンティティを削除した後、メタデータ ストアからレコードを削除するように自動クリーンアップを構成できます。

  • セグメントレコード
  • 監査記録
  • 監督記録
  • ルールレコード
  • 圧縮構成レコード
  • スーパーバイザーによって作成されたデータソース レコード この機能は、データソースのチャーンレートが高い場合、つまり、有効期間の短いデータソースやその他の関連エンティティを頻繁に作成および削除する場合に、パフォーマンスを維持するのに役立ちます。メタデータ ストアがいっぱいになるのを防ぐために、未使用のメタデータ レコードを保持する期間を制限できます。詳細については、自動クリーンアップのドキュメント を参照してください。 https://github.com/apache/druid/pull/11078 https://github.com/apache/druid/pull/11084 https://github.com/apache/druid/pull/11164 https://github.com/apache/druid/pull/11200 https://github.com/apache/druid/pull/11227 https://github.com/apache/druid/pull/11232 https://github.com/apache/druid/pull/11245

<a name="22-data-cleanup" href="#22-data-cleanup">#</a> データの削除

新しい設定 dropExisting が、Druid ネイティブのバッチ取り込みタスクと圧縮の ioConfig に追加されました。これが true に設定されている場合 (appendToExist が false)、取り込みタスクは、間隔内のすべての既存のセグメントをトランザクション的に未使用としてマークし、新しいセグメントのセットに置き換えます。これは、セグメント粒度をより小さいサイズに変更し、より小さい粒度のバケットの一部にデータがなく、元のセグメントが部分的にのみオーバーシャ​​ドウされたままになる場合など、通常のオーバーシャ​​ドウでは間隔内の一連のセグメントが完全に置き換えられない圧縮のユースケースで役立ちます。 この機能はまだ実験段階であることに注意してください。その結果、圧縮された interval 内のデータが一時的に使用できなくなる可能性があります。この設定を変更しても、間隔が再度圧縮されることはありません。 同様に、markAsUnused が Druid kill タスクのオプションとして追加されました。これは、未使用のセグメントをすべて削除する前に、指定された間隔内のセグメントを「未使用」としてマークします。これは、呼び出し側の 1 回の API 呼び出しで未使用マーク -> 削除シーケンスを実行できるようにする場合や、タスク間隔ロックの下でマーク解除アクションを実行できるようにする場合に便利です。 https://github.com/apache/druid/pull/11070 https://github.com/apache/druid/pull/11025 https://github.com/apache/druid/pull/11501

<a name="22-coordinator" href="#22-coordinator">#</a> コーディネーター

<a name="22-coord-timeout" href="#22-coord-timeout">#</a> Apache Zookeeper ベースのセグメント管理によるコーディネーター セグメントのロード タイムアウトのタイムアウト動作の制御

新しい Druid コーディネーターの動的構成オプションを使用すると、Zookeeper ベースのセグメント管理を使用しているときにセグメントのロード アクションがタイムアウトになるたびに動作を制御できます。 replicateAfterLoadTimeout true に設定すると、コーディネーターはロードに失敗したセグメントを別の履歴サーバーに複製しようとします。これは、クラスター内に低速な履歴サーバーがいくつかある場合に、セグメントの可用性を向上させるのに役立ちます。ただし、履歴が遅いため、後でセグメントが読み込まれる可能性があり、セグメントが過剰にレプ​​リケートされている場合、コーディネーターはドロップ リクエストを発行する必要がある場合があります。 https://github.com/apache/druid/pull/10213

<a name="22-coord-balance" href="#22-coord-balance">#</a> コーディネーター セグメントのバランシングの高速化

もう 1 つの新しいコーディネーター動的構成オプション useBatchedSegmentSampler を true に設定すると、コーディネーターがセグメント バランシング フェーズを処理できる速度が大幅に向上する可能性があります。これは、多くのセグメントを含む非常に大きなクラスター サイズで特に顕著になりますが、注意を払うためにデフォルトでは無効になっています。 https://github.com/apache/druid/pull/11257

<a name="22-coord-replication" href="#22-coord-replication">#</a> クラスタ サイズに基づいてアンダー レプリケーションをオプションで計算できるように、loadstatus API を改善しました。

Druid コーディネーターのロード ステータス API は、新しいオプションの URL クエリ パラメーター computeUsingClusterView をサポートするようになりました。これを指定すると、ロード ルールで構成されたレプリケーション数ではなく、セグメントをレプリケートできるクラスター内で使用可能なサーバーの数に基づいて、コーディネーターがセグメントのアンダー レプリケーションを計算します。たとえば、ロード ルールで 2 つのレプリカが指定されているが、セグメントを保持できるサーバーが 1 台しかない場合、セグメントは指定されたクラスター サイズで可能な限り複製されるため、この API は複製が不十分であると報告されません。 https://github.com/apache/druid/pull/11056

<a name="22-coord-rep-limit" href="#22-coord-rep-limit">#</a> コーディネーション サイクルごとにロードされる非プライマリ レプリカントの数に対するオプションの制限

新しいコーディネーター動的構成 maxNonPrimaryReplicantsToLoad (デフォルト値 Integer.MAX_VALUE) を使用すると、オペレーターは単一のコーディネーター実行サイクルでロードされる非プライマリ レプリカントの数に厳密な上限を定義できます。デフォルト値は、現在存在する動作を模倣します。 使用例: この構成を 1000 に設定すると、コーディネーターは実行サイクルの実行ごとに最大 1000 個の非プライマリ レプリカントをロードします。つまり、レプリケーション係数 2 で 2000 個のセグメントを取り込んだ場合、コーディネーターは最初の実行で 2000 個のプライマリ レプリカントと 1000 個の非プライマリ レプリカントをロードします。次に実行すると、最後の 1000 個の非プライマリ レプリカントがロードされます。 https://github.com/apache/druid/pull/11135

<a name="22-avro-union-by-type" href="#22-avro-union-by-type">#</a> Avro ユニオン フィールドをタイプ別に抽出する

Druid バッチまたはストリーミング インジェストを使用した Avro インジェストは、Avro Union タイプのデータを抽出する代替メカニズムをサポートするようになりました。この新しいオプション extractUnionsByType は、flattenSpec を使用してユニオン型からネストされたデータを抽出する場合にのみ機能し、抽出されたデータがフラット化パスの一部としてその型で使用できるようになります。たとえば、複数型の共用体列 someMultiMemberUnion がある場合、このオプションを有効にすると、長い値は $.someMultiMemberUnion ではなく $.someMultiMemberUnion.long によって抽出され、共用体からは長い値のみが抽出されます。詳細については、Avro のドキュメントを参照してください。 https://github.com/apache/druid/pull/10505

<a name="22-up-batch-lineage" href="#22-up-batch-lineage">#</a> ネイティブ バッチ取り込みセグメント割り当ての修正

Druid 0.22.0 には、ネイティブ バッチ インデックス作成における重要なバグ修正が含まれています。このバグ修正では、インデックス作成サブタスクの一時的な失敗により、結果セグメントに不連続なパーティションが生じる可能性があり、「完全な」セットをチェックするロジックにより、このようなパーティションがクエリ可能になることは_決して_ありません。この問題は Druid の最新バージョンで解決されましたが、バッチ タスクがセグメントを割り当てるために使用するプロトコルの変更が必要でした。この変更により、Druid 0.22.0 から以前のバージョンにロールバックする場合、ローリング ダウングレード中に問題が発生する可能性があります。 ローリング ダウングレード中のタスクの失敗を回避するには、次のように設定します。

druid.indexer.task.default.context={ "useLineageBasedSegmentAllocation" : false }

オーバーロード ランタイム プロパティで、useLineageBasedSegmentAllocation が true に設定されているすべてのタスクが完了するまで待ってから、ダウングレードを開始します。これらのタスクがすべて完了すると、ダウングレードにはそれ以上の問題は発生せず、設定をオーバーロード構成から削除できます (Druid 0.22.0 以降を実行している場合はこの設定を有効にすることをお勧めします)。 https://github.com/apache/druid/pull/11189

<a name="22-up-sql-buckets" href="#22-up-sql-buckets">#</a> SQL タイムシリーズは、あらゆる粒度で空のバケットをスキップしなくなりました

Druid 0.22 より前は、SELECT COUNT(*), SUM(x) FROM y WHERE z = 'someval' などの単一のユニバーサル グループ化キー (アグリゲーターのみ) を使用する SQL グループ化クエリでは、結果が一致しないこのクエリから予期される ZZPH100​​ZZ ではなく、空の結果セットが生成されます。これは、この下で「ALL」粒度の timeseries クエリが計画され、クエリ コンテキストで skipEmptyBuckets が true に設定されるためです。後者のオプションでは、集計する値を含むバケットがないためスキップされ、「nil」結果セットの代わりに空の結果セットが作成されるため、このようなクエリの結果は結果を返しません。この動作は、他の SQL 実装に合わせて動作するように変更されましたが、クエリ コンテキストで skipEmptyBuckets を明示的に設定することで以前の動作を取得できます。 https://github.com/apache/druid/pull/11188

<a name="22-up-reingest" href="#22-up-reingest">#</a> Druid の再取り込みに互換性のない変更

「Druid」入力ソースを使用してセグメント データを再取り込むバッチ タスクは、タスク仕様の「ディメンション」セクションと「メトリック」セクションを受け入れなくなり、内部で新しい列フィルターを使用して、元のセグメントのどの列を保持するかを指定するようになります。さらに、timestampSpec は無視されなくなり、__time 列を変更したり、別の列に置き換えたりできるようになりました。これらの変更により、変換された列が無視され、新しいセグメントで使用できなくなるバグも修正されました。 https://github.com/apache/druid/pull/10267

<a name="22-up-ie11" href="#22-up-ie11">#</a> デフォルトの最大セグメント読み込みキュー サイズを変更しました

Druid コーディネーター maxSegmentsInNodeLoadingQueue の動的構成が無制限 (0) から 100 に変更されました。これにより、ローリング アップグレードなどのクラスターの不安定性の期間中にコーディネーターがよりリラックスした方法で動作するようになりますが、特定のコーディネーター サイクルでロードされるセグメントの合計数がサーバーあたり 100 に制限されるため、完全に停止したクラスターが起動され、ディープ ストレージからロードされる速度が遅くなる可能性があります。 https://github.com/apache/druid/pull/11540

<a name="22-dev-notes" href="#22-dev-notes">#</a> 開発者向け通知

<a name="22-dev-expr-cache-key" href="#22-dev-expr-cache-key">#</a> CacheKeyBuilder は druid-processing から druid-core に移動されました

@PublicAPI の注釈が付けられた CacheKeyBuilder クラスは、druid-processing から druid-core に移動されました。これにより、式で Cacheable インターフェイスを拡張して、ルックアップ バージョンなどの外部状態に依存するキャッシュ キーを式で生成できるようになります。 https://github.com/apache/druid/pull/11358

<a name="22-dev-query-processing-pool" href="#22-query-processing-pool">#</a> クエリ エンジンは、ExecutorService ではなく新しい QueryProcessingPool を直接使用するようになりました。

これは、クエリ処理エンジンのいくつかのメソッド シグネチャ (QueryRunnerFactory や QuerySegmentWalker など) に影響を及ぼし、拡張機能が将来クエリ処理プールのさまざまな部分や代替処理プールのスケジューリング戦略にフックできるようになります。 https://github.com/apache/druid/pull/11382

<a name="22-dev-segment-loader" href="#22-dev-segment-loader">#</a> SegmentLoader が拡張およびカスタマイズ可能になりました

これにより、拡張機能は、Druid セグメントがディープ ストレージからロードされ、クエリ エンジンで利用できるようにする方法をカスタマイズするための代替セグメント ロード実装を提供できるようになります。これは不安定な api であると考えられ、コード内でそのように注釈が付けられています。 https://github.com/apache/druid/pull/11398

<a name="22-known-issues" href="#22-known-issues">#</a> 既知の問題

未解決の問題の完全なリストについては、https://github.com/apache/druid/labels/Bug. を参照してください。
