<a name="30.0.0-upcoming-removals" href="#30.0.0-upcoming-removals">#</a> 今後の削除予定

Druid の継続的な改善の一環として、より堅牢な機能を提供し、標準 ANSI SQL との整合性を高めた新しいイテレーションを優先して、特定の機能と動作を非推奨にします。これらの新機能の多くは、いくつかのリリースの新しい展開のデフォルトになっています。

次の機能は非推奨となり、現在 Druid 32.0.0 でのサポートを削除する予定です。

  • 非 SQL 準拠の null 処理: デフォルトでは、Druid は空の文字列とデータのないレコード、および空の数値レコードと 0 を区別するようになりました。詳細については、「NULL 値」を参照してください。 SQL 準拠のロジックに関するチュートリアルについては、Null 処理チュートリアル を参照してください。
  • 非厳密なブール演算: Druid は現在、1 (true) または 0 (false) を厳密に使用します。以前は、true と false は、それぞれ true と false、または 1 と 0 として表すことができました。さらに、Druid は、True && NULL のようなブール比較に対して null 値を返すようになりました。詳細については、「ブール ロジック」を参照してください。 SQL 準拠のロジックを使用するフィルターの例については、クエリ フィルター を参照してください。
  • 2 値ロジック: デフォルトでは、Druid は取り込みとクエリの両方に 3 値ロジックを使用するようになりました。これは主に、NULL 値を持つ列に対して論理 NOT 演算を使用するフィルターに影響します。詳細については、「ブール ロジック」を参照してください。 SQL 準拠のロジックを使用するフィルターの例については、クエリ フィルター を参照してください。

ストリーミング取り込みスーパーバイザーは同時追加をサポートするようになりました。つまり、同時ロックも使用している場合、ストリーミング タスクは置換タスク (圧縮または再インデックス作成) と同時に実行できます。同時追加を有効にするには、コンテキスト パラメーター useConcurrentLocks を true に設定します。

スーパーバイザを更新して "useConcurrentLocks": true を使用すると、取り込みの遅れやタスクの失敗を引き起こすことなく、同時追加への移行がシームレスに行われます。

Druid は、複雑な列とネストされた配列のグループ化をサポートするようになりました。 これは、ネイティブ クエリと MSQ タスク エンジンの両方が、結果を返すときに複雑な列と入れ子になった配列をグループ化できることを意味します。

さらに、MSQ タスク エンジンは、取り込み中に、サポートされている複雑な列 (JSON 列など) をロールアップして並べ替えることができます。

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-improved-and-filter-performance" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-improved-and-filter-performance">#</a> AND フィルターのパフォーマンスの向上

Druid クエリ処理は、AND フィルターの子がインデックスを計算するタイミングと、スキャン中に他のフィルターの選択性に基づいて単純に行を一致させるタイミングを適応的に決定するようになりました。 フィルター パーティショニングとして知られるこの機能は、クエリ内のフィルターの順序に応じてパフォーマンスが大幅に向上する可能性があります。

たとえば、SELECT SUM(longColumn) FROM druid.table WHERE stringColumn1 = '1000' AND stringColumn2 LIKE '%1%' のようなクエリを考えてみましょう。以前は、Druid はフィルターを処理するときに、インデックスが利用可能な場合にはインデックスを使用していました。 それは必ずしも理想的とは限りません。 stringColumn1 = '1000' が 100 行と一致する場合を想像してください。インデックスを使用する場合、フィルターのインデックスを計算するには、真となる stringColumn2 LIKE '%1%' の値をすべて検索する必要があります。 stringColumn2 に 100 を超える値がある場合、残りの 100 行の一致を単にチェックするよりも悪い結果になります。

新しいロジックにより、Druid は AND フィルターの各句を処理するときにインデックスの選択性をチェックするようになりました。 残りの行を照合するよりもインデックスを計算する方が多くの作業が必要であると判断した場合、Druid はインデックスの計算をスキップします。

クエリの WHERE 句にフィルターを記述する順序によって、クエリのパフォーマンスが向上する可能性があります。 今後もさらなる改善が予定されていますが、クエリの順序を変更することで既存の改善を試すことができます。 Druid がクエリをより効率的に処理できるように、IS NULL、=、比較 (>、>=,、<、<=) などの計算負荷の低いインデックスを AND フィルターの先頭近くに配置します。 フォールバック動作は Druid が以前に行っていたことであるため、この方法でフィルターを順序付けしなくても、以前のリリースからパフォーマンスが低下することはありません。

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-centralized-datasource-schema-%28alpha%29" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-centralized-datasource-schema-%28alpha%29">#</a> 一元化されたデータソース スキーマ (アルファ)

データソース スキーマをコーディネーター上で一元管理するように Druid を構成できるようになりました。 以前は、ブローカーはセグメント スキーマのデータ ノードとタスクをクエリする必要がありました。 データソース スキーマを一元化すると、ブローカーの起動時間と展開の効率が向上します。

この機能を有効にするには、次の構成を設定します。

  • 共通のランタイム プロパティで、druid.centralizedDatasourceSchema.enabled を true に設定します。
  • MiddleManager を使用している場合は、MiddleManager ランタイム プロパティで druid.indexer.fork.property.druid.centralizedDatasourceSchema.enabled を true に設定する必要もあります。

<a name="30.0.0-important-features%2C-changes%2C-and-deprecations-rabbitmq-extension" href="#30.0.0-important-features%2C-changes%2C-and-deprecations-rabbitmq-extension">#</a> RabbitMQ 拡張機能

新しい RabbitMQ 拡張機能は、コミュニティへの貢献として利用できます。 RabbitMQ 拡張機能 (druid-rabbit-indexing-service) を使用すると、Rabbit インデックス作成タスクの作成と存続期間を管理できます。これらのインデックス作成タスクは、RabbitMQ から スーパー ストリーム を通じてイベントを読み取ります。

スーパー ストリームはパーティショニングを完全にサポートし、正確に 1 回の配信を可能にするため、以前の RabbitMQ Firehose の欠点がなく、Druid の最新の取り込みアルゴリズムと互換性があります。

これは従来の交換ではなく、RabbitMQ ストリーム機能を使用することに注意してください。メッセージを使用する前に、メッセージがスーパー ストリーム内にあることを確認する必要があります。詳細については、RabbitMQ ドキュメント を参照してください。

TABLE(APPEND(...)) 関数を使用して、テーブル スキーマに基づいて暗黙的に共用体を作成できるようになりました。

たとえば、次のクエリは同等です。

そして

SELECT column1,NULL AS column2,NULL AS column3 FROM table1
UNION ALL
SELECT NULL AS column1,column2,NULL AS column3 FROM table2
UNION ALL
SELECT column1,column2,column3 FROM table3

同じ列が異なる入力タイプで定義されている場合、Druid は最も制限の少ない列タイプを使用することに注意してください。

#16236

  • 圧縮タスクのレポートが改善されました。以前のレポートを上書きするのではなく、セグメント出力レポートの複数のセットを含めることができるようになりました #15981
  • Azure でのセグメントの強制終了が高速化されるように改善されました #15770
  • ディープストレージ接続の再試行動作を改善しました #15938
  • セグメント作成が改善され、バッチで作成されたすべてのセグメントが同じ created_date エントリを持つようになりました。これは、取り込みの問題のトラブルシューティングに役立ちます #15977
  • charsetFix #16212 を使用して Druid が JSON を解析する方法を改善しました

Prometheus エミッター拡張機能は、service/heartbeat および zk-connected メトリックを出力するようになりました。

#16209

また、欠落していたメトリクス query/timeout/count、mergeBuffer/pendingRequests、ingest/events/processedWithError、ingest/notices/queueSize、segment/count をデフォルトの Prometheus エミッター マッピングに追加しました。

#16329

StatsD エミッターの queueSize、poolSize、processorWorkers、および senderWorkers パラメーターを構成できるようになりました。 これらのパラメーターを使用して、キュー サイズがいっぱいになったときに StatsD client の容量を増やします。

#16283

<a name="30.0.0-functional-area-and-related-changes-metrics-and-monitoring-improved-%60segment%2Funavailable%2Fcount%60-metric" href="#30.0.0-functional-area-and-related-changes-metrics-and-monitoring-improved-%60segment%2Funavailable%2Fcount%60-metric">#</a> segment/unavailable/count メトリックの改善

segment/unavailable/count メトリックは、ディープ ストレージ (replicaCount=0) からクエリできるセグメントを考慮するようになりました。

#16020

#16072

  • jvmVersion の寸法を JvmMonitor モジュールに追加 #16262

<a name="30.0.0-functional-area-and-related-changes-extensions-delta-lake-improvements" href="#30.0.0-functional-area-and-related-changes-extensions-delta-lake-improvements">#</a> デルタ湖の改善

これらのフィルターを使用してスナップショットからデータ ファイルを除外し、Druid がデルタ テーブルから取り込む必要があるファイルの数を減らすことができます。

#16288

#16379

<a name="30.0.0-functional-area-and-related-changes-extensions-improve-performance-of-ldap-credentials-validator" href="#30.0.0-functional-area-and-related-changes-extensions-improve-performance-of-ldap-credentials-validator">#</a> LDAP 資格情報バリデーターのパフォーマンスを向上させます。

パスワード ハッシュをメモリ内キャッシュに保持することで、LDAP 認証情報バリデータのパフォーマンスが向上しました。これにより、パスワード ハッシュの再計算が回避され、LDAP ベースの Druid 認証のプロセスが高速化されます。

  • maxRecordsPerPoll、代わりに maxBytesPerPoll を使用してください

stopTaskCount 構成では、古いタスクを最初に停止することが優先されるようになりました。この変更の一環として、stopTaskCount の値を明示的に設定する必要もあります。デフォルトでは taskCount と同じ値になりません。

コーディネーター サービスの次のデフォルト値が変更されました。

  • druid.coordinator.kill.period (指定されていない場合) のデフォルト値は、P1D から druid.coordinator.period.indexingPeriod の値に変更されました。オペレーターは druid.coordinator.kill.period をオーバーライドすることを選択でき、それがデフォルトの動作より優先されます。
  • 動的構成プロパティ killTaskSlotRatio のデフォルト値が 1.0 から 0.1 に更新されました。これにより、kill タスクは、使用可能なすべてのタスク スロットを消費するのではなく、デフォルトで 1 つのタスク スロットのみを使用するようになります。

GoogleTaskLogs のアップロード バッファ サイズを 15 MB ではなく 1 MB に変更して、より多くのアップロードを並行して実行できるようにし、MiddleManager サービスのメモリ不足を防ぎます。

<a name="30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-changes-to-%60targetdatasource%60-in-explain-queries" href="#30.0.0-upgrade-notes-and-incompatible-changes-incompatible-changes-changes-to-%60targetdatasource%60-in-explain-queries">#</a> EXPLAIN クエリの targetDataSource への変更

Druid 30.0.0 には、targetDataSource の動作を 28.0.0 以前の状態に戻す重大な変更が含まれています。これは、Druid 29.0.0 および 29.0.0 とは異なります。 29.0.0 では、targetDataSource はデータソース名を含む JSON オブジェクトを返します。他のすべてのバージョンでは、targetDataSource はデータソースの名前を含む文字列を返します。

29.0.0 以外のバージョンからアップグレードする場合、動作に変更はありません。

29.0.0 からアップグレードする場合、これは互換性のない変更です。

ZooKeeper ベースのセグメント読み込みは、既知の問題により削除されます。 いくつかのリリースで非推奨になりました。 Druid Coordinator の最近の改良により、HTTP ベースのセグメント読み込みのパフォーマンスが大幅に向上しました。

#15705

  • druid.coordinator.loadqueuepeon.type: この値は常に http であるため、必要ありません。
  • druid.coordinator.curator.loadqueuepeon.numCallbackThreads: ZooKeeper(curator) ベースのセグメント読み込みはオプションではなくなったため、必要ありません。

非アクティブなデータソースの圧縮構成の自動クリーンアップがデフォルトで有効になるようになりました。
