#ドルイドドルイド-24.0.0 Apache Druid 24.0.0 には、300 を超える新機能、バグ修正、パフォーマンス強化、ドキュメントの改善、および 67 人の寄稿者による追加のテスト カバレッジが含まれています。 詳細については、変更の完全なセットを参照してください。

<a name="24.0.0-new-features" href="#24.0.0-major-version">#</a> メジャー バージョンの変更

このリリースから、リリース バージョンから先頭の 0 を削除し、他のすべての桁を 1 つ左に移動しました。 Druid は現在メジャー バージョン 24 で、以前の 0.23.0 リリースから大幅に増加しています。下位互換性や重大な変更の点では、このリリースは、0.23.0 や 0.22.0 などの以前のメジャー リリースと大きな違いはありません。以前のリリースで使用したのと同じポリシーを継続します。つまり、アップグレード時に特別な注意が必要な変更の数を最小限に抑え、release note に存在する変更はすべて除外します。このリリースについては、このリリースでの下位互換性のない変更のリストについては、24.0.0 へのアップグレード セクション を参照してください。

<a name="24.0.0-new-features" href="#24.0.0-new-features">#</a> 新機能

<a name="24.0.0-new-features-multi-stage-query-task-engine" href="#24.0.0-new-features-multi-stage-query-task-engine">#</a> マルチステージ クエリ タスク エンジン

Apache Druid の SQL ベースの取り込み は、分散型マルチステージ クエリ アーキテクチャを使用します。これには、マルチステージ クエリ タスク エンジン (MSQ タスク エンジン) と呼ばれるクエリ エンジンが含まれます。 MSQ タスク エンジンは Druid のクエリ機能を拡張するため、外部データを参照するクエリを作成したり、SQL INSERT および REPLACE を使用して取り込みを実行したりできます。基本的に、Druid のネイティブ取り込みで使用される JSON 取り込み仕様を使用する代わりに、SQL ベースの取り込みを実行できます。使いやすい構文に加えて、SQL インターフェイスを使用すると、データの複数のシャッフルを伴う変換を実行できます。 Druid 24.0.0 以降のバッチ取り込みには、マルチステージ クエリ タスク エンジンを使用した SQL ベースの取り込みが推奨されます。ネイティブ バッチと Hadoop ベースの取り込みも引き続きサポートされます。 既知の問題 を確認し、実稼働環境に展開する前にステージング環境で機能をテストすることをお勧めします。マルチステージ クエリ タスク エンジンをプレーン SELECT ステートメント (INSERT ... SELECT や REPLACE ... SELECT ではない) で使用することは実験段階です。 以前のバージョンの Druid からアップグレードする場合、または Docker を使用している場合は、common.runtime.properties ファイル内の druid.extensions.loadlist に druid-multi-stage-query 拡張子を追加する必要があります。 詳細については、SQL ベースの取り込みに関する 概要 ドキュメントを参照してください。 #12524 #12386 #12523 #12589

<a name="24.0.0-new-features-nested-columns-" href="#24.0.0-new-features-nested-columns-">#</a> ネストされた列

Druid は、新しく追加された COMPLEX<json> 列タイプでのネストされたデータ構造の直接保存をサポートするようになりました。 COMPLEX<json> 列には、JSON 形式の構造化データのコピーと、ネストされたリテラル値 (STRING、LONG、および DOUBLE 型) の特殊な内部列とインデックスが格納されます。最適化された仮想列により、Druid は標準の Druid LONG、DOUBLE、STRING 列と一致する速度でこれらの値を読み取り、フィルター処理できます。 新しく追加された Druid SQL、ネイティブ JSON 関数、および仮想列を使用すると、クエリ時に COMPLEX<json> 値を抽出、変換、作成できます。 flattenSpec オブジェクトを使用してネストされたデータを取り込み用に「平坦化」する代わりに、SQL ベースの取り込みの INSERT および REPLACE ステートメントで JSON 関数を使用したり、ネイティブ取り込みの transformSpec で JSON 関数を使用したりすることもできます。 SQL JSON 関数、ネイティブ JSON 関数、ネストされた列、[virtual] を参照してください。 columns](docs/querying/virtual-columns.md#nested-field-virtual-column)、および詳細については 機能の概要 を参照してください。 #12753 #12714 #12753 #12920

<a name="24.0.0-query-engine-updates" href="#24.0.0-query-engine-updates">#</a> クエリ エンジンの更新

<a name="24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters" href="#24.0.0-query-engine-updates-updated-column-indexes-and-query-processing-of-filters">#</a> 列インデックスとフィルターのクエリ処理を更新しました。

列インデックスが非常に柔軟になるように再加工され、最終的には幅広い種類のインデックスをモデル化できるようになります。更新されたインデックスを使用するフィルターを構築するための機構を追加しました。また、他の列実装で組み込みインデックス タイプを実装して、Druid が提供する現在のセット フィルターでインデックスを使用するためのアダプターを提供できるようにしました。 #12388

<a name="24.0.0-query-engine-updates-time-filter-operator" href="#24.0.0-query-engine-updates-time-filter-operator">#</a> 時間フィルター演算子

Druid SQL 演算子 TIME_IN_INTERVAL を使用して、時間に基づいてクエリ結果をフィルターできるようになりました。時間どおりにフィルタリングするには、SQL BETWEEN 演算子よりも TIME_IN_INTERVAL を優先します。詳細については、「日付と時刻関数」(docs/querying/sql-scalar.md#date-and-time-functions) を参照してください。 #12662

<a name="24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter" href="#24.0.0-query-engine-updates-null-values-and-the-%22in%22-filter">#</a> Null 値と「in」フィルター

values 配列に null が含まれている場合、「in」フィルターは NULL 値と一致します。これは、NULL 値と一致しない SQL IN フィルターとは異なります。 詳細については、クエリ フィルター および SQL データ型 を参照してください。 #12863

<a name="24.0.0-query-engine-updates-virtual-columns-in-search-queries" href="#24.0.0-query-engine-updates-virtual-columns-in-search-queries">#</a> 検索クエリの仮想列

以前は、検索クエリ はデータ ソースに存在するディメンションでのみ検索できました。検索クエリは、クエリ内のパラメーターとして 仮想列 をサポートするようになりました。 #12720

<a name="24.0.0-query-engine-updates-optimize-simple-min-%2F-max-sql-queries-on-__time" href="#24.0.0-query-engine-updates-optimize-simple-min-%2F-max-sql-queries-on-__time">#</a> __time で単純な MIN / MAX SQL クエリを最適化します。

select max(__time) from ds のような単純なクエリは、セグメント内の時間ディメンションの並べ替えを利用するために timeBoundary クエリとして実行されるようになりました。機能フラグを設定して、この機能を有効にすることができます。 #12472 #12491

<a name="24.0.0-query-engine-updates-string-aggregation-results" href="#24.0.0-query-engine-updates-string-aggregation-results">#</a> 文字列の集計結果

最初/最後の文字列アグリゲータは、値に基づいてのみ比較するようになりました。以前は、最初/最後の文字列アグリゲーターの値は、最初に _time 列に基づいて比較され、次に値に基づいて比較されました。 既存のクエリがあり、_time 列と値の両方を引き続き使用したい場合は、ORDER BY MAX(timeCol) を使用するようにクエリを更新します。 #12773

<a name="24.0.0-query-engine-updates-reduced-allocations-due-to-jackson-serialization" href="#24.0.0-query-engine-updates-reduced-allocations-due-to-jackson-serialization">#</a> Jackson シリアル化による割り当ての減少

JacksonUtils に新しいヘルパー関数が導入および実装され、再利用が可能になりました。 SerializerProvider オブジェクト。 さらに、GroupByQueryToolChest のマップベースの行に対する下位互換性がデフォルトで無効になり、重い ObjectMapper をコピーする必要がなくなります。管理者が下位互換性を明示的に有効にできるようにする構成オプションが導入されました。 #12468

<a name="24.0.0-query-engine-updates-updated-ipaddress-java-library-" href="#24.0.0-query-engine-updates-updated-ipaddress-java-library-">#</a> IPAddress Java ライブラリを更新しました

IP アドレスを処理するための新しい IPAddress Java ライブラリの依存関係を追加しました。このライブラリには IPv6 サポートが含まれています。さらに、新しいライブラリを使用するために IPv4 機能が移行されました。 #11634

<a name="24.0.0-query-engine-updates-query-performance-improvements" href="#24.0.0-query-engine-updates-query-performance-improvements">#</a> クエリのパフォーマンスの向上

次のように最適化された SQL 操作と関数:

  • ベクトル化された最新の数値アグリゲーター (#12439)
  • RangeSet の isEmpty() および equals() を最適化 (#12477)
  • Yielder オブジェクトの再利用を最適化 (#12475)
  • インデックスを使用した数値列の操作が高速になりました (#12830)
  • 割り当てを削減することで GroupBy を最適化しました。エントリーとキーホルダーを再利用することで割り当てを削減 (#12474)
  • string last aggregator のベクトル化バージョンを追加しました (#12493)
  • IN フィルターに直接 UTF-8 アクセスを追加 (#12517)
  • Druid が同じ基になる行で仮想列を複数回呼び出した場合に備えて、仮想列の出力をキャッシュできるようにしました (#12577)
  • Druid は、IN 結合で可能な場合、結合をフィルターとして書き換えるようになりました (#12225)
  • GroupBy 辞書の自動サイズ設定を追加しました (#12763)
  • Druid は JDBC 接続をブローカー間でより均等に分散するようになりました (#12817)

<a name="24.0.0-improvements-to-ingestion-in-general" href="#24.0.0-improvements-to-ingestion-in-general">#</a> 取り込み全般の改善

このリリースには、取り込み全般に関して次の改善が含まれています。

<a name="24.0.0-improvements-to-ingestion-in-general-increased-robustness-for-task-management" href="#24.0.0-improvements-to-ingestion-in-general-increased-robustness-for-task-management">#</a> タスク管理の堅牢性の向上

サイズが自動的に設定されるさまざまなスレッド プールが不当に大きくなるのを防ぐために、setNumProcessorsPerTask を追加しました。各タスクがマシン全体の唯一のプロセスであるかのようにプールのサイズを設定することは理想的ではありません。大規模なマシンでは、これにより、「ネイティブ スレッドを作成できない」ことによる OutOfMemoryError の一般的な原因が解決されます。 #12592

<a name="24.0.0-improvements-to-ingestion-in-general-avatica-jdbc-driver" href="#24.0.0-improvements-to-ingestion-in-general-avatica-jdbc-driver">#</a> Avatica JDBC ドライバー

JDBC ドライバーは JDBC 標準に従い、Statement と PreparedStatement の 2 種類のステートメントを使用するようになりました。 #12709

<a name="24.0.0-improvements-to-ingestion-in-general-eight-hour-granularity" href="#24.0.0-improvements-to-ingestion-in-general-eight-hour-granularity">#</a> 8 時間の粒度

Druid は EIGHT_HOUR 粒度を受け入れるようになりました。受信データを EIGHT_HOUR バケットに分割したり、クエリ結果を 8 時間単位でグループ化したりできます。 #12717

<a name="24.0.0-ingestion-general" href="#24.0.0-ingestion-general">#</a> 摂取全般

<a name="24.0.0-ingestion-general-updated-avro-extension" href="#24.0.0-ingestion-general-updated-avro-extension">#</a> Avro 拡張機能を更新しました

以前の Avro 拡張機能では、パーサーからオブジェクトがリークしていました。これらのオブジェクトが取り込みに漏洩した場合、オブジェクトは .toString() の値を持つ文字列列として保存されます。この文字列列はアップグレード後も残りますが、GenericRecord.toString ではなく Map.toString() を返します。以前の動作に依存していた場合は、以前のリリースの Avro 拡張機能を使用できます。 #12828

<a name="24.0.0-ingestion-general-sampler-api" href="#24.0.0-ingestion-general-sampler-api">#</a> サンプラー API

サンプラー API には追加の制限 (maxBytesInMemory および maxClientResponseBytes) があります。これらのオプションは、既存のオプション numRows および timeoutMs を拡張します。 maxBytesInMemory を使用すると、サンプリング中に Overlord のメモリ使用量を制御できます。 maxClientResponseBytes は、client が処理したい応答の最大サイズを指定するために使用できます。 #12947

<a name="24.0.0-sql" href="#24.0.0-sql">#</a> SQL

<a name="24.0.0-sql-column-order" href="#24.0.0-sql-column-order">#</a> 列の順序

DruidSchema プロパティと SegmentMetadataQuery プロパティは、列をアルファベット順に並べるのではなく、列の順序を保持するようになりました。これは、クエリの順序が取り込み順序とよりよく一致することを意味します。 #12754

<a name="24.0.0-sql-converting-joins-to-filter" href="#24.0.0-sql-converting-joins-to-filter">#</a> JOIN をフィルターに変換する

クエリの enableRewriteJoinToFilter コンテキスト パラメーターを true に設定することで、実行時に JOIN の一部または全体をフィルターとしてベース テーブルにプッシュすることで、パフォーマンスを向上させることができます。 Druid は、クエリ計算結合が右側からの列を参照する場合に結合フィルターをプッシュダウンするようになりました。 #12749 #12868

<a name="24.0.0-sql-add-is_active-to-sys.segments" href="#24.0.0-sql-add-is_active-to-sys.segments">#</a> is_active を sys.segments に追加します

(is_published = 1 AND is_overshadowed = 0) OR is_realtime = 1) の短縮形として is_active を追加しました。これは、「実際に現在存在しているかどうかに関係なく、クエリ可能であるべきすべてのセグメント」を表します。 #11550

<a name="24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true" href="#24.0.0-sql-%60usenativequeryexplain%60-now-defaults-to-true">#</a> useNativeQueryExplain のデフォルトが true になりました

useNativeQueryExplain プロパティのデフォルトは true になりました。これは、EXPLAIN PLAN FOR が、デフォルトで、Explain Plan を同等のネイティブ クエリの JSON 表現として返すことを意味します。詳細については、「ブローカー生成クエリ構成の補足」(/docs/configuration/index.md) を参照してください。 #12936

<a name="24.0.0-inline-query-engine" href="#24.0.0-inline-query-engine">#</a> druid クエリ エンジンを使用したインライン データでのクエリの実行

select 1 など、テーブルを参照しない一部のクエリは、実行前に常に InlineDataSource を使用してネイティブ Druid クエリに変換されるようになりました。 SELECT (1, 2) などのクエリで変換できない場合は、エラーが発生します。以前のバージョンでは、このクエリは引き続き実行されます。 #12897

<a name="24.0.0-coordinator%2Foverlord" href="#24.0.0-coordinator%2Foverlord">#</a> コーディネーター/オーバーロード

<a name="24.0.0-coordinator%2Foverlord-you-can-configure-the-coordinator-to-kill-segments-in-the-future" href="#24.0.0-coordinator%2Foverlord-you-can-configure-the-coordinator-to-kill-segments-in-the-future">#</a> 将来、セグメントを強制終了するようにコーディネーターを構成できます。

druid.coordinator.kill.durationToRetain を負のピリオドに設定して、interval_end が将来の日付であるセグメントを強制終了するように Druid クラスターを構成できるようになりました。たとえば、PT-24H では、システムによって kill タスクが生成された時点で、interval_end の日付が 24 時間以内である場合に、セグメントを強制終了できます。 クラスター オペレーターは、新しい構成 druid.coordinator.kill.ignoreDurationToRetain=true を設定することで、druid.coordinator.kill.durationToRetain を完全に無視することもできます。これにより、強制終了するセグメントを探すときに interval_end の日付が無視され、代わりに未使用のマークが付けられたセグメントを強制終了できます。この新しい構成はデフォルトでオフになっているため、クラスター オペレーターは有効にする前にリスクを十分に理解し、受け入れる必要があります。

<a name="24.0.0-coordinator%2Foverlord-improved-overlord-stability" href="#24.0.0-coordinator%2Foverlord-improved-overlord-stability">#</a> Overlord の安定性の向上

管理スレッドとクラスターからのステータス更新の受信の間の競合が減少しました。これにより、タスク数が多い (1000 以上) 場合の、オーバーロードとクラスター内のすべてのタスクの安定性が向上します。 #12099

<a name="24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging" href="#24.0.0-coordinator%2Foverlord-improved-coordinator-segment-logging">#</a> コーディネーター セグメントのログの改善

現在のレプリケーション レベルを含むようにコーディネーターのロード ルールのログを更新しました。一部のログ メッセージに欠落していたセグメント ID と階層情報が追加されました。 #12511

<a name="24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage" href="#24.0.0-coordinator%2Foverlord-optimized-overlord-get-tasks-memory-usage">#</a> 最適化されたオーバーロード GET タスクのメモリ使用量

Web コンソールが Overlord の GET タスク API を間接的に呼び出すことによって引き起こされる重大なメモリ オーバーヘッドに対処しました。これにより、取り込みタブを複数回開いたときに応答しなくなったり、オーバーロードのエラーが発生したりする可能性がありました。 #12404

<a name="24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals" href="#24.0.0-coordinator%2Foverlord-reduced-time-to-create-intervals">#</a> 間隔の作成時間の短縮

間隔の作成にかかる時間を削減してセグメント コストの計算時間を最適化するには、セグメント間隔をプリミティブから毎回作成するのではなく格納し、間隔をインターニングすることで間隔を格納するメモリ オーバーヘッドを削減します。セグメントの間隔のセットはカーディナリティが低いです。 #12670

<a name="24.0.0--brokers%2Foverlord" href="#24.0.0--brokers%2Foverlord">#</a> ブローカー/オーバーロード

ブローカーは現在、デフォルトでクエリごとにキューに入れられる最大値が 25MB になっています。以前は、デフォルトの制限はありませんでした。ユースケースによっては、特に大規模な結果セットまたは大量の中間データがある場合には、値を増やす必要がある場合があります。使用可能な最大メモリを調整するには、druid.broker.http.maxQueuedBytes プロパティを使用します。 詳細については、「構成リファレンス」(docs/configuration/index.md) を参照してください。

新しいクエリ ビューを使用すると、古いクエリ ビューと同様に、/druid/v2/sql/task および /druid/indexer/v1/task/* API を使用したマルチステージのタスクベースのクエリ、およびネイティブ クエリと SQL ネイティブ クエリを実行できます。 sql-msq-task ベースのクエリの重要な点は、クエリが長時間実行される可能性があることです。これにより、以下を含む (ただしこれらに限定されない) 多くの UX の変更が生じ、または必要となりました。

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-tabs" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-tabs">#</a> 個のタブ

マルチステージ クエリ タスク エンジンで実行されるクエリには、概要進行状況バーに表示される詳細な進行状況レポートと、各ステップのカウンターの概要を提供する詳細な実行テーブルが表示されます。

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-error-and-warning-reports" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-error-and-warning-reports">#</a> エラーと警告のレポート

マルチステージ クエリ タスク エンジンで実行されるクエリは、何か問題が発生した場合にユーザー フレンドリーな警告とエラーを表示します。 新しいクエリ ビューには、スタック トレースを含む完全な詳細でこれらを視覚化するコンポーネントが含まれています。

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-recent-query-tasks-panel" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-recent-query-tasks-panel">#</a> 最近のクエリ タスク パネル

マルチステージ クエリ タスク エンジンで実行されるクエリはタスクです。これにより、現在実行中のクエリと最近実行されたクエリを表示できるようになります。 [最近のクエリ タスク] パネル内のクエリについては、その実行の詳細を表示したり、新しいタブとしてアタッチしてクエリの反復を続行したりすることもできます。また、トラブルシューティングに使用する特定のクエリの重要な詳細がすべて含まれている JSON ファイルである「クエリ詳細アーカイブ」をダウンロードすることもできます。

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-connect-external-data-flow" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-connect-external-data-flow">#</a> 外部データ フローを接続する

外部データ フローを接続すると、サンプラーを使用してソース データをサンプリングし、そのスキーマを決定し、取り込みジョブを開始する前にユースケースに合わせて編集できる完全な形式の SQL クエリを生成できます。このポイントアンド click フローにより、入力を大幅に節約できます。

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-preview-button" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-preview-button">#</a> プレビュー ボタン

INSERT または REPLACE SQL クエリを入力すると、[プレビュー] ボタンが表示されます。 Cliボタンをクリックして INSERT または REPLACE 句を削除し、制限付きの「インライン」クエリとしてクエリを実行します。これにより、Druid が SQL クエリからすべての変換を適用した後のデータの形状を把握できます。

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-results-table" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-results-table">#</a> 結果テーブル

Web コンソールには、ノートブックおよび CTE ユーザー向けの UI アフォーダンスがいくつか追加されました。ヘルパー クエリ (クエリを保持する折りたたみ可能な要素) は、WITH ステートメントで定義されたのと同じように、メイン クエリから参照できます。複雑なクエリを作成する場合、クエリを複数のクエリに分割して各部分を個別にプレビューすると便利です。

<a name="24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-Additional-web-console-tools" href="#24.0.0--brokers%2Foverlord-web-console-new-query-view-%28workbenchview%29-with-tabs-and-long-running-query-support-Additional-web-console-tools">#</a> 追加の Web コンソール ツール

<a name="24.0.0--brokers%2Foverlord-web-console-new-sql-based-data-loader" href="#24.0.0--brokers%2Foverlord-web-console-new-sql-based-data-loader">#</a> 新しい SQL ベースのデータ ローダー

データ ローダーは、ユーザーがポイントと click およびクイック プレビューを使用して JSON 取り込み仕様を作成するのに役立つ GUI ウィザードとして存在します。 SQL データ ローダーは、SQL ベースの取り込みに類似したものです。 ネイティブ ベースのデータ ローダーと同様に、SQL ベースのデータ ローダーは、すべての状態を SQL クエリ自体に保存します。どの段階でもクエリを直接操作することを選択できます。データローダーが 外部データの接続 ワークフローとどのように異なるかについて詳しくは、(#12919) を参照してください。

<a name="24.0.0-upgrading-to-24.0-behavior-for-unused-segments" href="#24.0.0-upgrading-to-24.0-behavior-for-unused-segments">#</a> 未使用セグメントの動作

Druid は、未使用としてマークされたセグメントを自動的に保持します。以前は、Druid は未使用のセグメントの保持期間が経過すると、メタデータ ストアとディープ ストレージから未使用のセグメントを完全に削除していました。この動作は 0.23.0 から元に戻りました。 #12693

<a name="24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60" href="#24.0.0-upgrading-to-24.0-default-for-%60druid.processing.fifo%60">#</a> druid.processing.fifo のデフォルト

druid.processing.fifo のデフォルトは true になりました。これは、同じ優先度のタスクが FIFO 方式で処理されることを意味します。ほとんどの使用例では、この変更により、負荷の高いクラスターのパフォーマンスが向上します。 #12571

<a name="24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure" href="#24.0.0-upgrading-to-24.0-update-to-jdbc-statement-closure">#</a> JDBC ステートメントのクロージャーを更新

以前のリリースでは、Druid は ResultSet が閉じられると自動的に JDBC ステートメントを閉じました。 Druid は EOF に ResultSet を閉じました。ドルイドは例外が発生した場合にステートメントを閉じました。ただし、この動作は標準ではありません。 このリリースでは、Druid の JDBC ドライバーは JDBC 標準にさらに厳密に従っています。 ResultSet は EOF で自動的に閉じますが、Statement または PreparedStatement は閉じません。コードでは、try-with-resources ブロックを使用して、これらのステートメントを閉じる必要があります。 PreparedStatement を異なるパラメータで複数回使用できるようになりました。 (以前は、ResultSet を閉じると PreparedStatement が閉じられるため、これは当てはまりませんでした。) Statement または PreparedStatement の呼び出しでエラーが発生した場合でも、client コードはステートメントを明示的に閉じる必要があります。 JDBC 標準によれば、ステートメントはエラー時に自動的に閉じられません。これにより、失敗したステートメントを閉じる前に、そのステートメントに関する情報を取得できます。 古い動作に依存するコードがある場合は、コードを変更して必要な close ステートメントを追加する必要がある場合があります。 #12709
