#ドルイドドルイド-27.0.0

Apache Druid 27.0.0 には、316 を超える新機能、バグ修正、パフォーマンス強化、ドキュメントの改善、および 50 人の寄稿者による追加のテスト カバレッジが含まれています。

[追加の詳細については、バグ修正 を含む変更の完全なセットを参照してください](https://github.com/apache/druid/issues?q=is%3Aclosed+milestone%3A27.0+sort%3Aupdated-desc+)。

Druid 27.0.0 にアップグレードする前に、アップグレードに関する注意事項と互換性のない変更を確認してください。

<a name="27.0.0-highlights-new-explore-view-in-the-web-console-%28experimental%29" href="#27.0.0-highlights-new-explore-view-in-the-web-console-%28experimental%29">#</a> Web コンソールの新しい Explore ビュー (実験的)

Explore ビューは、Web コンソールに対するシンプルでステートレスな SQL ベースのデータ探索ビューです。これにより、ユーザーは (SQL を書いてテーブルを確認する代わりに) ポイント アンド click の操作と視覚化を使用して Druid 内のデータを探索できるようになります。これにより、Druid を初めて使用するユーザーにとっては価値実現までの時間が短縮され、Druid のベテランは関心のあるデータをすばやくグラフ化できるようになります。

Explore ビューには、ヘッダーの More (...) メニューからアクセスできます。

<a name="27.0.0-highlights-query-from-deep-storage-%28experimental%29" href="#27.0.0-highlights-query-from-deep-storage-%28experimental%29">#</a> ディープ ストレージからのクエリ (実験的)

Druid は、ディープ ストレージにのみ保存されているセグメントのクエリをサポートするようになりました。ディープ ストレージからクエリを実行すると、より多くのデータに対応するために履歴プロセスを拡張する必要がなく、クエリに使用できるより大きなデータをクエリできます。潜在的なストレージ節約を活用するには、すべてのセグメントを履歴プロセスにロードしないようにロード ルールを構成してください。

ブローカーがクエリを計画できるように、データソースの少なくとも 1 つのセグメントを履歴プロセスにロードする必要があることに注意してください。ただし、どのセグメントでも構いません。

詳細については、以下を参照してください。

  • ディープストレージからのクエリ
  • ディープストレージからのクエリチュートリアル

<a name="27.0.0-highlights-schema-auto-discovery-and-array-column-types" href="#27.0.0-highlights-schema-auto-discovery-and-array-column-types">#</a> スキーマの自動検出と配列の列タイプ

タイプ認識スキーマ自動検出が一般提供されるようになりました。 Druid は、手動でスキーマを定義するのではなく、取り込んだデータのスキーマを決定できます。

型を認識したスキーマ検出の改善の一環として、配列列型が一般提供されるようになりました。 Druid は、auto 列タイプのタイプ認識スキーマ自動検出を使用してデータを取り込むときに、スキーマの列タイプを決定し、それらをこれらの配列列タイプに割り当てることができます。

この機能の詳細については、次を参照してください。

  • スキーマ自動検出用の 26.0.0 release note。
  • 配列列タイプの 26.0.0 release note。

<a name="27.0.0-highlights-smart-segment-loading" href="#27.0.0-highlights-smart-segment-loading">#</a> スマート セグメントの読み込み

コーディネーターはより安定し、使いやすくなりました。新しい SmartSegmentLoading モードでは、パフォーマンスを最大化するいくつかの構成の値を動的に計算します。 コーディネーターは、クラスターに既にいくつかのレプリカがロードされているセグメントのロードよりも、より新しいセグメントや完全に使用できないセグメントのロードを優先できるようになりました。また、以前の実行で行われた決定を再評価し、不要になった操作をキャンセルすることもできます。さらに、セグメントのバランシングによって開始される移動操作は、使用できないセグメントの負荷と競合しないため、クラスター内の変更に対する反応時間が短縮され、セグメント割り当ての決定が高速化されます。

さらに、リーダーシップの変更の影響は少なくなり、コーディネーターの実行中に再選が行われた場合でも、コーディネーターは行き詰まることはありません。

最後に、cost バランサー戦略のパフォーマンスが大幅に向上し、1 回のコーディネーター実行でより多くのセグメントを移動できるようになりました。これらの改善は、cachingCost 戦略からアイデアを借用して行われました。 cachingCost は廃止されたため、cachingCost の代わりに cost を使用することをお勧めします。

詳細については、以下を参照してください。

  • スマート セグメントのロードに関連する構成変更に関するアップグレードに関するメモ
  • 新しいコーディネーター メトリクス
  • スマートセグメントロードドキュメント

<a name="27.0.0-highlights-smart-segment-loading-new-query-filters" href="#27.0.0-highlights-smart-segment-loading-new-query-filters">#</a> 新しいクエリ フィルタ

Druid は次のフィルターをサポートするようになりました。

  • 等価: セレクター フィルターの代わりに使用します。 null 値と一致することはありません。
  • Null: Null 値と一致します。セレクターフィルターの代わりに使用します。
  • 範囲: ディメンション値の範囲でフィルターします。バインドされたフィルターの代わりに使用します。 null 値と一致することはありません

Druid の SQL プランナーは、druid.generic.useDefaultValueForNull=false または SQL クエリ コンテキストで sqlUseBoundAndSelectors が false に設定されている場合、デフォルトで古いフィルターの代わりにこれらの新しいフィルターを使用することに注意してください。

これらのフィルターを使用すると、前のセレクターとバインドされたフィルターで文字列のみをフィルターする代わりに、ARRAY 列の等価性と範囲をフィルター処理することができます。

詳細については、「クエリ フィルタ」(https://druid.apache.org/docs/latest/querying/filters.html) を参照してください。

<a name="27.0.0-highlights-smart-segment-loading-guardrail-for-subquery-results" href="#27.0.0-highlights-smart-segment-loading-guardrail-for-subquery-results">#</a> サブクエリ結果のガードレール

ユーザーは、ブローカーの構成で druid.server.http.maxSubqueryRows を設定するか、クエリ コンテキストで maxSubqueryRows を設定することで、サブクエリの結果が設定されたバイト数を超えないようにガードレールを追加できるようになりました。このガードレールは、行ベースの制限よりも推奨されます。

この機能は現時点では実験的であり、クエリによって消費される結果の正確なサイズを取得できない場合に備えて、デフォルトで行ベースの制限に戻ります。

<a name="27.0.0-additional-features-and-improvements-sql-based-ingestion-improved-query-planning-behavior" href="#27.0.0-additional-features-and-improvements-sql-based-ingestion-improved-query-planning-behavior">#</a> クエリ プランニング動作の改善

CLUSTERED BY 列に降順が含まれている場合、Druid はクエリ プランニングに失敗するようになりました。 以前は、CLUSTERED BY 列に降順が含まれているかどうかをクエリで正常に計画できました。

MSQ 障害 InsertCannotOrderByDescending は非推奨になりました。 CLUSTERED BY 式を含む INSERT または REPLACE クエリを降順にすることはできません。 Druid のセグメント生成コードは昇順のみをサポートします。障害の代わりに、Druid はクエリ ValidationException をスローするようになりました。

<a name="27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations" href="#27.0.0-additional-features-and-improvements-querying-new-broker-configuration-for-sql-schema-migrations">#</a> SQL スキーマ移行のための新しいブローカー構成

セグメント間のスキーマ変更に対する Druid の反応をより適切に制御できるようになりました。これにより、以前の列に LONG 値が含まれており、新しいセグメントに STRING が含まれている場合など、新しいセグメントに異なる型が導入された場合に、クエリの回復力が向上します。

新しいブローカー構成 druid.sql.planner.metadataColumnTypeMergePolicy を使用して、セグメント間の差異に直面した場合に SQL テーブル スキーマの列タイプを計算する方法を制御します。

次のいずれかに設定します。

  • leastRestrictive: すべてのセグメントが新しいタイプに再インデックス付けされた場合にのみスキーマが更新されます。
  • latestInterval: SQL スキーマは、新しいスキーマを使用した最初のジョブがデータの最新の時間間隔でセグメントをパブリッシュするとすぐに更新されます。

leastRestrictive では、クエリ時の動作が向上し、latestInterval の使用時に発生する可能性のあるクエリ時のエラーの一部が排除されます。

<a name="27.0.0-additional-features-and-improvements-developer-notes" href="#27.0.0-additional-features-and-improvements-developer-notes">#</a> 開発者向けメモ

表面化したエラーに対して、新しい統合例外 DruidException が導入されました。これは、エラー メッセージを報告する古い方法と部分的に互換性があります。応答コードは同じままで、errorMessage を含め、以前に応答に存在していたすべてのフィールドは引き続き存在し、値が設定されます。一部のエラー メッセージは人間が利用しやすいように変更されており、場合によってはメッセージが再構築されています。応答コードには影響がありません。

org.apache.druid.common.exception.DruidException は非推奨となり、より包括的な org.apache.druid.error.DruidException が優先されます。

org.apache.druid.metadata.EntryExistsException は非推奨であり、将来のリリースでは削除される予定です。 #14004 #14554

<a name="27.0.0-upgrade-notes-and-incompatible-changes" href="#27.0.0-upgrade-notes-and-incompatible-changes">#</a> アップグレードに関する注意事項と互換性のない変更点

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes">#</a> アップグレードに関する注意事項

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-hadoop-2-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-hadoop-2-deprecated">#</a> Hadoop 2 は非推奨になりました

Druid が使用する重要な依存ライブラリの多くは、Hadoop 2 をサポートしなくなりました。Druid を最新の状態に保ち、セキュリティの脆弱性を軽減する手段を確保するために、コミュニティは、このリリースから Hadoop 2.x リリースのサポートを廃止することを決定しました。 Druid 28.x 以降、サポートされている Hadoop バージョンは Hadoop 3.x のみです。

現在、取り込みに Hadoop 2.x を使用している場合は、SQL ベースの取り込みまたはネイティブ取り込みへの移行を検討してください。 Druid インジェストに移行できない場合は、次の Druid リリースにアップグレードする前に、Hadoop インフラストラクチャのアップグレードを計画してください。

druid 27 は Hadoop 2 と互換性がないことに注意してください。27.0.0 にアップグレードする前に、Hadoop クラスターを 3.x にアップグレードする必要があります。または、druid 27 ソース アーティファクトから Hadoop 2 プロファイルを明示的に選択して、Hadoop 2 と互換性のあるディストリビューションを構築することもできます。

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-worker-input-bytes-for-sql-based-ingestion" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-worker-input-bytes-for-sql-based-ingestion">#</a> SQL ベースの取り込みのワーカー入力バイト

SQL ベースの取り込みの各ワーカーの最大入力バイトは 512 MiB になりました (以前は 10 GiB)。

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-parameter-execution-changes-for-kafka" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-parameter-execution-changes-for-kafka">#</a> Kafka のパラメーター実行の変更

Kafka の組み込み FileConfigProvider を使用する場合、補間は Kafka プロバイダーに渡されるのではなく、JsonConfigurator によってインターセプトされるようになりました。これにより、既存のデプロイメントが破壊されます。

詳細については、KIP-297 を参照してください。

v1 レガシー エンジンを使用した GroupBy クエリは非推奨になりました。将来のリリースでは削除される予定です。代わりに v2 を使用してください。 v2 がデフォルトの GroupBy エンジンであることに注意してください。

詳細については、「GroupBy クエリ」を参照してください。

プッシュベースのリアルタイム取り込みのサポートは非推奨になりました。将来のリリースでは削除される予定です。

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60cachingcost%60-segment-balancing-strategy-deprecated" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-%60cachingcost%60-segment-balancing-strategy-deprecated">#</a> cachingCost セグメント バランシング ストラテジーは非推奨になりました

cachingCost 戦略は非推奨となり、将来のリリースでは削除される予定です。代わりに、cost などの代替セグメント バランシング戦略を使用してください。

<a name="27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-segment-loading-config-changes" href="#27.0.0-upgrade-notes-and-incompatible-changes-upgrade-notes-segment-loading-config-changes">#</a> セグメント読み込み構成の変更

次のセグメント関連の構成は非推奨となり、将来のリリースでは削除される予定です。

  • maxSegmentsInNodeLoadingQueue
  • maxSegmentsToMove
  • replicationThrottleLimit
  • useRoundRobinSegmentAssignment
  • replicantLifetime
  • maxNonPrimaryReplicantsToLoad
  • decommissioningMaxPercentOfMaxSegmentsToMove

代わりに、これらの変数の値を自動的に計算する smartSegmentLoading モードを使用してください。

さらに、次のコーディネーターの動的構成のデフォルトが変更されました。

  • maxsegmentsInNodeLoadingQueue : 500、以前は 100
  • maxSegmentsToMove: 100、以前は 5
  • replicationThrottleLimit: 500、以前は 10

これらの新しいデフォルトにより、ほとんどの使用例でパフォーマンスが向上します。
