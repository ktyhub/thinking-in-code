mempalace v3.3.6

パッチ 公開日2026年6月6日 出典MemPalace/mempalace 英語原文

#メンパレスv3.3.6 3.3.6 は機能リリースです。 このサイクルのヘッドライン作品: デフォルトでの多言語リコール (Embeddinggemma が MiniLM に置き換わります、言語間のコサインが 0.35 → 0.88 にジャンプします)、リビングメモリー グラフの最初のカット (翼内の廊下、翼を横切るトンネル、ヘビアン増強 + エビングハウス減衰により、接続は使用すると強化され、使用しないと消えます)、オフィス文書マイニング (PDF、DOCX、PPTX、XLSX、RTF、新しい --mode extract による EPUB)、仮想行番号 + 正確な日付の正確な行範囲を引用する外科用クローゼット ポインター、および「コード」を廊下から排除し、「クロード コード」をアトミックに保つエンティティ検出クリーンアップ パス。 約束は変わっていない。すべての単語が正確に保存されます。すべてがマシン上に残ります。テレメトリーはありません。リリースごとに、すでにあるものに磨きをかけます。

機能

  • --mode extract による Office ドキュメント マイニング。 新しい mempalace mine <dir> --mode extract は、既存のソース コード/テキスト パスに加えて、PDF、Word (.docx)、PowerPoint (.pptx)、Excel (.xlsx)、RTF、および EPUB ブックを取り込みます。 pip install mempalace[extract] でインストール — RTF の場合は striprtf をプルし、バイナリ形式の場合は MarkItDown ([docx,pdf,pptx,xlsx] サブエクストラを含む) をプルします。 Python 3.9 ユーザーは、MarkItDown が 3.10+ を必要とするため、RTF カバレッジのみを取得します。抽出パスのドロワーには extract_mode メタデータが含まれるため、コンボマイナーは「すでにマイニングされていますか?」チェックとドロワー ID の生成はモードごとに分離されたままになります (#1528)。 (#1555)
  • 仮想行番号 + 外科用クローゼット ポインタ。 格納された引き出しには仮想行番号が付けられるようになり、読み取り CLI 動詞とクローゼット ポインタで正確な行範囲を引用できるようになりました。クローゼット ポインター (Tier 6a) には、ファイル名とコンテンツ本文の日付解析 (python-dateutil がコア ディップ) から得られる日付 + 行範囲情報が含まれるため、MemPalace は、単に「この引き出しのどこか」ではなく、正確な日付の正確な行を示すことができます。 (#1555、#1584)
  • ウィング内の廊下 2 つのエンティティ (人、プロジェクト、トピック) が同じ引き出し内で同時に発生する場合、マイナーは「廊下」、つまりウィング内でそれらを接続するグラフ エッジを記録するようになりました。 compute_hallways_for_wing のポストマイニング ステップの一部として自動的に計算されるため、別個のコマンドを必要とせず、新しいコンテンツによってグラフが段階的に拡大します。 1 つの宮殿内のクロスルーム エンティティ ナビゲーションの基盤。 (#1558、#1560)
  • 廊下からプロモートされるクロスウィング トンネル。 同じエンティティが複数のウィングにまたがる廊下に表示される場合、MemPalace はそれを自動的にトンネルにプロモートするようになりました。これにより、誰かが create_tunnel を手動で呼び出すことなく、クエリが 1 人のユーザーのウィングからそのユーザーが表示されるプロジェクト ウィングにホップできるようになります。既存の compute_topic_tunnels パスからのトピック トンネルは変更されません。 (#1565)
  • 生きた記憶のダイナミクス (ヘブの増強 + エビングハウスの減衰)。 廊下とトンネルは、同じ接続が新しいコンテンツ (「ワイヤーを一緒に発火するもの」) によって強化されるたびに強化され、接続が入ってくる引き出しに表示されなくなると徐々に消えていきます。ナビゲーション ウェイトは静的ではなく実際の宮殿の使用状況を追跡するため、宮殿が実際に使用されるにつれて検索ランキングが時間の経過とともに向上します。 (#1578)
  • API ツールのトランスクリプトは wing_api に自動ルーティングされます。 API スタイルの AI ツール (Claude Code、Claude.ai、ChatGPT、Slack ボット エクスポート、汎用 OpenAI 形状 JSON など) からの会話トランスクリプトは、人間の会話ウィングに混合されるのではなく、専用の wing_api にルーティングされるようになりました。ツール呼び出しトラフィックが個人/プロジェクトの翼を汚染するのを防ぎ、「私が言ったこと」と「エージェントが言ったこと」を探すときの検索精度を向上させます。 (#1236)
  • 新規インストールのデフォルトの多言語埋め込み: embeddinggemma-300m ONNX (q8、MRL→384-dim)。 MemPalace の以前のエンベッダー (all-MiniLM-L6-v2) は英語のみでトレーニングされています。対訳テキストの言語間のコサイン類似度は、DE/FR/HI/IT/KO/RU 全体で平均 0.35 (RU は 0.17、ほぼ直交）。ロシア語を話すユーザーは事実上自分の記憶を見つけることができず、これは CLAUDE.md の「100% 再現」という設計の約束を破ることになります。 mempalace/embedding.py の新しい EmbeddinggemmaONNX クラスにより、これが 0.88 平均になります (直接 ONNX ランタイム テストにより Ollama gguf に対してロスレスで検証済み)。初回使用時に huggingface_hub 経由で onnx-community/embeddinggemma-300m-ONNX (~300 MB) を遅延ダウンロードします。出力は Matryoshka Representation Learning によって 384 次元に切り詰められるため、モデルは ChromaDB の 384 次元コレクションのドロップインとなり、スキーマの変更はありません。 Sim プレフィックス ("task: sentence similarity | query: ") が自動的に適用されます。 オンボーディング (python -m mempalace.onboarding) では、デフォルトとして多言語モデルが提供されるようになりました。これを選択すると、embedding_model: embeddinggemma から config.json に書き込まれるため、後続の実行では再プロンプトが表示されずにそれが選択されます。環境変数を設定しなかった、またはオンボードを実行しなかった既存のインストールは、minilm (バック互換) のままになります。 MEMPALACE_EMBEDDING_MODEL=minilm|embeddinggemma は両方をオーバーライドします。既存の宮殿でモデルを切り替えるには、再埋め込みが必要です。変更後に mempalace repair rebuild-index を実行します。 (#1483)
  • 多言語の DEP がコアに移動しました。 huggingface_hub、tokenizers、および numpy が必須の DEP になったので、pip install mempalace 以降は多言語パスがそのまま機能します。 [multilingual] エクストラは、インストール スクリプトとの逆互換のための no-op エイリアスとして保持されます。 300 MB ONNX モデル自体は、インストール時ではなく、初回使用時に引き続き遅延ダウンロードされます。
  • フレンドリーな ChromaDB EF 名の不一致エラー。 rebuild-index を実行せずに既存のパレスで MEMPALACE_EMBEDDING_MODEL を切り替えると、ChromaDB の裸の Embedding function conflict: new: X vs persisted: Y ValueError が以前に明らかになりました。正確ではありますが、回復方法はユーザーに示されていませんでした。 ChromaBackend.get_collection() はそのエラーをラップし、環境変数を元に戻すか、mempalace repair rebuild-index --palace <path> を実行するかの両方のオプションを示します。 (#1483)
  • hooks.auto_save はサイレント モード セッション用に切り替えます。 新しい設定ノブ (および保存フックを介した --silent CLI フラグ配線) により、ユーザーは Stop / PreCompact での日記の自動保存をオプトアウトできます。すべての会話をキャプチャしたくない「サイレント モード」セッションに役立ちます。デフォルトの動作は変更されていません。明示的に無効にしない限り、自動保存は引き続き実行されます。 (#711)
  • エンティティ検出から一般的な英語コンテンツの単語をフィルタリングします。 高頻度の英語コンテンツの単語 (「システム」、「ユーザー」、「メモリ」、「プロジェクト」、「コンテキスト」など) が、ドロワーごとの検出器によってエンティティとしてタグ付けされ、エンティティ レジストリを「人」として汚染していました。出荷された COCA ワードリスト (上位 N コンテンツワード) はエンティティの分類中に参照されるようになり、これらはレジストリに到達する前にフィルタリングされます。バンドルされた単語リスト内の不正な形式の JSON に対して強化されました。 (#1605)
  • 私の時点では大文字と小文字を区別しないエンティティ マッチング。 最初のパレス ビルド (mempalace init) はエンティティ名の大文字と小文字を区別せずに一致しましたが、インクリメンタル マイニング中に使用されるドロワーごとのタガーはそうではありませんでした。そのため、同じ人物が init と取り込みの間で異なるタグ付けが行われました (「Aya」と「aya」は別個のエンティティになりました)。インクリメンタル タガーは大文字と小文字を区別しないマッチャーをミラーリングし、パレスのライフサイクル全体でエンティティ タグの一貫性を復元します。 (#1557)

バグ修正

  • 3 つの upsert パスでのサイレント データ損失。 3 つの upsert サイト (ファイル インジェスト、会話インジェスト、および 1 つの修復ブランチ) が、チャンクされていないコンテンツでエンベッダーを呼び出し、エンベッダーの最大トークン制限に達したときにサイレントに切り詰めていました。長い引き出しは、先頭セクションのみがインデックス付けされた状態でランディングされ、長文コンテンツの「100% 再現率」の約束を破っていました。 3 つすべてが最初にチャンカーを介してルーティングされるため、完全なドキュメントが埋め込まれて保存されます。 (#1540、#1539 のフォローアップ)
  • 段落チャンカーは、長い段落に対して特大のチャンクを出力しました。 段落スプリッターは、段落が常に CHUNK_SIZE より短いと想定し、段落全体を出力しました。長い段落 (法律文書、緻密な技術文書) ​​は、エンベッダーのコンテキスト ウィンドウを静かに超えていました。スプリッターは、CHUNK_SIZE を尊重するために、放出された各チャンクをハードキャップするようになりました。 (#1538、#1534 を修正)
  • ファイルごとのチャンク キャップがハードコードされており、大規模なトランスクリプトには低すぎます。 ソース コード用に調整された値でファイルごとのチャンクに安全制限が設定されています。非常に大規模な会話トランスクリプトをマイニングすると、その上限を超えて尻尾が静かに落ちました。現実的なトランスクリプト サイズをカバーするためにデフォルト値を上げて設定できるようになりました。 (#1554、#1455を修正)
  • Windows 上のフック サブプロセス / ChromaDB デッドロック。 Windows 上で Stop/PreCompact フックがすでに開いている ChromaDB client に対してデッドロックし、ホスト (クロード コード) がフックで待機したままになる可能性があります。 3 つの部分からなる修正: 鉱山ロック再利用時の古い PID タイムアウト、MCP サーバーのアイドル終了パス、ホストが回復できるようにデッドロック パターンが検出されたときの構造化エラー。 (#1562、#1552 を修正)
  • create_tunnel はハイフンで区切られたウィング名を破損しました。 エンドポイント パーサーが - で分割されたため、名前にハイフンが含まれるウィング (mem-palace、my-app) は名前の途中で切り詰められ、トンネルは存在しないエンドポイントを指していました。エンドポイント解析では完全なスラッグが保存されるようになりました。 (#1529、#1504 を修正)
  • MCP ナレッジ グラフ キャッシュは、シンボリックリンクされた/大文字と小文字が異なるパレス パスに対して重複したグラフを生成しました。 キャッシュ キーは生のパス文字列であったため、/Users/me/.mempalace/palace および /Users/me/.mempalace/Palace (macOS では大文字と小文字が区別される)、またはシンボリックリンクされたエイリアスにより、同じ SQLite ファイルを指す 2 つの個別のキャッシュされた KnowledgeGraph インスタンスが生成され、古い読み取りのリスクがありました。キャッシュは realpath + normcase によって正規化されるようになり、単一の正規キーに集約されるようになりました。 (#1383、#1372 を修正)
  • 保存フックのハイフンで囲まれたプロジェクト フォルダー名は切り詰められました。 ウィング名パーサーは - で分割し、最初のセグメントのみを保持していたため、mem-palace は mem になりました。修正により、プロジェクト フォルダーの完全なスラッグが保存されるため、ハイフンで囲まれたパレスはフック呼び出し全体で一貫性を保ちます。 (#1424、#1410を修正)
  • マイナーはシンボリックリンクを黙ってスキップしました。 ユーザーは、マイニング後にデータが欠落していることに混乱しました。マイナーはシンボリックリンクを表示せずにスキップしていました。スキップされた各シンボリックリンクを理由とともにログに記録するので、ギャップが見えるようになります。 (#1466、#1462を修正)
  • ホストからリークされた PYTHONPATH は、インポート時に MemPalace 独自のモジュールをシャドウする可能性があります。 パッケージ __init__ は、インポート時にリークされたエントリを削除するようになり、インポートされた MemPalace が常にインストールされたものになります。 (#1439、#1423 を修正)
  • macOS の標準 bash フック スクリプト。 フック スクリプトは mapfile (bash 4+) を使用し、macOS の標準 /bin/bash 3.2 を破りました。 sed パイプラインに切り替えたので、フックはすぐにすべての Mac で動作します。 (#1441、#1440を修正)
  • プラグインの停止/PreCompact フックは、スタックした子で無期限にハングする可能性があります。 制限されたタイムアウトにより、MemPalace の子プロセスが異常な場合でも、ホストが常に前進できることが保証されます。 (#1470、#1465を修正)
  • MCP ハンドラーは、不正な入力に対して構造化 JSON-RPC エラーを返すようになりました。 不明なパラメーター名は、非構造化 Python TypeError ではなく -32602 Invalid params を返しました。間違った形状のパラメータは、生のトレースバックではなく構造化エラーを返します。 (#1500、#1513)
  • CLI は、「宮殿が存在しない」と「宮殿は存在するが空である」を区別しました。 新しいユーザーには同じように見える 2 つの状態が、それぞれのアクション可能な次のステップのメッセージとともに個別にレポートされるようになりました。 (#1532、#1498 を修正)
  • mempalace repair パス後: VACUUM + FTS5 再構築 パレス修復後、SQLite ナレッジ グラフ ファイルには断片化されたページと古い FTS5 インデックスが保持されていました。 VACUUM を実行し、最後に FTS5 を再構築すると、ディスクが再利用され、検索パフォーマンスが回復します。 (#1523)
  • Convo miner モードの分離。 「すでにマイニングされていますか?」チェックとドロワー ID の生成は extract_mode を無視したため、モードを切り替えると同じコンテンツ (データ重複) が再マイニングされるか、モード間でドロワー ID が衝突しました。モードによるスコープ設定により、各モードのドロワーが分離され、重複排除が正しく行われます。 (#1528、#1505を修正)
  • 私の最後に FTS5 を検証します。 マイニングでは、ポストステップとして FTS5 インデックスの整合性を検証するようになりました。これにより、破損は読み取り時ではなく書き込み時に検出されます。 (#1548、#1537 を修正)
  • hooks_cli は浅いインストール パスでクラッシュしました。 コードは深いインストール ツリーを想定して Path.parents[3] にインデックス付けされ、MemPalace が浅いパス (例: /opt/mp) から実行された場合に IndexError を生成しました。ガードを追加したため、浅いインストールがフック コマンドでクラッシュしなくなります。 (#1585)
  • HNSW セグメント検疫: ゼロバイトと欠落ディム。 以前の検疫ヒューリスティックでは、dim メタデータ フィールドが欠落している HNSW セグメントに破損のフラグが立てられましたが、ほとんどは回復可能でした。チェックでは、recoverable-missing-dim と実際に破損しているものを区別し、作業中のインデックス セグメントを保持するようになりました。ゼロバイトのリンク リスト ファイル (部分的に書き込まれたセグメント) は完全に拒否されるようになりました。 (#1452、#1461、#1457 を修正)
  • 鉱山ロック ホルダー ファイルは cp1252 ではなく UTF-8 として書き込まれます。 非 ASCII Windows ユーザー名とパスによってロック ファイルが破損し、古いロックの検出が中断されることがなくなりました。 (#1438)
  • マイナー スロットの要求は、プレースホルダー PID を即座に書き込むようになりました。 要求と PID 書き込みの間でクラッシュしても、ファントム ロックは残されなくなりました。 (#1543、#1443 を修正)
  • mine_convos は mine_palace_lock 内で実行されるようになりました。 2 つの同時 convos mine 呼び出しによってインデックスが破損することはなくなりました。 (#1477)
  • 移行ツールのクリーンアップ。 ChromaDB バージョンの移行ツールは、移行中に例外が発生した場合に SQLite 接続を閉じ、temp Palace ディレクトリを削除するようになりました。移行が失敗すると、ファイル ハンドルとディスクのリークが停止します。 Entity-registry atomic-write は、書き込みまたは名前変更が失敗した場合に、その .tmp サイドカーを削除するようになりました。 (#1216、#1408、#1373 を修正)
  • 修復ツールは空/なしのメタデータ セルを許容します。 ChromaDB は、再構築中に空のメタデータ辞書または None を含むセルを返すことがあります。どちらも適切なデフォルト値に強制設定されるため、再構築が完了し、スタックしていた宮殿が回復します。 (#1459、#1445、#1426 を修正)
  • create_tunnel MCP ハンドラーはエラーを伝播するようになりました。 不正なエンドポイントまたは方向が飲み込まれ、誤解を招く成功として返されました。構造化された MCP エラーとして伝播するようになりました。 (#1546、#1473 を修正)
  • 明示的なトンネルはハードコードされた場所に保存されていました。 ~/.mempalace/tunnels.json path that ignored MempalaceConfig.palace_path. Drawers, KG triples, the people map, and every other piece of palace state honour the configured palace_path (and the MEMPALACE_PALACE_PATH env var), but palace_graph._TUNNEL_FILE was a module-level constant initialised once from os.path.expanduser("~") + "/.mempalace/tunnels.json". Under any setup where $HOME is isolated from the configured palace — subagent profiles with their own $HOME, sandboxes, multi-tenant hosts, container mounts that move the palace to /srv/ — drawers landed in the configured palace while tunnels silently landed in a different file that no other process touching the same palace could see. Worst case is the agentic one: an isolated worker calls create_tunnel then list_tunnels`ZZPH10 0ZZ`palace_graph._TUNNEL_FILE is replaced by _get_tunnel_file() which derives the path from a new MempalaceConfig.tunnel_file property (sibling of palace_path). The default single-user install is unchanged because the default palace_path is still ~/.mempalace/palace and its sibling tunnels.json is the legacy path. Backwards-compatibility: if the configured tunnel file does not exist but a file is present at the pre-3.3.6 hardcoded ~/.mempalace/tunnels.json path AND the two paths differ, _load_tunnels logs a one-line WARNING両方のパスに名前を付け、空のリストを返します。2 つの場所にまたがるトンネル状態をサイレントにマージすると、新しいデータが破壊される危険があるため、意図的に自動移行はしません。ユーザーが自分でファイルを移動またはコピーします。 (#1467)
  • create_tunnel did not validate that the source and target rooms actually exist in the chroma index. _require_name only checked that wing/room names were non-empty strings; nothing queried the collection to confirm at least one drawer carried matching {wing, room} metadata. Pointing an explicit tunnel at a phantom room — common when an agent fabricates a room name it expects to exist, or types a slug wrong — silently succeeded. Combined with the read-bubble described in the previous fix, an agent could create_tunnel → list_tunnels and have both calls return its own bogus write. create_tunnel now calls _check_room_exists(wing, room, col) for both endpoints before persisting an explicit tunnel; if either endpoint has zero matching drawers the call raises ValueError naming the offending wing/room pair. Three deliberate carve-outs: (1) kind != "explicit" skips validation because topic tunnels generated by compute_topic_tunnels use synthetic topic:<name> room identifiers that don't correspond to real chroma rooms; (2) _get_collection returning None (palace not yet created, transient backend failure, tests without a real chroma backend) skips validation rather than fail-closed — matches the tolerance pattern used everywhere else in palace_graph; (3) exceptions raised by the underlying col.get(where=..., limit=1, include=[]) query are logged and treated as "can't verify, allow" so a temporary index fault never blocks legitimate writes. Behaviour change: existing callers that previously created tunnels pointing at empty rooms (e.g. as scaffolding before mining them) will now raise ValueError。最初にドロワーをファイルし、次にトンネルを作成します。これはドキュメントで常に推奨されている順序です。 (#1468)

パフォーマンス

  • Convo miner は mined-set を 1 回プリフェッチします。 「すでに採掘されているかどうか」を確認するために、ファイルごとに 1 つの WHERE クエリを発行していました。は、マイニングされた完全なセットを 1 回だけプリフェッチし、大規模なトランスクリプト コーパスの所要時間を短縮します。 (#1474)
  • rebuild_index 進行状況コールバック。 複数時間の再構築では、デフォルトの ETA プリンターで進行状況が報告されるようになりました。ユーザーは、プロセスが進行しているかどうかを推測する必要がなくなりました。 (#1487)
  • MCP コールド スタート診断 + オプトイン ウォームアップ どのエンベッダーがロードされているかとそれにかかる時間の可視性が追加され、さらにオプトイン ウォームアップ パスが追加されるため、ユーザーは最初のクエリの遅延を確認して対処できます。 (#1530、#1495 を修正)
