iotdb v2.0.11

パッチ 公開日2026年9月11日 出典apache/iotdb 英語原文

このページは機械翻訳です。内容は必ず英文原文をご確認ください。

#iotdbv2.0.11

ブレークチェンジ

  • このバージョンでは、必要な最小 JDK バージョンが 17 に引き上げられます。

機能と改善点

  • メタデータ: SHOW TIMESERIES は、測定名による並べ替えをサポートします。
  • クエリ: SELECT 句のみを含む SQL ステートメントをサポートします。
  • リージョン: SQL を使用したパーティション化されたテーブルの手動修復をサポートします。
  • ビュー: 論理ビューをサポートします。
  • メタデータ: テーブル モデルの COUNT DATABASE ステートメントを追加します。
  • IoTConsensus: IoTConsensus がスナップショットを受信するときに複数のディレクトリをサポートします。
  • リージョン: EXTEND REGION および REMOVE REGION 構文は、regionId リストをサポートしており、複数のリージョンを一度に処理できます。
  • クエリ: EXPLAIN ANALYZE は JSON 出力形式をサポートします。
  • Mods: Mod を含むクエリのメモリ制御を強化します。単一の大きな GB レベルの mods2 ファイルのメモリ使用量も制御可能である必要があります。
  • データの取り込み: データを削除するときは、現在のテーブルが属するリージョン グループにのみリクエストを送信します。
  • プロトコル層: プロトコル層にメモリ制御を追加します。
  • UDF: InternalSession インターフェイスを UDF API に追加します。
  • パイプ: リアルタイム データ定義ロジックを変更します。
  • 機能: 後続の値の入力をサポートします。
  • SQL 句: GROUP BY および ORDER BY は、SELECT 句の AS で定義されたエイリアスをサポートします。
  • パラメータ設定: クラスタ ランタイム設定のホット リロードをサポートします。
  • 通信の暗号化: 暗号化されたclient通信の相互認証をサポートします。
  • クエリ: SQL を使用して、指定されたパスにある TsFile へのクエリ結果の書き込みをサポートします。
  • 高可用性: テーブル管理、デバイス管理、書き込み可能ビュー管理、TTL 管理、データベース管理、およびユーザー権限の高可用性をサポートします。
  • Client: Node.js client をサポートします。バージョン 2.x のみがサポートされています。
  • Edge Edition: メモリが制限されているエッジ デバイスでの使用を容易にするために、ConfigNode と DataNode の合計メモリ使用量を 512 MB に制限する Edge Edition を導入します。目標ワークロードは、読み取りおよび書き込みワークロードで 1 Hz で動作する約 10,000 回の測定です。最初のバージョンでは、主に特定の JVM とデフォルトの構成パラメーターが調整されます。将来のバージョンでは、より統合された DataNode-ConfigNode アーキテクチャに向けて進化し続ける可能性があります。

バグ

  • クエリ: ツリー モデルとテーブル モデルでは、クエリ フィルター条件内の整数値と浮動小数点値の比較が一貫性のない動作をします。
  • スケーリング: スケールイン検証中に、監視ダッシュボードの IoTConsensus Used Memory の下の IoTConsensusQueue に負の値が表示されます。
  • TsFile のロード: 受信側に書き込み権限がある場合、LOAD TSFILE は失敗し、この操作には権限がありません。権限 SYSTEM を追加してください。データは同期されません。
  • SSL: NullPointerException を修正: "java.lang.Throwable.getMessage()" の戻り値が null であるため、"String.contains(java.lang.CharSequence)" を呼び出すことができません。
  • SSL: セキュリティ パッケージで SSL が有効になっているが、CLI が SSL を指定せずにクラスターに接続している場合に表示されるエラー メッセージを改善し、メッセージをより明確にしました。
  • クラスター管理: 問題 0228 の検証中に、新しい問題が発生しました。クラスターの再起動後、1 つのノードが不明状態のままで、メイン スレッドがブロックされていることを示すエンジョイ ログが生成されませんでした。ただし、ノードは引き続き圧縮を正常に実行できます。
  • スケーリング: スケールイン中、追加状態にある DataRegion の CompressionRatio フィールドには、SHOW REGIONS で負の値が表示されます。
  • 地域: SHOW REGIONS 結果の CompressionRatio フィールドの小数点以下 2 桁を保持します。
  • スケーリング: スケールイン中、クラスターを再起動した後、SHOW REGIONS のほとんどの DataRegions の CompressionRatio フィールドは、再起動前の値であっても NaN になります。
  • ConfigNode: ConfigNode スレッド リークを修正しました。 3 つのレプリカを備えた IoTV2 3C3D デプロイメントでは、ツリー モデル テスト ケースをカバーする SQL を実行すると、ConfigNodeRPC プロセッサ スレッドの数が 3,000 に達しました。クラスターに接続できなくなり、ConfigNode/DataNode が NullPointerExceptions を報告しました。
  • クエリ: CAST(1.1 AS FLOAT) のエラーを修正: java.lang.UnsupportedOperationException: org.apache.tsfile.read.common.block.column.DoubleColumn。作戦は成功することが期待される。
  • DataNode: PipeTsFileEpochProgressIndexKeeper が 50,000 を超える TsFileResource を保持しているため、DataNode のメモリ不足が発生します。 2 つのレプリカを備えた IoTV2 3C3D デプロイメントでは、1 つの DataNode が停止している間に読み取り、書き込み、削除が同時に実行されました。 54 時間のテストの後、1 つのデータノードでメモリが不足し、ON_HEAP_MEMORY="20G" の 23 GB の OOM ダンプが生成されました。
  • ユーザー管理: LIST USER、CREATE USER、および DROP USER を同時に実行すると、「301: Ratis request failed Unknown」が発生する場合があります。 ConfigNode ログには、「原因: java.util.ConcurrentModificationException: null」が表示されます。
  • IoTConsensus: 2 つのレプリカを持つ 3C3D デプロイメントでは、DataNode が停止している間に読み取り、書き込み、削除が同時に実行されました。 1 つの DataNode プロセスが終了し、25 GB のダンプ ファイルが生成されました。
  • メタデータ: テンプレート測定およびそのサブパスでのデバイスの作成を禁止します。
  • 領域: フレーム サイズ エラー、フレーム サイズ (69670459) が保護最大サイズ (67108864) より大きいと、クエリがハングする可能性があります。代わりに、システムは適切なエラー メッセージを返す必要があります。
