kubernetes-client v7.8.0

#kubernetes-client v7.8.0

バグ

  • 修正 #7953: (httpclient-jdk) ボディのないリクエストは、デフォルトで GET を黙って設定するのではなく、リクエストされた HTTP メソッドを保存するようになりました。 JdkHttpClientImpl.requestBuilder は body != null ブランチ内で HttpRequest.Builder.method(...) のみを呼び出したので、ボディのない DELETE/POST/PUT/PATCH (client.raw(uri, "DELETE", null) など) が JDK バックエンドで GET として送信されました。ボディがない場合、メソッドは OkHttp、Jetty、および Vert.x バックエンドに一致する BodyPublishers.noBody() で設定されるようになりました。
  • 修正 #7435: (kubernetes-client) 単一の再同期サイクルがスローされたときに、SharedIndexInformer の定期的な再同期が永続的かつサイレントに停止しなくなりました。 DefaultSharedIndexInformer.scheduleResync は、Utils.scheduleAtFixedRate を通じて再同期を実行します。その自己再スケジュール チェーンは、前のサイクルが正常に完了した場合にのみ次のサイクルを再準備します。キャッチされなかった例外により (観測されていない) resyncFuture が例外的に完了し、再同期はログなしで再度スケジュールされることはありませんでしたが、独立した監視は isWatching() から true を報告し続けました (回復するには再起動が必要でした)。 resync コマンドは障害を捕捉して WARN ログに記録するようになり、次の間隔でスケジュールが再度実行されるようになりました。
  • 修正 #7933: (kubernetes-client-api) 確定的 TLS trust の失敗 (untrusted 証明書、期限切れの証明書、ホスト名の不一致) は、共有 StandardHttpClient.shouldRetry バックオフ ループ (最大 19 秒のドレイン) によって再試行されるのではなく、端末として分類され、フェイルファストに分類されるようになりました。分類子は、CertificateException、CertPathValidatorException、CertPathBuilderException、および SSLPeerUnverifiedException について getCause() ツリーと getSuppressed() ツリーの両方を歩きます。 HTTP リクエストと WebSocket 接続パスの両方上の 5 つの HTTP client モジュール (jdk、jetty、okhttp、vertx-4、vertx-5) すべてに影響します。
  • 修正 #7867: (kubernetes-server-mock) WatchEventsListener は、Vert.x が onOpen を起動する前にスケジュールされた発信監視イベントをバッファリングし、WebSocket が利用可能になったらそれらを再実行します。これにより、リスナーを登録する handleWatch と、null webSocketRef を参照する送信をスケジュールした webSocketRef を設定する onOpen の間で CRUD 操作が到達するオープンサイド レースが終了します。結果として生成された NullPointerException は、実行プログラムによってサイレントに飲み込まれ、イベントは削除されました。バッファリングされたイベントは初期同期 ADDED の後に再生されるため、順序が維持されます。
  • 修正 #7896: (kubernetes-client) AbstractWatchManager.watchEnded() は、ウォッチが 2 秒以内にメッセージなしで正常に閉じた場合に WatcherException を発行するようになり、GKFE プロキシが、代わりに裸の WebSocket クローズ (コード 1000、本文なし) で古い resourceVersion を拒否する v1/events での GKE 固有の動作を補償します。 {"type":"ERROR","code":410}、同じ古い resourceVersion で無期限の再接続ループが発生する
  • 修正 #7907: (httpclient-vertx-5) WebSocket-over-TLS 操作 (exec/attach/portForward/WebSocket でサポートされる監視、およびそれらに依存する CRD 確立待機) でクラスター証明書が再び trust になるようになりました。 Vert.x 5.1 は WebSocket client を書き換えて、カスタム SslContextFactory を無視する接続ごとの ClientSSLOptions を介して TLS を解決しました。client が trust マテリアルの唯一のキャリアとして使用したため、WebSocket ハンドシェイクはサイレントにデフォルトの JVM trust ストアにフォールバックし、PKIX 検証に失敗しました。 client 側のタイムアウトまでハングしました (通常の HTTPS 要求/応答は影響を受けませんでした)。 HTTP と WebSocket の client は両方とも、提供された trust/key マネージャーから派生した Vert.x TrustOptions/KeyCertOptions を使用して均一に設定されるようになりました。
  • 修正 #7873: (kube-api-test) Utils.findFreePort は、JVM の存続期間中に渡されたすべてのポートを記録し、すでに返されたポートをスキップし、JUnitExtensionOnMethodTest.simpleTest2 フレークとして表面化した連続した重複ポート ウィンドウを排除します。プローブ ServerSocket は呼び出し元がバインドする前に閉じられていたため、EtcdProcess.startEtcd() と KubeAPIServerProcess.startApiServer() は同じポートを描画できました。 Random.nextInt からの場合、etcd がバインドに勝ち、apiserver は bind: address already in use で 1 を終了し、ProcessReadinessChecker で Connection reset by peer として表示されます。
  • 修正 #7857: (kubernetes-server-mock) WatchEventsListener.onClosing は、Vert.x イベント ループで直接呼び出すのではなく、リスナーの送信エグゼキューターでサーバー側 WebSocket.close(...) をキューに入れるようになりました。これにより、そのエグゼキュータですでにキューに入れられているデータ フレームの FIFO 順序が保持されるため、client によって開始された監視が閉じる前にスケジュールされたイベント (例: watch.close() より前の最後の create/delete の ADDED/DELETED ペア) は、すでに閉じているソケットに対する書き込みによってサイレントにドロップされるのではなく、閉じるフレームの前に配信されます。
  • 修正 #7832: (ソナー) 割り込みステータスを保存せずに InterruptedException を飲み込んだ 8 つのプロダクション コード キャッチ ブロック内のスレッドを再割り込みする (S2142)
  • 修正 #7841: (mockwebserver) Dispatcher のシャットダウンを 2 つのフェーズに分割し、HTTP サーバーが空になった後で MockDispatcher がセッションごとの WebSocketSession エグゼキュータのみを破棄するようにし、実行中のアップグレードの onOpen がシャットダウン エグゼキュータに到達する可能性があるウィンドウを削除します。 shutdown() は、ブロックされたディスパッチ (例: QueueDispatcher.take()) のブロックを解除するために、httpServer.close() よりも前に実行されます。新しいreleaseResources()が追いかけます。 WebSocketSession.send() はさらに防御的に RejectedExecutionException をキャッチするため、残りのシャットダウン レースは Vert.x Unhandled exception のように泡立つのではなく、沈黙したままになります。 KubernetesMixedDispatcher は両方のライフサイクル フックを内部の MockDispatcher に委任するようになり、CRUD モードの WebSocket セッション エグゼキューターがシャットダウンされなかった既存のリークを修正しました。
  • 修正 #7779: (kubernetes-client) ExecWebSocketListener は、terminateOnError / チャネル 3 終了ステータスの完了と競合するトランスポート レベルのエラーについて、ユーザー指定の ExecListener に通知するようになりました — listener.onFailure (または onClose) は、遅延時に黙って飲み込まれるのではなく、専用のフラグによってゲートされて、正確に 1 回だけ起動されます。 onError タスクは exitCode.isDone() を観察します
  • 修正 #7765: (kubernetes-client) BaseOperation.informOnCondition は、内部述語が Future を完了するとインラインでインフォーマーを停止し、依存関係の排水を支援するウェイターが cf.complete が既に偽の ?watch=true HTTP リクエストをトリガーした後に informer.stop を起動する可能性がある CompletableFuture postComplete レースを終了するようになりました。
  • 修正 #7847: (kubernetes-client) BaseClient.addToCloseable は呼び出し元が指定したパラメーターではなく、内部のクローズ可能なセットで同期するようになりました。そのため、呼び出し元は異なる参照を渡すことによって相互排他を解除できません (sonar S2445)
  • 修正 #7847: (kubernetes-client-api) KUBERNETES_SUBDOMAIN_REGEX は、外側のグループで所有量指定子を使用して、敵対的なサブドメイン入力に対する ReDoS スタイルのバックトラッキングをブロックします。セマンティクスは依然として正規の RFC 1123 サブドメイン パターンと一致します (ソナー S5998)
  • 修正 #7847: (kubernetes-client-api) Serialization.yamlMapper は、volatile フィールドに割り当てる前にマッパーをローカルに構築するため、同時リーダーはまだ登録されていないモジュールを含む部分的に初期化されたインスタンスを観察できなくなります (sonar S3064)
  • 修正 #7847: (mockwebserver) 自己署名証明書/キー一時ファイルのクリーンアップは、File.delete() 戻り値を飲み込むのではなく、ログ記録付きの Files.deleteIfExists を経由します (sonar S899)
  • 修正 #7847: (httpclient-okhttp) OkHttpClientBuilderImpl は、null を OkHttp の sslSocketFactory に渡して NPE するのではなく、マルチエントリ TrustManager[] から最初の X509TrustManager を選択するようになりました。ユーザー指定の sslContext はマルチ CA セットアップ用に保存されます (ソナー S2637)
  • 修正 #7847: (httpclient-okhttp) OkHttpClientImpl.doClose は、OkHttp API によって非 null であることが保証されている dispatcher および connectionPool のデッド null チェックを削除します (ソナー S2583)

改善点

  • 修正 #7675: (mockwebserver) MockWebServer.dispatcher フィールドが volatile とマークされるため、setDispatcher(...) 呼び出しはそれ以上同期しなくても Vert.x リクエスト ハンドラー スレッドに確実に表示されます。 MockWebServer.reset() Javadoc は非破壊コントラクトを明示するために強化されました (実行中のサーバー、ディスパッチャー、リスナー、SSL/TLS 状態、ポート、またはプロトコルは変更されません)。
  • 修正 #7809: (kubernetes-client) リストとウォッチのシャード セレクターのサポート - インフォーマーを含む
  • 修正#7837: (kubernetes-client) シャードセレクターのフォローアップ
  • 修正 #7899: (kubernetes-client) インフォーマーの再リスト前のコールバック

依存関係のアップグレード

  • 修正 #7849: istio.io/client-go を 1.29.2 から 1.30.0 に変更
  • 修正 #7894: k8s.io/autoscaler/vertical-pod-autoscaler を 1.6.0 から 1.7.0 に変更
  • 修正 #7894: k8s.io/gengo/v2 を 2.0.0-20251215205346-5ee0d033ba5b から 2.0.0-20260408192533-25e2208e0dc3 に変更
  • 修正 #7894: k8s.io/kube-openapi を 0.0.0-20260319004828-5883c5ee87b9 から 0.0.0-20260414162039-ec9c827d403f に変更
  • 修正 #7875: vertx5.version を 5.0.12 から 5.1.1 に変更し、httpclient-vertx-5 を Vert.x 5.1 に適応させると動作が変更されます (SSL エンジン オプションは空のプロトコル配列を受け入れなくなりました。リクエスト本文のストリーム エラーは HTTP/2 CANCEL でリセットされるため、一時的な IOExceptions として再試行されません)。

新機能

  • 修正 #7926: (httpclient-vertx-5、httpclient-vertx) Vert.x HTTP client ファクトリでのオプトイン TLS ウォームアップ。 Vertx5HttpClientFactory/VertxHttpClientFactory は、モード OFF、CONTEXT (デフォルト、変更なし)、および FULL で setTlsWarmup(TlsWarmup) を公開するようになりました。 FULL は、client の構築時に、同期の JVM ごとに 1 回のスローアウェイ ループバック TLS ハンドシェイクをイベント ループから実行します。そのため、最初の実際の接続は、コールドまたはハード CPU スロットルの JVM を使用しているユーザーが、最初の接続のブロック/タイムアウトに達する場合、1 回限りの JDK/Netty TLS クラスのロードでイベント ループをブロックしなくなりました。 #7921。デフォルトの動作は変更されません。 CDS およびハードスロットリングされたポッドの CPU サイジング ガイダンスに関する FAQ を参照してください。
  • 修正 #5084: graalVM メタデータを生成するための Jbang スクリプト
  • 修正 #7375: (crd-generator) 生成された CRD スキーマのクラスに説明を追加するための @JsonClassDescription をサポートします。
