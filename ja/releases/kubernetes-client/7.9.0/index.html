kubernetes-client v7.9.0

バグ

  • 修正 #8024: (httpclient-vertx-5) 派生 client での WebSocket 操作 (exec/attach/portForward/WebSocket でサポートされたウォッチ) (構築済みの HttpClient で newBuilder()/build() を呼び出すことによって生成されたもの) は、Vert.x のベア WebSocketClient デフォルトにフォールバックしなくなりました。派生 client に対する Vertx5HttpClientBuilder.build() の短絡パスは、元の client のプレーン HTTP 接続 (構成はそのまま) を再利用しましたが、常にオプションをまったく持たない新しい WebSocketClient を作成し、trust/キー マテリアル (そのため、TLS は、構成されたクラスター CA ではなく、JVM のデフォルトの trust ストアに対して検証されました) と、構成された制限 (maxFrameSize/maxMessageSize は無制限ではなく 64 KiB/256 KiB に戻り、maxConnections は 8192 ではなく 50 に戻ったため、サイズを超える exec/attach メッセージはプレーン HTTP 上でもサイレントにドロップされました)。これはオプトインである kubernetes-httpclient-vertx-5 のみに影響します。バンドルされているデフォルトの kubernetes-httpclient-vertx (Vert.x 4) は、派生時に再利用するのと同じ client から WebSocket を提供しますが、影響を受けることはありません。7.6.0 から 7.8.0 までに存在します。派生は、見た目よりも頻繁に発生します。OpenShiftClientImpl は、OAuth トークン リフレッシュ インターセプターをインストールするために adapt(OpenShiftClient.class) ごとに派生し、OpenShiftOAuthInterceptor はトークン リフレッシュごとに派生し、BaseClient#newClient は、異なる RequestConfig が設定されるたびに派生します。派生 client は、HTTP client を既に再利用したのと同じ方法で、元の WebSocketClient を完全に再利用するようになりました。そのため、派生ごとに 2 番目のトランスポートが割り当てられることはなくなり、そこからドリフトすることはなくなります。トランスポートの共有は、派生ファミリ内の client を閉じると、ファミリ全体でその client が閉じられることも意味することに注意してください。adapt(OpenShiftClient.class) から取得した client の close() は、派生元の client での WebSocket 操作も終了します。これは、すでにその client の HTTP リクエストと他の 4 つの実装で行われていることです。元の HTTP client は関係なく閉じられているため、使用できるものは何も失われません。変更点は、派生ごとの WebSocketClient が閉じられずに取り残されなくなったことです。
  • 修正 #8029: (httpclient-vertx-5、httpclient-jetty) WebSocket 接続は設定されたプロキシを尊重するようになりました。そのため、exec/attach/portForward および WebSocket ベースのウォッチは API サーバーに直接接続せず、必須の出力プロキシをバイパスしなくなりました。どちらの実装も、HTTP client (Vert.x 5 WebSocketClient、および WebSocketClient の背後にある 2 番目の Jetty HttpClient) とは別のトランスポートから WebSocket を提供しますが、どちらにもプロキシ構成は与えられませんでした。 Jetty の WebSocket トランスポートは、プロキシ BasicAuthentication エントリも受信するようになりました。 OkHttp、JDK、および Vert.x 4 モジュールは、単一の client が両方の機能を提供するため、影響を受けませんでした。 httpclient-vertx-5 では、設定された接続タイムアウトが WebSocket client にも適用されなかったため、WebSocket 接続がそれを大幅に超えてハングする可能性がありました。注目に値する結果の 1 つは、プロキシ資格情報をデコードできない場合 - HttpClientUtils.decodeBasicCredentials は、Basic 以外のもの、またはデコードされた値が : で区切られた 2 つの部分に正確に分割されないものに対して null を返すため、コロンを含むプロキシ パスワードで十分です。 client は、トランスポート上で設定するのではなく、要求に Proxy-Authorization をスタンプすることにフォールバックします。このような WebSocket 接続は、API サーバーへの直接接続をサイレントに完了するのではなく、プロキシに到達し、407 で拒否されるようになりました。そのため、プロキシをバイパスしているためにのみ機能しているように見えたセットアップは失敗するようになります。
  • 修正 #7807: (kube-api-test) KUBE_API_TEST_STARTUP_TIMEOUT 環境変数は、使用するたびに ClassCastException をスローするのではなく、解析されるようになりました。値 (常に String) は、Integer/Boolean ターゲットの Class.cast() に渡されました。これは、参照型を拡張するだけで解析は行わないため、環境経由でタイムアウトを構成することはできませんでした。 @EnableKubeAPIServer (例: @EnableKubeAPIServer(startupTimeout = 180000)) の新しい startupTimeout 属性により、宣言的にオーバーライドできるようになり、3 つの構成パス (アノテーション、ビルダー、環境変数) がすべて正以外の値を拒否するようになりました。
  • 修正 #7983: (mockwebserver) WebSocket のアップグレードは、非同期の HttpServerRequest#body() コールバックからではなく、Vert.x リクエスト ハンドラーから同期的に実行されるようになりました。アップグレードを延期すると、要求終了イベントが最初に処理されるため、HttpServerRequest#toWebSocket() が断続的に IllegalStateException: Request has already been read をスローし、アップグレードが失われました (不安定な exec/attach モックサーバー テストとして表面化)。アップグレード リクエストには本文が含まれないため、リクエストは Upgrade ヘッダーによって検出され、リクエストが読み取られる前にアップグレードされます。通常の HTTP リクエストの場合、非同期パスは変更されません。
  • 修正 #7955: (java-generator) 悪意のある CRD スキーマ値は、生成された Java ソースに実行可能コードを挿入できなくなりました。スキーマ制御の値 (列挙値、CRD グループ/バージョン/名前、プロパティ名、説明、およびデフォルト) は、完全にエスケープされた Java 文字列リテラルとして出力されるため、Unicode でエスケープされた引用符を含む値は、javac がデコードするとリテラルから抜け出すことができません。多層防御として、生成された各クラスも作成前に再解析され、構造的に検証され (javac と一致するように Java Unicode エスケープ前処理が有効になっています)、残りの構造的不一致がある場合は生成が中止されます。
  • 修正 #8028: (openshift-model、kube-api-test) パッケージが 2 つのアーティファクトによって出荷されなくなり、各ペアを一緒に JPMS モジュール パスに配置できます。 openshift-model は、openshift-model-config が所有する io.fabric8.openshift.api.model.config.* クラスをバンドルしなくなりました (その Export-Package ワイルドカードにより、その依存関係からクラスがインライン化されました)。彼らは今でもそれを通じて消費者に到達しています。 Fabric8ClientInjectionHandler は io.fabric8.kubeapitest.junit.inject に移動しました

改善点

依存関係のアップグレード

  • 修正 #8033: ゲートウェイ api を 1.5.1 から 1.6.1 にバンプします

新機能

  • 修正 #7752: Kubernetes v1.37.0 (Garhwal) のサポート
  • 修正 #8033: ゲートウェイ api モデルに v1.TCPRoute と v1.UDPRoute が追加されました (どちらもゲートウェイ api v1.6.0 の上流の v1alpha2 から卒業しました)。 v1alpha2 タイプは引き続き使用できますが、アップストリームでは非推奨となっており、将来のリリースでは削除される予定であるため、新しいコードでは v1 タイプを使用する必要があります。

注意: 重大な変更

  • 修正 #7752: Kubernetes モデル API の削除 (Kubernetes v1.37.0 の上流で削除)。次の API バージョンは Kubernetes から完全に削除され、client では使用できなくなりました。
    • certificates.k8s.io/v1alpha1/ClusterTrustBundle → certificates.k8s.io/v1 または v1beta1 を使用します
    • networking.k8s.io/v1beta1/IPAddress → networking.k8s.io/v1を使用
    • networking.k8s.io/v1beta1/ServiceCIDR → networking.k8s.io/v1を使用
    • storage.k8s.io/v1beta1/VolumeAttributesClass → storage.k8s.io/v1を使用
    • scheduling.k8s.io/v1alpha2 (APIバージョン全28種類) → v1alpha3またはv1beta1を使用
  • 修正 #7752: VolumeMount コンストラクターのシグネチャが変更されました (Kubernetes v1.37.0 に bindMountOptions フィールドが追加されました)。正規コンストラクターは、bindMountOptions (List<String>) を最初のパラメーターとして受け取るようになりました。ビルダーの使用法 (new VolumeMountBuilder().with...()) は影響を受けません
  • 修正 #8033: ゲートウェイ api モデル v1.SessionPersistence は idleTimeout を公開しなくなりました (ゲートウェイ api v1.6.0 で上流で削除されました)。これにより、フィールドに加えて、getIdleTimeout()/setIdleTimeout() が削除され、正規コンストラクターが 5 つの引数から 4 つに縮小され、SessionPersistenceFluent.withIdleTimeout()/getIdleTimeout()/hasIdleTimeout() が削除されるため、ビルダー フォーム (withNewSessionPersistence().withIdleTimeout(...)) はコンパイルできなくなります。実行時のデータ損失はありません。クラスは @JsonAnyGetter/@JsonAnySetter を保持し、フルエントとビルダーの両方が additionalProperties を伝送するため、idleTimeout を含む JSON または YAML はそのままの状態で逆シリアル化と再シリアル化を続行します。
  • 修正 #8028: (kube-api-test) Fabric8ClientInjectionHandler が io.fabric8.kubeapitest.junit.inject に移動されました。これは ServiceLoader を通じて解決されるため、クラスに直接名前を付けるコードのみが影響を受けます。
  • 修正 #8028: (openshift-model) バンドルは io.fabric8.openshift.api.model.config.* をエクスポートまたは含まなくなりました。 Maven コンシューマーは影響を受けません (openshift-model-config はコンパイル依存関係です)。ただし、これらのパッケージをインポートする OSGi デプロイメントでは、openshift-model-config バンドルをインストールする必要があります。これは、openshift-client Karaf 機能ですでに行われています。
