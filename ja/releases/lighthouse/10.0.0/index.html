注目すべき変更点

パフォーマンス スコアの変更

8.0 リリースでは、TTI の役割の衰退について説明 しましたが、今日はその続報です。インタラクティブまでの時間 (TTI) はパフォーマンス スコアに寄与しなくなり、レポートに表示されなくなりました。ただし、Lighthouse の結果 JSON では引き続きアクセスできます。 TTI を使用しない場合、Cumulative Layout Shift (CLS) の重み付けは 15% から 25% に増加しました。 10.0 でのパフォーマンス スコアの計算方法 または スコア計算ツールを使って遊ぶ の詳細については、ドキュメントを参照してください。

Node パッケージのタイプ

Lighthouse に型宣言が含まれるようになりました。 TypeScript レシピの例 は、Lighthouse で適切なタイプ セーフティを実現する方法を示しています。

サードパーティエンティティの分類

Lighthouse 5.3 以降、コミュニティ主導の third-party-web データセットは、third-party-summary 監査を通じて、ページ上で見つかったすべてのサードパーティが合計 JavaScript ブロック時間にどのように寄与しているかを要約するために使用されてきました。 Lighthouse 10.0 では、このデータセットをさらに活用するために、JSON の結果 (entities) に新しいプロパティを追加しています。ページ上で検出されるすべてのオリジンは、entities 内でファーストパーティまたはサードパーティとして分類されるようになりました。 10.0 では、この分類は既存のサードパーティ フィルター チェックボックスを強化するために使用されます。 Lighthouse の将来のバージョンでは、これは、元のエンティティに基づいて各監査のテーブル項目をグループ化し、その特定のエンティティからの項目の影響を集計するために使用されます。

🆕 新しい監査

バック/フォワード キャッシュ

バック/フォワード キャッシュ (略して bfcache) は、セッション履歴を前後に移動するときに、完全にシリアル化されたスナップショットからページを提供するブラウザーの最適化です。ページがこの最適化の対象にならない理由は 100 以上あります。そのため、開発者を支援するために、Lighthouse は BFC キャッシュの応答をトリガーしようとし、ブラウザによる BFC キャッシュの使用を妨げたものをすべてリストします。 #14465 bfcache の詳細については、web.dev の記事 を参照してください。 注: この監査は、最初は PageSpeed Insights では利用できません。

入力への貼り付けの防止

監査 password-inputs-can-be-pasted-into は paste-preventing-inputs になりました。この監査のロジックは以前と同様に機能しますが、[type=password] 入力だけを考慮するのではなく、読み取り専用以外の入力要素のいずれかによってユーザーが貼り付けを妨げられた場合に監査が失敗するようになりました。 #14313

Lighthouse のドキュメントは、developer.chrome.com にあります。

私たちのドキュメントは web.dev でホストされなくなりました。最新の監査ドキュメントについては、developer.chrome.com/docs/lighthouse/ にアクセスしてください。

💥 重大な変更

Lighthouse は内部的に、従来のナビゲーション実行であっても、デフォルトで新しいユーザー フロー サポート インフラストラクチャを使用するようになりました。これをオプトアウトするには、次の方法があります。 CLI では、--legacy-navigation を使用します。 DevTools: 設定メニューの「レガシー ナビゲーション」をチェックします。この脱出ハッチが必要なユースケースがある場合は、問題を提出してください。このレガシー パスは 11.0 で削除する予定です。

Lighthouse 結果 JSON (LHR) ユーザーの場合

Lighthouse 結果のページ URL

これまで、Lighthouse の実行を説明するための URL フィールドが 2 つありました。

  • requestedUrl: ユーザーが指定した URL。Lighthouse が Chrome にこの URL に移動するよう指示します。
  • finalUrl: サーバー開始の HTTP および JS 開始のリダイレクト後の URL この分類法では、JS によって開始されたリダイレクト、履歴 API またはソフト ナビゲーションの使用など、より複雑なシナリオを考慮することはできません。また、タイムスパン モードとスナップショット モードについても明確に定義されていませんでした。これを考慮して、Lighthouse 10.0 には次の URL フィールドが追加されました。
  • (変更) requestedUrl: Lighthouse がリダイレクトする前に最初に移動した URL。これはナビゲーション モードでは以前と同じですが、タイムスパン/スナップショットでは undefined になります。
  • (新) mainDocumentUrl: ナビゲーション中に要求された最後のドキュメントの URL。ソフト ナビゲーションやページの読み込み後に作成された履歴 API イベントは考慮されません。これはナビゲーション モードでのみ使用でき、タイムスパン モードとスナップショット モードでは定義されません。
  • (新) finalDisplayedUrl: Lighthouse の実行終了時にブラウザのコンボボックスに表示される URL。これは、ソフト ナビゲーションと履歴 Z​​ZPH527ZZ イベントを考慮します。ナビゲーション、タイムスパン、スナップショット モードで使用できます。
  • (非推奨) finalUrl: mainDocumentUrl と同じ値。

変更の監査

  • password-inputs-can-be-pasted-into -> paste-preventing-inputs
  • preload-lcp-image -> prioritize-lcp-image
  • third-party-summary は、item.entity の link 値を使用せず、代わりに生の text 値を使用します。
  • full-page-screenshot は監査ではなくなり、代わりに lhr.fullPageScreenshot に保管されます。 CLI でフルページのスクリーンショットの収集を抑制するには、--skip-audits full-page-screenshot から --disable-full-page-screenshot に移行する必要があります。

ノードユーザー向け

  • ノード 14 はサポートされなくなり、最小値はノード 16 になりました。
  • ライトハウス ノード パッケージ内でパスをインポートする場合: lighthouse-core/ フォルダーと lighthouse-cli/ フォルダーは、単に core/ と cli/ になりました。
  • CommonJS から ES モジュールに変換されました。動的インポート: await import('lighthouse') を使用することで、CommonJS で Lighthouse を引き続き使用できます。 CommonJS の lighthouse 関数のみにアクセスするには、require('lighthouse/core/index.cjs') を使用することもできます。
  • Lighthouse の CSV 出力がさらに便利になりました。 新しい形式の例 については PR を参照してください。
  • LHError は LighthouseError になりました。 Lighthouse によってスローされたエラーをキャッチしようとしている場合は、必ずこれを考慮してください。

ノード API の変更

lighthouse 関数は Puppeteer との統合が改善されました。 lighthouse(url, flags, config, page) を使用して Lighthouse を実行し、既存の Puppeteer.Page ハンドルを page として渡します。 ユーザー フロー api は最上位ノードのエントリポイントに移動し、import {startFlow} from 'lighthouse' を使用してインポートできるようになりました。 新しい flow.startNavigation() および flow.endNavigation() 関数を使用すると、コールバック関数を使用せずにユーザー トリガー ナビゲーションを定義できます。 例 については、ユーザー フローのドキュメントを参照してください。 単一のユーザー フロー ステップの設定を変更するには、settingsOverride プロパティではなく、トップレベルのフラグ オプション flow.snapshot({skipAduits: ['uses-http2']}) で設定のオーバーライドを定義します。 フロー ステップにカスタム名を付けるには、flow.snapshot({name: 'Custom name'}) を使用します。以前は、これは stepName 経由で行われていました。

Lighthouse のカスタマイズ用 (カスタム構成、ギャザラー、監査)

  • Lighthouse 10.0 で動作するには、カスタムギャザラーは新しいギャザラー インターフェイス (例) を実装する必要があります。それ以外の場合は、レガシー ナビゲーション モード および古いバージョンの Lighthouse でのみ動作します。
  • Lighthouse では、passes を使用してナビゲーション モードでページを複数回読み込むことができなくなりました。ページを複数回読み込む必要がある場合は、ユーザー フローを使用することをお勧めします。 新しい構成形式に変換する方法 の手順については、構成ドキュメントを参照してください。
  • ScriptElements アーティファクトは、形状が少し異なる Scripts になりました。
  • Audit.makeOpportunityDetails および Audit.makeTableDetails は、オプション オブジェクトを 3 番目のパラメーターとして受け入れるようになりました。これは結局、Audit.makeOpportunityDetails だけにとって重大な変更になります。 #詳細changelog
