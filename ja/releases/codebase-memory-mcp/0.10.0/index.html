コードベースメモリ mcp v0.10.0

コードベースメモリ mcp v0.10.0

⚠️ 代わりに v0.10.1 を使用してください。 v0.10.0 には重大な MCP-client 回帰 (#1522) が含まれていました。これは、Claude Code などの仕様に準拠した MCP client で空の {} としてレンダリングされるコア検出ツールのデフォルトの出力形式です。以下のすべてはこのリリースを正確に説明していますが、修正リリースはそれよりも優先されるため、インストールする必要があります。

v0.9.0 以来のマイルストーン リリース — cbm のバックエンドは共有調整デーモンを中心に再設計され、ツール出力はコンパクトなツリー形式に再構築され (大きな結果では出力トークンが最大 99% 減少)、長年の Windows メモリ ラチェットは修正および検証され、新しい カバレッジ システムによりグラフの盲点が可視化されています。cbm の 15 番目のツールである check_index_coverage とミスコード スケルトンの導入グラフ UI のコード ギャラクシーのすぐ横にレンダリングされます。リリース候補以降、グラフには新しい 証拠に裏付けられた CALL_REFERENCE エッジ クラスが追加され、Linux バイナリのアロケーター オーバーライドが静かに非アクティブであることが判明し、完全にオンになり、RC に対して報告されたすべてのデーモン/インストーラー/Windows の問題が修正されました。コミュニティ提供の 3 つの新しい言語サーフェス、Swift クロスパッケージ解決、Nix 抽出のオーバーホール、クエリ エンジン、ストア、抽出プログラムにわたる広範なコミュニティ主導の正確性バッチを追加します。

リリース候補から v0.10.0 まで

これは、2026 年 7 月 30 日に v0.9.1-rc.1 として出荷されたものの最終リリースです。これは、v0.9.1 ではなく v0.10.0 として表示されます。新しいバックエンド実行モデル、新しいツール、新しい出力形式、および新しいエッジ クラスはパッチ リリースではなく、バージョン番号がそのように示す必要があります。 v0.9.1 の最終版は存在しません。これがすべてです。

日々のワークフローで RC を実行したすべての皆様へ: ありがとう — 期待どおりに機能しました。 RC から 1.5 週間で、76 の PR にわたって 335 のコミットが行われ、そのうち最も価値のあるものはフィールド レポートとして始まりました。 client が「保留中」のままになるデーモン競合ハンドシェイク (#1383)、独自のクロード コード フックを追加する代わりに既存のクロード コード フックを削除するインストーラー (#1387)、何も通知せずに何も出力しないフック拡張 (#1388)、アクティブなセッションの停止を拒否する Windows インストール/アンインストール (#1416)、切り離されたデーモンからコンソール ウィンドウのフォーカスを盗む (#1427)、クエリ応答診断なしで MCP サーバーを強制終了する可能性のあるサイズ (#1375)、マルチキー ORDER BY が LIMIT をドロップする (#1334) — これらはすべて RC ユーザーによって rc.1 に対して報告されており、このリリースで修正されています。

カバレッジ アスクは有効です。 カバレッジ システムは、コードとグラフの間のギャップを 測定可能にし、それを縮小するのに役立ちます。エージェントに、リポジトリ全体で check_index_coverage を実行するよう依頼し (または、UI で欠落したスケルトンのレポート エッジ ケース コールアウトを click して)、結果の概要を GitHub の問題またはディスカッションに貼り付けます (欠席クラス、影響を受ける言語とファイルの種類、数)。これは集計された数値であり、ソース コードではありません。貼り付けることを選択しない限り、すべてがマシン上に残ります。実際のカバレッジの要約はすべて、修正できる具体的なパーサーのエッジ ケース、リゾルバーのギャップ、または言語の癖を示しています。リポジトリは、クローンを作成できないテスト コーパスです。

⚠️ 行動の変化

  • 新しいエッジ クラス: CALL_REFERENCE - および CALLS は、まったく 1 つのことを意味するようになりました。 グラフでは、呼び出し可能オブジェクトの 呼び出し と、それを値として渡す * (app.register(pluginFn, opts)) が区別されるようになりました。 CALLS は呼び出し専用に予約されています。 CALL_REFERENCE は、決定論的なパーサー/LSP/レジストリの証拠が正確な呼び出し可能な値 (出現正確なスパン、字句結合状態、解決されたシンボル ID) を証明する場合にのみ発行されます。あいまいな、シャドウされた、または動的リバウンドの発生は USAGE のままです。すべての呼び出し可能な関係が CALLS エッジであると仮定したクエリは、新しいラベルを考慮する必要があり、以前にはなかった精度が得られます。CALL_REFERENCE エッジは推測ではなく証拠です。

  • プラットフォームごとに 1 つのアーカイブ — UI は常に含まれます。 ui-* と非 UI バリアントの分割はなくなりました。現在、すべてのプラットフォームにグラフ UI が埋め込まれた単一のアーカイブが同梱されており、npm/PyPI パッケージにはデフォルトでそれが含まれています (RC からの CBM_VARIANT=ui オプトインは廃止されました)。アーティファクトが少なく、間違ったバリアントのダウンロードがなく、検証する構成は 1 つだけです。

ハイライト

  • 調整デーモン — バックエンドのマイルストーン。 これまで、すべての cbm セッションはアイランドでした。各 MCP サーバー、CLI 呼び出し、およびフックは独自にストアをオープンし、隣接するものについては何も知りませんでした。このリリースの時点では、これらはすべてユーザーごとのデーモン、つまりビルド/バージョン競合ハンドシェイク、インデックス作成アドミッション コントロール、および共有グラフ UI を通じて調整されます。新しいdaemon start|stop|status CLI;ウォーム デーモンにより、コマンドごとの起動コストが削減されます。8.5M ノード グラフで 40 ～ 58% 高速な CLI コマンドが測定されました (呼び出しごとに ~2.6 が節約されました)。 RC フィールド レポートによって強化されました。すべての拒否パスが、client を待たせるのではなく、理由を付けて応答するようになりました。これは、目先の成果を超えて、次のリリースが構築する基盤です。マルチエージェント ワークフローの一元管理 と ローカルのみのレポート/可観測性インフラストラクチャ — すべてがマシン上に残ります。どこにも何も送信されません。
  • 証拠に裏付けられたコール グラフ。 新しい CALL_REFERENCE エッジ クラス (動作の変更を参照) は長年の精度のギャップを埋めます。高次のパターン (値、コールバック、ハンドラー テーブルによって登録されたプラグイン) は、決定論的な証拠に裏付けられた最上級のグラフ関係になり、一方 CALLS は推測を吸収しなくなります。オプションの include_evidence 出力は、エッジが存在する 理由、つまりエッジの背後にある解像度の由来を示します。
  • ツリー形式ツールの出力 — TOON コンパクトで、1 回だけのページネーション、実際の detect_changes 影響レポート、およびグラフ サイクル検出を備えたプレフィックス グループ化された行。大規模なクエリ結果で、v0.9.0 と比較して出力トークンが ~99% 少ないことが測定されました。MCP 応答は structuredContent でペイロードを複製しなくなり、使用可能な応答バジェットが約 2 倍になりました。
  • Windows メモリ ラチェットが修正されました (#581) — そして、Linux オーバーライドがオンになりました。 アロケータ オーバーライドは MinGW の下でサイレントにコンパイルされるため、CRT は解放されたページをコミットし続け、長命デーモンが数か月間メモリをラチェットしました。 mimalloc は Windows 割り当てを完全に所有するようになり、スレッド終了時にスレッド ヒープが解放され、大声での所有権監査により、将来のリグレッションが起動時に通知されます。リリース アーティファクトで検証: v0.9.0-era ビルドで 53 倍のコミット ヒープ増加を測定した 10 分間の純粋なクエリ ソークでは、1.06× が測定されるようになりました。その後、同じ監査で Linux 上のミラー イメージが検出されました。出荷された Linux バイナリでは、通常の malloc が実際に mimalloc 経由でルーティングされたことは一度もありませんでした。このリリースでは、実際にルーティングされています。

何が変わったのか

調整デーモンと同時実行性

これは、プロジェクト開始以来最大のバックエンドの変更です。cbm の実行モデルは、独立したセッションごとのプロセスから、調整されたユーザーごとのバックエンドに移行しました。同時セッションは、デーモン (daemon start|stop|status、永続的またはセッション管理) を介して、認証された IPC、ビルドフィンガープリント/バージョン/キャッシュルートの競合検出、並列インデックス作成のための物理ジョブアドミッション制御、およびデーモンから提供されるグラフ UI を介して調整されます。ユーザーごとのデーモンはセキュリティ境界であるため、それに応じて IPC が強化されました。Windows では、パイプ client は偽装ではなくプロセス ID によって検証され、プライベート名前空間オブジェクトにはトークン ユーザーの SID で所有者スタンプが付けられ、DACL は厳密に検証されます。 POSIX では、ソケット ID は i ノードに固定されたレコードに対してチェックされます。すべては厳密にローカルのままです。

その後、RC フィールド レポートが継ぎ目を強化しました。デーモンが拒否したバイナリ イメージの client は、無期限の「保留中」(#1383) ではなく応答を取得するようになりました。特大の MCP 応答は、プロセスの停止ではなく構造化エラーを生成します (#1375)。フック表面デーモンは、何も発行せずに、呼び出し元に対して競合を構築します (#1388)。また、不一致のビルドを受け入れるアドミッション パスは、診断でそのコホートに名前を付けるようになりました。 macOS では、サブプロセスは fork+exec ではなく posix_spawn 経由で生成されます。

ワークツリー ネイティブのマルチエージェント ワークフローの準備 このデーモンは、今日マルチエージェント セットアップが実際にどのように実行されるか、つまり git ワークツリーごとに 1 つのエージェントを実行するための基礎でもあります。現時点では、各ワークツリーは個別のリポジトリであるかのようにインデックスを作成する必要があります。一元化されたデーモン層を導入すると、今後のリリースではまさにこれがやり直されます。ワークツリーはメイン リポジトリのグラフの子となり、変更されないものはすべて共有され、異なるもののみがインデックス付けされます。これにより、ワークツリーごとのエージェント パターンの時間とディスクのコストが大幅に削減されます。

グラフのセマンティクスとインデックスの再作成

CALL_REFERENCE の作業 (動作の変更を参照) は、抽出、LSP 解決、シーケンシャルおよびパラレル パブリケーション、永続性、MCP/UI カウント、ドキュメント化などのスタック全体を実行します。この処理では、LSP の結果が別の同名の使用を促進することがないように、出現時完全一致が行われ、字句のシャドウイングとあいまいさに対するフェールクローズ処理が行われます。これに伴い、ウォーム再インデックス作成も デルタマージ パイプライン に移行されました。変更されていないデータは前方にコピーされ、変更されたスライスのみがパッチされてアトミックにスワップインされ、以前の再構築および修復パスが置き換えられます。非常に大規模なウォーム再インデックスのパフォーマンスはまだ進行中です (既知の問題を参照) が、このリリースに含まれる構造的な再作業は、残りの勝利が着地する基盤となります。

工具出力と MCP 表面

TOON はクエリ サーフェス全体のコンパクトな出力 (約 10 倍小さい) と、その上部のツリー形式 (プレフィックスでグループ化された行、1 回だけのページネーション カーソル、detect_changes での実際の変更の影響、SCC サイクル検出) により、大規模な結果で v0.9.0 と比較して出力トークンを合計で約 99% 削減します。 MCP 応答は、structuredContent (#1375) でペイロード全体の複製を停止します。オプションの include_evidence は、エッジ解像度の由来を明らかにします。 detect_changes は、シード検出の範囲を変更された行範囲に限定します。 ADR ツールはコミュニティの正確性パスを取得しました。インデックス再作成中、読み取りはノンブロッキングのままであり、誤解を招くセクション書き込みは拒否され、カバレッジ スコープ ラベルは保持されます。 index_repository は、既知のプロジェクト名から repo_path を解決します。無効なプロジェクト名では、.corrupt.<hex> ファイルを散在させるデーモンを送信できなくなりました (#1425)。 CLI アクティベーションの拒否は、記録された安全性チェック (#1416) に起因すると考えられます。 --help は MCP レジストリからツール リストを取得するため、ドリフトすることはありません。

Windows とメモリの安全性

#581 チェーン: mimalloc (--wrap + 静的 CRT オーバーライド) を介して通常の Windows 割り当てをルーティングし、TLS デタッチ コールバックからスレッド ヒープを解放し、arm64 で障害が発生した SQLite ページ キャッシュ スラブをドロップし、起動時にサイズ クラスごとのアロケーターの所有権を大声で監査します。これにより、「チューニングは装飾」が再びサイレントに行われることがなくなります。 RC 以降の新機能: 出荷された Linux バイナリが実際に mimalloc を介して malloc をルーティングしていなかったという同じ監査哲学が捕らえられました。オーバーライドは現在、完全にアクティブです (#1360)。メモリ診断は、すべてのプラットフォームで OS-truth RSS をレポートします。 非 ASCII キャッシュ パス にあるグラフ データベースは Windows 上で確実に開きます (SQLite で開かれるすべてのメンテナンス パスは、プライマリ オープンと同じワイド パス正規化を経由するようになりました。以前は、たとえばキリル文字の名前が付いたキャッシュへの 2 番目の インデックスは失敗しました)。 stdio は、Windows 上の MCP ではバイナリ モードで実行されます。生成された子プロセスはコンソール ウィンドウをフラッシュしなくなりました (#1427、および一般的なケースに対するコミュニティ修正)。コードベースは MinGW GCC で正常にコンパイルされます。

Windows には単一のバイナリが同梱されるようになり、更新は install.ps1 から実行されます。

Windows は以前、小さな永続的なランチャーとその背後にある製品バイナリの 2 つの実行可能ファイルを出荷していました。 Linux や macOS とまったく同じように、1 つのバイナリ が同梱されるようになりました。

ランチャーは、製品自体を適切な場所で更新できるように存在していました。Windows では、実行中の実行可能ファイルはそれ自体のイメージを置き換えることができないため、2 番目の常駐バイナリがスワップを実行する必要がありました。この小さなヘルパーはウイルス対策のヒューリスティックを確実にトリップし、フラグが立てられるものを出荷せずにそれを維持することはできませんでした。そのため、更新ステップは実行中のプロセスから install.ps1 に移動しました。install.ps1 は、codebase-memory-mcp が実行されていないときに実行されます。

変更点: Windows では、codebase-memory-mcp update が適切に更新されなくなりました。代わりに実行する正確なコマンドが出力されます。

powershell -ExecutionPolicy Bypass -File "<install-dir>\install.ps1"

install.ps1 は冪等であるため、それを再実行すると更新が行われます。デーモンが停止し、実行中のバイナリがリタイアされ、新しいバイナリがインストールされ、クリーンアップされます。 npm または pip を介したインストールは影響を受けません。以前と同様にパッケージ マネージャーを使用して更新します。

言語と抽出精度

ウイルス対策の誤検知 — その全容とポリシーの変更

このリリースでは、すべてのアーティファクト、つまりすべてのバイナリ アーカイブ、インストール スクリプト、および通知ファイルの検出が 0 件で出荷され、それぞれが 60 以上のエンジンによってスキャンされます。以下の検証テーブルはこれらのスキャンから生成されており、その中のすべての VirusTotal リンクは耐久性があります。いつでも正確なバイトを自分で再確認できます。

リリース ゲートの動作方法が変更されたため、また、RC からファイナルまでの期間が数日ではなく数週間かかった主な理由の 1 つであるため、長めの話をする必要があります。

何が起こったのか。 RC および最終段階で、他のすべてのエンジンがクリーンであると報告する一方で、一部のビルドで 1 つ* の機械学習ヒューリスティック (Microsoft のエンジンが Trojan:Script/Wacatac.B!ml を報告) が断続的にトリップしました。 !ml サフィックスは、署名の一致ではなく、統計モデルのスコアをマークします。 Script トークンは、その命名スキームの汎用バケットであり、スクリプトの内容については何も言いません。まず、これを潜在的な妥協として扱いました。1 つのコミットから構築されたリリース マトリックスの完全な分析、フラグが立てられたアーティファクトのリバース エンジニアリング、パックされたペイロード プロファイルに対するエントロピー分析です。何もない。評決はすべての軸にわたって一度に分割されました。静的/動的リンク軸はアーキテクチャ間で「反転」し、同一のセグメント構造を持つ 2 つの macOS バイナリはクリーン/フラグ付きで分割され、1 つのビルドの兄弟アーティファクトは異なるバリアント バケットに配置されました。 決定的な証拠: 1 つの同一のファイル (同じ SHA-256) は、約 1 時間以内に 0/62 クリーンからフラグ付きになりましたが、こちら側には何の変化もありませんでした。そして、逆の方向で実行した実験でもそれが確認されました。埋め込まれたすべてのシェル スクリプトをバイナリから削除し、UI バンドルと統合テンプレートを検証済みの別個のファイルに移動しました。検出数は減少しませんでした。単にアーティファクト間を移動しただけであるため、より単純な単一バイナリ構成に戻しました。判定の一部は、バイト内ではなく、スキャナー自体の状態内に存在します。分類器はコードのみを判断しているわけではないため、コードを変更しても非検出を保証することはできません。

ポリシーが変更された理由 RC ノートには、私たちのゲートは永久に検出ゼロであり、許容度はないと書かれていましたが、私たちはそれを意図してこの文書を作成しました。しかし、同一のバイトをオンにする判定に対するゼロ ゲートは、リリースのタイミングがコードではなく Defender のクラウド モデルの状態の関数であることを意味します。各インシデントでは、ライブ Defender エンドポイントに対してバイトを検証し、Microsoft に誤検知レポートを提出し、分類子のリビジョンを待つのに「数日」のコストがかかります。その背後で開発は事実上ハードブロックされています。それは持続可能な出荷方法ではなく、絶対的なルールが依然として維持されていると偽るのは不誠実な選択肢だったでしょう。そこで、これを実際に保持できるポリシー SECURITY.md の契約テストによって文書化および固定されている に置き換えました。

  • リリースは、エンジンが Microsoft でラベルが !ml で終わる場合に限り、最大 1 つ の検出機能を備えて出荷されることがあります。これは、上記で説明した正確で証拠のある誤検知クラスです。
  • 他のすべては引き続きブロックされます。ハード: 2 つ以上のエンジン、署名ベースのラベル、他のベンダー、「疑わしい」判定。
  • 許容される検出は 公開され、決して非表示にはなりません。VirusTotal リンクと TOLERATED マーカーとともに以下の検証表に表示されるため、何が出荷されたかを常に正確に確認できます。

このリリースでは、完全にクリーンにスキャンされるため、許容範囲は必要ありませんでしたが、将来のリリースが出荷される際のルールを知っておく必要があります。

これは風土病であり、当社に特有のものではありません。 同じ !ml ファミリが、大規模で署名のないネイティブ オープンソース バイナリを繰り返しヒットします: llama.cpp (リバース エンジニアリングでは何も見つかりません)、GitHub 独自の gh CLI、Microsoft 独自の Go ツールチェーン、 Anthropic の Claude コード、OpenAI の Codex、rust-lang、yt-dlp、Godot、PyInstaller、Tauri。 Go チームの Microsoft エンジニア はっきり言って: 「正確に何かを修正して、Go の誤検知をすべて解決することはできません。」 分類子を回避するためにバイナリを再構成することは意図的に行っていません。これがマルウェアの動作であり、同じエンジニアがそれを報告しています。 「回避するのではなく、精査を強化します。」 私たちは、誤検知を判読できずに高いスコアを獲得するよりも、むしろスキャン可能で説明できることを望んでいます。 とにかく私たちが修正したもの 調査の結果、実際の欠陥が判明し、それぞれのメリットに基づいて修正され、現在はリリース ゲートによって主張されています。これまでに出荷したすべての Linux バイナリは、実行可能スタック (欠落している .note.GNU-stack アノテーション) を要求していました。テスト専用のフォーク プローブが実稼働ビルドにコンパイルされました。更新をチェックするために、GitHub リリース API に対して curl を生成したデーモンが削除されました。cbm は、自発的にネットワーク要求を行わなくなりました。未使用の抽出および SQLite ロード可能拡張機構がコンパイルされます。一時ファイルとシンボリックリンクスキャンの強化。そして、再現可能なバイトのタイムスタンプを削除してビルドします。

永続的な修正はコード署名であり、現在進行中です。ID 検証とプラットフォームの登録は技術的ではなく官僚的であるため、独自のスケジュールで実行されます。 Windows では署名が役に立ちます。 AV エンジンが Linux ELF バイナリを尊重するコード署名スキームは存在しないことに注意してください。そのため、上記の透過性は一時的なものではなく永続的なものです。私たちの評価に矛盾するものが見つかった場合は、av-analysis というラベルで問題を提起してください。具体的な発見によって、私たちの立場は変わります。土地に署名するまで、上のゲート、公開されたハッシュ、来歴証明書の構築、いつでも自分で構築できるソースが、このプロジェクトの trust アンカーです。

セキュリティの検証

VirusT合計で 32 個の正確に抽出されたアーカイブ メンバー をカバーする 14 個の個別に抽出されたバイト オブジェクトが完成しました。 抽出マニフェストは、SHA-256 の出自によって、これらの関連付けを 8 つのダウンロード可能なアーカイブにバインドします。ダウンロード可能な .tar.gz/.zip リリース コンテナーは VirusTotal に送信されませんでした。

スキャンされたすべてのオブジェクトは、悪意のあるものは 0 件、疑わしいものは 0 件 の判定を返し、決定的なエンジン結果は 54 ～ 69 件 (最低必要数: 50) でした。 Microsoft は、8 つの実行可能オブジェクトすべてに対して決定的なクリーンな評決を返しました。
