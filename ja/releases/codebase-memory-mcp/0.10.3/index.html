コードベースメモリ mcp v0.10.3

コードベースメモリ mcp v0.10.3

修正のみのリリースであり、そのほとんどはコミュニティからの完成作品として到着しました。ここには、v0.10.2 で出荷した 2 つのリグレッションの修正とともに、提供された 6 つのプル リクエストが含まれています。

アップグレードする前に知っておくべきことが 2 つあります。 同じプロジェクトに対して複数の MCP client を実行する場合、このリリースでは、健全なインデックスをサイレントに破壊する可能性があるバグが解決されています。最初のセクションから始めてください。 インストールまたは更新が失敗した場合、通常のホーム ディレクトリを拒否するアクセス許可ルール、完全に間違った理由を報告するエラー メッセージ、Codex がキャッシュ ディレクトリを失うという 3 つの原因がここで修正されます。そのうちのいくつかは「黙って」失敗したり、間違ったことを非難したりしたため、複数のリリースを経て生き残ったのです。

同時インスタンスは互いのデータベースを隔離しなくなりました

このリリースの最悪のバグは @LynxBay によって修正されました。 2 つの cbm インスタンスが同じプロジェクトで競合した場合 (2 人のエディター、エディターと CLI 呼び出し、デーモンと野良セッション)、ロック レースの敗者はデータベースが 破損している と結論付けて隔離する可能性があります。つまり、名前が変更され、最初から再構築され、何時間ものインデックス作成が不要になります。データベースは正常でした。整合性チェックでは、「破損」と「ビジー」を区別できませんでした (#1206)。

同じチェックには逆の盲点もありました。本当に破れたページのあるデータベースは、トップレベルの簿記が正しく見える限り合格するため、クエリが不正に動作するまで実際の損害は気づかれませんでした (#1037)。

Integrity は 3 方向の評決を返すようになりました。確認された汚職検疫のみ。ロック競合では、「プロジェクトがビジーです。インデックス作成後に再試行してください」と表示され、データが放置されます。そして、深い quick_check は、浅いプローブが見逃したページレベルのダメージをキャッチします。どちらの方向でも回帰テストが行​​われます。

グラフの決定論、2 回

@Studnicky からの 2 つの貢献により、実行間ドリフトの 2 つの長年の原因が解決されました。これは、0.9.1 RC 以降の既知の問題で追跡されている「同じリポジトリ、わずかに異なるエッジ数」の動作です。

  • 同じ論理エッジが異なる属性 (LSP 解決された呼び出しとテキストの一致など) で 2 回生成された場合、最後に到着したものが生き残ります (スレッド スケジューリングの機能)。マージは完全な順序になりました。信頼性が高い方が勝ち、同点は決定的に破られ、結果は構築による到着順序とは独立しています。
  • CONFIGURES 候補コレクションは上限を適用する前に何もソートしなかったため、どの候補が生き残るかはワーカーのマージ順序に依存しました。候補は、最初に純粋なコンテンツ キーによって順序付けされるようになりました。特にノード ID によってではなく、安定しているように見えますが、それ自体はマージ順序で渡されます。

Windows: 空の ACL で作成されたデーモン ファイル

@Kiborgik は、微妙な問題 (#1351) を診断して修正しました。デーモンのプライベート ディレクトリは、保護された DACL と継承不可能な ACE を組み合わせていました。Windows では、これは子が 何も継承しないことを意味します。内部で作成されたすべてのファイルは空の ACL を持って生まれ、その所有者であっても読み取ることができません。ディレクトリには適切に継承可能な所有者専用 ACE が保持されるようになったため、厳格なセキュリティ体制が維持され、ファイルは実際に機能します。同じ寄稿者によるコンパニオン修正により、ユーザーと同じ名前のマシンが空のプリンシパルにアクセス許可を付与するというトラップが閉じられました。ドメインに参加していないマシンでテストしたところ、ミラーイメージ トラップが表面化したため、ビルド ツールはアカウントを SID で識別し、名前解決を完全に停止するようになりました。

2 つの v0.10.2 回帰の修復

どちらも数時間以内に報告されました。素早い信号をありがとうございました。

  • update --ui が動作を停止しました (#1544、@ehendrix23)。 v0.10.2 は、廃止された UI/標準セレクター * と * それを駆動するフラグを削除したため、スクリプトとマッスル メモリに存在するコマンドはハード エラーになりました。どちらのフラグも再び受け入れられます。これらのフラグは何もせず、一度そう言うだけですが、本当に不明なフラグは依然として失敗します。
  • 生成された Pi 拡張機能は Pi を完全に破壊しました (#1550、@musichen)。 Pi は、デフォルトのエクスポートを呼び出して拡張機能をロードします。私たちのものは代わりに名前付き関数をエクスポートしました。ロードに失敗した Pi 拡張機能は、pi doctor を含むすべての pi コマンドを一緒にダウンさせます。拡張機能はデフォルトでファクトリーをエクスポートするようになりました。 @musichen と @henri-edh によっても個別に修正されました。Pi のローダーについてのより鋭い説明は、ソース内のコメントになっています。

構造化された出力により証拠が失われないようにする

trace_path(include_evidence: true) は、ホップごとの strategy 列と confidence 列を約束し、ツリー形式のみで提供しました。 format: "json" では、両方のフィールドが静かに消え、それらを必要とする可能性が最も高い呼び出し元、つまりプログラムで構造化出力を消費する呼び出し元 (#1542、@asemraza) に正確にヒットします。 JSON パスは、同じセマンティクスを持つ両方のフィールドを保持するようになり、ツリー形式で - が出力される場所には null が配置されます。

サブプロセスの生成はビジーなマシンでも存続します

CI フレークを追跡することで、本当の堅牢性のギャップが明らかになりました。カーネルが「再試行」でプロセスの生成を拒否した場合 (ロードされたマシン上のプロセス テーブルが一時的に満杯になりました)、cbm はそれを永続的な障害として扱いました。 git プローブまたは LSP サーバーは、ユーザーには見えない理由で起動を拒否します。一時的なスポーン失敗は短時間再試行されるようになりました。実際のエラー (バイナリやアクセス許可の欠落) は、セマンティクスが変更されずにすぐに失敗します。

インストールとアクティベーション: 誰も対処できない拒否

#1537 (@listepo) をフォローアップしたところ、2 つの欠陥が重なっていることが判明しました。

キャッシュ ディレクトリの 祖先 がグループ書き込み可能である場合、デーモンは実行を拒否しました。これは、v0.10.2 でインストーラー側で削除したのと同じルールで、兄弟チェックでその決定がカバーされていますが、変更されることはありませんでした。グループ書き込み可能な ~ または ~/.cache は一般的です (WSL2 は 0775 で出荷されるため、いくつかのディストリビューション スケルトンと共有プライマリ グループを持つマシンで同様です)。そのため、これらのユーザーにとってデーモンは永久に使用できず、閉じるものはなく、再起動しても修正されません。誰でも書き込み可能な祖先は依然として拒否されており、ローカル ユーザーはパス コンポーネントを交換できます。また、プライベート ディレクトリ自体は引き続き所有者のみに強制されているため、祖先を安全に受け入れることができます。 その下では、エラー メッセージが独自の証拠をでっち上げていました。拒否パスにはエラー コードが設定されていなかったので、レポートは errno がたまたま保持していたものを出力するように戻り、許可の決定を求めるためにレポーター ENOENT を手渡しました。彼らは、ずっとそこにあった行方不明のファイルを探しに行きました。メッセージには、ディレクトリとそれを拒否したルールの名前が表示されます。

また、この分野では、アクティベーション ガードは、何も実行されていない障害も含め、すべての拒否を「アクティブな CBM セッションを停止できませんでした」と報告しました。これらは個別のメッセージになりました。2 番目のメッセージは、何も閉じる必要はなく、どちらの救済策も codebase-memory-mcp バイナリがまだ PATH 上にあることを前提としていないことを明確に示しています。このアドバイスは、uninstall の直後に出力されたまさにその時点では使用できませんでした。

これも修正されました

  • CBM_CACHE_DIR が設定されている場合、コーデックスには cbm ツールが表示されませんでした (#1562、@anton-matosov)。 Codex は明示的にリストされた変数のみを MCP サブプロセスに渡すため、Codex が生成したサーバーはデフォルトのキャッシュを読み取り、デーモンは設定されたキャッシュを使用します。それらが一致せず、初期化中に接続が閉じられました。生成された構成は変数を転送するようになりました。
  • インストールされたスキル ファイルは厳密な YAML リーダーにロードできませんでした (#1554、@xezzon)。その description には引用符で囲まれていない Triggers on: が含まれており、引用符で囲まれていない YAML スカラー内のコロンスペースは「ネストされたマッピング」を意味します。そのため、パーサーはドキュメント全体を拒否し、スキルはサイレントにロードされませんでした。
  • search_code は結果カウントとして負の limit をエコーバックしました (#1511、@lukiod による修正)。これは、拒否された引数ではなく回答としてエージェントに読み取られます。
  • ~~OpenCode のインストールが間違ったファイル (@iandol) にインストールされました。~~ 訂正: これは誤ってここにリストされています。この修正は、v0.10.3 タグが削除されてから数時間後にマージされたため、このリリースにはありません。v0.10.4 で出荷されます。 OpenCode 構成が .jsonc ファイルの場合、v0.10.3 にアップグレードしても役に立ちません。時間を無駄にして申し訳ありません。
  • リリース アーカイブは抽出前に検証されます (#1510、@cyphercodes): 正確なメンバー セット。シンボリックリンクされたメンバーは完全に拒否されます。

アップグレード

  • バイナリ インストール: 以下をダウンロードするか、install.sh / install.ps1 を再実行します。インストーラーを再実行すると * 更新されます。
  • npm / PyPI: 通常どおり、パッケージ マネージャーを通じて更新します。
  • インデックス、キャッシュ、構成の移行はありません。

完全な changelog: https://github.com/DeusData/codebase-memory-mcp/compare/v0.10.2...v0.10.3

セキュリティの検証
