コードベースメモリ mcp v0.10.4

コードベースメモリ mcp v0.10.4

インストールと診断のリリース。 v0.10.3 がインストールまたは起動を拒否した場合、特に Windows 上、またはパッケージ マネージャーを通じて cbm をインストールしたマシン上で、これを実行します。

以下の内容のほとんどは、正確な報告を提出した人々からのものであり、いくつかのケースでは、私たちが報告する前にバグの根本原因を発見しました。

Windows: 昇格されたアカウントはインストールまたはまったく起動できませんでした

管理者グループ アカウントとして実行すると、install が activation transaction I/O failed: owner-not-current-user で失敗するか、MCP サーバーが起動中に終了し、ログには閉じられたトランスポート以外何も記録されませんでした。

原因は私たちに特有のものでした。ファイルの所有者をトークンの ユーザー SID と比較しましたが、Windows は新しく作成されたオブジェクトにトークンの 所有者 SID をスタンプします。これは、Administrators グループのメンバーのデフォルトは BUILTIN\Administrators です。そのため、インストーラーは独自のステージング ファイルを作成し、数秒後にはそれを他の人のものとして拒否しました。何も実行されていないため、いくら再起動したりプロセスを閉じたりしても役に立ちませんでした。

また、作成したものに Windows が実際にスタンプする SID も受け入れられるようになりました。これは「trust 任意の管理者」よりも範囲が狭く、まったく異なるアカウントが所有するファイルは依然として拒否されます。 @spam0115 と @gotspatel によって報告されており、これが長期にわたる #1416 の原因である可能性が非常に高いです。

インストールしても、所有していないものには触れなくなりました

私たちが設定を踏みにじっていた人々のための 2 つの変更:

mise、Homebrew、nix、asdf、または Cargo によってインストールされたバイナリはそのまま残されます。 以前は、install は 2 番目のコピーを ~/.local/bin にドロップし (PATH の順序に応じてマネージド コピーをシャドウイングし)、シェルの rc ファイルに追加していました。これで、エージェントが設定され、バイナリと PATH はそのまま残ります。update は正直に拒否して、機能するコマンドに名前を付けます (mise upgrade、brew upgrade)。PATH は、実際にバイナリを配置したときにのみ変更されます。 @SC-CTS によって報告されました。

どの client を構成するかを選択できます。 install は、検出されたすべての client に対して MCP 構成、エージェント、スキル、フックを書き込みました。次回のインストールで再作成されるため、不要なものを元に戻しても無意味でした。 --clients=claude,codex はそれを制限し、--clients はサポートされているすべてのトークンを独自にリストします。 @PsyTech-Rob によって報告されました。

実際に何が起こったかを示すエラー

ここで 3 回連続で修正が加えられましたが、すべて同じ苦情からのものでした。私たちのメッセージは明らかに間違っていました。

  • アクティベーションの拒否は、表示されない証拠を指すことはなくなりました。 v0.10.3 は、セッションが引き起こした障害を「アクティブな CBM セッション」のせいにすることを正しく停止しましたが、出力されなかったエラーをチェックするように指示しました。拒否されたディレクトリとルールに名前が付けられます。
  • 起動できないサーバーにはその理由が表示されます。 Client パスの起動エラーは stderr のみに書き込まれ、MCP client では表示されません。そのため、「トランスポートが予期せず閉じられました」という具体的な名前付きの拒否が届きました。これらの障害は、理由を伴う JSON-RPC エラーとして届くようになりました。
  • JSON を編集せずに UI リスナーをオフにすることができます。 ui_enabled はループバック HTTP ポートを制御します。これを無効にする唯一の方法は、config.json を手動で編集することでした。 config list には見えず、config set によって拒否されました。これと ui_port の両方がファーストクラスの構成キーになりました。 @PsyTech-Rob によって報告されました。彼は 2 つのデバッグ セッションを費やしてスイッチを見つけました。

Codex、OpenCode、および設定ファイルの修復

  • 重複インストールによって Codex が完全に壊れることはなくなりました (@astandrik)。所有されているインライン フックの割り当ては、無視されて一緒に再追加されるのではなく、正規ブロックに調整されます。外部フック エントリは変更されずに保存され、本当にあいまいな TOML はファイルをまったく変更せずに拒否されます。
  • ~~OpenCode は、OpenCode が実際に読み取るファイルにランドをインストールします (@iandol)。~~ 訂正 (2026-08-14): これは半分だけ真実であり、完全に主張すべきではありませんでした。 ターゲティング が修正されました。OpenCode が無視する .json ファイルを常に作成するのではなく、opencode.json / opencode.jsonc のどちらか既に存在するものを書き込むようになりました。ただし、v0.10.4 と error: agent_config agent=OpenCode op=mcp_install では 書き込み自体が依然として失敗します。これは Linux と Windows の両方で報告されています。 #1630で追跡されました。これは、この修正が完了したと説明した 2 番目のリリースです。申し訳ありませんが、そうではないと言い続けた記者の方々に感謝します。
  • 私たちが作成した孤立マーカーは自動的に修復されます。 以前のインストールでは、オープナーのない終了マーカー # <<< が残る可能性があり、その後、すべてのインストールがその client に完全に失敗しました。削除すると浮遊線が取り除かれます。 write は依然として不均衡を理由に拒否されます。マーカーが 1 つあると、置き換える防御可能な領域がありません。

クエリの正確性とプラットフォームのサポート

  • OPTIONAL MATCH がサイレントに行を削除するのを停止しました (@SEPURI-SAI-KRISHNA)。ホップ バッファが飽和すると、一致しない行 (まさに WHERE x IS NULL が表面化するために存在するもの) が破棄されました。クラッシュでもメモリエラーでもありません。静かに結果が減り、答えが不完全であることを示すものは何もありません。
  • FreeBSD は独自の実行可能パス (@PR9000) を解決します。これにはインストールと所有権のチェックが依存します。さらに、主要な 3 つ以外のプラットフォーム用のビルド修正も含まれます。

セキュリティ

リリース パイプラインは、上流のプロジェクトがビルド時に公開するものをすべて rust するのではなく、ダウンロードした外部ツールを実行前に固定して検証するようになりました。検証は、単一の固定された参照から、ジョブが実行される可能性のあるすべてのプラットフォームを対象とします。

Andrew Hundt によって報告されました (#1245)。

信頼性

サブプロセスの生成は、ビジーなマシンでも存続します。 v0.10.3 は、カーネルが「再試行」で拒否したスポーンの再試行を開始しましたが、その時間はわずか約 30 ミリ秒でした。これは、一時的な低下には十分であり、数百ミリ秒にわたってプロセスが枯渇したままになるマシンにとっては十分ではありません。まさにそれが起こる瞬間です。再試行は、あきらめるまでに約 0.5 秒まで指数関数的に後退します。本当に疲れ果てたマシンでも、ハングするのではなく高速に障害が発生し、実際のエラー (バイナリの欠落やアクセス許可の拒否) は以前と同様に即座に失敗します。

また、リリース パイプラインは、リリースが公開される前にレジストリ エントリを公開しなくなりました。v0.10.3 自身のレジストリ ステップが、自身のアセットに対して 404 で失敗する原因となったバグです。

アップグレード

  • バイナリのインストール: 以下をダウンロードするか、install.sh / install.ps1 を再実行します。
  • パッケージ マネージャー: 通常どおり、パッケージ マネージャーを通じて更新します。cbm はそのバイナリをそのままにしておくようになります。
  • npm / PyPI: いつものように。
  • インデックス、キャッシュ、構成の移行はありません。
