コードベースメモリ mcp v0.10.2

コードベースメモリ mcp v0.10.2

インストールしてアップグレードするリリース。 v0.10.0 または v0.10.1 がインストールを拒否した場合、更新を拒否した場合、または MCP client がどこにも接続していないサーバーを示した場合、これが修正であり、これらの障害はすべて、過去 24 時間以内に提出されたユーザー レポートに基づいています。

これらすべての背後にあるパターンは、原理的に正しいゲートが通常の正当な設定を拒否し、その理由を説明しなかったということです。以下のそれぞれは、重要な保護を維持し、実際のユーザーを拒否していた部分を削除し、拒否された内容と続行方法を正確に指定しています。

npx (およびすべての一時的なインストール パス) が再び動作するようになりました

npx codebase-memory-mcp を介して cbm を実行すると、サーバーは何も応答しませんでした。client は 30 秒待機し、標準出力にゼロ バイトで終了し、エージェントは -32000: Connection closed として表示されました。 npx を呼び出すたびに、これが決定的にヒットします。

デーモンは、接続している client のバイナリ イメージを検証し、2 つの非常に異なる結果を 1 つの失敗として扱っていました。「このイメージのハッシュ方法が私のものとは異なる」 (チェックが存在する改ざんケース) と、「このイメージはまったく検査できません」 — これは、一時的な npx キャッシュ パスが常に生成するものです。 2 つ目は現在認められています。直前のハンドシェイクでは、セマンティック バージョン、ビルド フィンガープリント、プロトコル/ストア/機能 ABI がすでに証明されているため、その上で拒否することは、実際の互換性証明を入手できないものと交換することになります。本物の指紋 不一致 は依然として拒否されますが、許可は大声でログに記録されるため、弱いチェックは決して目に見えません。

個別かつ無条件: デーモンに到達できない client は、静かに終了するのではなく、JSON-RPC でその旨を通知し、その理由を示します。 @wassolles さんに感謝します。複製版、すでに読まれた入場パス、および 3 つの修正候補 (私たちが発送したものは彼らのものです) とともに到着しました。

通常の Linux ホームへのインストールは再び機能します

install.sh は error: failed to stage install candidate: activation transaction I/O failed で失敗しました。このメッセージは、実際にはアクセス許可ポリシーであったものについて、ディスク エラーとファイル システム タイプを探す人々に送りました。インストーラーは、インストール ディレクトリ * およびその上のすべての親 * にグループ書き込みビットを必要としませんでした。 WSL2 は、いくつかのディストリビューション スケルトンと共有プライマリ グループを使用するサイトと同様に、~ と ~/.local を 0775 に出荷します。

誰でも書き込み可能な親は依然として拒否されます。ローカル ユーザーはインストール中にパス コンポーネントを交換できます。グループ書き込み可能な親は警告され、受け入れられるようになりましたが、インストール ディレクトリ自体は厳密に所有者プライベートのままです。そこにバイナリが配置され、そこにグループ書き込みを行うと、検証と起動の間に別のアカウントが実行可能ファイルを置き換えることになります。拒否では、ディレクトリ、そのモード、および拒否されたルールが指定されるようになりました。

正確な述語と行に至るまで、クリーンなコンテナ内の @AmirF194 によってルートが引き起こされます。 @shochdoerfer と @iandol によって個別に確認されました。

0.9.x からのアップデートが再び機能するようになりました

v0.10.0 はグラフ UI が常に埋め込まれたプラットフォームごとに 1 つのアーカイブに統合されましたが、update は引き続きどのバリアントが必要かを尋ねました。「ui」は 404 のみで、「standard」は静かに * UI ビルドでした*。セレクターとそのフラグは消えています。 すでにフィールドにインストールされているバイナリを遡って修正することはできないため、リリースでは各アーカイブの ui-* という名前のコピーも公開されるようになりました。古い名前を要求するすべての 0.9.x アップデーターは同じバイトを取得し、何も要求されずに正常に完了します。 @iandol によって報告されました。

macOS インストール診断

install.sh は No such xattr: com.apple.quarantine を出力しなくなりました。これは無害な行 (curl でダウンロードされたアーカイブには単に隔離属性がありません) であり、無関係な障害の原因と誤解され、バグ レポートのタイトルになるほどでした。また、実行中のセッションによってインストールが本当にブロックされている場合、エラーは codebase-memory-mcp daemon status を指し、セッションが存在することを主張してセッションを見つけるのではなく、実際にセッションを保持しているプロセスをリストするようになりました。 @listepo によって報告されました。

アップグレード

  • バイナリ インストール: 以下をダウンロードするか、install.sh / install.ps1 を再実行します — インストーラーを再実行すると * 更新されます。
  • npm / PyPI: 通常どおり、パッケージ マネージャーを通じて更新します。
  • 0.9.x より: このリリースでは、古いアップデーターが再び動作します。すでに失敗している場合は、インストーラーを再実行するのが最も早い方法です。
  • インデックス、キャッシュ、構成の移行はありません。

セキュリティの検証

VirusT合計で、32 個の正確に抽出されたアーカイブ メンバーをカバーする 14 個の個別に抽出されたバイト オブジェクトが完成しました。 抽出マニフェストは、SHA-256 の出自によって、これらの関連付けを 8 つのダウンロード可能なアーカイブにバインドします。ダウンロード可能な .tar.gz/.zip リリース コンテナーは VirusTotal に送信されませんでした。

スキャンされた 14 個のオブジェクトのうち 13 個で、悪意のあるものは 0 件、疑わしいものは 0 件の判定が返され、決定的なエンジン結果は 55 ～ 66 件ありました (最低必要数: 50)。 1 つのオブジェクトには単一の Microsoft 機械学習検出 (!ml) が含まれており、このプロジェクトではこれを既知の誤検知として扱い、非表示ではなく公開します。他のエンジンはすべてき​​れいに戻りました。証拠と、これらのアーティファクトを自分で検証する方法については、ウイルス対策誤検知 を参照してください: objects/scan-cac31c5358f3a1dcccc4d4ccbe2591f6fbae58949d23bb341429a6197e93a64b--codebase-memory-mcp
