コードベースメモリ mcp v0.12.0

#v0.12.0

CBM レンズとドキュメントを読み取るコード グラフをご紹介します。

v0.12.0 は codebase-memory-mcp のこれまでで最大のリリースです。v0.11.0 以来 231 件のマージされたプル リクエストがあり、そのうち 40 件はコミュニティからのものです。

4 つの見出しがそれを定義しています。

  1. CBM レンズ ベータ: 人間向けのコード グラフ。 これまで、グラフの力はエージェントを通じてのみ人々に届きました。 Lens は私たちの新しいヒューマン インターフェイスです。コードナレッジグラフを直接提供します。これは、すでに実行しているバイナリ内に同梱されており、ループバックでのみリッスンします。ソース、グラフ、アーキテクチャ、インデックス カバレッジ、ブラウザー ローカル アシスタントが並べて配置されており、表示されるすべての事実がどこから来たのかを示しています。 Lens は @BernhardJackiewicz の作品に基づいて構築されており、彼は現在、レンズを所有するためにプロジェクトに参加しています。

  2. ドキュメントがグラフに加わりました。 これまで、グラフはコードが停止した場所で停止していました。現在、ドキュメント コメント、Markdown、reStructuredText、AsciiDoc および PDF ドキュメント、アーキテクチャ決定記録、図、OpenAPI 仕様がその一部となっています。それぞれは、説明されている関数、タイプ、ファイルにリンクされています。エージェントはドキュメントをたどって、そのページで説明されている正確なコードに到達し、関数からそれを説明するすべてのページに戻ることができるようになりました。 Lens でもそれができます。リンクは設計上厳密です。参照は、定義が 1 つだけ指定されている場合にのみエッジになります。精度バーをまだクリアしていないリンク ファミリはカウントされて報告されますが、グラフに推測されることはありません。

  3. スマート CI: グラフがテストを選択します。 detect_changes は、変更がどのテストに影響するかを判断できるようになりました。差分からグラフにシードを取得し、変更されたコードに依存するすべてのものを調べ、それらのパスの最後にあるテストにそれぞれ理由を付けて名前を付けます。証拠が欠落しているか疑わしい場合は、「すべてを実行する」と答え、その理由を説明します。それは決して静かに狭くなることはありません。 codebase-memory-mcp 自身の CI が最初のユーザーです。プル リクエストは変更が触れるテスト レーンのみを実行し、グラフのテスト選択はすべての PR の横で実行されます。

  4. グラフ内のコードとしてのインフラストラクチャ。 Kubernetes マニフェスト、Helm チャート、Flux および Argo CD、Compose ファイル、Docker ファイルとスクリプト、Makefile、およびそれらをデプロイする CI ジョブがリンクされるようになりました。サービスは、ワークロード、イメージ、Docker ファイルを通じて、コンテナーが実行するプログラムまで追跡できます。

コードグラフ自体もより鮮明になりました。

  • C の typedef、マクロ、列挙子は独自の ID を取得します。
  • プロセスの起動は SPAWNS エッジになります。
  • 解像度の修正は、C#、C++、TypeScript、Python、PHP、Rust、Go をカバーします。

アップグレードしていますか? アップグレード後の各既存プロジェクトの最初のインデックスは、一度完全に再構築されます。詳細はアップグレードノートに記載されています。いくつかのアイデンティティとデフォルトも変更されました。 重大な変更を参照してください。

@BernhardJackiewicz は、UI のサブシステム所有者として codebase-memory-mcp に参加します。 @BernhardJackiewicz は、CBM レンズとなる CBM 読み取り面上に読み取りインターフェイスを構築し、プロジェクトに貢献しました (#2068; #1964 の設計と追跡)。彼はまた、README の Lens セクションを新しいウォークスルーとスクリーンショットで書き直しました (#2383)。このリリース以降、彼は UI サブシステムを所有し、Lens を担当します。彼を迎え入れることができてとてもうれしいです。

CBM レンズ ベータ (#2068)

MCP ツールは、グラフに対するエージェントのインターフェイスです。 CBM Lens Beta はあなたのものです。コードナレッジグラフの力を人間にもたらすという私たちの試みです。これは以前のグラフ UI を置き換え、バイナリに組み込まれています。

codebase-memory-mcp --ui=true --port=9749
  • Explore: は、現在のファイルまたはマークされたソースを追跡し、その直接の依存関係と、グラフおよびローカル Git の証拠からのファイルレベルの影響の概要を示します。
  • Galaxy: ノード、ファイル、フォルダーを検索し、深さとエッジ タイプに基づいて受信または送信の関係を拡張します。
  • アーキテクチャ: リポジトリ マップ、ルート、ホットスポット、システム構造および動作。
  • カバレッジとシステム: インデックスで欠落したものとその理由、さらにデーモンのステータス、インデックス、診断、MCP 構成。
  • ADR: manage_adr と共有されたプロジェクトの意思決定文書をブラウザーで編集します。
  • プロジェクト インデックスの追加 (Alt+P): ローカル リポジトリを選択し、名前を付けて、デーモンの進行状況を追跡します。
  • ローカル チャット: 選択したコードについて質問します。推論はブラウザ内で実行されます。モデルの重量はバンドルされていません。モデルをアクティブ化した場合にのみ、Hugging Face からダウンロードされます。
  • 実行時の証拠: ingest_traces 経由で送信されたコール パスが保存され、Lens は実際に実行されたホップをマークします。

Lens はループバックで実行され、ソース ファイルを読み取り専用に保ち、各事実の出所に名前を付けます。フロントエンド エラーはサーバー上でジャーナルに記録されるため、バグ レポートにフロントエンド エラーを含めることができます。

CBM レンズは、CBM 読み取り面に関する @BernhardJackiewicz の作業に基づいて構築されており、著者の同意を得て提供されています (#1964 の設計と追跡)。 @BernhardJackiewicz が UI サブシステムを所有するようになりました。ありがとう、@BernhardJackiewicz。あなたの取り組みがなければ、このリリースはまったく違ったものになるでしょう。

グラフ内のドキュメント

ドキュメントコメントリンク (#2550、#2593)

  • C# <see cref>、<seealso cref>、<exception cref>、および <inheritdoc cref> は、プロジェクト ファイルから評価された MSBuild グローバル使用を含む、コンパイラ独自の検索ルールによってバインドされます (#2550)。
  • Go doc リンク、Javadoc および KDoc タグ ({@link}、@see、@throws、{@value}、@sample)、Rust ドキュメント内リンク、Perl POD L<>、TypeScript/JavaScript {@link}、PHPDoc @see、Doxygen @ref/@see も同じルールに従います (#2593)。
  • #2593 で出荷される 17 のドキュメント コメント リンク ファミリはそれぞれ、ビルドに使用されなかったリポジトリに対するブラインド監査に合格しました (バー: Wilson 95% 下限 ≥ 0.90)。
  • ファミリは依然としてバーより下にありますが、TS/JS {@linkcode} と @see、ダイアグラム リンク、OpenAPI operationId リンクなど、グラフの外に残ります。
  • index_status は、doc_links ブロックを取得します。つまり、MENTIONS カウントと、理由によってカウントされた未解決の参照 (missing、ambiguous、external など) です。サンプルとして diagnostics='full' を渡します。

ドキュメント (#2551)

  • Markdown: セクションは、リンク、裸のパス、およびパスまたは修飾名を保持するコード スパンを介して、名前を付けたコードにリンクします。 #L3-L9 などの行範囲は、それを保持する最も内側の定義をバインドします。裸の名前は決してエッジではありません。
  • reStructuredText / Sphinx: ロール (:class:、:meth: …)、オブジェクト ディレクティブ、autodoc、literalinclude、およびインライン リテラルからのリンクを含む、タイトルごとの Section。 Python 名は、Sphinx が名前をインポートする方法によって解決されます。 conf.py はテキストとして読み取られ、実行されることはありません。
  • AsciiDoc / Antora: セクションは、include:: ディレクティブとタグ領域を通じてリンクします。
  • PDF: すべてのページは Section になり、そのテキストは検索可能になり、言及されているパス、ファイル名、修飾名にリンクされます。このエクストラクターは依存関係がなく、untrusted 入力用に構築されています。44,070 個のシード済み変異 PDF が ASan および UBSan で実行されましたが、検出結果はありませんでした。暗号化されたドキュメントはそのように報告されます。
  • ADR: マークダウンと reST で検出されました。それらの事実は、前付、ヘッダー フィールド、またはステータス セクションから得られます。
  • マークダウンのファイル間参照も REFERENCES_FILE エッジになるため、ドキュメント ハブがファンイン クエリに表示されます (#1832、@cdeust に感謝)。

完全なドキュメント コメント (#2459)。 複数行の // および /// の実行、属性とエクスポートの上のドキュメント、フィールドと列挙メンバーのドキュメント、Go パッケージのコメント、および Perl POD が、500 バイトのカットなしで完全にキャプチャされるようになりました。実際のコーパスでの完全なドキュメントのキャプチャ:

|言語 |前 |後 | |---|---|---| |行く | 35% | 99.999% | | C# | 10% | 99.8% | | Rust | 7% | 99.9% | |ジャワ | 74% | 99.99% | | TypeScript | 42% | 100% |

ドキュメントセクションの候補 (#2574). ドキュメントでは、名前を付けずに関数を説明することがよくあります。これらのセクションについて、get_code_snippet は possibly_about 候補 (セクションに関する) と possibly_described_in 候補 (関数に関する) をリストするようになりました。各候補者には、ブラインド サンプルで判断された確率が含まれます。これらはエージェントが検証するための手がかりであり、エッジではありません。せいぜい約半分が正しいため、ツールはそう判断します。 get_file_outline には、ファイルに関する可能性のあるセクションがリストされます。

スマート CI: グラフがテストを選択する (#2458)

変更ごとにすべてのテストを実行すると、時間がかかり、コストがかかります。どのテストをスキップするかという手書きのルールは推測にすぎません。このリリースでは、グラフが決定します。

  • グラフからのテストの影響 detect_changes と scope: "tests":

    • マージ ベースから HEAD への変更を固定します。
    • 変更されたハンクからグラフをシードします。
    • 呼び出し、参照、読み取り、ルートを介して、ヘッダー インクルードとそのマクロを介して、それらに依存するすべてのものをウォークスルーします。

    これらのパスの終点にあるテスト、スイート、ランナーのエントリ ポイントが答えであり、それぞれにどのように到達したかが示されています。

  • サイレントミスは決してありません。 証拠が欠けていたり疑わしいからといって、選択肢が狭まるわけではありません。解析不可能な変更、マップされていないテスト、またはテストランナー main に到達すると、その理由が示され、答えが「すべて実行」に変わります。

  • すべてのリポジトリのパラメータを探索します。 detect_changes は、edge_types、fixpoint、および via を受け取ります。どのプロジェクトでも、変更の完全なインバウンド依存関係のクロージャを要求し、各ヒットへのパスを確認できます。

  • チーム バンドル。 ZZPH100​​ZZ は、コミットの凍結グラフとそのテストごとのカバレッジ マップをバンドルとしてパッケージ化します。プル リクエストの選択は、最初からインデックスを作成するのではなく、マージ ベースのバンドルから開始されます。

  • Dogfooded. codebase-memory-mcp 独自のプル リクエストは、変更が関与するテスト レーンのみを実行します。ドライランとリリースでもすべてが実行されます。グラフのテスト選択は、すべての PR でレポート専用のシャドウとしても実行されます。これにより、デフォルトでテスト実行が絞り込まれる前に、必要なレコードが構築されます。

現在、テスト モデルは codebase-memory-mcp 自身の C テスト ランナーを認識しています。他のテスト ランナーの場合、scope: "tests" は、規則がマッピングされるまで「すべてを実行する」と答えます。ウォークパラメータはどこでも機能します。

グラフ内のコードとしてのインフラストラクチャ (#2597、#2643、#2644)

インフラストラクチャ グラフの一部は以前から存在していました。今、彼らは連鎖します。 kubespray、cluster-api から opentelemetry-demo まで、17 のオープンソース インフラストラクチャ リポジトリで測定しました。それら上で、サービスはそのコンテナが実行するコードまでウォークできます。

Service → Deployment → Image → Dockerfile → main()
                     └ the container's environment variables
  • Kubernetes:
    • すべてのマニフェスト ドキュメントは、安定した ID を持つオブジェクトです。
    • オブジェクトは、ConfigMap、Secret、ServiceAccount、およびそれらが指定したボリューム、およびそれらの Flux、Argo CD、Cluster API、および cert-manager 参照にリンクします。
    • サービスは、セレクター全体が選択するポッドにリンクします。
  • Helm: テンプレート化されたマニフェストもオブジェクトになり、チャート テンプレートはそれに含まれる名前付きテンプレートにリンクし、file:// チャートの依存関係が解決されます。
  • チェーンの展開: DEPLOYS エッジの由来:
    • Flux のカスタム化と HelmRelease、および Argo CD アプリケーション;
    • スクリプトおよび Makefile 内の kubectl apply、kustomize build、および helm install|upgrade|template。
    • Terraform helm_release、および Helm SDK を使用する Go インストーラー。
  • ビルドして実行:
    • Docker ファイルはビルド元のイメージに依存し、SPAWNS はそれぞれのコンテナーが実行するものにリンクします。
    • 新しい Image ラベルは、ワークロード、Compose サービス、およびビルド コマンドをイメージをビルドする Docker ファイルに結合します。
    • スクリプトと CI ジョブ (GitHub アクション、プロウ) は、それらが実行するスクリプトとプログラムにリンクし、make TARGET はそのルールにリンクします。
  • 環境、値なし: コンテナーが設定する各変数は、そのコンテナー独自の EnvVar になります。値が保存されることはなく、秘密情報がグラフに到達することもありません。
  • ツール: trace_path はモード run、deploy、topology を獲得します。 search_graph は、種類と名前空間によってインフラストラクチャをフィルター処理します。

より鮮明なコードグラフ

C および C++

  • Typedef とマクロ (#2543):

    • Typedef はノードになり、匿名 typedef struct/enum {…} X; 集合体はその typedef に基づいて名前が付けられます。
    • #define NAME は、NAME と呼ばれる関数または型を置き換えなくなりました。マクロは独自の <module>.<NAME>#macro ID を取得します。
    • 不明な先頭マクロの背後にある関数は、実際の名前を保持します。
    • 測定値: redis は 573 Type ノードとカール 193 を獲得しました。以前に同じ名前のマクロで失われた関数が復元されました (redis では 45、curl では 41)。

  • メンバー アクセス (#2458): a.b および a->b は、オブジェクトの実際のタイプのフィールドをバインドします。型が不明な場合、1 つの構造体が持つメンバー名のみをバインドします。このプロジェクトでは、ファイルが実際に名前を付ける構造体に使用される C フィールドの使用率が 58.1% から 97.6% に増加しました。

  • 条件定義 (#2458): #if ブランチ、#[cfg]、または Go ビルド タグごとに 1 回存在する定義ごとに 1 つのノード。すべてのバリアントのスパンは variants プロパティに保持されます。条件ブロック内の定義が、C++、C#、Objective-C、Elixir、Fortran、Haskell 用に抽出されるようになりました。

  • プラットフォーム バリアント (#2630): プラットフォーム ファイルまたはディレクトリごとに 1 回定義された C/C++ 関数 (src/unix/fs.c と src/win/fs.c、arch/x86/... と arch/arm64/...) は、独自のパスの下にファイルごとに 1 つのノードを保持するため、すべての実装はそのパスで検索できます。これらのバリアントは variant_key プロパティを共有しており、Smart CI はバリアントの変更をすべてのバリアントのテストに到達したものとして扱います。

  • マクロを多用した C/C++ でサイトごとに 1 つの定義 (#2626、#2629): 生の解析とマクロ拡張された解析で定義のスコープまたはスペルが一致せず、両方のコピーがグラフに表示されるために使用されました (例: bitonic<int64_t, AVX2> と bitonic < int64_t , AVX2 >)。各定義は 1 つのスペルを持つ 1 つのノードになりました。dotnet/runtime では、重複定義は v0.11.0 の 545 グループから 185 グループに減りました。

  • ファイル間の呼び出し (#2466):

    • Class::member 呼び出しは、X::instance()->m() や auto w = Widget::create(); w->m() などのファイル全体で解決されます。
    • qBittorrent は 489 個の正しい CALLS エッジを取得しました。

  • エクスポート マクロ (#2005): エクスポート マクロの背後に隠されていた型定義が回復されました (@XIYBHK に感謝)。

  • 戻り値の型 (#2274): C ファミリ関数の戻り値の型は、そのポインターと修飾子を保持します。

  • マクロでラップされた定義 (#2450): void FNAME(first)(void) および void Cls::__API_HOOK(Spawn)() は、マクロの引数 (first、Spawn) に基づいて名前が付けられます。 1 つのラッパー マクロが生成するすべての定義は、単一のノードを共有するために使用されます (#946、#1957)。 言語間 (#2458、#2227)

  • SPAWNS エッジ。 subprocess.run、exec.Command、child_process.spawn、posix_spawn、Process.Start、Command::new および約 30 言語のそれらの類似言語は、プログラムにちなんで名付けられた Process ノードを指すようになりました。以前は、これらは CALLS エッジと推測されていました。

  • 言語をまたいだ名前の推測はありません。 名前のみの一致は、別の言語で定義されたシンボルをバインドすることはなく、構成言語 (Makefile、CMake、YAML) はコードにバインドされなくなりました。

  • Bash インポート は、スクリプトが実行するすべてのコマンドではなく、スクリプトがソースとするファイルです。

  • 同じ語幹を持つファイルとフォルダーは両方とも残ります (#2624)。 genproto/ の隣の genproto.sh は 1 つの修飾名を共有していましたが、ファイルのモジュールはそれを指すエッジとともにドロップされました。フォルダーの綴りは proj.pkg.genproto/ になりました。ここで、ディレクトリが Java または Go パッケージの場合、フォルダーはその名前を維持し、ファイルのモジュールは proj.pkg.genproto#sh になります。シンボル名は変わりません。 17 のインフラストラクチャ リポジトリで、27 個の失われたモジュール → 0。

パフォーマンスとメモリ

  • 全面的に高速なインデックス作成 10 個のベンチマーク リポジトリ (LSP 言語ごとに 1 つ) において、このリリースの完全なインデックスはどこでも v0.11.0 を上回っています。 Apple M5 Pro での 3 回の実行の中央値:

    |リポジトリ | v0.11.0 | v0.12.0 |変更 | |---|---|---|---| |パール | 7.0 | 1.1 | −84% | | PHP | 7.4 | 1.7 | −77% | | Rust | 8.0 | 1.9 | −76% | | C | 9.2 | 3.0 | −67% | |行く | 45.2 | 18.6 | −59% | |コトリン | 11.0 | 4.7 | −57% | | Python (ジャンゴ) | 11.9 | 6.0 | −50% | | TypeScript | 33.9 | 21.6 | −36% | | C# | 132.0 | 120.8 | −8% | |ジャワ | 76.0 72.0 | −5% |

    ピーク メモリは 10 個中 9 個で低くなり、すべてのリポジトリが実行のたびに同じグラフを生成しました。

  • Linux カーネル、ドキュメント パスの有無にかかわらずインデックス作成にかかる時間。 グラフ内のドキュメント は、新しいインデックス作成ステップを 1 つ追加します。すべてのドキュメント セクションはコードに対してスコア付けされ、対象となる関数とファイルが検索されます。デフォルトでは、完全なインデックス (デフォルト モード) に対して実行され、moderate または fast インデックスに対しては実行されません。 doc_candidates は、どのモードでもオンまたはオフに切り替えます。

    | Linux カーネル、完全なインデックス | v0.11.0 | v0.12.0 | |---|---|---| |コードグラフのみ | 236 秒、21.3 GB ピーク | 225 秒、14.3 GB ピーク | |コードグラフ + ドキュメントパス (デフォルト) |該当なし | 396秒 |

    約 100,000 関数未満のリポジトリでは、ドキュメント パスのコストは約 1 秒以下です。

  • クエリ ツールは、すべてのプラットフォームで高速に応答します (#2642)。 macOS および Linux では、すべての応答は以前とバイト同一です。時間が変わっただけ。

    • search_code は、grep または PowerShell を使用する代わりに、プロセス中のインデックス付きファイルをスキャンします。 Django では、デフォルトの検索は 908 ミリ秒から 355 ミリ秒に短縮され、3.8 から 0.7 に幅が広がりました。 Windows on Arm では、検索は 1.6-3.4 から 0.2-0.5 に減少しました。 GitHub の Arm ランナーでは、PowerShell スキャンには 30 秒のスキャン制限に対して、呼び出しごとに最大 31 秒が必要でした。 Windows も macOS や Linux と同様に完全に一致するようになりました (重大な変更点 を参照)。
    • query_graph は、O(n²) ではなく O(n log n) でソート、重複排除、およびグループ化を行います。 django の 29,000 のメソッドを通じて、WITH ... ORDER BY は 41 秒から 62 ミリ秒に、RETURN ... ORDER BY は 2.2 秒から 50 ミリ秒に、WITH DISTINCT は 18 秒から 56 ミリ秒に短縮されました。
    • 読み取りツールは、検索ごとにデータベース ファイルをロックするのではなく、100 ミリ秒ごとに更新される 1 つの SQLite 読み取りトランザクションでグラフ検索を実行します。グラフ全体の count(*) は 508 ミリ秒から 184 ミリ秒に短縮され、ファイル ロックのコストが高くなる Windows では 2.9 から 0.39 に短縮されました。
    • カーネル スケールのグラフ (Linux カーネル: 8.5 100 万ノード、16.9 100 万エッジ):
      • trace_path および search_graph の次数フィルターは、インデックス バージョン (カーネル上の 1.2-1.5 ) ごとに 1 回構築され、メモリ バジェットに課金されるメモリ内の隣接インデックスを調べます。アイドル状態のものは 10 分後に解放されます。 schedule から trace_path は 7.5 s から 22 ミリ秒に短縮され、ハブ検索は 4.2 s から 0.17 s に短縮されました。
      • query_graph は、すべての一致をメモリ内に保持するのではなく、行をストリーミングします。グラフ全体 count(*) は、24.9 GB でピークに達し、クエリ時間制限で停止していました。 289 MB 以内であれば 11 秒で応答するようになりました。
      • get_architecture は 9 ミリ秒から 0.9 ミリ秒に短縮され、完全一致名またはプレフィックス名の検索は 1.1 秒から 14 ミリ秒に短縮されました。
      • search_code は 11.8 から 3.4 に下がりました。
    • 変更されていないリポジトリのインデックスを再作成しても、最初にデータベース全体がコピーされなくなりました。 18.4 を使用して 19 GB を書き込んだカーネル上。 2.4 がかかり、何も書き込まれなくなりました (django 841 ミリ秒から 539 ミリ秒)。
    • list_projects は、表示されているブランチに対してのみ git を要求します。プロジェクトごとに 7 回ではなく 2 回の git 呼び出しを実行します (1 つのプロジェクトで 94 ミリ秒から 40 ミリ秒になり、プロジェクトごとに節約量が増加します)。

  • すべての呼び出しでの起動が高速化。 SHA-256 が ARMv8 SHA2 および x86 SHA-NI 命令で実行されるようになりました。フック パスのセッション開始は、Apple arm64 上で 1.448 から 0.376 に、同一のダイジェストでドロップされました (#2575)。

  • 増分更新時のディスク チャーンが大幅に減少します。 294 MB の Django インデックスを 1 行編集すると、SQLite WAL に 5.2 GiB が書き込まれました。 0.52 GiB (#2469) と書き込まれるようになりました。

  • マシンを考慮したメモリ バジェット。

    • 予算は RAM の合計だけでなく、空きメモリに基づいて決定されるようになりました。ビジーな 48 GB ホスト上のカーネル インデックスは、使い果たすのではなく終了します。
    • ディスクへの流出は、空き容量が 10 GB 未満では開始されません。
    • プロセスが強制終了されてもスピル ファイルは消えます (POSIX)。
    • すべてのプロジェクトの孤立したステージング データベースが再利用されます (#2233)。

  • 無駄のない割り当て。 Go コーパスでは、割り当ては 245.5 M から 134.8 M に減少し、グラフ出力は変わりませんでした (#2233)。

  • macOS メモリ フットプリントの削減 macOS のインデックス ワーカーはパージされたメモリを返すため、OS が請求するメモリ フットプリントが減少し、バイト同一のグラフ (#2581) が表示されます。

  • アルゴリズムの修正:

    • LSP サーフェスは線形時間でデコードします (#2288、ありがとう @JosephStarobinets)。
    • Python スコープ チェーン ルックアップは 1 つのパスにまとめられます (#2252、Andrew Hundt による著作)。
    • ドキュメントセクションのスコアリングは正確かつ安価です (#2582)。
    • 繰り返しのリゾルバー作業は、大きなファイルを切り捨てることなく制限されます。境界に達したファイルは、部分的なものとして通知されるのではなく、不完全として報告されます (#2522、#1527)。
    • Python サブモジュールのプローブとクラスおよびワイルドカード スキャンは、レジストリ全体を調べなくなりました (#2532、#2535)。

  • 大きなインデックスが破損しなくなりました。 バルク SQLite ライターは、長いキーを持つ大きなグラフ上で空の内部ページで B ツリー レベルを終了することがありました。その後、SQLite はデータベースが不正であると報告しました。修正されました (#2330)。
  • 設定データベース (#2650):
    • 設定データベースの起動競合を修正しました。別のプロセスが設定を書き込んでいる間、daemon start --port、--ui=true --port、およびその他のコマンドが「デーモンが UI 構成を受け入れませんでした」または「保存されたランタイム設定をロードできませんでした」というエラーで失敗する可能性がありました。書き込みが完了するまで待機するようになり、デーモンを起動しても、変更されていない UI 設定が書き換えられることはなくなりました。
    • 回復ギャップを修正しました。設定の書き込み中にプロセスが強制終了された後、設定データベースが手動で修復されるまで、それ以降のすべてのコマンドが「保存されたランタイム設定を読み込めませんでした」というエラーで失敗しました。起動時に中断された書き込みがロールバックされ、続行されます。
  • 同時実行性とデータ損失のバグが減少します:
    • アイドル状態のデータベースの同時最初の読み取りが競合しなくなりました (#2561)。

    • 応答せずに終了したインデックス ワーカーには名前が付けられます (#2494)。

  • Git のリダイレクトはなくなりました。 cbm 独自の Git コマンドは、フックおよびエディター端末から継承されたリポジトリ リダイレクト変数 (GIT_DIR、GIT_WORK_TREE など) を無視します (#2341)。
  • メモリ安全性の修正:
    • WIT 文法スキャナーでの初期化されていない読み取り。MemorySanitizer によって表面化されました (#2596)
    • reST セクションのテキスト内の未書き込みバイトの読み取り (#2583)

    • 呼び出し引数が長すぎると、512 バイトのフォーマット バッファーがオーバーランし、深くネストされた構文によりスタックが使い果たされる可能性があります。両方のウォーカーが制限され、反復されるようになりました (#2478)

アップグレードに関する注意事項

  • プロジェクトごとに 1 回の完全なリビルド。 このリリースでは、C マクロ、列挙子、およびフィールドの識別方法が変更されます。また、ドキュメント レイヤーとインフラストラクチャ グラフも追加され、インデックス形式が 1 から 2 に移行します。したがって、v0.11.0 以前によって書き込まれたインデックスは、次回インデックスが作成されるときに一度完全に再構築されます (#2543、#2550、#2551、#2574、#2597、#2643)。
  • それまでは、古いグラフが応答し続けます。index_status は、インデックスがドキュメント リンクよりも古いことを指摘しています。
    • 大規模なリポジトリでは、最初のインデックスの時間を計画します。
    • プロジェクトの ADR 文書は引き継がれます。
    • v0.10.x から来たのですか? v0.11.0 (#1104) で導入されたインデックス形式の境界は、同じ 1 回の再構築でカバーされます。
  • Terraform と Ansible の編集では完全にインデックスが再作成されます。 変更された Terraform または Ansible ファイルは増分ではなく完全な再インデックスを取得するため、ファイル間のエッジが古くなることはありません (#2643)。
  • クロスリポジトリ リンクを再実行します。 リビルドにより CROSS_* エッジとそのステータスが一緒に削除されるため、リンクされたプロジェクトに対して index_repository(mode="cross-repo-intelligence") を再度実行します。
  • インデックスはより多くのファイルをカバーします。 PDF、AsciiDoc、ダイアグラム ファイル、OpenAPI 仕様、.NET プロジェクト ファイル、Sphinx .txt ソースが読み取られるようになり、ドキュメント レイヤーに独自のテーブルが追加されます。ドキュメントの多いリポジトリでは、より大きなインデックスが取得されます。
  • 非常に大規模なリポジトリ: ドキュメント パスと doc_candidates。 ドキュメント セクションの候補のスコアリング (#2574) は、非常に大規模なリポジトリでは最大の追加インデックス作成コストとなります。デフォルトでは、完全なインデックスに対して実行され、moderate または fast のインデックスに対しては実行されません。 Linux カーネルでは、約 3 分追加されます。約 100,000 関数未満のリポジトリでは、約 1 秒以下です。 codebase-memory-mcp config set doc_candidates false はすべてのモードでオフになり (true はすべてのモードでオンになります)、index_repository(doc_candidates: ...) は 1 つのインデックスに対して同じことを行います。どちらの方法でもコードグラフは変わりません。 possibly_about / possibly_described_in リードのみが省略されます。これをオフにすると、カーネルは v0.11.0 (#2610、#2628) よりも速くインデックスを作成します。
  • ウォッチャーのスコープ。 バックグラウンド ウォッチャーは、開いている各 MCP セッションがルートとなっているプロジェクトに従います。CLI または別のプロジェクトのセッションからインデックス付けされたリポジトリは監視されません。ここでは何も変わりませんが、index_status はそう言うようになりました (#2348)。
  • 新しいオプトイン設定 (デフォルトではすべてオフ):
    • watch_non_git
    • index_max_files
    • index_max_source_mb
    • CBM_STARTUP_TIMEOUT_MS
    • CBM_WALK_MAX_NODES (必要に応じて、AST ウォークのノード キャップを復元します)

    • C メンバーは、複数の構造体が共有する名前にアクセスし、任意のフィールドにバインドされなくなりました。
    • SEMANTICALLY_RELATED 入場とスコアが再調整されます。
  • Windows の search_code は、macOS や Linux と同様に一致します。 PowerShell Select-String を使用し、大文字と小文字を区別せずに一致し、.NET 正規表現構文を使用し、NUL バイトを含むファイルをテキストとして読み取りました。現在、すべてのプラットフォームは大文字と小文字を区別して照合し、拡張正規表現を使用し、バイナリ ファイルをスキップするため、同じクエリはすべての OS で同じ答えを返します (#2642)。
  • uninstall -y はプロジェクト インデックスを保持します。 それらを削除するには、--delete-indexes を追加します (#2517)。
  • detect_changes のデフォルトのベース。 常に main (#2496) ではなく、origin/HEAD (その後は main、master、アップストリーム) と比較するようになりました。
  • より厳密な入力:
    • Cypher は、以前は黙って無視していた非数値 SKIP/LIMIT を拒否します (#2002)。
    • コンパイルが大きすぎる正規表現は拒否されます (#2475)。
    • search_code は context を 200 行でキャップします (#2474)。
