コードベースメモリ mcp v0.10.1

コードベースメモリ mcp v0.10.1

迅速な修正リリース。 MCP client (Claude Code、Codex、またはその他の仕様準拠の client) を通じて cbm を使用している場合は、今すぐアップグレードしてください。 v0.10.0 では、コア検出ツールのデフォルトの出力形式は、まさにこれらの client で空の {} としてレンダリングされます。グラフは正常で、デーモンも正常で、データは応答に含まれていましたが、client が実際に読み取る応答の部分は空でした。 CLI の使用には影響がありませんでした。まさにそれが、これがリリース ゲートを逃れた理由です。

v0.10.0 リリースから数時間以内にこれを報告した @Navier8 さんの #1522 に多大な感謝を申し上げます。コードを読む前に、同じバイナリ、同じインデックス、フォーマットごとの呼び出しテーブルで、コードを読む前に障害の原因を MCP 応答パスに特定しました。レポートでは 2 つのバグを挙げています。それがトリガーした検証スイープにより 3 番目のものが見つかりました。ここでは 3 つすべてが修正されており、3 つすべてが 1 つの障害形状を共有して v0.10.0 として出荷されます。 成功ステータスを持つ空の結果 — LLM client にとって考えられる最悪の障害モードです。これは、「空」と「何も見つかりません」を区別できず、エラーが表示される代わりに誤った結論を黙って導き出します。

何が壊れ、何が変わったのか

1.ツリー形式のツールの応答は、MCP clients (デフォルト形式、プライマリ パス) で {} としてレンダリングされます。 v0.10.0 ワイヤ サイズの最適化により、ツール ペイロードの structuredContent への複製が停止され、空のオブジェクトがその場所に残されましたが、すべてのツールは引き続き寛容な outputSchema を宣言しました。 MCP 仕様では、clients に次のように指示しています。ツールが出力スキーマを宣言すると、結果は structuredContent になります。したがって、search_graph、trace_path、query_graph、get_architecture、search_code、および detect_changes はすべて、すべてのプラットフォームでスキーマを尊重する client に {} を返しました。コントラクトはエンドツーエンドで真実になりました: outputSchema を宣言するツールはありません (ツールの出力は format パラメーターによって正当に変化するため、正直な静的スキーマは存在しません)、JSON オブジェクトのペイロードは解析された structuredContent を運び、エラー エンベロープは機械可読な structuredContent.error を保持し、テキスト形式のペイロードは単純に structuredContent キーを保持しません。これも保持されます。 v0.10.0 は、ペイロードを 2 回送信しないという利点があります。

2. 7 つ以上のパイプライン リクエストが MCP サーバーを完全に強制終了しました。 このリリースのツール サーフェスを検証しているときに見つかりました。1 回のバーストで 7 つ以上のリクエストをサーバーに書き込むと (これはまさに並列ツール呼び出しを発行するエージェントが行うことです)、8 フレームの入力キューがオーバーフローし、オーバーフロー ハンドラーがセッション全体を破壊しました。終了コード 1、出力ゼロ バイト、計算済みの応答はすべて失われます。満杯のキューはバックプレッシャーになっています。ワーカーが追いつき、すべてのリクエストが応答を得るまで、リーダーは単に入力の受け入れを停止します。 7、24、64 回のバーストで検証。

3. config get はすべての質問に空の文字列で答え、0 で終了しました。 未設定のキーは何も出力しませんでした (一方、config list は喜んでデフォルトを表示しました)。また、スペルを間違えたキーも同様でした。タイプミスは、正しく読み取られた設定と区別できませんでした。 config get は保存された値またはキーの実際の実行時のデフォルトを出力するようになり、get、set、および reset では同様に不明なキーはエラーになります (既知のキーがリストされた出口 1)。

なぜ門がそれを見逃したのか — そして今それを守っているのは何なのか

正直な部分: structuredContent の変更に対する私たち自身のテストは、ユニット レベルと出荷されたバイナリ スモーク スイートの両方で 壊れた動作を正しいものとして固定しました。これは、間違ったコントラクトを主張するテストは、テストしないより悪いということを思い出させてくれます。パイプラインがバグに同意したため、リリース パイプラインは緑色でした。そのクラスは現在 3 つの方向からクローズされています。ユニット スイートはツール テーブル全体を列挙し、登録されているツールごとに 3 つのエンベロープ ブランチ (不在 / 解析済みオブジェクト / エラー) をすべてバインドします。フロントエンド スイートは、容量を超えたパイプライン入力が損失なく応答されることをアサートし、スモーク スイートはスキーマ準拠の MCP client が行う方法で 実際に出荷されたバイナリ を駆動し、デフォルト形式の応答は決してレンダリングできないことを主張します。 {}、outputSchema をアドバタイズするツールは存在しないこと、深さ 24 のパイプライン バーストは 24 の応答を取得すること、config get は実数値を返すこと。これらはすべて、修正前に v0.10.0 に対して赤で検証され、修正を元に戻すと再び赤で検証されました。

アップグレード

  • バイナリ インストール: 以下をダウンロードするか、install.sh / install.ps1 を再実行します — インストーラーを再実行すると * 更新されます。
  • npm / PyPI: 通常どおり、パッケージ マネージャーを通じて更新します。
  • インデックス、キャッシュ、構成の移行はありません。 v0.10.0 グラフは完全な互換性があります。
