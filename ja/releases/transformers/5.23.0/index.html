インクリング2

<img width="1200" height="675" alt="image" src="https://github.com/user-attachments/assets/9115e142-1be3-4f79-a51d-ea0e5c25b152" />

Inkling 2 Small は、Thinking Machines Lab のマルチモーダル モデルで、テキストと画像の入力を受け入れ、テキスト出力を生成します。英語やその他の言語、および複数のコーディング言語で使用することを目的としています。その言語バックボーンには 48 の専門家混合デコーダー層があり、各層が 384 人の専門家のうち 8 人にトークンをルーティングし、合計 594B と 17B のアクティブなパラメーターになります。 Inkling デコーダー (学習された相対アテンション、短い因果畳み込み、混合エキスパート層) を維持し、ブロック アテンション残差、学習されたシンクによるゲート アテンション、および動的なキー/値の畳み込みを追加します。画像は Perception Encoder ベースのビジョン トランスフォーマーによってエンコードされ、言語モデルの埋め込み (40x40 ピクセル パッチごとに 1 つの埋め込み) に投影されます。

ジェブ

JEV は、言語モデル ヘッドのロジットのようにソフト キャップされた、プロンプトの最後のトークンで線形層を使用して単一トークン ラベルをスコアリングするディシジョン ヘッドです。 JevForDecision はチェックポイントとそのヘッドのモデルであり、ウェイトの次に出荷されるヘッド ファイル (JEV の場合は head.safetensors および judge_config.json) を読み取ります。同じヘッドは GEV によっても使用され、pplx-decider と d3 の 255 応答コードを読み取り、実験的な decision パイプラインを通じて、または decide で直接実行できます。

注意: JEV と意思決定パイプラインは現在実験段階です。開発が進むにつれて、API、構成、および動作が変更される可能性があります。運用環境では注意して使用する必要があります。

LFM3

<img width="732" height="815" alt="image" src="https://github.com/user-attachments/assets/5a67fe26-2cee-4bbf-bc51-65e8f843b756" />

LFM3 は、Liquid AI の第 3 世代の Liquid Foundation モデルです。 LFM2 と同様、ゲートされたショート コンボリューションとグループ化されたクエリ アテンションを組み合わせたハイブリッド アーキテクチャであり、アテンション レイヤーはフル アテンション レイヤーとスライディング ウィンドウ レイヤーに分割されます。アテンション レイヤーは RMSNorm をクエリとキー ヘッドに適用し、ヘッドごとのシグモイドで出力をゲートします。すべての層は、残差加算の前に演算子とフィードフォワード出力にサンドイッチ ノルムを適用します。

Dots 3 ノートのプレビュー

Dots 3 Note Preview は、専門家が混合した因果言語モデルで、ネイティブ テキスト、画像、ビデオ、オーディオ入力を受け入れます。画像とビデオには共有ビジョン エンコーダと、Whisper スタイルのオーディオ エンコーダが使用され、両方のエンコーダは自己回帰テキスト生成の前に出力を言語モデルの隠れた空間に投影します。 BF16 および FP8 推論がサポートされています。

LFM3-VL

LFM3-VL は、LFM3 言語モデルに基づいて構築された、Liquid AI のビジョン言語モデル ファミリです。画像やビデオをネイティブ解像度でテキストと一緒に撮影します。これは、ハイブリッド ビジョン エンコーダー (線形パッチファイア、ゲート深度方向の 2D 畳み込みレイヤー、2D 回転埋め込みを備えた双方向グループ化クエリ アテンション レイヤー) をプロジェクターおよび LFM3 言語モデルと組み合わせます。プロジェクターは、レイヤー ノルムと 2 レイヤー MLP を通じて、パッチ機能の各 2x2 ブロックを 1 つの言語トークンにマージします。

IQuestCoder

IQuest-Coder-V1 は、IQuest Lab によって開発されたコード言語モデルのファミリーであり、ベース、命令、および思考のバリアントを備えた 7B、14B、および 40B サイズで利用できます。そのアーキテクチャは Llama と同じであるため、Transformers の自動クラスは LlamaModel および LlamaForCausalLM を使用して Llama をロードし、IQuestCoderConfig のみが IQuestCoder に固有です。ループされた IQuest-Coder-V1-*-Loop-* チェックポイントは異なるアーキテクチャを使用しているため、サポートされていません。

インターンLM3

InternLM3 は、上海 AI 研究所によって開発された 8B 命令チューニング言語モデル (チェックポイント: internlm/internlm3-8b-instruct) です。そのアーキテクチャは Llama と同じであるため、自動クラスは Llama 実装 (LlamaModel および LlamaForCausalLM) を使用して Llama をロードし、InternLM3Config のみが InternLM3 に固有です。この設定では、注意バイアスに qkv_bias 、出力投影と MLP バイアスに bias という名前が付けられています。 InternLM3Config は、これらを attention_bias および mlp_bias としてロードし、解放されたチェックポイントにあるため、それらが等しいことを要求します。

エクスポーター: バックエンドでモデルをエクスポート、共有、実行します (#50029、#50032、#50309、#50311)

https://github.com/user-attachments/assets/2b17b2ab-b2b8-4e34-a983-4a7177330e4e

すべてのエクスポートで ExportedModel が返されるようになりました。これを元のモデルと同じように呼び出し (同じ kwargs、同じ出力クラス)、ハブにプッシュして、バックエンド独自のランタイムにロードし直します。同じ API は、Dynamo、ONNX ランタイム、OpenVINO、および ExecuTorch をカバーします。

from transformers import AutoModel, AutoTokenizer
from transformers.exporters import ExportedModel, OnnxConfig, OnnxExporter

model = AutoModel.from_pretrained("google/embeddinggemma-2")
tokenizer = AutoTokenizer.from_pretrained("google/embeddinggemma-2")
inputs = tokenizer(["Exporters are here!"], return_tensors="pt")

exported = OnnxExporter().export(model, inputs, OnnxConfig(dynamic=True, ort_fusions="cuda"))
exported.push_to_hub("my-org/embeddinggemma-2-onnx")

exported_model = ExportedModel.from_pretrained("my-org/embeddinggemma-2-onnx", device="cuda")
outputs = exported_model(**inputs)  # same output class as model(**inputs)
  • ランタイム用に融合: OnnxConfig(ort_fusions="cpu" | "cuda" | "webgpu" | "dml") は、エクスポート時にグラフを ONNX ランタイムの融合トランス演算に書き換えます: アテンション、KV キャッシュ上の GroupQueryAttention、ロータリー、ノルム、および MoE。 OpenVINO エクスポートは、アテンション、RoPE、MoE エキスパート、圧縮 int8/int4 重み付けのために OpenVINO の融合 CPU カーネルにヒットするようになり、2.4 ～ 3.9× のデコードが以前より高速になりました。
  • torch.compile より高速: EmbeddingGemma2 (8 × 128 トークン) では、TensorRT EP を使用した ONNX ランタイムは、A100 上で 7.6 倍高速 PyTorch より高速であり、1.4 倍高速 torch.compile よりも高速です。 OpenVINO は、Xeon Platinum 8570 上で、Eager よりも 4.1× 高速であり、torch.compile よりも 2.2× 高速です (int8 重みを使用した場合、4.9× および 2.6×)。
  • 共有可能: エクスポートはモデルと同様に保存およびロードされます。オプションでモデル リポジトリの subfolder に保存されます。その export.json は、構成、入力形状、パッケージのバージョン、および I/O 名を記録します。量子化エクスポート (PT2E、NNCF、ONNX ランタイム) は、同じ方法で保存および実行されます。

🚨 export() は ExportedModel を返し、ONNX プログラムは onnx_ir.Model です。 OnnxConfig および OpenVINOConfig の output_path オプションは廃止され、save_pretrained が採用されました。カスタム バックエンドは register_backend に登録されます。

📚 ドキュメント: https://huggingface.co/docs/transformers/main/en/exporters
