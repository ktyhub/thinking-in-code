netdata v2.12.2

#ネットデータv2.12.2

Netdata v2.12.2 は、v2.12.1 以降に発見された問題に対処するパッチ リリースです。

このリリースでは、SNMP トラップ レシーバーでの SNMPv3 認証が強化され、古いチャートが無期限に存続することによるアラート評価が停止され、クラウドが切断された子をオフラインとして確実に認識し、すべてのアラート遷移を受信できるようになり、エージェントがクラウドに再接続したときに意図したバックオフが復元され、関数および動的構成リクエストで厳密な JSON を実行する必要があり、単一の不正な出力行の後に外部プラグインが実行され続け、Kubernetes ステート チャートとそのアラートが常に維持されます。同様の名前のオブジェクトが削除されると消えてしまうほか、長距離クエリで古い層のギャップの後に新しい層からデータが返されるようになり、Raspberry Pi 3 などの Cortex-A53 ボードで起動時にクラッシュする可能性がある静的な 64 ビット ARM ビルドが修正されました。

ストリーミングとネットデータのクラウド

  • 親から切断された子が Netdata Cloud 内でライブ状態を維持できるという競合を修正しました。ノード状態の更新は、子がオフラインとしてマークされる前にスケジュールされていたため、CPU 競合が発生すると、オフライン状態が送信されないことがありました (#24285、@stelfrag)
  • 親は、切断された子の予想再起動時間 (上限は 30 秒) の 125% 待機してから、オフラインであることを Netdata Cloud に報告します。整数演算によりマージンが 100% に減少しました。再起動時間が記録されていない子は、遅延ゼロ タイマーをスケジュールしなくなりました。これにより、古い libuv バージョンで CPU 使用率が高くなる可能性があります (#24343、@stelfrag)
  • Netdata Cloud への途中でアラートの遷移が失われる問題を修正しました。 MQTT 層が拒否したメッセージ (たとえば、オフライン時やバッファーがいっぱいのとき) は、配信されたものとして扱われ、キューから削除されました。現在は再試行されています。アラート スナップショットは、送信したよりも多くのチャンクを通知する可能性もあり、単一の一貫したクエリから構築され、再構築が成功した後にのみ送信されるようになりました (#24224、@stelfrag)
  • Netdata クラウドへの再接続バックオフを修正しました。バックオフが上限に達すると、クランプは数秒で戻されましたが、ミリ秒単位でスリープしていたため、切断されたエージェントは、意図した最大値 (現在 20 分) まで待機するのではなく、1 秒に 1 回程度再試行しました (#24340、@stelfrag)
  • パケット ID カウンターがラップアラウンドしたときにクラウド接続が MQTT パケット ID 1 を 2 回配布する問題を修正しました。同じ ID を持つ送信中の 2 つのメッセージは確認応答とタイムアウト追跡を失います (#24341、@stelfrag)
  • エージェントの Netdata クラウドへの HTTP 応答の t-rx タイムスタンプが、リクエストが受信された時刻ではなく、v2.0.0 以降 0 として送信されていた問題を修正しました (#24252、@stelfrag)

健康

  • 古いチャートを存続させるアラート評価を修正しました。評価パスごとにチャートの最終アクセス時刻が更新されるため、アラートが添付された古いチャートはクリーンアップできるほど古くなることはありませんでした。ポッド チャーンのある Kubernetes ノードでは、これにより k8s.cgroup チャートの数が増加し続け、それに伴い親のメタデータも増加しました (#24273、@stelfrag)
  • ヘルス永続性に関するいくつかのバグを修正しました。ACLK 設定のないホスト上のすべてのアラート遷移でプリペアド ステートメントがリークし、64 ビット イベント ID が 32 ビット値としてバインドされ、詳細行がない場合、次のアラーム イベント ID がアラーム ID ではなく 0 に戻りました (#24223、@stelfrag)

データベース

  • 停止する可能性があるメタデータ クリーンアップ パスを修正しました。スナップショットの最初の行が読み取られる前に削除され、中断されたコンテキストのクリーンアップによってコンテキストがキューから削除され、残りのディメンションがチェックされないままになっている場合、ディメンション、チャート、またはラベルのクリーンアップ パスは完了しませんでした。失敗したグラフ ラベル ストアが再試行されるようになり、クリーンアップ中に WAL サイズがチェックされる頻度が大幅に減りました (#24227、@stelfrag)
  • 削除コールバックが参照項目をまだ含むネストされた辞書を破壊する辞書を解放するときのデッドロックを修正しました。削除されたホストのチャートがそのディメンションの 1 つがまだ参照されている間に解放された場合、層バックフィルがそれに到達する可能性がありました (#24344、@stelfrag)
  • dbengine: 長さがバッファ サイズの倍数ではない破損したゴリラ圧縮ページは、割り当ての終わりを超えて読み取られるのではなく、拒否されるようになりました (#24310、@ArjunD3456)
  • 完全な追加ティア期間中、上位ティアの完了ポイントがクエリに表示されない問題を修正しました。それらは、コレクションが層境界に正確に到達した場合にのみ公開され、低速またはオフセットコレクターは毎回それを見逃す可能性があります。期限を過ぎたポイントは、次に収集されたサンプル (#24405、@ktsaou) で公開されるようになりました。
  • dbengine: 1 秒のギャップは、より長いギャップと同様にキャッシュされるようになりました。そのため、それらに対する繰り返しのクエリによってジャーナルが再度検索されることはなくなり、キャッシュされたギャップは、それに続くページの最初のポイントと重なりなくなりました (#24370、@ktsaou)

クエリ

  • /api/v1/context および /api/v1/contexts の dimensions= フィルターを修正しました。これは、名前がその ID と等しいすべてのメトリック (ほとんど) を無視し、すべてのディメンション、インスタンス、およびコンテキストを返しました (#24245、@stelfrag)
  • 何も一致しなかった重み API (メトリック相関、異常率) の instance@node_id パターンを修正しました (#24245、@stelfrag)
  • 裸のラベル名と name=value 用語を組み合わせるラベル フィルターを修正しました。これにより、負の name=value 用語が優先されながら、一致するチャートが保持されます (#24202、@stelfrag)
  • /api/v1/info がロックなしで分析文字列 (ビルド情報、リリース チャネル、通知メソッド、エクスポート コネクタ) を読み取る問題を修正しました。そのため、分析の更新と重複するリクエストで解放されたメモリを読み取ることができました (#24342、@stelfrag)
  • 新しい層への切り替えが予定されているかなり前に、古い層でデータが不足した場合に、残りの時間範囲で空の行を返すクエリを修正しました。クエリは新しい層に継続され、SES/DES は層の切り替えが失敗したクエリの末尾まで古い値を拡張しなくなりました (#24406、@ktsaou)

関数

  • 機能および動的構成リクエストは、厳密な JSON リクエスト本文 (RFC 8259) のみを受け入れるようになりました。 YAML、フォーム データ、プレーン テキストなどのその他の本文は、HTTP 400 で拒否されます。ダッシュボード、Netdata クラウド、およびエージェント自身の呼び出し元は、すでに JSON を送信しています。厳密ではない JSON を保存した動的構成は再適用に失敗し、ログに警告が記録されます。本体はプラグインとストリーミングの子に渡される場所で再度チェックされるため、親とその子を更新します (#24409、@ktsaou)
  • go.d.plugin: 関数リクエストの本文が、終了マーカーまでのデータとして扱われるようになりました。プラグイン コマンドのように見える本文内の行は、実行中の関数呼び出しを置き換えたり、別の関数呼び出しをキャンセルしたり、プラグインによるさらなるリクエストの読み取りを停止したりする可能性があります。不正な形式またはサイズが大きすぎるリクエストは、本体がコマンドとして解析されることなく、全体としてスキップされるようになりました (#24410、@ilyam8)

コレクター

  • 外部プラグイン: プラグイン出力の 1 行の破損などのプロトコル エラーにより、エージェントが再起動されるまでプラグインが永続的に無効になりました。プロトコル エラーは、エラー終了と同じポリシーに従います。プラグインは 10 × update_every 秒後に再起動され、有用な出力が生成されなかった場合、または 10 回を超えて連続して実行に失敗した場合にのみ無効になります (#24051、@ilyam8)
  • SNMP トラップ: SNMPv3 メッセージが、認証を要求するように構成されたユーザーの認証をスキップする場合、または非 USM セキュリティ モデルを宣言する場合、SNMPv3 メッセージは拒否され、usm_failures としてカウントされるようになりました。拒否されたメッセージは確認されず、エンジン ID も登録されません (#24188、@ilyam8)
  • SNMP: コミュニティ文字列と SNMPv3 パスフレーズは、デバッグ ログに書き込まれる接続の詳細に含まれなくなりました (#24217、@ilyam8)
  • ディスク統計: /proc/diskstats の破棄およびフラッシュ フィールドの検出が修正されました。 4.18 より前のカーネルは 6 つの disk_ext.* ゼロ チャートを取得し、4.18 から 5.4 までのカーネルは flushes 次元がゼロで固定されました。フィールドはディスクごとに検出されるようになり、ディスクがレポートを開始すると flushes ディメンションが追加されます (#24243、@stelfrag)
  • proc.plugin: Ubuntu 24.04 HWE (6.14) など、一部の /proc ファイルがシークできないカーネルでのオーバーヘッドが削減されました。このようなファイルを巻き戻すと、読み取りのたびにその名前が再度解決されなくなり、proc.plugin のビジー時間を約 9% 削減します (#24212、@stelfrag)
  • Kubernetes 状態: ノード、ポッド、デプロイメント、または cron ジョブを削除しても、web-1 が削除されたときのポッド web-10 から web-19 など、名前が同じ名前で始まるライブ オブジェクトのチャートが削除されなくなりました。これらのチャートは、オブジェクトが再作成されるかエージェントが再起動されるまで戻らず、k8s_state_deployment_condition_available などのアラートは静かに停止されました。ポッドをスケジュールしても、そのようなチャートのノード ラベルが書き換えられなくなりました (#24402、@stelfrag)
  • log2journal: パーサーの最大深さよりも深くネストされた配列を含む JSON 入力は、キー スタックをオーバーランさせるのではなく、エラーで拒否されるようになりました (#24290、@ArjunD3456)

インストールとパッケージ化

  • 64 ビット ARM の静的ビルドでは、Rust プラグインを含む Cortex-A53 errata 835769 および 843419 のリンカー回避策が有効になりました。コード レイアウトによっては、Raspberry Pi 3 や ODROID-C2 などの Cortex-A53 ボードでの起動時に静的ビルドが SIGILL で停止する可能性があります。 CI は、aarch64 静的アーカイブで未修正の命令シーケンスをスキャンするようになり、Rust 関数は 8 バイトにアライメントされるため、リンカーのエラッタム スタブは影響を受けるシーケンス (#24207、@stelfrag、#24387、 @vkalintiris)
  • Windows パッケージは、ソースからパッチ適用された 3.6.10 ランタイムを構築するのではなく、MSYS2 独自の msys2-runtime 3.6.11 パッケージの msys-2.0.dll をバンドルするようになり、URL とチェックサムによって固定されます。 3.6.11 には、v2.12.1 で対処された起動時のクラッシュに対するアップストリームの修正が含まれており、ソース ビルドは MSYS2 の現在のツールチェーン (#24390、@stelfrag) でコンパイルされなくなりました。
  • ベンダー提供の IBM MQ client ライブラリーを 9.4.5.1 (#24294、@Ferroin) に更新しました。

  • @ArjunD3456 log2journal JSON パーサーの配列のネストの深さを制限するため、および dbengine で破損したゴリラ ページを拒否するため。

サポート オプション <a id="v2122-support-options"></a>

当社は成長するにつれて、オープンソース ソリューションを通じてこれまでにない最高のサポートを提供することに尽力し続けます。このリリースで行われた変更または Netdata Agent の機能で問題が発生した場合は、次のいずれかのチャネルを通じてお気軽にお問い合わせください。

  • Netdata Learn: Netdata を使用してシステムを監視およびトラブルシューティングするためのドキュメント、ガイド、参考資料を検索します。
  • GitHub の問題: Netdata リポジトリを利用して、バグを報告したり、新しい機能のリクエストをオープンしたりします。
  • GitHub ディスカッション: Netdata 開発プロセスに関する会話に参加して、参加してください。
  • コミュニティ フォーラム: コミュニティ フォーラムにアクセスして、共同知識ベースに貢献してください。
  • Discord サーバー: Netdata Discord に参加して、同じ考えを持つシステム管理者、DevOps、SRE、その他のトラブルシューティング担当者と交流しましょう。すでに 2,000 人以上のエンジニアが使用しています。
