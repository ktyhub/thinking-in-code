#ディファイ1.13.0

🚀 新機能

人間参加型 (HITL)

AI と人間の関係を変革するメジャー アップデートである Human Input ノードを導入します。 Dify ワークフロー内で共同作業します。

背景

以前は、ワークフローは完全自動化または完全手動の 2 つでした。これにより、「trust ギャップ」が生じました。 AI のスピードは必要だが、人間の判断が不可欠である一か八かのシナリオ。 HITL を使用して、h を作成します。 uman はワークフロー アーキテクチャのネイティブ部分を監視し、埋め込みを可能にします。 実行グラフのステップを直接確認します。

主な機能

  • ネイティブ ワークフローの一時停止: 「ヒューマン入力」ノードを挿入して、重要な決定点でワークフローの実行を一時停止します。
  • レビューと編集: このノードは、プロセスを続行する前に人間が AI 出力をレビューし、変数を変更 (ドラフトの編集やデータの修正など) できる UI を生成します。
  • アクションベースのルーティング: 決定するカスタム ボタン (「承認」、「拒否」、「エスカレーション」など) を構成します。 ワークフローの後続のパス。
  • 柔軟な配信方法: 人間による入力フォームは、Web アプリ または 電子メール を介して配信できます。クラウド環境では、電子メール配信の可用性はプラン/機能の設定によって異なる場合があります。

🛠 アーキテクチャの更新

HITL に必要なステートフルな一時停止/再開メカニズムをサポートし、イベント サブスクリプション API を提供するために、実行エンジンをリファクタリングしました。 ワークフロー ベースのストリーミング実行と高度なチャットの実行は Celery ワーカーで実行されるようになりました。一方、非ストリーミングの WORKFLOW 実行は引き続き API プロセスで実行されます。 すべての一時停止/再開パス (HITL など) は Celery 経由で再開され、イベントは Redis Pub/Sub 経由でストリーミング バックされます。

大規模な導入およびセルフホスト ユーザーの場合:

workflow_based_app_execution という名前の新しい Celery キューを導入しました。標準セットアップはそのままで動作しますが、高スループット環境では、安定性とパフォーマンスを確保するために次の最適化を考慮する必要があります。

  1. ワーカーのスケール: 特定のワークロードに基づいて、workflow_based_app_execution キューを消費するワーカーの数を調整します。
  2. 専用 Redis (オプション): 大規模な展開の場合は、専用の Redis インスタンスを指すように新しい PUBSUB_REDIS_URL 環境変数を構成することをお勧めします。水平方向のスケーラビリティを確保するには、Redis クラスター モードとシャード PubSub を使用することを強くお勧めします。

⚠️ アップグレードに関する重要な注意事項

新しいセロリ キューが必要です: workflow_based_app_execution

デプロイメント構成 (Docker Compose、Helm Chart など) に、新しい workflow_based_app_execution キューをリッスンするワーカーが含まれていることを確認してください。
このキューは、ワークフローベースのストリーミング実行とすべての再開フロー (HITL など) に必要です。そうしないと、ストリーミング実行とタスクの再開は処理されません。

🔧 操作上の注意

追加のセロリキュー: api_token

ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK=true の場合は、デプロイメントに api_token をリッスンするワーカーがあることを確認してください。 このキューは、API トークン last_used_at タイムスタンプのスケジュールされたバッチ更新タスクによって使用されます。

⚙️ 構成の変更

アーキテクチャの変更をサポートするために、いくつかの新しい環境変数を導入しました。 大規模な展開では、スケーラビリティを確保するために PubSub Redis 構成に特別な注意を払う必要があります。

  • PUBSUB_REDIS_URL (重要): API ワーカーと Celery ワーカー間の PubSub 通信に使用される Redis URL を指定します。空のままにすると、デフォルトの標準 REDIS_* 構成になります。
  • PUBSUB_REDIS_CHANNEL_TYPE (重要): ストリーミング イベントのチャネル タイプを定義します。オプションは pubsub (デフォルト) または sharded です。 高スループット環境には sharded を使用することを強くお勧めします。
  • PUBSUB_REDIS_USE_CLUSTERS (重要): PubSub の Redis クラスター モードを有効にするには、true に設定します。シャードされた PubSub と組み合わせると、これは水平方向のスケーリングに不可欠です。

その他の追加事項:

  • WEB_FORM_SUBMIT_RATE_LIMIT_MAX_ATTEMPTS: レート制限ウィンドウ内で IP ごとに許可される Web フォーム送信の最大数 (デフォルト: 30)。
  • WEB_FORM_SUBMIT_RATE_LIMIT_WINDOW_SECONDS: Web フォーム送信レート制限の時間枠 (秒単位) (デフォルト: 60)。
  • HUMAN_INPUT_GLOBAL_TIMEOUT_SECONDS: グローバル タイムアウトになるまでに、ワークフロー実行が人間の入力を待機して一時停止状態を維持できる最大秒数 (デフォルト: 604800、7 日)。
  • ENABLE_HUMAN_INPUT_TIMEOUT_TASK: 期限切れの人為入力リクエストをチェックするバックグラウンド タスクを有効にします (デフォルト: true)。
  • HUMAN_INPUT_TIMEOUT_TASK_INTERVAL: タイムアウトチェックタスクの間隔 (分単位) を設定します (デフォルト: 1)。
  • ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK: API トークン last_used_at タイムスタンプをバッチ更新する定期的なバックグラウンド タスクを有効にします (デフォルト: true)。
  • API_TOKEN_LAST_USED_UPDATE_INTERVAL: API トークン last_used_at タイムスタンプをバッチ更新する間隔 (分単位) を設定します (デフォルト: 30)。
  • SANDBOX_EXPIRED_RECORDS_CLEAN_BATCH_MAX_INTERVAL: DB 圧力スパイクを軽減するための保持クリーンアップ バッチ間の最大ランダム遅延 (ミリ秒単位) (デフォルト: 200)。

📌 Changelog のその他のハイライト

信頼性と正確性

  • デフォルト モデル レコードの重複を防ぐために、移行時の重複排除とテナントのデフォルト モデルの一意の制約を追加しました。
  • プロバイダー ID タイプの不一致によって引き起こされるツール削除のエッジ ケースを修正しました。
  • 認証されたユーザーがリモート ファイル API で匿名として解決される可能性がある FastOpenAPI 統合リグレッションを修正しました。
  • ファイル関連の応答に対するメッセージ イベント タイプの検出を修正し、マネージャー以外のユーザーに対するワークスペースの招待アクションを非表示にしました。

パフォーマンスとスケーラビリティ

  • プラグイン マニフェストの事前キャッシュと AppListApi クエリの最適化により、バックエンドの負荷とコンソールの遅延が削減されました。
  • 分割 DB セッション、バッチ化されたクリーンアップ実行、インデックス調整、保持クリーンアップ ジョブの構成可能なバッチ間スロットリングにより、大規模データ タスクの安定性が向上しました。

API とプラットフォームの機能

  • テナント/アプリ スコープを適用したエンドユーザー検索用のサービス API エンドポイントを追加しました。
  • 実行状態遷移中のワークフロー実行履歴の更新動作が改善されました。
  • MCP 応答から使用状況メタデータ (トークン/コスト フィールドなど) を抽出してレポートすることにより、MCP ツールの統合が強化されました。

セキュリティ

  • ECharts 解析から動的 new Function 評価を削除し、サポートされていないチャート コードに対して明示的な解析エラーを返すようになりました。

ローカリゼーション

  • バックエンド言語マッピングおよび Web ローカリゼーション リソース全体にオランダ語 (nl-NL) 言語のサポートを追加しました。

ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK=true の場合は、api_token も含めてください。

Docker デプロイメントの構成

  1. カスタマイズした docker-compose YAML ファイルをバックアップします (オプション)

    cd docker
cp docker-compose.yaml docker-compose.yaml.$(date +%s).bak

  2. メインブランチから最新のコードを取得します。

    git checkout main
git pull origin main

  3. サービスを停止します。 dockerディレクトリ内で実行してください。

    docker compose down

  4. データのバックアップ

    tar -cvf volumes-$(date +%s).tgz volumes

  5. アップグレードサービス

    docker compose up -d

ソースコードのデプロイメント

  1. API サーバー、ワーカー、および Web フロントエンド サーバーを停止します。

  2. リリース ブランチから最新のコードを取得します。

    git checkout 1.13.0

  3. Python の依存関係を更新します。

    cd api
uv sync

  4. 次に、移行スクリプトを実行しましょう。

    uv run flask db upgrade

  5. 最後に、API サーバー、ワーカー、および Web フロントエンド サーバーを再度実行します。
