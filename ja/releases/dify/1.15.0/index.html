新機能

difyctl — コマンド ラインから Dify を実行する (ドキュメント)

  • difyctl は Dify のコマンドライン client です。端末からアプリやワークフローを直接実行できるようになり、パーソナル エージェント、スクリプト、CI パイプラインは Web UI を開かずに Dify ワークフローを呼び出すことができます (#37036)
  • アクセス トークンなしで 1 つのコマンドで任意のプラットフォーム (macOS、Linux、Windows) にインストールします。バイナリはチェックサム検証付きのパブリック リリースとして公開されます (#37036、#37454)
  • スコープ指定された環境変数を CLI ツール実行に渡し、difyctl と /openapi/v1 API の両方で、より明確で一貫したエラー メッセージ (わかりやすいレート制限処理を含む) を取得します (#37324、#37285、#37313、#36896)

ワークフロー、チャットフロー、CLI の CoT を参照

  • チャット フロー/ワークフローは、最終的な回答をクリーンで読みやすい状態に保ちながら、モデルの推論を専用のライブ「思考」パネルにストリーミングできるようになりました。推論は保存されるため、ページを更新した後も存在し、同じ推論が CLI およびワークフロー実行プレビューに表示されます (#37460、#37828)

より充実した人間参加型フォーム

  • ワークフローが一時停止して人に入力を求める場合、フリーテキストだけでなく、ドロップダウン選択やファイル/複数ファイルのアップロードをフォームに含めることができるようになり、ユーザーは構造化された選択肢と添付ファイルで回答できるようになりました (#36322)

低速で長時間実行されるモデルのサポート

  • ワークフローは、ポーリング メカニズムを介して、応答に時間がかかる生成モデル (画像やビデオの生成など) を使用できるようになりました。ノードはタイムアウトするのではなく、最終結果を辛抱強く待ちます (#37462)

豊富なスプレッドシートから得られる知識

  • Excel ファイル内に埋め込まれた画像がナレッジのインポート中に抽出されるようになったため、画像 (図、スクリーンショット、チャート) に依存するスプレッドシートのコンテンツが失われることがなくなりました (#37104)

より深い可観測性

  • Phoenix に独自のトレース セッション ID を設定して、トレースがアプリケーションのセッションと一致するようにし、トレース内のドキュメント取得手順に従って、RAG 結果がどのように生成されたかを理解します (#37056、#37283)

ワークフロー オーサリングの洗練

  • 更新された開始ノードにより、ワークフローの開始方法がより明確になり、よりスマートな出力ノードにより、ワークフローが返す内容をより詳細に制御できるようになります (#37348、#35511)
  • アプリまたはワークスペース ID の形式が不正な場合、混乱を招くエラーではなく、より分かりやすいエラー (#37212)

特定の地域でのプラグインのインストールが高速化

  • プラグイン デーモンは起動時にリージョンを自動検出し、PyPI へのネットワーク接続が不十分な場合は近くのパッケージ ミラーを自動的に選択するようになりました。そのため、プラグインのインストールは手動セットアップなしでより速く、より信頼性が高くなります。必要に応じて、特定のミラーを固定することもできます (dify-plugin-daemon#750)

セキュリティアップデート

このリリースでは、プラグイン デーモン転送におけるパス トラバーサルの問題 (cve-2026-41948) が修正されています。

バグ修正

  • Firecrawl、Jina、Watercrawl、Nacos、および Marketplace リクエストの制限付きタイムアウトによる強化されたアウトバウンド HTTP、および強化されたデフォルト SSRF プロキシ出力 (#37638、#37637、#37515、#37444、#37424、#36332)
  • opensearch-py アップデート (#37862) および Tongyi 資格情報の互換性 (#37942) によって引き起こされる Lindorm ベクター ストア エラーを修正しました
  • OAuth 更新後に認証情報キャッシュが無効になる (#37630)
  • ワークフロー実行エラー処理を改善し、ハングを防ぐために会話を熱心に検証し、従来の停止による GraphEngine の実行の中断を防止しました (#37919、#37224、#37129)
  • セッション管理リファクタリング (#37847) および安定化されたデプロイメント状態のハイドレーション (#37818) によって DetachedInstanceError を解決しました。
  • varchar(255) の切り捨てを防ぐために会話変数の説明の長さの検証を修正し (#33038)、検索が機能するように中国語を Unicode として保存しました (#37446)
  • 多数の Web UI とアクセシビリティ/フォーカスリングの洗練された修正

改善点

  • サービス間のセッション管理をリファクタリングし、一貫性を保つために依存関係注入を介して db.session を明示的に受け入れるようにしました (#37639、#37832、#37695、#37694、および関連)
  • 最新のタイピング (冗長な type: ignore/cast を削除、ABC を Protocol に変換、isinstance チェーンを match-case に置き換え)
  • Chatflow のワークフロー開始レイテンシーが短縮され (#36773)、ワークフロー終了レイテンシーが短縮されたため、実行の停止がより速く反映されます (#37106、#37129)
  • CVE 修正のためのアップグレードされた依存関係 (Bleach、PyJWT、starlette、ストレージ グループ) (#37860、#37008、#37076、#37861)

データベースの移行

このリリースには、新しいデータベースの移行が含まれています。コードを更新した後、flask db upgrade (または uv run --project api flask db upgrade) を実行します。注目すべきスキーマの追加:

  • OAuth アクセス トークン (ENABLE_OAUTH_BEARER)
  • 認証情報の可視性
  • ヒューマン入力アップロードテーブルと会話連携
  • カテゴリスコープのプラグイン自動アップグレード戦略 (add_plugin_auto_upgrade_category)
  • アプリのスター、推奨アプリの learn-dify / クラウド専用フラグ
  • 正規化されたレガシーエンドユーザータイプ

アップグレード ガイド

モデルタイプの移行

[!重要]

セルフホスト型アップグレードのための 1 回限りのレガシー モデル タイプの移行

この展開が 1.15.0 より前の Dify バージョンからアップグレードされており、この移行がまだ適用されていない場合は、アップグレード後に実行します。

この移行は flask db upgrade には含まれていません。これがないと、レガシー モデル レコードにより、モデル関連の API リクエストがエラーで失敗し、影響を受けるモデルのロードまたは使用ができなくなる可能性があります。

移行を適用する前にデータベースをバックアップします。コマンドはデフォルトでドライラン モードで実行されます。 --apply を再実行する前に、出力を確認してください。移行は冪等であるため、安全に再実行できます。

Docker 作成する

docker ディレクトリから実行します。

# Apply after reviewing the dry-run output
docker compose exec -T api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

ソースコードのデプロイメント

flask db upgrade の完了後、リポジトリのルートから実行します。

# Apply after reviewing the dry-run output
uv run --project api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

移行を適用した後、ドライラン コマンドを再度実行します。追加の行の更新または削除が報告されない場合は、関連するサービスを再起動し、既存のモデルを正常にロードして呼び出せることを確認します。

[!重要]

  • このリリースには、新しいデータベースの移行が含まれています。アップグレードの一部としてそれらを実行します。
  • プラグインの自動アップグレードがプラグイン カテゴリごとに設定されるようになりました。 flask db upgrade を実行した後、flask backfill-plugin-auto-upgrade も実行して、既存のテナントの自動アップグレード設定を新しいカテゴリ スコープのモデルに移行する必要があります。この手順をスキップすると、ユーザーが以前に構成したプラグインの自動アップグレード設定が有効にならなくなる可能性があります。
  • 環境変数が変更されました (19 個追加、2 個削除、1 個変更)。 「環境変数の変更」セクションを確認し、それに応じて .env を更新します。
  • Docker Compose 設定ファイルが変更されました。カスタマイズされた docker-compose.yaml を維持する場合は、変更を確認し、ローカルのカスタマイズを慎重に再適用してください。

Docker デプロイメントの構成

  1. カスタマイズした docker-compose YAML および env ファイルをバックアップします。 
    cd dockercp docker-compose.yaml docker-compose.yaml.$(date +%s).bakcp .env .env.$(date +%s).bak 2>/dev/null || true
  2. 1.15.0 リリースの最新コードを取得します。 
    git fetch --tagsgit checkout 1.15.0
  3. サービスを停止します (docker ディレクトリ内で実行)。 
    docker compose down
  4. データをバックアップします。 
    tar -cvf volumes-$(date +%s).tgz volumes
  5. env ファイルの変更を確認し、ローカルのカスタマイズを再適用します。
  6. サービスをアップグレードします。 
    docker compose up -d
  7. カテゴリを対象としたプラグインの自動アップグレード戦略をバックフィルします (必須)。 
    docker compose exec api flask backfill-plugin-auto-upgrade

ソースコードのデプロイメント

  1. API サーバー、ワーカー、および Web フロントエンド サーバーを停止します。
  2. 1.15.0 リリースの最新コードを取得します。 
    git fetch --tagsgit checkout 1.15.0
  3. Python の依存関係を更新します。 
    cd apiuv sync
  4. データベースの移行を実行します。 
    uv run flask db upgrade
  5. カテゴリを対象としたプラグインの自動アップグレード戦略をバックフィルします (必須)。 
    uv run flask backfill-plugin-auto-upgrade
  6. API サーバー、ワーカー、および Web フロントエンド サーバーを再起動します。
