LocalAI 4.8.0 が登場しました！

22 日間、386 件のプル リクエスト、3 つの新しいモダリティ。このリリースでは、LocalAI チームによって保守されている C++20 エンジンである vllm.cpp が導入されています。これは vLLM ポートとして始まり、現在では独自の機能セットを搭載しており、アルファ開発ビルドの vllm-cpp バックエンドとして出荷されています。その周辺: 新しいモダリティとしての 3D 生成、マルチファミリー audio.cpp エンジン、ハードウェアが実際に実行できるビルドをインストールするギャラリー エントリ、および運用インシデントによる分散モードでの深い信頼性の継承。

ハイライト:

  • 🚀 vllm.cpp (アルファ) - LocalAI チームによって保守されている C++20 エンジン。vLLM ポートとして開始され、vLLM を参照実装として維持します。推論時に Python、PyTorch、または ggml を使用しない V1 サービング アーキテクチャ (ページ化された KV キャッシュ、連続バッチ処理、プレフィックス キャッシュ、スケジューラー、サンプラー)。 Qwen3.6-27B NVFP4 の同時実行数 1、トークンごとに同一の出力で 1.045x vLLM で測定。セーフテンサーと GGUF をロードし、エンジン内で構造化出力を強制し、CPU、CUDA、Metal、Vulkan 上で実行します。 Apple Silicon ビルドには MLX GEMM プロバイダーが同梱されており、M4 で 1.5 倍から 2.2 倍と測定されます。アルファ開発ビルドとして出荷: 依存せずに試してみてください。
  • 🧊 3D 生成 - エンドツーエンドの新しいモダリティ: Generate3D RPC、FLAG_3D 機能、POST /v1/3d/generations、trellis2cpp image-to-3D バックエンド、ネイティブ GLB ビューアと印刷再メッシュを備えた UI ページ。
  • 🔊 audio.cpp - 多くのモデル ファミリにわたる 6 つのオーディオ エンドポイントにサービスを提供する 1 つのバックエンド プロセス。音声、文字起こし、VAD、日記化、ソース分離、音声生成など、GGUF 独自のメタデータから選択されます。
  • 🎛️ 1 つのモデル、多数のビルド - ギャラリー エントリで variants: を宣言でき、LocalAI はホストが実際に実行できる最大のビルドをインストールします。適切な量​​子化を見つけるためにギャラリーを探し回る必要はもうありません。
  • ⚡ はるかに軽量な Web UI - ネットワーク上の gzip、ハッシュされたアセットの不変キャッシュ、およびページ分割されたトレース エンドポイント: React バンドルは 3.48 分の 1 に小さくなり、トレース ポーリングは 21 MB から 7 KB に減少しました。
  • 📊 アクティビティ ページ - 積み重ねられた操作バーは 1 行に折りたたまれ、新しい管理アクティビティ ページには、インストール、失敗、またはキャンセルされた内容の記録が、完了した瞬間に削除されるのではなく保持されます。
  • 📦 Hugging Face アーティファクトの具体化 - 不変のスナップショット解像度、実際の進行状況を伴う認証されたダウンロード、およびリモート ワーカーがバインドできるステージングされたアーティファクト。
  • 🎚️ VRAM バジェット - LocalAI がノードごとに使用できるカードの量を、パーセント (80%) または絶対量 (12GB) として制限します。
  • 🗣️ 2 つの新しい TTS エンジン - magpie-tts-cpp (NVIDIA Magpie 多言語、5 音声、9 以上の言語) および moss-tts-cpp (リファレンス オーディオ音声クローン付き 48 kHz ステレオ)。

  • 🖧 分散モードの強化 - リーパーは、アクティブかつビジー状態のバックエンドの行を削除しなくなり、ファントム レプリカがクリーンアップされ、in_flight カウンターのリークが停止します。

🚀 新機能と主要な機能強化

🚀 vllm.cpp (アルファ版) の紹介

<p align="center"> <img src="https://raw.githubusercontent.com/mudler/vllm.cpp/master/benchmarks/media/concurrency_race.gif" alt="Qwen3.6-27B で並列して生成される vllm.cpp と vLLM" width="900"> <br><em>Qwen3.6-27B 上の vLLM に対する vllm.cpp、すべての同時実行で同一の出力。</em> </p>

vllm.cpp は Apache-2.0 であり、LocalAI チームによって保守されており、vLLM の C++20 ポートとして始まりました。 LocalAI 専用エンジンではなくコミュニティ第一であることを望んでいます。そのため、独自のドキュメント、ベンチマーク レコード、および問題トラッカーを備えた独自のリポジトリに存在し、LocalAI がなくても使用できます。これは、推論時に Python、PyTorch、ggml を使用しないポータブル テンソル ランタイム上に vLLM の V1 サービング アーキテクチャ (ページ化された KV キャッシュ、連続バッチ処理、プレフィックス キャッシュ、スケジューラー、サンプラー) を実装し、vLLM 自体をリファレンス実装として使用します。出力を比較することで正確性がチェックされ、ベンチマーク スコアボードがそれに対して保持されます。

それ以来、vLLM にはない機能セットが拡張されており、それがこのポートの目的でした。 GGUF と Hugging Face セーフテンサーをロードし、NVIDIA CUDA と並行して CPU、Apple Metal、Vulkan 上で実行し、投機的デコードと KV オフロードを搭載し、エンジン内で構造化出力を強制します (JSON スキーマ、正規表現、選択、GBNF)。そのベンチマーク ページでは、vLLM だけでなく、llama.cpp、MLX-LM、DwarfStar も測定しています。これらは、そのハードウェア上で実際に競合するエンジンだからです。

プロジェクトは名前変更される予定です。新しい名前はまだ決定されていません。これは vLLM から大きく乖離しているため、これをポートと呼ぶと過小評価され、vllm.cpp と呼ぶと最終的には誤解を招くことになります。

アップストリーム ページは、独自のノイズ バンドに注意しています。27B グリッドでは、ランツーラン スプレッドが 0.5% であり、それらのマージンが 0.7% と 1.7% の間に収まるため、27B グリッドでは勝ちではなく c2 から c32 までのタイを呼び出します。 c1の結果はそれを上回るものです。

DeepSeek-V4-Flash 行は、プロジェクトが vLLM ポートからどの程度離れているかを示します。 単一の DGX Spark 上で DeepSeek-V4-Flash を約 2 ビット (IQ2_XXS 混合、約 80 GB) で実行し、DwarfStar の 16.33 に対して 18.69 tok/s でデコードします。合計パラメータが 300B 以上になると、4 ビットのチェックポイントでも 156 GB 以上になるため、Spark の 119 GiB 統合プール内に収まるのは 2 ビットの GGUF であり、GGUF を読み取ることでそれが可能になります。 この数字は 1 週間に 2 回動き、2 回目の動きは 1 つのレバーによるものでした。高密度の Q8_0 プロジェクション タワーは、ユニファイド メモリを介して GGUF mmap から読み取られていました。GB10 の読み取りは、デバイス メモリよりも GEMV ごとに約 20% 遅くなります。最大 6 GiB のタワー デバイスをロード時に 1 回ステージングすると、同じバイト、同じカーネルで 16.23 から 18.69 へのデコードが行われ、同じトークンが生成され、ピーク メモリは使用されなくなりました。同じ変更により、Laguna-XS-2.1 は vLLM の 87% から 1.03 倍に先行しました。

投機的デコードも同様の形式です。Qwen3.6-27B NVFP4 上の MTP は、vLLM の MTP と同じトークンを生成し、同時実行数 1 で約 4% 高速に実行されます。

ここでは vllm-cpp バックエンドとして出荷され、purego を通じてエンジンの安定した C ABI (v5) を dlopen します。同時リクエストは、シリアル化ではなく、エンジンの共有スケジューラ内で連続的にバッチ処理されるため、バックエンドは SingleThread ではなく base.Base で実行されます。

チャットは同じオートパーサー パスを再利用するため、ツールの呼び出しは構造上、llama.cpp と同等です。 use_tokenizer_template を使用すると、エンジンはモデル独自のチャット テンプレート (GGUF tokenizer.chat_template または tokenizer_config.json、完全な minja) をレンダリングし、残りの部分をそれ自体で処理します。

  • tool_choice: auto は、遅延構造タグ デコード制約に引き下げられます。 required および名前付き選択肢は、表現可能な場合にはファミリーのネイティブ構文を強制します。
  • 方言ごとのストリーミング パーサーは、30 のツール方言と 7 つの推論パーサー をカバーし、ツール解析の前に <think> 推論が分割されます。
  • ChatDelta、ToolCallDelta および推論ストリームは、llama-cpp バックエンドとまったく同じように実行されます。

🎛️ 1 つのギャラリー エントリ、複数のビルド

<p align="center"> <img src="https://raw.githubusercontent.com/mudler/LocalAI/master/website/static/media/v4-8-0-ui-model-variants.png" alt="すべてのバリアントをリストするモデル詳細ペイン" width="900"> <br><em>1 つのエントリ、4 つのビルド。 LocalAI は、適合する最大のものを選択し、 自動選択としてマークします。</em> </p>

ギャラリー エントリは、同じウェイトの代替ビルドである他のギャラリー エントリへの参照のリストである variants: を宣言できるようになりました。

- name: nanbeige4.1-3b-q4      # still a normal, complete, installable entry
  url: github:mudler/LocalAI/gallery/nanbeige4.1.yaml@master
  overrides: {parameters: {model: nanbeige4.1-3b-q4_k_m.gguf}}
  files: [...]
  variants:
    - model: nanbeige4.1-3b-q8

インストール時に次の順序で選択します。

  1. バックエンドが実行できないバリアントをここに削除します。 Linux では MLX が消え、Mac では CUDA が消えます。バックエンド名に由来するため、作成者はハードウェア条件を記述することはありません。
  2. 適合しないものを削除します。GPU ホスト上の VRAM、CPU ホスト上の cgroup 対応システム RAM なので、コンテナーには独自の制限が適用されます。
  3. フットプリントが大きいほど、同じ重量でより優れたビルドであるということに基づいて、残っている最大のものを選択します。

エントリ自体のビルドはそのランキングで競合し、除外されることはありません。そのため、選択は常にインストール可能なもので終了します。

サイズは既存の pkg/vram 推定子 (リモート GGUF ヘッダー、HTTP HEAD、宣言された size:、その後 HF リポジトリ リスト) から取得されます。決定するために何もダウンロードされず、プローブの失敗によってインストールが失敗することはありません。

自動選択がデフォルトであり、すべてのサーフェスでこれをオーバーライドできます。POST /models/apply および POST /api/models/install/:id、local-ai models install <name> --variant <variant> の variant、install_model MCP ツールの variant パラメーター、およびモデル テーブルの分割ボタン メニューです。明示的な選択は、意図的な演算子のオーバーライドであるため、適合しない場合でも警告とともに受け入れられます。

既存のインストールは影響を受けません。リリースされたすべての LocalAI は gallery/index.yaml をライブで読み取り、理解できないキーを無視します。そのため、古い client は variants: を削除し、以前とまったく同じようにエントリをインストールします。仕様は、それを真実に保つために、レガシー形状の構造体を通じて実際のインデックスを再解析します。 言及する価値のある既知のギャップ: 分散モードでは、InstallModel はモデルにサービスを提供するワーカーではなくフロントエンドに対して解決されるため、小規模なフロントエンドと大規模なワーカーを持つクラスターは控えめに選択します。単一エントリ内のプローブは引き続きシリアルであり、上限はありません。

🖧 分散モードの信頼性

ホームページではロード済みとして表示されるが、クラスター内のどのノードにも表示されないモデルを調査したところ、4 つの個別のバグが判明し、すべてここで修正されました。

リーパーは、生きていて動作しているバックエンドの行を削除していました。 probeLoadedModels は 1 秒のヘルス チェックに失敗した後に node_models 行を取得しましたが、ビジー状態のバックエンドは応答できません。シングル スレッドの Python バックエンドはリクエスト内で数分間ブロックします。

  • 新しい models.running サブジェクトは、プロセス ハンドルを保持し、バックエンドによってブロックされないため、ワーカーに直接質問します。リコンサイラーは、ポート プローブの前にプロセス キーをレジストリと比較します。
  • 応答しないワーカーは空とみなされずスキップされるため、NATS ブリップはノードの行を削除できません。
  • ポート プローブは、3 回連続ミスした後、DeadlineExceeded (ビジー) と Unavailable (ゴーン) を分離し、後者のみをカウントするようになりました。

これらに加えて、in_flight カウンタのリークが高く、レプリカの VRAM がエビクションに対して固定される可能性があります。モデルロードの期限は、実時間ではなくチェックポイントのサイズと進行状況に応じて調整されるようになりました。ステージング検証は停止ではなく進捗としてカウントされます。バックエンド検出では、ワーカーがインストールしたバックエンドまたは GPU のみのバックエンドがコントローラーのファイル システムと機能の背後に隠されなくなりました。スケジューラは、モデルを保存できないノードにはモデルを配置しません。オープン応答はレプリカ間で表示され、キャンセル可能です。

🛡️ インライン微調整報酬コードがオプトインになりました

POST /api/fine-tuning/jobs は、手動で作成された組み込みホワイトリストに対して実行されたインライン Python ボディである reward_functions[].code を受け入れます。そのホワイトリストはセキュリティ境界ではありませんでした。標準の CPython イントロスペクションは実際の os モジュールに到達し、ホスト上で任意のコードを実行します。実行はジョブ開始時のスモーク テスト中に同期的に行われ、微調整エンドポイントはデフォルトでは認証されません。

ホワイトリストを強化するのではなく、オペレーターがバックエンドで LOCALAI_TRL_ALLOW_INLINE_REWARD=true を明示的にオプトインしない限り、インライン報酬コードは拒否されるようになりました。組み込みの報酬関数は影響を受けず、設定なしで動作し続けます。ドキュメントでは、ホワイトリストをサンドボックスとして説明することはなくなり、インライン コードは任意に実行されると明確に述べられています。

さらに 2 つの強化修正が同じサイクルで適用されました。

  • 抽出ルートをエスケープする Tar ハードリンクは拒否されます (#11266)。 ExtractArchive はメンバーと拒否されたシンボリックリンクを事前にスキャンしましたが、tar ハードリンク エントリは通常のファイル モードを実行してそのチェックに合格し、Header.Linkname は検証されなかったため、アーカイブは宛先ディレクトリの外部のパスへのリンクを作成する可能性がありました。 Linkname はメンバー名と同じパス チェックを受けるようになりました。ルート内で解決されるハードリンクは引き続き抽出されるため、通常のアーカイブは影響を受けません。
  • **JSON スキーマ文法の Cyclic $ref は、スタック オーバーフロー クラッシュを引き起こすのではなく、拒否されます (#11041)。

このリリースでは、CVE-2026-54290 の hono 4.12.25 も取り上げます。

  • プロセス: PR テンプレートのドキュメント チェックボックスと、エージェント手順の docs-with-code ルール。これにより、ユーザー向けのコードの変更により、同じ変更でドキュメントが更新されます。

また: grpc.attempts のタイミングとチューニングのガイダンス (#10868)、リアルタイムのための Opus バックエンドのインストール手順の修正 (#11018)、リバースプロキシと長い推論タイムアウトのガイダンス (#11195、#11065)、永続的なコンテナー ストレージの明確化 (#11190)、ROCm 7.x / RDNA 3.5 (Strix Halo、 gfx1151) が GPU アクセラレーション ガイド (#9229) に追加されました。

🌐 新しい localai.io

サイトは 2 つに分割されます。ルートのプロジェクト サイトと、ドキュメントが /docs/ の下に移動されました。 Hugo ドキュメント サイトは常に localai.io であり、LocalAI とは何かを説明したり、チームが何を構築しているかを示す場所がありませんでした。

以前に公開された URL はすべて引き続き機能します。 GitHub Pages にはサーバー側の書き換えがないため、ジェネレーターはビルドされたドキュメント出力を調べ、古いルート パスごとにメタ更新、正規リンク、および noindex を残します: 214 リダイレクト スタブ。これにより、裸の .html ファイルとディレクトリ インデックスがカバーされ、ルート サイトが所有するパスは決して上書きされません。

新しいサイトでは、完全に YAML データ ファイルによって駆動される /engines/ ページ (つまり、エンジンの追加は 2 か所で HTML を手書きするのではなく、1 回の編集で済みます)、/blog/、実際の POSIX install.sh および実際の /readyz および /healthz エンドポイントに接続された Kubernetes マニフェストを追加します。エコシステム バンドには、エンジニアが貢献した企業、LocalAI を統合するプロジェクト、LocalAI について書かれた場所がリストされ、それぞれが異なる明示された証拠基準に裏付けられており、リストへの掲載を希望する人のためのセルフサービス メカニズムとして ADOPTERS.md が使用されます。
