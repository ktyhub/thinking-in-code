#ローカルAI v4.7.0

🎉 LocalAI 4.7.0 リリース! 🚀

<h1 align="center"> <br> <img height="300" src="https://raw.githubusercontent.com/mudler/LocalAI/refs/heads/master/core/http/static/logo.png"> <br> <br> </h1>

LocalAI 4.7.0 が登場しました！

このリリースでは、LocalAI が生成できる内容とその実行方法が拡張されています。UI 管理の音声クローン ライブラリ、ローカル ビデオおよびオーディオ駆動型のアバター生成、ツール呼び出しに伴うインターリーブ推論などです。また、新しいオーディオ エンジン (ワンパス ダイアライズされたトランスクリプション、F5-TTS、真のストリーミング TTS) と、認証、トランスクリプション、モデル ギャラリーにわたる信頼性に関する一連の修正も導入されています。

ハイライト:

  • 🎙️ 管理された音声クローン作成 - UI で同意された参照を記録またはアップロードし、再利用可能なプロファイルとして保存し、安定した localai://voice-profiles/<id> URI を使用してクローン作成可能な TTS バックエンドから参照します。 YAML を手動で編集したり、オーディオをモデル フォルダーにコピーしたりする必要はもうありません。
  • 🎬 ローカル ビデオとアバター - 新しい longcat-video バックエンドは、テキストからビデオへ、画像からビデオへ、そしてオーディオ主導のトーキング アバターの生成をもたらし、オーディオと参照画像のコントロールを備えた Studio UI に組み込まれます。
  • 🧠 ツール呼び出しによるインターリーブ思考 - アシスタント ターンは、reasoning_content インバウンド エイリアスと Anthropic thinking ブロックのサポートにより、reasoning と tool_calls を一緒に実行し、ツールと結果のループ全体で推論を維持できるようになりました。
  • 🗣️ 新しいオーディオ エンジン - ワンパス ダイアライズされたトランスクリプション (moss-transcribe-cpp)、CrispASR での F5-TTS 音声クローン作成、vibevoice-cpp での真のストリーミング TTS (最初のオーディオまでの時間 2.38 秒対 CPU での 39.96 秒)。
  • 🎚️ 自動フルコンテキスト - context_size: -1 は、モデルごとに GGUF メタデータから読み取られた完全なトレーニング済みコンテキスト ウィンドウでモデルを実行し、VRAM フィット警告が表示されます。
  • 🖥️ より厳密な制御 - llama.cpp が (devices:) にオフロードする GPU を選択し、新しいモデル読み込みクールダウンにより、決定的に失敗したモデルがポーリングごとにバックエンドを再生成して VRAM をリークするのを防ぎます。

さらに、DFlash 投機的デコード ギャラリー モデル、EC/PS/EdDSA 署名付きトークンの OIDC 修正、バックエンドに到達する転写言語/翻訳設定、および通常の依存関係更新のセット。

🚀 新機能と主要な機能強化

🎙️ 管理された音声クローン作成プロファイル (音声ライブラリ)

<p align="center"> <em><img width="2880" height="1800" alt="ui-voice-library" src="https://github.com/user-attachments/assets/ea99bb2d-42b5-42b8-8c33-761090290e3f" /></em> <br><em>同意された参照を記録またはアップロードし、再利用可能なプロファイルとして保存し、クローン作成可能な TTS バックエンドから参照します。</em> </p>

音声クローン作成は、第一級の UI 主導のワークフローになります。 React UI で同意されたリファレンスオーディオを録音またはアップロードし、WAV に正規化し、プレビューして、名前付きプロファイルとして保存します。安定した localai://voice-profiles/<id> URI を使用して、TTS UI または /v1/audio/speech からプロファイルを参照します。YAML 編集やオーディオをモデル ディレクトリにコピーする必要はありません。

  • 新しい REST サーフェス: GET /api/voice-profiles、GET /api/voice-profiles/:id/audio、POST /api/voice-profiles (管理者)、DELETE /api/voice-profiles/:id (管理者)、Swagger、/api/instructions、および認証機能レジストリで公開されました。 MCP 管理ツール list_voice_profiles、create_voice_profile、delete_voice_profile。
  • 新しい型付き設定 tts.voice_cloning (ブール値) は、音声ライブラリの互換性の有無に応じてカスタム モデル名を選択します。 false は、HTTP 400 で保存されたプロファイル参照も拒否します。要求の優先順位は、voice -> tts.voice -> tts.audio_path です。既存のオプションは、重大な変更を加えることなく引き続き機能します。
  • 互換性はバックエンド機能からサーバーによって検出され (フロントエンドはバックエンド名をハードコードしません)、存在しない場合にインストールするギャラリー モデルを提供します。クローン作成は、vllm-omni、vibevoice-cpp、coqui、pocket-tts、qwen-tts、qwen3-tts-cpp、faster-qwen3-tts、fish-speech、neutts、chatterbox、voxcpm、omnivoice-cpp、およびモデル依存の crispasr の機能レジストリで宣言されます。
  • クロスバックエンドコントラクト: 参照 WAV + params.ref_text 経由の正確なトランスクリプト。 E2E は qwen3-tts-cpp で検証されました (4.47 秒のリファレンスにより、非サイレントの 3.44 秒 24kHz WAV が生成されました)。

🔗 PR: #10799

🎬 LongCat ビデオとアバターの生成

新しい longcat-video Python バックエンドは、LocalAI にローカル ビデオ生成機能をもたらします。テキストからビデオへ、画像からビデオへ、そしてオーディオ駆動の会話アバター用の LongCat-Video-Avatar 1.5 です。これは、オーディオおよび参照画像コントロールを備えた React Studio UI に接続されています。

  • ギャラリー エントリ longcat-video (テキスト + 画像入力、ビデオ出力) および longcat-video-avatar-1.5 (テキスト + 画像 + オーディオ入力、ビデオ出力)。バックエンド イメージ: CUDA 12 および CUDA 13 x86_64、および CUDA 13 ARM64 (DGX Spark / NVIDIA ARM64 ガイダンスを含む)。
  • 宣言機能メタデータの導入: 新しい known_input_modalities / known_output_modalities 構成フィールドにより、バックエンド名またはチェックポイント名で分岐する代わりに、汎用コードがチェックポイントが受け入れる内容を検出します。 HF インポーターは、一致する自己記述レシピ メタデータを出力します。
  • /video エンドポイントは、分散オーディオ ステージング (128 MiB に制限された入力) を使用して、ステージングされたオーディオおよびビデオ生成パラメーターを取得します。アバター モードは、マルチセグメント生成、BF16 またはオプションの INT8 量子化、蒸留設定をサポートしており、これについては新しい features/longcat-video.md ページに記載されています。

🔗 PR: #10792

🧠 ツール呼び出しによるインターリーブ思考

アシスタント ターンは reasoning と tool_calls を同時に実行できるようになり、推論はターンをまたいでツールと結果のループが続いても存続します。これは、バックエンドごとの事故ではなく、統一され、テストされ、文書化された動作です。

  • OpenAI チャット メッセージは、正規の reasoning フィールドの受信エイリアスとして reasoning_content を受け入れます (vLLM/DeepSeek/cogito スタイルの clients がそれを発行します)。放出は変更されず、両方が存在する場合は正規フィールドが優先されます。
  • Anthropic Messages ローカル パスは thinking ブロックをラウンドトリップします。受信 thinking ブロックはメッセージ推論に解析され、thinking ブロックは非ストリーミング応答とストリーミング応答の両方で tool_use の前に発行され、要求パラメーター thinking: {type: "enabled"} でゲートされます。クラウドプロキシのパススルー パスは変更されません。
  • ライブで検証済み: lfm2.5-8b-a1b と gemma-4-e2b は、1 ターンで reasoning と構造化 tool_calls を返します。新しい features/interleaved-thinking.md ドキュメントは、モデル構成、テキスト生成、および機能のガイドから相互リンクされています。

🔗 PR: #10744

🗣️ 新しいオーディオ エンジン: ダイアライズされた文字起こし、F5-TTS、ストリーミング TTS

3 つの追加により、オーディオの領域が広がります。

  • moss-transcribe-cpp (#10756): C++/ggml MOSS-Transcribe-Diarize ポートを開き、複数話者の共同文字起こし、ダイアライゼーション、およびタイムスタンプを 1 つのオフライン パスで実行する新しい Go バックエンド。ギャラリーモデル moss-transcribe-cpp-0.9b (デフォルトは q5_k GGUF)。 ggml ポートは、リファレンス PyTorch に対してバイト正確で、CPU では 1.6-2.2x より高速で、CUDA ではビット正確です (Blackwell / Jetson Thor で検証済み)。完全な Linux マトリックスと Darwin/Metal にわたって構築されます。
  • CrispASR の F5-TTS (#10753): F5-TTS 静的ランタイムを CrispASR ビルド (SWivid、MIT、Vocos ボコーダーを内蔵した 22 層 DiT フロー マッチング モデル) にリンクし、f5-tts-crispasr ギャラリー モデルを同梱します。 24kHz モノラル オーディオを生成し、f5-tts として自動検出します (backend: セレクターはありません)。 options: [voice:/path/ref.wav, voice_text:Transcript...] による音声クローン作成;注 F5-TTS は 32 ステップの ODE ソルバーを実行するため、CPU 合成は計算負荷が高くなります。
  • vibevoice-cpp の真のストリーミング (#10764): 全体の clip からチャンクまでの合成を、新しい vv_capi_tts_stream コールバック ABI を介した実際の増分ストリーミングに置き換えます。 VibeVoice-Realtime-0.5B の CPU のみのボックスでは、最初のオーディオまでの時間が 39.96 秒 (バッチ) から 2.38 秒 (ストリーミング) に低下し、約 17 倍になります。スコープはリアルタイム 0.5B モデルです。非ストリーミング パスは変更されません。

🔗 PR: #10756、#10753、#10764

🎚️ context_size: -1 による自動フルコンテキスト

context_size: -1 センチネル (負の値) は、ロード時に GGUF n_ctx_train メタデータからモデルごとに解決され、完全にトレーニングされたコンテキストでモデルを実行するようになりました。これにより、ギャラリー YAML がすでに値を固定している場合でも、数値をハードコーディングすることなく、モデルを真の最大ウィンドウに選択できます。グローバル同等の LOCALAI_CONTEXT_SIZE=-1 / ZZPH100​​ZZ は、すべてのモデルを独自のトレーニング済み最大値に解決しますが、明示的なモデルごとの値が引き続き優先されます。 3 つの防御層により安全性が保たれます。メタデータに使用可能な最大値が不足している場合は、GGUF 解像度がデフォルトに低下し、警告が表示されます。 GPU 専用の warnIfContextExceedsVRAM ヘルパーは、ウィンドウが収まらない可能性があるときにログを記録します (ブロックはしません)。バックエンド オプション レイヤーは、残りの負の値をデフォルトにクランプするため、バックエンドは負の n_ctx を受け取りません。以前の唯一のパス (context_size の設定を解除) は変更されません。

🔗 PR: #10752

🖥️ GPU デバイスの選択とモデル読み込みのクールダウン

  • llama.cpp デバイス選択 (#10724): llama.cpp options: 配列の新しい device / devices オプションはアップストリーム --device にマップされるため、特定の GPU へのオフロードを制限できます (たとえば、ディスプレイまたはデバッグ GPU を除外する)。例:options: [devices:CUDA1,CUDA2,CUDA3]。デバイス名はllama-server --list-devicesから来ています。
  • モデルロード失敗のクールダウン (#10728): ロードが失敗すると、クールダウンウィンドウ中に新しい独立したロードトリガーが拒否され、ポーリングごとにバックエンドを再生成するのではなく、503 + Retry-After にマップされた型付きエラーが返されます。これにより、決定的に障害が発生したモデルによる GPU/CUDA 状態のリーク (レポーターは climb から約 58 GB までのコンテキストのリークを確認しました)、および LOCALAI_SINGLE_ACTIVE_BACKEND の下では正常なモデルからアクティブ スロットを盗むことがなくなります。 --model-load-failure-cooldown / LOCALAI_MODEL_LOAD_FAILURE_COOLDOWN 経由で設定可能 (デフォルトの 10s、0 は無効)。クールダウンは連続失敗ごとに 2 倍になり、5 メートルで上限が設定され、ロードが成功するとリセットされます。本物の同時バーストの合体したフォロワーは、依然として 1 回の再試行を受けます。

🔗 PR: #10724、#10728

🧠 モデル

  • Qwen DFlash 投機的デコーディング モデル (#10791): llama-cpp バックエンドの 4 つのギャラリー エントリ。それぞれ、完全なターゲット モデルとその小さなブロック拡散ドラフター (ドラフターはスタンドアロンのチャット モデルではありません) をバンドルしています: qwen3-4b-dflash、qwen3.5-9b-dflash、qwen3.6-27b-dflash、qwen3.6-35b-a3b-dflash。エントリごとの構成は flash_attention: on、draft_model:、use_jinja:true、spec_type:draft-dflash、spec_n_max:15 です。アップストリームの DFlash サポートを備えた固定された llama.cpp が必要です。バンドルされているすべてのドラフターは general.architecture = dflash で検証されます (フォークのみの dflash-draft GGUF はロードに失敗するため意図的に除外されています)。 GPU推奨。
  • 推論のデフォルト (#10741): deepseek-v4 (unsloth から自動生成) の推奨サンプリング デフォルトを追加します。これにより、LocalAI はファミリに正しい生成パラメータを自動的に適用します。
  • さらに、ギャラリー エージェント (#10743、#10755) を介して追加された新しいギャラリー モデル。
