重大な変更

資産の分割

Airflow 3.2.0 の目玉機能は資産の分割です。これはデータ認識の大きな進化です。 スケジューリング。アセット全体に基づいて Dag をトリガーする代わりに、ダウンストリームをスケジュールできるようになりました データの特定のパーティションに基づいた処理。データの関連するスライスのみが下流でトリガーされます これにより、パイプライン オーケストレーションがはるかに効率的かつ正確になります。

これは、パーティション化されたデータ レイク (日付でパーティション化された S3 パス、Hive テーブル) を操作する場合に重要です。 パーティション、BigQuery テーブル パーティション、またはその他のパーティション化されたデータ ストア。以前は、どのようなアップデートでも アセットに変更すると、どのパーティションが変更されたかに関係なく、すべてのダウンストリーム DAG がトリガーされました。今は右側だけ 適切なタイミングで作業が開始されます。

詳しい使用方法については、:doc:/authoring-and-scheduling/assets を参照してください。

マルチチーム展開

Airflow 3.2 はマルチチーム サポートを導入し、組織が単一の Airflow 導入内で複数の分離したチームを実行できるようにします。 各チームは独自の Dag、接続、変数、プール、エグゼキュータを持つことができ、チームごとに個別の Airflow インスタンスを必要とせずに、真のリソースと権限の分離が可能になります。

これは、チームのリソースとアクセス間の強力な境界を維持しながら、共有インフラストラクチャから複数のデータ エンジニアリング チームまたはデータ サイエンス チームにサービスを提供するプラットフォーム チームにとって特に有益です。

詳しい使用手順については、:doc:/core-concepts/multi-team を参照してください。

.. 警告::

マルチチーム展開は 3.2.0 では実験的であり、将来のバージョンでは変更される可能性があります。 ユーザーからのフィードバック。

デッドライン アラートの同期コールバック サポート

デッドライン アラートは、既存のアラートに加えて、SyncCallback を介した同期コールバックをサポートするようになりました。 非同期AsyncCallback。同期コールバックは、(実行プログラムではなく) エグゼキュータによって実行されます。 トリガー)、オプションで executor パラメーターを介して特定のエグゼキューターをターゲットにすることもできます。

Dag は、deadline パラメーターにリストを渡すことで、複数の期限アラートを定義することもできます。 各アラートはいずれかのコールバック タイプを使用できます。

UIの強化とパフォーマンス

  • グリッド ビュー仮想化: グリッド ビューでは仮想化が使用されるようになりました。表示されている行のみが DOM にレンダリングされます。これにより、多数のタスクが実行される Dag を表示するときのパフォーマンスが大幅に向上し、複雑な Dag のレンダリング時間とメモリ使用量が削減されます。 (#60241)

  • UI での XCom 管理: XCom 値を Airflow UI から直接追加、編集、削除できるようになりました。これにより、CLI コマンドを必要とせずに、開発中や日常の操作中に XCom 状態のデバッグと管理が非常に簡単になります。 (#58921)

  • HITL 詳細履歴: Human-in-the-Loop の承認インターフェイスに完全な履歴ビューが追加され、オペレーターとレビュー担当者があらゆるタスクの承認と拒否の完全な監査証跡を確認できるようになりました。 (#56760、#55952)

  • ガント チャートの改善:

    • すべてのタスクの試行が表示される: ガント チャートには、最新の試行だけでなく、すべてのタスクの試行が表示されるようになりました。

  • ガントチャートでのタスク表示名: 読みやすくするために task_display_name を表示 (#61438)

    • ガントチャートの ISO 日付: ブラウザー間で一貫した日付形式 (#61250)
    • Null datetime クラッシュを修正: Null datetime フィールドを持つタスクでガント チャートがクラッシュしなくなりました。

カウントのみを行う airflow scheduler command has a new --only-idle フラグは、 スケジューラはアイドル状態です。これにより、ユーザーはスケジューラーを 1 回実行して、トリガーされたすべての Dag を処理し、 キューに入れられたタスク。小さな値を設定できるように、--num-runs フラグを必要とし、これを補完します。 スケジューラが必要とする反復回数を推測する代わりに。

すべての API サーバー出力の構造化された JSON ログ

新しい「json_logs`` option under the ``[logging]」セクションにより、エアフローが実現します。 すべての出力を、代わりに改行区切りの JSON (構造化ログ) として生成します。 人間が判読できる形式のログ。これは、API サーバー (gunicorn/uvicorn) をカバーします。 アクセス ログ、警告、未処理の例外が含まれます。

すべてのコンポーネントがまだこれをサポートしているわけではありません (特に「airflow celery worker」)。 json_logs が有効な場合の JSON 以外の出力はバグとして扱われます。 (#63365)

Airflow は、タスク側の例外 (AirflowSkipException, TaskDeferred など) を次からソースします。 airflow.sdk.exceptions. airflow.exceptions は引き続き同じ例外を公開しますが、 Dag 作成者が shim が削除される前に移行できるように、DeprecatedImportWarning を発行するプロキシ。

  • タスク SDK はこれらのクラスを再定義するため、ワーカーは実行時に airflow-core に依存しなくなります。
  • airflow.providers.common.compat.sdk はプロバイダーの互換性インポートを一元管理します。

  • 非推奨の例外名を「airflow.exceptions」からインポートすると、ユーザーに次のことを指示する警告がログに記録されます。 SDK インポート パス。

  • プロバイダーは airflow.providers.common.compat.sdk を利用して、機能する 1 つのインポート パスを維持できます。 サポートされている Airflow バージョン全体で。

retry_exponential_backoff パラメータの数値乗数値をサポート

「retry_exponential_backoff`` parameter now accepts numeric values to specify custom exponential backoff multipliers for task retries. Previously, this parameter only accepted boolean values (``True`` or ``False``), with ``True`` using a hardcoded multiplier of ``2.0」。

新しい動作:

  • 数値 (例: 2.0, 3.5) は、指数バックオフ乗数を直接指定します。
  • retry_exponential_backoff=2.0 は、各再試行間の遅延を 2 倍にします。
  • retry_exponential_backoff=0 or False disables exponential backoff (uses fixed retry_delay)

下位互換性:

ブール値を使用する既存の Dag は引き続き機能します。

  • retry_exponential_backoff=True → converted to 2.0 (元の動作を維持)
  • retry_exponential_backoff=False → converted to 0.0 (指数バックオフなし)

API の変更点:

retry_exponential_backoff has changed from type: boolean to type: number の REST API スキーマ。 API clients は数値を使用する必要があります (ブール値は拒否されます)。

移行:

Python Dags のブール値は下位互換性のために自動的に変換されますが、明確にするために明示的な数値に更新することをお勧めします。

  • retry_exponential_backoff=True → retry_exponential_backoff=2.0を変更します
  • retry_exponential_backoff=False → retry_exponential_backoff=0を変更します

  • シリアライザー モジュールは「airflow.serialization.serializers.*`` to ``airflow.sdk.serde.serializers.*」から移動されました
  • 新しいシリアライザーを airflow.sdk.serde.serializers.* 名前空間に追加する必要があります

オペレーターは、Dag レベルの「render_template_as_native_obj」設定をオーバーライドできるようになりました。 テンプレートをネイティブ Python としてレンダリングするかどうかをきめ細かく制御できるようにします。 タスクごとに型または文字列を指定します。 render_template_as_native_obj=True を設定するか、 False on any operator to override the Dag setting, or leave as None (デフォルト) Dagから継承する。

ダウンタイムゼロのワーカー recycling を備えた API サーバーの gunicorn サポートを追加します。

API サーバーは、ワーカーのローリング再起動を備えた代替サーバーとして gunicorn をサポートするようになりました。 長時間実行されるプロセスでのメモリの蓄積を防ぐため。

主な利点:

  • ローリングワーカーの再起動: 新しいワーカーが古いワーカーよりも先に生成され、ヘルスチェックに合格します。 が強制終了され、ワーカーの recycling 中にダウンタイムがゼロになります。

  • メモリ共有: Gunicorn はプリロード + フォークを使用するため、ワーカーは次の方法でメモリを共有します。 コピーオンライト。これにより、uvicorn と比較して総メモリ使用量が大幅に削減されます。 各ワーカーがすべてを個別にロードするマルチプロセス モード。

  • 正しい FIFO 信号処理: Gunicorn の SIGTTOU は最も古いワーカー (FIFO) を強制終了します。 最新 (LIFO) ではありませんが、ローリング再起動には適しています。

構成:

.. コードブロック::ini

[api]
# ユビコーンの代わりにガニコーンを使用する
サーバータイプ = ガニコーン

# 12 時間ごとのワーカーのローリング再起動を有効にする
ワーカー_リフレッシュ間隔 = 43200

# ワーカーを一度に 1 つずつ再起動します
ワーカー_リフレッシュ_バッチ_サイズ = 1

または環境変数経由:

.. コードブロック:: bash

エクスポート AIRFLOW__API__SERVER_TYPE=ガニコーン
エクスポート AIRFLOW__API__WORKER_REFRESH_INTERVAL=43200

要件:

追加のガニコーンをインストールします: pip install 'apache-airflow-core[gunicorn]'

uvicorn に関する注意事項 (デフォルト):

デフォルトの uvicorn モードは、次の理由により、ワーカーのローリング再起動をサポートしていません。

1.workers=1 の場合、シグナルを送信するマスター プロセスがありません。 2. uvicorn の SIGTTOU は最新のワーカー (LIFO) を強制終了し、ローリング リスタートの目的を無効にする 3. 各 uvicorn ワーカーは、メモリ共有なしですべてを個別にロードします。

ワーカー recycling またはメモリ効率の高いマルチワーカー デプロイメントが必要な場合は、gunicorn を使用してください。 (#60921)

多くのマップされたタスクを含む Dag のレンダリングされたタスク インスタンス フィールドのクリーンアップのパフォーマンスが向上しました (最大 42 倍高速)

設定「max_num_rendered_ti_fields_per_task`` is renamed to ``num_dag_runs_to_retain_rendered_fields」 (古い名前は非推奨の警告とともに引き続き機能します)。

保持期間は、最近の N 回のタスク実行ではなく、最近の N 回の DAG 実行に基づくようになりました。 その結果、条件付き/まばらなタスクに対して保持されるレコードが少なくなる可能性があります。 (#60951)

AuthManager バックフィル権限は requires_access_dag on the DagAccessEntity.Run によって処理されるようになりました。

「is_authorized_backfill`` of the ``BaseAuthManager」インターフェースは削除されました。コアはこのメソッドとそのメソッドを呼び出さなくなります。 プロバイダーの対応する実装は非推奨としてマークされます。 バックフィル操作の権限は、既存の権限を使用して「DagAccessEntity.Run」権限と照合されるようになりました。 requires_access_dag デコレーター。つまり、ユーザーが Dag を実行する権限を持っている場合、そのユーザーはその Dag に対してバックフィル操作を実行できます。

セキュリティ ポリシーを更新して、バックフィル操作を実行する必要があるユーザーが適切な DagAccessEntity.Run 権限を持っていることを確認してください。 (ユーザー DagRun 権限を持たずにバックフィル権限を持っている場合は、更新を行わないとバックフィル操作を実行できなくなります)
