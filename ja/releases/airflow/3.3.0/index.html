エアフロー 3.3.0

📦 PyPI: https://pypi.org/project/apache-airflow/3.3.0/ 📚 ドキュメント: https://airflow.apache.org/docs/apache-airflow/3.3.0/ 🛠 Release Note: https://airflow.apache.org/docs/apache-airflow/3.3.0/release_notes.html 🐳 Docker 画像: 「docker プル アパッチ/エアフロー:3.3.0」 🚏 制約: https://github.com/apache/airflow/tree/constraints-3.3.0

重大な変更

資産のパーティション分割 (#64571、#65447、#66030、#66848、#67184、#67475、#67716、#68978)

3.2.0 で導入された資産分割を基にして、Airflow 3.3.0 は、 単一の上流アセット イベントは、分割された下流 Dag 実行にファンアウトします。新しいパーティション マッパー — RollupMapper (many-to-one), FanOutMapper (one-to-many), and FixedKeyMapper + SegmentWindow (カテゴリロールアップ) — 時間枠 (日/週/月/四半期/年) と wait_policy (WaitForAll or MinimumCount(n)) を使用して、パーティションの実行が開始されるタイミングを制御します。窓 時間的に前方または後方にファンアウトすることができ、上流イベントごとの合計ファンアウトは新しいイベントによって制限されます。 [scheduler] partition_mapper_max_downstream_keys 構成 (マッパーごとに構成可能)。エアフロー 3.3.0 また、PartitionedAtRuntime タイムテーブルを追加します。これにより、Dag がそのパーティション キーを宣言できるようになります。 上流のイベントからマッピングされるのではなく、実行の開始時に割り当てられます。

詳しい使用方法については、:doc:/authoring-and-scheduling/assets を参照してください。

タスクおよびアセット状態ストア (#65759、#66073、#66160、#66463、#66586、#66859、#67041、#67292、#67319)

Airflow 3.3.0 には、タスクとアセット用のファーストクラスの状態ストア (AIP-103) が導入されています。タスクは永続化できる 再試行後も存続し、新しい task_state_store アクセサーを介して実行される任意のキーと値の状態、および アセットは「asset_state_store」を介して独自の状態を保持できます。どちらもタスク SDK から利用できます。状態が保たれている デフォルトでメタデータ データベース内、またはカスタムのワーカー側バックエンド ([workers] state_store_backend)、定期的なガベージ コレクションとオプションのキーごとの保持をサポートします。 clear_on_success であり、コア API および実行 API を通じて完全に管理可能です。

詳しい使用方法については、:doc:/core-concepts/task-and-asset-state-store を参照してください。

プラグイン可能な再試行ポリシー (#65474)

タスクの再試行動作がプラグ可能になりました (AIP-105)。固定の retries カウントに加えて、次のことができます。 タスクを再試行するかどうか、いつ再試行するかを決定するカスタム再試行ポリシーをアタッチして、次のような戦略を有効にします。 特定の例外でのみ再試行するか、カスタム ロジックに基づいてバックオフします。

詳しい使用方法については、:ref:concepts:retry-policies を参照してください。

言語タスク SDK (Java および Go) (#65958、#67161、#67635、#67699)

Airflow 3.3.0 は、個々のタスク実装を記述できるコーディネーター層 (AIP-108) を追加します。 Dag とそのスケジューリングは Python のままですが、非 Python 言語で使用できます。タスクは Dag で宣言されます 「@task.stub(queue=...)」付き。ワーカーはそれを設定されたコーディネーターにルーティングします (自己完結型ネイティブ バイナリの場合は「JavaCoordinator`` for JVM languages, ``ExecutableCoordinator」 Go など) は言語ランタイムでタスクを実行し、変数、接続、および XCom をプロキシして返します。 実行APIを通じて。

.. 警告::

コーディネーター層と Java/Go SDK は 3.3.0 では実験的なものであり、将来変更される可能性があります ユーザーのフィードバックに基づいたバージョン。

詳しい使用方法については、:doc:/authoring-and-scheduling/language-sdks/index を参照してください。

クリア、再実行、バックフィル時の Dag バンドル バージョン (#63884)

新しい rerun_with_latest_version 設定は、Dag 実行がクリアされるか、再実行されるか、バックフィルされるかを制御します。 最新のバンドル バージョンまたは最初の実行時のオリジナル バージョンを使用します。デフォルトは解決されました 優先順位: 明示的なリクエスト パラメーター/CLI フラグ、次に Dag レベルの rerun_with_latest_version、 次に「[core] rerun_with_latest_version``, and finally ``False`` for clear/rerun and ``True」 バックフィル（過去の動作を保存）。 Airflow 2.x は常に最新のコードで再実行されます。 3.x 元のバージョンをデフォルトとするバンドルのバージョン管理が導入され、この設定によりユーザーが制御できるようになりました。

詳細については、:doc:/administration-and-deployment/dag-bundles を参照してください。

専用バンドルとしてのプロバイダーの例 Dag (#66161)

プロバイダーのディストリビューションによって出荷されるサンプル Dag は、ProvidersManager 経由で検出されるようになりました。 独自の Dag バンドルとして登録されます — プロバイダーごとに 1 つ、名前が付けられます apache-airflow-providers-<distribution>-example-dags (or <distribution>-example-dags 用 サードパーティプロバイダー）。 [core] load_examples オプションは依然として、それらが登録されるかどうかを制御します。 プロバイダーが提供するサンプル Dag の bundle_name by "dags-folder" をフィルター処理した REST API clients 新しいプロバイダーごとのバンドル名に更新する必要があります。 DAG 識別子は変更されません。

リモート ロギング解決が airflow.logging_config から分離されました (#67056)

リモート タスク ログ ハンドラーの解決は、共有の airflow_shared.logging.factory によって所有されるようになりました。 モジュールを作成し、明確に定義された単一の優先順位を適用します。

  1. ユーザー定義の [logging] logging_config_class exporting REMOTE_TASK_LOG / DEFAULT_REMOTE_CONN_ID (既存のカスタム構成は引き続き機能します);
  2. ProvidersManager scheme dispatch — the scheme of [logging] remote_base_log_folder は、 プロバイダー RemoteLogIO class, instantiated via a no-argument from_config() クラスメソッド。
  3. airflow_local_settings.py を読み取る移行的なレガシー フォールバック (Airflow 4.0 では削除される予定)。

「airflow.logging_config.load_logging_config`` is deprecated (it now emits ``DeprecationWarning」および 新しいプライベート ヘルパーに委任されます)、configure_logging はリモートの問題を熱心に解決しなくなりました。 ハンドラー — 初回使用時の解決は遅延します。 remote-logging: ブロックを登録したが、 from_config を実装していない場合は、警告が表示されてスキップされ、レガシー パスにフォールスルーされます。

移行: airflow.logging_config.load_logging_config() への直接呼び出しを新しい呼び出しに置き換えます。 ヘルパーを作成し、プロバイダーのリモート ログ ハンドラー クラスに引数なしの from_config を実装させます。 airflow.providers.common.compat.sdk.conf というクラスメソッド。

OpenTelemetry タイマー メトリクスでヒストグラムが使用されるようになりました (#64207)

OpenTelemetry タイマーとタイミング メトリクスは、ゲージではなくヒストグラムとして記録されるようになりました。 記録全体にわたるカウント、合計、およびバケットの分散。

Dag 処理の「秒前」メトリクスがタグ付けされるようになりました (#62487)

dag_processing.last_run.seconds_ago.{dag_file} は従来のメトリックになりました。新しい 「dag_processing.last_run.seconds_ago`` is emitted with ``file_path``, ``bundle_name」および file_name tags (file_path + bundle_name は Dag ファイルを一意に識別します)。従来のメトリクス は依然としてデフォルトで発行され、[metrics] legacy_names_on を介して無効にすることができます。

「参照」の下の「新しい期限」ページ (#67586)

新しい 期限 ページが [参照] メニューの下に表示され、すでに持っている役割であればアクセスできます。 Dag Runs の「can_read`` and ``menu_access」。
