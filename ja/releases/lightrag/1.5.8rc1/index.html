#ライトラグv1.5.8rc1

重要な注意事項

v1.5.8rc1 はリリース候補です。本番環境をアップグレードする前に、データのコピーでテストしてください。

ハイライト

1.構成ストレージ: LightRAG は、どの埋め込みモデルがベクターを構築したかを記憶するようになりました

以前のリリースでは、既存のデプロイメントで EMBEDDING_MODEL または EMBEDDING_DIM を変更すると、サイレントに失敗しました。バックエンドに応じて、LightRAG は古いベクターを保持して間違った近傍を返すか、新しい空のベクター コンテナー (Milvus / Qdrant / PostgreSQL) を開いてベクターをまったく含まないナレッジ グラフを提供します。

v1.5.8 は 構成ストレージ を追加します。これは、各ワークスペースの埋め込みベースラインを保持する小さな KV 名前空間 (config) です。すべてのベクトル ターゲット (エンティティ、リレーションシップ、チャンク) について、そのベクトルが書き込まれた埋め込み空間です。起動時に、現在の埋め込み構成に対してベースラインがチェックされます。スペースが変更された場合、サーバーは起動を拒否し、悪い結果を提供するのではなく、ターゲットと出口を指定します。

  • バックエンド: JsonKVStorage、PGKVStorage、MongoKVStorage、OpenSearchKVStorage、LIGHTRAG_CONFIG_STORAGE で選択。設定しないままにすると、LIGHTRAG_KV_STORAGE に従います。そのため、ほとんどの展開では新しい設定は必要ありません。 RedisKVStorage は許可されないため、Redis デプロイメントはデフォルトで JsonKVStorage になり、起動警告が表示されます。
  • 準備は必要ありません。 v1.5.8 の最初の起動時に、既存の展開が独自にベースラインを記録します。ベースラインは証拠にのみ記録されます。採用プローブは、いくつかの保存されたレコード (ターゲットごとに最大 8 つ) を再埋め込み、それらを保存されたベクトルと比較するか、コンテナが空であることが確認されます。実行できないプローブ (埋め込みサービスがダウンしているなど) は何も記録せず、次回の起動時に再試行されます。
  • デプロイメント アンカー。 最初の起動では、WORKING_DIR/config_storage_anchor.json (バックエンド タイプ + コンテナー UUID) で開かれた構成コンテナーにデプロイメントがバインドされます。それ以降の起動では、別のタイプまたは別の UUID のコンテナが拒否されます。したがって、変更された LIGHTRAG_KV_STORAGE、別のデータベース、または交換されたボリュームによって、構成がサイレントに移動されることはなくなりました。
  • 新しいオフライン ツール:
    • lightrag-rebuild-vdb はワークスペースを現在のモデルに再埋め込み、新しいベースラインを記録します。これは意図的なモデルチェンジ後の解決策です。
    • lightrag-migrate-config は、構成ストレージを別のタイプのバックエンドに移動します (たとえば、JSON ファイルから PostgreSQL に)。
    • lightrag-clear-storage は、構成レコードを含むワークスペースをオフラインにクリアします。
  • 複数のサーバー、1 つの WORKING_DIR: 各サーバーに独自の WORKSPACE とポートがある場合にサポートされます。ファイル システムがファイル ロックをサポートしている場合、同じ ワークスペース上の 2 番目のサーバーは拒否されます。

詳細については、以下を参照してください。

  • docs/LightRAG-API-Server.md: バックエンド タイプ間の構成ストレージの移行
  • lightrag/tools/README_REBUILD_VDB.md、README_MIGRATE_CONFIG.md、README_CLEAR_STORAGE.md
  • docs/design/ConfigurationStorageDesign.md: 設計概要

2.より安全なグラフの書き込みとドキュメントの削除

  • 手動グラフ編集 (エンティティとリレーションの作成/編集/削除/マージ、insert_custom_kg) は、相互に、および NetworkXStorage の取り込みパイプラインに対してシリアル化されるようになりました。
  • 操作が中断された場合のデータ損失を防ぐために、エンティティ/リレーションの作成、編集、マージ、および名前変更のコミット順序が見直されました。
  • 中断されたドキュメントの削除は表示され、再試行可能です。
  • 新しい lightrag-repair-chunk-tracking ツールは、中断された削除によって残された孤立したチャンク追跡行を削除します。

3. PostgreSQL ストレージのデフォルト セットアップ ウィザードは、公式 pgvector/pgvector イメージから PostgreSQL を生成し、グラフに PGTableGraphStorage (プレーン テーブル、Apache AGE なし) を提供するようになりました。 PGGraphStorage (AGE) および Redis ストレージ (RedisKVStorage、RedisDocStatusStorage) は 非推奨です。これらは動作し続け、起動時に警告が記録されます。

4.セキュリティ強化と新しいプロバイダー

  • Ollama 互換の /api/* ルートは LIGHTRAG_API_KEY によって保護されています (重大な変更を参照)。
  • PDF 抽出では、リソースが制限された子プロセスで pypdf が実行されます。
  • ストリーミングされたエラー行は、生のプロバイダー例外テキストをエコーし​​なくなりました。
  • OpenAI Responses API 用の新しい openai_responses LLM バインディング。

重大な変更

  • Python 3.11 以降が必要です。 Python 3.10 はサポートされなくなりました。 Docker イメージ (Python 3.12) は影響を受けません。
  • 既存のワークスペースで埋め込みモデルを変更すると、起動が拒否されるようになりました。以前は間違った結果または空の結果が提供されていました。以前の EMBEDDING_MODEL / EMBEDDING_DIM を復元するか、lightrag-rebuild-vdb を実行して新しいモデルを再埋め込みます。
  • 最初の v1.5.8 の起動後の LIGHTRAG_KV_STORAGE の変更は、LIGHTRAG_CONFIG_STORAGE が設定されていない間は拒否されます。これは、構成ストレージがサイレントに一緒に移動するためです。 LIGHTRAG_CONFIG_STORAGE をアンカーされたバックエンドに明示的に設定するか、lightrag-migrate-config を使用して構成を移動します。
  • Ollama ルートには API キーが必要です。 LIGHTRAG_API_KEY が設定され、WHITELIST_PATHS が設定されていない場合、キーのない /api/* リクエストは HTTP 403 を取得するようになりました。 Open WebUI では、lightrag:latest モデルがリストから消えます。修正: キーを Ollama 接続の API キーとして入力するか (Authorization: Bearer <key> として送信)、古い動作を維持するには WHITELIST_PATHS=/health,/api/* を設定します。
  • POST /documents/clear_cache は削除されました。 代わりに DELETE /documents?clear_llm_cache=true を使用してください。 LLM キャッシュのクリアは、破壊的クリアと同時に行われるようになりました。
  • $ で始まるワークスペース名は予約されています。 サーバーは、WORKSPACE=$team を _team として提供していました。 WORKSPACE=_team (データが既に保存されている名前) を設定すると、データは移動されません。

アップグレードに関する注意事項

  1. 最初にバックアップし、v1.5.8 を起動する前に古いインスタンスをすべて停止します。 これには、すべてのワーカー、ストレージを共有するサーバー、およびメンテナンス ツールが含まれます。最初の開始では、構成コンテナーが作成され、アンカーがバインドされます。古いライターを実行したままにするローリング アップグレードは行わないでください。
  2. すべてのストレージがデータベースである場合でも、WORKING_DIR は永続する必要があります。 現在は config_storage_anchor.json を保持し、JSON 構成の場合は <workspace>/kv_workspace_config.json も保持します。 Docker では、マウントされたボリューム上に保持します。 Helm には persistence.enabled: true を保管してください。一時的な WORKING_DIR は、再起動するたびにアンカーと JSON 構成を失います。バックアップに含めてください。
  3. 最初の起動時に埋め込みサービスにアクセスできる必要があります。これにより、導入プローブはベースラインを記録できます。ベースラインを確立できなかったことを示す WARNING の起動ログを確認してください。埋め込みスペースの不一致により開始が拒否された場合は、保存されたベクトルが設定されたモデルと一致しません。設定を修正するか、lightrag-rebuild-vdb を実行してください。
  4. Redis ユーザー: LIGHTRAG_KV_STORAGE=RedisKVStorage では、構成ストレージはデフォルトで WORKING_DIR 内の JSON ファイルになります (注 2 を参照)。 Redis ストレージは非推奨になりました。 PostgreSQL への移行を計画しています。
  5. PGGraphStorage ユーザー: 展開は引き続き機能し、ウィザードはその AGE 対応イメージを保持します。 AGE を終了するには、最初にグラフを移行し (python -m lightrag.tools.migrate_graph_storage --apply、再インデックスは必要ありません)、次に PGTableGraphStorage と pgvector イメージに切り替えます。
  6. オプション: JSON ファイルではなくデータベースに構成を保持するには、すべてのサーバーを停止した状態で lightrag-migrate-config --target-backend PGKVStorage (または MongoKVStorage / OpenSearchKVStorage) を実行します。次に、LIGHTRAG_CONFIG_STORAGE をそのバックエンドに設定します。
  7. 新しい埋め込みモデルを最初からやり直すには、ファイルを手動で削除するのではなく、lightrag-clear-storage を使用します。ファイルを手動で削除する場合は、kv_workspace_config.json と config_storage_anchor.json も削除します。それ以外の場合、記録されたベースラインは新しいモデルを拒否します。
  8. TOKEN_SECRET は、少なくとも 32 バイトのランダムな値である必要があります (たとえば、openssl rand -hex 32)。アップグレードされた PyJWT は、短いシークレットについて警告します。
  9. ストリーミングされるエラー メッセージは一般的なものです。 /query/stream、/api/generate、または /api/chat のストリーム途中での障害は Internal server error (error_id: …) と表示され、LLM プロバイダーの例外テキストは含まれなくなりました。ストリーム形式は変更されません。 error_id のサーバー ログで詳細を調べます。ストリームからのプロバイダー エラー テキストを解析する (たとえば、レート制限を検出するため) client を更新する必要があります。
