LightRAG v1.5.8rc1

Important Notes

v1.5.8rc1 is a release candidate. Please test it on a copy of your data before upgrading production.

Highlights

1. Configuration storage: LightRAG now remembers which embedding model built your vectors

In earlier releases, changing EMBEDDING_MODEL or EMBEDDING_DIM on an existing deployment failed silently. Depending on the backend, LightRAG either kept the old vectors and returned wrong neighbours, or opened a new, empty vector container (Milvus / Qdrant / PostgreSQL) and served a knowledge graph with no vectors at all.

v1.5.8 adds a configuration storage. It is a small KV namespace (config) that holds each workspace’s embedding baselines: for every vector target (entities, relationships, chunks), the embedding space its vectors were written in. Startup checks the baselines against the current embedding configuration. If the space has changed, the server refuses to start and names the target and the way out, instead of serving bad results.

  • Backends: JsonKVStorage, PGKVStorage, MongoKVStorage and OpenSearchKVStorage, selected with LIGHTRAG_CONFIG_STORAGE. Left unset, it follows LIGHTRAG_KV_STORAGE, so most deployments need no new setting. RedisKVStorage is not admitted, so Redis deployments default to JsonKVStorage, with a startup warning.
  • No preparation needed. On the first start of v1.5.8, an existing deployment records its baselines on its own. A baseline is recorded only on evidence: an adoption probe re-embeds a few stored records (up to 8 per target) and compares them with the stored vectors, or the container is confirmed empty. A probe that cannot run (for example, the embedding service is down) records nothing and is retried on the next start.
  • Deployment anchor. The first start also binds the deployment to the configuration container it opened, in WORKING_DIR/config_storage_anchor.json (backend type + container UUID). Every later start refuses a container of another type or another UUID. A changed LIGHTRAG_KV_STORAGE, a different database or a replaced volume therefore no longer silently moves your configuration.
  • New offline tools:
    • lightrag-rebuild-vdb re-embeds a workspace with the current model and records the new baselines. This is the way out after an intentional model change.
    • lightrag-migrate-config moves the configuration storage to a backend of another type, for example from JSON files to PostgreSQL.
    • lightrag-clear-storage clears a workspace offline, configuration records included.
  • Several servers, one WORKING_DIR: supported when each server has its own WORKSPACE and port. A second server on the same workspace is refused where the filesystem supports file locks.

For more information, see:

  • docs/LightRAG-API-Server.md: Configuration Storage Migration Between Backend Types
  • lightrag/tools/README_REBUILD_VDB.md, README_MIGRATE_CONFIG.md, README_CLEAR_STORAGE.md
  • docs/design/ConfigurationStorageDesign.md: the design overview

2. Safer graph writes and document deletion

  • Manual graph edits (create / edit / delete / merge entities and relations, insert_custom_kg) are now serialized against each other and against the ingestion pipeline on NetworkXStorage.
  • Commit ordering for entity/relation create, edit, merge and rename was reworked to prevent data loss when an operation is interrupted.
  • Interrupted document deletions are visible and retryable.
  • New lightrag-repair-chunk-tracking tool removes orphan chunk-tracking rows left behind by an interrupted deletion.

3. PostgreSQL storage defaults

The setup wizard now generates PostgreSQL from the official pgvector/pgvector image and offers PGTableGraphStorage (plain tables, no Apache AGE) for the graph. PGGraphStorage (AGE) and the Redis storages (RedisKVStorage, RedisDocStatusStorage) are deprecated. They keep working and log a warning at startup.

4. Security hardening and new provider

  • The Ollama-compatible /api/* routes are protected by LIGHTRAG_API_KEY (see Breaking Changes).
  • PDF extraction runs pypdf in a resource-limited child process.
  • Streamed error lines no longer echo raw provider exception text.
  • New openai_responses LLM binding for the OpenAI Responses API.

Breaking Changes

  • Python 3.11 or later is required. Python 3.10 is no longer supported. The Docker images (Python 3.12) are not affected.
  • Changing the embedding model on an existing workspace now refuses startup, where it used to serve wrong or empty results. Either restore the previous EMBEDDING_MODEL / EMBEDDING_DIM, or run lightrag-rebuild-vdb to re-embed with the new model.
  • Changing LIGHTRAG_KV_STORAGE after the first v1.5.8 start is refused while LIGHTRAG_CONFIG_STORAGE is unset, because the configuration storage would silently move with it. Either set LIGHTRAG_CONFIG_STORAGE to the anchored backend explicitly, or move the configuration with lightrag-migrate-config.
  • Ollama routes require the API key. When LIGHTRAG_API_KEY is set and WHITELIST_PATHS is unset, /api/* requests without the key now get HTTP 403. In Open WebUI, the lightrag:latest model disappears from the list. Fix: enter the key as the API key of the Ollama connection (sent as Authorization: Bearer <key>), or set WHITELIST_PATHS=/health,/api/* to keep the old behaviour.
  • POST /documents/clear_cache is removed. Use DELETE /documents?clear_llm_cache=true instead. Clearing the LLM cache now happens together with the destructive clear.
  • Workspace names starting with $ are reserved. The server used to serve WORKSPACE=$team as _team. Set WORKSPACE=_team (the name your data is already stored under), and no data moves.

Upgrade Notes

  1. Back up first, then stop every old instance before starting v1.5.8. That includes all workers, servers sharing the storage, and maintenance tools. The first start creates the configuration container and binds the anchor. Do not do a rolling upgrade that leaves an old writer running.
  2. WORKING_DIR must persist, even if every storage is a database. It now holds config_storage_anchor.json, and for JSON configuration also <workspace>/kv_workspace_config.json. In Docker, keep it on a mounted volume. In Helm, keep persistence.enabled: true. An ephemeral WORKING_DIR loses the anchor and the JSON configuration on every restart. Include it in your backups.
  3. The embedding service must be reachable during the first start, so the adoption probe can record the baselines. Check the startup log for a WARNING that a baseline could not be established. If the start refuses with an embedding-space mismatch, your stored vectors do not match the configured model: fix the configuration, or run lightrag-rebuild-vdb.
  4. Redis users: with LIGHTRAG_KV_STORAGE=RedisKVStorage, the configuration storage defaults to JSON files in WORKING_DIR (see note 2). Redis storage is deprecated; plan a move to PostgreSQL.
  5. PGGraphStorage users: your deployment keeps working, and the wizard keeps the AGE-enabled image for it. To leave AGE, migrate the graph first (python -m lightrag.tools.migrate_graph_storage --apply, no re-indexing needed), then switch to PGTableGraphStorage and the pgvector image.
  6. Optional: to keep the configuration in your database instead of JSON files, run lightrag-migrate-config --target-backend PGKVStorage (or MongoKVStorage / OpenSearchKVStorage) with every server stopped. Then set LIGHTRAG_CONFIG_STORAGE to that backend.
  7. To start over with a new embedding model, use lightrag-clear-storage rather than deleting files by hand. If you do delete files by hand, also remove kv_workspace_config.json and config_storage_anchor.json. Otherwise the recorded baseline refuses the new model.
  8. TOKEN_SECRET should be a random value of at least 32 bytes (for example, openssl rand -hex 32). The upgraded PyJWT warns about shorter secrets.
  9. Streamed error messages are generic. A failure in the middle of a stream on /query/stream, /api/generate or /api/chat now reads Internal server error (error_id: …), and no longer contains the LLM provider’s exception text. The stream format is unchanged. Look up the details in the server log by that error_id. A client that parsed provider error text from the stream (for example, to detect rate limits) needs to be updated.
